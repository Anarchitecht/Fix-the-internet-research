## NAT traversal and reachability: a relay-introduced, timing-synchronized simultaneous connection attempt, with the relay kept as the session's fallback path, is the only mechanism in this corpus measured at internet scale

### Candidates

| **A. Bare rendezvous hole punching, no persisted fallback** — a rendezvous server introduces two NATed (Network-Address-Translated) peers, who each send a packet toward the other's reported address; the server plays no further role once the path opens | 82% of tested devices support UDP (User Datagram Protocol) hole punching, 64% support TCP (Transmission Control Protocol) — 380 volunteer-submitted data points, 68 vendors [FORD-USENIX-05]. Among a deployed peer population classified compatible, first-attempt success is only ≈41% for an asymmetric pair and 85% even for the most favorable pair type — field trial of 646-2,000 peers [HALKES-NETWORKING-11]. A punched mapping needs a keepalive at intervals ≤ ≈55 s to stay open [HALKES-NETWORKING-11] | None of its own; the calling application must authenticate every inbound packet, since a stray host sharing the peer's private-address pool can otherwise be mistaken for the intended peer [FORD-USENIX-05] | Fails permanently, with nothing to fall back to, whenever a NAT is Endpoint-Dependent-Mapping (symmetric) — 11% to over 40% of a NATed population depending on cellular versus fixed access [RICHTER-IMC-16] — or when a multi-level NAT stack lacks hairpin translation, measured present in only 24% (UDP) / 13% (TCP) of tested devices [FORD-USENIX-05] | A rendezvous server reachable by both peers before the session starts; nothing afterward [FORD-USENIX-05; DUARTE-ABAKOS-20] |

Relay-introduced, timing-synchronized hole punching, relay retained as fallback path (the DCUtR / Circuit-v2 pattern)** — both peers first hold a reservation on a resource-capped relay; one peer dials the other directly if it looks publicly reachable, and otherwise both peers time a simultaneous outbound attempt using the relay-measured round-trip time; if the attempt fails, the session stays on the relay | Conditional hole-punch success 70% ± 7.1% — 6.25 million attempts, December 2022-January 2023 [TRAUTWEIN-ARXIV-26]. Conditional on the relay-reservation-and-address-discovery step already succeeding, which itself fails ≈29% of attempts [TRAUTWEIN-ARXIV-26]. TCP and QUIC (Quick UDP Internet Connections) succeed at statistically indistinguishable ≈70% rates once timing-synchronized [TRAUTWEIN-ARXIV-26]. A controlled testbed forcing Endpoint-Independent-Mapping NATs only: punching completes in ≈55 ms (QUIC) / ≈56 ms (TCP) at 20 ms round-trip time, rising to ≈416 ms / ≈505 ms at 200 ms round-trip time [LIANG-ARXIV-24] | The relay honors whatever duration/data limit it advertises — the specification's own default is no limit unless the operator sets one [VYZOVITIS-SPECS-23]. Reservation vouchers are advisory, not enforced [VYZOVITIS-SPECS-23]. Both peers disclose their public address to the initiator and to the relay during setup, which can observe and correlate both parties' addresses and timing [TRAUTWEIN-ARXIV-26] | Degrades to a durable relayed session, not total failure, whenever the reservation/discovery precondition fails (≈29%) [TRAUTWEIN-ARXIV-26], the NAT on one or both sides is symmetric, or the two peers' one-way delays are significantly asymmetric, which shrinks the synchronization margin [TRAUTWEIN-ARXIV-26] | A relay [VYZOVITIS-SPECS-23] reachable by both peers and willing to hold a bounded reservation before punching begins; a self-reachability discovery step; a transport supporting near-simultaneous outbound attempts (TCP simultaneous open or QUIC) |

Data-plane throughput collapses to the relay path's own bottleneck: 9.28 Mbps measured against 88.49 Mbps for a direct/reversal path under a 10 Mbps-vs-100 Mbps bottleneck asymmetry — an 89% reduction [DUARTE-ABAKOS-20]. An economically incentivized variant adds ≈$0.40-$0.60 per client-side session and ≈$0.10-$0.20 per relay-side session in transaction charges, plus a one-time ≈$1.34-$2.68 deployment charge — April 2020 Ethereum gas prices, a private test blockchain, not the public network [KEIZER-MOBIHOC-20] | Relay trusted not to correlate or tamper with traffic; TURN's (Traversal Using Relays around NAT) Send/Data messages carry no authentication [REDDY-RFC-20]. The fully general symmetric case is derived, not measured: ≈54,000 packets for 50% collision probability, ≈170,000 for 99.9%, and a pure two-sided brute force at ≈21 hours, all computed from one assumed national median connection speed [KANARIS-ARXIV-23] | None stated; the mechanism is itself a high-volume probing burst against the target NAT's own connection-state table | Fully random port allocation defeats prediction outright — measured in 19 of 72 cellular carriers (26.4%), a behavior the source paper states "cannot be handled by most existing NAT traversal schemes" [WANG-SIGCOMM-11]. A single residence's external IPv6 byte-fraction carries a daily standard deviation exceeding 15% [VALAPU-ARXIV-25]. Where an IPv6-only client must reach an IPv4-only destination, the NAT64 bridge needed is present on only ≈4% of tested paths and adds a measured 23.13% more hops and 17.47% higher round-trip time than native IPv4 when present [BOSWELL-ARXIV-24] | None beyond ordinary IPv6 routing; an unconditionally reachable IPv6 host has a different exposure profile than a NATed host, a consequence this corpus does not separately measure for residential router defaults | Either participant is IPv4-only, or sits on a network without IPv6 deployment — the large majority of the population measured as sitting behind Carrier-Grade NAT [RICHTER-IMC-16; LIVADARIU-INFOCOM-18], a condition those papers tie to IPv4 address scarcity, independent of that same network's own IPv6 status | Nothing, when IPv6 is present on both sides; a NAT64/DNS64 translator, or one of the other rows here, when it is absent on either side |

A client following 3.5 million follower edges wastes a measured 98.2% of its download traffic (144 TiB) absent a relay-selection step, because it fetches every followed user's posts from every relay it shares with that user [WEI-PACMNET-25]. ### Selection

Select row B: a relay introduces two peers, each learns its own externally observed address, one peer attempts a direct dial if the other looks publicly reachable, and otherwise both peers time a simultaneous outbound connection attempt from the relay-measured round-trip time; if that attempt fails, the session continues over the relay rather than terminating. This is the mechanism libp2p ships as DCUtR (Direct Connection Upgrade through Relay), built on the Circuit-v2 relay specification, and it is the only mechanism in this corpus with a success rate measured on a real, geographically distributed peer population rather than in a laboratory testbed or as an arithmetic projection [TRAUTWEIN-ARXIV-26; VYZOVITIS-SPECS-23].

**Against A (bare hole punching, no fallback).** Row A and row B are close to the same mechanism at the moment of punching — FORD-USENIX-05's own connection-reversal-and-punch procedure is what DUARTE-ABAKOS-20 measures as comparably low-overhead, and TRAUTWEIN-ARXIV-26's ≈70% figure is not obviously higher than HALKES-NETWORKING-11's own ≈80% figure for eligible pairs. The difference is what happens on the ≈30% of attempts that fail. Row A has nothing left to try: HALKES-NETWORKING-11 measures ≈79% of the peer population as not directly connectable without traversal, and a punch that does not land there ends the session. Row B's relay never stops carrying the session, so a punch failure in TRAUTWEIN-ARXIV-26's data is a latency and bandwidth cost, not a connectivity failure [TRAUTWEIN-ARXIV-26 vs. FORD-USENIX-05; HALKES-NETWORKING-11].

**Against C (relay-only, mandatory).** Row C guarantees connectivity independent of NAT type, which row B does not fully match — TRAUTWEIN-ARXIV-26's own 29% prerequisite-failure figure is a case where row B needs C's relay path anyway. But DUARTE-ABAKOS-20 measures exactly what row C loses when it is the only path: a bandwidth-constrained relay collapses session throughput to 9.28 Mbps against an 88.49 Mbps direct/reversal alternative, an ≈89% reduction, and that reduction applies to every session, not only the ≈30% a punching attempt would otherwise resolve. Row B pays row C's cost only on the minority of sessions punching does not resolve; row C pays it on all of them. KEIZER-MOBIHOC-20's incentive layer addresses who funds row C's relay bandwidth, not this throughput ceiling, so it does not change the comparison [DUARTE-ABAKOS-20 vs. VYZOVITIS-SPECS-23, TRAUTWEIN-ARXIV-26].

**Against D (port prediction).** WANG-SIGCOMM-11's own field-validated port-prediction technique reaches 80% success in 12 seconds against one specific NAT subtype (a measured, linear, time-dependent port increment), found in only 8 of 72 carriers studied — a narrower population than row B's 70% figure, which TRAUTWEIN-ARXIV-26 measured across 859 client networks in 39 countries without restricting to one NAT subtype. Against the fully general symmetric case, KANARIS-ARXIV-23 has no field measurement at all, only a derived packet count, and that same paper notes the probe burst risks exhausting a router's own connection table before succeeding — a cost row B's timing-based synchronization does not carry, since TRAUTWEIN-ARXIV-26 measures a coordination exchange under 500 bytes per direction rather than tens of thousands of probe packets [WANG-SIGCOMM-11; KANARIS-ARXIV-23 vs. TRAUTWEIN-ARXIV-26].

**Against E (IPv6 direct addressing).** Row E, where available, removes the reachability problem at zero ongoing cost, and nothing in row B contradicts adding an IPv6 host candidate to the address-discovery step B already performs. The comparison is availability, not mechanism: VALAPU-ARXIV-25 measures only 12.6% of popular web destinations as fully IPv6-reachable end to end nine years after CZYZ-SIGCOMM-14 first measured single-digit IPv6 reachability, and BOSWELL-ARXIV-24 measures the IPv4-bridging fallback (NAT64) as both rare (≈4% of tested paths) and materially slower when present. A design that relies on E alone has no basis in this corpus for treating it as sufficient for the near term; row B is what a session falls back to when E is unavailable, which the corpus shows is the common case [VALAPU-ARXIV-25; BOSWELL-ARXIV-24 vs. TRAUTWEIN-ARXIV-26].

**Against F (structural avoidance in routing/storage).** Row F and row B answer different questions and are not substitutes. STEINER-IMC-07 measures that excluding ≈40-50% of a deployed peer population from the DHT's (distributed hash table's) own serving role works for that role specifically — a lookup can always be satisfied by a reachable holder of the same key. It supplies nothing when the object needed, or the session needed, belongs specifically to one currently-online NATed peer, which is exactly the case row B is measured against. A system can and should combine both: F reduces how often a session needs row B by preferring reachable holders when several exist, but does not remove the need for B when only one, NATed, holder exists [STEINER-IMC-07 vs. TRAUTWEIN-ARXIV-26].

**Against G (structural avoidance at the application layer).** Row G is measured, in WEI-PACMNET-25's Nostr dataset, to work well for what it is built for: publish-and-poll social content stays 80-90% available after removing a large fraction of relays or hosting networks. It is not built for, and WEI-PACMNET-25 does not measure it performing, a live session between two specific participants — every interaction in that architecture is asynchronous, mediated by a relay's storage. It also carries a directly measured cost the architecture under design here would inherit for every content type it applies to: 34.6x replication per post and 98.2% wasted download traffic absent a relay-selection mechanism [WEI-PACMNET-25]. Row G is a legitimate design for content publication and discovery; it is not a candidate that answers "how does a NATed participant become reachable for a session," because it declines to open sessions [WEI-PACMNET-25 vs. TRAUTWEIN-ARXIV-26].

**Against H (UPnP/NAT-PMP/PCP).** No comparison is possible on measured grounds; row H has no dedicated evidence entry in this corpus. The one available data point — TRAUTWEIN-ARXIV-26's finding that self-reported port-mapping correlates with higher Connection Reversal effectiveness — is consistent with including a port-mapping attempt as a cheap first step ahead of row B's punching sequence, since a successful mapping request removes the need for punching entirely, but this corpus supplies no success-rate, latency, or Carrier-Grade-NAT-availability figure for the mapping protocols themselves, so this remains an unevaluated addition rather than a selected alternative.

### What this selection requires from the rest of the system

- **Ordering.** The system must sequence, not parallelize arbitrarily: (1) obtain a relay reservation and confirm the relay holds it, (2) run a self-reachability/address-discovery step (an Identify/AutoNAT-equivalent) so each peer knows its own externally observed address, (3) attempt a direct dial if the target peer's discovered address looks publicly reachable, (4) failing that, exchange candidate addresses and a relay-measured round-trip time over the existing relayed connection and time a simultaneous outbound attempt from that measurement, (5) on failure of steps 3-4, keep the relayed connection as the session's path rather than terminating it [VYZOVITIS-SPECS-23; TRAUTWEIN-ARXIV-26].
- **Participant honesty assumed.** The relay is assumed to enforce whatever duration/data limit it advertises rather than relaying unboundedly — the specification's default is no limit unless the operator configures one, so a production deployment must not leave this field unset [VYZOVITIS-SPECS-23]. The relay is assumed not to deliberately delay or corrupt the coordination exchange, since the timing synchronization degrades under path asymmetry that a congested or adversarial relay can induce, and TRAUTWEIN-ARXIV-26's residual ≈30% failure rate is partly attributed to exactly this [TRAUTWEIN-ARXIV-26].
- **What another component must supply.** (a) A discovery mechanism publishing which relay or relays a given peer currently holds a reservation with — the relay specification states this is out of scope and names a distributed hash table or a rendezvous point only as examples [VYZOVITIS-SPECS-23]. (b) An admission or Sybil-resistance layer for relay operators, since an unauthenticated relay population is exactly the address-and-timing-correlation exposure TRAUTWEIN-ARXIV-26 and VYZOVITIS-SPECS-23 both state as a property of this mechanism, not a flaw to be fixed within it. (c) An application-layer authentication step for the first packets on a freshly punched path, since punching alone does not distinguish the intended peer from a stray host sharing the same private-address pool [FORD-USENIX-05].
- **What must be observable.** Each peer must be able to read its own externally observed address (Identify or STUN, Session Traversal Utilities for NAT) and the relay-measured round-trip time, since the synchronization wait time is computed directly from that measurement [TRAUTWEIN-ARXIV-26]. The calling system must be able to observe punch outcome (success or failure) per attempt, to drive the retry policy and to trigger the fallback-to-relay path on exhaustion [TRAUTWEIN-ARXIV-26].

### What it costs and where it fails

Conditional hole-punch success measures at 70% ± 7.1% across 6.25 million attempts spanning 859 client networks in 39 countries, December 2022-January 2023 [TRAUTWEIN-ARXIV-26]. That figure is conditional on the relay-reservation-and-address-discovery step already succeeding, which itself fails on ≈29% of attempts, so the unconditional success rate from a cold start is lower than 70% — though those failures degrade to a relayed session rather than to no session at all [TRAUTWEIN-ARXIV-26]. Coordination overhead is under 500 bytes per direction across two relay round trips; 97.6% of successful punches complete on the first of up to three attempts [TRAUTWEIN-ARXIV-26]. Once a direct path opens, its round-trip time falls to 70% or less of the pre-punch relayed round-trip time for half of measured peers [TRAUTWEIN-ARXIV-26].

The mechanism stops resolving to a direct path — falling back permanently to the relayed session — under three measured conditions: the NAT on one or both sides is symmetric (Endpoint-Dependent-Mapping), since TRAUTWEIN-ARXIV-26's outcome-only measurement cannot isolate this cause but RICHTER-IMC-16 measures symmetric mapping present in 11% of non-cellular Carrier-Grade-NAT Autonomous Systems and ≈40% of cellular ones; the relay-reservation or address-discovery precondition fails outright (≈29% of attempts) [TRAUTWEIN-ARXIV-26; VYZOVITIS-SPECS-23]; or the two peers' one-way path delays are significantly asymmetric, shrinking the synchronization margin the timing calculation depends on [TRAUTWEIN-ARXIV-26]. In every one of these cases the session continues on the relay, at the relay's own bandwidth ceiling — measured elsewhere in this corpus at up to an 89% throughput reduction under a constrained relay path [DUARTE-ABAKOS-20] — rather than failing outright.

### What the corpus does not settle

- **No entry measures the composite including an IPv6 host-candidate check.** Adding IPv6 direct addressing as a first-tried candidate ahead of relay-mediated punching is a natural extension of the address-discovery step row B already performs (analogous to the host-candidate step already defined in ICE, Interactive Connectivity Establishment [KERANEN-RFC-18]), but no entry in this corpus measures that specific combined pipeline's success rate or latency; VALAPU-ARXIV-25 and TRAUTWEIN-ARXIV-26 measure their respective mechanisms separately, never composed.
- **No entry reports what duration/data caps production relay operators actually set.** VYZOVITIS-SPECS-23 states the specification carries no default; TRAUTWEIN-ARXIV-26's 212 volunteer clients used relays whose configured limits are not reported in that paper. A builder needs an operational survey or a chosen, explicitly labeled default — not a figure this corpus supplies.
- **No entry separates the residual ≈30% failure rate by cause.** TRAUTWEIN-ARXIV-26 states directly that its outcome-only measurement cannot distinguish a genuinely unresolvable symmetric-NAT pair from a synchronization-margin failure caused by path asymmetry, nor can it distinguish a single NAT layer from an added Carrier-Grade NAT layer. A builder cannot derive, from this corpus, what fraction of failures a better synchronization formula (such as the refined, undeployed formula TRAUTWEIN-ARXIV-26's own §7.2 proposes) would actually recover.
- **No entry measures relay-operator sustainability for the unpaid, volunteer-run Circuit-v2 model this selection depends on.** VYZOVITIS-SPECS-23 states running a relay "proved to be an expensive proposition requiring dedicated hosts" but supplies no cost figure; KEIZER-MOBIHOC-20 measures an alternative, compensated relay design's transaction charges, not this one's operating cost, and its own evaluation runs on a private test blockchain, not a production deployment at any measured scale.
- **No entry measures residential or mobile router default behavior toward an unsolicited inbound IPv6 connection specifically.** Row E's "zero cost when available" claim assumes a dual-stack peer is reachable once an IPv6 address is confirmed; whether typical customer-premises equipment blocks unsolicited inbound IPv6 by default, the way NAT incidentally does for IPv4, is not measured by any entry in this corpus — a builder needs this figure before treating E's low measured translation overhead as equivalent to low measured reachability.
