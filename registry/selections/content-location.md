## Content location: S/Kademlia's disjoint-path lookup and puzzle-derived identifiers close the eclipse an unmodified Kademlia deployment already suffered on a live network

A content-location mechanism lets a participant, holding only a key, determine which other participant currently holds the item that key names, using state and messages proportional to the size of the whole network, not the whole network itself. Every candidate below does this by giving each participant an identifier from the same space as the keys and forwarding a lookup, hop by hop, toward whichever known participant's identifier is closest to the target key under some distance function.

### Selection

S/Kademlia — Kademlia's XOR-metric routing-table structure and bucket-based state, with disjoint-path lookup and crypto-puzzle-derived node identifiers added — is selected.

Against plain Kademlia: plain Kademlia has the strongest live-deployment evidence in the entire corpus for this component — hundreds of thousands of nodes, multi-year IPFS measurement showing sub-second median lookups and 99% of lookups completing under 18 hops [`CORTESGOICOECHEA-ARXIV-24`, `TRAUTWEIN-SIGCOMM-22`] — but that same live-deployment evidence, on a different Kademlia network (KAD), shows plain Kademlia's identity assumption fails outright: an attacker holding as few as 8 identities eclipsed a keyword completely on a several-million-peer live network, because any node's self-reported identifier is accepted without cost [`STEINER-CCR-07`]. S/Kademlia is preferred because it keeps Kademlia's proven-at-scale routing-table structure while adding exactly the missing cost (a computational puzzle per identifier) and exactly the missing redundancy (multiple disjoint lookup paths) that the demonstrated attack exploited.

Against Chord: at 20% malicious nodes under the same routing-success model, fixed-base Chord reaches only 42% success, the worst-performing geometry the model was applied to, because Chord's larger hop count under a small digit base gives an adversary more chances per lookup to sit on the path [`CASTRO-OSDI-02`]. Chord's own paper documents no defense beyond hashing identifiers from IP addresses, calling this only a hardening, not a fix [`STOICA-SIGCOMM-01`]. S/Kademlia's disjoint-path test and puzzle cost address the same identifier-forgery weakness structurally rather than incidentally.

Against Pastry with the Castro et al. secure-routing extension: the extension reaches over 99.9% routing success for f ≤ 0.18–0.25, better than S/Kademlia's stated 20%-adversary figure in raw success rate, but only by adding an external certification-authority infrastructure that issues and revokes per-node certificates bound to IP address — the paper's own words state this evaluation was performed "only in the context of Pastry," and the CA-based identity assumption reintroduces exactly the single-point-of-trust the rest of this architecture is designed to avoid [`CASTRO-OSDI-02`]. S/Kademlia's puzzle-based identity cost achieves comparable order-of-magnitude adversary resistance (99% at 20% adversarial, versus Pastry's 99.9% at 18–25%) without a certificate authority.

Against Tapestry: the same external-PKI identity dependency appears, stated directly by Tapestry's own authors as the mechanism's Sybil defense [`ZHAO-JSAC-04`]. Tapestry additionally shows the sharpest documented live-versus-simulator gap in this corpus — near-100% success in simulation against roughly 5% real-world query failure on PlanetLab under matching fault conditions [`ZHAO-JSAC-04`] — which argues for weighting live-network Kademlia figures (already available for the selected mechanism's base structure) over simulator-only figures wherever both exist.

Against CAN: CAN's own authors call adversary resistance "a particularly hard problem" and describe no defense at all, stating a malicious node "can act, not only as a malicious client, but also as a malicious server or router" [`RATNASAMY-SIGCOMM-01`]. At matched per-node connection counts, CAN also routes in more hops than Kademlia-family and ring/prefix designs [`MANKU-USITS-03`].

Against constant-degree designs (Koorde, Viceroy): Koorde's own proof rules the whole family out for this architecture, independent of any specific implementation — any network with maximum node degree below Ω(log n) cannot stay connected with constant probability once nodes fail independently at probability 1/2, so a true constant-degree design "cannot be fault tolerant against nodes failing with constant probability" [`KAASHOEK-IPTPS-03`]. Viceroy's own model excludes node failure and concurrent joins/leaves entirely by assumption [`MALKHI-PODC-02`]. Neither paper reports any implementation or simulation measurement, only proved bounds [`KAASHOEK-IPTPS-03`, `MALKHI-PODC-02`], so this exclusion rests on a structural proof, not a comparative cost figure.

Against Symphony: Symphony's own evaluation explicitly assumes cooperative, non-adversarial nodes throughout and supplies no identity-cost or adversary-resistance mechanism [`MANKU-USITS-03`], leaving the same identifier-forgery vulnerability S/Kademlia was built to close.

Against one-hop/two-hop full-membership routing: the Gupta-Liskov-Rodrigues design achieves lower hop count (99.99% of queries in ≤2 hops) [`GUPTA-NSDI-04`] but supplies no identity cost or adversary model anywhere in the paper, and its recovery from failure depends on background query volume happening to hit stale entries — a mechanism that stalls at low query rates for the full simulated window [`GUPTA-NSDI-04`]. It also concentrates load on an unspecified "supernode" selection mechanism, an availability and capture risk the paper does not analyze [`GUPTA-NSDI-04`]. Kelips, the gossip-affinity-group alternative in the same family, was never retrieved as a primary source in this corpus; the only figure available is a competing-paper's characterization of its convergence time exceeding an hour at 10⁵–10⁶ nodes [`GUPTA-NSDI-04`], not evidence this synthesis can rely on directly.

Against Whanau / the Sybil-proof one-hop DHT: this family has the strongest Sybil-resistance evidence in the corpus — correctness proved to depend only on attack-edge count, not identity count, validated against real multi-million-edge social graphs [`LESNIEWSKI-LAAS-NSDI-10`] — and is preferable to S/Kademlia wherever a fast-mixing honest social graph already exists as a byproduct of identity in the target deployment. It is not selected as the general-purpose mechanism because that graph is an external precondition this content-location layer cannot itself supply, SETUP is a synchronized, network-wide rebuild rather than an incremental per-node operation [`LESNIEWSKI-LAAS-NSDI-10`], and the mechanism supplies no result integrity of its own [`LESNIEWSKI-LAAS-NSDI-10`]. Where the rest of this architecture's identity layer does produce such a graph, Whanau is the better-supported choice for that deployment; this is a candidate for a follow-up composition check against whatever identity mechanism is selected elsewhere, not a rejection on cost grounds.

Against delegated lookup with client-side verification: no entry in this corpus evaluates this mechanism. Selecting it would not be a selection under this document's own rule — it is a guess, and this document does not make it. It is retained in the candidates table, marked as having no evidence, because the architecture may still need it as an open problem for a future retrieval pass, particularly for constrained clients unable to hold routing-table state at all.

### What this selection requires from the rest of the system

- An identity or key-issuance mechanism elsewhere in the system must produce the public key each node's identifier is derived from; S/Kademlia's added cost is a computational puzzle solved once per identifier, not a substitute for that key's own provenance.
- Every lookup issues d ≥ 2 independent, disjoint paths simultaneously (S/Kademlia recommends d=4–8), so any bandwidth budgeting elsewhere in the system for the content-location layer must multiply single-path Kademlia's bandwidth by d, not assume single-path cost.
- Bulk content publication (a single node calling provide() for a large batch of items, as Ethereum's Data Availability Sampling design would) must be spread across many originating nodes or amortized over more than one round, because a single seeder's own routing-table contacts become the throughput bottleneck regardless of the disjoint-path defense, which addresses lookup security, not provide() throughput [`CORTESGOICOECHEA-ARXIV-24`].
- The storage or replication component must supply its own value durability and integrity; content location resolves "who holds this key" and returns whatever that holder currently serves, and provides no guarantee the value is authentic or current beyond what a self-certifying object identifier (a content hash or signature checked by the caller) supplies. Kademlia's own evidence entries in this corpus never claim otherwise, and Whanau's entry states this limitation explicitly for the same DHT family [`LESNIEWSKI-LAAS-NSDI-10`].
- A churn-recovery discipline must be selected alongside routing-table structure: the strongest churn evidence in the corpus (Bamboo versus FreePastry versus Chord) argues for reactive per-neighbor failure recovery combined with TCP-style or Vivaldi-coordinate round-trip-time timeout estimation, not a fixed timeout or periodic-only recovery [`RHEA-USENIXATC-04`] — measured on Pastry's geometry, not Kademlia's, so this is a transferred requirement, not a directly measured one for the selected mechanism.
- Any deployment expecting to publish or retrieve DankSharding-scale item counts (hundreds of thousands of keys per publishing round) within a fixed per-round deadline must either shard publication across many nodes or accept that single-node Kademlia-family provide() cannot meet a 12-second-class deadline at that scale [`CORTESGOICOECHEA-ARXIV-24`].

### What it costs and where it fails

Base routing cost, inherited from Kademlia and confirmed at IPFS's live scale: median lookup under 1 second, 99% of lookups under 18 hops, at hundreds of thousands of active nodes with a 256-bit keyspace and k=20 bucket size [`CORTESGOICOECHEA-ARXIV-24`, `TRAUTWEIN-SIGCOMM-22`]. S/Kademlia's disjoint-path addition multiplies per-lookup bandwidth by d (4–8 recommended), a cost this corpus does not hold measured together with IPFS-scale conditions — the 99%-at-20%-adversarial figure comes from Baumgart & Mies' own paper, held here only as BRIEF §7's compressed summary, not as a full evidence-file entry stating node count, topology, or churn model.

It fails, by the security model it targets, once the fraction of colluding malicious nodes exceeds what its recommended d and k parameters were tuned for; adaptive k=2d is documented as worse than a fixed k=16, because shorter routing tables lengthen the paths an adversary can intercept (BRIEF §7). It fails independently, by the corpus's live-network evidence, if node-identifier issuance is not actually gated by the puzzle — plain Kademlia's demonstrated 8-identity eclipse on KAD [`STEINER-CCR-07`] is precisely the failure mode the puzzle exists to close, so any implementation gap in enforcing puzzle verification reopens that attack. It fails on publication throughput, independent of the security mechanism entirely, once a single node must announce more items per round than its routing-table contacts can absorb within the round's deadline [`CORTESGOICOECHEA-ARXIV-24`].

### What the corpus does not settle

- No entry in this corpus reports S/Kademlia's node count, topology, churn model, or run count — the 99%-at-20%-adversarial figure and the d/k recommendations are held only as BRIEF.md §7's compressed summary of a paper marked "read in full" outside this evidence-collection pass. A builder needs the primary paper's actual experimental conditions, not this summary, before treating the 99% figure as load-bearing.
- No entry measures S/Kademlia, or any Kademlia secure variant, against a live deployment; every live-network figure in this document (`CORTESGOICOECHEA-ARXIV-24`, `TRAUTWEIN-SIGCOMM-22`, `COSTA-DAIS-23`, `STEINER-CCR-07`) describes plain, undefended Kademlia deployments (IPFS or KAD). Whether disjoint-path lookup and puzzle-gated identifiers preserve IPFS-scale latency at IPFS scale, rather than only at the smaller scales simulated in the secure-Kademlia literature, is unmeasured here.
- No entry in this corpus combines S/Kademlia's identity-cost and disjoint-path mechanism with R/Kademlia's recursive-routing mode or with Kadabra's adaptive bucket selection. Each is measured only against plain Kademlia or against each other's baselines [`HEEP-ATNAC-10`, `ZHANG-FC-23`]; whether Kadabra's exploration threshold ρ and S/Kademlia's disjoint-path count d can be tuned jointly without one undermining the other is not established anywhere in this corpus.
- No entry measures eclipse-attack cost against IPFS's actual live Kademlia deployment specifically — `STEINER-CCR-07`'s 8-identity figure is from KAD (eMule/aMule), a different deployment of the same protocol family with a different bucket size, key length, and transport. Whether IPFS's larger k=20 buckets and 256-bit keyspace raise or lower the attacker-identity count needed for the same eclipse is not measured in this corpus.
- No entry establishes a derivation for the value of d (disjoint-path count) or k (bucket size) as a function of an assumed adversary fraction for this architecture's own expected node population and churn rate; BRIEF §7's d=4–8, k=8–16 are the original paper's own recommendations, not values derived here from this system's parameters, and must be labeled a pick, not a derivation, if carried forward.
- No entry in this corpus evaluates delegated lookup with client-side verification as a distinct mechanism. This is a genuine gap, not merely an unretrieved paper the escalation ladder in BRIEF.md §3.1 would resolve — a further retrieval pass targeting light-client and SPV-style (simplified-payment-verification-style) lookup designs is needed before this candidate can be compared on evidence rather than left blank.
