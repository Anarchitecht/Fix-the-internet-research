### Selection

The selection is composed by participant class, because no single mechanism is reachable from every participant this architecture must connect. WebRTC data channels (SCTP over DTLS, negotiated by ICE with STUN and TURN fallback) carry every connection where at least one side is an unprivileged browser tab. QUIC carries every connection between two socket-capable processes — a native mobile app, a desktop client, a relay or seed node — falling back to TCP exactly where QUIC's own discovery procedure already falls back to it: when the QUIC handshake is blocked or exceeds the path MTU. Onion-routed multi-hop encapsulation is a separate, user-selectable privacy tier layered on top of whichever of the above carries the actual bytes, not a default path for every connection.

**Against TCP as the general-purpose default (not merely QUIC's fallback):** [KAKHKI-IMC-17] found QUIC outperforms TCP on page load time in nearly every desktop scenario tested across a 5-100 Mbps / 0-100ms-RTT / 0-1%-loss matrix, and [LANGLEY-SIGCOMM-17] measured an 8.0%/3.6% mean search-latency reduction and an 18.0%/15.3% rebuffer-rate reduction (desktop/mobile) for QUIC against TLS/TCP at production scale (over 1 billion samples). QUIC's connection migration — surviving an IP-address change without a new handshake [LANGLEY-SIGCOMM-17] — matches a mobile participant switching from Wi-Fi to cellular without losing an open connection, a property TCP structurally lacks. TCP is retained only as a fallback, because [KAKHKI-IMC-17] also found TCP measurably outperforms QUIC under packet reordering (9% measured on live Verizon 3G) specifically because QUIC's fixed NACK threshold of 3 false-triggers loss detection where TCP's adaptive DSACK-based threshold does not — a condition a mobile participant on cellular data will encounter, so eliminating TCP entirely would remove the path that measurably performs better under that specific, common condition.

**Against WebTransport as the browser-facing candidate (instead of WebRTC data channels):** no entry in this corpus measures WebTransport's connection-establishment success rate, latency, or peer reachability — it is listed with no evidence. Independent of that gap, WebTransport's connection shape (a client validating a named server's certificate) does not perform the multi-candidate address exchange between two browser tabs that WebRTC's ICE machinery performs. A design whose client "reproduces the functional patterns of the most-visited websites" and has "no functional reason to return to a centralized service" needs arbitrary browser-tab-to-browser-tab connectivity; a mechanism shaped for client-to-known-server connectivity cannot supply that without introducing a server role for every pair, which is a structural mismatch this corpus does not quantify but which follows directly from the two mechanisms' differing connection models.

**Against onion-routed transport as the default path (rather than a tier):** [DINGLEDINE-USENIXSEC-04]'s own measurement shows a median page-fetch latency of 2.8s through a 32-relay network against 0.3s direct — roughly a 9x latency multiple — and the same paper's authors state their own threat model excludes a global passive adversary, the exact class of adversary a user who chooses this tier is defending against. Running every connection through this multiple by default is incompatible with reproducing the functional patterns of the most-visited websites; a user who does not face a global passive adversary pays the 2.8s median unnecessarily if it is the default rather than a choice, which is why [DINGLEDINE-USENIXSEC-04]'s own stated non-goal (no protection against a global passive adversary) is the deciding fact, not merely the latency number.

**Against QUIC or TCP as the sole default (excluding WebRTC entirely):** [SINGH-ARXIV-26]'s own implementation states directly that "web apps cannot create listening sockets in JavaScript," and the corpus contains no browser API exposing a raw UDP or TCP socket to page script — the only browser-reachable network mechanisms found in this corpus are WebRTC (`RTCPeerConnection`/`RTCDataChannel`) and WebTransport (rejected above). A default limited to QUIC or TCP would be unreachable from any participant running as an ordinary browser tab, which this architecture requires as its primary client shape.

### What this selection requires from the rest of the system

- The out-of-band signaling channel for a browser-tab participant's first WebRTC offer/answer exchange, since a tab cannot accept an unsolicited inbound connection [SINGH-ARXIV-26], must be supplied by whichever component handles peer discovery or introduction: a push-notification path, a rendezvous relay, or an already-open data channel from a prior connection.
- STUN and TURN server infrastructure reachable by every WebRTC participant must be provisioned by the NAT traversal component. [PETIT-HUGUENIN-RFC-18] states STUN Binding responses are unauthenticated by protocol design, so it is the NAT traversal component's connectivity-check step, not this transport selection, that a receiving side must trust before accepting a candidate address as valid.
- The identity/credential component must issue a long-term credential that a TURN relay authenticates against before granting a relay allocation [REDDY-RFC-20].
- Continuous per-connection keepalive traffic must be budgeted for the full lifetime of every open path, not only at setup, because NAT and firewall UDP bindings expire. [HALKES-NETWORKING-11]'s measured field data (a real peer population) recommends an interval no longer than 55 seconds — tighter than [KERANEN-RFC-18]'s specified-but-unmeasured 15-second minimum default — so the measured figure, not the protocol default, should set the budget.
- For a QUIC connection between two socket-capable participants, the receiving side must key connection state by Connection ID rather than the network 4-tuple for passive migration tolerance to hold [LANGLEY-SIGCOMM-17], and any component depending on active migration for continuity needs a full-reconnection fallback, since [BUCHET-CCR-25] measured migration succeeding for only 52% of IPv4 and 78% of IPv6 QUIC servers that had already completed a handshake with SNI supplied.
- The storage and content-delivery components built on top of this transport cannot assume uniform throughput across all reachable pairs: [HALKES-NETWORKING-11] measured roughly 15% of a real peer population unreachable even after hole punching, and [DUARTE-ABAKOS-20] measured relay-path throughput collapsing to the relay's own bottleneck (9.28 Mbps against an 88.49 Mbps direct/reversal path in a bandwidth-constrained scenario) for the population that falls back to relay.
- The naming/registry component must distribute a signed relay directory reachable by every client before a client can build an onion-routed circuit for the privacy tier [DINGLEDINE-USENIXSEC-04]; the transport layer does not supply this itself.

### What it costs and where it fails

The browser-facing half of this selection succeeds end-to-end for roughly the population [HALKES-NETWORKING-11] measured for UDP hole punching generally: about 21% of peers directly connectable plus up to 64% more reachable via hole punching at an 80%-or-higher pairwise success rate, leaving a minority on the order of 15% needing relay, at the throughput cost [DUARTE-ABAKOS-20] measured for a saturated relay path. This figure is corroborating, not WebRTC-specific evidence — [HALKES-NETWORKING-11]'s trial ran over a BitTorrent client's own UDP hole-punching implementation, not a browser's ICE stack, so it is directionally applicable to WebRTC (which performs the same class of mechanism) without being a direct measurement of it.

The socket-capable half of this selection (QUIC) fails to deliver its measured advantage on mobile handsets: [KAKHKI-IMC-17] measured QUIC spending 58% of connection time in an "Application Limited" congestion-control state on Nexus 6 and MotoG devices versus 7% on desktop, because QUIC's userspace packet processing cannot keep pace with TCP's kernel-resident processing — a mobile participant should not expect QUIC's desktop-measured latency and throughput gains to hold. QUIC's server-side cost also remains roughly double TLS/TCP's even after the cryptography, packet-reception, and state-handling optimizations [LANGLEY-SIGCOMM-17] describes, a cost every relay or seed node running this design pays per connection.

The onion-routing privacy tier's measured cost is the 2.8s median / 5.3s 90th-percentile page-fetch latency against 0.3s direct [DINGLEDINE-USENIXSEC-04], measured on a network roughly four orders of magnitude smaller (32 relays, a stated ~10,000-user design ceiling) than this architecture's likely user base. No entry in this corpus measures onion-routing latency at a larger relay population, so this figure should be treated as a floor for this design's actual privacy-tier latency, not a prediction of it.

### What the corpus does not settle

- No entry measures ICE/STUN/TURN connectivity success rates through an actual browser's WebRTC stack on a present-day (2020s) NAT and carrier-grade-NAT population at Internet scale. [HALKES-NETWORKING-11] (2011) and [FORD-USENIX-05] (2005) measure the same class of UDP hole-punching mechanism through a BitTorrent client, not a browser, and predate widespread carrier-grade NAT deployment; [RICHTER-IMC-16] (2016) measures CGN prevalence and NAT restrictiveness but not end-to-end WebRTC connection success.
- No entry measures the WebTransport browser API directly: its connection-establishment latency, its success rate, or a controlled comparison against WebRTC data channels for the same connectivity task is absent from this corpus.
- No entry measures onion routing at a relay count and user population matching this architecture's likely scale. [DINGLEDINE-USENIXSEC-04]'s own numbers come from a 32-relay network the authors designed for roughly 10,000 users; how the fixed 512-byte cell size and per-circuit congestion windows behave at a much larger relay population and user count is not measured here.
- [LIANG-ARXIV-24]'s QUIC-hole-punching timing figures (~55ms) were measured against a NAT ruleset the same paper's authors forced to Endpoint-Independent Mapping via `iptables`, which the paper states explicitly differs from the Address-and-Port-Dependent Mapping behavior they found on real NAT devices during preliminary testing — the measured figure applies to a NAT behavior the authors themselves say is not what they found in the field.
- [ENGELBART-ANRW-26]'s proposal to multiplex WebRTC's RTP and data-channel traffic over one QUIC connection (potentially resolving the bandwidth-unfairness problem between the two) carries no usable numeric result in this corpus — the retrieved source is an OCR transcript of presentation slides whose bandwidth/latency comparison exists only as unlabeled plots. It is a proposed evolution of the WebRTC data-channel candidate, not a measured or deployed one, and is not selected on that basis.
- No entry in this corpus gives a current, post-2020 measurement of the fraction of this architecture's actual target population reachable end-to-end via WebRTC/ICE. The best available connectivity figures ([HALKES-NETWORKING-11], [FORD-USENIX-05]) come from a self-selected file-sharing-client population 15-20 years old; [RICHTER-IMC-16]'s CGN-prevalence figures bound the problem (11% of non-cellular CGN autonomous systems and roughly 40% of cellular CGN autonomous systems show symmetric NAT mapping, the type hole punching cannot traverse) but do not themselves measure end-to-end connection success.
