## Privacy tiers: three independently cost-ordered ladders, one per action — fetch, query, message — and two named candidate families withheld from the ladders because their own measured cost is not reliable enough to offer a person as an informed choice

**Excluded outright: searchable encryption over the client's own stored index, as a query-content-privacy candidate.** [CASH-CCS-15]'s count attack recovers a client's queried keywords from access-pattern leakage alone — the least-revealing published leakage profile (L1) — using only public per-keyword document-count statistics, no known queries required; on the Enron corpus (30,109 documents, vocabulary swept 500-6,500 keywords) the worst tested trial failed to reconstruct only 5 of 650 keywords. [GRUBBS-SP-19] shows the same class of attack (order and value reconstruction from range-query access patterns) has a query count independent of the number of records or possible plaintext values — the attack does not get harder as the deployment scales. No tested operating point of searchable encryption in this corpus survives passive observation by the server it is stored on, so it is not offered as a tier: every published construction fails the requirement that a tier's stated adversary-defeated claim hold under the adversary the tier claims to defeat.

### Selection

Three ladders, ordered by measured cost within each, one per action a person takes. **Fetch** (retrieving one object from one peer): direct connection, then a 3-hop onion circuit with no padding, then the circuit plus WTF-PAD, then the circuit plus Tamaraw at its live-deployment operating point. **Query** (searching or reading a shared index without disclosing which record matched): direct query, then single-server computational PIR for a known index (Piano as the default instantiation), then Tiptoe for an unknown index needing ranked search. **Message** (point-to-point communication where the pattern of who-talks-to-whom is itself sensitive): direct message, then a mix network under a proven differential-privacy bound (Karaoke as the default instantiation for text, Yodel for real-time voice). Multi-server PIR, Stadium, and small-clique DC-net broadcast are offered as opt-in alternates within the Query and Message ladders, not as defaults, for the specific reasons given below. Wally is offered only as a background, non-interactive prefetch mode, never as an interactive Query tier. Searchable encryption is not offered at all.

**Against the deep-learning-tuned regularization family (RegulaTor, Surakav, Palette) as a Fetch tier.** [HOLLAND-POPETS-22]'s own live pluggable-transport deployment measured RegulaTor-Heavy at 13.9% latency / 78.2% bandwidth; [SHEN-SP-24]'s independent live-Tor reproduction of the same named defense measured 112% time overhead, described in that paper's own text as "versus 5% in simulation." Two independently produced live-network figures for one defense disagree by roughly 100 percentage points, and a third, simulated figure disagrees with both by a comparable margin. This document's own admission requirement — "a tier whose cost is not measured cannot be offered, because a person cannot make an informed choice about an unquantified cost" — is violated by any single number drawn from this family, since no single number represents what a live deployment of it will actually cost. WTF-PAD and FRONT remain offered instead because two to four independent measurements of each agree to within roughly 2x of each other, all under live-Tor-crawl conditions [JUAREZ-ESORICS-16; HOLLAND-POPETS-22; SHEN-SP-24; GONG-USENIXSEC-20], and Tamaraw remains offered at its own live-deployment figure specifically [SHEN-SP-24], not its simulated one, for the same reason.

**Against Tamaraw's simulated figure as the offered Fetch-tier cost, in favor of its live-deployment figure.** [CAI-CCS-14]'s own simulated headline (199%-687% bandwidth) assumed a 750-byte payload the authors chose to cover most outgoing packets in their own dataset, not Tor's actual 514-byte cell. [SHEN-SP-24] recalculated Tamaraw's rate parameters to the real cell size and measured 135% bandwidth / 78% time overhead on the live network against four trained deep-learning classifiers, each held near or below 15% accuracy. Citing the simulated figure as "Tamaraw's cost" would import a padding parameter fixed to one paper's own assumed transport frame size rather than the transport this architecture actually uses; the transferable form of the finding is that a padding defense's rate and size parameters must be recalculated to whatever frame size the deployment's transport component actually uses, and only the recalculated figure is offered here.

**Against multi-server information-theoretic PIR as the default Query tier, in favor of single-server computational PIR.** [CHOR-JACM-98]'s base two-database construction sends n bits total for an n-bit database, with no benchmarked implementation of any compressed variant, against Piano's measured 3.0ms/32KB per query at 1GB after amortized preprocessing [ZHOU-SP-24]. The multi-server scheme's unconditional privacy guarantee is real, but it requires the client to address two independently operated, non-colluding database copies — a trust decision the client must make in advance and cannot verify cryptographically — while the single-server schemes need only a computational hardness assumption (LWE or Ring-LWE) already relied upon elsewhere in this architecture's cryptography, and no second party to select or trust. Multi-server PIR is retained as an opt-in for a deployment where two specific, already-trusted, independently operated index-holding peers exist, not as the default.

**Against Pacmann and Panther as the default unknown-index Query tier, in favor of Tiptoe.** [ZHOU-EPRINT-24] reports Pacmann reaching 1.1-3.0s latency, comparable to or faster than Tiptoe's 2.7s [HENZINGER-SOSP-23], but Pacmann's security proof explicitly does not cover a malicious server, only a semi-honest one that follows the protocol — a strictly weaker guarantee than Tiptoe's, which tolerates a server that deviates arbitrarily. A single storage/index peer in a permissionless network cannot be assumed to follow its own protocol honestly merely because it is not actively colluding with a second party; Tiptoe's guarantee matches that threat model and Pacmann's does not. [LI-CCS-25-PANTHER]'s Panther adds the further property of hiding the corpus itself from the client, at the cost of both a semi-honest-only guarantee and materially worse wide-area latency (8.71-18.3s against Tiptoe's 2.7s at comparable scale) — a property this architecture does not need, because the content being searched is itself meant to be publicly indexed, not secret from the querier who is a legitimate participant in the same network.

**Against Wally as an interactive Query tier.** [ASI-ARXIV-24-WALLY]'s own throughput figures assume 100,000 to 500,000 simultaneous, non-coordinating queriers per epoch and a client's answer arriving only when that epoch closes — 10 seconds at the smallest tested configuration, 6 minutes at the largest. Tiptoe answers a single query in 2.7 seconds with no dependency on how many other people are querying at the same moment [HENZINGER-SOSP-23]. Wally's own authors state their target workload directly: "high throughput is a must, while low latency can be relaxed," naming background retrieval of photo context for on-device models, not a query a person is waiting on. A person fetching a search result is waiting on it; Wally is offered here only for a background prefetch action, never for an interactive one.

**Against Vuvuzela and Stadium as the default Message tier, in favor of Karaoke.** [LAZAR-OSDI-18] measures Karaoke reaching 6-8 seconds of latency at 2-8 million users on 100 servers, 5 to 10 times lower than Vuvuzela [VANDENHOOFF-SOSP-15] and Stadium [TYAGI-SOSP-17] at matched user count, because only a fraction of Karaoke's servers process each additional user's messages rather than every server processing every message. Stadium is retained as an opt-in alternate, not rejected outright: its own contribution is spreading trust across many independently operated mixchains rather than concentrating the one-honest-server requirement in as few parties as Vuvuzela's four-server design, a genuinely different security property a user distrusting Karaoke's smaller server set may prefer — at the measured cost of 43.6 seconds to 876 seconds depending on chain length and scale [TYAGI-SOSP-17].

**Against small-clique DC-net broadcast (Herbivore, Dissent, Riposte) as the default Message tier.** [GOEL-CORNELLTR-03] measures Herbivore's anonymous bandwidth falling to 50-100Kb/s once a clique reaches 40 members with 4 active senders, and [CORRIGANGIBBS-SP-15] measures Riposte's write throughput falling to 32.8 requests/second at a 65,536-row table — both far below Karaoke's 6-8 second latency at millions of users [LAZAR-OSDI-18]. The DC-net family's information-theoretic guarantee needs no cryptographic hardness assumption at all, a strictly stronger property than the mix network's proven-but-computational differential-privacy bound; that property is retained here as an opt-in for a small, bounded, mutually acquainted group that wants an assumption-free guarantee and does not need this architecture's general messaging scale.

### What this selection requires from the rest of the system

- The Query ladder's single-server PIR tier requires the client to already hold the numeric index of the object it wants, which composes directly with content addressing: a client that already has an object's content hash can supply that as the PIR index, but a client that does not yet know which object it wants needs the Tiptoe tier instead, which requires an embedding pipeline run over the whole corpus at indexing time [HENZINGER-SOSP-23] — a component this selection consumes, not one it supplies.
- The Query ladder's single-server PIR tier destroys the feedback signal square-root replication needs: a forwarding or storage node running Piano, SimplePIR, or Tiptoe never learns which item a query touched by design [ZHOU-SP-24; HENZINGER-SOSP-23], so content replicated through search-driven feedback (documented elsewhere in this corpus as a composition conflict between square-root replication and PIR-protected search) must be replicated by some other trigger for any content queried through this tier.
- The Message ladder's mix-network tier requires at least one server on every message's path to be honest and to actually perform its assigned mixing and noise-generation duties, with no cryptographic mechanism to enforce this against a fully open peer population [VANDENHOOFF-SOSP-15; DOUCEUR-IPTPS-02]. An identity or admission component that can vet or bond a small server-role subset is required before this tier can be offered with its proven guarantee intact; absent that, the tier's stated adversary-defeated claim (a global passive network adversary) should be disclosed to the user as conditional on trusting the specific server operators selected, not unconditional.
- The Message ladder's mix-network tier requires every user, active or idle, to generate cover traffic every round [VANDENHOOFF-SOSP-15; PIOTROWSKA-USENIXSEC-17]; any component that suspends a client's network activity to save power or bandwidth — including a mobile background-execution policy this architecture's transport/reachability component must contend with separately — collapses this tier's guarantee for that user during the suspended interval, since the guarantee depends on continuous, indistinguishable traffic volume, not on any single message.
- The Message ladder's mix-network tier hides network-level message origin only; it does not strip an application-layer sender identifier the application itself writes into a message body [PIOTROWSKA-USENIXSEC-17]. Any component that writes a peer's stable identifier into application data carried over this tier (a ranking or gossip mechanism that logs a querying peer's node ID, for instance) defeats the tier's guarantee at a layer this tier does not reach; the application-data component must be told explicitly which fields this tier does not protect.
- The Fetch ladder's onion-circuit tiers require a signed, current relay directory reachable by every client before circuit construction [DINGLEDINE-USENIXSEC-04], supplied by this architecture's naming/discovery component, not by this selection.
- Every tier in every ladder that names a specific padding parameter, chunk size, or cell size (Tamaraw's L/rho_out/rho_in, PIR's database-block size) must have that parameter recalculated against the transport component's actual frame size, not imported from the source paper's own assumed value [SHEN-SP-24 demonstrates the consequence of skipping this step directly, for Tamaraw].

### What it costs and where it fails

No ladder position anywhere in this document escapes a proven three-way bound. Das, Meiser, Mohammadi, and Kate ("Anonymity Trilemma: Strong Anonymity, Low Bandwidth Overhead, Low Latency — Choose Two," IEEE Symposium on Security and Privacy 2018) prove that a communication protocol defended against a global passive network-level adversary achieves at most two of three properties at once — anonymity up to a negligible probability of deanonymization, low bandwidth overhead, and low latency overhead — deriving, for a stated count of passively compromised protocol nodes, a required relationship between bandwidth overhead and latency overhead that a design violating it cannot achieve strong anonymity within. The same authors' follow-up ("Comprehensive Anonymity Trilemma: User Coordination is not Enough," Proceedings on Privacy Enhancing Technologies 2020) closes the one route around the 2018 bound that had been proposed — letting users coordinate their sending behavior out of band — by proving a second, strictly stronger impossibility result that covers coordinating users as well. Neither paper carries a full-text entry with its own key in this evidence corpus: this document states both results from this repository's own retained prior-pass record, which the project brief lists as already read in full before this pass began, and states them only in the qualitative form that record preserves — a required relationship between the two overhead quantities, not the closed-form bound itself. No specific numeric constant from either paper is asserted here; that constant is unverified in this corpus.

The measured tiers in this document trace the same shape directly, without needing the abstract bound. [LAZAR-SOSP-19]'s own trust-assumption sweep (§6.3) holds latency to roughly 100ms only by assuming every server honest, and needs 15 relay hops, with correspondingly higher latency, once the honesty assumption drops to 80%. [PIOTROWSKA-WPES-21]'s comparison of Elixxir, HOPR, and Nym under one simulator shows the same trade from the opposite direction: Elixxir's batch-and-reorder design bounds anonymity to its fixed batch size regardless of user count while latency grows without bound as users scale; HOPR's flat peer-to-peer topology keeps latency low but needs cover-to-real traffic ratios up to 10:1 to raise anonymity at all, and still falls short of Nym's stratified design at far less cover traffic. Every row in Table 3 sits somewhere on this surface — cheaper in bandwidth or latency at the price of weaker anonymity, a stronger honesty assumption, or a smaller usable scale — and no combination of parameters published in this corpus escapes it.

Fetch-ladder failure is per-tier and already stated in Table 1: no padding fails against any website-fingerprinting classifier; lightweight padding fails against deep-learning classifiers specifically; Tamaraw fails against an attacker that observes total transmitted size directly. Query-ladder failure is compositional: every tier in Table 2 protects only the query, not the requester's network identity, so a Query tier used without an underlying Fetch tier discloses the requester by IP address even while hiding which record was requested [stated directly by ASI-ARXIV-24-WALLY for its own design]. Message-ladder failure is assumption-dependent: the mix-network tier's proven bound holds only while at least one server per path stays honest, a condition this corpus supplies no cryptographic enforcement for in a fully open peer population [DOUCEUR-IPTPS-02].

### What the corpus does not settle

- The exact closed-form relationship Das, Meiser, Mohammadi, and Kate derive between bandwidth overhead, latency overhead, and compromised-node count is not present in this corpus with a citable full-text entry; a builder needing the precise numeric trade-off, rather than its qualitative shape, needs to retrieve IEEE S&P 2018 (ePrint 2017/954) and PoPETs 2020 directly.
- No entry measures onion-routing latency at a relay count and user population matching this architecture's likely scale; [DINGLEDINE-USENIXSEC-04]'s own figures come from a 32-relay network designed for roughly 10,000 users, and no later entry in this corpus re-measures Tor's own baseline circuit latency at a modern relay population.
- No entry measures a padding defense's cost on a transport this network actually uses (a peer-to-peer overlay circuit rather than Tor specifically); every website-fingerprinting figure in Table 1 is measured on live or simulated Tor traffic, and the transferable finding — recalculate padding parameters to the deployment's real frame size — has no measured worked example outside Tor's own 514-byte cell.
