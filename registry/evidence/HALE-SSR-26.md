## [HALE-SSR-26] Benchmarking of the Amortized Post Quantum Combiner for MLS
**Citation:** Britta Hale, Xisen Tian, Lee Wang. "Benchmarking of the Amortized Post Quantum Combiner for MLS." Security Standardisation Research (SSR), Lecture Notes in Computer Science, 2026. DOI 10.1007/978-3-032-19567-8_5.
**Retrieved:** full text via https://doi.org/10.1007/978-3-032-19567-8_5
**Source URL:** https://doi.org/10.1007/978-3-032-19567-8_5
**Domain:** H

### What it does
The Amortized Post-Quantum (APQ) combiner reduces the bandwidth, compute time, and memory cost of adding post-quantum protection to Messaging Layer Security (MLS), a continuous key agreement (CKA) protocol that ratchets keys forward through a tree-structured key encapsulation mechanism (KEM) called TreeKEM. This paper is an independent implementation and benchmark of the APQ combiner draft (Tian, Hale, Mularczyk, Joël, draft-ietf-mls-combiner), extending the proof-of-concept implementation of GREENE-EPRINT-25 with a second combiner mode and a head-to-head comparison against the X-Wing hybrid KEM.

The mechanism runs two MLS sessions in parallel with identical membership: a traditional session B (classical KEM and digital signature algorithm (DSA)) and a post-quantum (PQ) session A. Every epoch in session B advances by a Partial Commit (traditional KEM and DSA only). Periodically, a Full Commit advances session A using a PQ KEM, exports a PQ secret from A's key schedule, and injects it into B as a pre-shared key (PSK) proposal that B commits, mixing PQ entropy into B's key schedule via a key derivation function (KDF). Two modes are tested: PQ/T Confidentiality-Only (session A signs with a traditional DSA, so only confidentiality against a quantum adversary is PQ-protected) and PQ/T Confidentiality+Authenticity (session A signs with a PQ DSA, so authenticity is also PQ-protected, propagating into the authenticated-encryption-with-associated-data (AEAD) keys B derives). A partial commit does not update the PQ material, so a quantum break during a run of Partial Commits reduces the effective post-compromise-security (PCS) window to the interval between Full Commits, while forward secrecy (FS) is still achieved on every Partial Commit because each commit still ratchets the traditional key material forward.

The implementation extends OpenMLS (Rust) with the RustCrypto crypto-provider, adding ML-KEM and ML-DSA (the NIST-standardized post-quantum KEM and signature algorithms) via new RustCrypto and HPKE (Hybrid Public Key Encryption) crate integrations. It deviates from the draft by omitting the APQMLSInfo bookkeeping extension and by using OpenMLS's export_secret rather than the epoch_secret (unavailable via the OpenMLS API) as the PSK source; the authors state both differences have negligible effect on the measurements because APQMLSInfo is a small fixed-length byte string and the two secret types are the same size.

### Measured results
All tests ran a two-party MLS session (not scaled to larger group sizes; the paper argues the two-party case is the worst case for per-participant overhead amortization since MLS's tree-based scaling improves with group size) for 500 epochs, each epoch advanced by one empty commit from a single party. Timing figures are the average of 10 runs of the full 500-epoch test via the Rust Criterion microbenchmarking tool. Message-size and memory figures are totals across the 500-epoch run; memory was measured with the Rust Hotpath profiling tool. Hardware: a MacBook Pro with an Apple M2 Max (ARM CPU/GPU), 64 GB RAM, macOS Ventura.

Baseline (single, uncombined MLS sessions), total time over 500 epochs at 3 security levels (Low/Medium/High): traditional Edwards-curve ciphersuites (T-Ed-AES, T-Ed-Cha) ran faster than the lowest-security PQ ciphersuites, but at the 256-bit security level both PQ Confidentiality-Only (PQ-C-H, 3.353 s) and PQ Confidentiality+Authenticity (PQ-CA-H, 2.422 s) ciphersuites outperformed their traditional counterparts (T-EC-AES-H 5.244 s); PQ-CA-H ran 23% faster than PQ-C-H. Elliptic-curve traditional ciphersuites (T-EC-AES) ran roughly 4 times slower than Edwards-curve traditional ciphersuites (T-Ed-AES/T-Ed-Cha) within the traditional class.

Baseline message size, totaled over 500 epochs: PQ ciphersuites produced several orders of magnitude more bytes than traditional counterparts (e.g., low security: T-Ed-AES-L 0.24 MB vs. PQ-C-L 1.40 MB vs. PQ-CA-L 1.62 MB; high security: T-Ed-AES-H 0.24 MB vs. PQ-C-H 6.15 MB vs. PQ-CA-H 8.75 MB).

Baseline peak memory: classical ciphersuites capped at 1.2 MB peak regardless of security level; PQ ciphersuites' peak memory rose with security level, from 1.3 MB (PQ-C-L) to 1.8 MB (PQ-CA-H). Total (cumulative, 500-epoch) memory showed a larger gap: 235% higher for PQ-C-L versus T-EC-AES-L at low security, rising to 750% higher for PQ-CA-L versus T-Ed-AES-H comparison at higher security (the paper's own comparison pairing).

APQ amortization tests, Full:Partial commit ratios of 1:1, 1:10, 1:50, 1:100 (plus 1:2 and 1:5 in the X-Wing comparison), across the same 500-epoch, two-party, 10-sample-averaged setup, at three security levels for both modes:
- Total runtime: in all combinations except H-CA-L and H-C-X, APQ's total runtime exceeded the runtime of running the PQ component alone, even at 1:100 — because Partial Commits dominate the count and hit the traditional-ciphersuite component repeatedly, so APQ's per-epoch cost skews toward the traditional ciphersuite's cost, and for medium/high security levels that traditional component (P384-based KEM and DSA, or Ed448) was itself slower than its paired PQ component.
- Message size and memory: amortization behaved as expected in every configuration. At a 1:1 ratio, total message size approximately equaled the sum of running the two solo sessions separately. At ratios of 1:10 and beyond, message size dropped exponentially, converging toward the solo traditional session's magnitude; at ratios beyond 1:50, this reached a 94% cumulative message-size reduction relative to a single MLS session running the PQ ciphersuite alone, and up to an 85% reduction in total memory usage.
- Diminishing returns: efficiency gains from lowering the ratio flattened past 1:50 for all APQ modes, converging to a floor set by the slower of the two component ciphersuites.

Head-to-head against the X-Wing hybrid KEM combiner (a single-session hybrid that must invoke ML-KEM768 on every commit), at matched security levels, over the same 500-epoch protocol: APQ's Confidentiality-Only variant (H-C-X) overtook X-Wing in total runtime at a 1:2 Full:Partial ratio, with speedups from 26% (at 1:5) up to roughly 50% (diminishing, past 1:50). The Confidentiality+Authenticity variant (H-CA-X, which also carries ML-DSA65 signatures that X-Wing does not provide) overtook X-Wing's runtime only at a 1:5 ratio, still despite providing an authenticity property X-Wing lacks; its runtime floor approached the solo traditional Ed25519 ciphersuite's runtime. Message size and total memory for H-C-X overtook X-Wing starting at 1:2; for H-CA-X starting at 1:5.

### Stated limitations
The implementation omits the APQMLSInfo bookkeeping extension defined in the draft standard, and substitutes the export_secret for the epoch_secret as the PQ-to-traditional PSK source because the epoch_secret is not exposed by the OpenMLS API; the authors state both deviations have negligible measurement impact but do not measure that claim directly. Timing measurements exclude network transmission entirely — they measure cryptographic-operation cost only, with no packets sent across a network, so end-to-end latency in a real deployment is not represented. All commits in every 500-epoch run are issued by a single party for measurement clarity, which the authors state differs from normal operation where commits are distributed across group members. Testing is limited to a two-party group; the paper argues, but does not measure, that larger groups would only improve APQ's relative performance because of MLS's logarithmic tree-based scaling. The APQ combiner's total runtime exceeding its solo-PQ-session runtime in most configurations is left only partially explained; the authors identify the traditional ciphersuite component as the cause but state that testing alternative traditional-ciphersuite implementations across other crypto-providers and crypto-libraries to resolve the remaining discrepancy is left to future work. The underlying APQ draft standard was still under active discussion (GitHub and mailing-list) at the time of writing, so full-fidelity testing against a finalized, fully compliant implementation is deferred to future work.

### Requirements it places on the rest of the system
Requires maintaining two parallel MLS sessions with identical membership at all times, exactly as in GREENE-EPRINT-25; any membership-management component must apply every Add/Remove to both sessions. Requires the delivery/ordering layer to carry two independent commit streams (traditional and PQ) plus the PSK Proposal message that ties a Full Commit's PQ secret into the traditional session, at a cadence the application selects. A partial-commit-only period narrows the PQ post-compromise-security window to the gap between Full Commits, so a component that needs PQ PCS bounded below a target interval must fix the Full:Partial ratio no coarser than that interval allows; this paper's own data show ratios beyond 1:50 buy diminishing returns in bandwidth and memory while widening that PQ PCS gap, so the ratio choice is a direct trade against PQ PCS latency, not a free efficiency gain. The Confidentiality-Only mode leaves the traditional-session signatures as the sole binding on message authenticity, so an attacker with both a quantum computer and access to one session participant's traditional signing key can forge session-internal non-repudiation (a niche threat model distinct from external quantum authenticity, per the authors' own footnote). Requires an OpenMLS-compatible crypto-provider exposing ML-KEM and ML-DSA operations; the specific runtime and memory numbers are tied to the RustCrypto provider on Apple M2 Max hardware, and the authors' own data show large runtime variation between traditional-ciphersuite choices (Edwards-curve versus NIST-curve KEMs and DSAs) at matched security levels, so a different crypto-provider or CPU architecture is not guaranteed to reproduce the reported floors.

### Contradicts
Independently measures the same APQ combiner mechanism as GREENE-EPRINT-25 but reports contrary detail on the sign of the runtime benefit: this paper's amortization data show APQ's total runtime exceeding the solo-PQ-session runtime in most tested configurations (all except H-CA-L and H-C-X), which the authors describe as counter to the intuition that APQ reduces PQ cost relative to a PQ-only session; GREENE-EPRINT-25 by contrast reports APQ configurations running consistently faster than a PQC-only baseline (30-50% runtime advantage) at every group size tested. The two papers are not measuring the same baseline (GREENE-EPRINT-25 compares APQ against a PQC-only MLS session across group sizes 2-100 on an AMD FX-6300; HALE-SSR-26 compares APQ against both a solo-PQ session and a solo-traditional session, fixed at group size 2, on an Apple M2 Max, and additionally varies ciphersuite security level), so the two results are not a like-for-like disagreement, but both cannot be summarized as "APQ is faster than PQ-only" without stating which traditional-ciphersuite pairing and hardware the claim rests on.
