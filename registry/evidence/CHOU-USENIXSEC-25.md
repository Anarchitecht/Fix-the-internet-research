## [CHOU-USENIXSEC-25] Bots can Snoop: Uncovering and Mitigating Privacy Risks of Bots in Group Chats
**Citation:** Kai-Hsiang Chou, Yi-Min Lin, Yi-An Wang, Jonathan Weiping Li, Tiffany Hyun-Jin Kim, Hsu-Chun Hsiao. "Bots can Snoop: Uncovering and Mitigating Privacy Risks of Bots in Group Chats." 34th USENIX Security Symposium, 2025. Pages 6601-6618.
**Retrieved:** full text via https://www.usenix.org/system/files/usenixsecurity25-chou.pdf
**Source URL:** https://www.usenix.org/system/files/usenixsecurity25-chou.pdf
**Domain:** H

### What it does
The paper measures how much message content and sender-identity information a chatbot added as a full group member can access beyond what its own function requires, in deployed group-messaging platforms, and then proposes SnoopGuard, a tree-based Continuous Group Key Agreement (CGKA — the protocol family, described under CHOU's own citation of prior work, in which group members derive a shared key by walking a binary key tree) that restricts a chatbot's access to only the messages it needs and hides sender identity from chatbots without excluding them from the group.

SnoopGuard modifies the CGKA key tree into what the paper calls a Compressed Multi-Roots Tree (CMRT). The tree keeps one ordinary user subtree, whose root secret is the shared group secret among human users, and adds one additional root node per chatbot, each holding a separate secret shared between the user subtree and that one chatbot. A chatbot's key updates only when a message is specifically directed at it (a trigger function client-side decides relevance); if no message triggers a chatbot, its key stays unchanged, so a chatbot never needs to process key-update traffic for messages it will never read, unlike a chatbot represented as an ordinary tree leaf in plain TreeKEM, which must process every update to stay able to decrypt future messages. For sender anonymity, a chatbot sees only the root of the user subtree during a user-initiated update, never the individual node path a plain CGKA update path exposes, so a chatbot can compute the correct shared secret without learning which user initiated the update; the paper calls this property selective Internal Group Anonymity (IGA), a directional version of Internal Group Anonymity (from Chen and Chen's Anonymous ART) in which users stay indistinguishable to chatbots while chatbots stay distinguishable to users. An optional pseudonymity extension lets a chatbot tell users apart without learning real identities, through a registration step equivalent to one message from each user to the chatbot.

### Measured results

**Case study 1 — chatbot over-access, DISCO dataset (1.5 million Discord messages, 323,600 users, four groups, November 2019 to October 2020):** manual source-code review of one rule-based chatbot (Discord Gophers Bot, responding only to messages prefixed `?go`) found it reads `Author.ID` and `Author.Username` on every message it receives, though its function needs neither. Of 246,685 messages in its group, 580 (0.24%) matched its trigger prefix; the bot had standing access to all 246,685, a factor of 424 more messages than its function required ((246,685 − 580) / 580).

**Case study 2 — cross-group identification, Pushshift Telegram dataset (2.2 million users, 27,800 public channels, September 2015 to November 2019):** of 1,577 analyzed chatbots, 718 (45.5%) had Telegram's privacy mode disabled, granting full message and sender access. Of those 718, 253 (35.2%) appeared in more than one group, 44 (6%) appeared in more than 10 groups, and 3 appeared in more than 100 groups. Of 1,168,344 users who joined at least one group, 42,508 (3.6%) encountered the same privacy-disabled chatbot in more than one group, one user encountering 134 distinct such chatbots. Of 4,155,927 distinct user-chatbot pairs with at least one shared-group encounter, 97,813 (2.4%) shared more than one group, 96 pairs shared more than 10 groups, and two pairs shared 55 groups.

**Platform security-property survey (Table 1):** across WhatsApp, Viber, Signal, LINE, Telegram, Discord, Slack, and Keybase, no platform in the sample combines group End-to-End Encryption (E2EE), Post-Compromise Security (PCS — the property that a channel heals once a compromised party takes a further protocol step) with bots present, and both message access control and sender-identity hiding for bots. Signal supports PCS only in private one-to-one groups, not multi-party groups (marked partial).

**Computational complexity (Table 3, asymptotic, n = group members, m = chatbots), derived by the authors, not measured:** SnoopGuard's ongoing per-message cost is O(log n + m) public-key exponentiations and hash/encryption operations for the sender, O(1) for a user, and O(1) for a chatbot; the comparison baselines are Sender Keys (O(n+m) sender-side ongoing operations are O(1) per message but O(n+m) at setup), (A)ART (O(n+m) ongoing for sender and users), and MLS/TreeKEM (O(log(n+m)) ongoing for the sender, O(1) for other users). SnoopGuard's storage is O(n+m) for users and O(1) per chatbot.

**Empirical latency, prototype in Go on a Mac mini with an Apple M2 processor and 16 GB RAM, two backends (extended libsignal / Sender Keys, and go-mls / MLS):** adding a chatbot to a 50-member group takes about 2 ms in SnoopGuard versus about 30 ms when the chatbot is added as an ordinary member under either unmodified protocol. Sending one message to 50 members and 10 chatbots takes about 10 ms when SnoopGuard is layered on MLS and about 5 ms when layered on Sender Keys; per-message overhead rises linearly with the number of chatbots, matching the O(m) term in the derived complexity.

**Resource-constrained device simulation:** Docker containers capped at 0.5 to 1.0 CPUs, calibrated against Geekbench 6 single-core scores of 1,171 to 2,629 (the paper states this spans budget phones such as Snapdragon 865 and MediaTek Dimensity 8100 up to high-end devices such as Apple M2 and A16, as of 2024), group of 50 members and 30 chatbots: adding a chatbot without pseudonymity stayed under 15 ms across all tested CPU allocations, and under 20 ms with pseudonymity enabled at the lowest tested allocation. Message-send ciphertext generation on the Sender Keys backend stayed under 5 ms even at the lowest CPU allocation; on the MLS backend it stayed under 10 ms across all tested allocations.

### Stated limitations
SnoopGuard's message-filtering guarantee depends entirely on the correctness of a client-side trigger function that decides which messages are relevant to a given chatbot; the authors state that a poorly designed or maliciously crafted trigger function can mark every message relevant, restoring full unrestricted access, and that policing trigger-function correctness is beyond what the messaging protocol itself can enforce — they suggest a manual or automated vetting process as a separate, unbuilt mitigation. The authors state the two privacy properties they address (selective message access and sender anonymity) may not be an exhaustive list of chatbot privacy risks. The case studies analyze only public datasets (Discord and Telegram public channels) for ethical and practical reasons; the authors state they leave the study of sensitive content exposure in private group conversations to future work, so the measured over-access ratios and cross-group linkage rates are not shown to generalize to private groups. The design assumes the underlying CGKA scheme already provides Forward Secrecy (FS) and Post-Compromise Security (PCS); SnoopGuard's own security analysis is conditioned on that assumption rather than proved independently of it, and on the assumption that no chatbot itself is compromised. No user studies of the trigger-function or permission-disclosure interface exist yet; the authors list usability evaluation, a general chatbot permission model, and study of user perceptions of chatbot privacy in group settings as open future-work items, not solved by this paper.

### Requirements it places on the rest of the system
SnoopGuard requires an underlying tree-based CGKA (the paper builds specifically on TreeKEM) that already delivers FS and PCS to the human-user subtree; it does not supply those properties itself, it inherits them. It requires every user client to run a trigger function locally to classify incoming plaintext messages for chatbot relevance before encryption, meaning message content must be visible client-side at send time — the paper states this is precisely what conventional server-side E2EE filtering (as Telegram and Discord perform today) cannot do, and is why SnoopGuard moves the filtering to the client. It requires each user to store one root-node key per chatbot present in the group (O(n+m) storage for users), so client storage grows linearly with the number of chatbots a group carries, not just the number of human members. It requires a chatbot to store only O(1) state (its own subtree secret), but that chatbot's key only advances when a message triggers it, so any component relying on chatbot state monotonically tracking wall-clock epoch count (rather than message-relevant epoch count) does not compose with this design without modification. Pseudonymity requires an explicit one-time registration exchange between each user and each chatbot before pseudonymous messages, adding a message-count-linear setup cost the paper's own complexity table flags with an asterisk as excluded from its stated complexity figures. The design assumes an Internet Engineering Task Force Messaging Layer Security (MLS)-style client-managed group rather than a fully decentralized peer set with no distinguished Delivery Service; the prototype uses go-mls and an extended libsignal, both of which assume a central relay for message and control-message delivery.
