## [KOMLO-SAC-20] FROST: Flexible Round-Optimized Schnorr Threshold Signatures

**Citation:** Chelsea Komlo, Ian Goldberg. "FROST: Flexible Round-Optimized Schnorr Threshold Signatures." Selected Areas in Cryptography (SAC), 2020. DOI 10.1007/978-3-030-81652-0_2.
**Retrieved:** full text
**Source URL:** https://eprint.iacr.org/2020/852.pdf
**Domain:** E

### What it does
FROST (Flexible Round-Optimized Schnorr Threshold signatures) lets t out of n key-share holders jointly produce a single Schnorr signature, verifiable with the standard single-party Schnorr verification equation, while requiring only one network round of communication among signers during the signing operation itself, with an optional non-interactive preprocessing stage performed in advance. Each participant holds a long-lived secret share s_i from a threshold key generation built on Pedersen's distributed key generation (DKG) protocol, modified with a per-participant zero-knowledge proof of knowledge of the constant term of that participant's secret-sharing polynomial, added specifically to block rogue-key attacks (an adversary deriving its own public key share as a function of honest participants' public shares to forge a joint signature). During preprocessing, each participant generates and publishes commitments to pi single-use nonce pairs (d_ij, e_ij); a designated signature aggregator (SA) later selects a signing set S of t participants and the next unused commitment pair for each. Each selected participant computes a per-participant binding value rho_i by hashing the message, its own index, and the full set of participants' published commitments together (rho_i = H1(i, m, B)), which binds every signer's response to the specific message and the specific signing set; this binding is what defeats the Drijvers et al. forgery attack against prior two-round Schnorr multisignature and threshold schemes, in which an adversary interleaves signing sessions to solve a system of linear equations (the ROS problem) and forge a signature. Each participant returns a single response z_i computed from its nonce, its long-lived share, and a Lagrange interpolation coefficient; the aggregator sums the z_i values and publishes (R, z) as a standard Schnorr signature. FROST is not robust: if a participant returns an invalid response, the aggregator detects it (by checking g^z_i against the participant's published commitments) and the protocol aborts, to be rerun with that participant excluded, rather than tolerating the misbehavior and completing anyway.

### Measured results
The paper reports no runtime benchmark (wall-clock time, throughput, or hardware-measured latency); its Rust implementation over Ristretto/curve25519 is stated to exist, with source published, but no timing figures from that implementation are given in the text. All quantitative results in the paper are round-counts and computational-complexity terms for the underlying protocols, derived by describing each protocol's message flow rather than by executing it.

### Parameters
- n: total number of key-share holders.
- t: signing threshold, t <= n; no numeric default given, left as a deployment choice.
- pi: preprocessing batch size (number of nonce pairs generated per participant per preprocessing run); appears symbolically in the security bound but is not assigned a numeric recommended value in the paper.
- Group: Ristretto over curve25519, used in the stated Rust implementation; no other group is benchmarked.
- Signature aggregator (SA) role: optional centralized coordination point; the paper states FROST can also run fully peer-to-peer (participants broadcast commitments directly to each other) in a two-round setting without a designated aggregator, foregoing the preprocessing-stage optimization.

### Stated limitations
The paper states its argument that the FROST-Interactive-to-plain-FROST transition (replacing a one-time VRF with a random-oracle hash for generating rho_i) carries no security consequence is heuristic, not a proof: it proves sufficiency of its stated forgery condition but explicitly states it does not prove necessity. It states that FROST trades robustness for signing efficiency: unlike the Stinson-Strobl and Gennaro-Jarecki-Krawczyk-Rabin robust schemes, a single misbehaving or unresponsive participant causes the entire signing operation to abort rather than complete with the remaining honest participants, requiring the protocol to be rerun with that participant excluded and the cause investigated out of band. It states that the FROST-Interactive preprocessing round must be performed serially by each participant (rather than in parallel/non-interactively, as plain FROST's preprocessing can be), because the security proof's simulator needs to extract the discrete logarithm of the adversary's VRF-key proof of knowledge via rewinding, which requires serialized execution. It states three explicit security assumptions implementations must independently guarantee: every participant validates the message before issuing a signature share; the network delivers messages reliably; and misbehaving participants can be identified via authenticated messaging within the signing group — none of which FROST itself provides.

### Requirements it places on the rest of the system
FROST requires a location (a "commitment server" or equivalent) where participants publish their preprocessing-stage nonce commitments for the aggregator to consume; the paper states this location need not be trusted for confidentiality (public commitment values grant no extra power to an adversary who reads them) but must be trusted to serve correct, unused values, since a malicious commitment server could mount denial-of-service or supply stale/malformed commitments on behalf of honest participants. It requires an authenticated channel or equivalent participant-identification mechanism external to FROST itself, since the protocol's misbehavior-detection step depends on being able to attribute an invalid response to a specific participant identity. It requires reliable message delivery between the aggregator and each signing participant, stated as an explicit assumption rather than something FROST tolerates violations of. Because FROST is non-robust, any system embedding it must supply its own retry/exclusion logic above the protocol to recover from an abort, since FROST itself only detects and halts.
