### What it does
Tahoe stores a file across multiple untrusted servers such that possession of one short string (a capability) is both sufficient to access the file and necessary — no separate access-control server or list exists anywhere in the system. A capability is a bit string, at least 96 bits long to resist guessing, that identifies one file or directory; holding it is both necessary and sufficient to exercise the access it grants. This follows the Principle of Least Authority: a process should hold no more access than the specific task requires. Tahoe defines three capability levels per file with a strict hierarchy: a write capability (read-write-cap) can derive a read capability (read-cap), which can derive a verify capability (verify-cap), but the derivation is one-directional — a verify-cap holder can check a file's integrity without being able to read its plaintext, and a read-cap holder can read the file but not modify it. Producing a weaker capability from a stronger one is called diminishing.

Every file is erasure coded with Reed-Solomon codes over the finite field GF(2^8): a writer chooses N, the total number of shares written across N distinct servers, and K, the number of shares sufficient to reconstruct the file (K ≤ N ≤ 256), and any K of the N shares suffice for recovery regardless of which K. For an immutable file (written once, read many times), the client picks a symmetric key, encrypts the plaintext with AES-128 in counter mode, erasure-codes the ciphertext into N shares, and writes one share to each of N servers. Two separate Merkle trees (binary hash trees where each parent commits to both children, letting any subset of leaves be verified without downloading the whole structure) are built: one over the erasure-code shares, so a client that detects corruption knows which specific share to discard and reconstruct from the others, and a second over the ciphertext itself, so a client can verify and stream part of a file without fetching all of it, and so no single erasure-code-share Merkle tree alone could let a malicious writer plant shares from two different files under one nominal identifier. The read-cap is the verify-cap plus the symmetric decryption key; the verify-cap is the secure hash (SHA256d, meaning SHA256 applied twice, chosen to prevent length-extension attacks) of a small "Capability Extension Block" holding both Merkle roots, stored on every server alongside that server's share rather than embedded in the capability itself, keeping the capability string short.

A mutable file (contents can be overwritten) is bound to an RSA key pair generated at file creation. From the RSA signing key SK, the client derives a 16-byte write key WK = truncated-SHA256d(SK), and from WK derives a 16-byte read key RK = truncated-SHA256d(WK) — so holding WK lets a party compute RK, but RK alone reveals nothing useful about WK, giving the required one-directional hierarchy without needing three independently generated secrets. To write, the client derives an encryption key from RK and a fresh random salt, encrypts, erasure-codes, distributes shares, builds a Merkle tree over the shares, and signs the Merkle root, the salt, the erasure-coding parameters, the file size, and a monotonically increasing sequence number with SK; the corresponding RSA public key (the verifying key VK) is stored unencrypted alongside the shares on every server, and the verify-cap is the hash of VK. The signing key SK itself is stored on the servers too, but encrypted under WK, so only a write-cap holder can decrypt and use it. To defend against a server (accidentally or maliciously) returning a stale, validly signed earlier version, the read protocol queries K + E servers for share metadata first (in the deployed client, K = 3 and E = K = 3), and only proceeds to download once it either confirms at least K shares of the highest sequence number it has found, or exhausts the servers it can query — a scheme the authors state reduces the chance of a stale read given that enough queried servers are honest and current, but does not by itself guarantee freshness. Directories are themselves mutable files holding (child name, capability) pairs; to preserve a transitive read-only property — a holder of read-only directory access can obtain only read-only capabilities to children, never write access — each child entry stores two separately encrypted capability slots, one for read-write and one for read-only, with the read-write slot "super-encrypted" (encrypted again, on top of the directory's own encryption) so a read-only directory holder cannot recover it.

### Parameters
- Capability length: minimum 96 bits, chosen to be unguessable while remaining short enough to embed in a URL.
- Erasure-code field: GF(2^8), Reed-Solomon, with the constraint 1 ≤ N ≤ 256 and 1 ≤ K ≤ N; the byte-wise implementation over this field is what keeps encode/decode efficient despite Reed-Solomon's stated O(N^2) worst-case computational complexity.
- Deployed (K, N): K = 3, N = 10 in the allmydata.com production service — the paper's own stated production default, not a value it claims is universally optimal.
- Symmetric encryption: AES-128 in CTR mode, used for both immutable- and mutable-file content encryption.
- Hash function: SHA256d (SHA256 applied twice) throughout, with purpose-specific tag prefixes on every hash input to prevent cross-purpose collisions.
- Mutable-file signature key: 2048-bit (256-byte) RSA key pair, one generated per mutable file.
- Derived secrets for mutable files: write key WK and read key RK each 16 bytes (128 bits), each a truncated SHA256d output.
- Mutable-file freshness read protocol: queries K + E servers before proceeding to download shares; deployed setting E = K, so with K = 3 the client queries at least 6 servers for metadata before commit.
- Convergence secret: an additional secret mixed into the convergent-encryption key derivation, scoped per group of users who share that secret, to limit which users' identical files converge to identical ciphertext.

### Stated limitations
Tahoe's freshness-read protocol reduces, but the authors state does not eliminate, the chance of an accidental or malicious stale read, and only "provided that enough of the servers are honest and have fresh data" — the paper gives no numeric bound on how many dishonest or stale servers the K+E query can tolerate. The system makes no attempt to enforce any consistency property beyond single-file freshness; the authors state explicitly that it does not enforce linearization of operations spanning more than one file, unlike the Byzantine fault-tolerant filesystems they cite for comparison. Convergent encryption (deriving a file's encryption key from a hash of its own plaintext, so identical files by different users produce identical ciphertext and can be stored once) is stated to be able to undermine confidentiality in some cases, citing a separate paper by one of the authors; Tahoe's mitigation (a convergence secret scoping which users converge) is described but not claimed to close every such case. The two nonstandard cryptographic constructions used or proposed — encrypting the RSA signing key under a key derived from a hash of that same signing key, and the proposed semi-private-key scheme for future ECDSA-based capabilities — are both explicitly described by the authors as resting only on heuristic security arguments, not proofs, with the paper stating it would be surprising if a weakness existed that did not also break the underlying standard primitive (RSA, AES-128, SHA256), which is an expectation, not a proof. The paper states a Proof of Retrievability protocol (downloading and checking a randomly chosen subset of ciphertext rather than the whole file) was designed but explicitly not deployed in the current Tahoe release at time of writing, described as a work in progress. RSA-2048 key generation taking up to 3.2 seconds per mutable file is presented by the authors as a performance problem motivating their proposed (undeployed) DSA/ECC-based semi-private-key alternative described in the Future Work section.

### Requirements it places on the rest of the system
A reader needs to contact at least K of the N servers holding a file's shares to reconstruct it, and the freshness protocol additionally needs at least K + E servers to be reachable during the metadata-query phase for the staleness defense to function at all; a deployment with fewer than K+E reachable servers per file falls back to whatever subset it can reach, with the paper's stated freshness guarantee no longer applying at full strength. The one-directional capability hierarchy (write-cap → read-cap → verify-cap) requires every derivation to be computable forward (via a one-way hash) and infeasible backward without the higher-level secret; any component that needs to grant a weaker capability without ever exposing the stronger one must perform that hash-based diminishment locally, since Tahoe places no server or protocol step in the way of a party diminishing its own capability at will. For mutable files, correctness of the freshness scheme depends on servers correctly reporting the highest sequence number and share count they hold when queried in the metadata phase; the paper does not describe any independent mechanism forcing honest reporting, so the scheme's holding is conditional on the "enough honest servers" assumption above being met by whatever server-selection or diversity policy the surrounding system supplies. Directory transitive read-only requires every directory entry, not just the directory's own encryption, to carry the extra super-encryption layer on its read-write slot; a system storing directory entries any other way (for example a flat mutable file per child rather than an encrypted-slot pair) would not preserve this property.

### Contradicts
None found against another entry in this corpus (no other Tahoe deployment-measurement paper is in this batch). The paper's own conclusion states that Reed-Solomon codes "have been characterized as being asymptotically inefficient in the literature" — attributing that characterization to unnamed prior literature rather than presenting it as Tahoe's own finding — while reporting that in Tahoe's own deployment the erasure-coding cost measured lower than the encryption and hashing cost in the same pipeline; this is the paper's own qualification of a claim it attributes to others, not a disagreement with a specific paper elsewhere in this corpus.
