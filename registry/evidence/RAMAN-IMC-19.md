## [RAMAN-IMC-19] Challenges in the Decentralised Web: The Mastodon Case

**Citation:** Aravindh Raman, Sagar Joglekar, Emiliano De Cristofaro, Nishanth Sastry, Gareth Tyson. "Challenges in the Decentralised Web: The Mastodon Case." ACM Internet Measurement Conference (IMC), 2019. DOI 10.1145/3355369.3355572.
**Retrieved:** full text via https://arxiv.org/abs/1909.05801
**Source URL:** https://arxiv.org/abs/1909.05801
**Domain:** J+K

### What it does
The paper measures how independent, federated server operation in a deployed decentralized social network (Mastodon, a microblogging platform built on the ActivityPub federation protocol, where each independently run server is called an instance) produces concentration despite no central operator, and quantifies how much of the network's connectivity and content availability a small number of instance or hosting-provider failures can remove. The authors built three datasets by polling each instance's public API every five minutes over 15 months for metadata (user counts, toot counts, federation subscriptions, online status), crawling the full post history (toots) of every instance reachable in May 2018, and scraping follower relationships to build both a user-level follower graph and a derived instance-level federation graph (an edge from instance A to instance B exists if at least one user on A follows a user on B). They then run node-removal simulations on these graphs: iteratively strip the highest-ranked instances or hosting providers (Autonomous Systems, the routing-visible network blocks instances are hosted within) and measure the size of the largest connected component (LCC, the largest set of nodes still mutually reachable) and the number of disconnected components after each removal round. They separately simulate three toot-replication strategies — no replication (a toot exists only on its home instance and is fetched on demand), subscription-based replication (a toot is copied to every instance that has at least one user following its author, matching Mastodon's own caching behavior but assuming, unlike Mastodon, a global index such as a Distributed Hash Table so replicas remain discoverable), and random replication onto n randomly chosen instances — and measure toot availability under the same removal rounds.

### Parameters
LCC-removal simulations proceed in rounds removing the top 1% of remaining nodes per round for the user follower graph, and top-N instances or top-N ASes (N swept from small values up to several hundred/800+ instances and up to 20+ ASes) for the instance federation graph. Random-replication factor n tested at {1, 2, 3, 4, 7, 9} extra copies per toot. Ranking criteria varied across three axes for instance removal (number of users hosted, number of toots posted, number of instances hosted) and for AS removal (number of instances hosted, number of users hosted).

### Stated limitations
The dataset captures a moving target: because measurement infrastructure was deployed progressively, the exact time windows of the instance, toot, and follower datasets differ slightly, though the authors state this does not affect the analysis. The toot dataset covers only 62% of the toot population that instance-reported metadata indicates exists; the missing 38% is split between toots marked private (about 20%) and toots on instances that blocked crawling (the remainder), and the authors state they therefore avoided deeper semantic content analysis and confined themselves to instance-level activity. It is impossible to determine whether two accounts with the same name on different instances belong to the same person, so the authors treat every per-instance account as a separate graph node. The authors cannot confirm the exact cause of most instance unavailability, nor determine which operators run load balancers or replicated back-ends behind their instance. AS-wide removal is presented explicitly as a rare, worst-case theoretical scenario rather than a routine failure mode, though six such events were observed within the 15-month measurement window. The random and subscription replication simulations assume every toot is treated as equally important, though the authors note more recent toots are in practice more important; they also assume a global index (e.g. a Distributed Hash Table) exists to make any surviving replica discoverable, a mechanism Mastodon does not currently implement, since Mastodon's own subscription-based caching keeps replicas visible only to users local to the caching instance. The random replication strategy as tested does not weight replica placement by an instance's available storage; the authors state this is a practical concern for a real deployment. Future work stated by the authors: a longitudinal study of the same issues over a longer period, mitigations for malicious bots, an evaluation of Mastodon's existing instance-blocking mechanism and its effect on the social graph, and a study of alt-right community migration onto Mastodon-derived forks such as Gab.

### Requirements it places on the rest of the system
A replication mechanism intended to improve content availability under instance or AS failure requires a global index reachable from any surviving instance, because a replica that exists only on instances that also fail, or that is invisible outside the instance that cached it (Mastodon's current subscription-cache behavior), does not restore availability; the paper's own subscription-replication figures assume such an index and are not achievable under Mastodon's actual current caching visibility. A component performing follower-graph-driven (subscription-based) replication inherits the skew of the underlying social graph: because popular authors' followers cluster on the same small set of popular instances, subscription-based replica placement concentrates replicas on exactly the instances most likely to be targeted or to fail together in an AS-wide event, and any resilience analysis of that replication strategy must account for this correlated placement rather than assuming independent replica locations. A capacity-ordered or hosting-diversity mechanism placed above the federation layer needs per-instance hosting-provider (AS) information, since AS-level co-location, not merely instance count, determines how much connectivity a single correlated failure can remove. Any content-location or discovery mechanism relying on the federation subscription graph for reachability must tolerate a linear (not catastrophic) degradation under ordinary instance-count removal, but should expect a step-function collapse in reachability specifically when removal is concentrated on a small number of hosting providers with disproportionate user share, since the paper measures a materially worse component-count outcome (272 vs. 139 components after removing 5 ASes) when providers are ranked by user share rather than by instance count.
