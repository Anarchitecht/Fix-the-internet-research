## [REVUELTA-DLT-24] Message Latency in Waku Relay with Rate Limiting Nullifiers
**Citation:** Alvaro Revuelta, Sergei Tikhomirov, Aaryamann Challani, Hanno Cornelius, Simon Pierre Vivier. "Message Latency in Waku Relay with Rate Limiting Nullifiers." Distributed Ledger Technology Workshop (DLT), 2024. DOI: not recorded in registry.
**Retrieved:** full text via https://ceur-ws.org/Vol-3791/paper25.pdf
**Source URL:** https://ceur-ws.org/Vol-3791/paper25.pdf
**Domain:** I

### What it does
The paper measures the message-propagation latency added by attaching a Rate Limiting Nullifier (RLN) zero-knowledge proof to every message gossiped over Waku Relay, a GossipSub-based publish-subscribe layer. RLN enforces a shared publishing rate limit without identifying publishers: a publisher registers a commitment c = H(sk) (H is the Poseidon hash) against an on-chain smart contract, paying a one-time on-chain registration fee that raises the cost of creating multiple identities; every relaying node maintains a local Merkle tree of all currently valid commitments, kept in sync through Ethereum RPC calls. To publish, a node computes an epoch value from the current time divided by the rate-limiting interval, an external nullifier from a hash of the epoch and an application-specific rln_identifier, an internal nullifier from a hash of its own secret key and the external nullifier, and a zero-knowledge proof that it holds a valid membership for the current epoch; it attaches the proof, both nullifiers, the epoch, and the Merkle root to the message. Each relaying node accepts a message only if the proof verifies, no other message relayed within the last g seconds (g = 20 s in the deployed configuration) carried the same internal nullifier, and the epoch is within g seconds of the node's own clock; a node that forwards an invalid message has its GossipSub peer score lowered until it is eventually isolated, which the paper states discourages a node from relaying on a spammer's behalf. The paper's own contribution is measurement, not the RLN mechanism: it builds an analytical latency model splitting end-to-end delay into proof-generation time at the publisher, per-hop transmission time, and per-hop validation (proof-verification plus decoding) time at each relay, then checks that model against a 1,000-node single-host simulation and a five-node real-world multi-host deployment.

### Parameters
Merkle tree depth for the RLN membership set: 20, fixed across all experiments per the RLN protocol specification the paper cites, described as a trade-off between anonymity-set size and proof-generation/verification cost. Maximum epoch gap g (rate-limit window and nullifier-collision window): 20 seconds, stated as the current deployed value. GossipSub mesh degree bounds in deployed Waku: D_low = 4, D_high = 12; typical target D = 6 (cited from libp2p documentation as "the ideal network peering degree"). Single-host simulation: N = 1,000 nodes, target mesh degree D = 6, 25 additional gossip-only peers per node, 100 Mbps upstream/downstream bandwidth per node, 150 ms simulated per-link latency, 10 publisher nodes. Multi-host deployment: N = 5 nodes, static linear topology (no peer discovery), Digital Ocean 8 GB RAM / 4 vCPU machines, path length h = 4 hops, message sizes tested 2, 25, 100, and 500 KB, 5 runs per message size.

### Stated limitations
The paper states its analytical model assumes a stable, regular-degree full-mesh topology and explicitly excludes node churn (nodes joining and leaving), naming investigation of churn's effect on propagation latency as future work. The paper states its measurements cover only low message-publishing rates and explicitly excludes the effect of higher rates, which the authors expect to increase GossipSub control-message overhead and processing load; this is stated as unexamined, not measured. The current nwaku implementation is stated not to support the economic slashing-of-deposit punishment for malicious publishers described in the original RLN proposal, so a misbehaving publisher whose messages are dropped for reused nullifiers faces no on-chain financial consequence in the deployed system, only network-level isolation via lowered GossipSub score. The paper states the RLN membership Merkle tree must currently be constructed and maintained locally by every publisher and verifier, which it states may be impractical for resource-restricted nodes, and reports the authors are investigating (not yet built) a design where the tree lives entirely on-chain to allow delegated proof generation. The paper states its 4-hop-suffices simulation finding used only 10 of 1,000 nodes as publishers and did not test adversarial conditions, node faults, network failures, or clock desynchronization, naming these as future work rather than tested cases. The simulation is stated to underestimate latency for 100 KB and 500 KB messages because the Shadow framework does not model CPU time for message decoding (only the benchmarked proof-verification time is injected), and conversely to overestimate latency for small (2 KB) messages, a discrepancy the authors attribute to this same CPU-time-modeling gap rather than to a flaw in the underlying RLN mechanism.

### Requirements it places on the rest of the system
Every relaying node must maintain a locally synchronized copy of the current RLN Merkle tree of valid commitments, which requires either an Ethereum RPC provider connection (the paper names Infura and Alchemy as examples) or the node running its own Ethereum execution client; a node lacking this synchronization cannot validate incoming proofs correctly. The rate-limit and replay-detection mechanism (the nullifier-collision check) requires every participating node's local clock to stay within the fixed epoch-gap window (20 s in the deployed system) of the network's shared time reference, which the paper's own multi-host experiment satisfies only by adding NTP synchronization; a node whose clock drifts beyond that gap will reject valid proofs or accept expired ones. The rate-limiting property depends on GossipSub's separate peer-scoring mechanism to enforce the consequence of relaying invalid messages (score reduction leading to eventual isolation); RLN itself only supplies the validity check; a network without a scoring/isolation layer underneath RLN gets proof verification but no consequence for relaying-node misbehavior. The measured latency figures assume TCP transport with an already-negotiated window and established handshake between neighboring nodes (the first two published messages were excluded from measurement to remove this effect); a system with a different transport or high per-hop connection churn would not inherit these latency figures unmodified. The underlying spam-resistance property depends on the on-chain registration step remaining an actual (non-zero) cost to acquire a membership commitment; the paper states this fee, not the zero-knowledge proof itself, is what deters an attacker from registering unlimited identities.

### Contradicts
None found. No other entry in this batch measures Waku, RLN, or GossipSub latency, and this paper's central claim (RLN proof-related overhead is not the dominant cost, and is tolerable relative to end-to-end message latency) is not disputed by anything else here.

### References worth retrieving
- Whitehat, Taheri, Thoren, Kilic, Dimovski, "Rate Limit Nullifier," vacp2p RFC (rln-v1), cited [18] — foundational: the RLN protocol specification this paper's implementation follows and whose original economic-slashing design nwaku does not yet implement.
- Grassi, Khovratovich, Rechberger, Roy, Schofnegger, "Poseidon: A new hash function for zero-knowledge proof systems," USENIX Security 2021 — foundational: the hash function used for RLN's commitment and nullifier construction.
- Decker, Wattenhofer, "Information propagation in the bitcoin network," P2P 2013 — competing: prior latency-measurement methodology for a different gossip-based P2P network, cited as related work this paper's methodology follows.
- Neudecker, Andelfinger, Hartenstein, "Timing analysis for inferring the topology of the bitcoin peer-to-peer network," IEEE ATC 2016 — competing: independent latency/topology measurement on a comparable gossip network.
- Zhang, Lee, Ye, Qiao, "Evaluation of ethereum end-to-end transaction latency," NTMS 2021 — competing: comparable latency-measurement study on a related GossipSub-based network (Ethereum).
- Gluhovsky, "EIP-627: Whisper specification," 2017 — attack/superseded-by: prior proof-of-work-based spam-rate-limiting scheme for general-purpose messaging that the paper states "has not gained popularity," relevant as the direct predecessor mechanism RLN replaces.
- Unger, Dechand, Bonneau, Fahl, Perl, Goldberg, Smith, "SoK: Secure messaging," IEEE S&P 2015 — foundational: cited survey of decentralized/federated messaging protocol properties, relevant to comparing Waku's design goals against federated alternatives (ActivityPub, Matrix, Nostr, XMPP, AT Protocol, Farcaster) named in the same section.
