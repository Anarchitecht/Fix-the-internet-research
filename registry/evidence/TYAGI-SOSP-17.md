## [TYAGI-SOSP-17] Stadium: A Distributed Metadata-Private Messaging System
**Citation:** Nirvan Tyagi, Yossi Gilad, Derek Leung, Matei Zaharia, Nickolai Zeldovich. "Stadium: A Distributed Metadata-Private Messaging System." ACM SOSP, 2017. DOI 10.1145/3132747.3132783.
**Retrieved:** full text via https://people.csail.mit.edu/nickolai/papers/tyagi-stadium.pdf
**Source URL:** https://people.csail.mit.edu/nickolai/papers/tyagi-stadium.pdf
**Domain:** G

### What it does
Stadium delivers point-to-point messages while hiding metadata (which users communicate with which) from a network-level adversary, scaling the work of doing so across hundreds of independently operated, low-cost servers rather than concentrating it on a small trusted pair as Vuvuzela does. It bounds what the adversary learns using differential privacy: cover ("noise") traffic is added so that the observable traffic pattern for any two distinct communication patterns is statistically close, quantified by a privacy parameter epsilon (information leaked) and a failure probability delta. Servers are organized into "mixchains" — small ordered groups of servers, each belonging to a different, presumed non-colluding provider — and every message passes through one input mixchain and one output mixchain. Within a chain, each server permutes and re-encrypts (mixes) the batch of messages it receives using Bayer and Groth's verifiable shuffle protocol (a zero-knowledge proof that a claimed permutation and re-encryption were performed correctly), made non-interactive via the Fiat-Shamir heuristic and instantiated over the Curve25519 elliptic-curve group; this lets every other server in the chain — honest or not — check that the shuffle was executed correctly, without needing to trust the shuffling server itself. A message travels through seven processing phases per round: input, input-chain mixing, distribution (all-to-all exchange between input and output chains), output-chain mixing, an exchange step where messages are dropped at shared per-conversation "dead-drops" hosted by the output chain, and the reverse path back to the two conversing users, undoing each chain's permutation. Two users exchange messages only if they route to the same output chain and dead-drop, a restriction the paper states is required by its privacy analysis. Noise is generated in a distributed way (§8, not detailed in this extraction) so that no single server, honest or corrupt, needs to inject all the cover traffic Vuvuzela's two-server design requires. Verifiable processing lets a single honest server per chain detect corrupted or improperly mixed messages and abort or flag the round; the protocol's differential-privacy guarantee, and hence Stadium's metadata privacy, holds only if this per-chain honest-server condition is met.

### Stated limitations
The paper explicitly states that, due to time and cost constraints, it did not evaluate configurations larger than 100 servers directly; figures beyond 100 servers are extrapolations that assume Stadium's observed near-linear latency scaling continues, obtained by proportionally halving per-server load and linearly interpolating. It states that individual servers lacked sufficient memory to support very large message batch sizes at small server counts, so small-server-count deployments could not be fully benchmarked, and the paper separately notes that small numbers of servers are impractical for deploying Stadium. The prototype does not support real client message input — server-side message generation is simulated by having each server generate its own share of "client" messages — and the implementation excludes verifiable decryption and has no fault tolerance. Stadium is explicitly not resistant to wide-scale denial-of-service: the paper states this follows unavoidably from its own assumption that an adversary can block traffic on any network link, though it guarantees that a denial-of-service attack does not compromise the privacy guarantee. Stadium's core security property (metadata-privacy through differential privacy) depends on every mixchain containing at least one honest server; the paper evaluates only the probability of this condition holding under a random-assignment policy and an assumed upper-bound adversarial-server fraction f, not a proof that any particular real-world deployment satisfies it. The paper assumes a public-key infrastructure already exists (server public keys known to users) and assumes two communicating users already share a secret key, citing Alpenhorn as an external candidate mechanism for establishing that shared secret rather than building one itself.

### Requirements it places on the rest of the system
Stadium requires servers to be organized into mixchains such that servers within one chain belong to providers assumed unlikely to collude, and requires at least one server per chain to be honest and to follow the verifiable-shuffle protocol — the differential-privacy guarantee does not hold, and the paper does not claim it holds, if every server in some chain is adversarial. It requires two communicating users to independently select the same output chain and dead-drop for their messages to be exchanged, which the paper states is a restriction imposed directly by its privacy analysis, not an incidental implementation detail — any application layered on Stadium must supply or agree on this shared routing coordinate out of band. It requires a public-key infrastructure delivering authentic server public keys to users, and requires users to already hold a shared secret key with their communication partner before using Stadium — key establishment is out of scope and delegated to an external system (the paper names Alpenhorn). It requires standard cryptographic primitives under the random oracle model: public-key and symmetric encryption, key exchange, digital signatures, and hash functions. Chain length is a security-performance trade-off that must be set by the deployment: a longer chain lowers the probability that every server in some chain is adversarial (falling exponentially in chain length under the stated union-bound analysis) but raises per-message latency with a quadratic term from all-to-all proof verification within the chain, so any composed system choosing a chain length is trading measurable latency against a measurable compromise probability, not a free parameter.

### Contradicts
None found within this batch. The paper's own comparison figures for Vuvuzela (10 million users at 200 s latency, "more than nine minutes" for 30 million users) are drawn from Vuvuzela's own reported best-projected performance rather than an independent re-measurement by this paper's authors, which should be noted when this paper's comparative claims are cited as evidence about Vuvuzela's behavior specifically.
