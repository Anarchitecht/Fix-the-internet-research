## [ADAMS-ARXIV-25] DistributedANN: Efficient Scaling of a Single DiskANN Graph Across Thousands of Computers
**Citation:** Philip Adams, Menghao Li, Shi Zhang, Li Tan, Qi Chen, Mingqin Li, Zengzhong Li, Knut Risvik, Harsha Vardhan Simhadri. "DistributedANN: Efficient Scaling of a Single DiskANN Graph Across Thousands of Computers." Proceedings of the 1st Workshop on Vector Databases at ICML, 2025 (arXiv:2509.06046). DOI 10.48550/ARXIV.2509.06046.
**Retrieved:** full text via https://arxiv.org/pdf/2509.06046
**Source URL:** https://arxiv.org/pdf/2509.06046
**Domain:** B

### What it does
DistributedANN serves approximate nearest-neighbor (ANN, retrieving the k data vectors closest to a query vector without an exhaustive scan) search over a single vector-similarity graph index that spans over a thousand machines, rather than partitioning the dataset into independently searched shards. It builds on DiskANN, an ANN index designed to minimize round-trips to solid-state disk (SSD) by storing, per vector: a compressed representation kept in memory for cheap candidate scoring, and a full-precision vector plus its list of graph out-neighbors on disk. DistributedANN treats a distributed key-value store as the storage layer holding one graph node per key, and separates the system into three services: an in-memory head index (a smaller ANN index built by breadth-first traversal over the top layers of the full graph, used to produce good starting points for beam search and avoid the extra network hop a disk-resident node cache would otherwise cost on every cache hit); a near-data node-scoring service, run co-located with each key-value store host, that computes each candidate's distance to the query and returns only the resulting scores and IDs (not full node data) over the network; and an orchestration service that issues an initial search against the head index, then runs H rounds of beam search by taking the current best BW candidates, sending their keys to the node-scoring service, and merging returned results into bounded-size result and candidate heaps.

Two index-layout changes make this distributed decomposition work. First, the compressed vector of every graph node is duplicated into every other node that lists it as a neighbor, so a search never needs a second network round trip to fetch a candidate's compressed representation; this multiplies storage per vector by a factor the paper derives as (1+R)·sizeof(id)+d+R·d_OPQ, divided by R·sizeof(id)+d, which the paper evaluates at approximately 10x for its production parameters (R=100, d=384, d_OPQ=64, 8-byte IDs). Second, because only scores (not full node contents) cross the network from the node-scoring service to the orchestrator, network bandwidth per candidate is reduced by a factor the paper derives as (1+R)·(sizeof(id)+sizeof(score))+d+d_OPQ, divided by (1+R)·sizeof(id)+d+R·d_OPQ, evaluated at approximately 6x under the same parameters.

To build the graph without the prohibitive cost of full incremental insertion at multi-billion-vector scale, the system first builds an index using conventional clustered partitioning, inserting vectors that lie in the closure of multiple clusters into every one of those clusters' sub-indexes (graph stitching, following Subramanya et al. 2019 and Wang 2021). It then unifies these partition-local graphs into one graph by taking the union of each shared vector's neighbor lists across all the partitions it appears in. The head index is built from the union of the top layers of every partition's graph, not from the stitched graph's own top layer, to guarantee full-graph reachability. The paper states this stitched graph is of lower quality than one built entirely incrementally, but sufficient for good results and much faster to build.

### Parameters
- Production DistributedANN configuration: H (beam-search hop count) = 5, BW (beam width) = 128, R (graph out-degree) = 72 (only the first 72 of the ingested neighbors are kept, to reduce storage), k = L (result / candidate heap size) = 200, k_head (head-index result count) = 200, head index size = 2.5 billion vectors, out of a 50-billion-vector index slice.
- Production clustered-partitioning baseline: 203 total partitions of roughly 200 million vectors each, top 40 partitions selected per query, per-partition I (IO budget) = 120, BW = 6, R = 106, k = L = 120.
- Grid-search sweep for the recall/IO frontier (Figure 4): DistributedANN H from 4 to 8, BW = 32i for i from 3 to 6; clustered partitioning selected-cluster count N in {20, 25, 30, 40, 50, 60}, IO-per-cluster M = 32i for i from 2 to 6.
- Vector geometry used for the derived amplification/bandwidth-savings formulas: R=100 neighbors, d=384 full-precision dimensions, d_OPQ=64 compressed (OPQ, Optimized Product Quantization) dimensions, 8-byte vector IDs.
- Node-scoring-service failure-rate sweep for the reliability test: 100%, 99%, 98%, 97%, 96% availability.
- Production hardware, per host (mixed SKU pool, shared with other workloads): 256-768 GiB memory, 5-10 TiB SSD, roughly 200 IOPS per GiB of SSD, 32-64 physical cores, 40 Gbps network bandwidth.
- Dataset: one slice of the production Bing web index, roughly 50 billion 384-dimensional int8 vectors.

### Stated limitations
The paper states the head index becomes CPU-bound before the node-scoring service does at 3 replicas, an identified bottleneck in the current implementation; the deployed mitigation is adding more head-index replicas, which the paper states does not increase total machines needed because the head index is small relative to the full system's SSD-space bound. The compressed-vector duplication introduces roughly a 10x space amplification relative to conventional DiskANN under the paper's stated parameters; the paper lists reducing this overhead (for example, by placing several nearby full-precision vectors into one graph node) as future work still needing experimentation to understand its tradeoffs. The system uses standard kernel-based TCP networking for its remote service calls; the paper states kernel-bypass networking would likely reduce tail latency significantly but has not been implemented. The paper states that GPU-resident ANN systems offer very competitive price-to-performance at billion-scale but still cannot fit an index of this scale in a single machine's memory and eventually hit the same linear-scaling and operational-complexity issues as other partitioned indices; it does not claim DistributedANN dominates GPU systems in general, only that the scaling tradeoff favors DistributedANN for the paper's own scenario. The paper explicitly states it has not empirically compared DistributedANN against advanced partitioning schemes that reduce cross-partition graph edges (citing Dong et al. 2019 and Gottesbüren et al. 2024), and states those schemes may be preferable specifically in latency-constrained scenarios where DistributedANN's multi-hop network overhead is unacceptable. Deployment is within a single cloud region across machines with inter-zone latency up to 2 ms and oversubscribed cross-rack bandwidth; the paper states performance would improve, and shared-memory compressed-vector storage might become feasible (eliminating the amplification cost), on a dense fully-connected cluster, but this has not been tested. The system was designed for relatively high-traffic serving; the paper states further storage tiering to hard-disk drives (HDDs) may be needed for datasets with many mostly-cold tenants, such as per-user indices, and has not been built.

### Requirements it places on the rest of the system
The system requires a distributed key-value store with per-key durability and availability properties adequate for serving graph-node reads under load; the paper explicitly relies on this being a well-understood, separately operated component (citing Amazon Dynamo) rather than building its own storage layer. The reliability results assume node-scoring requests can be safely timed out under tail latency without materially harming recall — measured recall degradation was roughly proportional to failure rate down to 96% availability, not tested below that. The design assumes queries are served against a mostly-static or incrementally-stitched graph; the graph-stitching build process assumes an initial clustered-partitioning pass has already been computed and produces closures of vectors shared across multiple clusters, so any online-insertion story for a live system needs a separate mechanism, not evaluated here, since the paper explicitly states pure incremental insertion into the unified graph would need significantly more computation than building an equivalently sized partitioned graph. The compressed-vector-duplication and score-only-network-transfer optimizations both assume the operator can dedicate roughly 10x storage amplification and can co-locate the node-scoring computation with the storage host — a system without control over storage-host code placement (as in an untrusted peer storage layer) could not deploy the near-data scoring service as described. The described threat model is entirely a managed, trusted-cluster deployment: no participant identity is authenticated as adversarial-resistant, no mechanism defends against a storage host returning corrupted node data or false distance scores, and load balancing depends on the key-value store's random sharding producing a predictable, non-adversarial traffic distribution across hosts.

### Contradicts
None found — this is the first entry in the corpus addressing distributed approximate-nearest-neighbor graph indices at this scale; no other entry reports a conflicting recall, latency, or IO figure for the same or a comparable system. The paper's own reliability section states the common intuition that a distributed architecture is more fragile than a monolithic partitioned one does not hold for this design: measured recall degradation under synthetic node-scoring failures was described as "graceful," in contrast to the paper's own description of a conventional partitioned service, where losing one partition causes "a dramatic drop in search quality" because a large fraction of the dataset becomes entirely unreachable for that query.
