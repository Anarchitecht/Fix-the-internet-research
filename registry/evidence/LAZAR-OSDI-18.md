## [LAZAR-OSDI-18] Karaoke: Distributed Private Messaging Immune to Passive Traffic Analysis
**Citation:** David Lazar, Yossi Gilad, Nickolai Zeldovich. "Karaoke: Distributed Private Messaging Immune to Passive Traffic Analysis." USENIX OSDI, 2018.
**Retrieved:** full text via https://people.csail.mit.edu/nickolai/papers/lazar-karaoke.pdf
**Source URL:** https://people.csail.mit.edu/nickolai/papers/lazar-karaoke.pdf
**Domain:** G

### What it does
Karaoke hides which pairs of users communicate over text messaging from an adversary that controls the network and some fraction of the system's servers, at latency close to an order of magnitude lower than prior metadata-private designs (Vuvuzela, Stadium) at the same user count. Communication happens in fixed-length rounds. Each user sends and receives one message per round through a "dead drop," a location identified by a server and a per-round pseudorandom identifier; two users share a dead drop by prior agreement on a shared secret, and a user with no active conversation sends cover traffic to a randomly chosen dead drop. N servers are arranged in a full mesh and organized into l sequential layers; each message is onion-encrypted under the public keys of a client-chosen random path of servers, one per layer, so a message cannot be read until it has passed the honest servers on its path. Each layer decrypts one onion layer of every message it holds and re-orders the messages before forwarding, so a server's output order does not correlate with its input order (a parallel mixnet structure). At the final layer, the server holding a dead drop swaps the two messages addressed to it, so the server does not learn which of the two users sent which message.

To supply the noise messages that differential privacy requires without paying the cost of verifying every server actually sent its assigned noise, Karaoke uses two techniques. Optimistic indistinguishability lets the protocol assume, in the common case, that no messages are lost, revealing no information to the adversary; a client can detect precisely when a message it sent was lost (by checking a Bloom filter, described below) and only then does correlated information get revealed, so clients can switch to an idle mode after a detected loss to bound the number of future rounds in which loss-driven leakage can occur. Efficient noise verification lets each server generate noise messages independently and prove those messages were not later discarded, without a verifiable shuffle proof for every message: each server computes a Bloom filter (Bloom, 1970) over all ciphertexts it received during a round and sends this filter to every other server. If a server's own generated ciphertexts all appear in every other server's Bloom filter, it can conclude its noise was not dropped, without any server having to reveal which ciphertexts in its filter were noise versus real user traffic. The Bloom filter is deliberately imprecise (10% false-positive rate as configured) rather than a precise inclusion proof, because a false positive only costs slightly more noise, not a privacy violation.

Karaoke's privacy guarantee is stated as computational differential privacy: for any pair of users, the probability the adversary's observations are consistent with the pair having communicated is within a multiplicative factor e^epsilon and additive factor delta of the probability the observations are consistent with the pair not communicating.

### Measured results
Hardware: Amazon EC2 c5.9xlarge instances (36 Intel Xeon 3.0 GHz cores, 72 GB memory, 10 Gbps links) for the primary experiments; c4.8xlarge instances used additionally to match the instance type used by the Vuvuzela and Stadium papers for direct comparison. All server VMs placed in the same data center; 100 ms round-trip network latency added via `tc qdisc` to simulate a realistic geographically distributed deployment (the paper states this approximates US-to-Europe round-trip time). An additional coordinator VM starts each round and injects probe messages to measure round-trip latency. Millions of simulated users are generated as extra first-layer messages produced directly by servers (pre-generated before the round starts), not by launching that many client VMs. Unless stated otherwise, 80% of servers are assumed honest, which the paper's parameter selection translates into a 14-layer path length; Bloom filters are tuned to a 10% false-positive rate.

Prototype: approximately 4,000 lines of Go (compiled with Go 1.11); onion decryption implemented in native amd64 assembly via Go's NaCl library; gRPC over TLS for server-to-server communication, using streaming and batched RPCs over multiple TCP connections.

End-to-end latency versus number of users (Figure 6), 100 Karaoke servers, 3 Vuvuzela servers (Vuvuzela's own paper reports its latency does not improve with more servers), Stadium at 100 servers with chain length 9, Vuvuzela and Stadium figures as reported in their own papers:

| 2M | 6 s | 6 s | 10 s | 68 s |

| 6M | 7 s | 10 s | — | 136 s |

At 2M users, Karaoke achieves 5x lower latency than Vuvuzela and 8x lower latency than Stadium (on the weaker c4 instance type, matching the instance type used in the Vuvuzela/Stadium papers). At 16M users, Karaoke achieves 10x lower latency than Stadium. The paper attributes Karaoke's better scaling with user count to only a fraction of Karaoke servers handling each additional user's messages (versus every Vuvuzela server handling every message) and to Karaoke's marginal per-message cost being onion decryption and bandwidth rather than Stadium's per-message zero-knowledge proof.

Scaling by adding servers (Figure 7): with a fixed ratio of 25,000 users per server, latency across N = 50, 60, 80, 100, 150, 200 servers stays in the 6-12 second range and decreases slightly as server count grows, because more servers require less noise per server for the same privacy target (Figure 5's relationship).

Effect of honest-server fraction (Figure 8), fixed at 2M users and 100 servers: required path length l rises and end-to-end latency rises as the assumed honest fraction falls from 90% toward 30%. The paper states latency is acceptable for text messaging down to 60% assumed-honest, and states Karaoke "would not be a good fit" below 30% assumed-honest, without giving a latency figure for that point in the extracted text.

Ablation of Karaoke's two core techniques, both isolated at fixed workloads: (1) without optimistic indistinguishability, each server would need to add approximately 320,000 noise messages per server per round for the same privacy level, and end-to-end latency at 2 million users rises from 6.8 s to 31 s. (2) without Bloom-filter noise verification (substituting verifiable shuffles as in Stadium), at 6 million users and 100 servers each Stadium-style server spends 6 s generating a verifiable shuffle and 2 s verifying one at each hop, versus 250 ms for Karaoke's Bloom filter generation and checking at each hop; substituting verifiable shuffles into Karaoke's own 14-hop path would add roughly 2 minutes of latency (8 s per hop across 14 hops).

Parameter selection (§6.1): target epsilon = ln(4), delta = 10^-4, after 10^8 communication rounds of which 245 rounds are assumed to encounter message loss during a sensitive conversation. At the deployed configuration of N=100 servers, h = floor(0.8N) = 80 honest servers, route length l=14, each server generates a mean of N^2*lambda1 + N^2*lambda2 = 25,000 noise messages per round (from Figure 5, delta=10^-4 fixed, over the 10^8-round/245-loss composition).

Network-loss measurement (§7.6): probing one Karaoke server every 2 minutes for one day from 100 RIPE Atlas vantage machines distributed globally, 3 ping packets per probe spaced 1 second apart. 71,194 total probe results: 70,106 received all 3 responses, 991 received 2, 60 received 1, 37 received 0 (a complete connectivity loss). Complete losses clustered into bursts across 8 distinct machines (7 machines with one burst, 1 machine with two bursts). The paper extrapolates roughly 9 message-loss events per 100 days, or about 33 per year, per client, which it states is about an order of magnitude below the 245-round loss budget the chosen (epsilon, delta) parameters were designed to tolerate.

### Parameters
- Round-based communication; round length not stated as a fixed number of seconds in the extracted text (latency figures above are the measured per-round completion times under load).
- N = 100 servers in the primary deployment configuration (also tested 50-200 in the server-scaling experiment).
- Honest-server fraction h/N = 80% assumed in the default configuration (tested down to approximately 30-90% in the honest-fraction experiment).
- Path length (number of mix layers) l = 14 at 80% assumed-honest; l varies with the assumed honest fraction per Figure 8 (exact l values at other honest fractions not given as a table in the extracted text).
- Differential-privacy target: epsilon = ln(4), delta = 10^-4, over 10^8 rounds with a budget of 245 rounds of tolerated message loss during a sensitive conversation.
- Bloom-filter false-positive rate: 10%.
- Noise messages generated per server per round at N=100, h=80, l=14: approximately 25,000 (N^2*lambda1 + N^2*lambda2).
- Simulated network latency between servers: 100 ms round-trip, added via `tc qdisc`, to approximate a US-Europe geographic deployment.

### Stated limitations
Karaoke does not provide fault tolerance: it requires all servers to be online for a round to complete, and the paper states handling server outages and denial-of-service attacks is left to future work. Karaoke does not hide that a given user is using the system at all — an adversary observing a connection to a Karaoke server learns the user is a Karaoke user, though the paper states it hopes a large user population makes this fact alone less identifying. Karaoke makes no availability guarantees and states defending against denial-of-service attacks is future work. If an adversary compromises a user's own computer, Karaoke provides no privacy guarantee for that user's communications. Karaoke assumes clients already know the public keys of all servers and assumes users can establish a shared secret and initiate a conversation out-of-band; the paper states a complete system would need a separate "dialing" protocol (citing its own prior work, Alpenhorn) to perform that bootstrapping, and that bootstrapping protocol would add its own bandwidth and latency cost not accounted for in these measurements. Message loss is the primary channel through which information leaks; loss can come from an active attack or from a network outage long enough that TCP cannot recover, and the paper states it expects users to avoid sensitive conversations over highly unreliable network paths. The measured 33-events-per-year loss rate is drawn from probing one specific Karaoke deployment over RIPE Atlas for one day, an approximation, not a controlled adversarial measurement.

### Requirements it places on the rest of the system
Requires every server on a message's chosen path to participate honestly in decrypting and re-shuffling within its assigned layer; a message cannot be decrypted by an adversary who does not control every server on its path, but the overall privacy guarantee assumes a globally known, fixed set of N servers with h of them honest, so the system needs a mechanism (not supplied by this paper) to establish and distribute that server set and its public keys to every client before a round can run. Requires synchronous rounds across all N servers — a round only completes once every server has finished processing its layer — so any deployment needs a coordination mechanism to start rounds and detect a stalled server, which the paper states is unhandled (no fault tolerance). Requires TCP-level reliable delivery between client and server within a round; momentary packet loss is tolerated but an extended outage causes the client to miss the round, which the privacy analysis treats as a bounded, budgeted event (245 rounds) rather than an unbounded one. Requires an out-of-band channel supplying the initial shared secret (dead-drop schedule) between two users who wish to communicate; Karaoke provides no mechanism for this itself. Requires the adversary to be unable to break the underlying cryptographic primitives (standard cryptographic hardness assumption) and requires computational, not information-theoretic, differential privacy as a consequence of relying on cryptography for the onion encryption.

### Contradicts
None found within this corpus for the measured latency figures themselves. Karaoke's own comparison figures for Vuvuzela and Stadium are stated as drawn from those papers' own reported numbers, not independently re-measured by this paper on the same hardware for those two systems (only Karaoke's own c4/c5 comparison is apples-to-apples).
