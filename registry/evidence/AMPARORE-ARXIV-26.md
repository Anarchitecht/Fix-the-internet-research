## [AMPARORE-ARXIV-26] Range-Based Set Reconciliation via Range-Summarizable Order-Statistics Stores
**Citation:** Elvio G. Amparore. "Range-Based Set Reconciliation via Range-Summarizable Order-Statistics Stores." arXiv preprint, 2026. DOI 10.48550/arXiv.2603.19820.
**Retrieved:** full text via https://arxiv.org/pdf/2603.19820
**Source URL:** https://arxiv.org/pdf/2603.19820
**Domain:** D

### What it does
The paper reduces the local computational cost of Range-Based Set Reconciliation (RBSR) by specifying the exact storage-backend interface RBSR needs and by building a concrete implementation of that interface. RBSR is a set-reconciliation protocol (introduced by Meyer, already in this corpus as the range-based set reconciliation citation) in which two replicas holding ordered sets compare a compact summary of each contiguous key range; a range where the summaries agree is skipped, a small mismatching range is sent as an explicit list, and a large mismatching range is split by rank into balanced child ranges and compared recursively. The paper defines a Range-Summarizable Order-Statistics Store (RSOS): an ordered-set data structure exposing five operations — `size()`, `Aggregate(l,u)` (returning the count and a composable summary of the range), `Rank(z)` (count of elements below a value), `Select(r)` (the element at a given rank), and `Enumerate(l,u)` (the ordered contents of a range) — plus `Insert` and `Delete`. RBSR needs exactly this bundle: range aggregation to compare ranges, rank/select to cut a range into equal-cardinality children without rescanning it, and enumeration to resolve small mismatches directly. The paper proves that an aggregate-augmented B+-tree, where every internal-node child pointer also stores the cached pair (subtree element count, subtree composable summary), realizes an RSOS: `Rank` and `Select` cost O(h), `Aggregate(l,u)` costs O(Bh) (O(h) under a bounded page fanout B), `Enumerate(l,u)` costs O(h+k) for k returned elements, and `Insert`/`Delete` cost O(Bh), where h = Θ(log_B n) is the tree height for n stored elements — because each of these operations touches at most one root-to-leaf path plus, for updates, at most one split/merge/redistribution per level. Composing this per-operation bound over a full reconciliation gives a total local responder-side cost of O(Qh) for Q queried ranges, at fixed split fanout b and enumeration cutoff t (derivation in the paper's appendix). The paper implements this design as AELMDB (Anti-Entropy Lightning Memory-Mapped Database), an extension of the LMDB storage engine that stores the aggregate metadata directly in B+-tree branch-page node prefixes — selected per-database via flags for entry count, key count, and a fixed-size additive hash-sum — rather than in a separate auxiliary tree, and integrates it with Negentropy, a deployed RBSR protocol implementation used in the Nostr protocol's NIP-77 relay-synchronization specification and explored for Waku Sync. AELMDB additionally implements a window-subrange optimization (`MDB_agg_window`) that caches the mapping from a stable outer query range to its absolute rank interval, so repeated nested subrange queries inside that outer range avoid re-deriving the mapping from scratch.

### Measured results
All measurements ran on one machine: an AMD 3700X CPU under Linux, LMDB file mmap size 2048 MiB, Negentropy protocol parameters held fixed at split fanout b=16 and explicit-enumeration cutoff threshold t=32, 10 repeated reconciliations per benchmark instance averaged into one reported value, each instance run in an isolated fresh process. Four backends were compared, all executing the identical Negentropy/RBSR protocol logic over the same synthetic reconciliation workloads, differing only in how the RSOS oracle was realized: an in-memory Vector reference; BTreeLMDB, a baseline that computes range aggregates and rank navigation through a separate auxiliary tree layered inside LMDB; AELMDB, the paper's in-tree aggregate design plus window-subrange caching; and NoWndAELMDB, an ablation of AELMDB with the window-subrange path disabled. Six synthetic scenario families were used (base_dense, base_sparse, scale_dense, scale_sparse, stress, stress_dyn), each with 8 parametrically scaled instances (i=1..8) varying the size of the in-slice intersection, in-slice symmetric difference, and out-of-slice context on both sides; in the stress_dyn family both the in-slice intersection and in-slice symmetric difference grow quadratically in i (4096·i^2 and 1024·i^2 respectively).

The evaluation is explicitly scoped to single-machine, reconciliation-heavy workloads under one fixed protocol configuration; the paper states it does not characterize concurrent transactions, crash recovery, cold-cache behavior, or cross-engine portability, and reports no results for any of those conditions. All experiments verified computed reconciliation output against ground truth and confirmed byte-identical output across backends, so the reported speed and memory differences isolate storage-realization cost rather than reflecting different communication behavior.

### Parameters
- Negentropy split fanout b = 16 (paper states this is Negentropy's default value; held fixed across all backends in the evaluation, not varied).
- Explicit-enumeration cutoff threshold t = 32 (Negentropy default, held fixed, not varied).
- LMDB file mmap size: 2048 MiB, fixed for all benchmark runs.
- 10 repeated reconciliations per scenario instance, averaged into one reported value; no stated variance or confidence interval.
- Negentropy record identifier size: 256 bits; the composable summary is the modular sum of identifiers, mod 2^256, hashed with SHA-256 and truncated to the first 128 bits for the protocol-level comparison value.
- Six scenario families, each with 8 parametrically scaled instances (i = 1 to 8); exact per-family element-count formulas are given in the paper's Table 1 (for example, base_dense_i: 64i in-slice-shared elements, 4i in-slice-peer-only elements, 1000i out-of-slice-shared, 200i out-of-slice-peer-only).

### Stated limitations
The paper states a full end-to-end collision analysis of Negentropy's concrete comparison function (SHA-256 over the range aggregate, truncated to 128 bits) is outside its scope, and that this comparison rule is probabilistically sound rather than information-theoretically exact — a false SKIP can occur whenever two unequal ranges collide under the aggregate encoding or under hash truncation. The correctness proof for RBSR over RSOS (Proposition 4.1) is conditioned explicitly on an assumption that every SKIP decision is sound; the paper does not prove this assumption holds for Negentropy's concrete comparison function, only states the tradeoff exists. The evaluation is scoped to reconciliation-heavy, single-machine workloads and the paper states explicitly that it does not evaluate concurrent transactions, crash recovery, cold-cache behavior, or cross-engine portability, listing all four as left to future work. The RSOS abstraction and its bounds assume a bounded-page-size model (B = O(1) with respect to n) and O(1)-time aggregate-field combination; the paper does not state what happens to the derived bounds outside this model. Insertion (preparation) cost is higher for AELMDB than for the BTreeLMDB baseline in every tested scenario family (ratio 0.89x-0.96x, meaning BTreeLMDB is faster), attributed to AELMDB needing to propagate aggregate-delta updates along the entire root-to-leaf path on every write. The paper states the observed speedups are workload-dependent and that gains "will depend on workload characteristics, especially the balance between frequent reconciliation queries and the maintenance cost of aggregate metadata under updates," not a universal claim. The paper states an open question it does not resolve: how far the RSOS abstraction extends to comparison mechanisms other than homomorphic summary constructions, citing Meyer and Scherer's demonstration that RBSR can be realized using conventional (non-homomorphic) cryptographic hashes as a direction not covered by this paper's realization.

### Requirements it places on the rest of the system
RBSR over an RSOS backend requires the reconciling parties' data to be embedded in one totally ordered universe with a defined strict order relation, since every operation (Aggregate, Rank, Select, Enumerate) is defined over contiguous ranges of that order; Negentropy's concrete instantiation orders records lexicographically by (timestamp, 256-bit identifier), so any component storing data reconciled this way must expose that same ordering. The composable range summary requires the per-element contribution function ϕ to map into a monoid — an algebraic structure with an associative combining operation and an identity element — so that a range's summary can be computed by combining any partition of that range's sub-summaries; Negentropy's summary uses modular addition of 256-bit identifiers, which satisfies this by construction. The correctness of RBSR's SKIP decision (Proposition 4.1) requires that the protocol-level comparison function applied to two ranges' aggregates agrees only when the ranges are truly equal; a system substituting a different comparison rule (e.g., a smaller hash truncation) inherits a higher false-SKIP probability, a tradeoff this paper does not quantify for Negentropy's specific 128-bit truncation. Realizing an RSOS via the aggregate-augmented B+-tree construction requires the storage engine's tree to allow attaching fixed-size aggregate metadata to internal-node child pointers and to update that metadata along the insert/delete path; AELMDB does this by extending LMDB's on-disk branch-page format, so a different backend without an equivalent per-page metadata slot would need a separate auxiliary structure (as BTreeLMDB does), incurring the paper's measured 4.69x-13.98x reconciliation-time penalty. The window-subrange optimization requires the recursive reconciliation protocol to issue many queries against a stable, unchanging outer range; a protocol whose active-range set does not exhibit this locality pattern would not benefit from the measured 1.08x-1.27x speedup this component contributes.

### Contradicts
None found against other entries in this corpus. The paper explicitly draws a mechanism-level contrast, not a numeric contradiction, with AUVOLAT-SRDS-19 (Merkle Search Trees): it states Merkle Search Trees extend subtree-digest caching to ordered CRDT (Conflict-free Replicated Data Type) state by imposing a rigid, canonically derived tree representation of the data, whereas RBSR operates on logical ranges of an ordered set and drives its recursion by element order rather than by a predetermined canonical tree topology.
