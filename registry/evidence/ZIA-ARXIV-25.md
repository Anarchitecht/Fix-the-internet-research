## [ZIA-ARXIV-25] Collaborative Content Moderation in the Fediverse
**Citation:** Haris Bin Zia, Aravindh Raman, Ignacio Castro, Gareth Tyson. "Collaborative Content Moderation in the Fediverse." arXiv preprint arXiv:2501.05871, 2025. DOI 10.48550/ARXIV.2501.05871.
**Retrieved:** full text via https://arxiv.org/abs/2501.05871
**Source URL:** https://arxiv.org/abs/2501.05871
**Domain:** K

### What it does
FedMod lets Mastodon instances build a better local content-moderation classifier than any one instance could train alone, without any instance disclosing its labeled posts to another instance or to a central server. It runs three steps, repeated on a configurable interval t (default 24 hours):

1. Model initialization: each instance fine-tunes a local classifier (multilingual BERT, mBERT, 172M parameters, 714 MB storage) on its own small labeled set, for one of three moderation tasks — harmful-content detection, bot-account detection, content-warning assignment.
2. Peer selection: each instance picks k other instances to collaborate with. The paper's proposed selection method, hashsim, has each instance periodically fetch every other instance's weekly trending-hashtag list (via each instance's public Trends API) and compute Jaccard similarity between its own trending-hashtag set and each other instance's set, then picks the k instances with highest similarity as peers. A random-k baseline is also evaluated.
3. Parameter exchange: each instance requests model parameters from its k selected peers directly, peer to peer, with no central aggregator, and applies FederatedAveraging (McMahan et al.) locally to combine its own parameters with its peers' into an updated local model. Differential-privacy clipping (via the Flower federated-learning framework) is available to bound any one instance's influence on a peer's aggregated model.

For scalability, an optional pre-sampling step restricts the Jaccard-similarity computation to the top i instances by follow-count overlap (the number of the other instance's users followed by the local instance's own users) before computing hashtag similarity within that smaller set, avoiding all-pairs computation across every instance in the network.

### Measured results
Dataset: 50 Mastodon instances sampled from an 11,516-instance index (Fediverse Observer), split evenly between above-average and below-average user count (average across the full index: 1,162 users/instance); 219,577 unique posts by 44,840 users, collected March 1-June 21, 2023, across 17 languages (75.29% English, 17.73% German). Harmful-content labels came from the Perspective API (post flagged harmful if any of six emotional-attribute scores exceeded 0.5, a threshold matched to prior literature; a stricter 0.8 threshold gave similar relative results). Bot-content and content-warning labels were the platform's own self-declared/self-tagged metadata fields, not model-generated. Every reported model result used only 128 labeled posts per instance per task (8 online-learning steps of 16 posts each), chosen to represent what a volunteer administrator could plausibly label.

### Parameters
- Peer count k: default/primary evaluation k=2; also tested at k in {3, 4, 10}.
- Federation round interval t: 24 hours (default; not swept).
- Labeled posts per instance per task: 128 total (8 steps of 16), reported explicitly as an arbitrary, not derived, choice made to approximate what a volunteer administrator could realistically annotate.
- Base model: mBERT (172M parameters, 714 MB on disk); DistilmBERT and XLM-R (base) were compared in an appendix ablation and mBERT was selected for best macro-F1 among the three at matched training steps.
- Training: 2 epochs, learning rate 5e-5, batch size 16 (values are the original BERT paper's suggested fine-tuning hyperparameters, not independently tuned for this task).
- Pre-sampling set size i: {5, 10}, compared against no pre-sampling (similarity computed against the full instance pool).
- Perspective API harmfulness threshold: 0.5 (primary), 0.8 (robustness check, appendix).
- Label-noise rate for the "perturbed" harmful-content training set: 25% of posts per training step (4 of 16) relabeled.

### Stated limitations
The authors state that using the Perspective API to generate ground-truth harmful-content labels imposes a single, centrally defined notion of harmfulness on every instance, whereas real administrators would label according to their own, possibly inconsistent, judgment; they address this specific gap only by injecting synthetic label noise, not by using real per-administrator labels. The authors state the bot-detection and content-warning tasks rely on self-declared/self-tagged user metadata, which they did not independently verify. FedMod's peer-selection mechanism (hashsim) requires each instance to periodically fetch every other candidate instance's trending-hashtag list, which the authors state does not scale past roughly 10,000 instances without pre-sampling (all-pairs Jaccard similarity across 10,000 instances requires about 100 million computations); pre-sampling addresses the compute cost but the authors report it can miss the truly most-similar peer for some instances. The authors state that FedMod's performance degrades once instances with opposing moderation policies federate with each other, and that at 50% opposing-policy instances FedMod no longer outperforms training locally; they state this failure was deliberately provoked as a worst case, note it plausibly maps to a malicious actor deliberately federating with opposing-policy instances to degrade others' models, and list a reputation scheme or an alternative peer-selection strategy to defend against it as unimplemented future work. The authors state they have not evaluated FedMod over a real deployment among live instance administrators, nor over a longitudinal period spanning multiple months of continued collaboration; both are listed as future work. In an appendix, the authors state that relying directly on the Perspective API for moderation (rather than the FedMod approach) would deepen the Fediverse's dependence on a single centralized third-party service (operated by Jigsaw/Google) and offers only a fixed, non-customizable set of harmfulness attributes, misaligned with per-instance policy needs — presented as the authors' own reason for choosing the FedMod design over a Perspective-API-only alternative, not as a measured cost.

### Requirements it places on the rest of the system
FedMod requires each participating instance to expose two API surfaces to peers: a Trends endpoint (`<instance>/api/v1/trends/tags`) returning weekly trending hashtags, used for hashsim similarity, and a way to serve model parameters to selected peers on request. It requires each instance to maintain its own labeled training set locally; no instance is required to disclose its raw labeled posts to any peer or central party, only trained model parameters — the privacy property rests specifically on parameter exchange substituting for data exchange. Peer selection (hashsim) requires a follow-graph observation for the pre-sampling optimization: each instance must know, for every other instance it is considering, how many of that instance's users its own users follow — data drawn from the federation/follow relationships already visible to an ActivityPub-federated instance, not an added protocol requirement, but a dependency on that visibility existing. The federated-averaging aggregation step assumes participating peers are not adversarially poisoning their submitted parameters; the paper's own opposing-policy experiment demonstrates that a peer with an inverted labeling definition degrades the aggregate, and the paper states no defense against this beyond an unimplemented future reputation scheme — so any deployment needs either trusted peer selection or an added Byzantine-robustness mechanism the paper does not supply. The scheme assumes each instance can independently fine-tune a 172M-parameter transformer model (mBERT) locally on some interval (default 24 hours); this is a computational requirement on the hosting instance, not evaluated at low-resource extremes in this paper.

### Contradicts
None found. The commonly cited summary that "federated learning across instances solves Fediverse moderation" overstates this paper's own finding: the paper's measured result is that FedMod helps when instances' policies are broadly compatible and degrades or reverses its benefit once a large fraction of peers hold opposing policies — the paper states this itself and frames it as unresolved future work, not as a solved case.
