## [REDDY-RFC-20] Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)

**Citation:** Tirumaleswar Reddy, Alan Johnston, Philip Matthews, Jonathan Rosenberg. "Traversal Using Relays around NAT (TURN): Relay Extensions to Session Traversal Utilities for NAT (STUN)." IETF RFC 8656 (obsoletes RFC 5766 and RFC 6156), 2020. DOI 10.17487/RFC8656.
**Retrieved:** full text via https://www.rfc-editor.org/rfc/rfc8656
**Source URL:** https://www.rfc-editor.org/rfc/rfc8656
**Domain:** L

### What it does
TURN (Traversal Using Relays around NAT) lets two hosts that each sit behind a network address translator (NAT) exchange application data through a third-party relay when direct hole punching between them fails, by having one host (the TURN client) obtain a public IP address and port on the relay server (the "relayed transport address") and directing the server to forward data between that address and the remote host (the "peer"). The client authenticates to the server (typically with STUN's long-term credential mechanism) and sends an Allocate request; the server creates an allocation, a server-side data structure recording the relayed transport address, its expiry timer, and its permission list, and returns the allocated address in its response. The client keeps the allocation alive by periodically sending Refresh requests before the allocation's lifetime expires; TURN deliberately uses a distinct method (Refresh, not a repeated Allocate) so the client is told explicitly if the allocation has vanished, rather than silently getting a second, different allocation. A single relayed transport address can carry traffic to and from multiple peers, distinguishing TURN from relay protocols such as SOCKS that require one relayed address per remote destination; this multi-peer property traces to TURN's origin supporting SIP (Session Initiation Protocol) call forking.

Before the server relays any inbound peer traffic to the client, the client must install a permission for that peer's IP address (via a CreatePermission request or implicitly via a ChannelBind request); the server checks every inbound UDP datagram's source address against the allocation's permission list and silently discards traffic from an unlisted address. This mimics the address-dependent filtering behavior an RFC-4787-compliant NAT already performs, so a TURN server does not open an inbound path any address-dependent NAT or firewall between client and Internet would not already permit once the client has spoken first. Data can move over the relay through either of two mechanisms: Send/Data indications, which wrap each payload in a full STUN-formatted message (36 bytes of overhead), or channels, which bind a 4-byte channel number to a specific peer via a ChannelBind request and then use a lighter 4-byte-header ChannelData message for each subsequent payload, reducing per-packet overhead for bandwidth-sensitive applications such as VoIP (Voice over IP).

### Measured results
None. This document is a protocol specification defining message formats and normative client/server behavior; it contains no experimental measurement, testbed trial, or deployment dataset. The one numeric result present is an arithmetic derivation, not a measurement: a described amplification attack (Section 21.4) computes that an IPv6-over-TURN-over-IPv4 tunnel packet loop can achieve at most a four-to-one amplification out of a 1500-byte Ethernet MTU packet, because the IPv6+UDP+TURN header overhead is stated as 334 bytes per hop.

### Parameters
- Default allocation lifetime: 10 minutes (600 seconds); the client may request a longer value in the Allocate or Refresh request, and the server states the actual granted lifetime in its response; a Refresh request with lifetime 0 explicitly deletes the allocation, and the server MAY grant a smaller maximum than the default to limit resource consumption.
- Permission lifetime: fixed at 300 seconds (5 minutes), not client-configurable; expires automatically if not refreshed by a further CreatePermission or ChannelBind request, and there is no explicit permission-deletion message. This value is stated to be chosen to match RFC 4787-compliant NAT behavior.
- Channel binding lifetime: fixed at 10 minutes, refreshed by re-sending a ChannelBind request; like permissions, there is no explicit deletion message, only expiry. This lifetime is stated to be chosen to exceed the permission lifetime.
- Per-message overhead: Send/Data indication mechanism adds 36 bytes of STUN framing per payload; the ChannelData mechanism reduces this to a 4-byte header, offered specifically as a bandwidth reduction for applications such as VoIP.
- Tunnel-amplification bound: up to a 4-to-1 packet-size amplification, bounded by a 1500-byte path MTU against a 334-byte IPv6+UDP+TURN per-hop header size (both figures given in the spec text, not separately measured).

### Stated limitations
TURN is stated to require a high-bandwidth server-side connection, described as a high cost to whoever operates the server, so the document recommends using a TURN relay only when a direct path cannot be found — when TURN is combined with ICE (Interactive Connectivity Establishment), ICE performs hole punching first and falls back to TURN only on failure. Send and Data indications cannot be authenticated at all, because STUN's long-term credential mechanism does not support authenticating indications; the document states this is only a partial problem because the client-to-server leg of the path is not the whole path to the peer, and recommends that applications wanting end-to-end confidentiality or integrity encrypt the data themselves rather than relying on TURN to provide it. The document states TURN servers introduce several attacks not present in NAT-based address-dependent filtering, and describes each with its mitigation rather than declaring it solved: a TURN Loop Attack (an attacker spoofs Allocate and ChannelBind requests between two TURN servers to make data loop indefinitely between them) is mitigated by requiring authenticated requests and/or randomized relay port allocation, plus a per-username bandwidth limit and, where the OS permits, TTL decrementing on relayed packets; a Tunnel Amplification Attack (spoofed Allocate/ChannelBind requests turn a TURN server plus an IPv4/IPv6 tunnel endpoint into a packet-looping amplifier) is mitigated by the RECOMMENDED policy that a TURN server not accept allocation or channel-binding requests from addresses known to be tunneled, and MUST NOT accept Teredo or 6to4 addresses specifically. TURN servers are stated to provide "a degree of anonymization" letting a client send data to peers without revealing its own IP address, which the document flags as attractive to an attacker wanting to relay malicious traffic through chained TURN servers without detection; the only stated countermeasure is administrative logging of the actual client source address and installed permissions for later forensic tracing, not a protocol-level prevention. IPsec Authentication Header in transport or tunnel mode is stated not to operate properly through a TURN-allocated relay address, though tunnel-mode IPsec Encapsulating Security Payload is stated to still work.

### Requirements it places on the rest of the system
The client must have some way, out of the scope of the TURN protocol itself, to communicate its relayed transport address to its peers and learn each peer's own server-reflexive transport address; the document names email exchange or a dedicated rendezvous protocol (ICE, with SIP carrying the ICE candidates in its message body) as examples, but the mechanism itself is external. Relaying data requires the server to authenticate the client, typically via STUN's long-term credential mechanism or RFC 7635's third-party authorization extension, meaning the deployment must supply a credential-issuance and verification system the TURN server can check against. Every message that installs or refreshes a permission (CreatePermission, ChannelBind) must be authenticated for TURN's firewall-emulation property to hold; an unauthenticated Send indication cannot itself install a permission, so a peer cannot receive relayed data from the client until an authenticated request has explicitly authorized that peer's address. The server must track a distinct 5-tuple (client transport address as seen at the server, server transport address, and protocol) per allocation, and creating a second allocation requires a different 5-tuple, which places a constraint on how many concurrent relayed addresses a single client-server socket pair can obtain. The relay depends on the server operator provisioning enough allocation and bandwidth capacity per client to withstand the insider-attack case where a legitimately authenticated client floods its own allocation; the document's only stated mitigation is a server-side recommendation to cap per-username bandwidth and per-username allocation count, which the deployment must configure, not TURN itself.
