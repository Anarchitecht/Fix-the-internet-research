## [CORRIGANGIBBS-SP-15] Riposte: An Anonymous Messaging System Handling Millions of Users
**Citation:** Henry Corrigan-Gibbs, Dan Boneh, David Mazieres. "Riposte: An Anonymous Messaging System Handling Millions of Users." IEEE Symposium on Security and Privacy, 2015. Pages 321-338. DOI 10.1109/SP.2015.27.
**Retrieved:** full text via https://www.henrycg.com/files/academic/papers/oakland15riposte.pdf
**Source URL:** https://www.henrycg.com/files/academic/papers/oakland15riposte.pdf
**Domain:** G

### What it does
Riposte lets a large number of clients anonymously post fixed-length messages to a shared bulletin board maintained by a small set of minimally trusted servers, so that no server, and no network eavesdropper who observes all client-server traffic, can determine which client wrote which message. Messaging proceeds in fixed time epochs. To write, a client picks a row index in a shared database table and secret-shares a write vector that is zero everywhere except at that row (where it holds the client's message) across the servers, one share per server; a coalition of servers smaller than a protocol-specific threshold learns nothing about the message or the write location from its own shares. Instead of sending a full-length share vector (which would need to be as long as the whole database, an approach the paper calls the "first-attempt" construction and rejects for bandwidth cost), the client encodes its write using a distributed point function (DPF): a compact key, of size proportional to the square root of the table length L rather than L itself, that each server locally expands (via a pseudorandom generator, using AES-based symmetric-key operations in the two-server variant, or DDH-based elliptic-curve operations in the s-server variant) into its own share of the same all-zero-except-one-row vector. Riposte calls this technique "PIR run in reverse": ordinary Private Information Retrieval (PIR) lets a client read a hidden row privately; Riposte's DPF-based write lets a client set a hidden row privately. Servers accumulate every client's share vector by simple vector addition over the epoch; at epoch end, the summed table, containing every client's message in its own row, is revealed, but no server can attribute any row to any specific client because the sum was computed homomorphically over secret shares.

Riposte defines two variants trading server count for security assumption. The three-server variant uses two database servers plus one audit server and needs only that no two of the three collude; it detects and rejects a malformed client write (a write that is not actually zero-except-one-row, which would otherwise let one malicious client corrupt every row and deny service to everyone) using a computationally cheap multi-party protocol among the servers based on the Poly1305 keyed hash function and Pedersen commitments, run before the write is admitted. The s-server variant tolerates s-1 out of s servers behaving arbitrarily (Byzantine), at the cost of the more expensive DDH-based DPF and, in its full design, client-generated zero-knowledge proofs of well-formedness instead of the multi-party check.

### Measured results
Implemented in Go, source published; measured on the DeterLab network testbed, on commodity servers running Ubuntu 14.04 with four-core AES-NI-enabled Intel E3-1260L CPUs and 16 GB RAM. Network topology: 100 Mbps links among server nodes, 1 Gbps links among the eight client nodes and between client and server switches, 20 ms round-trip latency between every pair of nodes; eight client machines used multiple threads to saturate the servers with write requests. Error bars in the paper's figures report the standard deviation of throughput measurements across repeated runs (run count not stated).

Three-server variant (two database servers plus one audit server, no two colluding), fully implemented including the audit protocol, so throughput figures include the cost of detecting and rejecting malformed writes, using 160-byte database rows (chosen as the smallest 32-byte multiple large enough for a 140-byte Tweet), AES-128-CTR as the pseudorandom generator, Poly1305 for the audit protocol's keyed hash, and TLS for link encryption:

| Database table size (160-byte rows) | Write throughput |
|---|---|
| 64 rows | 751.5 requests/second |
| 65,536 rows | 32.8 requests/second |
| 1,048,576 rows (about 168 MB) | 2.86 requests/second |
| 2.3 million rows (377 MB table) | 1.4 requests/second |

The measured upper bound on throughput from the servers' AES pseudorandom-generator speed (a Go AES benchmark) is 605 MB/s; the paper states migrating the performance-critical code from Go to C using OpenSSL (reported OpenSSL AES throughput of 3.9 GB/s on the same hardware) could raise throughput by up to 6 times. At very small table sizes, TLS connection setup, not cryptographic computation, limits throughput to roughly 900 requests per second.

Effect of the square-root-size distributed point function versus a naive full-length write vector, holding total table size fixed at 10 MB while varying the table's width-to-height ratio: the DPF-optimal table shape achieves 38.4 requests per second; the naive-construction extreme (client sends a vector as large as the database) achieves 0.05 requests per second, a 768-times difference in this specific comparison. Elsewhere the paper describes the general bandwidth-efficient DPF as giving a 32-times speedup over the naive approach.

Total data transferred per write request scales sub-linearly with table size: at a 2.5 GB table, one database server transfers a total of 1.23 MB to process a single write request (against a naive-construction bound of transferring the full table size, i.e. 2.5 GB, per write).

Writing into a 377 MB table (2.3 million 160-byte rows) requires each client to upload less than 1 MB of data to the servers; the paper states a two-server Dining-Cryptographers-network (DC-net) based system would require each client to upload more than 750 MB of data for the equivalent write, though no citation gives the specific measured DC-net system this comparison figure was computed from.

s-server variant (Byzantine-tolerant, s-1 out of s servers may be malicious), implemented without the zero-knowledge disruption-resistance proofs (so these figures are stated as an upper bound on that variant's real throughput), using a DDH-based seed-homomorphic pseudorandom generator over the NIST P-256 elliptic curve, 160-byte rows, eight servers: at a table size of 1,024 rows, the cluster processes one request every 3.44 seconds; the paper computes that a table of one million rows would take nearly one hour per request under this construction (compared to 0.3 seconds for the three-server, AES-based variant at a comparable table size). Varying the number of servers from two to ten at fixed table sizes (16-row and 64-row tables) produces only a slight decrease in throughput, attributed to the workload being CPU-bound rather than network-bound.

Large-anonymity-set demonstration: a three-server Riposte cluster with a 65,536-row database table, run continuously for 32 hours, processed 2,895,216 write requests total, at an average rate of 25.19 requests per second. The paper computes that with this table size and the collision-rate technique of Section III-B, a table of 65,536 rows supports up to 0.3% of anonymity-set members writing per epoch while keeping the write-collision rate under 5%, so reaching a roughly 1,000,000-user anonymity set with a three-server cluster and a 65,536-row table requires a time epoch of at least 11 hours.

Scale comparison against Twitter's reported 2013 throughput of 5,700 140-byte Tweets per second (approximately 5,000 Riposte-equivalent 160-byte messages per second): at a one-million-row table, the measured three-server cluster processes 2.86 write requests per second (from the table above), so the paper computes that matching Twitter's Tweet volume at anonymity-set sizes of hundreds of thousands of clients would need roughly 1,750 times more computing power, i.e. about 5,250 servers split across three non-colluding data centers, or, accounting for the audit server needing only string comparisons, closer to 4,000 servers total. This is a derived projection, not a separately measured deployment.

The paper states prior DC-net-based anonymity systems (citing Dissent) scaled to 5,120 clients, and prior verifiable-shuffle-based systems (citing Bayer and Groth) scaled to 100,000 clients, as points of comparison for its own 2,895,216-client demonstration; these two figures are attributed to those other systems' own publications, not independently re-measured by this paper.

### Parameters
- Row (message) length: 160 bytes in every reported experiment, chosen as the smallest 32-byte multiple that holds a 140-byte Tweet; the paper notes throughput depends only on total table size (rows times row length), so a 4096-byte-row email application would reach 2.86 requests/second at a table size of 40,960 rows instead of 1,048,576.
- Server count for the three-server variant: exactly 3 (two database servers, one audit server); security holds as long as no two of the three collude.
- Server count s for the general s-server variant: tested at s = 8 in the throughput-vs-table-size experiment (Figure 6) and varied from 2 to 10 in the throughput-vs-server-count experiment (Figure 7).
- Time epoch length: not fixed by the protocol; the paper computes a required minimum of at least 11 hours to reach a roughly 1,000,000-client anonymity set with a 65,536-row table at a 0.3% per-epoch write rate and under 5% collision rate.
- Anonymity-set-to-writer ratio: the paper's collision-rate analysis (Section III-B, referenced but not re-derived here) ties this ratio to table size and target collision rate; 0.3% of the anonymity set writing per epoch is the value used in the 65,536-row worked example.

### Stated limitations
The paper states its threat model trusts all servers for availability (a server can always deny service by refusing to run the protocol) though not for privacy or correctness; disruption resistance in this paper is defined only against malicious clients, and the paper states explicitly it does not try to prevent servers themselves from corrupting the database state. The s-server variant's reported throughput is stated as an upper bound only, because the zero-knowledge proofs needed to make that variant resistant to malicious-client disruption were not implemented; the paper estimates the added cost as an additional order-square-root-of-L elliptic-curve operations per server, which it states would almost certainly be dwarfed by the linear-in-L elliptic-curve cost of updating the database table, but this added cost was not measured. The paper states three specific open problems it leaves unsolved: whether an (s, s-1)-distributed-point-function construction for s greater than 2 exists using only symmetric-key operations (the three-server variant already achieves this only for s=2); whether disruption resistance is achievable without a non-colluding audit server, using no public-key primitives; and whether any DPF construction allows processing a write request in amortized time sublinear in the database length L. The large-anonymity-set demonstration (2,895,216 users over 32 hours) is stated by the paper to require both hours-scale messaging latency tolerance and a read-heavy workload (few writers relative to readers); the paper states these two conditions hold for whistleblowing and microblogging but does not claim the demonstrated scale for lower-latency or write-heavy applications.

### Requirements it places on the rest of the system
The security property (no server learns which client wrote which row) holds only under the stated non-collusion assumption: no two of the three servers collude in the three-server variant, or no more than s-1 of s servers collude in the general variant; any system composing Riposte as a subcomponent must independently ensure operationally that the servers it selects do not collude, since Riposte itself provides no mechanism to enforce or detect collusion. A system relying on Riposte's large-anonymity-set property must accept messaging latency on the order of the epoch length (hours, in the paper's own worked example), and must supply a mechanism to generate "empty" read-only write requests from non-writing participants, since the anonymity-set-inflation technique described in Section VI-C depends on read-only clients submitting indistinguishable dummy writes into a fixed database row. The write-collision mitigation (Section III-B, cited but not fully re-derived in this extraction) requires the system to tolerate a nonzero message-loss rate from collisions (under 5% in the paper's worked example) and requires knowing or bounding the number of concurrent writers per epoch to size the table and epoch length correctly; a downstream component that cannot tolerate any message loss cannot rely on the collision-based capacity model as stated. The DPF-based write mechanism requires every server to independently and correctly expand its DPF key using its own pseudorandom generator (AES-based or DDH-based, depending on variant) with no coordination among servers beyond the client-issued keys; a component relying on Riposte must supply a fixed, agreed table row length in advance, since Riposte's per-write bandwidth cost is a function of that fixed row length and the table's row count.

### Contradicts
None found among papers currently in this corpus. Internally, the paper's headline claim ("millions of users" in the title, 2,895,216-client demonstration) applies only to the specific read-heavy, latency-tolerant, three-server configuration; it does not hold for the s-server variant, whose measured throughput at large table sizes (nearly one hour per request at one million rows) is far below the three-server figures and is explicitly labeled an upper-bound estimate rather than a full implementation result.
