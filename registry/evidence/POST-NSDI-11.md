## [POST-NSDI-11] Bazaar: Strengthening User Reputations in Online Marketplaces

**Citation:** Ansley Post, Vijit Shah, Alan Mislove. "Bazaar: Strengthening user reputations in online marketplaces." USENIX NSDI, 2011.
**Retrieved:** full text
**Source URL:** https://www.usenix.org/legacy/event/nsdi11/tech/full_papers/Post.pdf
**Domain:** F

### What it does
Bazaar bounds the amount of monetary fraud any user of an online marketplace can commit, regardless of how many identities that user controls, by computing a network flow value between buyer and seller instead of summing feedback counts. Every successful transaction between two identities creates or strengthens an undirected weighted link between them in a "risk network," where the weight equals the aggregate monetary value of past successful transactions between that pair. Before a transaction proceeds, the marketplace operator asks Bazaar for the maximum flow (the greatest total weight that can be routed via any combination of paths, limiting each edge to its own weight, the standard graph max-flow value) between the buyer and seller in the risk network; if that value is below the proposed transaction amount, the transaction is flagged as potentially fraudulent. If the transaction proceeds, Bazaar selects a set of paths between buyer and seller whose combined weight covers the transaction amount and temporarily lowers each path's weight by its assigned share of that amount, placing that credit "on hold" until feedback arrives. Positive buyer feedback restores the held weight and adds a new direct link (of the transaction's value) between buyer and seller; neutral feedback or a timeout restores the held weight without adding a link; negative feedback makes the reduction permanent, since a fraudulent seller's own risk-network links are what get depleted. Because the max-flow value across any network cut is bounded by that cut's total weight, a set of colluding or Sybil identities can defraud non-malicious users only up to the total weight of the links crossing the cut between the malicious identities and the rest of the network — a bound independent of how many identities the malicious party splits itself into or how much fictitious feedback it manufactures among its own identities. New users bootstrap by having real-world friends grant "virtual" starter links (at the friend's own reputational risk) or by depositing money in escrow with the marketplace operator, which then creates links of that value to random other users. To make max-flow computation tractable, Bazaar builds a "multi-graph": a series of nested subgraphs G_0 (the full risk network), G_1, G_2, ... where G_i keeps only edges of weight at least k^i for a configurable base k (suggested value 2); a flow query starts at the sparsest graph containing the needed weight and only descends to denser graphs as required, since Bazaar only needs to confirm the flow value exceeds a threshold, not compute its exact value.

### Parameters
- Multi-graph weight-threshold base k: suggested value 2 (each graph level keeps only edges of weight at least k^i)
- Feedback timeout T: configurable; used-value not stated as a specific number of days in the retrieved text
- Malicious-user fraction in the fraud-bound simulation: 1% of users, following a cited prior study's methodology
- Minimum observed-transaction count for a user to be included in the fraud-detection simulation: 5 transactions in the 90-day window
- Train/test split for simulation: 80% of feedback used to build the initial risk network, 20% replayed as simulated transactions
- Number of simulation runs per data point: 10, with different random seeds
- Purchase-time imputation: for the 45.4% of auctions lacking a recorded purchase time (fixed-price, multi-buyer auctions), a delay is subtracted from the feedback time, drawn from the observed delay distribution of auctions where both times are known
- Hardware for max-flow timing measurements: single machine, 2.83 GHz Intel Xeon processor

### Stated limitations
The paper states protecting sellers from fraudulent buyers is left to future work, noting this is partly mitigated because marketplace operators typically let sellers verify payment before shipping. It states that decentralizing the risk network (removing the requirement that the marketplace operator holds full knowledge of all transactions) is an open research question and future work, and that it does not know of any decentralized online marketplace to motivate a concrete design. It states a targeted-attack vector exists in which an attacker who has already accumulated legitimate transaction links can purchase a target seller's goods and give deliberately negative feedback to damage that seller's own outgoing links, though it argues Bazaar raises the cost of this attack relative to existing feedback systems because the attacker must first accumulate non-fraudulent transaction history. It states that a compromised user account lets an attacker conduct fraud up to that account's own Bazaar-bounded limit, an attack not unique to Bazaar but still bounded, unlike under unbounded feedback-based reputation. It states that if a malicious identity is the sole link between two otherwise-connected malicious identities and the rest of the network, the max-flow bound can be lower than the raw sum of that identity's prior successful transactions, because cut capacity, not link count, determines the bound. Multi-graph max-flow queries that fail (no sufficient-weight path set exists) must traverse every graph level and take longer on average than queries that succeed and can terminate early; the paper reports that treating queries running longer than 2 seconds as failures in the Computing category would misclassify only 5.5% of eventually-successful queries while lowering the average query time from 1.66s to 0.70s, an optimization not applied in the reported headline results.

### Requirements it places on the rest of the system
Bazaar requires the marketplace operator to hold complete, authoritative knowledge of every transaction and its outcome (buyer identity, seller identity, monetary amount, and eventual feedback), because the risk network and its max-flow computation are built and queried centrally by that operator; the paper states explicitly that decentralizing this knowledge is unsolved. It requires a feedback channel from buyer to marketplace operator with three outcomes (positive, negative, neutral) plus a configurable timeout T that resolves silence to the neutral case. It requires the ability to place transaction weight "on hold" atomically at the time a transaction is authorized, meaning the operator's transaction-processing pipeline must call into Bazaar's flow computation before finalizing a sale, not asynchronously afterward. It assumes link weights are non-negative and that a transaction's value is fully known at authorization time, since the flow-reduction bookkeeping charges an exact monetary amount to specific paths. The bootstrapping mechanism assumes some new users have existing marketplace users willing to vouch for them via virtual links, or that the operator is willing to hold user funds in escrow; a system lacking either path leaves new users with zero max-flow to everyone and every one of their transactions flagged. It assumes rational-actor incentive alignment for honest feedback: the paper's own reasoning for why buyers report truthfully depends on the buyer's own links being at stake, meaning it does not defend against buyers who have no remaining stake in their own risk-network position.

### Contradicts
None found within this corpus as of this batch. Note for later composition checking: Bazaar's core guarantee (fraud bounded by cut value, not identity count) depends on the operator's full-network view; this composes poorly with any anonymity or partial-visibility tier that hides identities' transaction graphs from a shared computation point, since the max-flow computation cannot be run over information the operator does not hold.
