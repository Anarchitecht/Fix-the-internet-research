## [BOLDYREVA-PKC-03] Threshold Signatures, Multisignatures and Blind Signatures Based on the Gap-Diffie-Hellman-Group Signature Scheme
**Citation:** Alexandra Boldyreva. "Efficient threshold signature, multisignature and blind signature schemes based on the Gap-Diffie-Hellman-group signature scheme." Public Key Cryptography (PKC), 2003. DOI 10.1007/3-540-36288-6_3.
**Retrieved:** full text via https://www.iacr.org/archive/pkc2003/25670031/25670031.pdf
**Source URL:** https://www.iacr.org/archive/pkc2003/25670031/25670031.pdf
**Domain:** E

### What it does
This paper gives three extensions of the BLS signature scheme (Boneh, Lynn, Shacham; a signature scheme whose security relies on the Computational Diffie-Hellman, CDH, problem being hard while the related Decisional Diffie-Hellman, DDH, problem is easy in the same group — such groups are called Gap Diffie-Hellman, GDH, groups) that let a group of parties jointly produce or delegate signatures, and states a formal proof of security for each.

TGS, the threshold GDH signature scheme, lets any subset of more than t out of n parties jointly compute a valid BLS signature while no coalition of t or fewer parties can forge one or learn the secret key, tolerating up to t < n/2 malicious parties (an optimal fraction, matching the maximum any threshold scheme can tolerate while remaining both robust and secure). Key generation uses Gennaro, Jarecki, Krawczyk, and Rabin's distributed key generation (DKG) protocol, run interactively by all n parties with no trusted dealer, producing a Shamir (t,n)-threshold secret sharing of the BLS secret key x — a sharing in which any t or fewer shares reveal no information about x, and any t+1 shares reconstruct it via Lagrange interpolation. To sign a message M, each participating party i simply runs the base BLS signing algorithm on its own share x_i, producing a signature share sigma_i = H(M)^{x_i}, and broadcasts it — no interaction or zero-knowledge proof is needed at signing time. A designated combiner reconstructs the full signature as the product of t+1 shares raised to their Lagrange coefficients, sigma = product over the chosen set R of sigma_i^{L_i}. Robustness (the property that the protocol produces a valid signature even if up to t parties actively deviate) is achieved because each share's validity can be checked directly: the DKG protocol publicly broadcasts B_i = g^{x_i} for every party, so the combiner verifies each sigma_i against B_i using the DDH-tuple check before combining, and requests a fresh share or treats the party as malicious if the check fails. Share length does not grow with n. The scheme can be made proactive (periodically re-randomizing shares so an adversary's knowledge from one time period becomes useless in the next) using the general proactive secret sharing techniques of Herzberg, Jarecki, Krawczyk, and Yung, because TGS meets the three preconditions those techniques require: it is a discrete-log-based threshold scheme, its key generation implements Shamir sharing with publicly verifiable share commitments, and its signing protocol is simulatable.

MGS, the GDH multisignature scheme, lets an arbitrary subgroup L of players, decided at signing time rather than fixed in advance, jointly produce one constant-size signature that a verifier accepts as proof every member of L participated. Each player P_j with secret key x_j computes and broadcasts its own BLS signature share sigma_j = H(M)^{x_j} on the message; a designated combiner (any party can serve this role) multiplies the shares from the participating set to produce sigma = product of sigma_j; a verifier reconstructs the combined public key pk_L = product of the individual public keys g^{x_j} for j in L and checks the DDH tuple (g, pk_L, H(M), sigma). Verification and signature length are independent of the number of players in L, and — unlike the prior formalized multisignature scheme of Micali, Ohta, and Reyzin, which required the subgroup to be fixed before any signature share was computed and required three communication rounds — MGS requires no prior agreement on the signer set and is non-interactive (one round). Each signature share is exactly a standard BLS signature, so the same technique supports batch verification of separate BLS signatures on the same message under different public keys, using the same product-then-verify approach.

BGS, the blind GDH signature scheme, lets a user obtain a valid BLS signature on a message from a signer without the signer learning the message, and prevents the user from deriving more than one valid signature per completed protocol run. The user picks a random blinding factor r, sends M-hat = H(M) * g^r to the signer; the signer, without learning M, computes sigma-hat = (M-hat)^x and returns it; the user removes the blinding factor by computing sigma = sigma-hat * y^{-r}, which equals the standard BLS signature H(M)^x. The construction parallels Chaum's RSA-based blind signature protocol structurally.

### Measured results
None. This is a pure cryptographic-construction paper: every claim is a formal security theorem with an accompanying reduction proof (given in the paper's appendices), not an experimental measurement. The paper states no benchmark, implementation, node count, or runtime figure of its own. Where it discusses efficiency, it does so structurally — round counts, share-length independence from n, and dependence or independence of a value on the number of participants — not as measured numbers.

### Parameters
- (t, n)-threshold: the threshold signature scheme TGS tolerates any t < n/2 malicious parties, stated as the achieved bound, not a tested range; the paper calls this "an optimal result" for the threshold fraction a robust, non-interactive threshold scheme of this kind can tolerate.
- Signature/share/key sizes: not given as numeric byte counts in this paper. The paper does state, citing the BLS base scheme, that BLS signatures are "approximately 160 bits" in some GDH group instantiations — this figure is attributed to the base BLS paper, not measured here.
- Chosen-target CDH problem query bound: the blind-signature security definition parameterizes adversary advantage by q_t (queries to a "target" oracle) and q_h (queries to a "helper" signing oracle), with the forgery condition requiring the adversary to produce more valid signatures than helper-oracle queries (q_h < q_t); this is a security-definition parameter, not a numeric value chosen for an instantiation.

### Stated limitations
The paper states its threshold-signature security proof (Theorem 4.2) holds "in the random oracle model only" — an idealized model in which a hash function is treated as a public random function — because the underlying BLS base signature scheme's own security proof requires the random oracle model; the threshold construction inherits this dependency rather than removing it.

The paper states that its multisignature security model, following Micali-Ohta-Reyzin, does not address robustness by default: an adversary that has corrupted all but one signer can always deviate from the protocol to prevent a valid multisignature from being produced, and the paper states it does "not focus on the robustness property in this work," only sketching how robustness could be added.

The paper states that its comparison of subgroups in a multisignature is left to the application: a verifier may reject a valid multisignature because it disagrees with which subgroup L signed, and the paper explicitly states it does "not take this problem into account" in its formal analysis.

The paper's blind-signature security proof rests on a new, unproven computational assumption it introduces (the chosen-target CDH assumption) rather than reducing to the standard CDH assumption; the paper states only that it conjectures this new assumption holds "for all groups where the CDH problem is hard," not that this has been proved.

The paper explicitly leaves multisignature robustness, and the exact efficiency trade-offs of alternative threshold DKG protocols, outside its formal treatment, citing related open problems from Micali-Ohta-Reyzin (the composition-after-signing problem, which this paper's MGS explicitly resolves) as context rather than closing every open question in the area.

### Requirements it places on the rest of the system
The threshold scheme TGS requires an underlying communication substrate providing both a broadcast channel and secure point-to-point channels among all n participants; the paper states this explicitly as its assumed communication model, and the distributed key generation protocol (DKG) it reuses from Gennaro-Jarecki-Krawczyk-Rabin depends on this channel structure for its own security guarantees.

Robust operation depends on every party's per-share public commitment (B_i = g^{x_i}) being available to whichever party performs signature-share combination, since the combiner's DDH-tuple check against B_i is what lets it detect and exclude an invalid share instead of silently producing a corrupted combined signature; a deploying system must make DKG's publicly broadcast commitments persistently available to the combiner role, not just to participants during key generation.

Proactivization requires layering the separate PSS (Proactive Secret Sharing) protocol from Herzberg-Jarecki-Krawczyk-Yung on top of TGS and requires periodic synchronized share-refresh rounds among all n parties; TGS alone does not provide forward security against an adversary that compromises different subsets of parties across multiple time periods without this addition.

The multisignature scheme MGS requires each verifier to know, and be given, the complete list of public keys for every player in the claimed signing subgroup L at verification time, since the combined public key pk_L is recomputed by the verifier as the product of the individual keys — the verifier cannot check a multisignature against an unlisted or partially specified signer set.

The multisignature security model requires that corrupted players prove knowledge of their secret key at public-key registration time (to prevent rogue-key attacks, where an adversary derives a public key mathematically related to an honest party's key without knowing a corresponding secret key); a deploying system must enforce a proof-of-possession or equivalent registration check, or the paper's security guarantee for MGS does not apply.

The blind signature scheme BGS requires the signer to hold the GDH secret key x and to compute exponentiations on demand as an online interactive party for every blind-signing request; the scheme provides no mechanism for a signer that is offline or whose key material is distributed (that composition — blind signing over a threshold-shared key — is not addressed in this paper).

None found against other entries in this corpus.
