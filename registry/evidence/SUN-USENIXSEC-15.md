## [SUN-USENIXSEC-15] RAPTOR: Routing Attacks on Privacy in Tor

**Citation:** Yixin Sun, Anne Edmundson, Laurent Vanbever, Oscar Li, Jennifer Rexford, Mung Chiang, Prateek Mittal. "RAPTOR: Routing Attacks on Privacy in Tor." 24th USENIX Security Symposium, 2015. Pages 271-286.
**Retrieved:** full text via https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-sun.pdf
**Source URL:** https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-sun.pdf
**Domain:** J

### What it does
The paper deanonymizes Tor users through routing manipulation at the level of BGP (Border Gateway Protocol, the protocol autonomous systems use to exchange reachability routes across the Internet), rather than by running a Tor relay. Three related attacks: first, an autonomous system (AS) that already sees the forward-direction path from a client to its guard relay can independently examine whether it also sees the return path from the exit relay to the destination, or vice versa — asymmetric routing on the Internet means the two directions of a single connection frequently take different AS-level paths, so any single AS observing either direction on both segments of the same Tor circuit already possesses a correlation opportunity that whole-flow-symmetric adversary models miss. Second, routine BGP route changes over time (churn) cause a growing set of ASes to have appeared, cumulatively, on both segments of a given (client, destination) pair's circuit at different moments, so the compromising AS set for a fixed pair of endpoints only grows as time passes. Third, an AS can actively manipulate BGP itself: a hijack (announcing a route to a prefix the announcing AS does not own, causing traffic to be misdirected) reveals which clients use a targeted guard relay, and an interception (announcing a more specific prefix so that traffic is drawn to the attacker but still forwarded on to the legitimate destination, keeping the connection alive) lets the attacker perform traffic analysis on live Tor circuits without the client or relay detecting an outage. The paper's traffic-correlation technique (used to confirm a suspected client-server pairing) computes the Spearman rank correlation between the time series of transmitted-byte counts derived from TCP sequence and acknowledgment numbers captured at each end, and needs only one direction's data, not the full duplex stream — that is what makes the asymmetric-routing observation exploitable.

### Parameters
- Circuit compromise definition for churn analysis: an AS counted as compromising a circuit only if it remained on-path for at least 30 seconds, "as it is unlikely that a time-correlation attack can be performed in shorter timescale" (the paper does not derive this threshold from a separate measurement; it is stated as an assumption).
- Traceroute measurement: daily over a 3-week period, 4 AS sets of size 10, 25, 25, 10, giving 62,500 possible circuit combinations.
- BGP dataset: January 2015, 6 RIPE-maintained Looking Glass collection points, 250+ BGP sessions, 612+ million updates over 550,000 prefixes.
- Interception-attack timing: traffic drain after more-specific announcement took ~35 seconds to propagate; traffic recovery after withdrawal took ~22 seconds; attack window was 300 seconds of a 100 MB download per client.

### Stated limitations
The authors state the interception-attack accuracy (90%) is lower than the static asymmetric-analysis accuracy (95%) because all 50 test clients shared one guard relay and started requests simultaneously, artificially compressing the achievable bandwidths of different client-server pairs toward similarity — a condition the authors describe as "an extreme and very unlikely case in real Tor connections," expecting higher accuracy with fewer clients sharing a guard. The authors state they consider only individual, non-colluding autonomous systems as adversaries, and note in discussion that colluding ASes, such as those "within the same legal jurisdiction," would increase attack capability beyond what is measured. The authors state their proposed "select closer guards" countermeasure (favoring guards with a shorter AS-level path from the client) has an unresolved trade-off, because it makes the guard's identity more informative about the client's likely location, and explicitly leave this trade-off for future work. The authors state their real-world hijack and interception experiments used only their own generated traffic and their own controlled relay, with a firewall dropping real user traffic from the experimental relay, so no live Tor user was exposed to the interception experiment.

### Requirements it places on the rest of the system
A privacy tier that assumes symmetric routing observation is required to defeat a traffic-correlation attack is broken by any network topology exhibiting routing asymmetry, because an adversary needs only one direction of one of the two path segments (client-to-guard, exit-to-destination) to run the correlation attack described here, which halves the on-path coverage an adversary needs relative to a full-duplex observation model. A relay-selection mechanism that keeps a client's guard fixed for a long tenure (also measured, from the network-adversary angle, in JOHNSON-CCS-13) accumulates additional exposure over that tenure purely from BGP route churn, independent of any adversary action, because the set of ASes that have appeared on-path for a fixed (client, destination) pair only grows monotonically as routing updates accrue. A design that concentrates a large share of relay bandwidth or relay count within a small number of network prefixes (measured here at 6 ASes and 70 prefixes for ~30% of Tor relays and ~40% of bandwidth) creates a small set of maximally attractive BGP hijack and interception targets, so any capacity-ordered overlay reusing a similarly concentrated hosting pattern inherits the same vulnerability without additional relay-diversity requirements on physical network placement. A design relying on route-security protocols (secure BGP variants, cited by the authors as a mitigation) to close this attack requires deployment across multiple independent network operators simultaneously, which the authors state has been slow to happen in practice.

### Contradicts
None found within this batch. This paper's asymmetric-routing and churn-based attack results are additive to, and build on, the AS-level and IXP-level adversary analysis in JOHNSON-CCS-13, which the RAPTOR authors cite directly as related work analyzing "the security of the Tor network against AS-level adversaries in terms of user understandable metrics"; the two papers measure different adversary capabilities (route manipulation here versus passive fixed-position observation there) and do not report conflicting figures for the same quantity.
