## [HU-SP-21] Merkle²: A Low-Latency Transparency Log System

**Citation:** Yuncong Hu, Kian Hooshmand, Harika Kalidhindi, Seung Jin Yang, Raluca Ada Popa. "Merkle²: A Low-Latency Transparency Log System." IEEE Symposium on Security and Privacy (S&P), 2021. DOI 10.1109/SP40001.2021.00088.
**Retrieved:** full text via candidate URL `https://eprint.iacr.org/2021/453.pdf`
**Source URL:** https://eprint.iacr.org/2021/453.pdf
**Domain:** E

### What it does
Merkle² lets a transparency log publish a new digest every second while keeping both the cost a data owner pays to check her own entries and the cost an auditor pays to check the whole log's integrity independent of how many digests have been published since the owner last checked, so a system does not have to trade short publication intervals (low latency for detecting a wrongly-served entry) against growing per-check cost as time passes. Prior designs split into two families: prefix trees (leaves ordered lexicographically by key, as in CONIKS), which support efficient lookup of a specific entry's current value but force a data owner to check every published digest because states in different epochs carry no defined relationship to each other; and chronological trees (leaves ordered by time of append, as in Certificate Transparency), which let an owner check only the newest digest against an old one via an efficient extension proof, but do not support efficient lookup by key. Merkle² nests the two: the outer structure is a chronological tree ordered by append time, and every internal node of that chronological tree — not just the leaves — is itself the root of an inner prefix tree covering all entries appended up to that point, so each data block ends up stored in O(log n) prefix trees, one per level on the path from its chronological leaf to the chronological root, where n is the number of entries. A lookup for a key locates it via the prefix trees, giving CONIKS-style key-indexed retrieval; monitoring compares only the latest chronological root against the last root the owner or auditor has already checked, using an extension proof over the chronological tree, and does not touch intervening epochs' prefix trees at all. Appending a new entry in the naive version of this structure would require rebuilding O(log n) prefix trees from scratch each time; the paper's "pre-build" technique instead maintains each prefix tree incrementally in the background before it becomes the append target, at the cost of fixing a maximum chronological tree height (and hence a maximum log capacity) in advance. A data owner needs to verify only two proofs ever, in the paper's design: a first-value proof at enrollment and, from then on, only the current-epoch monitoring proof — because monitoring proofs can be cached and skipped for prefix-tree branches already checked, an owner who has checked before does not have to re-download the intervening structure to catch up after being offline.

### Parameters
- Hash function: SHA-3 (128-bit security level target).
- Signature scheme: Ed25519, stated as the only public-key operation in the system.
- Chronological tree height cap: 31, chosen to support the pre-build strategy; bounds total log capacity at 2^31 ID-value pairs and means each append touches 31 prefix trees.
- Persistent storage backend: LevelDB.
- VRFs (verifiable random functions) are explicitly not implemented, because the paper states privacy is not its focus — this is a deliberate scope exclusion, not a measured limitation.
- Baseline systems compared: CONIKS (both the original design and the authors' own persistent-data-structure-optimized "CONIKS*" variant), AAD (bilinear-accumulator-based transparency log), and ECT (chronological+prefix-tree hybrid for certificate transparency); AAD and ECT figures are taken from their own papers/repositories, not re-run on the authors' hardware.
- Asymptotic cost table (Table I) parameters: n = number of log entries, λ = AAD's security parameter, E = number of epochs elapsed, P = number of appends between epochs.
- Test-scale range: up to 2^20 ID-value pairs for microbenchmarks; up to 10⁶ ID-value pairs for end-to-end system evaluation and application scenarios.

### Stated limitations
The paper states directly, under "Limitations and future work," that Merkle² cannot outperform CONIKS when the epoch interval is long, because at long intervals append and lookup cost (which are more expensive in Merkle² than in CONIKS) dominate over monitoring cost (Merkle²'s comparative advantage); the crossover in the paper's own certificate/email-workload experiments occurs around a 1-hour epoch interval. The paper states it leaves improving append and lookup efficiency to future work, naming two unimplemented directions: a two-server split where one server pre-builds large future prefix trees while another serves current requests from smaller cached trees, and batching lookup proofs across users with a proxy layer to reduce server bandwidth. The paper states memory usage is a concern because data is replicated across the nested tree structure (Merkle² measured at ≈22 GiB vs. CONIKS's ≈6.3 GiB at the same 2^20-entry scale), and states an unimplemented optimization — skipping storage of prefix trees associated with chronological tree right children, which the paper says are not needed — is left to future work. The pre-build strategy requires fixing a maximum chronological tree height (31 in this implementation) in advance, which caps the total number of ID-value pairs the log can ever hold at 2^31; the paper does not describe a mechanism for extending capacity beyond a chosen height without redeployment. The paper explicitly declines to compare against Google Key Transparency's newer design because it is "still in its early stages" with "no protocol detail or implementation available for benchmarking" — this is a stated evidentiary gap, not a claim that the design underperforms.

### Requirements it places on the rest of the system
The construction assumes the server picks the maximum chronological tree height (and thus maximum log capacity) before deployment, since the pre-build technique that keeps append cost bounded depends on the height being fixed in advance; a component needing unbounded future capacity must plan a height large enough in advance or accept a redeployment when the cap is reached. Concurrency control requires the server to serialize appends against each other (two concurrent appends may touch the same prefix tree), enforced in the prototype by having the server issue a position number to the user and reject the append if the corresponding signature is not returned within a short time bound; lookups and monitoring can run concurrently with appends because the hashes they need were already computed in past epochs. The soundness of an owner's monitoring shortcut (checking only the latest digest, skipping intervening epochs) depends on the owner having verified at least a first-value proof once at enrollment and having cached the resulting prefix-tree branch checks; a system that discards this cached state between sessions forces the owner back to a from-scratch check. Any external mechanism relying on Merkle²'s auditor cost advantage needs auditors who checked the log recently enough that the number of appends since their last check exceeds the paper's measured 28-append break-even point against CONIKS-style per-epoch digest fetching — below that append count, the paper's own data shows CONIKS's simpler per-epoch fetch is not meaningfully more expensive. The system assumes an Ed25519 key infrastructure for the one public-key operation it performs (append confirmation signing) and a SHA-3 hash function for all tree-node commitments; substituting either changes the paper's stated 128-bit security-level target and none of the reported performance numbers were measured under an alternative choice.

### Contradicts
This paper makes a specific claim about SEEMless (CHASE-CCS-19, same batch) worth flagging for cross-reference: it states SEEMless "relies on strong auditors to monitor the append-only property of the Persistent Patricia Trie, which still incurs a super-linear cost on the auditors" — an asymptotic-complexity characterization, not a disputed measured figure. This does not contradict SEEMless's own reported measured numbers (under 4.24 MB and under 0.3 s per adjacent-epoch audit at 10M users, per the CHASE-CCS-19 entry in this corpus) — a cost can be super-linear in an asymptotic sense while still being small in absolute terms at the specific scale SEEMless measured. A reader combining these two entries should treat the asymptotic classification and the absolute measured numbers as compatible, not conflicting, claims. No other paper in this corpus was found to directly contradict a measured figure in this entry.
