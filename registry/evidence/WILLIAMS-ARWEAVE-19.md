## [WILLIAMS-ARWEAVE-19] Arweave: A Protocol for Economically Sustainable Information Permanence
**Citation:** Sam Williams, Viktor Diordiiev, Lev Berman, India Raybould, Ivan Uemlianin. "Arweave: A Protocol for Economically Sustainable Information Permanence." Arweave technical report (yellow paper), 2019.
**Retrieved:** full text via https://arweave.org/yellow-paper.pdf
**Source URL:** https://arweave.org/yellow-paper.pdf
**Domain:** C

### What it does
Arweave gives a single upfront transaction fee that funds storage of a piece of data indefinitely, replacing the per-contract renewal model other decentralized storage networks use. A block producer earns a mining reward only if it holds a copy of one specific prior block, the "recall block," selected deterministically but unpredictably from a hash of the previous block and its height. To build or verify a new block a miner must present the recall block's full content as input to the proof-of-work hash, a construction the paper calls Proof of Access (PoA). Blocks link to two predecessors, the previous block in sequence and the recall block, forming a graph the paper calls the blockweave rather than a linear chain. Because the recall block is chosen uniformly at random from block history, a miner maximizes its win probability by storing a larger share of the full blockweave, and rarely held blocks give the miners holding them a competitive edge over a smaller pool of rivals also holding that block, so PoA rewards storing scarce data more than storing already-abundant data. Each new full node need not download the entire blockweave: block headers memoize a Block Hash List and a Wallet List sufficient to verify and process new blocks, so a joining node can operate by holding only the current block and progressively verifying backward proofs of work, trading verification trust for the amount of history it fetches. Block propagation sends a compact "blockshadow" — a hash of the Wallet List and Block Hash List plus a list of transaction hashes — rather than the full block; a receiving node that already holds those transactions locally reconstructs the block itself, following the compact-block design of Bitcoin's BIP-152 and the Graphene protocol. Storage cost accrues through a formula for the price of storing one gigabyte on one hard disk drive for one hour, PGBH = HDD_price / (HDD_sz * HDD_mtbf); the perpetual price of storing a data item is modeled as the infinite sum of this per-period cost as the cost is projected to decline over time. Transaction fees fund a storage endowment; each block's total miner reward combines instantly-released transaction fees, a fixed inflation schedule declining with block height, and a top-up drawn from the endowment only when the first two do not cover the modeled storage burden for that block. Node-to-node bandwidth allocation is governed by "wildfire," a reference implementation of an "Adaptive Interacting Incentive Agent" (AIIA) meta-game: each node ranks its peers by a rolling average of response speed and accuracy and by observed generosity in forwarding transactions and blocks, then serves higher-ranked peers first and prunes low-ranked peers probabilistically.

### Parameters
- 1 AR = 1,000,000,000,000 Winston (the sub-unit).
- Genesis supply: 55,000,000 AR, created 8 June 2018; a further 11,000,000 AR (20% of genesis supply) released gradually as block mining rewards, for a maximum circulation of 66,000,000 AR.
- Inflation reward per block: R_inflation = GAR * 0.2 * ln(2) * 2^(-BH/By), with GAR = 55,000,000 (genesis AR) and By = 262,800 (blocks per year).
- Total miner reward per block: R_total = R_fees + R_inflation + R_endowment, where R_fees sums the per-transaction instant reward across all transactions in the block.
- Endowment draw is nonzero only when R_inflation + R_fees fall short of (block_size * PGBB), the modeled per-block-period storage cost of the block; the drawn amount is scaled by Prop(), which weights it by the ratio of the required recall block's size to the network's average block size, so miners forced to hold larger-than-average recall blocks are compensated proportionally more.
- Transaction pricing: TX_cost = TX_size * sum over future block periods of PGBB[i] (price to store 1 GB for one block period at height i); TX_reward = TX_cost * C_fee, a constant fraction; TX_total = TX_cost + TX_reward is what the user pays.
- No numeric value for C_fee is given in the retrieved text.

### Stated limitations
The AIIA/wildfire adaptive mechanism-design layer has three limitations the authors state directly. First, it can only reinforce behavior that a majority of participating agent designers already favor; it cannot compute pro-social behavior independent of that majority, and is exposed to the same class of majority-collusion attack as blockchain Sybil-resistance games generally. Second, AIIA games can adjust only off-chain reputation-like peer rankings; they cannot shift network-wide consensus rules. Third, the speed at which the network adapts to a changing environment is bounded by how much short-term utility nodes are willing to sacrifice to express a pro-social bias; excessively selfish nodes slow that adaptation. The paper reports that as of writing, the only two deployed AIIA agents are wildfire and a second agent called Weaver, and that Weaver nodes are a minority, de-prioritized by the majority of wildfire nodes. The paper's proposed Succinct Proofs of Access mechanism (future work, unimplemented at time of writing) trades away Proof of Access's proof-of-distribution guarantee: it lets a large dataset enter the blockweave by storing only its Merkle root, so consensus about the transaction's inclusion no longer implies the data was ever fully replicated to the network. The paper states this mechanism is intended only as an optional feature for large low-redundancy-requirement datasets. ArQL, the transaction-tag query mechanism, returns results only from the single servicing node's locally held data; the paper states explicitly that a query gives no certainty of completeness across the network. The authors state they do not expect the Arweave network to mine blocks "in true perpetuity," anticipating that the mechanism-design-driven network itself will eventually stop, after which they expect data preservation to depend on social incentives and prior replication rather than the protocol's financial incentives.

### Requirements it places on the rest of the system
A verifying or mining node must be able to fetch the specific deterministically-selected recall block for the current height on demand, so the network requires enough live nodes holding a spread of historical blocks that any given recall block is retrievable within the block-time window; the paper gives no quantified bound on how sparse blockweave replication could become before recall-block retrieval starts failing. Block validation depends on the miner receiving a Wallet List and Block Hash List consistent with the block being validated; a node must synchronize these two structures before it can verify new transactions or blocks, so any indexing or serving layer built on Arweave needs those structures kept current locally rather than fetched per query. Blockshadow-based block reconstruction requires a receiving node to already hold the referenced transactions locally before the compact shadow arrives; a node that does not will fail to reconstruct the block from the shadow alone and must fall back to fetching full transaction data, so any transport layer serving Arweave must propagate individual transactions ahead of, or independent from, block propagation. The storage-endowment pricing model requires the projected decline in PGBH (storage cost per gigabyte-hour) to hold over the multi-decade span needed to fund perpetual storage from a one-time payment; if the actual decline rate falls below the rate priced in at upload time, the endowment underfunds later storage periods, a risk the paper acknowledges only by citing the historical trend's 50-year consistency, not by any margin analysis. ArQL and any application built on transaction tags must tolerate node-local, incomplete query results, since no node is required to hold the full blockweave.
