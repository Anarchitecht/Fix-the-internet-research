## [AZARI-ACNS-25] Tighter Provable Security for TreeKEM
**Citation:** Karen Azari, Andreas Ellison. "Tighter Provable Security for TreeKEM." Applied Cryptography and Network Security (ACNS), 2025. DOI 10.1007/978-3-031-95761-1_20.

**Source URL:** https://doi.org/10.1007/978-3-031-95761-1_20
**Domain:** H

### What it does
The paper computes how many bits of concrete security TreeKEM — the ratchet-tree continuous group-key agreement (CGKA) construction inside the Messaging Layer Security (MLS) protocol — retains for group sizes and operation counts used in practice, by proving a tighter reduction than the prior best bound. TreeKEM's group members occupy the leaves of a binary tree; each commit re-keys the committing user's path to the root and produces ciphertexts encrypting new secrets to sibling subtrees, and the protocol's proof-theoretic security loss (how much an attacker's advantage against the whole protocol can exceed its advantage against the underlying encryption scheme) had previously been bounded only in terms that become vacuous — worse than a random guess — once realistic user counts and commit counts are substituted. The authors' method: define a "generalized selective decryption" (GSD) game specific to a public-key setting, which formalizes the encryption-chain structure TreeKEM produces (each ratchet-tree secret is itself encrypted under other tree secrets, forming a graph of encryption dependencies) and captures how a party's compromise reveals only the state reachable from it, and then prove security of that game directly for DHIES — the Diffie-Hellman Integrated Encryption Scheme, the only public-key encryption scheme currently standardized for use in MLS — in the random oracle model (ROM), rather than proving a generic bound for any IND-CPA-secure (indistinguishable under chosen-plaintext attack) scheme and specializing afterward, which is what produced the prior work's looser bound. The proof reduces GSD security to two underlying assumptions: eavesdropping (EAV) security of the private-key encryption component of DHIES, and hardness of the Diffie-Hellman problem in the group DHIES is instantiated over.

### Measured results
No implementation and no benchmark; every figure below is a numeric consequence of the paper's Theorem 1 security bound, evaluated at named parameter settings, not a measured runtime or bandwidth cost.

| Scenario | Group size / lifetime / commit rate | 128-bit parameters (this paper vs. prior [Klein et al., IEEE S&P 2021]) | 256-bit AES only | 256-bit parameters |
|---|---|---|---|---|
| Large group, hourly commits, frequent updates (update proposals p bounded by p ≤ c·u, dominated by p) | ~10,000 users (u ≤ 2^14), 5-year session, one commit per hour (c ≤ 2^16) | 81 bits (this paper) vs. 64 bits (prior) | 95 bits (this paper) | 209 bits (this paper) vs. 192 bits (prior) |
| Few updates (proposals p ≤ c·log(u), so 3·c·log(u) + p ≤ 2^22) | Same group size and commit rate as above | 90 bits (this paper) vs. 82 bits (prior) | 104 bits (this paper) | 218 bits (this paper) vs. 210 bits (prior) |
| Very large group, one commit per minute, frequent updates (p ≤ c·u) | ~1,000,000 users (u ≤ 2^20), 50-year session, one commit per minute (c ≤ 2^25) | 60 bits (this paper) vs. 34 bits (prior) | 80 bits (this paper) | 188 bits (this paper) vs. 162 bits (prior) |

Conditions common to every row: 128-bit parameters use the MLS_128_DHKEMX25519_AES128GCM_SHA256_Ed25519 cipher suite (Curve25519 Diffie-Hellman group, 128-bit AES), assumed to give a 128-bit security level for both the Diffie-Hellman problem and the private-key encryption scheme, with adversary running-time-to-advantage ratio set to t/ε_EAV = t/ε_DDH = 2^128; 256-bit parameters use MLS_256_DHKEMP521_AES256GCM_SHA512_P521 (curve P-521, 256-bit AES) at a 256-bit security level, with the same running-time ratio set to 2^128. Add proposals are assumed rare relative to update proposals throughout.

Asymptotic form of the two bounds being compared, general (not tied to the numeric scenarios above): this paper's security loss is O(u·(c·log(u) + p)) reducing to EAV security of the private-key encryption scheme, plus O(c·log(u) + p) reducing to Diffie-Hellman hardness; when proposals are few (p < c·log(u)) these simplify to O(c·u·log(u)) and O(c·log(u)) respectively. The prior bound (Klein, Pascual-Perez, Walter, Kamath, Capretto, Cueto, Markov, Yeo, Alwen, Pietrzak, IEEE S&P 2021 — "Tainted TreeKEM") is O((c·log(u) + p)²), reducing to IND-CPA security of the public-key encryption scheme as a whole rather than splitting into a private-key EAV term and a Diffie-Hellman term. Here c is the number of commits, p is the number of add or update proposals, and u is the maximum number of users.

### Parameters
- DHIES construction: a group-generation algorithm G producing a Diffie-Hellman group (𝔾, q, g); a private-key encryption scheme Π_s used for the message payload; a key-derivation function family H_pk, modeled as a random oracle. No numeric group parameters beyond the two cipher-suite examples above (Curve25519 / 128-bit AES; P-521 / 256-bit AES) are evaluated.
- Theorem 1 bound: ε ≤ 2·u·(3·c·log(u) + p)·ε_EAV + 2·(3·c·log(u) + p)·ε_DDH + negl, where ε_EAV is the private-key scheme's EAV-security advantage bound and ε_DDH is the Diffie-Hellman decision problem's advantage bound, each paired with a running time t; the theorem holds for a single challenge query, and the paper states the proof extends to multiple challenge queries without a stated additional multiplicative loss (unlike the prior work's bound, which the paper states requires an additional multiplicative loss in the number of challenges under a hybrid argument to reach the multi-challenge case).
- GSD-graph parameter δ: the maximum in-degree in the generalized selective decryption graph the proof constructs; the general reduction to private-key encryption incurs a security loss of O(δ·N), reduced further to O(N) in Appendix B.4 for "a very specific set of schemes" the paper does not enumerate in the passage read.

### Stated limitations
The paper states, in relation to Alwen, Coretti, Dodis, Tselekounis's modular MLS-security reduction (CCS 2021), that even after substituting this paper's tighter TreeKEM bound into that reduction, the overall MLS protocol's proved security is not expected to reach a meaningful level, because that reduction's own loss (separate from TreeKEM's) is "very large (but polynomial)"; the authors state finding a tighter reduction for MLS as a whole remains "a crucial open problem." The result is proved specifically for DHIES, the one public-key encryption scheme currently standardized in MLS, and the paper does not state that the tighter bound transfers to a different public-key encryption scheme without re-proof. The bound is proved in the random oracle model, requiring the deployed key-derivation function to be treated as an ideal random function; the paper states it does not rely on random-oracle "programmability" in this work, but the analysis is not a standard-model result. The 60-to-95-bit security levels obtained even under this tighter bound are below the 128-bit or 256-bit nominal security level of the underlying primitives at the same parameter choice, so the paper's own numbers show the reduction still gives up security margin relative to the raw primitive strength, particularly in the largest-scale scenario (1,000,000 users, 50-year session, one commit per minute), where the 128-bit-parameter result is only 60 bits.

### Requirements it places on the rest of the system
The bound requires the deployed CGKA construction to be exactly TreeKEM instantiated with DHIES for its public-key encryption component; the proof structure (splitting the security loss into an EAV-security term for the private-key encryption sub-component and a Diffie-Hellman-hardness term) does not apply as stated to a different combination of primitives. It requires whatever key-derivation function DHIES uses to be treated as a random oracle by the rest of the security analysis — a system substituting a concrete hash construction accepts the random-oracle idealization as a standing assumption, not a proved property of that construction. The numeric security levels in the table above are conditioned on assumed 128-bit or 256-bit security levels for the underlying Diffie-Hellman group and AES instantiation, at a stated adversary running-time-to-advantage ratio of 2^128; a deployment assuming a weaker concrete hardness for those primitives, or facing an adversary with a different running-time budget, gets a different bit count than the ones tabulated here, not these ones directly. Achieving the higher bit counts in the "few updates" scenario over the "frequent updates" scenario requires the deployment's actual ratio of add/update proposals to commits to fall in the p ≤ c·log(u) regime — a policy decision made by whatever component in the wider system decides how often users are permitted or required to issue update proposals per commit, not by TreeKEM itself.
