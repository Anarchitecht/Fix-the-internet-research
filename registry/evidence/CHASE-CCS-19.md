## [CHASE-CCS-19] SEEMless: Secure End-to-End Encrypted Messaging with less Trust

**Citation:** Melissa Chase, Apoorvaa Deshpande, Esha Ghosh, Harjasleen Malvai. "SEEMless: Secure End-to-End Encrypted Messaging with less Trust." ACM CCS, 2019. DOI 10.1145/3319535.3363202.
**Retrieved:** full text via candidate URL `https://eprint.iacr.org/2018/607.pdf`
**Source URL:** https://eprint.iacr.org/2018/607.pdf
**Domain:** E

### What it does
SEEMless lets a user detect whether the messaging provider serving her public key to her contacts is showing everyone the same key (non-equivocation), so a compromised or coerced provider cannot silently insert its own key for a man-in-the-middle attack, while also letting key changes take effect in well under a minute instead of the roughly one-hour delay the paper attributes to prior work. It formalizes a privacy-preserving verifiable key directory (VKD): a stateful directory that, at each discrete round (epoch), accepts a batch of username-to-public-key registrations and updates, and produces a short cryptographic commitment to the current directory state. A client queries the directory for a username and receives the current public key plus a proof that the key is bound to the published commitment, without the proof revealing anything about other users' keys (zero-knowledge, with a well-defined leakage function). The construction keeps two append-only zero-knowledge sets (aZKS) built on a Patricia trie: an "all" aZKS holding every version of every (username, key) pair ever issued, and an "old" aZKS holding retired key versions; verifying that a key is current means proving membership in "all" and non-membership in "old." Both aZKS root commitments are chained into a Merkle tree of per-epoch commitments (replacing the plain hash chain used by CONIKS), which the paper states shortens the audit-proof cost. A verifiable random function (VRF) hides which entry in the trie corresponds to which username by mapping the username to a pseudorandom label, so an observer of the tree structure cannot tell how many times a given user has updated her key without also holding a proof; SEEMless uses three VRF evaluations per query response (versus CONIKS's one) as the mechanism enforcing this stronger label-privacy property. Auditors — any party, not a privileged role — verify between consecutive epochs that the aZKS commitments were correctly appended to the Merkle tree and that both aZKS grew append-only; the paper states one honest auditor per adjacent epoch pair is sufficient for the non-equivocation soundness guarantee to hold. A persistent authenticated data structure ("Persistent Patricia Trie," PPTr) stores only the state of each tree node that actually changed at each epoch, rather than the whole tree, which the paper credits with letting the same construction run entirely in RAM at scales where CONIKS's implementation exhausted memory.

### Parameters
- VRF construction: Secp384r1 elliptic curve, Bouncy Castle library, Icart's function for hashing to the curve, SHA-384, with the input hashed twice (`SHA384(0||input)` and `SHA384(1||input)`) and Icart applied to both hashes, because applying Icart once does not give an output indistinguishable from random.
- VRF value size: 48 bytes.
- VRF calls per operation: 1 for a new registration; 2 for a key update (one for the new key entering the "all" aZKS, one for the old key entering the "old" aZKS); 3 total per Query response in SEEMless versus 1 in CONIKS.
- Epoch length: not fixed by the construction; the paper's own experiments treat half-a-minute epochs as a realistic working assumption (525,600 minutes/year approximated by 1M epochs), and states the epoch length is not bounded by blockchain block time when a blockchain is used only for periodic root-commitment posting.
- Test scale range: up to 10M registered users for Query and server-update experiments; up to 1M "regular" users and 10 "special" users, up to 1M epochs, for KeyHistory experiments.
- Auditing granularity: one audit unit covers one pair of adjacent epochs; parallel auditors can each cover disjoint adjacent-epoch pairs.

### Stated limitations
The paper places specific trust assumptions on users and the surrounding system, listed under "Model Assumptions": it assumes the user's device can store her current secret key but may be lost or re-imaged, losing that secret; it assumes the user has some out-of-band way to authenticate to the service provider (a second factor, e.g., a text message or phone call), stated as already required by existing end-to-end encryption systems and therefore not an added attack surface; it assumes the server enforces access control on who may query whose key; and it assumes the user can recognize approximately when she last updated her key, to notice if the log lists updates she does not recognize. It assumes Alice, Bob, and the server keep approximately synchronized clocks. It assumes some external mechanism (a blockchain post, as in Catena, or a gossip protocol, as in CONIKS) exists so that different users' views of the current root commitment do not silently diverge; the paper explicitly leaves that mechanism outside SEEMless itself. The paper explicitly defers to future work: usability studies for the end-user interface exposing VKD verification, and storage optimizations such as moving inactive users' cached VRF values to disk rather than keeping them all in RAM. Server-side caching of every user's VRF proof (to avoid recomputing on Query) is stated to require ≈28 GB at 10M users with 20 updates each — an increasing, not bounded, cost as update counts grow, which the paper does not resolve inside this construction. The paper states Keybase's competing design assumes users hold multiple trusted devices and manage long-term cryptographic signature keys themselves, and states its own authors' judgment that "for an end user, it is incredibly difficult to manage keys" under that assumption — this is the paper's own stated opinion about a different system's user-facing usability, not a measurement.

### Requirements it places on the rest of the system
A working SEEMless deployment needs at least one honest auditor examining every adjacent pair of epochs; the non-equivocation soundness guarantee is stated as conditional on that minimum, and auditing can be distributed arbitrarily across many independent parties without coordination since each adjacent-epoch check is independent. The system needs an external, out-of-band mechanism ensuring all clients' views of the current root commitment do not fork silently — SEEMless does not supply this itself; the paper names a blockchain post (as in Catena) or a gossip protocol (as in CONIKS) as options, and states client software must periodically interact with whichever mechanism is chosen (for a blockchain option, checking the chain at least as often as the "vulnerability window" the deployment is willing to tolerate, since a misbehaving server is caught only at the next post). The user's client software must persist her current key locally between sessions to detect equivocation, since the whole non-equivocation guarantee depends on the user's own device being the source of truth for what her key currently is; a device that never independently remembers this cannot detect a server showing a different party the wrong key. The system assumes the user or her software has an out-of-band, already-established authentication channel to the service provider (e.g., a second factor) independent of the VKD itself — SEEMless does not create or replace this channel. The server needs synchronized-enough clocks with clients to make epoch boundaries meaningful to all parties. Any component relying on SEEMless's stronger label-privacy property (hiding how many times a user has updated relative to CONIKS) inherits the added VRF cost (3x the VRF calls per query) as an explicit privacy/performance trade-off — a caller not needing that specific privacy property gets no benefit from paying this cost.

### Contradicts
None found against other entries in this corpus. Cross-reference: Parakeet (MALVAI-NDSS-23, same batch) presents its own reimplementation of this paper's aZKS construction and measures markedly worse persistent-storage numbers than SEEMless's own self-reported figures here (Parakeet reports ≈66 minutes, 47 storage accesses, to insert 100k users into a 300k-user set with a MySQL-backed persistent layer, versus this paper's RAM-only 0.28-second update-time figure at 10M users). This is not a contradiction of a shared measurement — the two papers measure different storage backends (SEEMless's own experiments run entirely in RAM; Parakeet's SEEMless reimplementation adds a MySQL persistence layer) and different operations, so the discrepancy reflects added persistent-storage cost, not a disputed figure for the same configuration. A reader combining the two entries should not average or directly compare these two sets of numbers as if they described the same experimental setup.
