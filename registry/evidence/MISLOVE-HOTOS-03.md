## [MISLOVE-HOTOS-03] POST: A Secure, Resilient, Cooperative Messaging System

**Citation:** Alan Mislove, Ansley Post, Charles Reis, Paul Willmann, Peter Druschel, Dan S. Wallach, Xavier Bonnaire, Pierre Sens, Jean-Michel Busca, Luciana Arantes-Bezerra. "POST: A Secure, Resilient, Cooperative Messaging System." Proceedings of HotOS IX, USENIX Association, 2003. Pages 61-66.
**Retrieved:** full text via https://www.usenix.org/legacy/events/hotos03/tech/full_papers/mislove/mislove.pdf
**Source URL:** https://www.usenix.org/legacy/events/hotos03/tech/full_papers/mislove/mislove.pdf
**Domain:** L

### What it does
POST delivers messages (electronic mail, instant messages, news, calendar and whiteboard updates) between users without a dedicated server, by storing every message once in a peer-to-peer store and telling the recipient where to find it. POST is built on Pastry, a structured peer-to-peer overlay in which every node and every stored object holds a 160-bit identifier from the same numeric space, and a message can be routed to the node whose identifier is numerically closest to a given key. Two services layer on Pastry: PAST, a distributed hash table that stores each object's replicas at the k nodes whose identifiers are numerically closest to the object's handle (a 160-bit key), and Scribe, a multicast system that builds a tree from Pastry routes joining every subscriber to one rendezvous node per group.

A user creates a message and inserts it, encrypted, into the shared store; the insertion produces a handle. POST's event-notification service then sends the recipient a small signed, encrypted message containing that handle and the decryption key, delivered to the contact address recorded in the recipient's identity block (itself a signed, mutable record stored in PAST under the hash of the user's public key). The recipient's client reads its own metadata log — a chain of content-hash blocks, each linked to the previous one and signed only by its single owner — to track which messages have arrived, without any other party being able to insert or alter log entries undetected. Message bodies are stored once system-wide through convergent encryption: the store computes Hash(X) over the plaintext X, uses that hash as the symmetric encryption key, and stores the ciphertext at the handle Hash(Encrypt_Hash(X)(X)); because the same plaintext always produces the same ciphertext and handle, POST stores only one copy of any message body inserted independently by multiple senders, even before any of those senders authorize a given recipient to read it — decryption still requires knowledge of the plaintext hash.

For a recipient who is not online when a message arrives, the paper states the sender delegates the notification-delivery obligation to a set of k randomly selected nodes, but does not describe the mechanism further, citing lack of space. Message delivery itself does not depend on the recipient being online: the message body is durably stored in PAST (replicated at k nodes) at insertion time, and the recipient retrieves it, together with the queued notification, whenever its own daemon next comes online and polls or receives the delegated notification.

To bound the network scope over which any one message is replicated, POST groups nodes into organizational overlays nested inside one global overlay: documents inserted by a member of an organization replicate only among that organization's own nodes, rather than across the entire global Pastry ring, while retrieval still works from anywhere in the global overlay. The paper states this construction in outline and omits its mechanism, again citing lack of space.

### Measured results
None. The paper is a HotOS (Hot Topics in Operating Systems) position paper describing a system design; its final section states that prototype implementations of POST and ePOST (the email application built on POST) exist and are "currently under experimental evaluation," and that calendaring and instant-messaging applications are "underway," but no quantitative result — no message count, node count, latency, storage overhead figure, or replication-factor measurement — appears anywhere in the text. Any figure attributed to this paper for delivery latency, storage overhead, or replication behavior is not supported by this text.

### Parameters
- Replication factor: denoted k throughout (the number of nodes holding a replica of each PAST-stored object); no numeric value is given in this paper. The system is stated to tolerate up to k-1 faulty or unreachable nodes in any replica set without loss of data or service.
- Notification delegation set size for offline recipients: also denoted k random nodes; no numeric value given, and the delegation mechanism itself is not described (cited as omitted for space).
- Log clustering parameter M: consecutive log records are stored together in clusters of M records on a single node, to reduce the cost of walking the log; no numeric value is given.
- No parameter in this paper carries an experimentally chosen value; every one is presented symbolically.

### Stated limitations
The paper states that determining an appropriate replication factor and appropriate assumptions about the fraction of faulty nodes in a given deployment requires further analysis and experimentation, and cites a prior study of peer-to-peer file systems in enterprise settings as evidence that "modest levels of replication can yield high availability," without itself supplying that measurement. Storage overhead per message is stated to be higher in POST than in a conventional server-based email system, because of the k-way replication PAST performs, an effect the authors say is partly offset by the single-copy property of convergent encryption removing duplicate attachment storage, and further offset by using otherwise-idle desktop disk space; erasure coding is cited as a further possible reduction that "we have not yet explored." Convergent encryption is stated to be vulnerable to a known-plaintext attack: an adversary who can guess a message's plaintext can confirm the message's presence in the store (though not who inserted it, and not who else references it, since metadata referencing a message is itself encrypted); the authors recommend prepending random bits before convergent encryption for small, highly structured, or otherwise predictable content. Single-writer logs are stated to be the only supported mechanism for mutable state, adopted specifically to avoid the cost and complexity of a general Byzantine fault-tolerant replicated state machine; the authors state this is not flexible enough for every cooperative application and that a separate line of work at LIP6 was investigating additional Byzantine fault-tolerant mechanisms for multi-writer mutable state, unresolved at the time of writing. Objects stored in PAST are assumed non-deletable throughout the design, which the paper states requires available disk space in the system to be always increasing and to exceed total storage demand. The paper states it remains an open question whether decentralized email of this kind will be sufficient to displace existing server-based email infrastructure.

### Requirements it places on the rest of the system
The mechanism requires a trusted certificate authority that signs a binding between each user's unique name (for example, an email address) and their public key, and separately issues the node-identifier certificates Pastry's secure routing depends on to resist adversarial node placement; POST assumes this authority exists and may set policy (for example, requiring each user's node identifier to be bound to a live IP address) to force resource contribution. Every user is assumed to trust exactly one node, their own "trusted node," with their private key; no other node in the system is trusted by that user. The durability of any stored message depends on the failure independence of the k nodes holding its replicas and on a replication factor chosen relative to the actual node failure rate in the deployment, neither of which this paper measures; the organizational-overlay construction is offered specifically so that failure-independence assessment can be scoped to nodes under one administrative domain rather than the global overlay. The event-notification and metadata-log mechanisms both depend on Pastry's secure routing service (cited to Castro, Druschel, Ganesh, Rowstron, Wallach, OSDI 2002) to resist a malicious node intercepting or misdirecting a lookup; POST does not reimplement that defense itself. The offline-delivery mechanism (notification delegated to k random nodes) is asserted but its correctness properties, including what happens if some delegated nodes are themselves offline or faulty, are not specified in this text.

### Contradicts
None found. No other paper in this batch reports a directly comparable delivery-latency or storage-overhead figure for a store-and-forward peer-to-peer messaging design, and this paper reports no measured figures of its own to be contradicted.
