## [KLEPPMANN-TPDS-17] A Conflict-Free Replicated JSON Datatype

**Citation:** Martin Kleppmann, Alastair R. Beresford. "A Conflict-Free Replicated JSON Datatype." IEEE Transactions on Parallel and Distributed Systems, 2017. DOI 10.1109/TPDS.2017.2697382.
**Retrieved:** full text via https://arxiv.org/pdf/1608.03960
**Source URL:** https://arxiv.org/pdf/1608.03960
**Domain:** D

### What it does
Lets independent replicas modify a JSON document (arbitrarily nested maps, ordered lists, and registers holding primitive values) concurrently, offline, and merge every replica back to the same state with no coordination and no lost input, using a CRDT (Conflict-free Replicated Data Type, a data structure whose concurrent updates are constructed to commute so any delivery order produces the same result). Each replica applies a mutation to its own local copy immediately, generates an operation describing that mutation, and asynchronously broadcasts the operation to other replicas; no operation can fail once performed locally, unlike systems such as Bayou that allow tentative transactions to later be rolled back.

Every operation is assigned a unique identifier that is a Lamport timestamp: a pair `(c, p)` where `p` is the identifier of the generating replica (for example, a hash of its public key) and `c` is a per-replica counter incremented for every operation the replica generates, so `c` is compared as an integer. When a replica receives an operation with a counter value greater than its own stored counter, it advances its local counter to that value; this guarantees any operation causally caused by an earlier operation has a strictly greater counter, and only concurrent operations can share a counter value. Ties between concurrent operations with the same counter are broken by comparing replica identifiers, producing a total order over all operation identifiers.

Every operation carries an explicit `deps` field, the set of Lamport timestamps of its direct causal dependencies. A replica buffers an incoming remote operation and applies it (APPLY-REMOTE) only once every identifier in its `deps` set is already present in the replica's own set of applied operation identifiers; delivery need not arrive in causal order over the network, because the replica enforces the ordering itself before application. List elements form a linked structure: each element has a unique identifier (the identifier of the insertion operation that created it), and local state maps each identifier to the identifier of the following element (`next`). A deletion never removes an element from this linked structure; it clears the element's presence set (the set of operations that assert the element exists) to empty, marking it a tombstone, so ordered position is preserved even after deletion and a concurrent operation referencing a deleted element can make its presence set non-empty again. Maps and registers use the same presence-set mechanism: a key or register value is considered absent when its presence set is empty. Because assignment to a register is not globally serialized, concurrent assignments to the same register from different replicas leave all concurrently assigned values present simultaneously rather than picking one as a winner, preserving every user's input; nested lists and nested maps compose recursively by the same rule (an insertion or assignment can target a position inside an already-nested structure).

A "cursor" identifies a position in the document as a path of alternating map keys and list-element identifiers from the document root, so a cursor can be transmitted between replicas and used to locate the same logical position even after concurrent edits change the surrounding structure.

### Measured results
None. The paper states, in its own conclusion, that it is a formal semantics only: a practical implementation and its performance characteristics are explicitly deferred to follow-on work. No implementation, benchmark, message-size figure, or memory-overhead figure for this algorithm appears anywhere in the text. The paper cites Attiya et al. [31] as having independently analyzed metadata overhead for collaboratively edited lists and provided a correctness proof of the RGA (Replicated Growable Array) algorithm, but does not itself reproduce or report that analysis's figures, and RGA is a component this paper builds its list semantics on, not a separately measured baseline in this paper.

### Parameters
None with numeric values; the algorithm is presented as operational semantics (inference rules), not as a system with configuration parameters.

### Stated limitations
The paper is scoped to formal semantics of the JSON CRDT; a practical implementation and measurement of its performance are deferred to follow-on work. The supported operation set is insertion, deletion, and assignment; the authors state a move operation (reordering list elements or relocating a subtree) and an undo operation would be useful but are not defined here. Tombstones (deleted-element markers) are retained forever in this design; the authors state garbage collection of tombstones is required to prevent unbounded growth of the data structure and is left to future work. The authors state the "no input is ever lost" design principle produces merged states that can surprise application programmers unfamiliar with concurrent semantics (their Figure 6 example), and that further work is needed on understanding programmer expectations and on a possible schema language to express, for example, that a numeric field should behave as a counter rather than a plain register. The liveness property (every replica eventually processes every operation) is stated as an assumption, not proved in the paper; the authors assert it "can usually be provided in practice" because network interruptions are of finite duration, without a supporting measurement. Lamport-timestamp causal dependency sets (`deps`) are defined in the paper as the full set of an operation's causal-history timestamps; the paper notes a real implementation would need a more compact representation of causal history than storing the full set, without specifying one.

### Requirements it places on the rest of the system
Every replica needs a transport that eventually delivers every generated operation to every other replica; delivery order across the network need not be causal, but the replica must buffer any operation whose `deps` are not yet all locally applied and apply it only once they are — so the replica-side apply logic, not the network, is what enforces causal order. Each replica needs a stable, comparable replica identifier (the paper suggests a hash of the replica's public key) and a monotonically increasing local counter, and must advance that counter upon receiving any operation with a higher counter value, to keep Lamport timestamps globally unique and causality-respecting. The system must retain tombstones for every deleted list element or map key indefinitely unless a separate garbage-collection mechanism (not defined in this paper) is added, so storage grows monotonically with the number of insert/delete operations ever issued, not with the current document size. Because concurrent assignments to the same register are all retained rather than resolved to one winner, any component consuming the document (the client application) needs its own policy for choosing among multiple concurrently present register values or presenting them to the user. The mechanism assumes every operation reaches every replica eventually (fair-loss, retry-based delivery); it does not itself provide encryption, authentication, or defense against a replica that forges another replica's Lamport timestamp or fabricates false causal dependencies.
