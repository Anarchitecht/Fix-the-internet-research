## [MALKOV-TPAMI-20] Efficient and robust approximate nearest neighbor search using Hierarchical Navigable Small World graphs
**Citation:** Yu. A. Malkov, D. A. Yashunin. "Efficient and Robust Approximate Nearest Neighbor Search Using Hierarchical Navigable Small World Graphs." IEEE Transactions on Pattern Analysis and Machine Intelligence 42(4), 2020 (preprint arXiv:1603.09320, 2016). DOI 10.1109/TPAMI.2018.2889473.
**Retrieved:** full text via https://arxiv.org/abs/1603.09320
**Source URL:** https://arxiv.org/abs/1603.09320
**Domain:** B

### What it does
Hierarchical Navigable Small World (HNSW) finds the approximate K nearest neighbors of a query vector in a stored set of vectors, at a query cost that scales logarithmically with the number of stored elements rather than linearly, by searching a multi-layer proximity graph greedily from the top layer down. Each stored element is assigned an integer maximum layer at insertion, drawn from an exponentially decaying probability distribution controlled by a normalization parameter mL; the assignment needs no separate shuffling step, because the randomness comes from the layer draw itself. Within each layer, elements are connected into a proximity graph approximating a Delaunay graph (the graph in which two points are connected if their Voronoi cells touch), with fewer, longer-range connections at the upper layers and denser, shorter-range connections at the bottom layer. A search starts at a fixed entry point on the top layer and greedily moves to whichever connected neighbor is closest to the query (the "zoom-in" phase) until it reaches a local minimum in that layer; the local minimum is then used as the entry point into the next lower layer, and the process repeats until a search of the bottom layer (layer zero) returns the final result set. Insertion runs the same greedy-descent search on each layer down to the newly assigned element's own maximum layer, then applies a neighbor-selection heuristic to pick which of the search's candidate closest elements become the new element's graph connections; the heuristic examines candidates from nearest to farthest and connects to a candidate only if that candidate is closer to the element being inserted than to any already-connected candidate, which keeps well-separated clusters connected to each other (Section 3, Fig. 2) rather than only connecting to the single nearest cluster. Each element's connection count per layer is capped (parameter Mmax, with a separate cap Mmax0 for the bottom layer); when a capped element gains a new connection, its existing connections are re-pruned by the same heuristic.

### Measured results
Search-quality claims are stated as approximate K-nearest-neighbor recall against a controllable search-width parameter ef; the paper defines no single fixed "accuracy" figure independent of ef and dataset. Complexity: search and insertion both scale as O(log(N)) in expectation for datasets where the average node degree in the true Delaunay graph is bounded by a constant independent of dataset size N, a condition the paper states holds for random Euclidean data but which the authors say is not established for other spaces; insertion (construction) time for the whole index therefore scales as O(N log N). Comparison against the flat (non-hierarchical) NSW baseline (nmslib 1.1 "sw-graph" implementation): on a d=8 random hypercube dataset with 10-NN search at fixed recall 0.95, HNSW's query-time scaling with dataset size was not worse than logarithmic and outperformed NSW at every dataset size tested, on a Core i5 2400 CPU, single thread. On general (non-Euclidean, non-metric) datasets from a prior comparison study, repeated with the same nmslib test scripts: on the "wiki-8" dataset (2M elements, 8-dimensional Jensen-Shannon-divergence topic histograms, 10-NN search, distance-computation count rather than CPU time used to avoid confounding by implementation), HNSW's improvement over flat NSW reached almost three orders of magnitude, the largest margin of any dataset tested, on a dataset the authors state was NSW's weakest case. Comparison against open-source Euclidean K-approximate-nearest-neighbor (K-ANNS) algorithms (FLANN 1.8.4, Annoy, VP-tree, FALCONN 1.2) using the ann-benchmark testbed, single thread, on a 4-socket Xeon E5-4650 v2 server with 128 GB RAM, GCC 5.3 with -Ofast: HNSW is reported to outperform all rivals "by a large margin" on SIFT (1M points, d=128, brute-force query time 94 ms), GloVe (1.2M points, d=100, cosine similarity, BF 95 ms), CoPhIR (2M points, d=272, BF 370 ms), and DEEP (1M points, d=96, BF 60 ms); on 30M random d=4 points (BF 590 ms) HNSW is reported slightly faster than Annoy at high recall and clearly ahead of the remaining baselines; no single numeric recall-versus-latency figure is stated in the extracted text outside the plotted curves (Fig. 13). Construction-time and thread scaling: on a 10M-point SIFT dataset (d=128, M=16, efConstruction=100), build time was measured on two CPUs (a 4-socket Xeon E5-4650 v2 with 40 cores total, and a 6-core/12-thread Core i7-6850K) across 0-40 threads (Fig. 9), showing construction time falling with added threads with no measurable loss of index quality (specific minute values are read from a plot, not a table, and are not extracted here). At efConstruction=100 on the 4-socket Xeon server, a reasonable-quality 10M-SIFT index was built in 3 minutes. Comparison against Facebook's Faiss product-quantization (PQ) library on a 200M-point subset of the 1B SIFT dataset, on the same 4-socket Xeon E5-4650 v2 / 128 GB RAM server (Table 3): HNSW with M=16, efConstruction=500 built in 5.6 hours and used 64 GB peak runtime memory; HNSW with M=16, efConstruction=40 built in 42 minutes and used the same 64 GB; Faiss configuration 1 (OPQ64, IMI2x14, PQ64) built in 12 hours using 30 GB; Faiss configuration 2 (OPQ32, IMI2x14, PQ32) built in 11 hours using 23.5 GB. The paper states HNSW used significantly more RAM than Faiss but achieved higher accuracy, higher query speed, and faster index construction on this comparison (Fig. 15); the query-time-versus-dataset-size scaling for HNSW on this 200M-point run deviated from pure logarithmic scaling, which the authors attribute to the dataset's relatively high dimensionality.

### Parameters
- M (number of established connections per element per layer, the algorithm's one construction parameter left for the user to tune): reasonable range 5 to 48; smaller M favors lower recall targets and lower-dimensional data, larger M favors high recall and high-dimensional data; M is proportional to the index's memory consumption.
- Mmax0 (maximum connections per element at the bottom, zero, layer): setting it equal to M produces a strong performance penalty at high recall; the paper's simulations find 2*M a good default, with values above that degrading performance and increasing memory use without benefit.
- mL (normalization factor for the exponentially decaying layer-assignment distribution): the paper's suggested default is 1/ln(M) ("Autoselect" in the figures), determined empirically rather than derived from a formula given in the extracted text.
- efConstruction (candidate-list size used during index construction, controlling construction-time recall): the paper states it must be large enough to reach K-ANNS recall close to 1 during construction (0.95 is stated as sufficient for most use cases); larger values give little additional performance benefit but significantly increase construction time; efConstruction=100 was used for the 10M-SIFT construction-time measurement, and efConstruction=500 vs 40 for the two 200M-SIFT/Faiss comparison configurations.
- ef (candidate-list size used at query time, controlling the search-time recall/latency tradeoff): tuned per query; no single default value is stated, since it is the mechanism by which the query-time recall/latency point is chosen.
- extendCandidates (heuristic option, default false; stated as useful only for extremely clustered data) and keepPrunedConnections (heuristic option to keep a fixed number of connections per element), both parameters of the neighbor-selection heuristic (Algorithm 4).

### Stated limitations
The authors state that the search always starts from the top layer's single fixed entry point, and that this structure cannot be distributed by the same techniques used for the flat NSW graph, because congestion concentrates at the small number of high-layer elements; they describe partitioning data across cluster nodes as a workaround, but state that under partitioning the total parallel throughput of the system does not scale well with the number of nodes. The authors state that the theoretical O(log N) complexity derivation assumes an exact Delaunay graph with node degree bounded by a constant independent of dataset size, a condition they can confirm empirically only for low-dimensional data (their empirical check uses d=4); for high-dimensional data (e.g., d=128) they state that the average Delaunay-graph degree scales exponentially with dimensionality, making the same empirical check infeasible at reachable dataset sizes, and that further analytical work is needed to know whether the resilience result generalizes to higher dimensions. The paper states that M is the one construction parameter still requiring user selection with no auto-tuning method offered, and lists as future work inferring M automatically, testing at full 1-billion-point scale, and adding support for element update and removal, which the version described here does not support.

### Requirements it places on the rest of the system
The search algorithm requires a fixed, designated entry point for the top layer of the graph; any system serving queries with HNSW must know or discover this entry point before it can start a search, and the entry point is updated whenever an inserted element's randomly drawn layer exceeds the current top layer. Distributing this index across separate machines (relevant for a decentralized deployment across untrusted peers, open problem 2 in the governing brief) is a problem the authors state their approach does not solve, because search congestion at the top layer defeats the flat-NSW technique for distribution, and the stated workaround (partitioning data across nodes) is stated not to scale its aggregate query throughput with added nodes. The paper's evaluated construction and query pipeline assumes a stable stored vector set for the duration of a query burst; it offers construction-time parallelism across threads with no measured index-quality loss, but does not evaluate concurrent insertion and deletion, which the authors state is unsupported by the version tested.
