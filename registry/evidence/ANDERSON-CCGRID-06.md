## [ANDERSON-CCGRID-06] The Computational and Storage Potential of Volunteer Computing
**Citation:** David P. Anderson, Gilles Fedak. "The Computational and Storage Potential of Volunteer Computing." IEEE/ACM International Symposium on Cluster Computing and the Grid (CCGrid), 2006. DOI 10.1109/CCGRID.2006.101.
**Retrieved:** full text via https://boinc.berkeley.edu/potential_ccgrid.pdf
**Source URL:** https://boinc.berkeley.edu/potential_ccgrid.pdf
**Domain:** C

### What it does
The paper measures the hardware capacity that "volunteer computing" — a deployment model where members of the public run client software on their own machines to contribute computing and storage to a project they do not administer — actually supplies, using logged measurements from the SETI@home project's host pool as of November 18, 2005. Each participating host runs the BOINC (Berkeley Open Infrastructure for Network Computing) client, which periodically benchmarks the host's central processing unit (CPU) speed via the Whetstone and Dhrystone synthetic benchmarks, measures installed random-access memory (RAM), swap space, total and free disk space on the volume it is installed on, and download network throughput measured during active file transfers, and reports these along with availability statistics to a scheduling server. The paper aggregates these per-host reports (217,551 hosts with data as of the measurement date, per the paper's own breakdown tables) into distributions and combines them into project-wide capacity estimates. The paper's central mechanism is a multiplicative capacity model: total usable floating-point computing power X is stated as the product of nine independently measured factors — host arrival rate, average host lifetime, average CPUs per host, average floating-point operations per second (FLOPS) per CPU, average CPU efficiency (fraction of CPU time actually available to the volunteer application net of other load), average on-fraction (fraction of time the client runs), average active-fraction (fraction of on-time during which the user's preferences permit computation or communication), the reciprocal of the average redundancy factor applied for fault tolerance, and the average per-project resource share when a host is attached to more than one project. An analogous multiplicative expression is used to estimate storage and network-transfer capacity from the corresponding measured factors.

All figures below are drawn from the SETI@home BOINC host pool, snapshotted November 18, 2005, restricted to hosts that had completed at least one unit of work in the prior two weeks. The breakdown tables in the paper sum to 217,551-217,552 hosts (Table 1: CPU-type breakdown totals 217,551; Table 5: hosts-per-user breakdown totals 217,552); the paper's own abstract separately rounds this to "about 200,000 hosts."

### Parameters
- Host inclusion window: hosts that completed work within the prior two weeks of the November 18, 2005 snapshot.
- Redundant computing factor: 2-way redundancy assumed in the capacity-reduction estimate ("slightly more than two" reduction), with escalation to a third instance only on result disagreement; no specific measured disagreement rate given.
- Default BOINC user-preference values reported as measured settings, each with its default alongside the measured average: "run if user active" (default No, 71.9% of users select Yes); active-hours restriction (default none, 3.3% of users set a range, average duration 12.41 hours); communication-hours restriction (default none, 0.8% of users set a range, average duration 12.18 hours); minimum connection interval (default 0.1 days, average setting 0.69 days); disk access interval (default 60 seconds, average setting 78.9 seconds); disk maximum used (default 100 GB, average setting 63.6 GB); disk maximum percent used (default 50%, average setting 42.6%); disk minimum free (default 0.1 GB, average setting 0.97 GB); per-project resource share (average 0.917 for SETI@home, with 16.8% of users also attached to other BOINC projects).

### Stated limitations
The paper states BOINC measures disk space only on the volume where the client is installed, so its per-host disk figures underestimate hosts with additional unmeasured volumes and can overestimate space where several BOINC installations share one network-accessible volume. The paper states the churn/lifetime measurement (89.5 days average) "underestimates lifetime because it omits active hosts," since it counts only hosts that had already gone a month without communicating. The paper states BOINC does not measure RAM or swap usage by other, non-BOINC applications on the host, so the capacity figures reflect installed hardware rather than what is actually free for a volunteer application to use at any given moment. The paper states its data-intensive-application analysis "omits some important factors: saturating lots of client network connections could swamp the outgoing server links, ISP backbone networks, and shared incoming links," and that addressing this "raises numerous research issues." The paper states it has about ten months of historical host data at the time of writing but that "the rapid change in the host pool makes it hard to derive meaningful conclusions from this data," so no longitudinal churn trend is reported, only the single-snapshot lifetime average. The paper states peer-to-peer communication between volunteer hosts (needed for large intermediate or replicated input files) is not yet supported by BOINC and is future work requiring separate measurement of peer-to-peer connectivity and bandwidth.

### Requirements it places on the rest of the system
Requires that whatever component consumes this capacity estimate tolerate the redundancy overhead the paper describes as necessary for correctness: because "anonymously volunteered computers can't be trusted," the paper's own capacity model already discounts raw hardware capacity by a redundant-computing factor of slightly more than two, so any storage or computation layer built on this host population must either replicate the same validation technique (multiple independent hosts computing or holding the same unit, compared for agreement) or accept unvalidated results from untrusted volunteer hosts. Requires the consuming system to model per-host availability rather than assume durable presence: mean on-fraction 0.81, connected-fraction 0.83, active-fraction 0.84, and mean host lifetime 89.5 days (itself an underestimate) mean a storage or compute placement mechanism must plan for a host disappearing from the network on a timescale of roughly three months on average, and must not assume uninterrupted network reachability even while a host is on. Requires the consuming system to supply its own inter-host communication mechanism if it needs volunteer hosts to exchange data directly, since the paper states BOINC's architecture is entirely client-initiated communication with a central scheduling server (which the paper notes as an advantage for firewall and network-address-translation, NAT, traversal) and has no peer-to-peer transfer capability at the time of writing. Requires accounting for the fraction of a host's disk space and network throughput that its owner has reserved via BOINC's own preference settings (e.g., the default 50% maximum-disk-percentage and 100 GB maximum-disk-usage limits), since the measured averages already reflect these self-imposed caps rather than raw hardware totals.

### Contradicts
The target registry's own citation note for this key states the paper covers "more than 330,000 hosts." The retrieved full text's own breakdown tables (Table 1, Table 2, Table 5) sum to 217,551-217,552 hosts, and the paper's abstract independently rounds this to "about 200,000 hosts." No figure matching 330,000 appears anywhere in the retrieved text. The 330,000 figure in the registry's `why_needed` field is not supported by this paper and must not be carried into any downstream synthesis; the correct measured host count from the primary source is approximately 217,551-217,552 (as of the November 2005 snapshot), rounded by the paper itself to "about 200,000."

- Chien, Calder, Elbert, Bhatia. "Entropia: architecture and performance of an enterprise desktop grid system." Journal of Parallel and Distributed Computing 63, 2003, 597-610. — competing (a differently architected volunteer/desktop-grid deployment, studied for application speedup rather than raw capacity measurement).
- Germain, Neri, Fedak, Cappello. "XtremWeb: Building an Experimental Platform for Global Computing." 1st IEEE/ACM International Workshop on Grid Computing, 2000. — competing (another volunteer-computing platform studied for application speedup; shares an author, Fedak, with this paper).

"Condor - A Hunter of Idle Workstations." 8th International Conference on Distributed Computing Systems, 1988, pp. 104-111. — foundational (pioneered idle-workstation cycle-stealing; the paper explicitly contrasts Condor's trusted, migratable-task model against volunteer computing's untrusted, non-migratable model).
- Kubiatowicz et al. "OceanStore: An Architecture for Global-Scale Persistent Storage." ASPLOS, 2000. — foundational (cited as the type of long-term storage application for which the paper's measured host-churn statistics are directly relevant).
- Foster, Iamnitchi. "On Death, Taxes, and the Convergence of Peer-to-Peer and Grid Computing." 2nd International Workshop on Peer-to-Peer Systems, 2003. — foundational (source of the comparison data-processing ratios — 60 MB and 660 MB per CPU-hour for astrophysics applications — that this paper's data-intensive-application analysis is built against).
- Kondo, Taufer, Brooks, Casanova, Chien. "Characterizing and Evaluating Desktop Grids: An Empirical Study." IPDPS, 2004. — competing (an independent empirical measurement study of desktop-grid host availability, comparable in kind to this paper's own measurement).

Microsoft Research Technical Report MSR-TR-2003-24, 2003. — foundational (cited as the paper's source for the incentive and participation-driver factors that determine host-pool growth, referenced in the paper's Section 3.1 discussion of host-count growth).
