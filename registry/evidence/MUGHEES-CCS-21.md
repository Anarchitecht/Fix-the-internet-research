## [MUGHEES-CCS-21] OnionPIR: Response Efficient Single-Server PIR
**Citation:** Muhammad Haris Mughees, Hao Chen, Ling Ren. "OnionPIR: Response Efficient Single-Server PIR." ACM CCS, 2021. DOI 10.1145/3460120.3485381.
**Retrieved:** full text via https://eprint.iacr.org/2021/1081.pdf
**Source URL:** https://eprint.iacr.org/2021/1081.pdf
**Domain:** G

### What it does
OnionPIR retrieves one entry from a server-held database without revealing to the server which entry was requested (single-server private information retrieval, PIR), while keeping the amount of data the client must download close to the size of the entry itself. In single-server PIR, the database of N entries is treated as an array; a basic protocol has the client send an encrypted query vector of N ciphertexts, one per database position, each homomorphically encrypting 1 at the target index and 0 elsewhere, and the server homomorphically computes the dot product of the query vector against the plaintext database and returns the encrypted result. Because N ciphertexts is too large to send directly, prior schemes reduce request size with hierarchical (multi-dimensional hypercube) queries and query compression (packing many query bits into one ciphertext, as in the prior system SealPIR), at the cost of a large response: the server's homomorphic dot-product computation in the second dimension of the hypercube multiplies together large ciphertexts, and this multiplication's noise growth forces the use of a large ciphertext modulus, which inflates the size of the encrypted response the client must download to on the order of 100 times the size of the underlying plaintext entry, independent of database size.

OnionPIR controls this noise growth using a technique from fully homomorphic encryption bootstrapping literature adapted to PIR: it replaces the second-dimension ciphertext-ciphertext multiplication with an "external product," a ciphertext-plaintext-style operation between a regular BFV ciphertext and an RGSW ciphertext (RGSW is a homomorphic-encryption ciphertext format designed for this operation). An external product decomposes one operand into small digits before multiplying, which grows the result's noise far more slowly than a direct ciphertext-ciphertext product, so the response can be encrypted under a much smaller ciphertext modulus while remaining decryptable, directly shrinking the response's byte size. A single query ciphertext is decomposed into RGSW form and expanded into the individual per-index selection ciphertexts server-side using a homomorphic "ciphertext expansion" procedure, so the client sends only a logarithmic number of query bits rather than one ciphertext per hypercube row.

Stateful OnionPIR extends this with a precomputation ("offline") phase, following the framework of Patel et al.'s stateful PIR: the client downloads compact helper information (subset sums over c partitions of the database, each partition of size k) ahead of time, cached as local client state; at query time (the "online" phase), the client combines its held state with a lightweight per-query request to retrieve the target entry using far less server computation per query than the stateless scheme, at the cost of periodically refreshing the state offline. Patel et al.'s original scheme requires the client to download the entire database once during the offline phase, which makes its amortized response size scale with the whole database. OnionPIR's stateful variant instead uses a technique the paper calls PBSR (partition-based subset retrieval), built on a homomorphic evaluation of a Benes copy network (a routing network built from a sequence of 2x2 switches, each a multiplexer selecting one of two inputs) to combine batched PIR retrieval of the needed subset sums with the copy-network routing homomorphically, so the offline phase downloads only the small helper data rather than the whole database, at a stated cost of doubling the per-query response size relative to stateless OnionPIR.

### Measured results
Hardware: Amazon EC2 t2.2xlarge instance, 32 GB RAM, 8 CPU cores with AVX enabled. Implementation built on Microsoft SEAL, a homomorphic-encryption library, with the paper's own implementation of RGSW ciphertexts and external products added on top. Batched PIR was not implemented; its offline-phase computation cost is simulated rather than measured, and this simulation applies only to the stateful-OnionPIR offline-phase figures (all other reported figures are direct measurements). Each non-simulated result is the average of 10 runs. Monetary cost is computed, not separately measured, from Amazon EC2's published on-demand rates as of the paper's writing (July 2021): one cent per CPU-hour and nine cents per GB of internet traffic.

Parameters: polynomial degree n = 4096, ciphertext coefficient modulus q = 124 bits, plaintext modulus t = 60 bits, giving a ciphertext expansion factor F = 4.2x; SEAL's default noise standard deviation and secret-key distribution; the Albrecht et al. LWE (learning with errors) hardness estimator rates these parameters at approximately 111 bits of computational security. Comparison baseline SealPIR uses n = 2048, q = 60 bits (115 bits of security by the same estimator), t = 12 bits, giving expansion factor F = 10. Each database entry is fixed at 30 KB; at n=4096/t=60-bit, one OnionPIR ciphertext holds 30 KB of plaintext, versus 3 KB per ciphertext in SealPIR (so a 30 KB entry there is split across 10 chunks). Database sizes tested: N = 2^16, 2^18, 2^20, 2^24 entries.

Stateful OnionPIR reduces computation by 1.8x to 22x over stateless OnionPIR across the tested database sizes (larger reduction at larger N), at a stated cost of doubled per-query response size (128 KB stateless to 256 KB total stateful) and a 1.1x-2x increase in request size. Compared to Patel et al., stateful OnionPIR's amortized response size is 27x to 3,900x smaller (256 KB fixed versus up to 1,009,832 KB at N=2^24, because Patel et al.'s offline phase downloads the entire database). Patel et al.'s own computation is smaller than stateful OnionPIR's (its offline phase requires no public-key computation, and the paper states it chose a larger subset size k for Patel et al. specifically to reduce that scheme's online computation), but stateful OnionPIR's monetary cost is 10x to 107x lower than Patel et al.'s across the tested sizes because of the response-size difference.

Comparison to other single-server PIR systems, cited from those systems' own reported figures, not independently re-measured on this paper's hardware except where stated: XPIR (Aguilar-Melchor et al.) takes about 383 seconds of server computation to retrieve a 30 KB entry from a 1-million-entry database (slightly less than OnionPIR's own measured cost for a comparable configuration) but has a 17 MB request size and about 100x response overhead. SealPIR reduces request size to 32 KB via query compression but keeps about 100x response overhead, matching XPIR on that metric. Two concurrent 2021 systems are compared: Park and Tibouchi's construction achieves 16x response overhead but more than doubles computation cost relative to SealPIR; Ali et al.'s scheme, measured by this paper's authors for a 60 KB entry from a 1-million-entry database (a size chosen because Ali et al.'s scheme performs best at multiples of 20 KB and OnionPIR at multiples of 30 KB, so 60 KB is used as the common comparison point), takes about 900 seconds of computation, 357 KB response size, and 119 KB request size, versus OnionPIR's own measured 800 seconds, 256 KB response size, and 64 KB request size for the same 60 KB-entry, 1-million-entry configuration.

### Parameters
- Polynomial degree n = 4096 (SEAL BFV scheme parameter).
- Ciphertext coefficient modulus q = 124 bits.
- Plaintext modulus t = 60 bits.
- Resulting ciphertext expansion factor F = 4.2x.
- Computational security level: approximately 111 bits, per the Albrecht et al. LWE estimator.
- Database entry size: fixed at 30 KB throughout the main evaluation (60 KB used only in the direct comparison against Ali et al.'s scheme, which performs best at multiples of 20 KB).
- Database sizes N tested: 2^16, 2^18, 2^20, 2^24 entries.
- Stateful-PIR partition count c = 500 (both stateful OnionPIR and the Patel et al. baseline, at every tested N).
- Stateful-PIR subset size k for stateful OnionPIR: 8, 16, 16, 64 at N = 2^16, 2^18, 2^20, 2^24 respectively (paper states this was chosen for a good computation/request-size trade-off, not derived from a closed-form rule).
- Stateful-PIR subset size k for Patel et al. baseline: sqrt(N)/2 at every N, per that scheme's own original paper's recommendation.
- Hypercube dimensionality d = 2 in all existing protocols the paper discusses, including this one (paper states this is what "all existing protocols" use, not a value this paper varies).

### Stated limitations
Batched PIR (serving multiple queries from a single client more efficiently in one round) was not implemented; the paper states OnionPIR can be extended to support batched queries and that batched querying is used inside the stateful PBSR construction, but its offline-phase computation cost in the reported tables is simulated, not measured on the actual system. The paper explicitly separates this from all other reported figures, which are measured. Batched PIR generally is stated to be inapplicable in many real scenarios because a client often has only one query to make at a time. Stateful OnionPIR only applies to a static database; the paper states supporting updates to the database under the stateful framework is an open direction, not solved here. Removing the public-key operations from stateful PIR's online phase entirely, without requiring the offline phase to be rerun after every query, is stated as a promising future direction, not achieved by this construction — the cited alternative construction (Corrigan-Gibbs and Kogan) that has a very cheap online phase requires rerunning its offline phase after every single online query, which the paper states makes its overall cost worse than stateless PIR despite the cheap online step. Symmetric-key doubly-efficient PIR with preprocessing (Canetti et al., Boyle et al.) only supports a single client per preprocessed database copy, which the paper states does not match the public-database model of PIR (many clients querying one shared database) without the server storing a separate preprocessed copy per client; the public-key variant of doubly-efficient PIR requires obfuscation, which the paper states makes it impractical currently. Oblivious RAM (ORAM), a related primitive providing access-pattern privacy, is stated as solving a different problem because conventional ORAM constructions serve only a single client against a private database, and prior extensions of ORAM to multiple clients require inter-client communication, a trusted proxy, or per-client-scaling computation.

### Requirements it places on the rest of the system
Requires the server to hold the full plaintext database and perform O(N) homomorphic operations (a dot product across all N entries, or the hypercube-decomposed equivalent) per stateless query, so server-side compute cost scales linearly with database size regardless of which entry is requested; a caller needing sub-linear per-query server computation must use the stateful variant or an orthogonal preprocessing scheme, which this paper states requires either a static database (stateful OnionPIR) or an unsolved efficient-online-phase problem (Corrigan-Gibbs/Kogan-style constructions). Requires the client and server to agree in advance on the homomorphic-encryption parameters (polynomial degree n, moduli q and t) sized to the deployment's target database entry size, since the paper's own comparison shows entry-size mismatches change which scheme is more efficient (OnionPIR is tuned for 30 KB-multiple entries, Ali et al.'s scheme for 20 KB-multiples). Requires the client to generate and hold local state (c subset sums of size k) for the stateful variant, refreshed via a periodic offline phase that itself costs response bandwidth (128 KB per offline round in the measured configuration) and compute; a caller using the stateful mode must schedule and pay for this refresh independently of individual queries. Provides single-query, single-server privacy only against a database held by one honest-but-curious server; the paper does not analyze or claim resistance to a malicious server that deviates from the protocol, and multi-server PIR variants (requiring non-colluding servers) are treated as a separate, not-implemented, family in this paper's own related-work discussion.

None found within this corpus. No other retrieved paper in this batch measures single-server PIR response size or computation under comparable conditions.

- **Foundational**: Eyal Kushilevitz's original blueprint is separately foundational to the multi-server line via Benny Chor, Oded Goldreich, Eyal Kushilevitz, Madhu Sudan's information-theoretic multi-server PIR — the first multi-server construction, O(sqrt(N)) request size with two servers.
