## [BONEH-ASIACRYPT-16] Balloon Hashing: A Memory-Hard Function Providing Provable Protection Against Sequential Attacks
**Citation:** Dan Boneh, Henry Corrigan-Gibbs, Stuart Schechter. "Balloon Hashing: A Memory-Hard Function Providing Provable Protection Against Sequential Attacks." ASIACRYPT, 2016 (revised May 12, 2017). DOI 10.1007/978-3-662-53887-6_8.
**Retrieved:** full text via https://eprint.iacr.org/2016/027.pdf
**Source URL:** https://eprint.iacr.org/2016/027.pdf
**Domain:** I

### What it does
A memory-hard function forces any evaluator to use a large amount of working memory, so that an attacker checking many candidate passwords against a stolen password-hash file cannot substitute cheap computation for expensive memory and thereby parallelize the attack cheaply on custom hardware. Balloon Hashing achieves this with a data-independent memory-access pattern (the sequence of memory addresses touched during evaluation does not depend on the password), which prevents an attacker who can observe a victim's memory-access trace (for example, through a cache-timing side channel) from learning anything about the password. The algorithm takes a password, a salt, a space-cost parameter `s_cost` (buffer size in blocks), and a time-cost parameter `t_cost` (number of mixing rounds `r`), and runs in three steps: (1) Expand — fill an `s_cost`-block buffer with pseudo-random bytes by repeated hashing of the password and salt; (2) Mix — perform `r` rounds over the buffer, where each round updates every block to the hash of the previous block, the block's current contents, and `δ` (delta) other blocks chosen by a pseudorandom function of the salt and position (not of the password); (3) Extract — output the last block of the buffer. The construction uses only a standard (non-memory-hard) cryptographic hash function `H` as its compression-function subroutine, modeled as a random oracle for the security proof, so any hash function whose output size matches or exceeds its internal state size can be substituted.

The paper's security proof works by mapping the algorithm's computation to a data-dependency graph — a directed acyclic graph with one vertex per random-oracle query, edges representing which prior outputs a later query depends on — and applying a graph-pebbling argument: an adversary "graph-respecting" if it queries the random oracle for a value only once all of that query's input values are already computed and held in memory. The proof shows the Balloon data-dependency graph, built by stacking random "sandwich graphs," satisfies well-spreadedness and expansion properties with high probability over the choice of random oracle, and that these properties force any graph-respecting adversary using space `S` and time `T` to satisfy `S · T ≥ n²/32` for an `n`-block computation. A technique from Dwork, Naor, and Wee then extends this bound from graph-respecting adversaries to arbitrary adversaries in the random-oracle model.

### Measured results
All experimental figures from an Intel Core i7-6700 (Skylake) at 3.40 GHz with 8 GiB RAM, code compiled with gcc 4.8.5 at `-O3`, using the OpenSSL 1.0.1f implementation of SHA-512 and reference implementations of Blake2b, ECHO, and SHA-3/Keccak, all algorithms compared using Blake2b as the underlying compression function for consistency, each measurement averaged over 32 trials.

- Minimum buffer size for a given hashing throughput (Figure 5, two security-parameter settings): at a target authentication rate of 100 hashes/second on a four-core machine (25 hashes/second/core, one core doing the measured single-core work), one-round Balloon hashing (`r=1`, "Normal Security," `δ=3`) needs a 2 MiB buffer, and eight-round Balloon hashing (`r=8`, "Strong Security") needs a 256 KiB buffer, both instantiated with Blake2b. Under the same 100-hashes/second target, single-pass Argon2i (v1.2.1, also instantiated with Blake2b) permits an attacker to use only roughly 1.5 MiB — smaller than Balloon's 2 MiB buffer at the comparable round setting — which the authors state as evidence Balloon simultaneously gives better performance and a stronger memory-hardness guarantee than Argon2i at matched parameters.
- Argon2i attack, space reduction with no measured computation-time increase: the paper's pre-computation-based attack computes `n`-block single-pass Argon2i using `n/4` blocks of storage (expected value; the paper's own empirical Figure 4 shows the attack achieving `n/5` blocks in practice, tighter than the idealized `n/4` analysis predicts) against the Argon2i design document's claimed 7.3× computational penalty at `n/4` space (Biryukov, Dinu, Khovratovich, Argon2 design document Table 2) — the paper's attack incurs no computational penalty at that same space budget. For multi-pass Argon2i (default: 3 passes) the attack's expected space usage tends to `n/e ≈ n/2.7` blocks as pass count grows, against the design document's claimed 16,384× penalty at `n/3` space (Argon2i design document, Section 5.4) for the same space class — again with no computational penalty measured by this attack.
- Compression-function throughput comparison (Figure 6, buffer sizes 16 KiB to 4 MiB): Blake2b and ECHO (the latter exploiting AES-NI instructions) outperform SHA-3 and SHA-512 by "a bit less than a factor of two" in bytes written per second when used as the Balloon compression function, on the same test machine; the paper's plotted curves also mark the machine's L1, L2, and L3 cache boundaries as visible throughput inflection points, though no numeric cache sizes are stated in the text extracted.
- Pre-computation table cost for the Argon2i attack: at most `8·p·n` bytes on a 64-bit machine for `p`-pass, `n`-block Argon2i (one 8-byte timestamp per generated block); for the single-pass case the paper computes the combined table-plus-buffer cost as `8n + 1024(n/4) = 8n + 256n` bytes against the `1024n` bytes Argon2i's straightforward implementation requires — stated as still a substantial reduction.

### Parameters
- `δ` (delta), dependencies per block per mixing round: the main theorem is stated for `δ=3` (giving bound `S·T ≥ r·n²/32`) and for `δ=7` combined with `S < n/64` (giving the stronger bound `S·T ≥ (2r−1)·n²/32`). The reference pseudocode (Figure 1) sets `delta = 3` as its example value; the paper states the real construction uses `δ ≥ 3`.
- `s_cost` (space cost / buffer size in blocks) and `t_cost` (time cost / number of mixing rounds `r`): both user-specified with no fixed recommended values; block size is set equal to the output size of the underlying compression function `H`.
- Hash function `H`: instantiated in experiments with Blake2b, SHA-3/Keccak (rate 1344, operating on 1344-bit blocks), SHA-512, and ECHO (512-bit blocks for the latter three); the construction is stated to be agnostic to this choice provided `H`'s internal state size is at least as large as its output size.
- `M`-core parallel variant: defined as the XOR of `M` independent single-core Balloon evaluations on the same password with `M` different salt suffixes; computing it is argued to require computing `M` full single-core instances, with no numeric `M` fixed.
- Comparison baselines' parameters, as configured for Figure 5: bcrypt at cost factor 12; PBKDF2-SHA512 at 10^5 iterations.

### Stated limitations
The proof's `S·T ≥ n²/32` (or the `δ=7` variant's tighter bound) is a single-instance, sequential-adversary guarantee: it lower-bounds the space-time product of computing the Balloon function once, and treats an adversary limited to one random-oracle query per time step; the authors state a password-guessing attacker in practice makes billions of evaluations and may have thousands of cores in parallel, which the underlying definition does not model. Alwen and Blocki's result, cited by this paper, shows no perfectly memory-hard function with a password-independent access pattern exists under the amortized, parallel adversary model (the parallel random-oracle model, pROM); their special-case attack computes Balloon in the pROM using an amortized time-space product of roughly `O(n^(7/4))`, weaker than the sequential `Ω(n²)` guarantee. The composed construction the authors recommend (Balloon composed with scrypt) defends against memory-access-pattern leakage and against the parallel pROM attack separately but not simultaneously — an attacker with both capabilities at once defeats the composition, which the authors state explicitly. The Argon2i time-space lower bound the paper proves in Appendix F (`S·T ≥ n²/1536` for single-pass, `n`-block Argon2i) is stated by the authors to be weaker than the Balloon bound and to leave open the possibility of an attack saving a further factor of 1536 in space with no increase in computation time. The paper's Argon2i attack analysis is restricted to the single-threaded instantiation; the authors state they "have not tried to extend it to the many-threaded variant." The attack targets Argon2i v1.2.1, the version that won the Password Hashing Competition; the authors state they notified the Argon2i designers and that a later specification version incorporates a design change intended to prevent the attack.

### Requirements it places on the rest of the system
The security proof requires the compression function `H` to behave as a random oracle; a real deployment substitutes a concrete hash function and inherits whatever gap exists between that function and true random-oracle behavior. The proof further requires `H`'s internal state size to be at least as large as its output size — the paper states this specifically to avoid an unspecified pitfall detailed in its Appendix B.3, meaning a compression function violating this size relationship voids the stated memory-hardness guarantee. The parallel-attack-resistant composed construction (Balloon then scrypt) requires running the password through the data-independent algorithm first and the data-dependent algorithm second — the ordering is stated explicitly and is not argued to be secure in the reverse order. Any system relying on this paper's provable memory-hardness guarantee against parallelized attackers must treat the sequential-model guarantee as inapplicable to a many-core attacker and instead rely on the weaker, separately-cited pROM results (amortized `Ω(n²/log n)` at best, per Alwen, Blocki, and Pietrzak, not proven achieved by Balloon itself) if resistance to parallel attack is a requirement.

### Contradicts
The paper's own experimental result contradicts a claim in the cited Argon2i (v1.2.1) design document: that document states computing `n`-block single-pass Argon2i in `n/4` space incurs a 7.3× computational penalty, and that computing three-pass Argon2i in `n/3` space incurs a 16,384× penalty; this paper's measured attack computes both in the stated space budgets with no computational penalty. No other paper in this corpus was found to report Argon2i or Balloon Hashing figures.
