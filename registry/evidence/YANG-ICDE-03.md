## [YANG-ICDE-03] Designing a Super-Peer Network
**Citation:** Beverly Yang, Hector Garcia-Molina. "Designing a Super-Peer Network." IEEE ICDE, 2003. DOI 10.1109/ICDE.2003.1260781.
**Retrieved:** full text via http://infolab.stanford.edu/~byang/pubs/superpeer.pdf
**Source URL:** http://infolab.stanford.edu/~byang/pubs/superpeer.pdf
**Domain:** B

### What it does
A super-peer network reduces the cost of query broadcast in a peer-to-peer file-sharing system by having a small subset of nodes (super-peers) answer queries on behalf of a larger set of weaker nodes (clients) that connect to exactly one super-peer each, so that only super-peers route messages to each other while clients are shielded from all query traffic. A super-peer and its clients form a cluster; cluster size is the node count in a cluster including the super-peer. A pure peer-to-peer network (every node routes for itself, as in Gnutella's baseline design) is the degenerate case where cluster size is 1. Every other node in the pure network model has an outdegree (a count of open neighbor connections it maintains) and messages travel hop by hop only along these open connections; a query carries a time-to-live (TTL) that is decremented at each hop and stops the query once it reaches 0, and the reach of a query is the number of nodes that end up processing it.

In a super-peer network, a client sends a query only to its own super-peer; the super-peer answers on the client's behalf by consulting an index it keeps over its clients' data (built by having clients send file metadata to their super-peer at join, update, and leave time), then forwards the query to its neighboring super-peers exactly as if it were the super-peer's own query, and relays back any results. This converts client-to-super-peer traffic into a client-server pattern while leaving super-peer-to-super-peer traffic as an unstructured overlay routed as in a pure peer-to-peer system (the paper studies the baseline Gnutella flooding rule specifically: forward to every neighbor until TTL reaches 0).

k-redundancy adds k nodes ("partners") that jointly serve as one virtual super-peer: every partner holds a complete index of the cluster's clients and of the other partners, clients send queries to partners in round-robin rotation, and incoming queries from neighboring super-peers are distributed evenly across partners. This lowers each partner's per-query load by roughly a factor of k relative to a single non-redundant super-peer with the same clients, at the cost of the aggregate cost of every client-join action increasing by a factor of k (because a joining client must send its metadata to every partner) and the number of open super-peer-to-super-peer connections increasing by a factor of k^2 (because every neighbor super-peer must connect to every partner). The paper restricts its analysis to k=2 because connection count grows too fast beyond that.

### Measured results
The paper's numbers come from an analytical cost model (an event-driven mean-value simulation over generated network topologies), not a live deployment; the per-action bandwidth and processing-cycle costs feeding that model were measured (bandwidth costs specified by the Gnutella wire protocol; processing costs measured on a Pentium III 930 MHz processor running Linux kernel 2.2, with one "unit" defined as the roughly 7,200-cycle cost of sending and receiving a Gnutella message with no payload), while file-count, lifespan, and query/match-probability distributions were taken from independent Gnutella measurement studies (Saroiu, Gummadi, Gribble, 2002; Yang and Garcia-Molina, 2001, for OpenNap query/match probabilities). All headline results below are expected-value outputs of this cost model over generated topologies, with 95% confidence intervals shown in the paper's figures where applicable.

### Parameters
- Graph Type: strongly connected or power-law; default power-law, generated via the PLOD algorithm to match measured Gnutella topology.
- Graph Size: default 10,000 peers (used 20,000 in the global-design-procedure worked example, matching a reported Gnutella network size at the time of writing).
- Cluster Size: default 10; swept across the full range in experiments (1 to Graph Size).
- Redundancy: boolean, default off; only k=2 evaluated, because open-connection count among super-peers grows as k^2.
- Average Outdegree: default 3.1 (measured from a June 2001 Gnutella network crawl); swept up to 100+ in experiments; actual per-node outdegree follows a power-law distribution around this average, reflecting observed voluntary variation in peer capability.
- TTL: default 7; swept from 1 upward.
- Query Rate: default 96.26 x 10^-3 queries per user per second (paper's own general statistic, source cited to a prior Gnutella measurement study).
- Update Rate: default 1.68 x 10^-2 updates per user per second (same source).
- Atomic action costs (bandwidth and processing) drawn from the Gnutella wire-protocol specification and from processing-time measurements on a single Pentium III 930 MHz / Linux 2.2 machine; the paper states these processing-cost values are "meant to be representative, rather than exact" because they will vary across machines and implementations.
- Open-connection overhead model: derived from a cited measurement of select()-call scan cost (about 3 microseconds per file descriptor on a Pentium 100 under Linux 2.1.x) and a cited finding that per-call select() overhead grows linearly with open-connection count up to roughly 1,000 connections, after which it levels off; the paper states none of its own reported results exceed 1,000 open connections, so only the linear-growth regime applies to its figures.

### Stated limitations
The paper states its performance model does not capture absolute response time, only relative response time inferred through Expected Path Length (mean hop count of a response's return path), and explicitly excludes "relevance of results" as a quality metric because it is "subjective and application specific." The bootstrapping problem — how a joining node discovers already-connected nodes, which determines the actual distribution of cluster sizes in practice — is stated to be "an open problem in pure and super-peer networks, with many potential solutions," and the paper sidesteps it by assuming any well-constructed discovery method is fair or random, using a normal distribution for cluster-size variation rather than deriving one from a specific discovery mechanism. The global design procedure is stated explicitly not to be provably optimal: "we can not prove the procedure yields the 'best' topology," only that empirical evidence shows it usually returns a topology that cannot be improved without violating the designer's stated constraints. Rule #3 (maximize outdegree) is stated to have a caveat in extreme cases: once increasing average outdegree stops reducing Expected Path Length for a given target reach, further increases only add redundant-query overhead and harm performance, so outdegree should be increased only as long as it continues to shorten EPL. The local-decision-making guidelines (Section 5.3) are stated to rely on a "limited altruism" assumption — that every super-peer is willing to accept load up to a self-set limit purely to reduce load for the rest of the network — and the paper notes this assumption does not address the possibility of freeloading or malicious non-participation, citing separate ongoing research on detecting and punishing such nodes as outside its own scope. The choice of cluster size involves a stated unresolved tension the paper does not fully resolve numerically: individual load favors small clusters, aggregate load and the "knee" effect favor large ones, and reliability (fewer single points of failure) favors small ones, with the paper stating only that "the answer to this question is specific to the application and situation."

### Requirements it places on the rest of the system
The mechanism requires every client to maintain metadata synchronization with exactly one super-peer: on join, a client must transmit metadata for every file it holds; on any update (insertion, deletion, or modification of a shared item), it must resend the corresponding delta; and on leave, its super-peer must remove its metadata — without this discipline the super-peer's index (which is the sole basis on which it answers queries for that client) becomes stale relative to the client's actual holdings. The design assumes clients are reachable through exactly one super-peer at a time (no client multi-homing in the base design), so a super-peer's failure disconnects every one of its clients until they locate a replacement, which is the specific failure the k-redundancy extension is built to reduce, not eliminate. Any routing protocol run at the super-peer-to-super-peer layer is treated as an orthogonal, pluggable choice — the paper states explicitly that "the use of super-peers and the choice of routing protocol are orthogonal issues" and only evaluates the plain Gnutella flooding rule, so its cost figures do not carry over automatically to a structured-overlay routing layer (e.g., a distributed hash table) run among super-peers instead. The k-redundancy mechanism requires every neighboring super-peer to open and maintain a connection to every one of the k partners (not just one representative), which is the source of its stated k^2 connection-count growth, and requires clients to be able to address multiple partners in round-robin fashion rather than a single fixed super-peer address. The global design procedure requires the designer to know or estimate several system-wide properties in advance — total network size, desired reach (equivalently, desired result count per query), and per-node limits on bandwidth, processing power, and open-connection count — and the paper notes obtaining these accurately before the system runs can be difficult, offering periodic re-evaluation by a centralized decision-maker as the fallback rather than a way to avoid the requirement.

### Contradicts
None found against another entry in this batch. Section 5.1's finding that raising average outdegree from 3.1 to 10 lowers both individual and aggregate load is stated by the paper itself to hold only if adopted uniformly across all super-peers; the same change made by a single super-peer acting alone is stated to increase that node's own load by 303% — an internal qualification the paper states directly, not a contradiction between two different results.

- Yang and Garcia-Molina, "Comparing Hybrid Peer-to-Peer Systems," VLDB, 2001 — foundational/competing (source of the OpenNap query/match-probability model reused as the default query distribution, and the paper's own prior work comparing hybrid P2P systems).
