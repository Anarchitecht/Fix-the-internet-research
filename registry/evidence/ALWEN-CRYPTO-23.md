## [ALWEN-CRYPTO-23] Fork-Resilient Continuous Group Key Agreement
**Citation:** Joël Alwen, Marta Mularczyk, Yiannis Tselekounis. "Fork-Resilient Continuous Group Key Agreement." CRYPTO, 2023. DOI 10.1007/978-3-031-38551-3_13.
**Retrieved:** full text via https://eprint.iacr.org/2023/394.pdf
**Source URL:** https://eprint.iacr.org/2023/394.pdf
**Domain:** H

### What it does
This paper generalizes continuous group key agreement (CGKA — the primitive letting an evolving group of clients agree on a sequence of shared group keys, the basis of scalable end-to-end-encrypted group messaging) to a new primitive, Fork-Resilient CGKA (FR-CGKA), that lets clients process protocol messages ("packets") arriving in any order consistent with causality, not only the single fixed order every prior CGKA protocol required. A fork occurs when group members end up with diverging views of the group's event history, typically because a network or server outage let different subsets of members exchange packets independently for a period; once connectivity is restored, members must reconcile ("resolve") their divergent views into one agreed group state. The paper's stated goal is to remove the specific cryptographic obstacle that stops today's CGKA protocols — including the CGKA underlying the IETF's Messaging Layer Security (MLS) draft standard — from supporting the "natural fork resolution" pattern already used by systems like Matrix: gather the packets each side is missing, then run a deterministic state-resolution algorithm over the combined causal history. Every prior CGKA protocol deletes cryptographic secrets as soon as they are used to transition to a new epoch (a numbered version of the group's state), specifically to guarantee forward secrecy (FS — that a later state compromise cannot expose earlier communications); this deletion also makes it cryptographically impossible to reprocess a delayed packet describing an alternate, un-taken transition out of an already-abandoned epoch, which is exactly what fork resolution by replaying missed packets requires.

Formal model: the paper replaces "the client's current epoch" (the concept every prior CGKA authenticity/forward-secrecy definition is built around) with "the client's current view of the group's history," represented as a history graph — a directed tree of epochs where an edge from epoch E0 to E1 represents one group-modifying event (add, remove, or key update) turning E0 into E1. A client's local state is described via a "pebbled history graph": three kinds of markers (move, visited, key pebbles) placed on epoch nodes track, respectively, whether the client can still send/receive packets referencing that epoch, whether a packet transitioning out of that epoch has already been irreversibly processed (which forward secrecy requires), and whether the client still holds that epoch's symmetric group key. This pebbling abstraction is presented as a minimal, protocol-independent interface that a higher-level fork-resolution procedure can query to determine which missing packets a client can still process, without needing to know the underlying cryptographic state.

Two constructions are given. FREEK is a practical FR-CGKA protocol built on SAIK (a prior server-aided CGKA the paper cites as [AHKM22a], itself built on MLS/TreeKEM). Its core mechanism replaces standard forward-secrecy-by-deletion with a puncturable pseudorandom function (PPRF — a PRF whose key can be "punctured" on a chosen input, after which the key still evaluates the PRF everywhere except that input, and reveals nothing about the punctured output): the "init secret" a client retains for a parent epoch is now the key to a PPRF, and instead of deleting that secret entirely after deriving a child epoch's key (which would forbid processing any other, un-taken child epoch later), the client punctures the PPRF key only on the specific challenge tied to the epoch it actually transitioned into, preserving the ability to derive keys for other, still-unprocessed child epochs while still achieving forward secrecy for the one it already committed to. The challenge value that gets punctured is constructed from a cryptographic commitment to the new epoch's public state combined with half of the freshly generated "commit secret" (the paper states a naive alternative — punncturing on the commit secret directly, or on a random attacker-suppliable value — either leaks old secrets through the punctured key or opens a denial-of-service attack in which a malicious member front-runs an honest packet's challenge value to block a target from ever processing the honest packet). O-FREEK is a second, optimally secure FR-CGKA construction achieving the strongest security predicate the paper defines (every epoch is secure unless keeping it secure would be logically inconsistent with protocol correctness), built by extending a technique from prior work (cited as [ACJM20]) that uses hierarchical identity-based encryption (HIBE, a public-key encryption scheme whose secret keys form a tree-shaped hierarchy, where a key at one node can derive keys for all its descendants but reveals nothing about ciphertexts encrypted to non-descendant identities) restricted to a binary identity space (binary-tree encryption, BtPke), combined with an analogous hierarchical identity-based signature scheme (binary-tree signatures) for authenticity, and a puncturing mechanism built on top of BtPke to prevent two attack classes specific to the FR-CGKA setting: cross-fork attacks (in which a single retained secret key remains valid across multiple forked epochs simultaneously, so corrupting one member after it "moves on" from one fork branch still exposes secrets in a sibling branch it never officially left) and collusion attacks (in which an unpunctured shared secret, combined with a second corrupted member's independently retained key, jointly reconstructs a group key that neither compromise alone should expose).

### Measured results
This is a theory paper: its contributions are formal security definitions, two protocol constructions, and machine-checkable-style security proofs (game-based reductions), not empirical benchmarks. No experimental measurements — no node counts, wall-clock timings, message-size measurements from a running implementation, or comparable numeric performance figures with stated conditions — appear in the paper; the authors state FREEK is intended as "practical" and O-FREEK as having "only theoretical efficiency" (their own characterization, not a benchmarked figure), and no implementation or deployment is described.
- Structural complexity claim (context, not a new measurement of this paper): CGKA protocols in general reduce the O(n) communication and computation cost of pre-CGKA group-messaging protocols for operations like member removal or a forward-secrecy-refreshing update to O(log n), under mild assumptions about client online/offline behavior — a property informally called "fair-weather complexity." The paper attributes this comparison figure to prior work on pre-CGKA protocols (cited as [Fou23a, MP22, Wha23, HLA19]), not to a measurement of its own.
- Comparison to Matrix, DCGKA [WKHB21], and [CEST22] (stated as an existing-system property drawn from those works, not remeasured here): each already supports the natural-fork-resolution pattern this paper targets for CGKA, but none achieves CGKA's fair-weather logarithmic complexity — removing a group member requires O(n) download bandwidth per client in each of them, as does a single post-compromise-security (PCS) update.
- Comparison to distributed MLS (dMLS, an experimental Matrix-team modification of MLS cited as [Mat23b]): dMLS achieves the ability to process packets in any causality-respecting order (the same headline property FR-CGKA targets), but the paper states it does so "at the cost of seriously weakening forward secrecy," concretely because dMLS stores old secrets rather than deleting them — corrupting a client while it still holds a "move pebble" on an old epoch can reveal the epoch keys, and therefore the message contents, of every descendant epoch of that node, even ones the client has already logically "moved past." FREEK is designed specifically to avoid this: the paper states FREEK keeps those descendant-epoch keys secure.
- FREEK vs. its base protocol SAIK: the paper proves that when FREEK is restricted to operate as an ordinary CGKA (each member keeps only a single "current" move pebble, immediately discarding the old one on every transition, matching how SAIK behaves), FREEK achieves the identical CGKA security level as SAIK — the two become "almost equivalent" because FREEK's puncturing operations become vacuous once old pebbles are always deleted immediately.
- O-FREEK's security predicate is explicitly the optimal one (P = false in the paper's general predicate framework): every epoch is secure except where insecurity is logically forced by protocol correctness.

### Parameters
- The paper does not fix concrete numeric parameters (group sizes, key lengths, PPRF/HIBE security-parameter bit widths) anywhere in the main body; all constructions are described and analyzed asymptotically or via formal security-game reductions, with cryptographic primitives (PPRF, HIBE/BtPke, HIBS/BtSig, mmPKE — multi-message multi-recipient public-key encryption) treated as black boxes satisfying stated security properties (one-wayness with adaptive corruptions for the PPRF; RCCA, a relaxation of chosen-ciphertext security, plus one-wayness for mmPKE; unforgeability for the signature scheme).
- O-FREEK's BtPke puncturing structure: a client's secret key for parent epoch U, once it needs to be punctured on a descendant epoch V, is represented as a binary tree of height |V| (the number of epochs, i.e., the fork-branch depth, since the key was inserted into the client's state) — the paper does not give this as a numeric benchmark, but this height-scales-with-history-depth structure is the concrete mechanical basis for the paper's own characterization of O-FREEK as having "only theoretical efficiency," recorded here as a structural fact traceable to the construction rather than as the authors' bare assertion.

### Stated limitations
The paper states O-FREEK, despite achieving the strongest (optimal) security predicate defined, has only theoretical efficiency, in explicit contrast to FREEK, which is presented as the practical construction — no numeric threshold or benchmark is given for what makes O-FREEK impractical, only the structural fact (noted above) that its punctured keys scale with fork-branch depth.

FREEK's security predicate is explicitly weaker than optimal: the paper states this stems from certain secrets (the init secret and the MAC key) being shared among all group members rather than personalized per member, so an adversary that merely holds a move pebble for any one member on a parent epoch U — not necessarily the specific target member — gains enough shared secret material to help compromise a child epoch V, whereas the optimal predicate would require compromising the specific target member's own state on U.

The paper explicitly does not solve, and states as an open design question, how to choose which epoch a fork-resolving client should base its new current epoch on: the choice affects each member's transition cost, and constructing a long chain of resolution steps can destroy TreeKEM's normally logarithmic communication cost, degrading it to "super-logarithmic"; the authors state there is no one-size-fits-all solution, since different applications may want to minimize average transition cost versus minimizing cost for a subset of resource-constrained clients (e.g., IoT devices).

The example fork-resolution protocol given (Section 6) is explicitly presented as "a proof of concept" demonstrating that the pebbling abstraction and FR-CGKA together can support natural fork resolution, not as a complete or optimized fork-resolution system; the paper states it reuses an existing state-resolution algorithm from Matrix's specification (cited as [Fou23b]) rather than designing a new one.

The paper's related-work discussion states that prior concurrent-CGKA protocols (cited as [AAN+22b, AAN+22a, BDG+22, BMO+18]) support concurrent post-compromise-security updates only within a single epoch: once a client applies one or more concurrently generated updates, it enters a new epoch and can no longer process any other event still pertaining to the old epoch, including delayed packets — the paper characterizes this as "only a very limited type of fork resilience," which the FR-CGKA construction in this paper is designed to go beyond.

### Requirements it places on the rest of the system
- Any fork-resolution procedure built on FR-CGKA needs the underlying transport to guarantee only causality-respecting delivery per sender-receiver pair (packets from the same origin to the same destination arrive in the order sent) — the paper states an otherwise-unreliable network satisfying only this property already suffices to deliver packets in "arbitrary but causality respecting order," which is the exact class of delivery order FR-CGKA is designed to tolerate; a network that reorders even same-origin, same-destination traffic is not covered.
- A client must retain enough of its pebbled-history-graph state (move, visited, and key pebbles per known epoch) to determine which of its missing packets it can still process; deleting move or key pebbles is safe at any time (it only forgets keys the client no longer needs), but a visited pebble, once placed, can never be removed, because its presence records that a cryptographic secret required to reprocess that transition has already been irreversibly used or deleted — a client that discards this bookkeeping loses the ability to correctly determine which delayed packets remain processable.
- FREEK specifically requires the challenge value punctured into the PPRF key to be derived from a commitment to the new epoch's public state plus half the freshly generated commit secret, not from the commit secret alone and not from an unauthenticated value attached to the packet; the paper's own analysis shows that either alternative reopens either a forward-secrecy leak (through what a punctured PPRF key can reveal, notably for common Goldreich-Goldwasser-Micali/GGM-tree-based PPRF constructions) or a denial-of-service vector where a malicious member preempts an honest packet's challenge to block a target from ever accepting it.
- O-FREEK's optimal-security guarantee depends on every group member ratcheting (updating and puncturing) its own hierarchical key material at every epoch transition it processes, including transitions across fork branches; a client design that keeps a single long-lived key across multiple fork branches reopens the cross-fork attack the paper identifies, in which one retained secret key remains valid for decrypting or signing in more than one branch of a fork simultaneously.
- The paper's formal model treats an untrusted server or mailboxing service purely as an availability mechanism — the agreement, confidentiality, and authenticity guarantees of FR-CGKA do not rely on that server behaving correctly, honestly, or consistently, but a client still needs some delivery mechanism (server-relayed, peer-to-peer gossip, or otherwise) that eventually gets it the packets it is missing, since FR-CGKA's own guarantees say nothing about whether or when a given packet arrives.
- The paper's Section 1 explicitly frames FR-CGKA as the CGKA-level piece needed before a decentralized or federated messaging system (its own example: a group split across two host servers whose inter-server link goes down) can support scalable fork resolution — but the paper does not itself construct or evaluate a complete fork-resolution protocol beyond the Section 6 proof of concept, so a system adopting FR-CGKA still needs to supply its own state-resolution algorithm (the paper points to the Matrix specification's algorithm, [Fou23b], as one usable building block) and its own policy for which epoch to resolve onto (left as the unresolved design question noted above).
