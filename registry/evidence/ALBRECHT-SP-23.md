## [ALBRECHT-SP-23] Practically-exploitable Cryptographic Vulnerabilities in Matrix
**Citation:** Martin R. Albrecht, Sofía Celi, Benjamin Dowling, Daniel Jones. "Practically-exploitable Cryptographic Vulnerabilities in Matrix." IEEE Symposium on Security and Privacy (S&P), 2023. DOI 10.1109/SP46215.2023.10351027.
**Retrieved:** full text via https://eprint.iacr.org/2023/485.pdf
**Source URL:** https://eprint.iacr.org/2023/485.pdf
**Domain:** H

### What it does
This paper is a security analysis, not a mechanism proposal: it reports six practically-exploitable cryptographic vulnerabilities in Matrix, an open federated real-time-communication standard, and its flagship client Element (built on matrix-js-sdk and matrix-react-sdk). Matrix lets clients on different homeservers (accounts hosted by different, mutually untrusted federated servers) exchange end-to-end-encrypted messages; the analysis targets that end-to-end encryption layer against a malicious homeserver, in the setting where every device and user has completed out-of-band verification (the strongest protection the protocol offers) — the paper states this is the hardest, most interesting setting for an attacker, and that when verification has not been completed for even one device, impersonation becomes trivial regardless of the vulnerabilities reported here. All six attacks require the cooperation of a homeserver; the paper assumes a single homeserver throughout for simplicity.

Matrix's cryptographic core: pairwise device-to-device channels use Olm, an implementation of the Signal X3DH key-exchange protocol combined with the Signal Double Ratchet algorithm. Group/room messages use Megolm, a custom unidirectional ratchet built on top of Olm: a device creating a Megolm session distributes its session key to every other device over individual pairwise Olm channels, then symmetrically ratchets forward and signs each subsequent Megolm ciphertext with an Ed25519 key tied to that session. Devices that missed the initial key distribution (e.g., a newly added device) can request the session via the Key Request protocol, receiving it as a "forwarded" Megolm session over Olm; the Element user interface marks messages decrypted from forwarded sessions with a lower-trust warning than messages from sessions received directly.

The six vulnerabilities, each with the class of design flaw the paper attributes to it:
1. Trivial confidentiality break via homeserver control of room membership and device lists (design flaw): room-management messages that add users to a room, and a user's device list, are neither encrypted nor cryptographically authenticated even in end-to-end-encrypted rooms; a malicious homeserver can forge a room-join message or insert its own device into a target user's device list, causing legitimate devices to share future Megolm session keys directly with the attacker-controlled device or user.
2. Attack against out-of-band (SAS, short authentication string) verification (lack of domain separation): the verification protocol does not separate device identifiers from users' cross-signing master public keys in the same field; the paper implements an attack that gets a victim to cryptographically sign an attacker-controlled cross-signing identity, believing it belongs to their conversation partner, enabling a mallory-in-the-middle position over the victim's Olm (and therefore Megolm) channels.
3. Semi-trusted impersonation against Megolm authentication (implementation bug plus lack of specification guidance): matrix-js-sdk accepts m.forwarded_room_key messages from any device as long as the message is Olm-encrypted, regardless of whether the receiving device requested them and regardless of the sender's actual relationship to the claimed session, letting an attacker push an attacker-controlled Megolm session to a target device; the resulting messages carry the same UI trust warning as legitimately forwarded keys, so the attack reaches parity with, not below, the trust level of the honest Key Request protocol.
4. Trusted impersonation against Megolm (protocol confusion): building on vulnerability 3, an attacker creates a new inner Megolm session sent over the outer forged Megolm channel; the inner session inherits the forged sender identity but not its "forwarded" (lower-trust) status, so the resulting message displays with no warning at all, exceeding the trust level achievable through the legitimate Key Request protocol.
5. Impersonation escalated to a confidentiality break against server-side Megolm backups (implementation bug): by impersonating a trusted device during self-verification (chaining vulnerability 3), the attacker can respond to a victim device's SSSS (Secure Secret Storage and Sharing) request for the server-side Megolm-backup key with an attacker-chosen key; the victim device then encrypts its backup of every inbound Megolm session it holds under that attacker-controlled key, which the colluding homeserver can then decrypt, exposing the plaintext of every Megolm message the victim device has access to.
6. IND-CCA (indistinguishability under chosen-ciphertext-attack) break in symmetric Megolm Key Backups and SSSS (specification-level cryptographic issue): Matrix composes AES-CTR encryption with an HMAC-SHA-256 message authentication code (MAC) in an encrypt-then-MAC construction, but the initialization vector (IV) is not covered by the MAC. The paper constructs a standard IND-CCA distinguishing attack: querying an encryption oracle for a known plaintext, splicing its ciphertext body onto the challenge ciphertext's IV, and querying a decryption oracle on the spliced ciphertext (which still passes the MAC check) to recover the AES keystream and decrypt the original challenge.

### Measured results
This is a vulnerability-disclosure paper; its measured facts are which attacks the authors implemented and verified against the real Matrix specification and the Element/matrix-js-sdk codebase (specifically Element Web at commit #479d4bf, matrix-react-sdk at commit #59b9d1e, matrix-js-sdk at commit #4721aa1), not performance benchmarks.
- Vulnerability 1 (room-membership/device-list control): design-level flaw demonstrated by construction from the specification (no cryptographic protection exists by design for the affected message types); no separate proof-of-concept run count reported.
- Vulnerability 2 (out-of-band verification attack): "We implemented this attack and report that it succeeds in practice" against the target commits listed above; the paper further states the attack can plausibly run in parallel against both parties of a verification exchange, but does not report a separate measured trial for the parallel case.
- Vulnerabilities 3-5 (impersonation chain and backup-key confidentiality break): each is a working proof-of-concept implemented against the same commits, chained together as described above; the paper reports the chain succeeds but does not give a trial count, success rate, or timing.
- Vulnerability 6 (IND-CCA break on backups): the attack is constructed formally and the paper states it is exploitable only against symmetric Megolm Key Backups and SSSS in the abstract cryptographic sense; the authors explicitly state that in practice they do not know how to instantiate it against real Matrix, because (a) per-session keys limit the decryption oracle's scope to sessions the attacker already controls, and (b) a modified ciphertext will generally fail to parse as valid JSON before it reaches the decryption step, so it is characterized as theoretical only, not a demonstrated practical break.
- Disclosure timeline: reported to Matrix developers between 20 May 2022 and 6 July 2022; coordinated public disclosure on 28 September 2022, alongside the developers' first countermeasures. At the time of public disclosure, the out-of-band verification attack (vulnerability 2), the semi-trusted impersonation attack (vulnerability 3), the trusted impersonation attack (vulnerability 4), and the impersonation-to-confidentiality attack (vulnerability 5) were fixed; the room-membership/device-list attack (vulnerability 1) was not fixed by disclosure, though a per-room local setting was added to mitigate the device-list variant, and the IND-CCA fix (vulnerability 6) was deferred because the developers judged it not practically exploitable.
- CVEs assigned by the Matrix developers: CVE-2022-39250 (verification attack); CVE-2022-39246, CVE-2022-39249, CVE-2022-39257, and (found in their own ecosystem review of other clients) CVE-2022-39252, CVE-2022-39254, CVE-2022-39264 (semi-trusted impersonation and variants); CVE-2022-39248, CVE-2022-39251, CVE-2022-39255 (trusted impersonation); the impersonation-to-confidentiality break is covered by the same CVEs as the trusted impersonation attack.
- Deployment scale (context, from the paper's introduction, not an experimental measurement): matrix.org reported 28 million global visible accounts as of March 2021.
- Cryptographic parameter noted as a departure from standard guidance: Matrix truncates HMAC-SHA-256 output to 64 bits, versus the HMAC RFC's recommendation of at least 128 bits (no less than half the hash output) and no fewer than 80 bits.

### Parameters
- Analysis target versions: Element Web commit #479d4bf, matrix-react-sdk commit #59b9d1e, matrix-js-sdk commit #4721aa1.
- Cryptographic primitives used by Matrix, as documented and relied on by the attacks: AES-256 (256-bit keys) for AES-CTR and AES-CBC (with PKCS7 padding for CBC block splitting in Olm, Megolm, and the asymmetric Megolm backup scheme); HMAC-SHA-256 truncated to 64 bits for message authentication; HKDF-SHA-256 for key derivation; Ed25519 for Megolm session-authenticity signatures and cross-signing; X25519 for the SAS out-of-band-verification key exchange.
- Threat model parameter: single homeserver assumed throughout (stated as a simplification, not a claimed limit of the attacks' generality).

### Stated limitations
The out-of-band-verification attack (Section IV/V per the paper's own numbering) is explicitly stated not to work when a user verifies two of their own devices — a malicious homeserver cannot use this specific attack to compromise Olm connections between two devices belonging to the same user. The IND-CCA break on backups (vulnerability 6) is stated by the authors to be of only theoretical interest: they state they do not know how to instantiate it in practice against real Matrix, for the two structural reasons given above (oracle scope limited by per-session keys; ciphertext modification breaks JSON parsing before the decryption oracle can be reached). The paper's scope is explicitly restricted: it covers only the Matrix specification and the Element client (not other Matrix clients, some of which do not even use matrix-js-sdk, and which the authors state they did not investigate); it covers only authentication and confidentiality without requiring a client secret compromise, explicitly leaving forward secrecy, post-compromise security, and deniability out of scope, on the stated grounds that a protocol failing at the more fundamental goals makes these advanced properties moot for the purposes of this paper. The paper states that Matrix's specification does not enforce that messages inside "encrypted" rooms are actually encrypted, so unless a client is configured to reject all communication from unverified devices or rooms containing them, no cryptographic authentication guarantee holds regardless of whether the six reported vulnerabilities are fixed.

### Requirements it places on the rest of the system
- A federated group-messaging design in which a server (homeserver) controls room membership and device-list metadata needs that metadata itself to be cryptographically authenticated to end-to-end-encrypted-room participants, or a malicious server can silently insert an eavesdropping device without breaking any per-message cryptography — the paper's vulnerability 1 shows the absence of that authentication is sufficient by itself to break confidentiality.
- A key-forwarding mechanism (here, the Key Request protocol) that lets a device request a missing group-session key from another device needs the receiving side to enforce the same trust checks the sending side enforces; the paper's vulnerability 3 exists specifically because matrix-js-sdk enforces sharing restrictions when a device offers a key but not when a device receives one, so a design that only checks trust on the sending side does not achieve the trust level it appears to provide.
- Verification of message authenticity (checking cryptographic identity/signature bindings) must happen no later than message-decryption time, not at message-display time, when other parts of the system act on decrypted-but-undisplayed state; the paper's vulnerability 4/5 chain is enabled specifically because Element checks authenticity at display time, so protocol messages that silently update client state without ever being displayed bypass authentication entirely.
- Any identifier space shared between two logically distinct key types (here, device identifiers and cross-signing master public keys) needs explicit domain separation — a distinguishing tag or type field checked consistently everywhere the identifier is consumed — or an attacker can substitute one type of key where the other is expected, which is exactly how the out-of-band-verification attack achieves a mallory-in-the-middle position.
- An encrypt-then-MAC construction needs the MAC to cover every input that varies per ciphertext, including the initialization vector, or an adversary with encryption- and decryption-oracle access (achievable here via the legitimate key-forwarding and backup-upload protocol flows) can mix IVs across ciphertexts and break IND-CCA security; whether this is practically exploitable in a given deployment depends on whether an attacker can obtain oracle access broader than one session's worth and whether modified ciphertexts still parse as valid application-level data before reaching the MAC check.
- The system-wide guarantee that "out-of-band-verified means trustworthy" only holds if every participating device and user completes verification; the paper states that a client design must offer, and a deployment must enable, an explicit reject-unverified-devices setting, because otherwise the presence of even one unverified device or user in a room removes cryptographic authentication guarantees for everyone in it, independent of whether the six specific vulnerabilities here are fixed.

### Contradicts
None found. This paper does not claim to contradict any specific figure attributed to Matrix elsewhere in the corpus; it establishes that Matrix's end-to-end encryption, at the versions studied, fell short of both confidentiality and authentication against a malicious homeserver, which the authors state runs counter to Matrix's own advertised claim that end-to-end encryption is enabled by default and protects against untrusted third-party servers.
