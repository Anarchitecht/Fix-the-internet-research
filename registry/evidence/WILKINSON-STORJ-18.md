### What it does
Storj lets a client store an object across many independently operated, mutually distrusting storage nodes with high durability and without simple replication's bandwidth overhead, coordinated by an operator-run "Satellite" that tracks metadata, schedules repairs, and settles payments, rather than by a fully peer-to-peer consensus mechanism. An object is broken into segments (a whole small file may be a single "inline" segment stored directly with its metadata if it is smaller than the metadata itself), each large segment further divided into stripes (sub-segment units on the order of a couple of kilobytes, the granularity at which erasure encoding and audit both operate), and each stripe erasure-coded with a Reed-Solomon (k, n) code: n erasure shares are generated per stripe, any k of which reconstruct it, so each share is 1/k the size of the stripe. Same-indexed erasure shares across all the stripes of a segment are packed together into one "piece," so a storage node holds one piece per segment rather than many small per-stripe shares; a piece is 1/k the size of its segment, and only k of the n pieces are needed to reconstruct the whole segment.

The system extends the standard two Reed-Solomon numbers (k, n) to four: k ≤ m ≤ o ≤ n. k is the minimum pieces needed for reconstruction and n the total pieces generated. m is the repair-trigger threshold: when a segment's live piece count falls to m, the Satellite immediately schedules a rebuild, so m − k is the safety margin against data loss between detecting the need for repair and completing it. o is the piece count considered "optimal": during upload or repair, once o of the up-to-n pieces have finished uploading, the remaining upload attempts (up to n) are canceled, so o − m is the number of nodes that can go simultaneously offline without forcing a repair, and n − o is the number of slow ("long-tail") nodes the system tolerates without waiting on them — the mechanism the paper credits with letting every read or write proceed at the speed of the fastest responding nodes in the selected set rather than the slowest.

A per-Satellite node-discovery cache (in this v3.1 edition, replacing the earlier Kademlia distributed hash table (DHT) used in the 2018 edition) tracks each storage node's current address, available space, and other metadata; a node announces itself to every Satellite on its trustlist, checks in periodically (the paper suggests roughly once per hour), and a Satellite that cannot reach a node stops recommending it to clients. Audits verify that a storage node still holds what it claims: a Satellite requests a randomly chosen stripe's erasure shares from every node responsible for it and runs the Berlekamp-Welch error-correction algorithm across the returned shares, which both detects which specific responses are missing or wrong and lets the Satellite reconstruct the correct data from whichever responses are correct, without needing to have pre-generated the challenge and expected response ahead of time (which the paper states was a weakness of the Merkle-tree-based proof scheme used in Storj's earlier, 2016 design — a storage node could pass most audits without holding all the data simply by memorizing which pre-generated challenges existed and caching only their expected responses). A node that responds to an audit dial but not with the requested data within the expected time is placed into "containment mode" and retried until it succeeds, actively fails, or is disqualified for prolonged unavailability, rather than immediately marked as failing.

Repair operates against the same m threshold: when the node-discovery cache observes a node transitioning from online to offline, a reverse index over the Satellite's metadata identifies every segment that had a piece on that node; any segment whose live-piece count drops to m is downloaded, reconstructed from its surviving pieces, re-encoded to replace the missing pieces, and the replacement pieces are uploaded to newly selected nodes, with the segment's pointer (the metadata record listing which nodes hold which pieces, plus encryption and erasure-coding parameters) updated accordingly. Bandwidth accounting between an Uplink (client-side software) and a storage node uses a scheme the paper derives from Neuman's proxy-based accounting protocol: the Satellite issues a signed "bandwidth allocation" capping the resources an Uplink may use in an operation, the Uplink sends the storage node successively larger restricted sub-allocations (each one covering only the data transferred so far, using the same non-reusable check number so only the largest one can ever be redeemed), and the storage node periodically forwards its largest received allocation to the Satellite for later payment — a design intended to bound the loss either party is exposed to if the exchange is interrupted partway through, rather than depending on both peers' end-of-operation reports being honest.

Payment moves from clients to Satellites in any medium a Satellite accepts, and from Satellites to storage nodes exclusively in the Ethereum-based ERC-20 STORJ token, calculated monthly per node from the Satellite's own stored-piece and bandwidth-usage accounting; a Satellite withholds part of a storage node's earnings until the node has sustained good uptime for a period the paper states is on the order of "greater than half a year," reclaiming the withheld amount if the node departs early. The design explicitly avoids Byzantine fault-tolerant consensus and blockchain-style global coordination for its metadata and control plane, on the stated reasoning that systems requiring less inter-node coordination scale in throughput more directly with added resources; the paper cites this as the reason the current design places the Satellite, rather than a decentralized consensus mechanism, at the center of metadata authority, repair scheduling, and payment settlement.

### Parameters
- Erasure code family: Reed-Solomon.
- Reed-Solomon working example throughout the paper: (k=20, n=40), used repeatedly for illustration but the text does not state this as the production default in the v3.1 edition read here.
- Extended parameter set for long-tail tolerance: (k, m, o, n) with k ≤ m ≤ o ≤ n, where m − k is the safety buffer before data loss risk, o − m is the number of nodes tolerated offline without triggering repair, and n − o is the number of slow uploads tolerated without waiting.
- Illustrative object-size assumption used in one bandwidth calculation: average object size 50 MB, n = 40.
- Design assumption on typical object size: the initial product targets objects of 4 MB or larger; smaller objects are supported but the paper states they may be more costly to store.
- Bandwidth-cap example (US ISP): Comcast's stated residential cap of 1 TB/month, which the paper computes bounds sustained throughput to no more than 385 KB/s averaged over a month.
- Node check-in interval: suggested roughly once per hour (v3.1 node-discovery cache design).
- Storage node payment withholding period: on the order of "greater than half a year" of sustained good uptime before a Satellite releases withheld earnings in full.
- Bayesian audit-estimator priors evaluated: Uniform β(1,1) and Jeffrey's β(0.5,0.5).
- Simulation scale for the repair-bandwidth decision tables: 10,000-node simulated network, 1000 independent 24-month runs per parameter row, mean-rebuilds/month read at the 99th percentile of the observed rebuild-count distribution.
- Payment token for Satellite-to-storage-node transfers: Ethereum-based ERC-20 STORJ token (client-to-Satellite payment may use any mechanism the Satellite accepts).

### Stated limitations
The paper states plainly, in its own Future Work chapter, that "we place significant burdens on the Satellite operator to maintain a good service level with high availability, high durability, regular payments, and regular backups," and that eliminating Satellite control of metadata via a workable Byzantine fault-tolerant consensus algorithm is a long-term goal not yet achieved — "should one arise" is the paper's own qualifier. Data repair depends on the Satellite process running continuously: the text states explicitly that if a user's Satellite stops running, repairs stop and data will eventually be lost to node churn, an acknowledged single-point-of-failure dependency the paper compares to the requirement in Kademlia that a value's original publisher must periodically republish it or the value expires. The bandwidth-measurement and payment-accounting system tracks only bandwidth used during storage and retrieval operations; the paper states it explicitly does not cover node-discovery traffic or other maintenance overhead, so total network bandwidth exceeds what is measured and paid for. Reed-Solomon-based audit error-correction (the Berlekamp-Welch algorithm) is stated to depend on the assumption that most storage nodes behave rationally and store data faithfully; the paper frames this as an assumption underlying the mechanism, not a guarantee the mechanism itself enforces. The Honest Geppetto attack (an adversary operating many nodes that accumulate reputation before defecting simultaneously) is stated to have no complete defense; the paper's best answer is that the attack becomes ineffective only at sufficient network scale, backed partially by Bayesian relatedness analysis across node behavioral signals, not by a mechanism that eliminates the exposure. The hostage-bytes attack (a node withholding data to extort added payment) is stated to be defeated by Reed-Solomon redundancy only when malicious nodes do not collude to control multiple pieces of the same file; collusion is explicitly identified as the residual case the redundancy does not cover. A faithless Satellite or storage node modified to serve any paying requester is stated not to compromise data privacy, because client-side encryption is independent of Satellite behavior, but the paper states explicitly that "Storj is not designed to protect against compromised clients."

### Requirements it places on the rest of the system
The Satellite must run continuously for repair to occur at all; a design that depends on Storj for durability therefore inherits an availability requirement on a specific centralized-per-user-or-organization process, not just on the storage-node population, which is a materially different assumption from a system whose repair logic runs from any node's local view (the paper's own comparison point is Kademlia, where republishing similarly depends on the original publisher staying online). The audit and repair pipeline requires the erasure code to operate at the stripe granularity (not the whole-segment or whole-piece granularity) so that a Berlekamp-Welch challenge-response can run against a single small stripe rather than downloading a full segment for every audit; a storage backend that only exposes whole-piece reads could not reuse this audit mechanism without modification. Data repair additionally requires a separate per-piece hash, stored alongside each piece and validated against the pointer, because the paper states Reed-Solomon decoding alone is insufficient to confirm correctness when only the minimum k pieces are downloaded for a repair — so a system relying purely on the erasure code's own error-correcting property during repair, without this extra hash layer, would not have the same correctness guarantee the paper claims. The bandwidth-allocation accounting scheme requires every Uplink to already hold a public/private key pair as part of its node identity, since restricted bandwidth allocations are authenticated with that existing key rather than a newly issued one; any client identity system without persistent asymmetric keys would need to add one before this accounting mechanism could apply. The described payment settlement requires the Satellite to hold an accurate day-by-day accounting of which pieces each storage node stores; a storage node that misses a delete command while offline continues holding data the Satellite no longer credits it for, which the paper states is cleaned up later by garbage collection, not by an accounting reconciliation at the time of the missed command.
