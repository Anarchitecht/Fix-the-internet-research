### What it does
QUIC is a transport protocol that reduces the round trips needed to start an encrypted connection and lets an ongoing connection survive a change in the client's IP address or port, by running entirely in user-space over UDP (User Datagram Protocol) instead of inside the kernel as TCP (Transmission Control Protocol) does. A traditional HTTPS connection requires a TCP handshake (1 round trip) followed by a separate TLS (Transport Layer Security) handshake (1-2 more round trips) before any application data moves; QUIC merges transport and cryptographic setup into one handshake. On a first-ever connection to a server, QUIC completes in one round trip (1-RTT): the client sends a client hello, learns the server's public credentials (a server config and certificate), and on repeat connections to the same server can reuse those cached credentials to send encrypted application data in its very first packet, with zero added round trips (0-RTT) beyond the first packet's transit time — provided the client still holds a valid cached server config and a valid source-address token (a server-encrypted blob attesting the client's validated IP address from a prior handshake). Every QUIC connection carries a 64-bit Connection ID that identifies it independently of the underlying IP address and port pair; because Connection ID rather than the traditional (source IP, source port, destination IP, destination port) tuple identifies the connection, a NAT (Network Address Translator) rebinding a client's mapped external port, or a client itself changing IP address, does not by itself break the connection — the packet still carries the same Connection ID, so the server continues to recognize it. The paper distinguishes this passive survival of address changes ("QUIC endpoints simply elide the problem of NAT rebinding by using the Connection ID to identify connections") from client-initiated connection migration, an active protocol feature for a client to move a connection to a new path on purpose, which the paper states was, at time of writing, "a work in progress with limited deployment." QUIC multiplexes multiple independent byte streams within one connection and applies loss detection and congestion control at the connection level rather than per-stream, so a lost packet on one stream does not stall delivery of data already available on another stream (eliminating the head-of-line blocking that arises when HTTP/2 multiplexes streams over one underlying TCP connection, where TCP's own in-order delivery guarantee blocks all streams behind one lost segment). QUIC encrypts most of its packet header, leaving only the fields a receiver needs to route and decrypt a packet (flags, Connection ID) unencrypted, explicitly to prevent middleboxes (network equipment that inspects or rewrites protocol fields, positioned between endpoints) from depending on and thereby freezing ("ossifying") any other transport-layer signal.

### Parameters
- QUIC protocol version used for all reported experiments unless otherwise noted: version 35.
- Default QUIC UDP payload size: 1350 bytes, chosen from the packet-size reachability experiment above (unreachability rises sharply above 1450 bytes of total packet size against a 1500-byte Ethernet MTU).
- Connection ID size: 64 bits.
- Default initial connection-level flow-control (receive window) limit advertised by a QUIC client: 15 MB.
- TLS/TCP-side QUIC-discovery delay: when racing a QUIC connection against a fallback TLS/TCP connection on a repeat visit to a known-QUIC origin, the client delays initiating the TLS/TCP attempt by up to 300 ms, preferring QUIC if it succeeds first.
- Congestion control: both QUIC and the TCP comparison group use a paced variant of the Cubic algorithm.
- 0-RTT handshake success precondition: the client must hold both a valid cached server config (the server's credentials) and a valid cached source-address token (a server-encrypted attestation of the client's IP address from a prior successful handshake) for the specific origin and data center being contacted.

### Stated limitations
The paper states client-initiated connection migration — actively moving an established connection to a new network path — was, at time of writing, "a work in progress with limited deployment," distinct from and more limited than QUIC's passive tolerance of NAT rebinding via the Connection ID. The paper states QUIC "may perform worse than TCP" on networks with high bandwidth (over 100 Mbps) and/or very low RTT (a few milliseconds), attributed to client CPU limits and/or client-side OS or application scheduler inefficiencies, though it states these conditions are "outside typical Internet conditions." The paper states applications that pre-warm connections in the background before the user's action requires them (as the YouTube app does) receive no measurable benefit from QUIC's 0-RTT handshake, because the handshake latency was already hidden; it further states some applications, such as web browsers, "cannot always pre-warm connections since the server is often unknown until explicitly indicated by the user." The paper states QUIC's server CPU cost remains roughly twice that of TLS/TCP even after the described optimizations, and states this higher cost "will remain" even though further reductions (for example, general kernel bypass) are believed possible. The paper states it does not know whether protocol bits QUIC exposes, other than the one bit that triggered the documented October 2016 middlebox incident, have been ossified by other middleboxes, and states explicitly "we do not have a method to answer this question at Internet scale." The paper states networking (specifically handshake latency) "contributes to well under 20% of Search Latency and Video Latency," so QUIC's transport-level gains bound only a fraction of end-to-end application latency regardless of further transport optimization.

### Requirements it places on the rest of the system
QUIC's 0-RTT handshake requires the client to have completed at least one prior successful handshake with the specific server (or, more precisely, the specific data center's server configuration) it is reconnecting to, and to still hold both the cached server config and a still-valid source-address token from that prior handshake; a client reconnecting to a server it has never contacted, or whose cached credentials have expired or been invalidated by an IP-address change, falls back to a 1-RTT handshake instead. The paper states QUIC's passive survival of NAT rebinding depends on the receiving endpoint continuing to recognize packets by Connection ID alone, independent of the observed source IP and port — a requirement that composes only with a design in which nothing else in the system re-derives session identity from the network-layer address tuple. Because most of the QUIC packet header is encrypted, any network operator or middlebox that needs to classify, prioritize, or otherwise act differently on QUIC traffic must do so using only the deliberately small set of fields the protocol leaves unencrypted, and the paper's own middlebox incident (Section 7.5) demonstrates that any such external dependency on an unencrypted field is fragile to a protocol-side change the middlebox operator was not consulted on in advance. QUIC's server-side deployment requires an operator willing to accept roughly double the CPU cost per connection compared to TLS/TCP (after the optimizations described), and requires an unencrypted (fallback) TLS/TCP path already exists for clients or paths where the QUIC handshake fails, since the paper's own discovery mechanism (Section 3.8) depends on a TLS/TCP fallback whenever QUIC is blocked or its handshake packet exceeds the path's MTU.

- S. Radhakrishnan, Y. Cheng, J. Chu, A. Jain, B. Raghavan, "TCP Fast Open," ACM CoNEXT, 2011 — competing (the paper's Section 8 gives a direct, mechanism-level comparison: TCP Fast Open limits first-round-trip client data to what fits in a TCP SYN segment, which QUIC does not, and works only for repeat connections to the same server IP, which QUIC's origin-based 0-RTT handshake does not require).
- W Michael Petullo, Xu Zhang, Jon A. Solworth, Daniel J. Bernstein, Tanja Lange, "MinimaLT: Minimal-Latency Networking Through Better Security," ACM CCS, 2013 — competing (a contemporaneous protocol with a similar 0-RTT handshake and encrypted multiplexed tunnel; the paper states MinimaLT additionally prevents linkability of a connection across an IP-address migration, a privacy property QUIC did not have at time of writing and which the paper states was "under consideration as QUIC evolves at the IETF").
- B. Ford, "Structured Streams: A New Transport Abstraction," ACM SIGCOMM, 2007 — foundational (the paper states QUIC's design is closest to Structured Stream Transport, sharing a channel identifier, monotonically increasing packet numbers, encrypted transport header, and lightweight streams).
- E. Rescorla, "The Transport Layer Security (TLS) Protocol Version 1.3," IETF Internet Draft, 2017 — competing/superseded-by (the paper states TLS 1.3, partly inspired by QUIC's own handshake protocol, now provides equivalent latency benefits to QUIC's homegrown cryptographic handshake, and that IETF standardization work would replace QUIC's original handshake with TLS 1.3).
