## [DAVIDSON-POPETS-18] Privacy Pass: Bypassing Internet Challenges Anonymously
**Citation:** Alex Davidson, Ian Goldberg, Nick Sullivan, George Tankersley, Filippo Valsorda. "Privacy Pass: Bypassing Internet Challenges Anonymously." Proceedings on Privacy Enhancing Technologies (PoPETs), 2018 (3):164-180. DOI 10.1515/popets-2018-0026.
**Retrieved:** full text via https://petsymposium.org/popets/2018/popets-2018-0026.pdf
**Source URL:** https://petsymposium.org/popets/2018/popets-2018-0026.pdf
**Domain:** I

### What it does
Privacy Pass lets a client redeem one unlinkable anonymous token per rate-limited action, obtained in a batch of N tokens after passing a single challenge (a CAPTCHA in the deployed case), so a server can rate-limit or gate repeated access without learning which of the client's earlier challenge-passes any later redemption corresponds to. The mechanism is a verifiable oblivious pseudorandom function (VOPRF): an oblivious PRF is a two-party protocol letting a client obtain F_k(x) for a server-held key k without revealing x to the server, and "verifiable" means the client also gets a proof that the server used the same key k it committed to. The client generates N random token values t_1...t_N, computes T_i = H1(t_i) for a hash-to-curve function H1, blinds each with a random exponent r_i to get a blinded token, and sends the batch to the server together with proof of having passed the challenge. The server signs each blinded token under its own private key and produces one non-interactive zero-knowledge proof (a batched discrete-log-equality, or DLEQ, proof) that every signature in the batch used the same private key, rather than one DLEQ proof per token; the client verifies this single batched proof and unblinds each signed token to recover N usable (t_i, W_i) pairs, where W_i = the PRF evaluation F_k(t_i). To redeem a token later, the client presents an unspent pair (t, W) together with a MAC computed over request-binding data R using a key derived from W; the server recomputes F_k(t) from its own key, checks that t has not been redeemed before, and verifies the MAC to confirm the client actually holds a validly signed token, without either side ever having linked this redemption to the earlier signing session that produced it. This unlinkability follows from the OPRF's message-hiding property (the server never saw t or T_i unblinded during signing) plus the one-more-token security property, which the paper proves under a standard hardness assumption and which guarantees a client holding l signed tokens cannot construct l+1 valid ones. Key rotation invalidates old tokens: the server periodically retires old signing keys and clients must obtain fresh tokens under a key still on the server's accepted-key list, which the paper recommends keeping to about 2-3 concurrently accepted keys to limit how far the user base is split across key-specific anonymity sets.

### Parameters
- Elliptic curve: NIST P-256.
- Token batch size N: benchmarked at N = 5, 10, 15, ..., 100 in 5-token increments; deployed value N = 30; server-enforced maximum N = 100.
- Key rotation interval: the paper recommends short rotation periods "such as 3-4 days" to bound how long a stockpiled token batch of signed tokens remains redeemable.
- Number of concurrently accepted signing keys: recommended at 2-3, to limit the degree to which multiple active keys split the anonymity set of token holders into smaller, more identifiable groups.
- Threat/security model: security proofs are given in the random oracle model, and one-more-token security is stated to follow from "a standard assumption" without the paper stating that assumption's name at the point cited in the main text (developed in the paper's Section 5.4.3 proof).

### Stated limitations
The paper states its protocol does not defend against a monster-in-the-middle (MitM) adversary during the signing phase: because tokens carry no client-binding metadata (by design, to avoid deanonymization via that metadata), a MitM that intercepts a client's completed-challenge signing request can substitute its own blinded tokens and receive signed tokens without having solved the challenge itself; the paper's stated mitigation is only that this requires a renewable source of challenge solutions to exploit repeatedly, not a cryptographic fix. Token accumulation ("farming") is stated as a residual risk enabling stockpiling for a denial-of-service attack; the paper's countermeasures are operational limits (the 100-token signing cap, and key rotation on the order of days) rather than a protocol-level prevention. Token exhaustion is stated as possible: an embedded sub-resource that repeatedly triggers redemption can drain a client's stored tokens; the paper's mitigation (rate-limiting redemptions per URL, tracked client-side) is described as reducing rather than eliminating the attack, and a stronger fix (blacklisting URLs after one redemption attempt) is stated as "not implemented at time of writing." The paper states a structural anonymity limit shared with all such registration-based systems: early-adopter clients belong to a small anonymity set, and a server that signs tokens for very few clients (or immediately after a key rotation) can narrow a later redemption to one of a small number of possible signers; the paper states this makes the scheme, like Tor itself, "only really effective when the number of users is quite large." The paper explicitly states its threat model does not defend against a verifier (the edge/CDN) colluding with the token issuer to break unlinkability, nor against a client that shares its tokens with other parties — both are named directly by the target registry's citation as out of scope, and correspondingly this paper's security proofs (Section 5, unlinkability and one-more-token security) are stated relative to an honest-but-possibly-curious single verifier-issuer, not a colluding pair. Double-spending protection is stated to require each service to implement its own redemption-index check (a hash table or Bloom filter over spent tokens); the paper does not measure the storage or lookup cost of this index at Cloudflare's request volume, only recommends it be present.

### Requirements it places on the rest of the system
The protocol requires the server to run and maintain a signing key, publish a small, low-churn list of currently accepted verification commitments (2-3 keys recommended) so clients whose tokens were signed under a recently-rotated-out key can still redeem before those tokens expire, and requires some out-of-band or globally-consistent channel for distributing key-rotation updates; the paper suggests "beacons or other globally visible and consistent locations, such as the Tor consensus" for this, but states the initial deployment instead updates commitments directly inside the browser extension. It requires the calling application (the "challenge" the client must first pass) to supply the actual work-based anonymity guarantee: Privacy Pass tokens are only as scarce as the challenges that produce them, so the mechanism composes with any challenge type (the paper's deployment uses a CAPTCHA) but supplies no scarcity of its own. It requires the redeeming server to maintain a double-spend index across every previously redeemed token value t, and the paper states each service's own redemption index must be separate from every other service's, since services must "use their own private keys for signing tokens so that tokens cannot be spent multiple times across different services." It requires the client to be able to store unspent token pairs locally between the signing and redemption phases (the browser extension's local storage in the deployed case) and to track, per domain, whether a token has already been spent, since the paper's own mitigation for the token-exhaustion attack depends on this per-domain spend tracking being available and enforced client-side.
