## [ELLIS-SIGMOD-89] Concurrency Control in Groupware Systems

**Citation:** C.A. Ellis, S.J. Gibbs. "Concurrency Control in Groupware Systems." ACM SIGMOD, 1989. Pages 399-407. DOI 10.1145/67544.66963.
**Retrieved:** full text via https://dl.acm.org/doi/10.1145/67544.66963
**Source URL:** https://doi.org/10.1145/67544.66963
**Domain:** D

### What it does
The dOPT algorithm (distributed Operational Transformation) lets every participant in a real-time multi-user editing session apply their own edits to their local replica immediately, without acquiring a lock, while still converging every replica to the same final state once all edits have propagated. It achieves this by rewriting a received operation against operations already applied locally that the sender had not yet seen, so that operations applied in different orders at different sites still produce the same result. Each site holds a replicated site object (an application data structure, for example a character string), a request queue, a request log of executed operations, and a state vector with one counter per site recording how many operations from that site have been executed locally. When a user acts, the local site executes the operation immediately, assigns it a priority, and broadcasts a request tuple (originating site id, the originating site's state vector at generation time, the operation, its priority) to every other site. A receiving site compares the incoming request's state vector to its own: if the sender's state vector is not yet dominated by the receiver's own state (the sender still has unseen predecessor operations to receive), the request is queued and deferred (Case I); if the two state vectors are equal, the operation executes unmodified (Case II); if the receiver has executed operations the sender had not yet seen when it generated the request, the receiver scans its own log for those extra logged operations and applies a transformation function to the incoming operation for each one, then executes the transformed operation (Case III). The transformation step is defined by a transformation matrix T, one entry T_uv per ordered pair of operators (u, v) in the system, each entry a hand-written function that computes a corrected operation from two conflicting operations and their priorities so that applying operation A followed by transformed operation B produces the same site-object state as applying B followed by transformed A. For a text editor with two operators, insert[X; P] (insert character X at position P) and delete[P], the paper gives the four transformation-matrix entries explicitly: insert-insert, delete-delete, insert-delete, and delete-insert. Tie-breaking between two operations at the same position uses a priority value; the paper shows a naive priority equal to the site identifier alone diverges (a three-site worked example produces the string "xyz" at one site and "zxy" at another) and replaces it with a priority defined as the list formed by concatenating an operation's largest same-position predecessor's priority with the site's own identifier, comparing two such priority lists element by element from the first list position where they differ.

### Measured results
None. The paper is a theoretical/algorithmic contribution with a worked numerical example (the three-site insert scenario in Figure 4) used to illustrate correctness and a failure mode, not a benchmark. It reports no runtime, message-count, node-count, or throughput figures, and the retrieved text describes no evaluation section, testbed, or performance measurement of any kind. It states qualitative operational guidance for its GROVE implementation: system quiescence (resetting the growing log) "should be enforced periodically (e.g., once per minute) and when the system falls quiet for an extended period of time (e.g., ten seconds)" — the paper gives no derivation for these two numbers and does not label them as measured; they read as suggested defaults.

### Parameters
- Number of sites N: assumed constant for the algorithm as presented (assumption A1); the paper states an extension to a varying site count is possible and defers it to end of section 4, then does not give it in the retrieved text.
- Quiescence interval: suggested "once per minute" as a periodic trigger and "ten seconds" of inactivity as an idle trigger for resetting the request log; stated as example values, not derived or measured.
- Priority: for the text-editing instantiation, a list formed by concatenating an operation's highest-priority same-position predecessor in the local log with the originating site's own identifier; compared element-by-element, longer list wins ties, giving temporal successors placement to the left of predecessors in the string.
- Transformation matrix size: m x m, where m is the cardinality of the operator set O; the text-editing example instantiates 4 of the m^2 entries (insert-insert, delete-delete, insert-delete, delete-insert) for m=2 operators.

### Stated limitations
The algorithm as specified assumes a constant number of sites (assumption A1), exactly-once and error-free message delivery (assumption A2), and that a message cannot be executed before it is generated (assumption A3); the paper states the second assumption "should be satisfied by the communications protocols so we take it as given," meaning dOPT itself supplies no reliable-delivery mechanism. The request log grows without bound during a session and must be scanned both to calculate a new operation's priority and to transform incoming operations, so the paper states the system needs periodic quiescence (all sites confirmed to have executed all outstanding requests) to reset the log to empty; detecting quiescence is stated to be "equivalent to the well known distributed consensus problem." The paper's own worked example (Figure 4, three sites, priority-by-site-ID) demonstrates that using the site identifier alone as an operation's priority causes divergent final states between two sites (one produces "xyz," the other "zxy") when three insertions at the same position race in different orders relative to each other; the fix (the priority-list scheme) is proposed and given a sketched, not complete, proof — the paper states "the details of the full proof are beyond the scope of this paper." The proof sketch itself explicitly excludes some cases: it states "we have not discussed the case involving insertions at different positions" (argued not to need priority numbers) and "we have also not discussed cases involving deletion" (argued to often commute). Stated future work: generalizing the characterization of the transformation matrix beyond the two-operator text example, and extending the correctness proof to hypertext and other groupware data models — meaning the paper's own correctness argument is proved only for the character-string insert/delete case, not proved in general for an arbitrary operator set.

### Requirements it places on the rest of the system
Every operator pair (u, v) in the application's operator set O needs a hand-specified transformation function T_uv before dOPT can run over that data model; the paper gives no automatic or general method for deriving T from an operator definition, so a system adopting dOPT for a different data structure than a character string must independently design and prove correct a new transformation matrix. The algorithm requires the communications layer to guarantee each message is received exactly once and without error (assumption A2, taken as given rather than provided by dOPT). It requires each site to replicate the full site object locally, since operations execute against a local copy immediately, before any global ordering is established. It requires a way to detect global quiescence (equivalent to distributed consensus, per the paper) to bound the log's growth, meaning the rest of the system must supply a consensus or barrier mechanism dOPT itself does not define. The priority-list scheme requires every site to compare priorities using the same element-by-element list-comparison rule and to compute an operation's priority from the correct predecessor entry in its own local log at the moment of generation, so all sites must apply an identical, deterministic priority-calculation procedure for convergence to hold.

### Contradicts
The paper's own abstract states the algorithm's "overall structure is independent of the semantic information," but the algorithm's central mechanism (the transformation matrix T) is a set of hand-written functions, one per operator pair, each function embedding operation-specific semantics (for example, incrementing or decrementing a text position); only the algorithm's control structure (request queue, state-vector comparison, log scan) is semantics-independent, not the transformation step it depends on. ### References worth retrieving
- Lamport, "Time, Clocks, and the Ordering of Events in a Distributed System," CACM 21(7), pp. 558-565, 1978 — foundational, supplies the partial-order (happened-before) definition dOPT's precedence property is built from.
- Bernstein, Goodman, Hadzilacos, "Concurrency Control and Recovery in Database Systems," Addison-Wesley, 1987 — foundational, the database serializability framework the paper contrasts its non-serializable correctness criterion against.
- Grief, Seliger, Weihl, "Atomic Data Abstractions in a Distributed Collaborative Editing System," POPL 1986 — competing, a locking-based ("tickle locks") concurrency-control approach for collaborative editing the paper argues against.
- Stefik, Foster, Bobrow, Kahn, Lanning, Suchman, "Beyond the Chalkboard: Computer Support for Collaboration and Problem Solving in Meetings," CACM 30(1), pp. 32-47, 1987 — competing, source of the dependency-detection concurrency-control approach the paper compares against and of the WYSIWIS interface concept.
- Sarin, Grief, "Computer-Based Real-Time Conferences," Computer 18(10), pp. 33-45, 1985 — competing, source of the reversible-execution (optimistic, undo-based) concurrency-control approach the paper compares against.
- Cohen, Fish, Kraut, Leland, "Quilt: A Collaborative Tool for Cooperative Writing," ACM SIGOIS, pp. 30-37, 1988 — competing, a transaction-based non-real-time groupware editor the paper contrasts with GROVE's real-time model.
