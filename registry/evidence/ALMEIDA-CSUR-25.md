## [ALMEIDA-CSUR-25] Approaches to Conflict-free Replicated Data Types
**Citation:** Paulo Sérgio Almeida. "Approaches to Conflict-free Replicated Data Types." ACM Computing Surveys, 2025. DOI 10.1145/3695249.
**Retrieved:** full text via https://arxiv.org/pdf/2310.18220
**Source URL:** https://arxiv.org/pdf/2310.18220
**Domain:** D

### What it does
A Conflict-free Replicated Data Type (CRDT) lets independent replicas of one data object accept local updates without coordinating with other replicas first, remain available under network partitions, and reach identical state on every replica that has received the same set of updates, whatever order those updates arrived in. The paper systematizes four families of CRDT design, comparing their message content, delivery-guarantee requirements, and state-size growth. Operation-based CRDTs propagate individual update operations: each replica runs a side-effect-free `prepare` step that turns an invoked operation into a message, and an `effect` step at every replica (including the origin) that applies the message to local state; this family needs causal-broadcast delivery — every message delivered at most once, and delivered only after every message it causally depends on. Pure operation-based CRDTs are a stricter version that require Tagged Causal Broadcast middleware to expose message timestamps and causal-stability notifications to the CRDT itself, so the CRDT logic never touches local state directly, only a partially ordered log (PO-Log) of received operations; a message is causally stable at a node when every message the node will later receive carries an equal or later logical timestamp, so no further concurrent operations remain to interleave with it, letting the PO-Log discard stable entries. State-based CRDTs instead propagate full or partial local state; correctness requires only that local state form a join-semilattice (a partially ordered structure with a defined merge, or join, operation for any two states) and that every state-mutating operation be an inflation — the state after the operation is greater than or equal to the state before it, under the semilattice order — so that repeated or reordered delivery of the same state never moves a replica backward; delivery need only be reliable and eventually complete (at-least-once, eventually), not ordered. Delta-state CRDTs keep the join-semilattice state model of state-based CRDTs but replace each mutator with a delta-mutator that returns a small delta-state instead of the full next state; a naive propagation algorithm accumulates deltas in a per-replica delta-buffer, joins each locally applied or received delta into both the buffer and the durable state, and periodically broadcasts and clears the buffer. The paper derives an optimal delta-mutator using Birkhoff's join-decomposition theorem from lattice theory: for a distributive lattice, every state has a unique irredundant join decomposition into join-irreducible elements, so the difference between two states can be computed exactly as the join of the elements in one state's decomposition that are not already below the other state, and the optimal delta-mutator is defined as this difference between the mutator's full-state result and the current state.

None. The paper is a systematization survey; it defines formal properties, derives algorithms, and cites deployed systems (Riak, Redis, AntidoteDB, SwiftCloud, Automerge, Yjs), but reports no experiment of its own, no benchmark, and no figure with stated node counts, message counts, or latency. The one specific number given about a cited deployment — "a list of over 40 applications using [Yjs]" — carries no experimental conditions (measurement date, counting method) and is not attributed to a primary measurement, so it is not usable as a quantitative result under this batch's rule 1.

### Parameters
Not applicable in the sense of tunable runtime parameters — the paper defines formal design-space choices rather than numeric parameters. Where later CRDT implementations expose a parameter (for example, a retention window for tombstones or causal-context compaction), this survey states the mechanism generally and does not fix a value.

### Stated limitations
Operation-based CRDTs are unsuitable for large weakly-connected systems prone to long partitions: the paper states each replica must retain every operation not yet delivered to every other replica, and this retained set grows linearly with partition duration, producing unbounded memory growth under a sufficiently long partition, and that two independent groups of operation-based replicas that evolved separately cannot be merged in realistic (non-full-history) implementations. Pure operation-based CRDTs cannot extract information from the CRDT's own state inside `prepare`, because `prepare` in this family never touches local state; this is stated as a strict limitation relative to the general operation-based model. State-based CRDTs carry a metadata component that grows linearly with the number of replicas in the causal context or replica-indexed map (for example, a counter represented as a map from replica id to integer, rather than a single integer), and this overhead cannot be amortized transparently across multiple CRDT objects the way operation-based middleware cost can — amortizing it requires explicitly nesting multiple CRDTs inside one container CRDT, which the paper states is a non-transparent refactoring cost. The naive delta-state propagation algorithm is stated to be too naive for practical use: the per-replica delta-buffer tends to grow back toward the size of the full state, for two identified reasons — deltas are re-propagated back to the replica they originated from, and a received delta-group is joined into the local buffer in full even where most of it duplicates already-held state. Server-based identity-collapsing techniques for scaling CRDT replica-id maps down when no client session is active are described as "not aware of these techniques having been described or if they have been used," marking that idea as unimplemented and unverified rather than a result. List-CRDT approaches using a pre-existing dense total order for element identifiers (Treedoc, Logoot, LSEQ) are stated to have identifiers whose size keeps growing over time. List-CRDT approaches that instead explicitly order small unique identifiers (Woot, Causal Trees, RGA, YATA) are stated to accumulate tombstones in state, addressed only by causal-stability-based removal.

### Requirements it places on the rest of the system
Operation-based CRDTs and, more strictly, pure operation-based CRDTs require the messaging layer to supply causal broadcast: exactly-once, causally-ordered delivery to every replica. Pure operation-based CRDTs additionally require the messaging middleware to expose causal timestamps and per-node causal-stability notifications to the CRDT logic (Tagged Causal Broadcast), which is a stronger interface requirement than plain causal broadcast provides. State-based and delta-state CRDTs require only at-least-once, eventually-complete delivery with no ordering guarantee, but every operation-mutator in this family must be provably an inflation over the state's join-semilattice order, a property the implementer must establish per data type, not something the messaging layer can enforce. Named (non-anonymous) CRDTs of any family require every replica to hold a globally unique replica identifier; the paper states this as the only requisite for state-based CRDTs to support dynamic joining, leaving, and merging of independently evolved replica groups. Achieving the delta-state model's optimal (smallest) delta-mutator requires the CRDT's state lattice to be a finite distributive lattice, or reducible to one through finite quotient sublattices, so that Birkhoff's unique-irreducible-join-decomposition result applies; a state lattice without this structure cannot use the optimal-delta construction the paper derives. The inter-datacenter delta-propagation simplification (skipping general join-decomposition-based redundancy elimination) requires a small, fixed, fully-meshed set of replicas — the example given is one replica per datacenter — and requires tracking a version vector per replica to gate delivery on causal-dependency satisfaction.

### Contradicts
None found. The paper explicitly corrects two claims it identifies as widespread misconceptions rather than disagreeing with any specific paper in this corpus: that CRDTs are defined by having commutative operations (the paper states the more significant advance over prior optimistic replication, such as Lazy Replication, is supporting non-commutative operations under operation-based design), and that state-based CRDT mutators must be monotonic functions (the paper states the correct requirement is that mutators be inflations, which is what produces monotonic state evolution, not monotonicity of the mutator function itself).
