## [VORICK-SIA-14] Sia: Simple Decentralized Storage

**Citation:** David Vorick, Luke Champine. "Sia: Simple Decentralized Storage." Nebulous Inc. technical report, 2014-11-29. Pages 1-8. DOI not stated.
**Retrieved:** full text via https://sia.tech/whitepaper.pdf
**Source URL:** https://sia.tech/whitepaper.pdf
**Domain:** C

### What it does
Sia lets a storage provider (a "host") and a client agree on a storage arrangement and enforces that agreement through a blockchain, without a third party escrowing funds or verifying storage on the network's behalf. Sia is built as a fork of Bitcoin's transaction model: it replaces Bitcoin's scripting system with an M-of-N multi-signature scheme for all transactions, and adds a new transaction type, the file contract, that both parties sign.

A file contract states the Merkle root hash of the file to be stored (computed by splitting the file into fixed-size segments and hashing them into a Merkle tree — a tree of hashes where each parent node is the hash of its children, letting one root hash commit to the entire file), a duration, a challenge frequency, and payout parameters: the amount released to the host for a valid storage proof, the amount released elsewhere for a missing or invalid proof, and the maximum number of proofs the host may miss before the contract becomes invalid. The challenge frequency divides the contract duration into discrete challenge windows, one storage proof required per window.

A storage proof works as a proof of retrievability: the host reveals one segment of the file plus the list of Merkle-tree hashes needed to verify that segment against the committed root hash. Which segment is demanded is unpredictable in advance: for challenge window W_i, the random seed is the hash of the contract ID concatenated with the hash of the block immediately preceding the start of W_i, so the host cannot know which segment will be checked until that block is mined. Because the seed derives from a specific prior block, submitting a proof of possessing only a fraction of the file succeeds only in that same fraction of challenge windows — the paper states a host storing 50% of a file fails roughly 50% of proofs. A valid proof submitted inside its window triggers an automatic blockchain transaction crediting the host, enforced by network consensus alone; an unmet window instead directs the contract's held funds toward an unspendable "missed proof" address, so a client never needs to personally check host behavior. A contract can also be edited if it carries pre-agreed "edit conditions," with any edit's effect deferred to a future challenge window so it cannot retroactively invalidate an in-flight proof.

The design assumes a single host provides poor availability alone, so the paper recommends clients split a file across multiple hosts using an erasure code — specifically regenerating codes, splitting the file into n pieces recoverable from any m of them — encrypting each piece before distributing it, so that availability depends on the m most reliable hosts among those holding a piece rather than on the average host's reliability, and download latency or throughput can be optimized by choosing the closest or fastest m pieces to fetch, in parallel.

Because a storage proof only demonstrates that a host still holds the file, not that the host will transfer it on request, Sia has no protocol-level mechanism forcing a host to serve downloads. The paper's proposed fix inverts the usual download-fee relationship: instead of a client paying for a download, a client offers a reward for the host sending it a file (an "upload incentive"), so an uncooperative host can simply be ignored in favor of one of the other m-of-n hosts, and hosts compete on responsiveness for the reward. Actual per-segment rewards for this scheme are expected to move through pre-existing micropayment channels, exchanging small amounts of currency for small transferred segments in rapid succession to bound each party's exposure to being cheated mid-transfer.

Sia mitigates a Sybil attack against host reputation — a host fabricating a storage history for itself by repeatedly forming self-contracts over fabricated data — by having clients require that a host's self-announcement (posted in the blockchain's arbitrary-data field) include a volume of coins locked for a future date; the paper defines a lock's value as coins × days-until-unlock (10 coins locked 14 days out creates a lock valued at 140 coin-days), and recommends clients favor hosts presenting higher-value locks, on the reasoning that a valuable lock is not inexpensive to fabricate.

Sia funds its developer, Nebulous Inc., through a separate token, siafunds, rather than through currency premining: when a file contract is created, 3.9% of the contract's committed funds is diverted to whoever holds siafunds at that time, with Nebulous Inc. initially holding roughly 88% of all siafunds and early backers holding the remainder. The paper frames this as tying Nebulous's revenue to the total value of contracts actually created on the network rather than to currency-supply appreciation.

### Measured results
None. This is a design whitepaper: it presents the protocol and its incentive reasoning, with no implementation benchmark, deployment measurement, or simulation. The one quantitative claim resembling a measured result — "a host storing only 50% of the file will be unable to complete approximately 50% of the proofs" — is a probabilistic argument from the random-sampling proof design, not a number from a run system, and carries no experimental conditions.

### Parameters
- File-contract Merkle segment size: described as "constant size," with no specific byte value stated in the retrieved text.
- Challenge-window random seed: H(contract ID || H(block immediately preceding the window)).
- Contract fee routed to siafunds holders: 3.9% of the contract fund, deducted at contract creation.
- Initial siafund distribution: approximately 88% held by Nebulous Inc., the remainder by early crowd-fund backers.
- Block-reward schedule: first block mints 300,000 siacoins; the reward decreases by 1 coin per block until reaching a floor of 30,000 coins per block; target block interval 10 minutes.
- Stated annual currency-supply growth at that schedule: 90% (year 1), 39% (year 2), 21% (year 3), 11.5% (year 4), 4.4% (year 5), 3.2% (year 8), 2.3% (year 20) — these are the paper's own derived figures from the block-reward schedule above, not independently measured.
- Arbitrary transaction data field: nodes accept up to 64 KB of arbitrary data per block, used for host self-announcement and other out-of-band coordination.
- Erasure-code redundancy (n pieces, recoverable from any m): left as a design choice for the client; the paper illustrates with an example of m = 10 out of n = 100 but states this is only illustrative ("as an extreme example").

### Stated limitations
The authors state the protocol contains no mechanism enforcing host uptime and no provision requiring a host to transfer a file to the client on request; both properties depend entirely on an out-of-band incentive layer the paper proposes but does not make part of the protocol. Block-withholding attacks let a miner controlling a share of hashing power bias the random segment-selection seed in its own favor; the paper states an attacker controlling 50% of hashing power can manipulate roughly 50% of challenges but still fails the remaining unmanipulated half, and the paper's recommended defense (high challenge frequency, large missed-proof penalties) is stated to deter only a financially motivated attacker below the 50% hashing-power threshold, not a Byzantine attacker acting without financial motive. Closed-window attacks let a miner refuse to include a host's storage-proof transaction in a block, or extort a large transaction fee for doing so, forcing a proof failure; the paper's defense is a larger challenge-window size so more miners have an opportunity to include the proof, which reduces but does not eliminate the exposure. A host reputation still depends on clients configuring their own selection criteria (price, lock value, storage volume offered, missed-proof penalty); the paper explicitly leaves any more complex host-selection method, including human review, to out-of-band and more centralized systems. The currency's price volatility is stated as a risk to hosts mid-contract, expected to raise prices on long-term contracts as a hedge, with a two-way peg to other crypto-assets described as future work rather than a present mitigation.

### Requirements it places on the rest of the system
Every consumer of a storage proof needs only to read the blockchain, since proof validity is fully checkable from public data (the Merkle root committed in the contract, the revealed segment, and the accompanying hash path) — no direct interaction between client and host is needed for proof verification itself. The random-sampling proof-of-storage design requires a source of unpredictable randomness the host cannot control in advance; the paper supplies this from block hashes, which means the scheme's unpredictability is only as strong as the blockchain's own resistance to hashing-power concentration (stated explicitly as the 50%-hashing-power boundary above). Achieving actual file availability, not just provable possession, requires a client-side erasure-coding and multi-host placement layer that Sia's contract mechanism does not itself provide — the paper is explicit that a single-host contract "guarantees little in the way of availability, bandwidth, or general quality of service." Achieving actual download service from hosts requires a separate, client-configured incentive layer (micropayment-based upload rewards) that is not part of the protocol Sia enforces; a system relying on Sia for storage without also implementing this layer has no guaranteed way to retrieve stored data. Sybil-resistant host selection requires clients to independently evaluate a host's locked-coin value and other self-reported metrics; the protocol supplies the locking primitive but not a policy for how much lock value is sufficient.
