## [SATHIAMOORTHY-VLDB-13] XORing Elephants: Novel Erasure Codes for Big Data

**Citation:** Maheswaran Sathiamoorthy, Megasthenis Asteris, Dimitris Papailiopoulos, Alexandros G. Dimakis, Ramkumar Vadali, Scott Chen, Dhruba Borthakur. "XORing Elephants: Novel Erasure Codes for Big Data." Proceedings of the VLDB Endowment, Vol. 6, No. 5, 2013. Pages 325-336. DOI 10.14778/2535573.2488339.
**Retrieved:** full text via https://www.vldb.org/pvldb/vol6/p325-sathiamoorthy.pdf
**Source URL:** https://www.vldb.org/pvldb/vol6/p325-sathiamoorthy.pdf
**Domain:** C

### What it does
A locally repairable code (LRC), in the family this paper calls Xorbas, reduces the number of blocks read to repair one lost block below what a plain Reed-Solomon code requires, at the cost of storing extra parity blocks. The paper's explicit (10, 6, 5) LRC starts with 10 data blocks encoded by a standard (10, 4) Reed-Solomon code over a binary extension field to produce 4 global parity blocks (the same code Facebook's production clusters used at publication time), then adds local parity blocks computed as fixed linear combinations of subsets of data blocks (for example S1 = c1*X1 + c2*X2 + c3*X3 + c4*X5, using coefficients chosen so every relevant linear system stays invertible): a single lost data block is reconstructed by downloading only the other blocks in its local group and its group's local parity, rather than the larger set a plain Reed-Solomon repair requires. The paper implements this code in a Hadoop Distributed File System (HDFS) module named HDFS-Xorbas, extending Facebook's existing HDFS-RAID module, and adds two decoders: a light decoder invoked for single-block failures using local parities, and a heavy decoder invoked when a failure pattern the local parities cannot resolve requires the underlying Reed-Solomon decode.

### Parameters
- LRC code parameters used: (n=16, k=10, r=5) written as (10, 6, 5)-LRC in the paper's own notation, meaning 10 data blocks, 6 total parity blocks (4 global Reed-Solomon parities + 2 local parities, with an implied third local parity derivable from the others), and local repair groups of 5 blocks each.
- Baseline compared against: (10, 4) Reed-Solomon, the code the paper states was in production use at Facebook at the time.
- Block size: 64 MB in the EC2 experiments, 256 MB in the Facebook-cluster experiment (the paper states 256 MB as Facebook's production default).
- Storage overhead: 14% more storage than plain RS in the idealized case (Table 1 and abstract); the paper states this overhead is information-theoretically optimal for the locality obtained, citing its own theoretical result (referenced but not re-derived as a numeric bound in the extracted sections).
- Markov model repair-bandwidth cap: cross-rack communication capped at 1 Gbps, derived from Facebook cluster measurements, used uniformly across all three compared schemes in the MTTDL calculation.

### Stated limitations
The Facebook-cluster experiment's dataset (94% of files at 3 blocks) is stated by the authors as not representative of Facebook's production cluster's actual dataset, and the storage overhead observed there (27%) exceeded the code's ideal 13% because of this small-file skew; the paper flags both facts explicitly rather than presenting the numbers as production-representative. The reliability (MTTDL) comparison assumes independent node failures and exponential inter-failure and repair-time distributions; the paper states repair times may not actually be exponential and that this assumption is made only to simplify the analysis. The paper states the absolute MTTDL values are not meaningful in isolation, useful only for relative comparison between the three schemes under the same model. The EC2 experiments do not saturate available network bandwidth (traffic peaks differ between the two systems), so the paper states the measured repair-time gains understate the gains expected at larger scale, where the authors expect network saturation to delay RS repairs further relative to LRC; this is stated as an expectation, not a further measurement.

### Requirements it places on the rest of the system
The light-decoder single-block repair path requires the block's full local repair group (the other blocks sharing its local parity) to be simultaneously available for download; the paper's Markov model explicitly computes separate probabilities for invoking the light decoder versus falling back to the heavy (full Reed-Solomon) decoder when more blocks are lost from a stripe than the local-parity structure alone can resolve. The coefficients ci used to build each local parity must be chosen so that every linear system a repair could need to solve stays invertible over the finite field used (the paper states this coefficient-selection problem is the main theoretical challenge and defers the construction to an appendix), so an implementer cannot pick arbitrary coefficients and expect the guaranteed fault tolerance. Cross-rack bandwidth-limited placement (each stripe's coded blocks placed in different racks) is assumed by the paper's reliability model as the source of the 1 Gbps repair bandwidth cap; a placement policy that instead colocates a stripe's blocks within one rack would invalidate that specific numeric cap, though the paper does not re-derive the model under that alternative.
