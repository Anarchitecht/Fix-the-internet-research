### What it does
OverCite distributes CiteSeer, a centralized computer-science research-paper search and citation index, across many volunteer-donated nodes using a distributed hash table (DHT) — peer-to-peer software that lets a set of nodes jointly store and retrieve data without a central coordinator, remaining available under node churn (nodes joining, leaving, or failing). The goal is to let institutions donate spare storage and bandwidth instead of running the whole service on one organization's hardware, while keeping search quality comparable to the centralized system.

Each OverCite node runs up to four components: a DHT process, an index server, a Web crawler, and a Web front-end. The DHT process (the paper uses DHash, a Chord-based DHT) stores every document file, every piece of meta-data, and the full citation graph as key/value pairs in a shared table, so any node can retrieve any object without contacting a specific owning node directly; because OverCite is designed to run on at most a few hundred relatively stable nodes, each DHT node keeps a full routing table and achieves one-hop lookups rather than the O(log n) multi-hop lookups typical of larger DHT deployments. The inverted search index (the data structure mapping search terms to matching documents) is partitioned by document rather than by keyword, into k partitions, so that each document is indexed in exactly one partition; a query is sent in parallel to one server in each of the k partitions, so each server searches only about 1/k of the full index, and the k servers' top-ranked results (by a specified ranking criterion such as citation count) are merged and sorted at the node that received the query from the client. Document-based partitioning is chosen specifically to avoid the expensive join operation a keyword-partitioned index would need to combine multiple keyword's posting lists for a multi-keyword query, and to limit the communication needed when inserting a new document (an insertion only needs to reach the one partition holding that document, rather than every partition holding one of its keywords). The Web crawler coordinates via a shared to-be-crawled URL list stored in the DHT: each crawler process picks a random pending URL, fetches the page, extracts text and citations from any new document found, stores the document, its extracted words, and its meta-data in the DHT, and notifies the other nodes in its own index partition to fetch and index the new document's words. A subset of nodes run the Web front-end, which accepts a query, forwards it to the appropriate partition servers, merges and ranks the returned results, retrieves requested document files from the DHT (optionally converting file formats), and serves them to the user; round-robin DNS spreads client load across the front-end nodes.

### Parameters
- n: total number of participating OverCite nodes; illustrative value 100 used in Chapter 4's calculations (approximating PlanetLab's then-available donated capacity); the Chapter 6 prototype used 11 nodes.
- k: number of inverted-index partitions; illustrative value 20 used in Chapter 4's bandwidth/storage calculations (chosen so only a few nodes index the full text of each new document); the Chapter 6 prototype used k=2.
- f: DHT replication factor (number of redundant fragments/copies DHash stores per block); the paper's calculations use f=2 for content-hash data and separately note f=5 as the DHash default for non-content-hash (mutable) data.
- m: number of top-ranked results each per-partition index server returns per query; b: number of top results the front-end ultimately displays to the user; both set to 30 in the Chapter 6 experiments (m = b = 30), though Chapter 4's bandwidth calculation illustratively uses m=10.
- Document ID (DID) size: 20 bytes, used in the per-query traffic calculation.
- Per-result context/meta-data/rank payload: about 150 bytes, used in the same calculation.
- DHT virtual nodes per physical node: 3 (for load balancing in the Chapter 6 deployment).
- File-download throttling: the deployment throttles outstanding DHash fetch operations; the paper reports both the throttled (stable, 1.2 MB/s plateau) and unthrottled (livelock, throughput collapse) behavior as a direct comparison.

### Stated limitations
The thesis states directly that "a well-funded, professionally-maintained, centralized library service will always have more available resources ... and obtain better performance, than a distributed approach constructed from volunteer resources," framing OverCite's contribution as feasibility, not superiority, at matched resource levels. The implementation described has no working crawler module: the thesis states "the current implementation does not yet include a Crawler module; we have populated OverCite with existing CiteSeer data, and plan to implement a distributed crawler in the future," so every reported measurement operates on data loaded from the existing centralized CiteSeer corpus, not on data OverCite itself discovered and indexed. The evaluation is stated by the authors to be preliminary and small-scale relative to the system's design target: "the scale of the following preliminary experiments is smaller than the expected size of an OverCite system, and the code is currently an early prototype." The CiteSeer-versus-OverCite throughput comparison is explicitly flagged as not a fair or direct comparison, because the CiteSeer mirror served the full repository (over 700,000 documents) on different hardware than the OverCite prototype's 14,755-document, 11-node deployment; the paper states "a more direct comparison is an objective for future work." The file-serving throughput ceiling (1.2 MB/s) and the unthrottled livelock behavior are both stated to be artifacts of running on a small (11-node) DHT specifically, where a large fraction of nodes participates in every block fetch; the paper states this behavior is not expected to persist "once we deploy OverCite on a larger DHT." The thesis lists an unimplemented feature required before full operation: "there remain many ways to improve the system," specifically an automatic document-set reconciliation algorithm between nodes sharing an index partition (proposed future use of Merkle trees for gossip-based synchronization, not implemented), and states the DHT does not natively support storing mutable data under an arbitrary application-chosen key, a feature the authors state they found "essential" and had to work around, and which they recommend future DHT designs include. The one-hop DHT routing design is stated to depend on OverCite running on "a relatively small number of nodes"; the paper notes the underlying Chord lookup protocol it uses is optimized for much larger deployments than OverCite targets, and states a plan (not yet executed) to move to a different lookup protocol, Accordion, designed to perform well at both small and large scale.

### Requirements it places on the rest of the system
Document-based (rather than keyword-based) index partitioning requires every query to be broadcast to all k partition-holding servers in parallel, so query cost scales with the number of partitions regardless of how few keywords the query contains; this is an explicit design tradeoff the paper makes to avoid keyword-partitioning's join cost, not a free choice. The DHT layer must support one-hop lookup for the system's latency assumptions to hold, which the paper states requires every participating node to maintain a full routing table — a requirement that in turn assumes network size stays in "the few hundred volunteer servers" range the design targets, not the scale of a general-purpose global DHT deployment. The system assumes participating nodes are relatively stable and that failed nodes typically return with their disks intact, which the paper uses to justify making the DHT layer "lazy about re-replicating data stored on failed nodes" — a churn model different from one where failed nodes are assumed to be permanently gone or to return with data loss. The meta-data and content tables are stored as generic key/value pairs in one shared DHT keyspace, interpreted by context rather than by an explicit schema, which requires every component reading a given key to already know, out of band, what type of value it should decode there. The crawler's deduplication logic (checking a new document's title, authors, and shingle-level text similarity against existing entries) requires the Titles and Files tables to already be populated and consistent at the time of a new insertion, so insertion order and DHT read consistency directly affect whether duplicate documents are correctly detected. The file-serving throughput result demonstrates that DHT block-reconstruction cost (fetching a threshold number of fragments per block, here 7 of 11 fragment-holding nodes) is not independent of total DHT size: the same erasure-coding-style redundancy parameter that provides fault tolerance on a large DHT concentrates load onto nearly every node when the DHT is small, so a deployment's minimum viable node count is constrained jointly by the replication/reconstruction parameters and by the target per-node fetch rate, not by storage capacity alone.
