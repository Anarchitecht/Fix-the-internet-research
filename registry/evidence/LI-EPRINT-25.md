## [LI-EPRINT-25] A Place for Everyone vs Everyone in its Place: Measuring and Attacking the Ethereum Global Network

**Citation:** Chenyu Li, Ren Zhang, Xiaorui Gong. "A Place for Everyone vs Everyone in its Place: Measuring and Attacking the Ethereum Global Network." Cryptology ePrint Archive, 2025/588.
**Retrieved:** full text via https://eprint.iacr.org/2025/588.pdf
**Source URL:** https://eprint.iacr.org/2025/588.pdf
**Domain:** A

### What it does
The paper measures the Ethereum Global Network (EGN), the single Kademlia-based peer-to-peer overlay that Ethereum's node-discovery protocols Discv4 and Discv5 form, and shows that a design decision to let one overlay serve thousands of distinct blockchain services (Ethereum mainnet and its testnets, forks, and unrelated chains such as BNB Smart Chain, Polygon, and Gnosis) degrades both discovery efficiency and attack resistance for every one of those services. A Discv4 or Discv5 node's routing table (DHT) fills with peers regardless of which service those peers run, because neither protocol's node record carries reliable, mandatory service information: Discv4 servicing is inferred from four fields (protocolVersion, networkID, genesisHash, forkID) that only Ethereum-family services populate, and Discv5's node-record extension for service and topic information exists in the specification but the paper finds it implemented in no deployed client. A node therefore spends most of its discovery messages contacting peers of other services, which reject the resulting application-layer handshake, wasting bandwidth without narrowing the search. The same blending is then shown to weaken a standard node-discovery-table (DHT) pollution attack, described in section 5.1: an attacker who controls a small number of always-responsive nodes sends unsolicited Ping messages faster than the honest liveness-check interval, so its own node records occupy each victim's replacement slots and, once an existing entry fails its own liveness check, get promoted into the victim's bucket proper; the attacker also answers every Findnode request with Neighbors messages listing only its own entries, so its records propagate passively through the rest of the network. Because a blended DHT already holds mostly other-service peers before the attack starts, filling the remaining slots with attacker entries removes almost all of a victim's remaining same-service peers, producing far more nodes cut off from every honest same-service peer (a network partition) than the same attack causes in a hypothetical dedicated (single-service) overlay of the same size.

### Parameters
- Crawler: Nebula, 30-minute crawl duration per iteration (chosen because the newly-discovered-node rate falls to about one per second beyond that duration, which the authors treat as ordinary churn rather than incomplete discovery); each Discv4 node queried with 15 Findnode messages against randomly selected target IDs (bucket-specific queries unsupported in Discv4); each Discv5 node queried with 17 Findnode messages, one per bucket.
- Discv4 liveness-check interval assumed by the attack: 10 seconds; attacker Ping interval: 1 second (chosen shorter than the liveness-check interval to win eviction races).
- Attack scale simulated: 1 to 330 attacker nodes, with the headline results reported at 300, representing under 0.3% of the measured network.
- Outgoing-connection targets in the efficiency experiment: 66 connections for BSC Mainnet and Polygon, 16 for the other four tested services, or a 12-hour timeout, whichever came first.

### Stated limitations
The threat model is explicitly described by the authors as weak: the attacker cannot remove long-term active honest peers from a victim's DHT, because those peers pass periodic liveness checks before eviction, so a node retains full isolation only if all its long-term peers already fall inside the attacker-controlled partition. A node the authors classify as partitioned by their DHT-based definition may still receive new blocks and transactions until its existing application-layer TCP connections close, including a connection that traverses a NAT (network address translator) the DHT-based analysis cannot observe. The DHT composition analysis in section 3.3 is stated to be infeasible for Discv5 for lack of service information; the authors substitute the Discv4 service distribution when calibrating the Discv5-adjacent simulation and state this as an assumption ("we use the service distribution of Discv4 as such information is not available in Discv5"), not a measured Discv5 fact. The simulation-based attack results are not measured on the live network; the paper states the choice to simulate is to avoid disrupting real-world services, and states the simulated environment was checked against the crawler's measurements but does not claim the simulation's absolute partition percentages would reproduce identically against the live network. The authors state they contacted the Ethereum Foundation about the findings and had not received a response at the time of writing.

### Requirements it places on the rest of the system
The attack requires that a node discovery protocol's passive-DHT-maintenance mechanism inserts any node record that pings it into a bucket or replacement slot without verifying the record's claimed service; removing that requirement (mandatory, verifiable service information at the record-insertion step, which is the paper's own section 6 proposal) would prevent the attack described here. The attack also requires that the liveness check interval a client uses (10 seconds in the deployed protocol) exceeds the interval an attacker can sustain a faster Ping rate at; a defense would need either a liveness check faster than any plausible attacker Ping rate or a bound on how quickly one source's record can occupy a replacement slot. Recovery from a network partition, in this paper's own model, depends entirely on some node in the partition retaining a link to a bootnode's DHT or receiving a new join from a node that bridges both sides; a component that manages bootnode routing tables independently of this design (for example, prioritizing same-service peers, the paper's second proposed fix) directly determines the partition-recovery probability this paper measures, so any redesign of bootnode peer selection changes the partition outcome measured here.

### Contradicts
DISC-NG (Krol, Ascigil, Rene, Sonnino, Pigaglio, Sadre, Lange, Riviere, EuroS&P 2024), described in this paper's related-work section as a parallel study addressing Discv5 inefficiency, is stated by this paper's authors to have identified the same low node-discovery-efficiency symptom but not the root cause (EGN's blended, multi-service overlay architecture); this paper states DISC-NG contains no comparison to dedicated single-service overlays and no security analysis. This is the paper's own characterization of DISC-NG, not independently verified against DISC-NG's own text in this entry, since DISC-NG was not part of this extraction batch.
