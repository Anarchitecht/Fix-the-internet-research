## [CASTRO-OSDI-02] Secure Routing for Structured Peer-to-Peer Overlay Networks
**Citation:** Miguel Castro, Peter Druschel, Ayalvadi Ganesh, Antony Rowstron, Dan S. Wallach. "Secure Routing for Structured Peer-to-Peer Overlay Networks." USENIX Symposium on Operating Systems Design and Implementation (OSDI), 2002.
**Retrieved:** full text via https://people.mpi-sws.org/~druschel/publications/security.pdf
**Source URL:** https://people.mpi-sws.org/~druschel/publications/security.pdf
**Domain:** A

### What it does
This paper makes a structured peer-to-peer overlay (a network in which each node holds a small routing table and a lookup for a key is forwarded hop by hop toward the node or nodes responsible for that key) deliver a message to every correct replica root for a key with high probability, even when a bounded fraction of nodes actively try to prevent delivery. It decomposes the problem into three mechanisms, each closing one attack the paper demonstrates against overlays that lack it.

First, certified node-identifier (nodeId) assignment: a set of certification authorities (CAs), which can be offline and uninvolved in day-to-day operation, sign a certificate binding a node's randomly assigned nodeId to its public key and IP address. This stops an attacker from choosing a nodeId, which the paper shows otherwise lets an attacker place itself as the sole custodian of a target key's replicas or as every routing-table entry of a targeted victim.

Second, a constrained routing table alongside the normal proximity-optimized one: every constrained-table slot must hold the live nodeId numerically closest to a publicly computable point in the identifier space, a rule independent of network-measured proximity and therefore not manipulable by an attacker who intercepts or fakes proximity probes. The paper demonstrates that without this constraint, an attacker's routing-table updates propagate malicious entries faster than honest ones do, and derives that the fraction of faulty entries in a node's table after processing one further update is at least (1 − f)·f + f, strictly greater than the starting fraction f, so repeated updates push the faulty fraction toward one.

Third, secure message forwarding: a node routes a lookup using the fast proximity-aware table, then applies a routing failure test to the returned set of prospective replica roots. The test compares the average numerical distance between consecutive nodeIds in the sender's own neighbor set (call it µ_p) against the same statistic computed over the returned prospective root set (µ_rn), because faulty nodeIds cluster less densely than the full honest population would. The set is accepted (test returns negative) only if every certificate in it is valid and µ_rn ≤ µ_p × γ, where γ is a tunable threshold. If the test returns positive, or if no response arrives before a timeout, the sender falls back to redundant routing: it sends r message copies through r different members of its own neighbor set (a technique the paper calls neighbor set anycast for overlays, such as Pastry and Chord, whose replica roots cluster in one node's neighbor set rather than spreading uniformly over the identifier space), collects signed certificates from any node that reports the destination's root in its own neighbor set, and iterates up to three times to assemble the definitive replica set.

The paper's own headline conclusion: the combination of certified nodeIds, constrained routing tables, and the routing-failure-test-plus-redundant-routing primitive "allow us to tolerate up to 25% malicious nodes while providing good performance when the fraction of compromised nodes is small" — stated as the paper's summary claim, distinct from and not identical to any single numbered figure above; treat it as the paper's own qualitative headline, not an additional independent data point.

### Parameters
- f: fraction of nodes in the overlay that are faulty/malicious.
- c: upper bound on the fraction of faulty nodes that can collude (c ≤ 1, and α, β are shown to depend on c but not on f directly).
- γ: routing-failure-test threshold controlling the tradeoff between false-positive rate α and false-negative rate β; values used in experiments range from 1.23 to 1.8 depending on target security level.
- l: neighbor set size (also root-neighbor-set size k in most experiments, k=l); values tested: 16, 32, 64, 128, 256 as sample counts, with l itself tested at 16 and 32 for the end-to-end scenarios.
- n: number of nodeId-distance samples the sender uses to compute µ_p; tested at 32, 64, 128, 256, with 256 used as the paper's primary operating point.
- b: digit base for the routing table (controls table size versus hop count); tested at b=4 (Pastry's typical default) and b=6; Chord is fixed at b=1.
- N: overlay size; tested at 1,000, 10,000, 100,000, and 1,000,000 for the base routing-success model, with 100,000 used for all routing-failure-test and redundant-routing simulations.
- r: number of redundant-routing message copies sent per lookup, set equal to l in the reported experiments.

### Stated limitations
The paper states explicitly that "the security and performance of our techniques was fully evaluated only in the context of Pastry; a full evaluation of the techniques in other protocols is future work" — the CAN, Chord, and Tapestry adaptations described are design sketches, not evaluated implementations. The paper states the routing failure test's own accuracy is undermined by a nodeId suppression attack it identifies as "unavoidable": an attacker can leave the overlay to thin nodeId density near the sender (raising the false-negative rate β) or near the destination root (raising the false-positive rate α), can alternate between the two, and the paper states honest nodes have no way of detecting which mode is in effect. The paper states two further routing-failure-test attacks — collecting certificates of departed nodes to inflate a set's apparent density, and mixing controlled and correct nodeIds within one prospective root set — and offers a mitigating certificate-confirmation protocol but does not fully close either. The paper states its own hop-test variant of checked iterative routing has a high minimum error (≈0.35) because it relies on a single density sample at each hop, and rejects the technique after finding no measurable improvement when combined with redundant routing, attributing the failure to iterative routes being less independent of one another than recursive routes. The paper states it does not have a model for the effect of proximity-manipulation attacks on the locality-aware (non-constrained) routing table, and states only a belief, not a proof, that such attacks are hard to mount for small f. The self-certifying-data reduction the paper proposes does not remove the need for secure routing when inserting new objects, verifying an object's absence, or handling node joins — the paper states these cases still require the full secure routing primitive.

### Requirements it places on the rest of the system
The certified-nodeId mechanism requires an external certification-authority infrastructure whose public keys are distributed out of band (the paper suggests bundling them with node software, as browsers bundle root certificates), and requires a certificate-revocation or reissuance path for any node whose IP address changes, since the paper binds nodeId certificates to IP addresses specifically to block certificate-swapping among colluding attacker-controlled nodes. The constrained-routing-table mechanism requires that the overlay's routing table slots be defined by a public, verifiable function of node identifiers (a point p in the identifier space), which forecloses proximity as the sole neighbor-selection criterion for that table; a system wanting both proximity optimization and this defense must maintain two separate tables, as this paper does. The routing failure test requires every node in a neighbor or root-neighbor set to hold a valid nodeId certificate that the testing node can check, so it depends on the certified-nodeId mechanism as a precondition — the test's stated accuracy figures (the α/β values in the measured-results table) hold only once nodeIds are already unforgeable. Self-certifying data as a way to reduce reliance on secure routing requires an independent per-object integrity mechanism (a content hash or an owner signature) supplied by the application layer, since routing itself does not embed integrity checking; the mutable-object extension the paper sketches additionally requires a Byzantine-fault-tolerant replication algorithm run by the replica group holding the object.
