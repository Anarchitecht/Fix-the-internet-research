## [BENET-ARXIV-14] IPFS - Content Addressed, Versioned, P2P File System (DRAFT 3)
**Citation:** Juan Benet. "IPFS - Content Addressed, Versioned, P2P File System (DRAFT 3)." arXiv:1407.3561, 2014.
**Retrieved:** full text via https://arxiv.org/abs/1407.3561
**Source URL:** https://arxiv.org/abs/1407.3561
**Domain:** C

### What it does
The InterPlanetary File System (IPFS) lets any participating computer publish and retrieve files and other data structures by content — every unit of data is located by the cryptographic hash of its own bytes rather than by a server address — so that the same content can be served by any peer holding it, verified by any receiver without trusting the sender, and deduplicated automatically whenever two objects hold identical bytes. The system is a stack of seven sub-protocols, each independently swappable behind a defined interface, described bottom-up:

Identities: a node's identifier (NodeId) is the cryptographic hash of its public key, generated using S/Kademlia's proof-of-work identity-generation puzzle (a difficulty parameter requiring the hash to have a minimum number of leading zero bits), which raises the cost of an attacker minting many node identities. On connection, peers exchange public keys and verify each peer's claimed NodeId is the hash of the key it presents; a mismatch terminates the connection. Hash values throughout the system are stored in a self-describing "multihash" format (a header naming the hash function and digest length precedes the digest), so the choice of hash function can change over time without breaking compatibility.

Network: transport-agnostic; the paper recommends WebRTC DataChannels for browser connectivity or uTP/LEDBAT (Low Extra Delay Background Transport) elsewhere, with SCTP (Stream Control Transmission Protocol) available for reliability atop transports that lack it, ICE (Interactive Connectivity Establishment) for NAT (Network Address Translation) traversal, and optional per-message integrity (hash checksum) and authenticity (HMAC keyed to the sender's public key) checks. Addresses are stored in a self-describing "multiaddr" format that names the protocol stack used to reach a peer, so IPFS does not assume IP (Internet Protocol) reachability and can run over overlay networks.

Routing: peers locate other peers' network addresses and locate which peers can serve a given content-addressed object using a distributed hash table (DHT) that combines S/Kademlia's Sybil-resistant identity generation and disjoint-path lookups with Coral's design of storing peer references rather than the data itself at DHT-selected nodes. Objects of 1 KB or smaller are stored directly in the DHT as values; larger objects are represented in the DHT only by the NodeIds of peers who can serve them, retrieved by a `FindValuePeers` call, avoiding the storage and bandwidth cost of forcing "nearest" DHT nodes to hold data they may not need, a design property the paper attributes to Coral. The routing interface (`FindPeer`, `SetValue`, `GetValue`, `ProvideValue`, `FindValuePeers`) is stated as swappable for any component implementing it, e.g., a static hash table in a local, non-churning network instead of a DHT.

Exchange (BitSwap): a block-trading protocol modeled on BitTorrent but operating across all files a node holds rather than within one torrent's swarm — a node's `want_list` and `have_list` can be satisfied by blocks unrelated to any single file. Each pair of connected peers keeps a ledger of bytes sent and received; the debt ratio `r = bytes_sent / (bytes_recv + 1)` feeds a sigmoid function `P(send | r) = 1 − 1/(1 + exp(6 − 3r))` giving the probability a node sends a requested block to a debtor peer, so the willingness to send falls off as a peer's owed debt to the sender grows, described by the paper as providing leniency to established trust relationships and resistance to both freeloading and Sybil node creation. A node declining to send a block to a peer subsequently ignores that peer for a cooldown period (default 10 seconds) so the peer cannot simply retry to game the probabilistic decision. Ledgers are exchanged and compared when a connection activates; a mismatch resets the ledger to zero for both parties, discarding accrued credit or debt, which the paper notes a malicious node could exploit to erase its own debt (at the cost of also erasing any accrued trust). A node holding nothing its peers want seeks pieces its peers want at lower priority than its own wants, incentivizing caching and dissemination of rare pieces even when not immediately useful to the caching node.

Objects: content-addressed immutable objects form a Merkle directed acyclic graph (DAG) — a generalization of Git's object model in which any object's links to other objects are themselves cryptographic hashes embedded in the linking object, so tampering with any linked object changes its hash and is detected by whichever object refers to it. Each object carries an array of named links (each link naming a target hash and target size) plus an opaque data field whose format is entirely application-defined, so IPFS can transport arbitrary data structures — key-value stores, relational databases, linked-data triple stores, publishing systems, or blockchains — without needing to understand their internal format itself, while still being able to list an object's references, resolve string path lookups by walking the link table one component at a time, and recursively enumerate every object reachable from a root. There is no global root object; instead, every path begins with a specific object's hash, and the same descendant object is reachable via multiple equally valid paths rooted at any of its ancestors. Objects can be optionally wrapped for encryption or signing; an `EncryptedObject` or `SignedObject` frame changes the wrapped object's hash (defining a distinct object identity), and encrypted links make traversal past that point impossible without the corresponding decryption key, so a parent object can be encrypted under one key while a child is encrypted under a different key or left unencrypted.

Files: a Git-inspired object model of `block` (a variable-size chunk of data), `list` (a collection of blocks or other lists), `tree` (a collection of blocks, lists, or trees, used to model directories), and `commit` (a version-history snapshot of a tree) objects, layered on top of the general Merkle DAG. Because commits and their ancestor trees remain reachable through hash links, every prior version of a filesystem tree stays retrievable and the full change history is recoverable directly from the object graph, without a separate version-history store. Large files are split into blocks and lists using one of three interchangeable strategies the system offers rather than mandates: Rabin fingerprinting (as used in the Low-Bandwidth File System, LBFS) to choose content-defined block boundaries, the rsync rolling-checksum algorithm to detect which blocks changed between versions, or a user-supplied block-splitting function tuned to a specific file type.

Naming (IPNS, the InterPlanetary Name Space): because Merkle DAG objects are immutable, a mutable pointer scheme is layered on top so that new content can be found at a stable path. Every node is assigned the mutable namespace `/ipns/<NodeId>`; the node publishes an object to that path signed with its private key, and the object is itself published as an ordinary immutable IPFS object whose hash is then stored in the DHT as the value associated with the node's NodeId (`routing.setValue(NodeId, <object-hash>)`), so retrieving `/ipns/<NodeId>` means looking up that DHT value, fetching the referenced object, and checking its signature against the public key implied by the NodeId — this construction is drawn from the Self-Certifying File System (SFS) naming scheme. Because hash-based names are not memorable, the paper layers human-friendly naming on top: peer links (one user's namespace linking directly to another's, forming a web of trust), DNS TXT records mapping a domain name to an IPNS path, Proquint pronounceable encodings of a hash, and third-party name-shortening services analogous to DNS/URL shorteners today.

### Measured results
This paper reports no experiments, benchmarks, or deployment measurements of IPFS itself. Every performance-relevant number in the retrieved text is either a design parameter (e.g., the 1 KB DHT direct-storage threshold, the BitSwap sigmoid coefficients, the 10-second default ignore-cooldown) or a figure the paper attributes to a different, cited system: Kademlia's expected `⌈log2(n)⌉` lookup hops (e.g., stated as 20 hops for a 10,000,000-node network, attributed to Maymounkov and Mazières' Kademlia paper) and S/Kademlia's stated 0.85 lookup success rate at up to 50% adversarial nodes using disjoint-path lookups (attributed to Baumgart and Mies' S/Kademlia paper, matching this corpus's own already-verified S/Kademlia entry). Per Rule 1 of this extraction protocol, neither of these cited figures is recorded here as a result of this paper, because this paper did not produce them. The registry's own citation note for this key states that measured deployment behavior for IPFS is covered by a separate paper in this corpus (Trautwein et al., SIGCOMM 2022), not by this design document.

### Parameters
- DHT small-value storage threshold: objects ≤ 1 KB stored directly as DHT values; larger objects stored in the DHT only as peer references (NodeIds of peers able to serve the block).
- BitSwap sending-probability function: `P(send | r) = 1 − 1 / (1 + exp(6 − 3r))`, where `r = bytes_sent / (bytes_recv + 1)` is the debt ratio between two peers; the paper states this sigmoid "works in practice" but explicitly leaves broader exploration of the BitSwap strategy space as future work.
- BitSwap ignore cooldown after a declined send: default 10 seconds.
- S/Kademlia identity-generation difficulty: an integer parameter controlling the minimum number of leading zero bits required in a candidate NodeId's hash before it is accepted; no specific numeric value is given in this paper (the underlying scheme is cited to Baumgart and Mies).
- File-splitting strategy: not a fixed parameter but a choice among three interchangeable mechanisms (Rabin fingerprinting, rsync rolling checksum, or a user-supplied function), left to the application.

### Stated limitations
The paper states BitSwap's strategy-selection function (which peer to send to, and how much) is unexplored design space: "The exploration of the space of such strategies is future work," with the sigmoid function offered only as one choice that "works in practice." The paper states a token/currency-based BitSwap strategy is a natural extension but is deferred: "This can be implemented as a BitSwap Strategy, and will be explored in a future paper," and such a system would additionally require a global ledger to track currency ownership and transfer, which the paper does not design. The paper states BitSwap's ledger-reset-on-mismatch behavior is exploitable: "It is possible for malicious nodes to purposefully 'lose' the Ledger, hoping to erase debts," noting the mitigating factor that doing so also discards any trust the malicious node had accrued, and that a partner peer may treat the mismatch as misconduct and refuse to trade, without the paper specifying any protocol-level defense beyond that discretion. The paper states path-based lookups carry "considerable overhead" because each path component requires a DHT lookup, peer connection, and block retrieval, mitigated only by two unevaluated techniques (indefinite tree caching, since hash-addressed objects never change, and constructing a flattened tree that lists every object reachable from a root in one structure) rather than by a measured fix. The paper states object encryption is entirely optional and application-controlled, so IPFS's own content-addressing and deduplication properties do not by themselves provide confidentiality; a parent and child object can be encrypted under different keys or not at all, and traversal past an encrypted link fails without the corresponding key, meaning the same data uploaded unencrypted by two different users deduplicates while encrypted data generally will not (the paper does not measure this effect but the mechanism described implies it).

### Requirements it places on the rest of the system
Requires every participating node to provide local storage (disk or, for non-persistent caches, RAM) in which retrieved blocks are held, because "all blocks available in IPFS are in some node's local storage" and there is no other persistence layer; a node with no local storage cannot serve content it does not currently have live in a network buffer. Requires an explicit pinning operation for any object a node wants to guarantee will survive local garbage collection or cache eviction — the paper describes an object as durably available in the network only if some node pins it (optionally recursively, covering its descendants), so content whose only copies are held unpinned, transiently, by nodes that fetched it as a caching side effect is not guaranteed to persist; the mechanism supplies no default retention policy beyond what participants choose to pin. Requires the DHT/routing layer to remain reachable and correctly answer `FindValuePeers` queries for any large object to be locatable at all, since large objects are represented in the DHT only by peer references, not by their content; if no peer that both holds the object and has announced itself via `ProvideValue` is discoverable through routing, the object is unretrievable regardless of whether some node still holds its bytes. Requires BitSwap's debt-ratio incentive mechanism to be paired with a strategy that a deployment separately selects and tunes, since the paper's own default sigmoid is presented as an example rather than a specified, evaluated default. Requires the naming layer (IPNS) to depend on the same DHT/routing layer for its only mutable-state distribution path — publishing a new value at `/ipns/<NodeId>` means writing to the routing system's key-value store, so if routing is partitioned, degraded, or attacked (e.g., an eclipse or Sybil attack against the DHT), name resolution degrades along with it even though the underlying immutable objects remain independently fetchable by hash. Requires every consumer that verifies an IPNS record to independently confirm the signature against the public key implied by the claimed NodeId, since the mutable pointer itself carries no other authenticity guarantee.
