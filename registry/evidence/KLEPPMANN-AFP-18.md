## [KLEPPMANN-AFP-18] OpSets: Sequential Specifications for Replicated Datatypes
**Citation:** Martin Kleppmann, Victor B. F. Gomes, Dominic P. Mulligan, Alastair R. Beresford. "OpSets: Sequential Specifications for Replicated Datatypes." Archive of Formal Proofs, 2018. Extended version also at arXiv:1805.04263.
**Retrieved:** full text via https://arxiv.org/abs/1805.04263
**Source URL:** https://www.isa-afp.org/entries/OpSets.html ; https://arxiv.org/abs/1805.04263
**Domain:** D

### What it does
OpSets (Operation Sets) give a way to state precisely which final states a replicated data structure — a data structure held as a separate copy on each of several nodes and updated independently — is allowed to reach after a set of concurrent edits, going beyond the weaker guarantee that copies merely converge to agreement without saying what they agree on. A node holds an OpSet: a set of immutable operation records, each carrying a globally unique, totally ordered identifier (an identifier can be a Lamport timestamp — a pair of a locally incrementing counter and a node identifier, compared first by counter then by node identifier, so any node manufactures a fresh identifier without coordinating with any other node). Two nodes exchange operations as messages and merge OpSets by plain set union, which is commutative, associative, and idempotent, so applying the same operations in a different arrival order or with duplicates or reordering still yields the same OpSet. An interpretation function reads an OpSet and produces the current state of the data structure by applying every operation once, strictly in ascending identifier order, starting from a fixed initial state; because this function is pure (deterministic, no side effects) and depends only on the OpSet's contents, any two nodes holding the same OpSet compute the same state regardless of the order operations physically arrived in. On top of this mechanism the paper specifies composable datatypes — maps, sets, lists, text (a list of characters), graphs, and trees — as a single relation-based object graph: an element relation E holding (operation-id, object-id, key, value) tuples and a list-order relation L holding predecessor-successor pairs, with each insert-after or assign operation adding or overwriting tuples in E or L. A concurrent-move operation on trees is specified as a redefinition of the assign operation: an assign whose target value is already an ancestor of the destination object is dropped (this alone prevents cycles), and an assign that would give an object two parents instead first removes any existing tuple in E referencing that value (this preserves the one-parent-per-node tree invariant) — evaluating this precondition at interpretation time, not at the time the operation was generated, is what lets concurrent moves resolve deterministically without acquiring a lock.

### Measured results
This paper reports no runtime performance measurements, no simulation, and no deployment data — its results are machine-checked mathematical theorems, not measured figures, so no entry in the four-rules sense (a number with experimental conditions) applies. The stated results are: (1) the OpSet list specification, formally proved in Isabelle/HOL (a proof assistant for machine-checked mathematics), rules out interleaving of two users' concurrently inserted character sequences at the same position — the merged result contains one user's whole sequence immediately followed by the other's, never an interleaving of the two; (2) the RGA (Replicated Growable Array) list CRDT is proved, in Isabelle/HOL, to satisfy this no-interleaving list specification; (3) the Logoot and LSEQ list CRDTs are proved not to satisfy it, and the paper additionally reports informally observing this interleaving anomaly occurring when running open-source implementations of Logoot and LSEQ, without stating how many trials, what input, or on what platform — this observation is not a quantified measurement and is recorded as unusable for the schema's Measured Results table; (4) the OpSet list specification is proved, in Isabelle/HOL, to be strictly stronger than the "Astrong" collaborative-text-editing specification of Attiya et al. (PODC 2016) — every algorithm satisfying the OpSet list specification also satisfies Astrong, but Astrong permits character interleaving that the OpSet specification forbids; (5) the tree-with-atomic-move specification is proved never to produce a cycle and never to give a node two parents, for arbitrary concurrent move operations, without requiring any lock or globally synchronized coordination step.

### Parameters
None in the empirical sense — the paper defines no tunable numeric parameter (no buffer size, timeout, replication factor, or similar). The one structural choice stated is the total order used for operation identifiers: the paper uses Lamport timestamps (counter, node-id pairs) ordered lexicographically by counter then by node identifier, and states this is one sufficient choice among possible schemes for generating unique, totally ordered identifiers without coordination.

### Stated limitations
A naive OpSet interpretation that recomputes the full data-structure state by replaying every operation in order from the initial state on each read "may exhibit poor performance," in the paper's words, because a node may need to reapply the same operations repeatedly; the paper states more efficient algorithms can be developed and shown to satisfy the specification (as it does for RGA) but does not itself supply or measure such an algorithm for the tree-with-move datatype. The paper explicitly does not resolve which of two symmetric outcomes a conflicting concurrent tree move should produce beyond "the move operation with the greater ID determines the item's final location" — an arbitrary, ID-based tie-break, not a semantically motivated choice. Practical implementation details of a JavaScript CRDT built around the OpSet model are stated to exist but are stated to be "beyond the scope of this paper," so no implementation or deployment evidence for that system is given here. The paper states an unproved hypothesis, not a result: that a commutative (rather than sequential-replay) tree-move CRDT can be derived from the OpSet specification in the paper, usable for a distributed peer-to-peer file system — labeled explicitly as future work. A second unproved hypothesis is stated: that materialized-view-maintenance techniques from database theory could be applied to make OpSet interpretation incremental rather than full-replay; also labeled future work, with no supporting proof or benchmark in this paper.

### Requirements it places on the rest of the system
The specification requires every operation to carry a globally unique identifier from a total order, generated locally without any node needing to coordinate with any other node to obtain it; a system supplying only per-node monotonic counters without a tie-breaking node identifier would not satisfy the uniqueness requirement. It requires the underlying transport to guarantee, at minimum, eventual reliable delivery of every operation to every node — the paper explicitly tolerates arbitrary reordering, duplication, and transient loss of messages (with retransmission assumed for lost messages, "e.g. using TCP"), but a message that is permanently lost and never retransmitted leaves the receiving node's OpSet permanently short of an operation the sender applied, which the specification does not detect or repair. It requires the interpretation function to be pure: deterministic and free of side effects, computing its result from the OpSet's contents alone — any operation whose effect depends on wall-clock time, on random input, or on state outside the OpSet breaks the convergence guarantee the whole approach rests on. The specification does not require, and explicitly contrasts itself against, an atomic broadcast or total-order broadcast protocol (which the paper states is equivalent to solving distributed consensus and requires communication with a quorum of nodes to make progress) — a system built on OpSets must not require quorum availability to accept a local write, and any consensus layer placed underneath would defeat the property the paper is built to provide (local, always-available reads and writes even while a node is offline or partitioned). For the tree-move specification specifically, every node must apply the assign-based move interpretation over the full OpSet each time state is computed, evaluating the ancestor-cycle precondition at interpretation time rather than caching a stale precondition computed when the operation was first generated — a system that evaluates the precondition once, at generation time, and caches the result would reintroduce the possibility of cycles that this specification is built to rule out.

### Contradicts
The paper's own Theorem 1 contradicts a claim commonly associated with the Astrong specification of Attiya et al. (PODC 2016): Astrong is often treated as a sufficient correctness condition for collaborative text editing, but the paper proves algorithms satisfying Astrong (including Logoot and LSEQ) can still interleave two users' concurrent insertions into an unreadable jumble, so satisfying Astrong alone does not rule out this failure mode. Cross-reference within this corpus: KLEPPMANN-PAPOC-19 (a companion paper by the same authors) restates and extends this same interleaving result in a shorter form and states which algorithms are and are not subject to it; the two entries should be read together, not treated as independent confirmations, since PAPOC-19 draws on the same underlying analysis. None found — no measurement in this batch's other entries speaks to CRDT specification correctness.
