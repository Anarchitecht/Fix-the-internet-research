## [COX-SOSP-03] Samsara: Honor Among Thieves in Peer-to-Peer Storage
**Citation:** Landon P. Cox, Brian D. Noble. "Samsara: Honor Among Thieves in Peer-to-Peer Storage." ACM SOSP, 2003. DOI 10.1145/945445.945458.
**Retrieved:** full text via https://courses.cs.duke.edu/fall05/cps296.1/papers/samsara-sosp03.pdf
**Source URL:** https://courses.cs.duke.edu/fall05/cps296.1/papers/samsara-sosp03.pdf
**Domain:** I

### What it does
Samsara forces a node that requests storage from a peer to consume no more space than it contributes, without a trusted third party, a currency system, or a certified identity. It converts every asymmetric storage relationship into a symmetric one. When node A stores an object on node B, B must in return hold a claim from A: a placeholder block equal in size to the space B consumed, computed so that A can prove it is physically stored but B never has to store a local copy to verify it. A claim is built from a chain of SHA1 hashes seeded by a secret passphrase P and a private symmetric key K: the storage space is logically filled with hash values h_i = SHA1(P, i), and a claim C_i is the encryption under K of 26 consecutive hash chunks (25 full 20-byte hashes plus the first 12 bytes of the 26th). Because the claim is derived from a keyed hash chain, the claim owner (A) can recompute it on demand without storing it, while the holder (B) can produce it only by actually having reserved the corresponding space. Each side periodically queries the other to confirm the exchanged data or claim is still held: the querying node sends an initial value h0 and a list of n objects to verify, and the responder chains h0 through each object with SHA1 (h1 = SHA1(h0, object1), h2 = SHA1(h1, object2), and so on) and returns only the final hash h_n, so verification costs one hash value in bandwidth regardless of how many objects are checked. A node that fails a query is punished probabilistically rather than immediately: each replica site independently discards the failed node's object with probability p_i, where p_i = (1/(r−i+1))^(r−i+1) for the i-th consecutive failed query and r is the system's normative replication factor, so an honest node with a transient outage loses at most a fraction of its replicas and can rebuild from survivors, while a node that keeps failing queries loses data at a rate that grows super-exponentially with consecutive failures. When local storage runs short, a node reduces its claim-storage overhead by claim forwarding: it replaces the claim it is holding for a downstream peer with a claim it itself is owed from an upstream peer, extending a dependency chain; if a forwarded claim eventually returns to the node that originally issued it, a dependency cycle forms and the claim is removed from the system entirely, restoring space with no loss of enforcement.

### Parameters
- Claim size: 4,096 bytes (implementation default).
- Replication factor r: 4 in the simulation study; r=5 used in the worked probability examples in the design section.
- Discard probability for the i-th consecutive failed query: p_i = (1/(r−i+1))^(r−i+1); tested against r = 5, 6, 7, 10 in the analytic figure.
- Pastiche node's assumed object population for the worked examples: 2,000,000 objects, about 32 GB of state.
- Query response hash: SHA1, 20-byte hash chunks.
- Symmetric encryption key K and passphrase P: node-local secrets, sizes unspecified beyond hash-chunk boundaries.
- Storage utilization tested: 50%, 57%, 67%, 80%, 100% (space-overhead and chain-length experiments); 50% and 80% (reliability-vs-utilization experiment).
- Permanent node failure rate tested: 1%, 2%, 4%, 8%, 16%.
- Chain-forwarding caps tested in the reliability-vs-chain-length experiment: 1, 2, 4, 8, unlimited.

### Stated limitations
The authors state Samsara targets greedy users, not arbitrarily malicious ones, and does not stop a node that promises to store data and then immediately discards it, nor prevent a node from refusing service once it detects a restore is in progress. Samsara enforces that consumption is matched by an equal claim but does not force a node to ever accept storage requests from others: if every node refuses to store anything but the claims it receives, no data is ever stored anywhere. The claim-and-query mechanism is stated to apply only to non-renewable resources such as storage and memory; the authors say they cannot see how to build an equivalent placeholder for a renewable resource such as bandwidth or processor cycles, because monitoring the resource's use would itself consume it. Forwarding weakens reliability for as long as a chain stays open, and the authors state it is unclear how to induce claim cycles (which restore reliability) without either constraining replica-site choice or first creating a chain; they list this as an open direction. The reliability simulations are stated to be pessimistic because they model every failure as permanent, whereas the cited failure-rate study found permanent failures far less frequent than transient ones. The implementation's free-space lists are described as linearly searched and single-level, with no fragmentation handling or placement optimization, and all stores are whole-object grained rather than claim-block grained.

### Requirements it places on the rest of the system
Samsara requires that objects are replicated across multiple independent sites so that a probabilistic per-replica discard on a failed query does not destroy the only copy of an object; the punishment mechanism assumes replication is already the availability strategy, not an add-on. It requires periodic bidirectional querying between every pair of nodes in a storage relationship (the querying schedule in the paper's worked example runs daily for the first three days, then weekly), so it needs a live channel between peers and a component that keeps track of who currently holds a claim for whom (Samsara's location, storage, and replica lists). It assumes an underlying storage-placement layer (in the paper, Pastiche over Pastry) decides where replicas go; Samsara sits below that layer and does not perform lookup or routing itself, so it requires the calling storage system to supply replica-site selection. It assumes each node behaves honestly toward its own interest in retaining its own data — a node forwarding a claim remains liable for it, so correctness of the incentive depends on the assumption that a node protects its own stored objects by punishing failures on claims it is holding, not on any external auditor. It does not require certified identity or a public-key infrastructure for its core exchange, but its Sybil-attack resistance argument (an alias gains no advantage from a forwarded claim because it must still produce the claim on demand) depends on the object-storage mechanism, not the identity layer, carrying that guarantee.

### Contradicts
None found within this corpus. The paper's own related-work section distinguishes its no-identity, no-payment, no-symmetry design from CFS, PAST, Cooper's data trading, Ngan's audit-based accounting, Fileteller's micropayments, and SHARP, each of which requires certified identity, symmetric placement, or a trusted clearance/authentication step Samsara does not need; these are the authors' own comparisons, not measurement disagreements.
