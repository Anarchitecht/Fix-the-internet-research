## [EVERSPAUGH-USENIXSEC-15] The Pythia PRF Service
**Citation:** Adam Everspaugh, Rahul Chatterjee, Samuel Scott, Ari Juels, Thomas Ristenpart. "The Pythia PRF Service." USENIX Security Symposium, 2015. Pages 547-562.
**Retrieved:** full text via https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-everspaugh.pdf
**Source URL:** https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-everspaugh.pdf
**Domain:** I

### What it does
Pythia is a network service that evaluates a pseudorandom function (PRF, a keyed function whose output is indistinguishable from random to anyone without the key) on a client's behalf, so a client can harden a low-entropy secret such as a password without storing the PRF key itself and without letting an offline attacker who steals the client's database brute-force the secret. The service introduces a partially oblivious PRF (PO-PRF): the client's PRF input splits into a tweak t, which the client reveals to the server in the clear, and a message m, which stays hidden from the server through cryptographic blinding. The server evaluates F_kw(t, m) = e(H1(t), H2(m))^kw, using an admissible bilinear pairing e over three prime-order groups G1, G2, GT and two hash-to-group functions H1, H2 modeled as random oracles; kw is an ensemble key derived as kw = HMAC(msk, K[w]) from a server-held master secret key msk and a per-client table entry K[w]. The client blinds m by sending x = H2(m)^r for a random exponent r, the server returns y = x^kw together with a proof pi that the same discrete logarithm relation holds between a public commitment p_w = g^kw and the pair (x, y), and the client checks the proof, then unblinds by computing y^(1/r) to recover F_kw(t, m). Revealing t to the server, while hiding m, is what lets the server rate-limit or flag repeated queries against a specific account or key selector without learning the password or message being hardened. The construction supports key rotation: because kw is HMAC-derived from a table entry K[w], the server can issue a compact update token that rolls previously computed PRF outputs forward to a freshly generated K[w] without the client needing to resubmit every prior message, and rotating the entire master secret msk works the same way, one compact update token per active ensemble. An unblinded variant exists for deployments that do not need message privacy: the client sends m directly and the server computes H3(t‖m) using a single elliptic-curve group instead of a pairing, at the cost of losing message secrecy but keeping verifiability and key rotation.

### Parameters
- Pairing curve: Barreto-Naehrig 254-bit prime order curves (BN-254), chosen to provide approximately 128 bits of security.
- Security parameter n for symmetric key lengths: the paper states a typical choice of n = 128.
- Server stack: nginx web server, uWsgi application gateway, Django backend module implementing PRF-Srv in Python, MongoDB for the key table and rate-limiting records, Relic cryptographic library (C) with a Python wrapper.
- Test hardware: Amazon EC2 c4.xlarge instance, 8 virtual CPUs (Intel Xeon, third generation, 2.9 GHz), 15 GB RAM, SSD storage, Ubuntu 14.04; LAN client also a c4.xlarge instance; WAN client an Intel Core i7 3.4 GHz at University of Wisconsin-Madison.
- Example rate-limiting policy tested: tiered limit of 10 queries per hour per account and 300 per month, at hour-granularity expiry.
- Password-onion login latency budget used in the paper's worked example: T = 300 ms.

### Stated limitations
The paper states a formal proof of security for the full one-more pseudorandomness notion is deferred to the full version of the paper and is not obtained within this paper for every claimed property; only one-more unpredictability (sufficient for applications where the PRF output is used as an unforgeable credential rather than stored, such as the brainwallet application) is proved in the paper's own appendix. The paper's PO-PRF construction relies on a new, unproven-in-prior-literature hardness assumption the authors introduce, a one-more bilinear computational Diffie-Hellman assumption, stated as "to the best of our knowledge this assumption is new." The rate-limiting mechanism depends entirely on the tweak t being learned by the server; the paper's own related-work analysis states that any oblivious-PRF or blind-signature variant that also hides t "does not allow granular rate limiting" because the server cannot verify that a query's tweak matches the one it was told, so attackers can bypass rate limits by lying about which account a blinded query targets. The client-side denial-of-service risk: because Pythia performs per-tweak rate limiting, an attacker who can associate a specific tweak with a target user gains a vector for locking that user out; the paper states this is mitigated in the brainwallet application only because Bitcoin addresses are not directly usable as the tweak. The forward-secrecy guarantee from key rotation is explicitly conditioned on the old key and update token being completely erased after rotation; the paper does not measure or verify this erasure occurring on real storage media. The paper's WAN latency figures (389-403 ms cold) are dominated by TLS/TCP connection setup, not by Pythia's own computation, and the paper states straightforward engineering fixes (TLS session resumption, QUIC, or a custom UDP protocol) were not implemented or measured in this evaluation, only proposed.

### Requirements it places on the rest of the system
Pythia requires the client to already possess a per-client key selector w (an "ensemble" identifier) established through an out-of-band Init call, and requires that selector, together with a server-held table entry K[w], to be treated as long-term state the server must retain and be able to update; loss of this table by the client or corruption at the server changes which PRF outputs subsequently verify. It requires the tweak t to be chosen by the client such that it is exactly the granularity at which the calling application wants rate limiting applied (the paper's example uses a per-account salt as t), because the server can rate-limit only at the granularity of distinct tweak values it observes, not at any finer or coarser grain. It requires an authenticated channel or process for the client to request key rotation (the paper's Reset call takes an authtoken) to prevent an attacker from forcing a spurious rotation that discards a legitimate client's stored ensemble key. It requires whatever system stores the client's own PRF-derived values (the paper's password-onion example) to track a version marker per stored entry so it knows whether that entry has already received a pushed key-update token, since updates can run concurrently with normal logins rather than under a database lock. The construction assumes the decisional bilinear Diffie-Hellman-family hardness assumption holds in the chosen pairing group and that H1, H2 behave as random oracles; a system substituting a non-pairing-friendly group or a different hash construction cannot reuse the stated security proof.
