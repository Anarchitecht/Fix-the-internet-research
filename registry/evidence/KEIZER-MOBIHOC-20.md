## [KEIZER-MOBIHOC-20] Rewarding Relays for Decentralised NAT Traversal Using Smart Contracts
**Citation:** Navin V. Keizer, Onur Ascigil, Ioannis Psaras, George Pavlou. "Rewarding Relays for Decentralised NAT Traversal Using Smart Contracts." ACM MobiHoc, 2020. DOI 10.1145/3397166.3412799.
**Retrieved:** full text via https://discovery.ucl.ac.uk/id/eprint/10108564/
**Source URL:** https://doi.org/10.1145/3397166.3412799
**Domain:** L

### What it does
This paper supplies unreachable peers (those behind a Network Address Translator, NAT, that ordinary hole punching cannot traverse) with a relay path staffed by other network participants, using an Ethereum smart contract to enforce that a relay is compensated in proportion to the service it actually delivers, without a centralized relay operator. The mechanism has three parts. First, Proof of Timely Relay (PoTR): a client C selects two relay nodes for one relay session, a working relay R_A that forwards the actual data and a check node R_C used only for verification. A peer P sending data to C sends the payload through R_A and, at the same time, sends a hash of the data chunk plus a transmission-start timestamp to R_C, which forwards that hash-and-timestamp to C separately; C compares the hash-and-timestamp report against what R_A actually delivered to detect added delay, altered data, or dropped packets, without trusting R_A's own report of its performance. Second, a smart contract deployed on the Ethereum blockchain records a negotiated agreement between C and R_A — a minimum Quality-of-Service (QoS) threshold (drawn from latency, packet-drop rate, or throughput), an evaluation-interval length, a deposit from C that funds the relay credit, a payment-rate function mapping observed QoS to a payment amount, and a timeout duration — and both C and R_A submit a mutual trust score (1 for satisfactory, 0 otherwise) to the contract when the agreement terminates; the contract releases payment to R_A and returns the remaining deposit to C only once both trust scores are recorded, so refusing to submit a score blocks payment for both sides and creates an incentive for both parties to participate honestly in scoring. Third, a reputation system built from the trust-score history stored on-chain: any node can query the blockchain for another node's prior transaction count, trust scores, contract duration, and QoS scores, and each node applies its own local scoring policy over these historic values to rank candidate relays before contracting one, rather than relying on a globally computed or centrally published reputation number.

### Parameters
- PeerSim simulation network size: 100,000 nodes, each with a boolean maliciousness flag; all nodes act as both client and relay.
- Neighbor sample size per discovery cycle: k=5.
- Combined scoring function ratio found best-performing: 1:4:5 (QoS:trust:duration).
- Trust score values: binary, 1 (satisfactory) or 0 (unsatisfactory); a node scored 0 does not go negative, to remove any advantage from leaving and rejoining with a new identity.
- Smart contract negotiated parameters per agreement: minimum QoS promise (from latency, packet-drop rate, or throughput), evaluation-interval time, deposit amount, payment-rate function parameters, timeout duration — none given fixed numeric defaults in the paper; the paper states these should be application-specific and leaves their concrete selection to the developer or to future work.
- Payment-rate function: proposed as a negative exponential function of QoS score, with the paper stating it leaves the specific function parameters and further exploration to future work.

### Stated limitations
The paper states the system requires network synchrony — constant blockchain monitoring by both parties — as a drawback of using the smart contract as a mediating trusted third party, and simplifies its own analysis by assuming all nodes maintain a stable connection to the Ethereum blockchain. The paper states the payment-rate function is left largely unspecified: "due to space limitations we leave the further details of the payment rate functions for the future work." The dishonest-scoring attack (a node scoring another dishonestly to reduce a competitor's reputation) is analyzed only qualitatively; the paper states there is "no direct loss" for scoring dishonestly under the current design and explicitly defers "further exploration of this mechanism and trade-off for future work." Peer discovery — how an unreachable client actually locates nearby candidate relay nodes before applying the reputation scoring — is stated as unimplemented: the paper lists flooding, location-based server registration, and application-level anycast as options and states "further details of this is left for future work." The paper's cost evaluation was run on a private virtual blockchain (Ganache), not Ethereum mainnet, and the reported USD costs are pinned to April 2020 Ether-to-USD conversion rates and gas-price estimates, which the paper does not claim generalize to other periods. The paper states relay selection under the proposed system, in the best case, should outperform centralized relay solutions in latency, but reports no direct latency measurement against a centralized-relay baseline — the claim is stated as a design goal in Section 3, not validated as a measured result in Section 5.

### Requirements it places on the rest of the system
The Proof of Timely Relay mechanism requires the client to have simultaneous, independent contact with two separate relay-capable nodes for every relay session — a working relay and a check node — so a network with too few reachable, relay-capable nodes near a given client cannot supply the second, independent verification path this mechanism depends on. The smart-contract payment-release logic requires both parties to submit a trust score before either receives its settlement, so a system adopting this mechanism must accept that an unresponsive party blocks payment until the stated timeout duration elapses, at which point only the calling party's payment is settled and the unresponsive party automatically receives a negative trust score. The reputation system requires an append-only, publicly queryable transaction ledger (a blockchain) recording every past agreement's negotiated parameters and both parties' trust scores, so any system without persistent, tamper-evident, publicly readable transaction history cannot reproduce this reputation mechanism as described. Because gas costs are incurred per on-chain function call, the paper's cost model assumes clients contract with the same relay repeatedly over time rather than renegotiating per transfer; a usage pattern with frequent relay switching would incur the deployment- and agreement-setup gas costs more often than this paper's cost estimate assumes. The threat model assumes malicious actors are rational (motivated by resource gain, principally bandwidth oversubscription, rather than by an intent to damage the network at a loss to themselves); the paper's own security analysis states this assumption explicitly and does not evaluate the system against an irrational or purely destructive adversary.
