## [LOO-IPTPS-04] The Case for a Hybrid P2P Search Infrastructure
**Citation:** Boon Thau Loo, Ryan Huebsch, Ion Stoica, Joseph M. Hellerstein. "The Case for a Hybrid P2P Search Infrastructure." IPTPS, 2004. DOI 10.1007/978-3-540-30183-7_14.
**Retrieved:** full text via http://www.huebsch.org/papers/IPTPS04.pdf
**Source URL:** http://www.huebsch.org/papers/IPTPS04.pdf
**Domain:** B

### What it does
The mechanism routes a query to query broadcast (query flooding) or to a distributed hash table (DHT) depending on whether the sought item is popular or rare, so the network avoids both the high response-time cost query broadcast incurs for rare items and the high publishing bandwidth a DHT incurs for popular items. A DHT-based search publishes a copy of each document's identifier into an inverted index (a posting list per keyword) stored across the DHT, then answers a query by routing to the nodes holding each keyword's posting list and computing a distributed join across those lists; this gives complete recall in the absence of node failure but the publishing cost scales with how many documents contain each keyword, so a query on a keyword with a large posting list (the paper's example is a query for "Britney Spears") is expensive to keep indexed. Query broadcast, in contrast, needs no publishing step and finds popular items quickly because many nodes hold a copy, but performs poorly for rare items because few nodes can answer within a hop-limited flood. The hybrid scheme organizes ultrapeers (Gnutella supernodes that perform query processing on behalf of leaf nodes) into a DHT overlay. Each ultrapeer identifies items likely to be rare from its leaf nodes' traffic and selectively publishes only those into the DHT, using the heuristic that an item returned in a small query-result set is rare; a query is first sent by conventional query broadcast, and if too few results return within a timeout, the query is reissued as a DHT lookup.

### Measured results
Live Gnutella network measurement: a modified LimeWire client instrumented to log all Gnutella traffic, run as ultrapeer or leaf node, deployed on 30 PlanetLab ultrapeers. Network crawl on 11 October 2003 (around noon Pacific time), 45 minutes, from 30 ultrapeers in parallel, measured network size of approximately 100,000 nodes and approximately 20 million files. 700 distinct queries taken from Gnutella query traces, replayed from each of the 30 ultrapeers at three different times (giving 700 x 30 x 3 total query instances), to compute recall (fraction of results returned by one node relative to the union of results from all 30 nodes, itself a lower bound on total available results). Findings: 41% of all queries received 10 or fewer results; 18% of queries received no results. For queries returning a single result, average first-result latency was 73 seconds; for queries returning 10 or fewer results, average first-result latency was 50 seconds; for queries returning more than 150 results, average first-result latency was 6 seconds. Taking the union of results across all 30 ultrapeers instead of a single node's results reduces the fraction of queries with 10 or fewer results from 41% to 27%, and reduces the fraction with zero results from 18% to 6% — described as a lower-bound estimate because the 30-node union itself underestimates total network results. Distributed-join bandwidth comparison: replaying 70,000 Gnutella queries against a 700,000-file sample collected from the same 30 ultrapeers, queries returning 10 or fewer results required shipping on average 7 times fewer posting-list entries via a DHT distributed join than the average across all queries. Connection-lifetime (churn) measurement: two leaf nodes and two ultrapeers monitored over 72 hours. Average connection lifetime: leaf nodes 58 minutes, ultrapeers 93 minutes (ultrapeers 1.5x longer). Median connection lifetime: leaf nodes 13 minutes, ultrapeers 16 minutes. Excluding leaf nodes with lifetimes under 10 minutes raised the average remaining leaf-node lifetime to 106 minutes. Preliminary hybrid-system deployment: multiple hybrid clients (the paper's summary states 50 ultrapeers) deployed on PlanetLab as Gnutella ultrapeers, each also running a DHT-based search engine built on PIER (a peer-to-peer relational query engine over DHTs). Query results for queries returning fewer than 20 results were published into the DHT at a rate of approximately one file per 2-3 seconds per node; publishing bandwidth overhead was 3.5 KB per file without Join Indexes (an index technique storing the filename redundantly with each posting-list entry) and 4 KB per file with Join Indexes. Leaf queries returning no result within 30 seconds via Gnutella were re-issued to the PIER-based DHT search, which returned a first result in 10-12 seconds (with and without Join Indexes respectively); average first-result latency for these same queries under Gnutella alone was 65 seconds, so the hybrid approach reduced latency by about 25 seconds for that class of query. The hybrid deployment reduced the fraction of queries receiving no results in Gnutella by 18% (a smaller reduction than the 66% lower-bound figure from the earlier union-of-30-ultrapeers measurement), which the authors attribute to the deployment only republishing files that had already appeared as query results, not proactively republishing all rare files, and to the small number of participating ultrapeers limiting coverage. With Join Indexes, each query's routing cost was dominated by shipping the PIER query itself, approximately 850 B; the plain distributed-join algorithm without Join Indexes incurred a 20 KB overhead per query.

### Parameters
- Ultrapeer fan-out observed in the crawl: most ultrapeers supported either 30 or 75 leaf nodes (older LimeWire ultrapeers: 75 leaf nodes, 6 ultrapeer neighbors; newer: 30 leaf nodes, 32 ultrapeer neighbors).
- Republishing threshold for the hybrid scheme: query results with fewer than 20 total results were republished into the DHT.
- Re-query timeout: 30 seconds before a Gnutella leaf query with no result is reissued via the DHT.
- Publishing rate achieved: approximately 1 file published per 2-3 seconds per node.
- Query-instance corpus: 700 distinct queries x 30 ultrapeers x 3 replay times.

### Stated limitations
The authors state the deployment "should be seen as a strawman," because a full hybrid infrastructure would require upgrading all existing Gnutella clients, and their PlanetLab deployment did not do this. The selective-publishing heuristic (republish items seen in small result sets) misses rare items that have never previously been queried and found; the authors state this explicitly and note that proactive publishing of leaf nodes' full rare-item lists would be needed to close that gap, left to future work. The paper states as future work a plan to quantify how increasing the query-broadcast search horizon (larger time-to-live) affects overall system load, rather than measuring it in this paper. The paper states as future work a plan to study the tradeoff between the DHT re-query timeout and query workload, rather than optimizing it here. The connection-lifetime measurement is stated by the authors to be a lower bound on true session lifetime, because a node may change which neighbors it is connected to during a single Gnutella session without the measurement detecting a new session.

### Requirements it places on the rest of the system
The hybrid scheme requires ultrapeers to participate in both a query-broadcast overlay and a DHT overlay simultaneously, and requires each ultrapeer to observe the result-set size of every query it forwards, so it can apply the small-result-set heuristic to decide what to publish. It requires a query-execution path capable of falling back from one search mechanism to the other within a bounded timeout (30 seconds in the deployment measured), which requires the query originator or its ultrapeer to track outstanding queries across that interval. The DHT side requires an inverted-index publishing pipeline (posting lists keyed by keyword) and a distributed-join execution engine (PIER, in this deployment); Join Indexes trade higher publishing bandwidth (4 KB/file versus 3.5 KB/file) for lower per-query bandwidth (850 B versus 20 KB), so which index variant is preferable depends on the query-to-publish ratio of the deployment. The DHT-side stability recommendation (only index ultrapeers, and only after a minimum uptime) requires the overlay to have a way to detect a node's session age before admitting its published data as authoritative.

### Contradicts
The paper describes an apparent conflict with an earlier Gnutella measurement study (Chawathe, Ratnasamy, Breslau, Lanham, Shenker, SIGCOMM 2003) that found most file downloads are for highly replicated items; the authors resolve this as measuring a different quantity, download requests (successful queries only) versus query result-set sizes (including queries that returned few or no results), not as a factual disagreement. None found against other entries in this evidence corpus.
