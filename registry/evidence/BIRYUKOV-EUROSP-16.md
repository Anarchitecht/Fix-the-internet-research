### What it does
Argon2 is a memory-hard function (MHF): a key-stretching function designed so that computing it requires a large amount of memory, making brute-force password guessing on custom hardware (FPGAs, GPUs, ASICs) no cheaper per guess than on the memory-limited hardware a legitimate server uses. Argon2 fills a caller-specified amount of memory M with pseudo-random blocks, then performs T passes over that memory, where each new block is computed by a compression function G from a previous block and one or more reference blocks selected by an indexing function; the caller also sets a parallelism degree, splitting memory into that many lanes so multiple threads fill blocks concurrently, with cross-lane references allowed after the first column of blocks. Argon2 has two data-flow variants: Argon2d selects each block's reference index using the contents of previously computed data, so the access pattern depends on the secret input, giving strong resistance to a class of time-memory tradeoff attacks but exposing a data-dependent memory-access pattern (a timing side channel) that an adversary co-located on the same machine can observe; Argon2i selects reference indices independently of the data, using the compression function itself as a pseudo-random number generator in counter mode, so the memory-access pattern is public and reveals nothing about the input, at the cost of needing more passes to reach comparable tradeoff resistance. The compression function G is built by applying a permutation P (a modification of the Blake2b round function called BlaMka, which adds 32-bit multiplications to the modular additions to increase the latency of an ASIC's arithmetic circuit while preserving CPU-friendly pipelining) across pairs of 128-bit register groups, then shuffling and reapplying it, so an 8-register permutation P produces a compression function over a p^2-register block with two rounds. To resist the ranking-based time-space tradeoff attack (in which an adversary recomputes cheaply reconstructible blocks instead of storing them), the indexing function's reference-distance exponent (a tunable parameter called gamma in the reference-block-selection formula) is chosen to bound how large a memory reduction is achievable without a matching increase in time-area product, the metric used throughout this document to compare adversary cost against honest cost.

### Parameters
- Memory parameter M: user-controlled, no value stated to be insecure; recommended settings above range from 250 MB to 6 GB depending on application.
- Number of passes T: user-controlled, running time scales linearly with it; Argon2i is specifically recommended with 3 passes "to get rid entirely of the password in the memory" against memory-leak attacks.
- Degree of parallelism (lanes) d: user-controlled up to 2^24 threads, though the document states 8 threads already exhaust the bandwidth and computing power of its Haswell test machine; slice count l fixed at 4 in the reference design (values of l=8 or l=16 are noted as possible alternatives), chosen because the time-area penalty multiplier (1 - (p-1)/(p*l)) * (1 + (p-1)/l) stays between 1.05 and 3 for 2<=p,l<=10.
- Indexing-function reference-distance exponent gamma: set to 2 in the shipped design, selected from a swept range of 1 to 5 (step 0.1, restricted to integers for the final choice) to balance time-area-product resistance against uniformity of block-reference frequency.
- Salt length: 128 bits recommended as sufficient for all applications, reducible to 64 bits under space constraints.
- Tag (output) length: 128 bits recommended as sufficient for most applications including key derivation; longer tags recommended if longer keys are needed.
- Compression function: BlaMka, a modification of the Blake2b round function adding 32-bit (permutation P uses 64-bit in the appendix specification) multiplications to the modular additions; block size 1024 bytes (8192 bits) in the reference design.

### Stated limitations
The document states Argon2d does not overwrite memory and is therefore vulnerable to garbage-collector and similar memory-disclosure attacks, and states it is not recommended for settings where such threats are possible; Argon2i with 3 passes overwrites memory twice specifically to close this exposure, so that even if the entire working memory is disclosed after hashing completes, recovering the password requires the adversary to recompute two full passes. The authors state the compression function G is not claimed to be collision-resistant or preimage-resistant, relying instead on the attacker's lack of control over its inputs to make collisions unlikely; the proof of block distinctness (Theorem 1) is stated to depend on two explicit assumptions about the permutation P (that P(Z) XOR Z is collision-resistant and 4-generalized-birthday-resistant) that are not independently proved in this document. The document explicitly states it will be updated if better attacks are found against the Alwen-Blocki tradeoff strategy, describing that line of attack as "a subject of active research" rather than closed, and its conclusion states that further tradeoff-attack development specific to Argon2 remains future work and that Argon2's resistance to GPU cracking with low memory requirements "remains to be seen." The multi-lane parallelism construction is stated to admit a computable time-area penalty reduction of up to a factor of 3 (an adversary computing the last memory column sequentially with reduced memory), which the design's choice of l=4 is stated to be a deliberate trade against synchronization overhead rather than a claim of immunity to that reduction.

### Requirements it places on the rest of the system
A system deploying Argon2 must choose between Argon2d and Argon2i (or a hybrid) based on whether the execution environment can leak timing information to an adversary: the document's own selection procedure directs the caller to pick Argon2i whenever side-channel observation is a viable threat, and either variant otherwise, meaning the calling system must characterize its own co-tenancy and physical-access threat model before parameter selection is possible. The recommended-parameters procedure requires the caller to supply, from outside this specification, the maximum thread count available per call, the maximum memory each call may use, and the maximum wall-clock time (in seconds) a call may take, then to search over the pass count T for the largest value fitting that time budget; Argon2 supplies no default for any of these three inputs; they must come from the deployment's own hardware and latency requirements. Argon2's proof of no block collisions (Theorem 1) depends on the mode-of-operation rule that a segment's first block never refers to the last block of any segment in the previous slice, so an implementation that alters the indexing rule without preserving that constraint invalidates the stated collision-freedom guarantee. The document states the memory-wiping option should be enabled at the call site "if side-channel attacks is a viable threat," meaning defense against the memory-disclosure attacks described above requires the caller to explicitly opt into a library-level feature rather than receiving it as a mode default.

### Contradicts
This document, describing itself as source [BDK16] in ALWEN-EUROSP-17, is the origin of the claim ALWEN-EUROSP-17 (Alwen, Blocki, EuroS&P 2017) directly disputes: this specification's own text states that its analytically derived time-area advantage for the Alwen-Blocki tradeoff attack "is not better than the ranking attack" for memory up to 16 GB, concluding that approach poses no practical threat at the memory sizes this document analyzes. ALWEN-EUROSP-17's simulated results show a concrete attack that reduces cost by a factor of 2 against Argon2i-B at 1 GB of memory and 6 passes — within the parameter space this document treats as safe — using heuristics (an improved depth-reducing-set construction and a bounded-parallelism analysis) this document's own analytic argument does not consider. See ALWEN-EUROSP-17's entry in this evidence file for the full measured comparison; the two documents disagree about the practical severity of the same underlying attack family at the same memory scale.
