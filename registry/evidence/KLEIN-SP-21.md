## [KLEIN-SP-21] Keep the Dirt: Tainted TreeKEM, Adaptively and Actively Secure Continuous Group Key Agreement
**Citation:** Joël Alwen, Margarita Capretto, Miguel Cueto, Chethan Kamath, Karen Klein, Ilia Markov, Guillermo Pascual-Perez, Krzysztof Pietrzak, Michael Walter, Michelle Yeo. "Keep the Dirt: Tainted TreeKEM, Adaptively and Actively Secure Continuous Group Key Agreement." IEEE Symposium on Security and Privacy (S&P), 2021. DOI 10.1109/SP40001.2021.00035.
**Retrieved:** full text
**Source URL:** https://eprint.iacr.org/2019/1489.pdf
**Domain:** H

### What it does
Tainted TreeKEM (TTKEM) is a Continuous Group Key Agreement (CGKA) construction: a protocol by which a group of parties who are not necessarily online at the same time derive a shared secret group key and refresh it over time, so that a group messaging protocol built on top gets forward secrecy (an old key stays secure even after a later state leaks) and post-compromise security (a party that leaked its state recovers security after it next updates). Parties are arranged as leaves of a binary tree; the secret value of the root is the group key, and each internal node's secret is derived from its two children (the "parents" in the paper's inverted edge direction, since edges point from leaves to root). A party updates by generating a new secret for its own leaf and re-deriving every node on the path from that leaf to the root, then sending the new public keys along that path, encrypted, to the rest of the group — a message of size logarithmic in group size for a balanced tree. Adds and Removes change tree membership. TreeKEM's existing mechanism for handling adds/removes overwrites ("blanks") nodes on the affected path; TTKEM instead marks such a node "tainted" by the identifier of the party who caused the taint, without overwriting its key, and every use of a tainted node's key requires XOR-ing in a fresh value contributed by the tainting party. A node is fully healed ("untainted") only once every tainted node in the subtree it roots has itself been overwritten by an Update, not merely once any single Update has touched it — this is the mechanical difference from blanking, where any leaf refresh anywhere under a blanked node "unblanks" it. Group membership changes and key updates are ordered and confirmed through an untrusted delivery server that all parties send operations to; the server can withhold delivery but cannot forge or read secrets.

### Parameters
- Group sizes simulated: 2^3 to 2^15 members.
- Operation sequence length: 10·2^i for a tree of size 2^i.
- Operation-type ratio (Update:Remove:Add): 8:1:1, matching the ratio Richard Barnes used in an IETF MLS mailing-list simulation of TreeKEM with blanking.
- Administrator density: 1 administrator per group for groups under 128 members; 1 administrator per 64 members for larger groups.
- Update-author distribution tested: uniform at random, and Zipf-distributed (used to model that message-sending activity per individual follows Gibrat's law, which implies a Zipf distribution of activity level, citing Rybski et al., PNAS 2009, and Gabaix, QJE 1999).

### Stated limitations
The paper proves security only against a "partially active" adversary: one that can arbitrarily reorder or withhold delivery-server messages but cannot forge messages using a corrupted party's secret keys or otherwise deviate from the protocol using stolen key material. Security against a fully active adversary — one that can also inject or alter messages using leaked keys — is stated as open; the authors cite this as "the subject of ongoing research." The construction assumes a pre-existing public-key infrastructure through which a party initializing a group already knows every invitee's public key; the paper treats this key-distribution problem as orthogonal to CGKA and does not address it. The paper's simulations start from a fully healed tree (no blanks or taints) and separately analyze only the cost of reaching that healed state from group creation; they do not simulate a mixed steady-state workload that interleaves initialization with ongoing operations. The authors state they cannot conclude TTKEM is more efficient than TreeKEM in every setting, only in the distributions of operations tested (administrator-driven adds/removes, or Zipf-distributed update authorship). One additional inefficiency is stated but not resolved: when a group member returns online after a long absence and must process a large backlog of operations, there is "still room for improvement," potentially through server-side batching, which the paper does not design.

### Requirements it places on the rest of the system
Requires an untrusted delivery server that every party sends Update/Add/Remove operations to and that enforces a single global order on those operations across all group members — when two parties submit conflicting operations concurrently, the server's ordering decision is what each party's confirm/reject response is built from. The server can prevent communication (withhold delivery) but the protocol's confidentiality guarantee does not depend on the server being honest about content. Requires a pre-existing mechanism, external to this protocol, by which any prospective group initiator already holds the public key of every invitee — the paper explicitly assumes this infrastructure exists rather than building it. Requires parties to process delivered operations in the order the server assigns; a party's local state becomes inconsistent with the group's if it processes operations out of that order. Requires that this order be enforced at least strongly enough to define a linear or partial order the safety predicate can reason over — the paper's security proof is stated for a specific ordering/confirmation protocol (send to server, wait for confirm-or-reject, update or discard local state accordingly) and would need re-derivation for a delivery model without server-mediated ordering (for example, a partition-tolerant broadcast).
