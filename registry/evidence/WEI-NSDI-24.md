## [WEI-NSDI-24] The Eternal Tussle: Exploring the Role of Centralization in IPFS
**Citation:** Yiluo Wei, Dennis Trautwein, Yiannis Psaras, Ignacio Castro, Will Scott, Aravindh Raman, Gareth Tyson. "The Eternal Tussle: Exploring the Role of Centralization in IPFS." USENIX/ACM NSDI, 2024.
**Retrieved:** full text via https://www.usenix.org/system/files/nsdi24-wei.pdf
**Source URL:** https://www.usenix.org/conference/nsdi24/presentation/wei
**Domain:** A+J

### What it does
The paper, written by IPFS (InterPlanetary File System) core maintainers at Protocol Labs, reports on three centralized components deliberately added to the deployed IPFS system to compensate for measured weaknesses of the pure Kademlia-DHT (distributed hash table) design, and measures each component's effect using operational data from the live network. It is a measurement-and-engineering-experience paper, not a proposal of a new decentralized mechanism.

InterPlanetary Network Indexers (Indexers): a server-based key-value store that receives an announcement message from a content provider (containing a batch, or "advertisement," of many content-identifier-to-provider mappings, possibly 16,000-20,000 records at once) and answers CID-or-multihash lookup queries over a RESTful HTTP API, bypassing DHT traversal entirely. Advertisements form a hash-linked chain per provider, so an Indexer can reconstruct all of a provider's records by walking the chain and can audit what a provider has published. Indexers gossip announcement messages among themselves (over Gossipsub) and cache query results at a frontend server ahead of the backing Pebble database.

Hydra Boosters: a set of DHT-server nodes ("Hydra Heads") deliberately positioned across the Kademlia identifier space so that, in expectation, every ordinary peer has at least one Hydra Head within its 20-peer XOR-proximity bucket. All heads share one backing database (Amazon DynamoDB), so a query answered by any head can return provider records collected by every other head, collapsing what would otherwise require multiple DHT hops into fewer hops.

HTTP Gateways: a small set of HTTP-to-IPFS bridge servers that let an ordinary web client fetch IPFS content without installing IPFS software. A gateway runs Nginx with default web caching in front of a co-located IPFS node's own block-storage cache, so already-fetched or already-stored content is served without any DHT lookup.

### Parameters
- DHT replication factor for provider records, cited as the baseline the Indexer departs from: k=20 peers (paper cites Maymounkov and Mazières, [30]).
- Hydra Booster deployment: 135 nodes on Amazon ECS in us-east-1, 10-15 heads per node, 2,015 total heads.
- Active-retrieval test object size: 0.5 MB per published CID.
- Hydra-disabled condition (used as the "without" baseline): ADD-PROVIDER queries to Hydra Heads ignored (heads make up ~10-15% of the network, so this is described as "artificially decreasing the k-replication to 19"); GET-PROVIDER queries answered with closer-peer lists only, no provider records, because the shared database is disconnected.
- Nginx and IPFS-node caching layers at each gateway: default Nginx web cache in front of a co-located IPFS node's own block cache; no explicit cache-size or eviction-policy parameter is stated in the reviewed text.
- Number of publicly known Indexers at time of writing: 7. Number of gateways: over 80.

### Stated limitations
The authors state the Indexer introduces a single point of failure: some provider records exist only in the Indexer and are not replicated in the DHT, so a centralized Indexer failure can make "significant volumes" of provider records inaccessible; they state this risk is only partially mitigated by inter-Indexer Gossipsub announcement sharing, which "offers no hard guarantees on real-time synchronization." They state the Indexer's monetary operating cost ($5,000-10,000 capital, ~$1,000/month) contrasts with the DHT's load-spreading design, which needs no comparable individual hardware investment. They state Hydra Booster failure (of the shared DynamoDB database, or of the routing function itself) degrades performance (they measured up to 36.5%) but does not reduce content availability, because peers fall back to ordinary DHT routing; they state they observed no failed retrievals when Hydra Boosters were excluded from routing entirely. They state a centralized entity operating multiple Hydra Heads could theoretically attempt result poisoning or eclipse attacks, but argue (not measure) that IPFS's self-validating content identifiers (CIDs) limit a Hydra Head to, at most, forcing a re-query rather than delivering falsified content, and that the low mean Hydra-Head density in any single peer's proximity set (2.36) limits routing-manipulation leverage. They state gateways sacrifice IPFS's end-to-end cryptographic content validation, creating a man-in-the-middle exposure that would require additional client-side hash verification to close, which they say "may undermine the goal of improving adoption." They state that as centralized instances, Indexers, Hydra Boosters, and gateways let their operators monitor which content identifiers are queried by which clients, and that most clients' reliance on Protocol-Labs-operated instances of these three components is "not a sustainable solution" given the resulting dependency. They state privacy and censorship attacks are independently possible in the pure decentralized DHT routing layer as well (citing Balduf et al. [10] and Sridhar et al. [37]), so the centralized components are not the sole source of that exposure, though the paper does not quantify the DHT-only attack surface itself. They state none of the three types of incentive they identify for third-party Indexer/Gateway operators (storage-service self-interest, application self-interest, ecosystem-alignment interest) is a "formal incentive model," and that it is undetermined whether third-party uptake will be wide without one.

### Requirements it places on the rest of the system
A content-identifier-to-provider indexing layer that adds a centralized fast path (as the Indexer does) requires the content addressing scheme underneath it to be self-validating (a hash-derived content identifier) so that a compromised or malicious index operator cannot substitute false content, only false or withheld provider pointers — this paper's own security argument for Hydra-Booster safety depends specifically on that property and does not hold for an indexing layer sitting in front of a non-self-validating naming scheme. A fallback-to-DHT design for availability (as used for both Hydra Boosters and, implicitly, gateways) requires the DHT to remain independently reachable and populated at all times; the paper's own robustness argument for Hydra Boosters rests entirely on ordinary DHT routing continuing to function when the centralized accelerator is absent, so a design that lets the DHT's own participant population shrink (for example, by deprecating DHT-server responsibilities in favor of only using the Indexer) would remove the fallback this paper relies on for its no-availability-loss claim. Any accounting of "decentralization" for this class of system needs to state which of at least four separate observable channels it measures — content-provider count, publication volume, query volume, or entry-point traffic — because this paper's own data shows these four diverge sharply (56,000 DHT publishers vs. 604 Indexer publishers, but the Indexer holding over 100x more provider records).

### Contradicts
No claim commonly attributed to this paper was found unsupported by its text; the paper is explicit that Indexers "do not replace the DHT" and that the DHT "still plays a larger role" by publisher count and query volume even though the Indexer holds the numerical majority of provider records — a nuance a headline restatement of "one centralized indexer holds over 100x the DHT's location records" (as flagged by the target registry's why_needed note) risks flattening if the publisher-count and query-volume figures are dropped.
Disagrees with BALDUF-IMC-23 on IPFS cloud/DHT-node-hosting share: this paper does not itself report a DHT cloud-hosting percentage in the sections reviewed, but is the direct target of BALDUF-IMC-23's methodological critique — BALDUF-IMC-23 attributes the 2022 Trautwein-et-al. figure of "less than 3% of cloud nodes" (a predecessor measurement by overlapping authors, cited in this paper's own bibliography as [41], Trautwein et al., ACM SIGCOMM 2022) to a counting-methodology difference, not to network change; this NSDI-24 paper by largely the same author group does not revisit that cloud-hosting percentage, so the two papers' cloud-centralization findings are not directly comparable on the topology channel, only on the indexing/traffic channels this paper covers.
