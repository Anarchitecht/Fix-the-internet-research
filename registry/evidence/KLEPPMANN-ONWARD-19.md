## [KLEPPMANN-ONWARD-19] Local-First Software: You Own Your Data, in Spite of the Cloud
**Citation:** Martin Kleppmann, Adam Wiggins, Peter van Hardenberg, Mark McGranaghan. "Local-First Software: You Own Your Data, in Spite of the Cloud." ACM SIGPLAN International Symposium on New Ideas, New Paradigms, and Reflections on Programming and Software (Onward!), 2019. DOI 10.1145/3359591.3359737.
**Retrieved:** full text via https://www.inkandswitch.com/local-first/
**Source URL:** https://www.inkandswitch.com/local-first/ ; https://doi.org/10.1145/3359591.3359737
**Domain:** D

### What it does
This paper states seven requirements — "ideals" — that the authors argue software must meet to give users both real-time collaboration and full ownership of their data, and argues that Conflict-free Replicated Data Types (CRDTs — data structures whose concurrent updates on different replicas always merge to the same result without central coordination) are a mechanism that can satisfy several of the seven simultaneously. This is a requirements and position paper drawing on qualitative prototype experience, not a mechanism paper proposing a new algorithm; nothing in the schema's "Requirements it places on the rest of the system" section should be read as this paper mandating an implementation choice, only as the property set an implementer must reach. The seven ideals, each defined by contrast with the "cloud app" architecture in which a remote server holds the authoritative copy and every client copy is a subordinate cache: (1) No spinners — the software responds to input without a network round trip, because the primary copy of the data lives on the local device and synchronization happens in the background; (2) work is not trapped on one device — data synchronizes across every device a user works from, not merely stored on one; (3) the network is optional — the application functions fully offline, reading and writing the local copy, and reconciles with other devices only when a connection later becomes available; (4) seamless collaboration — multiple users edit the same document, matching or exceeding the simultaneous-editing experience of a centralized cloud app, without requiring a central server to mediate; (5) the long now — data and the software needed to read it remain accessible indefinitely, independent of whether the vendor that produced the software continues to operate; (6) security and privacy by default — a local-first design avoids the large centralized data store that concentrates every user's data behind one company's access controls, and can add end-to-end encryption so an assisting server holds unreadable ciphertext; (7) user retains ultimate ownership and control — the user is not restricted in copying, exporting, or otherwise using their own data by a provider's terms of service or API surface. The paper surveys eleven existing technologies and application categories (plain files with email attachments, Google Docs, Trello, Pinterest, Dropbox, Git plus GitHub, thin web clients, thick mobile clients, backend-as-a-service platforms such as Firebase, and CouchDB) against these seven ideals and states that none satisfies all seven; the paper's own conclusion from this survey is that CRDTs, used as the client-side data layer with a synchronization mechanism to move updates between devices, are the technology class it identifies as capable of jointly satisfying the collaboration ideal (4) alongside the offline and multi-device ideals (2, 3) without requiring a central authoritative server.

### Measured results
Server-to-server round-trip time between geographically distributed AWS datacenters, presented as a bound on the fastest possible cloud-app response latency, is cited from a separate paper (Bailis, Davidson, Fekete, Ghodsi, Hellerstein, Stoica, "Highly Available Transactions: Virtues and Limitations," VLDB 2014) and not independently re-measured here; the network-latency numbers behind Figure 1 belong to that source paper, not to this one, and must not be recorded as this paper's own measured result. Beyond that cited figure, this paper reports no quantitative benchmark of CRDT performance, network cost, or user-study statistics; its own empirical content is qualitative field experience from three internally-built prototypes (Trellis, a Kanban board; PixelPusher, a collaborative drawing tool; PushPin, a mixed-media canvas), tested by regular use within a five-person development team and individual usability sessions with approximately ten external users (professional designers, product managers, and software engineers), explicitly run without a formal evaluation methodology ("we did not follow a formal evaluation methodology, but rather took an exploratory approach"). No trial count, task list, or outcome metric is reported for these usability sessions, so no number from them meets this schema's bar for a measured result with experimental conditions; only their qualitative findings are recorded below, each clearly attributed to the authors' informal observation rather than to a quantified experiment.

### Stated limitations
The authors state their prototype findings are "somewhat subjective," collected without a formal evaluation methodology, from a five-person internal team plus roughly ten external testers, so the findings below are field observations, not controlled-experiment results. CRDTs (specifically the Automerge library used in the prototypes) accumulate a complete change history, including every character-by-character text edit, which the paper states created measured performance and memory/disk problems in real use (e.g. using PushPin for actual sprint planning); the paper states this history cannot easily be truncated because a collaborator might reconnect after months away and need to merge from that earlier point forward, and that this remained a major area of ongoing, unresolved work at the time of writing. CRDT algorithms by themselves specify only how to merge data, not how updates physically reach other users' devices; the paper states network communication "remains an unsolved problem" in their prototypes, having tried WebRTC, manual file-copying via Dropbox and USB drives, IPFS, and eventually the Hypercore peer-to-peer libraries from the Dat project. Peer-to-peer NAT traversal (routing around network address translation so two devices behind separate home routers can connect directly) is stated to be unreliable, varying by the specific router and network topology in use, and the P2P technologies used in the prototypes are stated to be "nowhere near production-ready." A purely peer-to-peer design without any server creates a "closed-laptop problem": if one user shares a document and closes their laptop before a second user comes online, the two never connect, so the paper concludes servers retain a role as "cloud peers" — non-authoritative supporting nodes for backup, discovery, bridging to traditional APIs, and burst compute — rather than being eliminated. The paper states unresolved, open research questions rather than solved problems for: access permissions for shared documents beyond an unguessable secret URL; algorithms and programming models for branching, forking, and rebasing a document's edit history among collaborators (most CRDT research assumes all collaborators immediately apply edits to one shared version, which the paper states does not match practical needs); and how differing application versions with differing data schemas can safely interoperate absent a central authoritative schema server. The paper's own qualitative finding is that Automerge's default, generic conflict-resolution policy was sufficient across all three prototypes and no case requiring application-specific merge semantics was identified — but the paper explicitly labels this a hypothesis ("we hypothesise that this is the case generally") awaiting further research, not a proven general result.

### Requirements it places on the rest of the system
For the seamless-collaboration ideal to hold without a central server, the paper's prototype experience found that merge behavior needs to operate at a fine granularity that accounts for a datatype's own semantics — its example is that Automerge positions two users' concurrent insertions into the same array position deterministically, whereas a line-oriented tool like Git treats the same situation as a manual-resolution conflict — so a synchronization layer that treats a document as an undifferentiated byte blob rather than a structured, datatype-aware CRDT will reintroduce the manual-merge burden the ideal is meant to remove. Achieving the offline and multi-device ideals together requires the application's data layer to keep a full local, independently readable and writable copy at every device, with synchronization handled as a background process rather than as a precondition for any read or write — an architecture where any operation blocks on reaching a server does not meet ideal 1 or 3 regardless of how fast that server responds when reachable. Achieving the long-now (longevity) ideal requires that both the data format and the software needed to interpret it remain usable independent of any single vendor continuing to operate a backend service; the paper's own recommendation is to favor durable, well-documented formats (plain text, JPEG, PDF, or, per the US Library of Congress's guidance which the paper cites, XML, JSON, or SQLite) precisely because these do not depend on a specific company's servers to remain interpretable. Realizing the security/privacy ideal with an assisting server in the loop requires end-to-end encryption at the application layer, so that any server holding a copy of the data holds only ciphertext it cannot read — the paper names this as necessary specifically because it foresees the server role persisting (as a "cloud peer" for backup, discovery, and bridging) rather than disappearing.

### Contradicts
The paper's own findings section explicitly narrows a claim that might otherwise be attributed to it: it does not claim CRDTs require a peer-to-peer network layer — the paper states plainly "CRDTs do not require a peer-to-peer networking layer; using a server for communication is fine for CRDTs" — and frames the move toward peer-to-peer transport as motivated specifically by the longevity ideal (outliving any single vendor's backend), not as a property CRDTs themselves demand. A claim sometimes attributed to this paper — that conflict resolution in collaborative CRDT-based software requires application-specific merge logic — is contradicted by the paper's own finding across all three prototypes, where the generic default resolution policy in Automerge was found sufficient and no case requiring customized semantics was identified (stated as a hypothesis for further testing, not a proof).
