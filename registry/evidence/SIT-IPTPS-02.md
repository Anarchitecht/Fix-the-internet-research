## [SIT-IPTPS-02] Security Considerations for Peer-to-Peer Distributed Hash Tables

**Citation:** Emil Sit, Robert Morris. "Security Considerations for Peer-to-Peer Distributed Hash Tables." IPTPS, 2002. DOI 10.1007/3-540-45748-8_25.
**Retrieved:** full text via https://pdos.csail.mit.edu/papers/chord:security02/chord:security02.pdf (candidate URL from registry; local file matches title/authors/abstract)
**Source URL:** https://pdos.csail.mit.edu/papers/chord:security02/chord:security02.pdf
**Domain:** A

### What it does
The paper classifies liveness attacks against distributed hash table (DHT) lookup systems — attacks that prevent participants from finding data, as distinct from data-authenticity attacks, which the authors state are already addressed by cryptographic techniques such as self-certifying path names. It defines the adversary model, enumerates attack classes against routing and against storage, and derives six design principles from the defenses discussed for each class. The paper contains no implementation and no experiment; it is an analytical taxonomy applied to three published DHT designs, Chord, Pastry, and CAN (content-addressable network).

The adversary model: a malicious node can generate packets with arbitrary content, including forged source IP addresses, but can only receive packets addressed to its own IP address. This lets a node use IP address as a weak identity check: a node receiving a packet from address X can confirm the sender controls X by sending a confirmation request to X. Malicious nodes may conspire, each individually bound by this same constraint. Malicious nodes cannot overhear or modify traffic between other nodes.

The six design principles the paper derives: (1) define verifiable system invariants and verify them; (2) let the querier observe lookup progress hop by hop, so it can detect a lookup that fails to converge toward the target key; (3) assign node identifiers to nodes in a verifiable way, for example by deriving the identifier from a cryptographic hash of the node's IP address and port, so another node can check a claimed identifier against the claimant's network address; (4) treat routing-table entries chosen by a latency- or performance-based server-selection rule as attacker-influenceable, since an adversary can offer itself as the lowest-latency or best-ratio option and thereby bias which nodes get chosen; (5) cross-check a node's own routing table by issuing random queries through previously-trusted nodes and comparing results, to detect that a node has been diverted into a parallel, internally-consistent malicious network (a partition attack); (6) avoid single points of responsibility in the storage layer — replication must be organized so that no single node governs whether a client obtains a replica, and clients must independently determine the correct replica set rather than asking one node for it.

Attack-specific mechanisms discussed: incorrect lookup forwarding (a node forwards a query to a wrong or non-existent node) is detected when the querier can verify that each hop's identifier distance to the key strictly decreases, which requires an iterative-lookup design where each hop reports back to the querier — this check is stated to be impossible under CAN's proposed recursive-forwarding round-trip-time (RTT) optimization, where a node forwards to whichever neighbor has the best progress-to-RTT ratio without involving the querier. Incorrect routing-table updates (a node injects false entries into another node's routing table) are mitigated by requiring each update to satisfy a checkable structural rule (Pastry requires each table entry to share the correct address-prefix length) and by requiring reachability verification before an update is incorporated. Partition attacks (an adversary builds a self-consistent parallel network and diverts a joining or rejoining node into it) are mitigated by bootstrapping new nodes only from an out-of-band trusted source, and by an already-joined node periodically cross-checking against previously-used nodes with random queries. Storage-denial (a node claims not to hold data it is responsible for, or claims to hold data but refuses to serve it) is mitigated only by replication combined with the single-point-of-responsibility principle: querying clients must consult at least two independent replica sites before concluding data is truly missing, because consulting only the node structurally responsible for replication (as DHash does) leaves the client unable to distinguish "data missing" from "the one node that controls replica lookup is lying." Inconsistent behavior (a node behaves correctly toward nearby-in-identifier-space nodes and incorrectly toward distant ones) is stated to be undetectable by distant nodes reporting the bad behavior to near ones unless responses are signed, because an unsigned complaint cannot be distinguished from a false complaint meant to discredit a benign node. Node overload (packet flooding against a targeted node or its replicas) is mitigated by assigning node identifiers independently of network topology and by physically dispersing replicas, so a topologically localized attack cannot take out an entire portion of the key space. Unsolicited/forged responses (a node that referred a querier to a next hop forges a reply purporting to come from that next hop) are mitigated with a per-query random nonce that the genuine respondent must echo back.

### Parameters
None stated. The paper introduces no tunable parameter of its own; it discusses design choices made by the systems it analyzes (Chord's successor-list replication, Pastry's prefix-verification rule, CAN's RTT-ratio neighbor selection) without stating specific numeric configurations for any of them.

### Stated limitations
The paper explicitly scopes itself to liveness attacks only, stating that data-correctness and data-authenticity attacks are considered already addressed by existing cryptographic techniques (citing self-certifying path names) and are out of scope. The adversary model explicitly excludes a node's ability to overhear or modify traffic between two other nodes; an adversary with that capability is not analyzed. The paper states that trust metrics built on IP address are dangerous in a network with high churn and weak identity, because a Dynamic Host Configuration Protocol (DHCP)-assigned address can belong to a malicious node one day and a benign node the next. For the inconsistent-behavior attack, the paper states plainly that without public-key signatures on responses, "each node must make its own determination as to whether another node is malicious," i.e., no cross-node verification mechanism is offered. For the verifiable-node-identifier defense, the paper states that deriving a node's identifier from a hash of its IP address, port, and virtual-node number (as Chord does) still leaves a single physical host able to run many virtual nodes and thereby exercise some choice over which keys it becomes responsible for, so Chord's approach only partially closes the attack DHash remains exposed to. The rapid-join/-leave rebalancing attack is stated to be unavoidable in general: any DHT, with or without adversaries, must already handle rebalancing triggered by ordinary churn, so the paper offers no defense beyond noting that the adversary's model here (no ability to fake liveness of a node cheaply, and rebalancing requiring acknowledged data transfer) limits how cheaply an adversary can trigger excess rebalancing.

### Requirements it places on the rest of the system
For principle 2 (observable lookup progress) to be enforceable, the lookup protocol must be iterative (each hop reports the next hop back to the querier) rather than fully recursive/relayed, because the paper states this check is impossible under CAN's proposed RTT-optimized recursive forwarding. For principle 3 (verifiable node identifiers) to be enforceable, the identifier-derivation function must bind the identifier to something the querier can independently check against the network, such as the claimant's IP address and port; a system letting a node choose its own identifier arbitrarily (as the paper states CAN allows) cannot support this check. For principle 5 (cross-checking via random queries) to work, a node must maintain a set of other nodes it has successfully used in the past, obtained through an out-of-band trusted bootstrap the first time, and query randomness must be preserved so a malicious partition cannot distinguish a verification probe from a real query it wants to intercept. For the storage/replication defenses (principle 6) to work, the system must let a client independently compute or discover the full replica set for a key rather than obtaining it through one designated node, and must support the client querying at least two replica sites per lookup. For the inconsistent-behavior and unsolicited-response defenses, the system needs either digital signatures on all node responses (to let a third party verify a complaint about a node, and to let a querier verify a reply's claimed origin) or, absent that, a per-query random nonce that a legitimate respondent echoes back, which defends only against response forgery, not against a node lying about its own state.

None found among the papers in this batch (W1-5).
