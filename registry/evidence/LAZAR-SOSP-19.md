## [LAZAR-SOSP-19] Yodel: Strong Metadata Security for Voice Calls
**Citation:** David Lazar, Yossi Gilad, Nickolai Zeldovich. "Yodel: Strong Metadata Security for Voice Calls." ACM SOSP, 2019. DOI 10.1145/3341301.3359648.
**Retrieved:** full text via https://people.csail.mit.edu/nickolai/papers/lazar-yodel.pdf
**Source URL:** https://people.csail.mit.edu/nickolai/papers/lazar-yodel.pdf
**Domain:** G

### What it does
Yodel hides which pairs of users are on a voice call from an adversary that controls the network and compromises some servers, at latency low enough to carry a voice conversation, by avoiding a public-key operation per network hop for every message. Users route voice packets through a mixnet of N servers arranged so that each message passes through a client-chosen circuit, a fixed sequence of servers established once with public-key cryptography and then reused for many messages using only symmetric-key cryptography, unlike Karaoke (this same author group's prior system), which performs a public-key operation at every hop for every message.

Two mechanisms make circuit reuse safe against a network-observing, server-compromising adversary. Self-healing circuits let a circuit survive without leaking metadata when a user's network briefly drops: because a server would otherwise be able to notice "no message arrived on this circuit this round" and infer whose circuit it is, each server that would have relayed a real message instead relays a server-generated cover message on any round where the client fails to send one, so from an observing server's point of view a circuit always carries traffic whether or not its owning client is actually connected. Guarded circuit exchange addresses the separate problem of connecting two users to a shared circuit without one of them revealing, by connecting or not connecting to a given circuit endpoint, whether a call attempt succeeded: each user maintains two circuits, one dedicated to background cover traffic and one for an actual call partner (buddy); if a call setup message is lost, the user still has a safe circuit endpoint to connect to (either the cover circuit or the buddy circuit) without revealing to the server whether the call attempt succeeded.

Circuit setup (establishing the public-key-encrypted onion layers for a fresh circuit for the next round) proceeds in the background, using a separate small pool of CPU cores from the pool handling the current round's message relay, so the two phases do not compete for the same resources within a round. Noise circuits (server-generated cover circuits with no real user behind them) are created during setup in a volume derived from the assumed fraction of honest servers and the desired failure probability, following the same noise-generation-and-Bloom-filter-verification approach as Karaoke. Yodel relies on an external metadata-private messaging system (the paper uses its own prior systems, Alpenhorn for out-of-band dialing and Karaoke for circuit-endpoint exchange) for users to first tell each other which circuit to connect to.

### Measured results
Hardware: Amazon EC2 c5.9xlarge instances (Intel Xeon 3.0 GHz, 36 cores, 72 GB memory, 10 Gbit/s link) per server. On each server, 30 of 36 cores were dedicated to circuit-messaging relay for the current round and the remaining 6 cores to circuit setup for the next round. Deployment: 100 servers evenly distributed across 5 Amazon data centers (Virginia us-east-1, Ireland eu-west-1, London eu-west-2, Paris eu-west-3, Frankfurt eu-central-1), chosen to minimize inter-server latency while maximizing independent trust zones. Measured weekly-average round-trip latency between Virginia and Frankfurt (the highest-latency pair): 90 ms; between European server pairs: 15-40 ms. Millions of simulated users were generated as extra circuits created by servers during circuit setup (2 circuits per simulated user), excluding the cost of generating those circuits' setup onions (a cost that in a real deployment would fall on clients, not servers). Two real users ran the Yodel voice client from Boston (maximum measured round-trip latency to a Yodel server: 90 ms), using Alpenhorn for out-of-band dialing and Karaoke (on separate servers) for circuit exchange, to measure real end-to-end latency and throughput. Baseline configuration for all experiments except the trust-assumption sweep in §6.3: servers assumed honest with 80% probability, requiring 15-hop circuits; target failure probability 10^-8, which required approximately 3,700 noise circuits generated per server per round at a 100-server deployment. Relative standard deviation of each reported data point: 6% or less.

One-way voice-packet latency versus number of users, 100 servers, two audio codecs (Figure 10): with the LPCNet neural vocoder, latency stays under 1 second up to 5 million users (990 ms at 5 million users), rises to 1.4 seconds beyond 5 million users (at which point the paper states the system "would need more servers to support voice calls for that user load"), and beyond 8 million users inter-server packet loss made sustained voice-call throughput with LPCNet difficult. With the standard Opus codec at its lowest-quality setting (5x more bandwidth per call than LPCNet), 100 servers supported 1 million voice calls at 965 ms latency; Opus supports fewer simultaneous users than LPCNet at the same server count because of its higher bandwidth requirement.

Circuit setup latency versus number of users, 100 servers, 6 of 36 cores dedicated to setup (Figure 11): under 40 seconds at 8 million users. The paper states rounds start every 5 minutes, so setup completes with margin at every tested user count.

Scaling by adding servers, fixed per-server user ratio (Figure 12): at 25,000 users/server and 50,000 users/server ratios, latency rises slightly from 50 to 200 servers because per-server noise-circuit count scales with server count (at 200 servers each server creates 4x as many noise circuits as at 50 servers, for the fixed 80%-honest / 15-hop security target). At the 50,000-users/server ratio and 200 servers (10 million users), one-way latency is 848 ms.

Effect of trust assumption (path length) on latency, 100 servers, 2 million users (Figure 13): latency increases linearly with path length. At 100% assumed-honest servers (adversary controls only the network, no servers), path length 2 suffices, giving approximately 100 ms one-way latency. At the paper's baseline 80%-honest assumption, path length 15 is required. Under an assumption matching Herd's single-honest-first-hop model, Yodel needs 9 layers, giving approximately 450 ms latency at 2 million users and 100 servers — compared against Herd's own reported 200 ms for North American users at 10 million users and 1,000 servers, which the paper states comes with a weaker privacy guarantee than Yodel's (elaborated in the paper's discussion, not reproduced here as a number).

Server bandwidth (Figure 14), 100 servers, varying user count: average per-server transmit bandwidth reaches approximately 3 Gbit/s at 5 million users with LPCNet. The measured per-server bandwidth tracks closely to the analytically computed minimum bandwidth needed just to carry the raw audio (2 calls per user divided across servers, no security overhead), which the paper attributes to circuit messaging adding no bandwidth overhead from onion encryption and only a small overhead from inter-user checksums. The prototype could not sustain over 4.6 Gbit/s per server across the real internet without significant packet loss, which limited the Opus configuration to 1.75 million users on 100 servers.

Cost estimate (not an experimental measurement, a derivation from a 2016 published bandwidth-pricing figure): the paper cites a 2016 reported price of approximately $4,000/month for a 10 Gbit/s U.S.-to-Europe link and computes from it that Yodel's bandwidth could be funded by charging users under $1/year; this is a derived estimate from an external, unverified-by-this-pass pricing source, not a measurement this paper performed.

Fault tolerance (§7, stated as a limitation, not a headline result): at the evaluated 15-hop configuration, if 2% of servers are unavailable, approximately 30% of messages are lost.

### Parameters
- N = 100 servers in the primary evaluation (also tested 50-200 in the server-scaling experiment).
- Honest-server-probability assumption: 80% in the default configuration, swept from 100% down through configurations tested in Figure 13 (exact intermediate percentages for each tested path length not given as a table in the extracted text beyond the 80%/100% and Herd-comparison points).
- Path length (hop count): 15 hops at the 80%-honest baseline; 2 hops at 100%-honest; 9 hops when matching Herd's single-honest-hop trust assumption.
- Target failure probability: 10^-8.
- Noise circuits generated per server per round at N=100, 80%-honest, 15 hops: approximately 3,700.
- Round interval: 5 minutes.
- CPU allocation per server: 30 of 36 cores to current-round circuit messaging, 6 of 36 cores to next-round circuit setup.
- Audio codecs tested: LPCNet (low-bitrate neural vocoder, 1.6 kb/s per the codec's own citation) and Opus (standard VoIP codec) at its lowest-quality, highest-compression setting; Opus used 5x the bandwidth of LPCNet in this configuration.
- One-way inter-server delay used in the paper's own accounting of the 990 ms figure: 45 ms per hop across 15 hops in the synchronous-batch design.

### Stated limitations
Yodel's own stated most significant limitation is latency: 990 ms one-way exceeds the ITU G.114 recommendation of at most 400 ms for interactive telephone-quality calls, and the paper states this would make fast, interruption-heavy conversation difficult, while asserting (based on the authors' own use, not a controlled study) that longer, less-interrupted conversations remained usable. Noise generation per server scales linearly with the number of servers in the deployment, which the paper identifies as a bottleneck at deployments of several thousand servers (citing Tor's approximately 6,000-server scale as the comparison point); the paper states it believes the overhead stays low at deployments of hundreds of servers, based on Figure 9 and the §6.2 server-scaling measurement, but does not measure a several-thousand-server deployment. Fault tolerance is bounded: at the evaluated 15-hop configuration, 2% of servers being unavailable causes about 30% of messages to be lost, so the paper states Yodel is useful only when few servers are simultaneously down. Geographic latency is architecturally coupled across all users: because total latency is approximately the hop count times the maximum one-way latency between any two servers in the deployment, adding a server in a new region to reduce latency for users in that region raises latency for every other user in the system; the paper's own worked example is that adding an Australian server to the evaluated US/Europe deployment would raise end-to-end latency for all users from 990 ms to about 3 seconds. The paper states this coupling is inevitable given an anonymity set defined as all connected users in the system. Sybil circuit creation (an attacker creating many circuits to mount denial of service) is identified as a risk the paper suggests mitigating with existing mechanisms such as subscriptions or proof-of-work, explicitly stating that fully solving the problem needs further research, not addressed by this paper's own construction.

### Requirements it places on the rest of the system
Requires an external metadata-private messaging channel to bootstrap each call: the evaluation itself used Alpenhorn (this author group's own prior OSDI 2016 system) for out-of-band dialing and Karaoke (this author group's own prior OSDI 2018 system) for circuit-endpoint exchange, running on separate servers from the Yodel mixnet; Yodel supplies none of this bootstrapping itself. Requires synchronous rounds across the full server deployment, the same coordination requirement as Karaoke; a circuit's self-healing property depends on every server on its path relaying either a real message or a cover message every round, which requires all N servers to remain reachable and processing rounds in lockstep for the low-loss operating regime the fault-tolerance figures describe. Requires the deployment's server set and path lengths to be fixed in advance around a target honest-fraction assumption (15 hops for 80% honest in the evaluated configuration); changing the assumed honest fraction changes the required path length and therefore the latency, so the system needs an externally supplied, trusted estimate of the fraction of compromised servers before path length can be chosen. Requires geographic co-location of the server deployment's regions to keep per-hop latency low; because total latency scales with the worst-case inter-server round-trip time, any component that needs to add servers in a new geographic region to improve locality for a subset of users instead raises latency for the whole population, so a caller cannot use per-region latency optimization without a global redesign. Requires an independent Sybil-resistance mechanism (not supplied by this paper) to bound the number of circuits an attacker can create for denial of service.

### Contradicts
None found within this corpus for its own measured figures. The paper's comparison to Karaoke (8 seconds latency, 0.24 kbit/s throughput per user, at 4 million users) and to Herd (200 ms for North American users at 10 million users, 1,000 servers) are cited from those systems' own papers, not independently re-measured by this paper on the same hardware, so those specific comparison numbers should be checked against LAZAR-OSDI-18's own entry rather than treated as this paper's own measurement.
