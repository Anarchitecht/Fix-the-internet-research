## [VYZOVITIS-SPECS-23] Circuit Relay v2 (libp2p specification)

**Citation:** Dimitris Vyzovitis (@vyzo), with interest-group review by Max Inden, Steven Allen, Raúl Kripalani. "Circuit Relay v2." libp2p/specs repository, recommendation-stage specification, revision r3, 2023-02-28.
**Retrieved:** full text via https://raw.githubusercontent.com/libp2p/specs/master/relay/circuit-v2.md
**Source URL:** https://github.com/libp2p/specs/blob/master/relay/circuit-v2.md
**Domain:** L

### What it does
Circuit Relay v2 lets a peer that cannot receive unsolicited inbound connections (a "private" peer, typically behind a NAT) become reachable by routing a connection through a third, publicly reachable peer (the relay), while keeping the relay's resource exposure bounded and explicit instead of open-ended. The protocol splits into two subprotocols: `hop`, which a client speaks to a relay to reserve relay capacity and to request that the relay open a connection to another peer, and `stop`, which the relay speaks to the connection's ultimate endpoint. A private peer A first opens a connection to relay R and sends a `hop` `RESERVE` message; if R accepts, it returns a `STATUS:OK` reply carrying a `Reservation` (an expiration time, R's public relay addresses, and a signed voucher) and, optionally, a `Limit` (a maximum relayed-connection duration in seconds and a maximum data volume in bytes per direction). A is expected to keep its connection to R alive and to refresh the reservation before it expires; the reservation becomes invalid if A disconnects. A now advertises a circuit multiaddress of the form `/p2p/QmR/p2p-circuit/p2p/QmA`, discoverable out of band (e.g., via a Distributed Hash Table or a rendezvous point). A second peer B that wants to reach A connects to R, opens a `hop` stream, and sends `CONNECT` naming A; R checks that it holds an active reservation for A, opens a `stop` stream to A carrying a `CONNECT` message naming B, and if A responds `STATUS:OK`, R relays `STATUS:OK` back to B and bridges the two streams — the `hop` stream between B and R, the `stop` stream between R and A — into one relayed connection, over which A and B then negotiate their own end-to-end security and stream multiplexing exactly as they would over a raw TCP connection. If the connection exceeds the negotiated data or duration `Limit`, the relay resets both the B-side and A-side streams. A now-deprecated "active relay" mode, in which a `hop` `CONNECT` request itself supplies a target address for R to dial rather than requiring a pre-existing reservation, is retained in the wire format but flagged as deprecated for security reasons in public relays. Reservation vouchers are cryptographically signed certificates (a Signed Envelope with domain `libp2p-relay-rsvp`, multicodec `0x0302`) by which R testifies it is willing to serve A; the spec states vouchers are advisory only, since dialing a relay address is not currently required to carry one.

### Measured results
None. This is a protocol specification document, not an experimental paper; it contains no deployment measurement, no reservation-duration default, no per-relay concurrent-reservation cap, and no per-circuit data-cap value. The `duration` and `data` fields of the `Limit` message are defined as protocol fields whose numeric values are set by each relay implementation and communicated per-reservation; the specification text states no default numbers for them. (TRAUTWEIN-ARXIV-26's measured DCUtR hole-punch dataset, which runs over Circuit v2 relayed connections as its precondition, is the measurement counterpart to this specification within this corpus, but it measures hole-punch outcomes, not relay resource-limit values.)

### Parameters
- `Limit.duration`: maximum relayed-connection duration in seconds; value 0 means no limit applied; no default numeric value stated in this document — set per relay implementation and communicated to the client in the reservation/connection response
- `Limit.data`: maximum bytes transmitted per direction over the relayed connection; value 0 means no limit applied; no default numeric value stated in this document
- `Reservation.expire`: reservation expiration as a UTC Unix timestamp in seconds; no default lifetime value stated in this document
- Protocol IDs: `/libp2p/circuit/relay/0.2.0/hop` and `/libp2p/circuit/relay/0.2.0/stop`
- Reservation-voucher envelope domain: `libp2p-relay-rsvp`; multicodec code `0x0302`

### Stated limitations
The `limit` field, when omitted from a relay's response, "indicates that the relay does not apply any limits" — the specification does not require a relay to bound duration or data volume; a relay operator that omits the field runs unbounded relaying for that reservation. Reservation vouchers are stated to be advisory only: "the intention is to eventually require the use of reservation vouchers for dialing relay addresses, but this is not currently enforced." Active relay functionality (a `hop` `CONNECT` that itself supplies a dial target rather than requiring a pre-existing reservation) is retained in the wire format "for the rare cases where it is actually desirable... in a controlled environment" but is explicitly flagged "deprecated for security reasons, at least in public relays" without the specification stating what that security reason is. The specification states that implementations "should not" accept a new reservation or a new connection-initiation request over a connection that is itself already a relayed connection, but this is stated as a should-not, not an enforced protocol rule. A relay retains discretion to drop a connection with an active reservation "if a relay server becomes overloaded" and doing otherwise "would prevent it from maintaining its resource quotas," meaning the expiration time in a `Reservation` is not a guarantee against earlier termination under relay-side resource pressure.

### Requirements it places on the rest of the system
A private peer depending on Circuit v2 for reachability must maintain a live, continuously refreshed connection to at least one relay holding its reservation, because the specification states the reservation becomes invalid immediately if the reserving peer disconnects — so any component that assumes a private peer stays reachable through a relay across that peer's own connection churn is unsupported by this mechanism as specified. A peer that wants to reach a private peer through a relay must already possess that private peer's circuit multiaddress (naming both the relay's peer ID and the target's peer ID) obtained out of band — the specification names a DHT or a rendezvous point as examples but does not itself supply address discovery, so any calling system must supply its own mechanism for publishing and looking up which relay(s) a given private peer currently holds a reservation with. Because reservation vouchers are advisory and not currently enforced for dialing, a system that needs cryptographic proof that a relay actually agreed to serve a specific peer, rather than trusting an unauthenticated `p2p-circuit` address, cannot rely on this specification's default behavior to supply that proof — it would need to add its own voucher-verification step before treating a relayed connection as authorized. DCUtR (TRAUTWEIN-ARXIV-26), the mechanism used to upgrade a Circuit v2 relayed connection to a direct one, requires this reservation-and-connection sequence to succeed first as its own precondition; TRAUTWEIN-ARXIV-26 measured that precondition failing for approximately 29% of its campaign's attempts, a figure this specification document does not itself state or bound.
