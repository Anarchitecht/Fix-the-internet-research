## [KLEPPMANN-TPDS-22] A Highly-Available Move Operation for Replicated Trees

**Citation:** Martin Kleppmann, Dominic P. Mulligan, Victor B. F. Gomes, Alastair R. Beresford. "A highly-available move operation for replicated trees." IEEE Transactions on Parallel and Distributed Systems, 2022. DOI 10.1109/TPDS.2021.3118603.
**Retrieved:** full text via https://martin.kleppmann.com/papers/move-op.pdf
**Source URL:** https://martin.kleppmann.com/papers/move-op.pdf
**Domain:** D

### What it does
Lets independent replicas of a tree-structured document (a filesystem directory hierarchy, or a nested XML/JSON structure) each perform a move operation on any node, concurrently and without coordination, while guaranteeing every replica converges to the same tree and that tree never contains a cycle or a duplicated node. The authors first demonstrate the problem empirically: Google Drive, under concurrent moves of the same subtree to two different destinations, either duplicates the moved files or shows an "unknown error" and enters an inconsistent state; Dropbox duplicates the moved files under the same scenario. Both are widely deployed systems whose replicated-tree handling has this defect.

Every update, including node creation and deletion, is represented as a single kind of operation, `Move t p m c`: at logical time `t`, node `c` becomes a child of parent `p`, carrying metadata `m` (for a filesystem, the child's filename). A move operation does not name the node's prior location; applying it removes `c` from wherever it currently sits in the tree and reattaches it under `p`. Node identifiers must be globally unique (for example, UUIDs — Universally Unique Identifiers); timestamps must be globally unique and totally ordered (the paper uses Lamport timestamps, a logical clock construction from Kleppmann and Beresford's own prior citation [9] that pairs a per-replica counter with a replica identifier to produce a total order consistent with causality). Node creation is implemented as a move of a freshly generated ID under its intended parent; deletion is a move to a designated "trash" node ID that does not otherwise appear in the tree, and the algorithm does not recursively remove a deleted node's children, because a concurrent operation might move part of the deleted subtree back out of the trash, and every child of that subtree must be preserved unmodified in that case.

A single-order function, `do_op`, applies one move to the current tree and rejects it (leaves the tree unmodified) if the moved node `c` is currently an ancestor of the destination `newp`, or if `c` equals `newp` — either case would create a cycle. To keep every replica consistent despite each replica potentially receiving operations in a different order, every replica maintains an operation log alongside the tree, in descending timestamp order. Applying a new operation with timestamp `t` proceeds by an undo-do-redo cycle: the replica first undoes every previously applied logged operation whose timestamp exceeds `t` (restoring each such move's previous parent and metadata, recorded in the log entry itself), applies the new operation with `do_op`, then reapplies (redoes) the undone operations in timestamp order. The resulting tree state is always identical to what applying every operation the replica knows about, in increasing timestamp order, from an empty tree would produce — regardless of the actual arrival order — which is what makes application-order independent and guarantees convergence. Conflicting concurrent moves of the same node resolve deterministically: the lower-timestamped move applies first, the higher-timestamped move then applies second and its destination wins. Conflicting moves that would jointly create a cycle resolve by the lower-timestamped move taking effect and the higher-timestamped move being silently ignored (rejected by the cycle check inside `do_op` when replayed in timestamp order).

The paper extends the base mechanism three ways. Hardlinks are supported by having leaf nodes reference a separate file-inode object rather than embedding file data directly, so multiple leaf nodes can reference the same inode; symlinks are leaf nodes holding a path string. Log truncation removes indefinite memory growth: because `apply_op` only ever inspects the log prefix with timestamp greater than the operation being applied, once a timestamp `t` is causally stable — no future operation from any replica will ever have a timestamp of `t` or less — every log entry at or below `t` can be discarded, and trashed nodes below the causally-stable threshold can likewise be garbage-collected. Causal stability is computed, in a system where the replica set is known and each replica generates strictly increasing timestamps over FIFO (First-In-First-Out) links, as the minimum of the most recent timestamp seen from each replica. Sibling ordering (an explicit order among children of the same parent, needed for e.g. an XML element's child sequence) is added by attaching a separate list CRDT (RGA or Logoot) per branch node and embedding that list CRDT's per-element identifier in a move operation's metadata field.

### Measured results
Correctness proof: every stated theorem (unique-parent property, acyclicity, commutativity of move operations, and Strong Eventual Consistency) is mechanically checked in Isabelle/HOL with no unproved assumptions (no use of the `sorry` placeholder). The Isabelle/HOL formalization totals 59 lines of core definitions plus 2,495 lines of proof: 203 lines proving unique parent, 443 proving acyclicity, 450 proving commutativity and convergence, 327 proving Strong Eventual Consistency, 743 defining and proving equivalence of the executable variant, and 779 proving safety of the log-truncation/causal-stability optimization. Checking the complete proof takes 3 minutes on a 2018 MacBook Pro.

Performance evaluation used two Scala implementations — one generated automatically from the Isabelle/HOL definitions via code generation, one handwritten and functionally equivalent but not formally verified — deployed as three replicas on Amazon EC2 c5.large instances in us-west-1 (Northern California), eu-west-1 (Ireland), and ap-southeast-1 (Singapore). Measured round-trip network delay: Ireland–California median 145 ms; Singapore–California median 176 ms. Workload: each replica starts from an empty tree and generates move operations at a fixed rate, each move's parent and child chosen uniformly at random from a pool of 1,000 tree nodes; timestamps are Lamport clocks; node identifiers are 64-bit integers; operations propagate over TCP; each replica runs for 10 minutes per rate to reach steady state.

| Metric | Isabelle-generated code | Handwritten (optimized) code |
|---|---|---|
| Median time to apply a local operation | ~50 µs | ~1–2 µs |
| Median time to apply a remote operation, at saturation | ~1 ms | not separately stated at saturation |
| Peak sustained throughput (CRDT algorithm) | 600 operations/sec | 5,700 operations/sec |
| Peak sustained throughput, leader-based state machine replication (same code, same network, leader in California) | 14,000 operations/sec | 22,000 operations/sec |

The 9.5x throughput difference between the two CRDT implementations (600 vs. 5,700 ops/sec) is attributed entirely to code-generation inefficiency, since both implementations perform functionally identical work. At peak throughput, the optimized implementation performs on average 200 undo/redo operations per remote operation applied. Leader-based state machine replication achieves 23x (Isabelle-generated) or 4x (handwritten/optimized) the CRDT algorithm's throughput on the identical hardware and network, but a single move operation issued by the Irish or Singaporean replica requires a full round trip to the California leader (145–176 ms), roughly five orders of magnitude slower than the 1–2 µs local-CRDT-operation latency; the Singapore/Ireland-to-leader round trips are plotted directly against both CRDT curves in the paper's Figure 7 to make this comparison explicit. A lock-based alternative (acquire a lock from a remote lock server, perform one move, release) is bounded by one round trip per operation and so is limited to 1/176 ms ≈ 5.7 operations/sec when the lock server is in California and the client in Singapore — three orders of magnitude below the optimized CRDT algorithm's 5,700 ops/sec.

### Parameters
Node identifiers: required to be globally unique (paper uses 64-bit integers in the benchmark; suggests UUIDs generally). Timestamps: required to be globally unique and totally ordered (paper uses Lamport timestamps, i.e. a `(counter, replica_id)` pair per its own earlier citation [9]). Benchmark workload pool: 1,000 tree nodes, parent and child chosen uniformly at random per operation. Steady-state measurement window: 10 minutes per operation rate. EC2 instance type: c5.large, three regions (us-west-1, eu-west-1, ap-southeast-1).

### Stated limitations
The algorithm as specified retains every operation in the log indefinitely, so memory use grows without bound unless the causal-stability truncation extension (§3.6) is applied; that truncation itself requires the replica set to be known in advance, requires monotonically increasing per-replica timestamps, and requires FIFO delivery between every pair of replicas — none of which the base algorithm assumes. The base algorithm's benchmark deliberately does not use the log-truncation optimization ("for simplicity we do not use the optimisation discussed in §3.6"), so the measured throughput numbers include unbounded log growth over the 10-minute run and do not measure the truncation optimization's cost or benefit. The optimized implementation's throughput could be raised further by batching operations to amortize undo/redo cost across a batch; the authors state this is left to future work and unevaluated. Sibling ordering (explicit child order within a parent) is not part of the core algorithm; it requires attaching a separate list CRDT per branch node, described but not evaluated in this paper. The paper explicitly identifies a fundamental throughput/latency trade-off rather than a limitation to be removed: leader-based state machine replication gives 4x to 23x higher throughput than the CRDT algorithm on identical hardware, at the price of clients being unable to make updates while offline and of every write requiring a round trip to a leader that may be geographically distant. The authors state applications needing maximum throughput should prefer state machine replication; applications needing minimum response latency or continued availability during network partition should prefer this algorithm. Only one type of update (move) is defined; other document mutation types are represented by encoding them as a move (creation as move-under-desired-parent, deletion as move-to-trash), so the model does not natively express operations outside that encoding.

### Requirements it places on the rest of the system
The transport must deliver every operation to every other replica eventually, but need not preserve delivery order — the replica's own undo-do-redo application logic reorders operations into timestamp order regardless of arrival order — and the paper explicitly assumes an underlying network protocol detects and retransmits lost messages and suppresses duplicates (i.e., reliable, deduplicated delivery is assumed, ordering is not). No central server or consensus protocol is required or assumed; any number of replicas may crash, and any non-crashed subset continues operating. Every replica must retain a full operation log alongside current tree state (not just current state) to support the undo/redo mechanism, and must retain trashed (deleted) nodes and their descendants until causal stability is established, or storage grows unbounded. If log truncation is used, the system needs a mechanism to determine causal stability, which in turn needs the full replica set to be known, monotonically increasing per-replica timestamps, and FIFO-ordered pairwise links. Timestamps issued by different replicas must be globally unique and totally ordered; the paper does not specify how uniqueness is enforced against a Byzantine or misbehaving replica, and assumes correct replicas do not forge timestamps. If sibling ordering is required, another list CRDT (RGA or Logoot, both cited as prior work, not designed in this paper) must be composed per branch node, and its element identifiers must be threaded through the move operation's metadata field.

### Contradicts
None found against other entries in this corpus. Against common assumption, the paper documents that Google Drive's and Dropbox's actual deployed concurrent-move handling is not merely theoretically imperfect but produces observable defects (file duplication in both; an explicit "unknown error" state in Google Drive) under directly reproduced scenarios (§2), which the authors state is the real-world motivation for the algorithm.
