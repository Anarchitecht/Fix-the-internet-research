## [TRAUTWEIN-INFOCOM-24] IPFS in the Fast Lane: Accelerating Record Storage with Optimistic Provide

**Citation:** Dennis Trautwein, Yiluo Wei, Yiannis Psaras, Moritz Schubotz, Ignacio Castro, Bela Gipp, Gareth Tyson. "IPFS in the Fast Lane: Accelerating Record Storage with Optimistic Provide." IEEE INFOCOM, 2024. DOI 10.1109/INFOCOM52122.2024.10621404.
**Retrieved:** full text via https://gipplab.uni-goettingen.de/wp-content/papercite-data/pdf/trautwein2024.pdf
**Source URL:** https://gipplab.uni-goettingen.de/wp-content/papercite-data/pdf/trautwein2024.pdf
**Domain:** A+J

### What it does
Optimistic Provide shortens the time a Kademlia-based InterPlanetary File System (IPFS) node takes to store a provider record (a PUT operation: publishing that this node holds a given piece of content) by ending the record-placement process as soon as it is statistically confident it has found the right peers, instead of waiting for every peer contacted to confirm. The unmodified (classic) PUT operation runs in two phases: a DHT walk that queries progressively closer peers until the three currently-closest-known peers have all responded, and a follow-up phase that pushes the record to the 20 peers closest to the target key found during the walk. The paper's own measurement (section III) finds the DHT walk consumes over 90% of total PUT latency in most cases, because the walk's own termination rule waits for confirmation from the three closest known peers even after the eventual 20 recipients have already been discovered; an unreachable peer among those three stalls the whole walk while the algorithm backtracks to more distant peers (a behavior the paper calls DHT Walk backtracking). Optimistic Provide replaces this rule with three changes. First, it computes, using an estimate of the total DHT population size, a maximum XOR distance from the target key such that any peer discovered inside that distance is a member of the true closest-20 set with probability p_individual; a peer discovered within that distance is stored to immediately, without waiting for the walk to finish. Second, it computes a second maximum average distance for the currently-known set of 20 closest peers such that, with probability p_set, that set already equals the true closest-20 set; once the known set's average distance falls under that threshold, the walk terminates early instead of waiting for the three-closest-peer confirmation. Third, since ending the walk early skips backtracking and can leave a slow or unreachable peer among the 20 recipients in the follow-up phase, the follow-up phase itself returns control to the caller once k' of the 20 contacted peers have responded (k'=5 chosen in this paper's evaluation, tunable), while the remaining queries continue asynchronously in the background rather than being canceled. The distance thresholds behind steps one and two require a live estimate of the total number of peers in the DHT; the paper derives this from Kademlia's own XOR-distance order statistics (the expected distance to the i-th-closest peer among N total peers is 1/(N+1) times i, so measuring several order-statistic distances and fitting a line through the origin yields an estimate of N), sampled for free from the routing-table-refresh lookups every node already performs, corrected for a keyspace-density bias that would otherwise skew the estimate.

### Parameters
- p_individual (probability threshold for immediately accepting a single discovered peer as a member of the closest-20 set): chosen as 0.9 in evaluation; stated as freely tunable.
- p_set (probability threshold for accepting the current known 20-closest-peer set as the true closest-20 set, computed via the expected distance of the hypothetical 10.5th-closest peer): chosen as 0.9 in evaluation; stated as tunable.
- k' (number of the 20 follow-up-phase peers whose responses are awaited before returning control to the caller, remaining queries continuing asynchronously): chosen as 5, based on a cited prior study finding that lowering k to 15 in classic IPFS record replication has negligible impact on availability; stated as configurable.
- Network size estimation rolling window t_window: 2 hours.
- Network size estimation minimum/maximum sample counts S_min / S_max: 16 / 192 lookups (S_min corresponds to one full routing-table refresh; S_max corresponds to one full refresh every 10 minutes for 2 hours); both stated as tunable and affecting estimation accuracy.
- Kademlia identifier length L: 256 bits (used in the order-statistic-based network-size derivation).
- Maximum bucket level k_max for the bias-correction weighting function: 20 for IPFS.
- Routing-table refresh depth in the deployed Kubo and Lotus clients: the first 16 of 256 possible buckets, each refresh issuing 16 lookups.
- DHT walk timeout (both approaches, regional experiment): 3 minutes.
- Kubo (IPFS reference implementation) version supporting Optimistic Provide: v0.20.0 and later.

### Stated limitations
The authors state as future work an investigation of how severe network conditions — network partitioning, high churn, and Sybil attacks — affect Optimistic Provide and its component mechanisms; none of these conditions are evaluated in this paper. They state as future work a deeper investigation into the cause of the observed difference in RPC success-rate variation between the IPFS and Filecoin networks, which this paper does not explain. The network-size estimation method systematically underestimates true network size (6.0% for IPFS, 13.5% for Filecoin, both relative to a full-crawl baseline) because it reuses routing-table-refresh lookups that are biased toward the requesting peer's local keyspace neighborhood and excludes peers made undialable by the same backtracking behavior the paper's mechanism is designed around; the authors state this underestimate does not measurably harm PUT performance in their results but note that a deployment needing more accurate absolute counts would need a separately-derived scaling factor, since the underestimate is consistent across measurement points rather than fully corrected. The full network-size crawl used as the accuracy baseline is itself described only as covering the peers the crawler could find and dial, not as a verified ground truth; the paper treats it as the best available comparison rather than an exact count.

### Requirements it places on the rest of the system
Every participating peer must implement the same threshold-based termination logic to be optimistically stored to during another peer's DHT walk, which the paper achieves by upstreaming the change into the shared go-libp2p-kad-dht implementation used by both the IPFS reference client Kubo and the Filecoin reference client Lotus; the paper states full backward compatibility is maintained, meaning a peer without the update still participates correctly in a walk initiated by an updated peer, but does not state what performance a walk initiated by an updated peer against entirely non-updated peers would achieve. Every peer must independently estimate the live network size to compute the distance thresholds; this estimate is derived only from data the peer's own routing-table-refresh queries already produce, so a peer skipping refreshes or refreshing fewer than the S_min=16 lookups per rolling 2-hour window operates on state accuracy the paper does not evaluate. Both the p_individual and p_set thresholds assume DHT peer identifiers are uniformly randomly distributed across the identifier space (stated explicitly in section IV-B); a system where identifiers cluster non-uniformly (through adversarial identifier selection or a non-uniform assignment scheme) would compute unreliable proximity thresholds, and the paper's stated future work on Sybil-attack impact has not yet examined this. Reducing k' below 20 in the follow-up phase requires accepting that a record's full 20-way replication is asynchronous rather than confirmed at return time; a caller that needs the paper's own PUT operation to guarantee replication before returning must use the done strategy, whose latency the paper measures separately and which is markedly slower.

### Contradicts
None found. This paper's own comparison to Trautwein et al.'s earlier IPFS measurement study (cited as reference [5], "Design and evaluation of IPFS: a storage layer for the decentralized web") is presented as complementary, not contradictory: this paper describes that earlier study as reporting GET performance as "already satisfactory" while this paper's contribution addresses PUT latency specifically. That earlier paper is the source of the 112-second 90th-percentile content-storing latency figure cited secondhand in ZHANG-FC-23 in this corpus; ZHANG-FC-23 should be checked against the original IPFS measurement paper directly rather than against this Optimistic Provide paper, which measures a modified protocol and different latency figures (6.3-49.8 s baseline).
