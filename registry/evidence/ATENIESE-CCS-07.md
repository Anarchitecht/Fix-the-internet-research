### What it does
Provable Data Possession (PDP) lets a client that has stored a file at an untrusted remote server verify that the server still holds the complete, unmodified file, without the client retrieving the file or the server transmitting the file back. The client generates a proof request (a challenge) naming a small, randomly chosen subset of the file's blocks; the server computes a short response over exactly those blocks; the client checks the response against metadata it kept locally. Because the check touches only a sampled subset of blocks rather than the whole file, both server-side computation and the data transmitted per challenge are held constant, independent of file size, so long as the server actually holds every block requested.

The scheme is built from a homomorphic verifiable tag (HVT): a short, cryptographically unforgeable per-block credential that lets the server prove it holds one or more specific blocks without transmitting those blocks, and lets tags for multiple blocks be combined into one aggregate value that still checks against the corresponding aggregate of the underlying blocks. Setup: the client picks a public/secret key pair, computes one tag per file block (each tag bound to that block's position by a one-time index derived from a secret value and a global counter, preventing tag reuse across positions or files), and sends the file plus all tags to the server; the client then deletes its local copy and keeps only a small constant amount of key material. Challenge: the client picks a fresh random key for a pseudo-random permutation and sends a challenge naming how many blocks to sample (`c`) and the keys needed to derive which `c` block indices are being requested; the server locates those blocks and their tags, combines the requested tags into one aggregate value `T` and computes a second aggregate value `ρ` from the same blocks raised to a client-supplied random exponent; the client verifies the algebraic relation between `T` and `ρ` holds, which is possible only if the server actually possessed every one of the `c` requested blocks (in the paper's strong variant, S-PDP) or their sum (in the paper's efficient variant, E-PDP). The paper's key point of difference from the schemes it compares against is blockless verification: the server never returns the actual data, only an aggregate cryptographic value, so verification bandwidth stays constant regardless of block size or count.

Two constructions are given. S-PDP assigns each sampled block an independent pseudo-random coefficient before combining tags, which the paper states guarantees the server possessed each of the `c` requested blocks individually. E-PDP sets every coefficient to 1, reducing server and client computation to a single modular exponentiation each, at the cost of only guaranteeing possession of the sum of the requested blocks rather than each block individually; the paper argues this weaker guarantee is not a practical concern because a cheating server would need to precompute and store an astronomically large number of block-sum combinations to exploit the gap (for n=1,000 blocks and c=101 sampled per challenge, on the order of 10^140 stored values).

### Parameters
- File block size: 4 KB, chosen (per Fig. 6's measured pre-processing-vs-challenge tradeoff) to minimize server effort; the paper states the best balance occurs at "natural file system and memory block sizes of 4-64 KB."
- RSA modulus size: 1024 bits, used throughout all reported experiments.
- Sample size `c` (blocks queried per challenge): worked example uses c=460 for 99% confidence and c=300 for 95% confidence, both at t=1% of n deleted; general closed-form bound given as a function of n, t, and c (Section 5.1), with the paper noting detection probability at fixed `t`-as-a-fraction-of-n is achievable with `c` independent of the total block count n.
- Security parameters κ, ℓ, λ: defined as construction parameters for the pseudo-random function, pseudo-random permutation, and public-verifiability threshold respectively; the paper gives no single numeric default, deferring to standard cryptographic parameter sizes (e.g., ℓ=160 is used as a typical value in one computation-cost comparison).

### Stated limitations
The paper states E-PDP guarantees possession only of the sum of the requested blocks, not of each individual block, unlike S-PDP; it argues (not measures) that exploiting this gap requires a server to precompute and store a combinatorially infeasible number of block-sum values, and gives a numeric example (n=1,000, c=101) rather than a proof that no smaller feasible attack exists for all parameter choices. The paper states it leaves devising a publicly-verifiable PDP scheme with challenge and response sizes smaller than one file block as "an open problem" — the public-verifiability variant it does construct has communication cost "slightly larger r than the size of a file block," which the paper flags as worse than the main scheme's constant, sub-block-size communication. The paper states the KEA1-r (Knowledge of Exponent Assumption, RSA variant) cryptographic assumption underlies its main scheme's security proof, and separately gives an alternative construction avoiding that assumption at the stated cost of "a significant amount" of added network communication. The paper states client-side pre-processing throughput (162 KB/s) is the limiting performance factor for E-PDP overall, since challenge and verification are far cheaper; it offers two unmeasured mitigations — pre-processing is a one-time cost per file (unlike repeated challenges) and is "completely parallelizable" across files or, given shared key material, within a single file — without measuring parallelized throughput. The paper states its probabilistic detection guarantee applies only when the server has deleted or corrupted a fraction `t` of the blocks; detecting the loss of a small, fixed absolute number of blocks (rather than a fraction of n) requires proportionally larger `c` as n grows, which the paper's own bound formula implies but does not separately tabulate.

### Requirements it places on the rest of the system
Requires the client to retain the full file (or reconstruct it) at Setup time in order to compute one tag per block before deletion, and requires the client to retain a small constant amount of secret key material (about 3 KB in the paper's 4 GB worked example) for the life of the stored file; losing that key material makes the client unable to issue or verify any future challenge. Requires the storage server to retain the tag set alongside the file: the paper's worked example adds 128 MB of tag storage for a 4 GB file (roughly 3.2% overhead), so any storage layer this mechanism sits on top of must accommodate that fixed per-file overhead in addition to the raw file bytes. Requires the client to be able to issue challenges specifying particular sampled block indices and receive a response tied to exactly those indices — this means the underlying storage or transport layer must let the verifying party address individual fixed-size blocks of a stored object by position, rather than only by whole-object retrieval; a storage layer that reshapes, recompresses, or re-chunks the object between Setup and Challenge without preserving block boundaries breaks the tag-to-block binding the scheme relies on (the paper does state the server may store the file however it likes, including compressed, provided it can still answer per-block challenges correctly). Provides only a possession check, not a retrievability guarantee: the paper explicitly separates its own scheme from proof of retrievability (POR), so any system requiring a proof that the client (or a third party) could actually reconstruct the full file from what the server holds needs POR or POR-equivalent verification (see ATENIESE-CCS-07's own Related Work discussion of Juels and Kaliski), not PDP alone. Detection is probabilistic over a deleted-block fraction: a system that must detect the loss of a small fixed number of blocks regardless of total file size needs to size `c` accordingly (per the paper's own formula), and PDP's guarantee for t below the sampling resolution is correspondingly weaker.

### Contradicts
None found against other entries in this corpus as currently extracted. The registry's own citation note (`why_needed`) states this paper's guarantee "does not necessarily prov[e] the client could reconstruct the whole file if some blocks were in fact lost" and calls out possession-versus-retrievability as a commonly conflated distinction — the retrieved full text confirms this directly, stating its schemes are a distinct, more restricted guarantee from proof of retrievability (POR) as introduced by Juels and Kaliski, whose POR scheme (per this paper's own related-work description) applies only to encrypted files and only to a number of queries fixed in advance, while this paper's PDP schemes apply to unencrypted, public data and place no bound on the number of challenges.
