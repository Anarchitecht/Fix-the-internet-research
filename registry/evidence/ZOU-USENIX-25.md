## [ZOU-USENIX-25] PoisonedRAG: Knowledge Corruption Attacks to Retrieval-Augmented Generation of Large Language Models
**Citation:** Wei Zou, Runpeng Geng, Binghui Wang, Jinyuan Jia. "PoisonedRAG: Knowledge Corruption Attacks to Retrieval-Augmented Generation of Large Language Models." 34th USENIX Security Symposium, 2025. Seattle, WA, August 13-15, 2025.
**Retrieved:** full text via https://www.usenix.org/system/files/usenixsecurity25-zou-poisonedrag.pdf
**Source URL:** https://www.usenix.org/conference/usenixsecurity25/presentation/zou-poisonedrag
**Domain:** B

### What it does
PoisonedRAG makes a large language model (LLM) generate an attacker-chosen answer to an attacker-chosen question, by inserting a small number of crafted texts into the knowledge database that a Retrieval-Augmented Generation (RAG) system searches before answering. RAG has three components: a knowledge database of texts, a retriever that embeds a question and the database's texts into vectors and returns the top-k texts most similar to the question, and an LLM that generates an answer using the retrieved texts as context. The attack requires each malicious text to satisfy two conditions at once: the retrieval condition (the retriever's similarity score between the malicious text and the target question must be high enough for the text to land in the top-k retrieved set) and the generation condition (the LLM must output the attacker's target answer when that malicious text is used as its context).

The mechanism splits each malicious text P into two concatenated parts, P = S + I, so the two conditions can be engineered separately instead of fighting each other in one string (the paper shows that making a text maximally similar to the question, e.g. copying the question itself, achieves retrieval but not generation). I is generated first: the attacker prompts an LLM (GPT-4 in the experiments) with the target question and target answer and asks it to write a short passage of a stated length that would produce the target answer if used as context; if the RAG-side LLM does not produce the target answer when tested against this passage, the passage is regenerated, up to a maximum number of trials. S is then crafted to satisfy the retrieval condition without breaking I's effect. Two settings are defined by what the attacker knows about the retriever: in the black-box setting (no access to retriever parameters or queries), S is simply set equal to the target question itself, on the reasoning that a question is most similar to itself; in the white-box setting (retriever parameters known), S is instead solved for by gradient-based adversarial-text optimization (the paper uses HotFlip) to directly maximize the embedding similarity between S+I and the target question's embedding under the retriever's own encoder.

### Parameters
- N: number of malicious texts injected per target question; default 5.
- k: number of texts the retriever returns per query; default 5, swept up to 50 in the Knowledge Expansion defense test.
- L: maximum number of regeneration trials allowed when crafting I; default 50, with saturation of effectiveness observed by L=10.
- V: target word length of the generated passage I; default 30.
- LLM decoding temperature: 0.1 for the RAG-side answering LLM; 1 for the GPT-4 call used to generate I.
- Retriever: Contriever by default; Contriever-ms and ANCE also tested; similarity measured as the dot product of question and text embedding vectors by default.
- White-box optimization method for S: HotFlip (a discrete gradient-based adversarial-text search method), used to solve Equation 5 in the paper (maximizing embedding similarity between S+I and the target question).
- Target-question selection: 10 close-ended questions per dataset per trial, repeated 10 times excluding already-used questions, giving 100 target questions total per dataset.

### Stated limitations
The paper states PoisonedRAG does not reach a 100% attack success rate and defers a per-case failure analysis to an appendix rather than characterizing the failure condition in the main text. The authors state their own paraphrasing defense does not paraphrase the knowledge-database texts themselves, only the incoming question, "due to high computational costs," so the defense as tested is a partial mitigation by the authors' own design choice, not a ceiling on what paraphrasing could achieve if applied to the corpus. The authors state it is "still an open challenge to develop a perfect metric" for automatically judging whether a generated answer matches an attacker's target answer (their substring-matching proxy is validated only against the authors' own manual judgments, not independent annotators). Listed future work: extending optimization-based methods (such as adapting the GCG jailbreak-suffix method) to craft I itself, jointly optimizing a single malicious text against multiple target questions at once (currently each malicious text targets one question), and developing new defenses, since all four defenses evaluated in Section 7 (paraphrasing, perplexity detection, duplicate-text filtering, knowledge expansion) are stated to fail to fully stop the attack.

### Requirements it places on the rest of the system
The attack requires write access to the RAG system's knowledge database — an attacker who can insert texts that the retriever will later index and search. It requires the retriever to support a fixed similarity function between a question embedding and a text embedding (dot product in these experiments); the black-box variant needs no further access, but the white-box variant requires the attacker to know the retriever's parameters (specifically its two encoders, one for questions and one for texts) well enough to run gradient-based optimization against them. The black-box variant additionally requires access to some LLM (not necessarily the one used by the target RAG system) capable of following an instruction to write a short passage that entails a given answer to a given question; this LLM-generation step is itself iterative and needs a way to test whether a candidate passage, used alone as context, causes an LLM to output the target answer, which the paper implements by querying an LLM up to L times and checking the output. The attack's retrieval condition assumes the retriever ranks by embedding similarity to the question and returns a bounded top-k set; a retrieval method that does not expose or is not well-approximated by such a scoring function (for instance, a privacy-preserving retrieval channel that returns a match without exposing similarity scores or embeddings) is not evaluated here as either a target or an obstacle. The knowledge-expansion defense result implies that any system relying on “retrieve enough texts to dilute the attacker's texts” must trade retrieval-set size against the LLM's context-window computation cost, since the paper states this defense “incurs large computation costs for an LLM to generate an answer due to the long context.”
