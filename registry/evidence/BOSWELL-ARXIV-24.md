## [BOSWELL-ARXIV-24] Measuring NAT64 Usage in the Wild
**Citation:** Elizabeth Boswell, Stephen McQuistin, Colin Perkins, Stephen Strowes. "Measuring NAT64 Usage in the Wild." arXiv preprint (CoRR), 2024. DOI 10.48550/ARXIV.2402.14632.
**Retrieved:** full text via https://arxiv.org/abs/2402.14632
**Source URL:** https://arxiv.org/abs/2402.14632
**Domain:** L

### What it does
NAT64 lets an IPv6-only host reach an IPv4-only destination by translating between the two address families at a middlebox, given a DNS64 resolver that synthesizes an IPv6 AAAA record from the destination's IPv4-only A record. This paper does not build NAT64; it measures how widely NAT64 and DNS64 are actually deployed on the public Internet and what reachability and latency cost crossing one imposes, using the RIPE Atlas measurement platform (a distributed network of volunteer-hosted measurement probes).

Detection method: four tests run from each probe. DNS Test 1 sends a DNS AAAA query for the reserved name `ipv4only.arpa` (RFC 7050); a working DNS64 resolver returns a synthesized AAAA record, while a plain IPv6-only host without DNS64 gets NXDOMAIN. DNS Test 2 repeats the same query against a second IPv4-only name (`time-c-b.nist.gov`), because the paper found some resolvers correctly synthesize a record for `ipv4only.arpa` specifically but not for other IPv4-only names. The Standard Prefix ping test sends an ICMPv6 ping to a fixed IPv4 target address encoded under the standard NAT64 prefix (`64:ff9b::/96`), run from every probe regardless of DNS-test outcome, to catch probes that can reach a NAT64 device without having received the prefix via DNS64. The Custom Prefix ping test repeats that ping using whatever non-standard prefix a probe's DNS Test 1 response supplied, and is also run on other probes in the same Autonomous System (AS, an internet routing domain) as a probe that received a non-standard prefix, to detect probes whose own configured DNS resolver is unaware of an available NAT64 device even though the network path has one. Passing tests sorts probes into two device categories: NAT64+DNS64 (fully working path-and-name-resolution pair) and NAT64-only (working translation path with no automatic AAAA synthesis, requiring the client to already know or construct the address).

Path characterization method: from the dual-stack probes identified as having working NAT64, the authors ran Paris traceroute (a traceroute variant tolerant of per-flow load balancing) to a fixed set of IPv4-only targets, once natively over IPv4 and once over IPv6 through the NAT64-synthesized address, and compared the two paths' success rate, hop count, count of non-responding ("missing") hops, and round-trip time (RTT).

### Parameters
- Test window: several weeks, December 2022-January 2023; 6,154 participating probes out of RIPE Atlas's roughly 12,000.
- Detection tests: 4 (DNS Test 1 against `ipv4only.arpa`, DNS Test 2 against `time-c-b.nist.gov`, Standard Prefix ping to 91.201.7.243 encoded as `64:ff9b::5bc9:7f3`, Custom Prefix ping using each probe's own synthesized prefix).
- Preliminary traceroute round: 183 of 205 dual-stack NAT64-capable probes online (9 NAT64+DNS64, 14 NAT64-only usable after filtering); 3 UDP probe packets per hop (Paris traceroute); 18 IPv4-only targets (7 NTP servers, 11 RIPE Atlas anchors), chosen for geographic spread; raw yield 3,565 IPv4/NAT64 path pairs, reduced to 1,230 usable pairs (54 probes, 18 destinations) after excluding 2,320 traceroutes with no hop matching the NAT64 prefix (mostly targeting a non-ICMP-responsive Hurricane Electric deployment) and 15 other anomalies.
- Recurring traceroute round: 37 of the 54 usable probes still available; hourly traceroutes over 41 hours to 14 of the 18 targets (4 anchors had gone offline); final usable set 15,564 IPv4/NAT64 path pairs from 34 probes, after removing 5 probes' data (incomplete runs), the 41st hourly run, 6 unresponsive targets, and 1,076 pairs whose NAT64 leg never touched the NAT64 prefix.

### Stated limitations
The authors state they have no mechanism to detect a CLAT (customer-side NAT46, used in 464XLAT deployments) because CLAT translation hides IPv6 addresses on the path before they reach the measurement point, so the paper's results measure only standalone NAT64/DNS64 deployment and explicitly exclude 464XLAT. The authors state RIPE Atlas gives wide coverage of residential and operator networks but limited visibility into mobile networks, and note a wireless-testbed platform such as the discontinued MONROE would have given broader mobile-network visibility, which was unavailable to them. The authors state traceroute measurements do not directly reflect real application performance; they characterize traceroute-visible path properties (hop count, missing hops, RTT) as a proxy, not application-level latency or throughput, and state that further application-performance measurement is out of scope for this paper. The authors state their AS-assignment heuristic for locating a NAT64 device (matching the announced prefix's AS, or falling back to the last non-NAT64-prefixed hop's AS) can be indeterminate, in which case they default to assuming the NAT64 is in the probe's own IPv6 AS — a default that could misclassify some remote deployments as local. The authors state that one identified NAT64 device does not check the source address of translated packets, calling this a minor security concern because it could be used to hide the source AS of traffic; this is reported as an observed configuration issue in one deployment, not a general property of NAT64.

### Requirements it places on the rest of the system
Any peer-reachability design that assumes IPv6-only clients can always reach IPv4-only destinations, or vice versa, through NAT64 needs to account for measured NAT64 deployment being rare among the probes tested (255 of 6,154, about 4.1%) — most tested networks have no detectable NAT64 path at all, so a design cannot assume a translator will be present on an arbitrary IPv6-only client's path. Where a NAT64 path does exist, a peer-to-peer transport or hole-punching layer that depends on stable, low round-trip-time paths needs to tolerate the measured average 23.13% longer hop count and 17.47% higher RTT relative to native IPv4, and needs to tolerate substantially reduced traceroute-level path visibility (a mean 38.06% of hops non-responding on NAT64 paths versus 16.52% on native IPv4), which affects any mechanism relying on path-hop diagnostics (e.g., a NAT-traversal probe that infers translator behavior from ICMP responses) rather than end-to-end reachability alone. A design that discovers NAT64 presence by relying solely on the RFC 7050 standard prefix-discovery DNS query needs to account for this paper's finding that this method alone is insufficient: the paper's four-test method found working NAT64-only paths on hosts that never received a synthesized AAAA record via that discovery mechanism, so a design that checks only for a synthesized address will undercount reachable translators. A design that treats "the NAT64 device is inside my own network" as a security or trust boundary needs to independently verify that assumption per deployment, since the paper found 7 of 34 measured cases used a translator outside the probe's own AS.
