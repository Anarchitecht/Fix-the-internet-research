## [REYNOLDS-MIDDLEWARE-03] Efficient Peer-to-Peer Keyword Searching
**Citation:** Patrick Reynolds, Amin Vahdat. "Efficient Peer-to-Peer Keyword Searching." ACM/IFIP/USENIX Middleware, 2003. DOI 10.1007/3-540-44892-6_2.
**Retrieved:** full text via https://piki.org/patrick/papers/search.pdf
**Source URL:** https://piki.org/patrick/papers/search.pdf
**Domain:** B

### What it does
The system answers multi-keyword boolean-AND queries over a distributed inverted index built on a distributed hash table (DHT), so that a peer-to-peer file-storage or archival system gets keyword search without a central index. Each keyword maps, via the DHT's hash function, to the single node responsible for storing the full list of document IDs containing that keyword (a vertically partitioned index — one node per keyword, as opposed to a horizontally partitioned index in which every node holds a shard of every keyword's list and every query must contact every node). Vertical partitioning bounds the number of nodes an n-keyword query must contact to n, independent of network size, while horizontal partitioning requires contacting every node regardless of query size.

Resolving a single-keyword query means contacting the one node holding that keyword's document-ID list. Resolving a multi-keyword AND query naively requires transferring an entire document-ID set from one keyword's node to another to compute the intersection, a transfer whose size scales with the number of documents containing the more common keyword, not with the size of the final answer. The paper's core mechanism replaces most of that transfer with a Bloom filter — a bit-array structure that lets a receiver test set membership with a tunable, one-directional error rate (false positives possible, false negatives never) — computed by the sending node over its own document-ID set and sent in place of the full set. The receiving node tests every member of its own set against the filter, sends back the (smaller) set of matches, and the false positives introduced by the filter's error rate are stripped out by the originating node by re-intersecting against its full local set. Sending only the filtered candidate matches directly to the client instead of returning them to the originating node for filtering trades correctness (some false positives reach the client) for eliminating one message round trip, with the tradeoff made at run time once the false-positive-rate parameters are known.

Three further mechanisms reduce cost. Caching lets a node store another keyword-node's Bloom filter or partial filter locally, so a repeated query for a keyword pair can skip a network round trip entirely on a cache hit; sending filters in fixed contiguous hash-space chunks lets a cache store and reuse partial filters. Incremental results retrieve only as many document IDs as the client actually wants (starting from an initial small batch M and doubling it if too few results survive intersection), rather than the full match-list, which the paper argues reduces cost to a constant per query when the requested result count is small relative to the true match count — except when the true match count is itself smaller than requested, in which case incremental retrieval degenerates to fetching the entire search space, and its benefit disappears. Virtual hosts address capacity heterogeneity by mapping each physical node to a number of DHT positions (virtual host IDs) proportional to that node's network and CPU capacity relative to a fixed baseline, concentrating more of the keyword-to-node assignment load onto more capable machines; an optional scaling factor multiplies the number of virtual hosts per node further to reduce the chance any one node is assigned a disproportionate share of the keyword-ID space.

Dataset: a real crawled document set of 1.85 GB of HTML, 1.17 million unique words across 105,593 documents (crawl depth 5 from 100 seed URLs); a real search-query trace of 95,409 searches with 45,344 unique keywords, drawn from a 10-day January 2002 IRCache proxy log. Document IDs assumed 128-bit hashes. Simulated host characteristics: three network-speed distributions (all-modem, all-backbone/WAN, and a heterogeneous mixture based on Saroiu et al.'s measured Gnutella population); CPU speeds drawn from a bell curve centered at 750 MIPS; local storage from 1 MB to 100 MB (heavy-tailed); hosts placed at random on a simulated 2,500-mile-square grid with signals assumed to propagate at 100,000 miles/second. CPU costs modeled as 1,500 simple operations per index-lookup hit, 500 per element intersected, 10,000 per document ID inserted into or checked against a Bloom filter — the paper states these are chosen as upper bounds on real CPU cost. Simulator validated by hand-calculated small traces and by comparing simulated Bloom-filter-size curves against the paper's own closed-form analytical prediction (stated as closely matching).

### Parameters
- Document identifier size: 128 bits (assumed content-hash length).
- Bloom filter false-positive formula used: p_fp = 0.6185^(m/n), m = filter bits, n = set size (from Fan et al.'s Summary Cache analysis, cited).
- Bloom filter size sweep: 0 to 40 bits/entry; optimum found at 18 (no caching) or 24 (with caching) bits/entry.
- Bloom filter invocation threshold sweep: 1 to 100,000 documents; optimum found at ~300 for the IRCache trace.
- Allowed false-positive rate in returned results: 0%, 1%, 10% tested.
- Baseline host for virtual-host assignment: 57.5 MIPS CPU, 30 Kbit/s network links (chosen as the speed needed for 5,000 Bloom operations/second).
- Virtual host scaling factor: tested at 1, 10, 100 (multiplies each node's baseline-relative virtual host count).
- Network size swept: 1 to 10,000 simulated hosts.
- Network-speed distributions compared: all-modem, all-WAN/backbone, heterogeneous (Saroiu et al.'s Gnutella measurement-based mixture).

### Stated limitations
The simulator does not model network contention; the authors state that per-query averages would be worse than reported if any individual node's network connection becomes saturated, and note this limitation is mitigated (not eliminated) under network conditions where individual nodes have more spare bandwidth or where virtual hosts spread load away from underprovisioned hosts. Incremental results provide no benefit, and can increase both bytes sent and latency, when a query's true result count is nonzero but smaller than the number of results the client requested — a case the paper illustrates with a multi-keyword query where each keyword individually matches millions of documents but only a handful of documents match all keywords together, forcing the full search space to be considered regardless of the incremental-retrieval optimization. Bloom filters and caching alone (without incremental results) leave both bytes sent and end-to-end query time roughly proportional to the number of documents in the system — they are described by the authors as constant-factor, not asymptotic, improvements. Bloom filters complicate result ranking: because a Bloom filter only conveys set membership and not auxiliary data (such as within-document word position or ranking score), sending only the compressed filter loses the information needed to rank results on the criteria of the keyword whose set was filtered; the authors state ranking is more important than the marginal savings from full Bloom compression, but leave the choice a runtime tradeoff rather than resolving it. The combination of incremental results (sending non-contiguous hash-space chunks ordered by rank) and the CPU-saving optimization of testing only contiguous hash-space chunks against a filter are described as mutually exclusive — a system cannot have both simultaneously. Load balancing under vertical partitioning is uneven because keyword appearance popularity and search popularity are both roughly Zipf-distributed, unlike the more even distribution a horizontally partitioned index would produce; virtual hosts only shift more load onto more capable nodes, they do not make the underlying load distribution itself more even, and the authors' claim that this is acceptable rests on the assumption that peer-to-peer networks are generally over-provisioned, which the paper does not itself measure. The paper's results are drawn from one document set and one search trace; the authors state they do not expect other workloads to change the benefits significantly but do not test any other workload to confirm this. Update discovery (detecting new, removed, or modified documents) is assumed to use a "push" model in which clients notify the index directly, rather than crawling; the paper does not evaluate a workload with high update rates, since it assumes queries will dominate updates for its target file-storage and archival-storage use cases.

### Requirements it places on the rest of the system
- The mechanism requires a DHT layer beneath it to map each keyword to the node responsible for that keyword's document-ID list; the paper explicitly treats content/document placement as an orthogonal problem the DHT and storage layer solve separately, and assumes no benefit from co-locating a document with the keyword entries pointing to it.
- Vertical partitioning requires that the number of participating nodes exceed the average number of keywords per document for its claimed insert/update cost advantage over horizontal partitioning to hold; below that ratio, horizontal partitioning's single-node update cost becomes cheaper.
- The false-positive-elimination step (sending B intersect F(A) back to the originating node sA rather than directly to the client) requires an extra round trip that the mechanism trades off explicitly against sending unfiltered, partially-incorrect results straight to the client; a component further downstream that needs an exact result set must keep this extra round trip, while one that tolerates a bounded false-positive rate can drop it.
- Ranking of results using a keyword's own auxiliary data (word position, per-document score) requires transmitting document-level detail alongside the Bloom-filtered candidate set; a design that keeps the compressed-filter-only path for bandwidth reasons gives up the ability to rank on that keyword's contribution, and the paper does not supply a mechanism that gets both.
- The system assumes queries vastly outnumber document updates and that most files change rarely if at all; a deployment with high update rates relative to query rates was not modeled and the cost trade-off between vertical and horizontal partitioning would need to be re-derived for it.
- Caching's benefit is contingent on repeated queries or repeated keyword pairs in the workload; the measured >50% bandwidth reduction from caching is specific to the IRCache trace's actual query-repetition structure and is not derived as a property that holds for an arbitrary or adversarially chosen query distribution.

### Contradicts
None found against other entries in this corpus. Relevant for cross-referencing against BRIEF.md's open-problem 1 (ranked full-text search across peers at web scale, "~6 MB per query for 3 billion documents" per Li et al.): this paper reports under 1 KB per query, but at a far smaller scale (105,593 documents, 1.17 million unique words) and using boolean-AND matching with no ranking on the compressed path, not the ranked full-text retrieval Li et al.'s bound addresses — the two figures describe different problems and are not a direct contradiction.
