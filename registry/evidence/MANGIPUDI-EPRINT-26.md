## [MANGIPUDI-EPRINT-26] Auditable Continuous Group Key Agreement
**Citation:** Easwar Vivek Mangipudi, Maddie Gorman, Sasha Levinshteyn. "Auditable Continuous Group Key Agreement." IACR Cryptology ePrint Archive, 2026. DOI not stated in source.
**Retrieved:** full text
**Source URL:** https://eprint.iacr.org/2026/1710.pdf
**Domain:** H

### What it does
Auditable CGKA (Au-CGKA, where CGKA is Continuous Group Key Agreement, the key-refresh mechanism underlying Messaging Layer Security, MLS, RFC 9420) lets a designated auditor committee recover the encryption key of any past epoch of an end-to-end encrypted group chat, for compliance audits, while every ordinary group member checks at admission time that recovery will actually be possible for that epoch, so a broken escrow is refused before the epoch is accepted rather than discovered only when an audit later fails. In each MLS epoch a single member, the committer, rotates the group's keys through the standard TreeKEM update path and posts a commit message to a public, append-only log kept by the delivery service. Au-CGKA adds three objects to that commit: a commitment c_root binding the epoch's root secret e_se, an escrow ciphertext holding N Shamir secret shares of e_se — one per auditor-committee member — encrypted under each auditor's post-quantum public key, and a zero-knowledge proof (a STARK, Scalable Transparent Argument of Knowledge — a proof system requiring no trusted setup) that the escrow ciphertext decrypts to a valid Shamir sharing of the same value c_root commits to. Every member derives the epoch secret itself through the ordinary MLS key schedule and checks it against c_root; a mismatched escrow is rejected at admission by any honest member that performs the check. Recovery is per-epoch independent: any threshold t of the N auditors can jointly decrypt their shares and reconstruct e_se for one target epoch without touching any other epoch's escrow. The auditor committee stays offline except when an audit is requested. The proof's only in-circuit work is the escrow's well-formedness and the commitment opening; the MLS key schedule and the TreeKEM update path are not encoded in the circuit, which keeps the proof's cost independent of group size.

### Parameters
- Auditor committee size N = 5, threshold t = 3, held constant through every reported measurement (a 3-of-5 threshold scheme).
- Encryption for the MLS update path and the escrow's Module-LWE-based post-quantum public-key encryption: ML-KEM-768 throughout.
- FRI query count derived from the target security level: n_q = 156 at branching factor l_b = 2, chosen so n_q · l_b ≥ 2·(128+24+4), leaving 135 quantum bits of security after the knowledge-soundness charge, against the paper's own 2^21 event-class bound.
- Published commitment truncated to l_pub = 16 lanes, giving a 64 B commitment (the paper separately reports a 32 B stand-in digest width used as a placeholder in the reference implementation).
- Group-size sweep: update-path depth h_e from 4 to 20, corresponding to group sizes 16 to approximately 1,048,576 (2^20) members.
- Measurement basis: each reported figure is the arithmetic mean of five runs at the operating point, and of three runs per depth in the sweep, on a verified-idle Apple M5 Pro with 48 GB RAM.

### Stated limitations
The auditability guarantee holds only for epochs an honest member admits: if every member of a group colludes, the group can accept an epoch whose escrow holds a value different from the actual epoch secret, and no check performed from the log alone can detect this, because an admission check cannot recompute a secret it does not itself hold. The paper states this case is explicitly out of scope. The auditor committee's long-term decapsulation keys are not erasable — each auditor must retain its key indefinitely because an audit may be requested arbitrarily far in the future — so adaptive corruption of an auditor unavoidably exposes that key; the paper's secure-erasure model treats this key, alone among all protocol secrets, as persistent rather than erasable. The scheme deliberately trades forward secrecy against the auditor committee for recoverability: a coalition of t auditors assembled at any point in time can recover every past epoch, and no later rekeying operation removes that ability. The construction does not authenticate or verify the TreeKEM update path itself — the escrow's correctness is proven, but "the auditor recovers the epoch keys but obtains no independent account of how they were distributed" — group-management authentication is left to a complementary mechanism (TreeSync, cited as orthogonal). Reported figures exclude the MLS signature, which the prototype does not implement. The custom STARK backend's security levels are conditional on an assumption the paper labels (A3') and on the ethSTARK conjecture underlying the FRI commitment row, both unproven cryptographic conjectures rather than proofs. Absolute timings are stated as single-machine research-prototype figures that "drift by a few percent with sustained load."

### Requirements it places on the rest of the system
Requires a public, append-only log maintained by a delivery service that every commit message is posted to, and against which any member or third party can check an escrow's proof without trusting the committer or the server — the paper's stateless verification model needs this log and nothing else. Requires the underlying protocol to be MLS-shaped: a TreeKEM update path producing an epoch root secret through the standard RFC 9420 key schedule, since the escrow commits to that specific value without re-deriving it in-circuit. Requires an auditor committee of N designated parties, fixed at deployment, whose public keys under a post-quantum Module-LWE-based encryption scheme are known to every committer at commit time; recovery requires any t of these N to come online and jointly decrypt. Requires every group member to enforce the secure-erasure discipline already required by ordinary MLS — deleting each ephemeral secret (path secrets, node secrets, rotated HPKE secrets, the sharing randomness, individual Shamir shares, the STARK witness) immediately once no longer needed — because the paper's adaptive security proof holds specifically in this secure-erasure model and a party that fails to erase exposes more than the model accounts for. Requires the auditor committee's long-term decapsulation keys to be protected against compromise for the full retention period the deployment cares about, since these keys are never erased and their exposure at any point recovers every past epoch's secret. Does not require or provide any mechanism for detecting a fully colluding group; a caller relying on Au-CGKA for compliance against an adversarial group, not merely an adversarial network, needs an additional mechanism outside this protocol.
