### What it does
Chord answers one question for a peer-to-peer system: given a key, which node in the network is responsible for storing that key's associated value. It provides only this one operation, `lookup(key) -> node`, and leaves data storage, replication, and caching to the application built on top of it.

Chord assigns every node and every key an identifier by hashing (the paper uses SHA-1) the node's IP address or the key's content into the same fixed-length identifier space, arranged as a circle (the identifier ring) that wraps from the highest value back to zero. A key is assigned to its successor: the first node whose identifier is equal to or follows the key's identifier when moving clockwise around the ring. This assignment is a form of consistent hashing, chosen because when a node joins or leaves, only the keys assigned to that node's immediate ring neighbors need to move, not the whole key space.

Every node maintains a successor pointer (the next node clockwise on the ring) and a finger table: a routing table whose i-th entry points to the first node succeeding the current node's identifier plus 2^(i-1) (using a fixed identifier length in bits, so the finger table has one entry per bit). A lookup is resolved by forwarding the query to the finger-table entry with the largest identifier that still precedes the target key, repeatedly halving the remaining identifier-space distance to the key at each hop until the query reaches the key's successor.

Because only the successor pointer is required for correctness (a node with an empty or wrong finger table can still find the right key eventually by walking successor pointers, just more slowly), Chord separates a fast path (the finger table, an optimization) from a correctness-critical path (successor-pointer maintenance). New-node joins and node departures are handled by a periodic background "stabilization" protocol: each node periodically asks its successor for the successor's own predecessor, and updates its own successor pointer if that predecessor turns out to be a more accurate (or newly joined) node; each node also notifies its successor of its own existence, letting the successor update its predecessor pointer. Finger-table entries are corrected by the same periodic process, run independently by each node, without requiring any global coordination or synchronized round.

Consistent hashing alone can allocate keys unevenly if node identifiers do not cover the identifier space uniformly. Chord addresses this by allowing each physical node to run multiple independent "virtual nodes," each with its own independently hashed identifier and its own slice of keys and finger-table entries; the paper's discussion of an a-priori-bounded network (at most one Chord server per IPv4 address) recommends 32 virtual nodes per physical node in that case to achieve good load balance.

### Parameters
- Identifier length used in the deployed prototype: 160 bits, derived from SHA-1.
- Deployed-prototype lookup count per data point: 16 lookups per physical site per node-count value tested.
- Deployed testbed: 10 physical sites (RON testbed subset), located in California, Colorado, Massachusetts, New York, North Carolina, Pennsylvania.
- Measured typical inter-site round-trip time: 60 ms (via ping), used to explain the 285 ms median lookup latency at 180 node instances.
- Recommended virtual-node count under an a-priori bound of one Chord server per IPv4 address: 32 virtual nodes per physical node.
- Stabilization interval in the churn simulation: randomized, averaging 30 seconds per node, independently scheduled per node (no global synchronization).
- Simulated churn-experiment network size: 500 nodes (this specific figure is legible; the corresponding key-population and churn-rate axis values referenced in the same section are not legible in the retrieved text).
- Finger-table structure: one entry per bit of the identifier space, entry i covering identifiers starting at the node's own identifier plus 2^(i-1) (the exact per-experiment identifier-space size used in the simulations is not legible in the retrieved text).

### Stated limitations
The authors state Chord "currently has no specific mechanism to heal partitioned rings," and that such rings could appear locally consistent to the stabilization procedure even while globally split; they propose (without implementing) two mitigations — periodic lookups for a node's own identifier to detect whether the ring reports it as absent, and each node maintaining a long-term memory of a random set of previously encountered nodes to increase overlap across a partition — and note the first only detects partitions among nodes that already know of each other. They state a malicious or buggy set of participants "could present an incorrect view of the Chord ring," calling this a threat to data availability rather than authenticity, conditional on the data itself being cryptographically authenticated. They state an attacker could target one data item by inserting a node with an identifier immediately preceding that item's key and returning errors when queried for it, and that requiring (and checking) SHA-1-derived node identifiers from IP addresses "makes this attack harder" without eliminating it. They state that although the number of routing messages per lookup may already be too many for some applications, especially when each message crosses the wide-area Internet to a random host, no implemented fix is offered — only an unimplemented sketch (placing fingers at higher-radix intervals or measuring delay across multiple equivalent finger candidates via server selection, most effective under recursive rather than iterative routing). For the simulator itself, the paper states its lookup-failure-during-churn experiment does not retry failed queries, calling the reported failure rates "the worst-case scenario for the query failures induced by state inconsistency," and that its correctness criterion (reaching the current successor of a key) is "slightly optimistic" because it ignores whether the higher-layer application has actually migrated the associated data to that successor yet.

### Requirements it places on the rest of the system
Chord resolves only to the responsible node for a key; the paper states explicitly that the correctness of a lookup under concurrent joins, leaves, and failures depends on maintaining accurate successor pointers via the periodic stabilization protocol, so any deployment needs that background process running continuously and needs to tolerate a bounded self-correction delay (governed by the stabilization interval, 30 seconds average in the paper's experiments) before newly joined or newly failed nodes are reflected network-wide. Because Chord itself provides no data replication or value storage, an application built on Chord (the paper names a "cooperative file sharing," "time-shared available storage," and "distributed indices for document and service discovery" as intended uses) must independently replicate or otherwise recover values stored under a key before that node fails, since the paper's own failure experiment explicitly modeled "a system that stores values with keys but does not replicate the values or recover them after failures," and states this design choice, not Chord's routing correctness, as the reason a node failure can still lose a key's stored value even though the ring self-heals its routing structure. Any component built on Chord's identifier assignment needs node identifiers to be derived by a hash function whose preimages are hard to construct (SHA-1, in the deployed prototype); the future-work section states this specifically as the defense against an attacker inserting an identifier chosen to sit immediately before a target key.
