## [PERCIVAL-BSDCAN-09] Stronger Key Derivation via Sequential Memory-Hard Functions
**Citation:** Colin Percival. "Stronger Key Derivation via Sequential Memory-Hard Functions." BSDCan (self-published technical report; later standardized as RFC 7914), 2009. DOI: 10.17487/RFC7914 (registry-cited; this document itself carries no DOI).
**Retrieved:** full text via https://www.tarsnap.com/scrypt/scrypt.pdf
**Source URL:** https://www.tarsnap.com/scrypt/scrypt.pdf
**Domain:** I

### What it does
The scrypt key derivation function raises the cost of a brute-force password search performed on custom hardware, by forcing every evaluation to hold a large pseudorandom array in memory rather than only performing many arithmetic operations. The paper defines a memory-hard algorithm as one whose memory use S(n) grows almost as fast as its operation count T(n) (formally S(n) is Ω(T(n)^(1-e)) for arbitrarily small e), and a sequential memory-hard function as one where, in addition, no parallel machine with S*(n) processors and S*(n) memory can compute the function in expected time T*(n) such that S*(n) times T*(n) is asymptotically less than T(n) squared — meaning a parallel attacker gains nothing from adding processors unless it adds a matching amount of memory to each one. The construction, ROMix, builds an array of N pseudorandom blocks by repeated hashing, then makes a second pass reading blocks at positions selected by the current hash state, so that discarding the array to save memory forces recomputation from scratch; the paper proves ROMix is sequential memory-hard under the random oracle model. Because random hash-function calls waste real memory bandwidth on modern CPUs (cache lines and memory latency dominate a single hash call), the paper replaces the raw hash step with BlockMix, which mixes 2r blocks of state through repeated applications of the Salsa20/8 stream-cipher core, giving one sequential-memory-hard step that better matches real cache-line and memory-latency behavior; the combination is called SMix. The overall function, scrypt(P, S, N, r, p, dkLen), first derives p independent MFLen-sized blocks from the password P and salt S using one PBKDF2 (RFC 2898-family Password-Based Key Derivation Function 2) call, mixes each of the p blocks independently through SMix with cost parameter N, and finally runs PBKDF2 once more over the concatenated mixed blocks to produce the derived key of length dkLen. Because the p independent mixing computations do not communicate, an implementor increases p to raise computational cost without increasing the memory footprint, which the paper states lets scrypt remain useful if CPU parallelism and memory capacity grow at different rates in the future.

The paper does not run a hardware implementation or a live-network deployment; its cost figures are derived estimates computed from published cryptographic-circuit design data and manufacturing-cost data for a stated process node, not from an executed experiment.

### Parameters
scrypt's tunable parameters: N (CPU/memory cost parameter, controlling array size and thus memory use and computation time), r (block-size parameter for BlockMix, set to 8 in the paper's worked examples), p (parallelization parameter, a positive integer at most (2^32-1)*hLen/MFLen, set to 1 in the paper's worked examples). The paper states r=8, p=1 "appears to yield good results" at the time of writing but expects the optimal r and p to rise as memory latency and CPU parallelism increase. Worked N values in the cost table: N=2^14 for the 100 ms (interactive-login) parameter set and N=2^20 for the 5 s (file-encryption) parameter set, both with r=8, p=1. ROMix's work parameter N must be less than 2^(k/8) for a k-bit hash output. SMix operates on 1024r-bit blocks and uses 4Nr applications of the Salsa20/8 core with 1024Nr + O(r) bits of storage (Theorem 2, proved in the paper, not measured). Conjecture 1 (unproven, stated as a conjecture) gives an expected minimum amortized area-time product per password of 1024*N^2*r^2*p*s*t for any circuit computing scrypt, where s is the minimum area to store one bit and t is the minimum time to evaluate one Salsa20/8 core — the basis for the paper's claim that doubling N is expected to roughly quadruple hardware attack cost, since both time and required space double.

### Stated limitations
The paper states that ROMix is proved sequential memory-hard only under the random oracle model, and that scrypt's own sequential-memory-hardness is a conjecture ("appears very likely"), not a proof, contingent on no new attack being found against scrypt or its Salsa20/8, BlockMix, or PBKDF2 components. The paper states its Table 1 dollar-cost figures are "very approximate" and reflect only cryptographic-circuit cost at circa-2002, 130 nm technology; the authors state the true cost including control circuitry, boards, power supplies, and operating costs could be 10 times higher, while future semiconductor and circuit-design improvements could make it 10 times lower. The paper states it could not obtain accurate real-world data on actual password-cracking hardware because organizations that build such hardware are described as "somewhat secretive," so all estimates rest on published cryptographic-circuit datasheets rather than measured attacker hardware. The paper documents a bug (an even-valued LCG multiplier arising 50% of the time on reinitialization) in the HEKS scheme by Reinhold, which it analyzes but states it does not believe meaningfully weakens HEKS; this is presented as an aside on a related prior scheme, not a limitation of scrypt. The paper proves HEKS itself is not sequential memory-hard (a parallel machine with O(L) processors computes it in O(N*K*L^0.5+e) time versus O(L^2 + N*K*L) sequentially), motivating scrypt's alternative construction rather than being a limitation of scrypt.

### Requirements it places on the rest of the system
Any deployment of scrypt requires a general-purpose machine with random-access memory on the order of 1024*N*r bytes available during key derivation, since the mixing step must hold the full pseudorandom array to avoid the intended recomputation cost; a memory-constrained device (embedded hardware, a low-memory mobile client) cannot use large N without paying the same time cost the scheme imposes on an attacker. Requires an underlying pseudorandom function for the two PBKDF2 calls that bracket the mixing step (the paper instantiates this with HMAC-SHA256); the security argument (Conjecture 1) is contingent on Salsa20/8 having no faster hardware evaluation and on BlockMix's shuffle step (unproven, only conjectured to hold) actually preventing partial-value pipelining attacks. Any system selecting scrypt as its key-derivation or proof-of-work-style memory-hard primitive must fix N, r, and p as a joint choice trading peak memory footprint against wall-clock latency; the paper does not give a formula deriving these from a target hardware-cost multiplier, only two worked example parameterizations (100 ms and 5 s targets on a specific 2.5 GHz CPU) that a later system must recompute against its own reference hardware and target latency.

### Contradicts
None found. No claim in this batch or corpus is described in the paper as being overturned, and no other entry in this batch reports a conflicting figure for scrypt's cost. This paper is itself the origin of the memory-hard-function cost argument that BIRYUKOV-FC-15 (also in this batch) references when noting that memory-hard proof-of-work functions such as scrypt (used in Litecoin) reduce GPU/ASIC advantage relative to CPU miners; BIRYUKOV-FC-15 states this consistently with this paper's own claim, not in contradiction to it.

### References worth retrieving
- Kelsey, Schneier, Hall, Wagner, "Secure applications of low-entropy keys," ISW 1997 — foundational: the paper that first formalized key stretching, cited as an early ancestor requiring "32-bit arithmetic and moderately large amounts of RAM."
- Provos, Mazieres, "A future-adaptable password scheme," USENIX ATC 1999 — competing: the paper defining bcrypt, this paper's direct comparison point throughout the cost table.
- Kaliski, "PKCS #5: Password-based cryptography specification version 2.0," RFC 2898, 2000 — foundational: defines PBKDF2, used both as a comparison KDF and as scrypt's own bracketing subroutine.
- Reinhold, "HEKS: A family of key stretching algorithms," 1999 (personal communication 2009 for confirmation) — foundational/superseded-by: the memory-hard-but-not-sequential-memory-hard predecessor this paper's Section 3 analyzes and whose parallel-attack weakness motivates ROMix.
- Florencio, Herley, "A large-scale study of web password habits," WWW 2007 — foundational: source of the cited 42.02-bit average password entropy figure for paypal.com used to motivate the need for key stretching.
- Bernstein, "The Salsa20 family of stream ciphers," 2007 — foundational: defines the Salsa20/8 core used as the underlying hash primitive in BlockMix and SMix.
