## [HEILMAN-USENIXSEC-15] Eclipse Attacks on Bitcoin's Peer-to-Peer Network
**Citation:** Ethan Heilman, Alison Kendler, Aviv Zohar, Sharon Goldberg. "Eclipse Attacks on Bitcoin's Peer-to-Peer Network." USENIX Security Symposium, 2015.
**Retrieved:** full text via https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-heilman.pdf
**Source URL:** https://www.usenix.org/system/files/conference/usenixsecurity15/sec15-paper-heilman.pdf
**Domain:** A

### What it does
This paper takes over every connection a target Bitcoin node makes to the rest of the network (an eclipse attack), by exploiting how bitcoind version 0.9.3 selects which peer addresses to store and to reconnect to, rather than by poisoning a distributed-hash-table routing structure — Bitcoin's peer-to-peer network is unstructured, so the mechanism here is identity forgery against a connection table, not DHT routing-table poisoning. A node with a public IP address stores peer addresses in two on-disk tables: tried (64 buckets of up to 64 addresses each, for peers it has already successfully connected to) and new (256 buckets of up to 64 addresses each, for peers it has only heard about). Each address hashes deterministically to one tried bucket via a per-node secret key and the address's /16 IP prefix ("group"); when a bucket is full, bitcoin eviction picks four addresses from the bucket at random and replaces the oldest of the four with the new one, then moves that evicted address into new.

The attack has three exploitable properties the paper identifies directly in this table structure. First, any node can insert an address into a victim's tried table simply by making an unsolicited incoming connection to the victim from that address, and the eviction rule described above means an attacker's fresher addresses tend to displace older legitimate ones over repeated rounds. Second, a node accepts unsolicited ADDR messages (up to 1,000 addresses each) and inserts their contents directly into new without testing connectivity, so an attacker can flood new with "trash" (unreachable) addresses that eventually overwrite every legitimate entry there. Third, because outgoing-connection selection is biased toward addresses with the freshest timestamps, an attacker who keeps re-touching its own addresses across repeated rounds (each round taking a duration τ_a) can make its addresses look newer than the legitimate ones, whose timestamps grow stale as the attack runs for a duration τ_ℓ. Once the victim restarts — which the paper argues is not a rare event, citing a 25% chance of any given public-IP node going offline within 10 hours, forced software updates, and DDoS-induced restarts as ordinary causes — the victim reconnects using only tried and new, both of which the attacker has already populated, so with high probability all eight of its outgoing connections and its open incoming slots land on attacker-controlled addresses.

The paper derives a closed-form probability of eclipsing a victim, q(f, f′, τ_a, τ_ℓ)^8, as a function of f (the fraction of tried the attacker controls), f′ (the fraction of legitimate addresses still actively connected to the victim when it restarts), and the two time parameters, and validates this model against Monte Carlo simulation and live experiments on real bitcoind nodes.

### Parameters
- τ_a (attack round length): 27 minutes used throughout the closed-form model and most experiments.
- τ_ℓ (total time invested in the attack before the victim restarts): varied across experiments — 1, 2, 4, 5, 10 hours.
- f (fraction of tried controlled by the attacker) and f′ (fraction of tried still actively, freshly connected to the victim before restart): f′ = 8/(64×64) used as the standard "full table" assumption.
- s (number of distinct /16 address groups an infrastructure attacker controls) and t (addresses per group): tested at s=32, t=256 (8,192 total, the paper's primary worst-case infrastructure configuration) and s=20, t=256 (5,120 total).
- Botnet size (t, total distinct addresses, one group each): tested at 200, 400, 600, 2,300 (×2 groups = 4,600), with 400 identified as sufficient against the paper's own live nodes.
- p (per-address churn / liveness probability): measured at 28% on the paper's own live nodes (Table 1), used as the churn input for the test-before-evict bound.
- h (number of legitimate addresses in tried before the attack): the paper's own live nodes measured h<400 after 43 days of continuous uptime; the paper computes 3,700 as the h needed for 10% bounded eclipse probability at p=28% under test-before-evict.
- Number of outgoing connections: 8, the value bitcoind used at the time; the paper's own Countermeasure 7 proposes 12, reducing worst-case eclipse probability from f^8 to f^12.
- Table sizes: tried holds 64 buckets × 64 addresses (4,096 total); new holds 256 buckets × 64 addresses (16,384 total); Countermeasure 6 (deployed) scales both by a factor of four.

### Stated limitations
The paper states its attack applies only to nodes with public IP addresses; a private-IP node is affected only indirectly, if every one of its outgoing connections happens to be to an already-eclipsed public-IP node. The paper states its success-rate predictions from the closed-form model (Section 3.3) are a lower bound on the true success rate in practice, because the model assumes legitimate addresses are exactly τ_ℓ old at restart when in practice they are typically older — the paper's own experiments confirm this, with the actual success rate exceeding the model's prediction in almost every logged case (for example, one botnet configuration reached 88% actual success against a 34% prediction). The paper states Countermeasure 6 (more buckets) is effective only when tried already holds many legitimate addresses; if tried is mostly empty or stale, doubling the bucket count does not reduce the attacker's achieved fraction of tried, so this countermeasure is stated as requiring pairing with another (feeler connections) that actually populates tried with fresh legitimate entries. The paper states ensuring tried is kept full of legitimate addresses remains a challenge even after its proposed countermeasures, particularly because the live Bitcoin network may hold fewer than 16,384 public-IP nodes at a given time — fewer than the expanded table's total capacity. The paper explicitly limits its own scope by not studying Tor-connected nodes, citing separate prior work for that case.

### Requirements it places on the rest of the system
The attack and its analysis assume the victim node eventually restarts; the paper argues this assumption is realistic (citing a measured 25% chance of a public-IP node going offline within 10 hours, forced software updates, and DDoS-inducible restarts) rather than treating it as a special case, so any system relying on connection-table integrity across the node's lifetime must account for restart as a normal, not exceptional, event. The paper's proposed test-before-evict countermeasure requires the node to attempt a live connection to the currently-stored older address before evicting it in favor of a new one, adding a network round-trip to every table-insertion decision, and its protection is bounded by the fraction of legitimate addresses actually online during the attack (parameter p) — a system deploying it still needs a separate mechanism (feeler connections, in this paper) to keep the legitimate-address count h in tried high enough for the resulting bound to be tight. The anchor-connections countermeasure requires the node to persist a small table of long-lived outgoing-connection addresses across restarts specifically so that at least one reconnection target is not subject to the tried/new selection process at all; this requires durable local storage that survives the same restart event the attack exploits. The paper's own diversify-incoming-connections and anomaly-detection suggestions both require the ability to observe and rate-limit by source IP address, which assumes the attacker cannot cheaply acquire many distinct source addresses — a assumption the paper's own infrastructure-attack analysis shows fails against any actor holding many IP address groups.
