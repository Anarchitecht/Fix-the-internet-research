### What it does
DiskANN answers k-nearest-neighbor queries over a billion-point vector dataset from a single workstation holding 64 GB of random-access memory (RAM) and one inexpensive solid-state drive (SSD), by keeping the proximity graph on the SSD instead of in RAM. The system has two parts: a graph-construction algorithm named Vamana that builds a directed proximity graph over the point set, and a disk search procedure named BeamSearch that walks that graph while amortizing the SSD's round-trip latency.

Vamana builds the graph in two passes over the dataset in random order. Each pass, for a data point `p`, runs GreedySearch from a designated start node (the medoid of the dataset) to find the set of points visited while approaching `p`, then runs RobustPrune on that visited set to select at most `R` out-neighbors for `p`. RobustPrune repeatedly picks the closest remaining candidate as a new out-neighbor and discards any other candidate `p'` for which `α · d(p*, p') ≤ d(p, p')`, where `p*` is the neighbor just picked; a threshold `α > 1` forces each edge to shrink the remaining distance to the query by a multiplicative factor rather than merely decrease, which the paper states is what caps the number of hops needed on a search path, because a graph where distance only decreases (the smallest-neighborhood-graph property) can still have hop count linear in the point count. After adding `p`'s out-edges, the algorithm also adds the reverse edge from each of `p`'s new out-neighbors back to `p`, and re-runs RobustPrune on any node whose out-degree that reverse-edge insertion pushes above `R`. The first pass runs with `α = 1`; the second runs with the user-set `α`, because running both passes at the final `α` produces a higher-average-degree intermediate graph that slows construction.

Because a billion 100+-dimensional vectors do not fit in 64 GB of RAM, DiskANN stores each point's full-precision coordinate vector together with its out-neighbor list on the SSD, in one fixed-offset disk sector per point (padded with zeros to a constant degree `R` so the sector address for point `i` is computable without an in-memory offset table), and keeps only a lossy-compressed encoding of every point (via product quantization, 32 bytes per point in the paper's configuration) in RAM to score candidates cheaply during the graph walk. BeamSearch modifies the base greedy-search procedure to fetch the neighbor lists of the `W` closest not-yet-visited candidates in one parallel batch of SSD reads per round, rather than one candidate at a time, because a small batch of random SSD reads takes about the same wall-clock time as a single read; each fetched sector also returns the full-precision coordinates for those points, at no added disk-read cost, letting the final top-k result be re-ranked using exact distances instead of the lossy-compressed approximations used during the walk. To keep the billion-point build inside 64 GB RAM, DiskANN can instead build the graph as a merged index: partition the dataset into `k` clusters by k-means, assign each point to its `𝓁` closest cluster centers, build a separate in-memory Vamana graph per cluster, and take the union of all per-cluster edge sets as the final graph.

### Parameters
- `α` (RobustPrune distance-shrink threshold): must be `α > 1` to bound hop count; first construction pass uses α=1, second pass uses a user-set α ≥ 1; billion-point experiments used α=2.
- `L` (GreedySearch candidate-list size during construction): 125 in all billion-point and DEEP1M experiments; general constraint stated is `L ≥ k` where k is the result size requested.
- `R` (maximum out-degree per node): 128 for the single-index SIFT1B build, 70 for in-memory DEEP1M comparisons, 64 for each shard of the merged SIFT1B build, 60 for NSG on DEEP1M.
- `W` (BeamSearch parallel-fetch width): explored at 2, 4, 8; the paper states W=1 reduces to plain greedy search and W ≥ 16 wastes both compute and SSD bandwidth; W=4 used for the hop-count comparison figure.
- `k` (number of k-means shards for the merged index): 40.
- `𝓁` (cluster assignments per point for the merged index): 2; the paper states 𝓁=2 "typically suffices."
- `C` (candidate-list cache depth / cached breadth-first-search radius from start node): C=3000 for the RobustPrune candidate list size in one in-memory configuration (DEEP1M NSG); separately, C=3 or 4 hops used for caching frequently visited vertices in RAM, with the paper noting the number of nodes at distance C grows exponentially with C so larger C is memory-expensive.
- Product-quantization compressed-vector size: 32 bytes per data point in the paper's configuration.

### Stated limitations
The paper states one explicit assumption, in the hop-count comparison: for NSG and Vamana it assumes the first 3 breadth-first-search levels around the start node are cached in DRAM, and for HNSW it assumes all levels above the base level are cached in DRAM; the comparison is not run without these caching assumptions. The paper reports, without further investigation, that the merged (sharded) index underperforms the single index because "it traverses more links to reach the same neighborhood," attributed to each node's edges being confined to roughly 𝓁/k = 5% of all points, and states this needs no further characterization beyond the reported 20% latency penalty. The paper explicitly defers a detailed comparison of its overlapping-cluster merge technique against prior overlapping-index-merging work (Bentley 1980; Wang et al. 2012), stating "a more detailed comparison of these different techniques needs to be done."

### Requirements it places on the rest of the system
Requires a single physical machine holding both the RAM for the compressed-vector table and the SSD for the graph and full-precision vectors; the paper's mechanism is not distributed across machines, and the registry's own note (in `why_needed`) states the paper is being read as the baseline single-machine mechanism prior to evaluating any distribution proposal. Requires the full compressed representation of every point resident in RAM simultaneously — the paper explicitly rejects a shard-and-route architecture (partition data across multiple independent indices, route each query to a subset of shards) as its design starting point, on the stated ground that shard routing increases search latency and reduces throughput, and instead builds one graph with overlapping shard membership merged by edge-set union. Requires a distance function and a vector representation compatible with product quantization for the compressed in-RAM candidate scoring; the paper never evaluates a non-metric or non-quantizable similarity function. Requires the query-processing layer to accept an approximate top-k result, since GreedySearch/BeamSearch produce approximate rather than exact nearest neighbors, with the exactness/latency tradeoff controlled by L and W. Requires disk sector alignment (the paper packs a full-precision vector plus a fixed-degree neighbor list into one on-disk sector, 4-KB aligned) so a storage layer without addressable fixed-size sectors could not directly reuse the disk-layout mechanism as described.
