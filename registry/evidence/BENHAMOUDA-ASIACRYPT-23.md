## [BENHAMOUDA-ASIACRYPT-23] Anonymous Counting Tokens
**Citation:** Fabrice Benhamouda, Mariana Raykova, Karn Seth. "Anonymous Counting Tokens." ASIACRYPT, 2023. DOI 10.1007/978-981-99-8724-5_8.
**Retrieved:** full text via https://eprint.iacr.org/2023/320.pdf
**Source URL:** https://eprint.iacr.org/2023/320.pdf
**Domain:** I

### What it does
An anonymous counting token (ACT) scheme lets a client obtain a blind signature or message authentication code (a "token") on a message of its own choosing, while letting the issuer enforce that any one registered client obtains at most one token per distinct message, without the issuer or a verifier learning which client requested which message or linking two tokens to the same client. This generalizes Privacy Pass-style anonymous tokens, whose messages are random values with no application meaning, to tokens bound to client-chosen messages that carry rate-limiting semantics (for example, counting distinct users who joined a given interest group, without counting one user twice or revealing which group a user joined). The scheme has five algorithms: `GenParam` (issuer setup), `ClientRegister` (client generates a registered key pair with the issuer), `Request` (client blinds a message into a request), `Sign` (issuer signs the blinded request, optionally emitting a throttling tag), `Unblind` (client recovers a token for its chosen message), and `Verify` (checks a token, optionally emitting a throttling tag). Throttling — detecting a second token request or redemption for the same message by the same client — can be enforced either at issuance time or at verification time, and each of the paper's four constructions states which point it enforces at.

The paper gives four constructions. Construction 4.3 builds a token as an evaluation of the Boneh-Boyen pseudorandom function `F(sk=(u,y), msg; r) = (msg + u + r·y)` over a single cyclic group, using a random-oracle-based verifiable oblivious pseudorandom function (VOPRF) for blind issuance and a rate-limiting pseudorandom function the client evaluates on the message under its own registered key to produce a detectable tag; it needs no bilinear pairing, using instead Camenisch-Shoup encryption and Pedersen commitments over a strong-RSA group for its zero-knowledge proofs. Constructions 5.1, 6.3, and 8.1 build tokens from equivalence-class signatures (EQS) — signatures on vectors of group elements that a signature holder can transform ("adapt") into a valid signature on any vector in the linear span of the original, without the signer's involvement — combined with one of two rate-limiting pseudorandom functions evaluated by the client: `PRF(u, msg) = u · H(msg)` (random-oracle-based) or the Dodis-Yampolskiy PRF `PRF(u, msg) = (msg + u)^(-1) · G`. The paper identifies and rules out three naive designs before settling on this approach: fixed client randomness with a zero-knowledge proof of a hash evaluation (rejected for the cost of proving correct evaluation of a general hash function); Pedersen-hash-based blinding (rejected because the hash's linearity lets an attacker derive a fresh token for `msg1 OR msg2` from tokens on `msg1` and `msg2` individually, via `H(1‖0‖…) + H(0‖1‖…) = H(1‖1‖0‖…)`); and omitting the client's proof of knowledge of the message underlying its blinded request (rejected because the resulting token is additively homomorphic in the hashed message, letting an attacker split a target message into two shares, request tokens on each share, and recombine them into a second token for the original message — defeating the one-token-per-message guarantee).

### Measured results
The paper reports no runtime benchmarks (no wall-clock timing measurements on any hardware). Its "Performance" table (Table 2) instead states the exact communication cost of each construction's message flow, in group-element and scalar counts, which is a size computed by construction rather than measured by execution:

| 4.3 | DCR + q-DDHI | No | any | 5×Ped + 4×CS + 12×Zp + 11×ZN | 1×Ped + 1×Zp + 3×ZN | 1×G |
| 5.1 | SXDH + 2\|msg\|-DDHI in G1 | Yes | O(log λ) | 7×G1 + 6×G2 | 5×G1 + 1×G2 | 23×G1 + 12×G2 |

Concrete byte sizes, stated by the paper from named curve choices, not measured: using Edwards25519 for the cyclic group `G`, one group element is 32 bytes; using BLS12-381 for the bilinear groups, one `G1` element is 48 bytes and one `G2` element is 96 bytes; one `Zp` scalar is 32 bytes for either curve choice; using a 3072-bit RSA modulus (the NIST 128-bit-security recommendation), one Pedersen commitment (`Ped`) is 384 bytes and one Camenisch-Shoup ciphertext (`CS`) is 1536 bytes. The paper notes the reference row for [FHS19] reports cost for a single message/attribute although that scheme natively supports vectors of messages.

A cited external figure, not this paper's own measurement, used only to motivate a design rejection: the Poseidon hash function's Section 6 benchmark (Grassi et al., USENIX Security 2021) reports approximately 40 ms for a SNARK proving correct Poseidon hash evaluation alone; the authors estimate (not measure) that adding the required scalar multiplication would at least double this to over 80 ms, and that STARK or Bulletproof proofs (needed if a trusted setup is to be avoided) would run approximately 10 times more expensive than SNARKs for the same Poseidon evaluation.

### Parameters
- `q-DDHI` parameter `q`: the number of signature queries an adversary is allowed to make; no specific numeric value fixed, used as a security-proof parameter.
- Curve choices used only for the byte-size column of Table 2, not prescribed as the scheme's only option: Edwards25519 for the single-group construction (Construction 4.3), BLS12-381 for the three pairing-based constructions.
- RSA modulus size for Construction 4.3's Pedersen commitments and Camenisch-Shoup encryption: 3072 bits, cited to NIST recommendation for 128-bit security.
- General-rate-limiting extension parameter `k`: the number of bits appended to a message to allow `2^k` tokens per message per client, described as a generic transformation (Section 9) rather than instantiated in any of the four main constructions; no numeric value recommended.

### Stated limitations
The paper's generalization from "exactly one token per message" to "up to `2^k` tokens per message" (Section 9) is presented as an unresolved-in-full construction: the straightforward approach of appending a random `k`-bit suffix `s` to the message before the rate-limiting pseudorandom function evaluation "does not preserve unlinkability across clients" if `s` is sent in the clear, because two redemptions carrying the same suffix value for the same message reveal to the verifier that they came from different clients. The paper describes only the outline of a zero-knowledge proof needed to prove the suffix has correct length without revealing it, and does not carry this generalized construction through a full security proof in the main constructions. Construction 4.3 achieves no public verifiability — verification requires the issuer's private key, unlike the three equivalence-class-signature-based constructions. The paper states three of its four assumption sets require bilinear pairings, which the authors note can be difficult to add to some enterprise products for non-technical reasons (audit and approval-process requirements), citing the IETF draft rate-limited-token-issuance context as the case where this matters.

### Requirements it places on the rest of the system
Every construction requires a client registration step (`ClientRegister`) before any token issuance: the client generates a long-term key pair with the issuer and this registered key is the input to the rate-limiting pseudorandom function that produces the throttling tag; a system without a prior client-registration phase cannot supply this. The randomness `r` used to combine a message with the pseudorandom function evaluation must be generated jointly by client and issuer through a coin-tossing protocol using the Fiat-Shamir transform for the issuer's contribution — client-only randomness lets a malicious client force homomorphism in the token and forge tokens by the additive-share attack described above; issuer-only randomness creates a fingerprinting channel that breaks unlinkability. The throttling mechanism requires the issuer (for issuance-time throttling) or verifier (for redemption-time throttling) to maintain a persistent set `T` of previously seen tags across all interactions with a given key population, and to reject any request or redemption whose tag is already in `T` — a system without durable tag-set storage across sessions cannot enforce the one-token-per-message guarantee. The three equivalence-class-signature constructions require a bilinear pairing-capable cryptographic library at both client and issuer; Construction 4.3 avoids this dependency but requires a strong-RSA-group setup with a trusted modulus for the Camenisch-Shoup encryption and Pedersen commitments it uses.

None found.
