## [WANG-SIGCOMM-11] An Untold Story of Middleboxes in Cellular Networks

**Citation:** Zhaoguang Wang, Zhiyun Qian, Qiang Xu, Zhuoqing Morley Mao, Ming Zhang. "An Untold Story of Middleboxes in Cellular Networks." ACM SIGCOMM, 2011. Pages 374-385 (as paginated in text pp. 374-386). DOI 10.1145/2018436.2018479.
**Retrieved:** full text via https://conferences.sigcomm.org/sigcomm/2011/papers/sigcomm/p374.pdf
**Source URL:** https://conferences.sigcomm.org/sigcomm/2011/papers/sigcomm/p374.pdf
**Domain:** L

### What it does
NetPiculet is a measurement tool that infers a cellular carrier's Network Address Translation (NAT) and firewall policies end-to-end, without administrative access to carrier equipment, by coordinating probes between an Android client running inside the carrier's network and a dedicated server on the open Internet. For NAT mapping, it opens 12 back-to-back connections to 4 destinations using the same local port (following prior methodology) plus, as this paper's own addition, 12 more connections to a single destination using different local ports, to classify how a NAT box assigns external (IP, port) endpoints to internal connections: Independent (same external endpoint reused for every connection), Address-and-Port-dependent (external endpoint changes when the destination changes), or Connection-dependent (external endpoint changes for every new connection), each further classified by whether the port increments by a fixed value or a random value. For endpoint filtering, the client first establishes a connection to the server (creating a NAT mapping), then the server varies its own source address/port when sending unsolicited SYN packets back to that mapped external endpoint, and the client checks which packets it receives, to determine whether the NAT filters inbound packets by destination-endpoint match only or also checks the source. For firewall behavior, NetPiculet separately probes IP spoofing tolerance (client modifies the source-IP field of outgoing packets), TCP state-machine transitions (probing which sequences of SYN/SYN-ACK/ACK/DATA/FIN/RST packets are permitted, inferring a state diagram), TCP idle-connection timeout (multiple parallel connections held open without keep-alive, timed until reset), and out-of-order-packet buffering (whether packets outside the expected sequence window are dropped, buffered, or immediately delivered). Both server and client are implemented in C and Java, approximately 3,000 lines of code total, released as a free Android application to recruit a broad user base across carriers the authors could not access directly.

### Parameters
- Test parallelization budget: all tests except TCP-timeout inference complete within 10 seconds on the client, to save user time and device battery
- NAT-mapping-type discovery probe count: 12 connections to 4 destinations (3 each) on the same local port, plus 12 additional connections to one destination on different local ports (24 total)
- IP-spoofing scan range tested: /24 and /16 address ranges
- Time-dependent-NAT port-prediction search window: ±n around the predicted port, with n=15 by default
- Time-dependent-NAT traversal retry interval: 1-second timeout between consecutive dial trials
- Measurement period: two weeks, January 2011
- Deployment scale: ~400 users, 107 carriers total (with smaller sub-populations for tests requiring root privilege or private-IP assignment)

### Stated limitations
NAT tests apply only to carriers that assign private IP addresses to devices (72 of 107 carriers in the dataset); carriers assigning only public IPs are excluded from this analysis entirely. Several probes (IP spoofing, TCP state-machine inference, packet-mangling detection) require raw-socket access, which needs root privilege not available on every phone, so those results are reported for a smaller subset (20-60 carriers) than the full 107-carrier or 72-carrier NAT-capable population. The full TCP state-machine diagram is measurement-intensive and time-consuming, so it was inferred only in local controlled experiments for two named U.S. carriers (A and B); the publicly released tool substitutes a simpler TCP-connection-timeout measurement rather than the full state diagram. The authors state their classification of a given policy as "NAT" or "firewall" is only a convenience label and may not correspond to the carrier's actual implementation, since a single network device can implement both functions, and their end-to-end black-box probes can infer only the existence of a policy, not its internal mechanism. The paper's NAT-load-balancing analysis (deriving that Carrier B splits traffic across two NAT boxes by the parity of source+destination port sum) is described by the authors as "2-way balancing solely based on our measurement observation"; the authors state a more complex hash function, or n-way balancing with n>2, would be "much more challenging" and explicitly leave this for future work. The authors state their findings, though drawn from cellular networks, likely generalize to wired-network middleboxes (e.g., time-dependent NAT mapping or out-of-order buffering could also occur there) but explicitly leave verification of that generalization as future work — they did not measure wired-network middleboxes in this study.

### Requirements it places on the rest of the system
Any peer-to-peer NAT-traversal scheme that assumes a client sits behind exactly one NAT box with one consistent mapping type is unsupported for the 3 of 72 carriers this paper measured assigning a client's connections to two different NAT boxes (with two different mapping types and sometimes two different external IP addresses) depending on a hash of the connection's five-tuple; a traversal scheme must first discover and hold constant whichever five-tuple property the carrier's load-balancing hash keys on (in Carrier B's case, the parity of the summed source and destination port numbers) before it can assume a single, predictable NAT mapping applies. A traversal scheme relying on port-prediction (as this paper's own time-dependent-NAT traversal scheme does) requires knowing the specific NAT's port-increment behavior (fixed-value versus time-dependent versus fully random) in advance, obtained here only by first running NetPiculet's own 24-connection discovery probe against that specific carrier; a scheme lacking this per-network characterization step cannot distinguish a time-dependent mapping from the harder Connection-random case the paper found in 19 of 72 carriers, for which the authors state no traversal technique existed prior to this paper's own contribution (and which the birthday-paradox approach of NATBlaster, cited by this paper, needs 439 connections and root access to attempt). A component depending on a long-lived idle connection to a cellular endpoint (e.g., for push-based delivery) must either issue periodic keep-alives at an interval no larger than the carrier's inactivity timeout — measured here to be under 10 minutes for 11 of 73 carriers and under 5 minutes for 4 of 73 — or accept that the connection will be silently reset by the firewall and must be re-established, which the paper's own tested example (MSN Talk under Carrier B's 255-second timeout) confirms happens in practice. A design assuming firewall-level TCP state enforcement (e.g., relying on the firewall to reject connections with out-of-spec sequence numbers as a security boundary) cannot assume this holds broadly, since the measured acceptance window reaches up to 1G in Carrier A's firewall, which the paper's own security-implication discussion (§4.3.3, not itself reproduced here in full) uses as the basis for a feasible TCP RST-injection/hijacking attack surface.

### Contradicts
The paper's own finding directly contradicts a prior study cited within it: Makinen and Nurminen (cited [28] in this paper's related work) measured NAT properties from one vantage point in each of six cellular networks and concluded existing NAT-traversal techniques would work in cellular networks without modification; this paper's own 316-user, 72-carrier measurement instead finds 19 of 72 carriers (26.4%) use a Connection-random mapping type that existing techniques of the time could not handle, and identifies an entirely new time-dependent mapping type absent from prior classification schemes. No other paper in this corpus directly disagrees with this paper's own measured figures as of this batch; TRAUTWEIN-ARXIV-26 measures a different, later-generation, decentralized-relay-based traversal mechanism (DCUtR) rather than the direct port-prediction NAT traversal this paper studies, so the two are not measuring the same mechanism.
