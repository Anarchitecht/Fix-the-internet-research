## [TAHERIBOSHROOYEH-ARXIV-22] WAKU-RLN-RELAY: Privacy-Preserving Peer-to-Peer Economic Spam Protection
**Citation:** Sanaz Taheri-Boshrooyeh, Oskar Thorén, Barry Whitehat, Wei Jie Koh, Onur Kilic, Kobi Gurkan. "WAKU-RLN-RELAY: Privacy-Preserving Peer-to-Peer Economic Spam Protection." arXiv:2207.00117, 2022. DOI 10.48550/arXiv.2207.00117.
**Retrieved:** full text via https://arxiv.org/pdf/2207.00117
**Source URL:** https://arxiv.org/pdf/2207.00117
**Domain:** I

### What it does
WAKU-RLN-RELAY limits each participant of a gossip-based publish-subscribe network to one message per fixed time interval (an epoch) without requiring any per-message computational cost or a central rate-limiting authority, and it turns a second message in the same epoch into cryptographic proof of the sender's identity key that any observer can extract and use to forfeit that sender's deposited stake. Each participant registers by generating a private identity key sk and a public commitment pk = H(sk) (H a cryptographic hash function), submitting pk plus a deposit of Ether to a smart contract on the Ethereum blockchain, and having pk added as a leaf of a Merkle tree (a binary tree in which each internal node is the hash of its two children, so a leaf's presence can be proven by a path of hashes to the root) called the identity commitment tree; unlike the base Semaphore protocol on which this construction extends, the contract itself stores only an ordered list of registered public keys, not the Merkle tree, and each peer builds and maintains the tree locally by listening to the contract's insertion and deletion events, which the paper states avoids the gas cost of on-chain tree updates that scales logarithmically in group size and, for deletion, cannot be batched. An epoch is a public, universally computable value: the current Unix time divided by a configured epoch length T and rounded up. To publish a message m in epoch e, a sender computes a two-point Shamir secret share of its own identity key using (2,n)-Shamir secret sharing (a scheme by which a degree-1 polynomial is uniquely determined by any two of its points, so one point alone reveals nothing about the polynomial while two points reconstruct it): the sender sets x = H(m) and y = sk + H(sk, e) * x, so distinct messages in the same epoch produce distinct (x, y) points lying on the sender's own secret line, while two messages sharing an epoch value give two points on the same line. The sender also computes an internal nullifier phi = H(H(sk, e)), a value that any two messages from the same sender in the same epoch will share, and attaches (x, y), phi, e, the identity-commitment-tree root, and a zkSNARK (a zero-knowledge succinct non-interactive argument of knowledge, a proof system letting a prover convince a verifier a computation was performed correctly without revealing its private inputs) proving membership in the tree, correctness of the share, and correctness of phi, all without revealing sk or the sender's position in the tree. A routing peer relaying the message bundle keeps, for the last Thr epochs, a local table (the nullifier map) of every internal nullifier phi and share (x,y) it has seen; on receiving a new bundle it verifies the zkSNARK, checks whether phi already appears in the table for a different (x,y) pair, and if so uses the two (x,y) points from the same line to solve for sk directly (evaluating the reconstructed line at x=0), publishes that recovered sk to the contract, and collects the offending sender's deposit as a reward, after which the sender's identity commitment is removed from the group. A message whose attached epoch differs from the routing peer's own current epoch by more than a threshold Thr is dropped outright, bounding both the memory a peer must retain in the nullifier map and the exposure of newly joined peers replaying stale epochs.

### Measured results
| Measurement | Conditions |
|---|---|
| Membership-proof generation time: approximately 0.5 s | Group size 2^32 (approximately 4 billion peers); measured on an iPhone 8; figure attributed to the RLN library the authors used [17], not independently re-measured in this paper. |
| Proof verification time: approximately 30 ms, constant regardless of group size | Same RLN library and proof-of-concept implementation; hardware for the verification-side measurement not separately stated. |
| Per-peer persistent storage: 32 bytes each for the identity public and secret keys, plus a prover key of approximately 3.89 MB | Figure attributed to the RLN library [17]. |
| Identity-commitment-tree storage: 67 MB per peer for a tree of depth 20 (up to 2^20, approximately 1,048,576, members) | Stated as reducible to 0.128 KB using a separate storage-efficient tree-update proposal [18] not implemented in this paper's proof of concept. |
| Ethereum gas cost of one membership insertion or deletion: 40,000 gas, stated to exceed 20 USD at the time of writing | Stated as reducible to 20,000 gas using batch insertion; batching does not apply to deletion because deletions touch non-adjacent leaves. This figure depends on Ethereum gas-price and Ether-price conditions specific to the time of writing and is not a property of the RLN mechanism itself. |

The paper labels its own performance section a proof-of-concept implementation with a "rough performance evaluation" and states that Merkle-tree computation overhead specifically was not benchmarked ("the concrete benchmarking result in this regard is not available").

### Parameters
- Epoch length T: the time interval in seconds over which one message is permitted per identity; application-set, with the paper giving 1 second as an example acceptable rate for a chat application and stating that same rate would be too low for communication among Ethereum network validators, without giving a numeric alternative for that case.
- Maximum epoch gap Thr: the number of epochs of drift a routing peer tolerates between its own current epoch and a received message's attached epoch before dropping the message; the paper gives the formula Thr = ceil((NetworkDelay + ClockAsynchrony) / T), where NetworkDelay is the maximum time for a message to fully propagate through the network and ClockAsynchrony is the maximum clock drift observed across peers, both in seconds; no numeric value for NetworkDelay or ClockAsynchrony is measured or given in this paper.
- Merkle tree depth used in the storage measurement above: 20 (supports up to roughly 1,048,576 registered identities without resizing).
- Deposit amount v (the Ether quantity locked per registration): described only as "some amount of Ether"; no numeric value given.
- Proof system: Groth16 (a specific zkSNARK construction), with parameter generation via a multi-party trusted setup ceremony citing prior implementations.

### Stated limitations
The authors state Merkle-tree computation overhead was an unknown discovered only during the proof-of-concept build and remains unbenchmarked. The design leaves the identity commitment tree stored in full by every publishing peer, which the authors state produces storage cost linear in the size of the group, and list as future work a partial-view tree construction giving O(log N) storage instead. The authors state registration and slashing transactions are subject to Ethereum block-mining delay before taking effect, so a peer must wait after registering before it can publish, and list off-chain group-management alternatives (state channels, optimistic rollups, a distributed-hash-table-based scheme) as unimplemented future directions to remove this delay. The authors state a race condition exists when two peers simultaneously attempt to submit a recovered spammer identity key to claim the reward, since submitting the key in plaintext lets an observer copy and resubmit it first; their proposed fix (commit to the key, then later reveal it) is presented as a mitigation, not as implemented and measured. The authors identify two open problems with no known solution stated in the paper: an attacker who registers k identities and spends k times the membership fee obtains k messages per epoch rather than one, a limitation the authors say can only be raised in cost, not eliminated, by increasing the membership fee; and a spammer can withdraw its deposited stake before a routing peer catches and reports a double-signaling attempt, forfeiting only the initial registration fee rather than the full deposit a slasher would otherwise have claimed.

### Requirements it places on the rest of the system
Every routing peer must independently reconstruct and keep synchronized an identity commitment tree by observing the registration/removal event stream from the same smart contract, because the contract itself no longer stores the tree; a peer that falls behind risks proving membership against a stale root, which the paper states can expose that peer's leaf index and compromise its own anonymity. The mechanism requires loosely synchronized clocks across peers (bounded by the ClockAsynchrony term in the Thr formula) and a bound on network propagation delay, since both terms are inputs the deploying application must estimate to set the epoch-gap threshold; setting Thr too low drops legitimate recently-published messages arriving after a slow propagation path, and setting it too high extends how far back a newly registered peer could replay stale epochs. The mechanism assumes participant honesty only in the negative sense that spam is defined purely by messaging rate (more than one message per epoch), not by content, so a downstream component relying on this mechanism for content moderation gets none: a single properly rate-limited message can carry arbitrary content and passes unmodified. The scheme requires an underlying transport that delivers the full message bundle (message, identity-key share, internal nullifier, epoch, tree root, and zkSNARK proof) to every peer that must run the routing/slashing check, and it requires every such peer to hold a verifier for the specific zkSNARK proof system (Groth16) and, if trust in a single-party setup is unacceptable, requires the identity commitment tree's proving/verifying parameters to have come from a multi-party trusted-setup ceremony trusted by that peer.

### Contradicts
None found within this paper's own claims. Cross-reference for later composition: this mechanism and BACK-HASHCASH-02's non-interactive hashcash rate limiter are not measurements of the same mechanism and do not disagree numerically, but they differ in what a rate-limited peer must possess: hashcash requires only local compute and no registration, while WAKU-RLN-RELAY requires a funded on-chain registration and a live view of a specific smart contract's state, a materially different requirement on the rest of the system that a synthesis comparing the two must state explicitly rather than comparing on cost alone.
