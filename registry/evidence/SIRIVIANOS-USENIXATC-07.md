## [SIRIVIANOS-USENIXATC-07] Dandelion: Cooperative Content Distribution with Robust Incentives
**Citation:** Michael Sirivianos, Jong Han Park, Xiaowei Yang, Stanislaw Jarecki. "Dandelion: Cooperative Content Distribution with Robust Incentives." USENIX Annual Technical Conference, 2007. Pages 157-170.
**Retrieved:** full text via https://www.usenix.org/legacy/events/usenix07/tech/full_papers/sirivianos/sirivianos.pdf
**Source URL:** https://www.usenix.org/legacy/events/usenix07/tech/full_papers/sirivianos/sirivianos.pdf
**Domain:** I

### What it does
Dandelion incentivizes peer-to-peer clients to upload content to each other by withholding the decryption key for a content chunk from a downloading client until that client's upload activity has been credited by a central server, so that a client gains no benefit from downloading without also uploading, regardless of whether its peers hold content it wants in return. A file is split into fixed-size chunks; each chunk is distributed encrypted, and a client must obtain the corresponding decryption key from the server to use it. The server maintains a per-client credit balance: a downloading client B spends delta_c credit units to acquire a chunk from an uploading client A, and A earns delta_r credit units for correctly serving that chunk, with delta_c set equal to delta_r so two colluding clients cannot inflate their combined credit by falsely claiming to have exchanged chunks with each other. The protocol runs as a three-party fair exchange for every chunk transaction: client A encrypts the chunk fresh for each request and sends it to client B along with a signed ticket; B, upon receiving the encrypted chunk, immediately requests the decryption key from the server rather than waiting to verify the chunk's integrity itself; the server authenticates the request (HMAC), verifies the ticket (HMAC), decrypts the server-held copy of the decryption key (symmetric encryption), updates both clients' credit, signs the decryption key response, and returns it. Because the server is a mandatory party to every single-chunk exchange, and because the server can check a client's credit balance before releasing a decryption key, the paper proves (Lemmas 4.1-4.4 in the paper, proofs deferred to a companion technical report [51]) that a selfish client cannot claim credit for chunks it never delivered, cannot claim credit for corrupted chunks it delivered, cannot impersonate another client's ID, and cannot replay old signed messages to fraudulently charge or blacklist another client. If a client cannot retrieve a chunk from peers in time, it falls back to requesting the plaintext chunk directly from the server for a higher, delta_s > delta_c credit charge, or receives an error if the server is overloaded, so the pipeline degrades gracefully rather than stalling.

### Parameters
- Credit unit values: delta_c (cost to download a chunk) set equal to delta_r (reward for uploading a chunk), specifically to prevent two colluding clients from inflating their combined credit through mutual false claims.
- Server fallback charge for direct plaintext-chunk delivery when the server is moderately busy: delta_s, set greater than delta_c to discourage clients from preferring the server over peers.
- Chunk size: swept at 64, 128, 256, 512, 1024, 2048 KB; 128 KB adopted for the main evaluation.
- Cryptography: HMAC-SHA1 with 128-bit keys for authentication, ticket verification, and response signing; 8-byte-block Blowfish-CBC with 128-bit key and 128-bit IV for chunk and key encryption; SHA-1 for chunk hashing.
- Test hardware for profiling: dual Pentium D 2.8 GHz/1 MB CPU, 1 GB RAM, 250 GB/7200 RPM HDD, Linux 2.6.5-1.358smp.
- Test hardware for the system-performance (Section 6.3) experiments: Xeon 3 GHz/2 MB CPU, 2 GB RAM PlanetLab VServer, server rate-limited to 2 Mb/s; TCP sender/receiver buffer size set to 120 KB to cover PlanetLab's bandwidth-delay product.
- Deployment scale evaluated: up to ~200-300 PlanetLab-hosted clients (leechers) per experiment; the profiling-based projection (not a direct load test at this scale) states a server on the tested commodity hardware with a 4-5 Mb/s access link can support "a few thousand clients."

### Stated limitations
The paper states its threat model explicitly excludes bandwidth or connection-flooding denial-of-service attacks ("we consider bandwidth or connection flooding attacks outside the scope of this work"); the non-manipulability proofs cover only protocol-message-level attacks. Observation 4.8 states a malicious client can always abandon a protocol run partway through, denying the counterparty resources already spent, and the paper's only mitigation is that this costs the attacker resources roughly proportional to the victim's, calling the attack "not particularly practical" rather than prevented; a further, partial mitigation (short-lived tickets issued only to accounts in good standing, and an option for the server to charge for ticket issuance) is described as deterrence, not elimination. The security proofs for Lemmas 4.1-4.4 are stated but not proved in this paper; the paper states the proofs are deferred to the Appendix of a companion technical report. The paper explicitly declines to claim general superiority over BitTorrent, stating performance of both protocols depends on unexplored parameters. The design assumes "weak security of the IP network": clients can eavesdrop but the paper assumes they cannot corrupt or interfere with routing/forwarding at the network layer, and separately assumes communication errors may occur during message transmission; a network model departing from this (active tampering with routing, not just message content) is outside what the paper's guarantees cover. The 1,200-clients-per-server figure and the "few thousand clients" scalability projection are extrapolated from a 200-client PlanetLab throughput measurement and single-machine CPU/bandwidth profiling, not from a load test actually run at thousands of concurrent clients; the paper's own Section 6.1 states the per-operation profiling "does not consider the parallel processing of I/O and CPU operations" and "does not include the cost of system calls and the cost of TCP/IP stack processing," and explicitly states "we refrain from deriving conclusions on the throughput of the server" from that profiling data alone. The scheme's non-manipulability rests on centralizing every single-chunk exchange through one server that checks credit balances synchronously; the paper's own Section 5.1 states this server, though logically separable from the credit base, is combined into a single machine in the actual prototype, and single-server involvement in every chunk exchange is the design choice the paper explicitly trades for scalability ("we trade scalability for the ability to provide robust incentives").

### Requirements it places on the rest of the system
The provable non-manipulability property depends on each client holding one authenticated, paid account with the content provider; the paper states explicitly that "a user cannot boost its credit by presenting multiple IDs (Sybil attack) and claiming to have uploaded to some of its registered IDs" precisely because "each user maintains an authenticated paid account with the provider" and "essentially purchases its initial credit." This means the fair-exchange proof depends on a centralized, identity-verifying, paid-registration process external to the peer-to-peer protocol itself; the paper does not analyze or claim the proof holds for clients that can obtain fresh, unauthenticated identities at low or zero cost. The mechanism requires a single server (or a server cluster acting with a shared, consistent credit ledger) to be reachable and responsive for every chunk exchange between any two clients, since decryption keys are withheld until the server processes and settles a credit transaction for that specific chunk; a design in which client pairs can complete a chunk exchange without contacting a shared arbiter is incompatible with this proof structure. It requires clients to encrypt each served chunk freshly per request (stated in Lemma 4.2's precondition) rather than caching one encrypted copy, so that credit crediting and content delivery stay bound to the exact request being served. It requires the server to issue short-lived, per-transaction tickets to prevent abandoned-protocol-run denial-of-service attacks from unauthorized or blacklisted clients, meaning ticket-issuance state (validity windows, per-account status) must be tracked centrally alongside the credit ledger. The design assumes the content provider can price accumulated virtual credit such that "the benefit that a selfish client gains from acquiring virtual currency for content it uploads exceeds the cost of utilizing its uplink to upload it" — an external pricing decision the protocol itself does not make or verify, and without which the stated incentive-compatibility (Nash equilibrium of cooperation) argument does not follow.
