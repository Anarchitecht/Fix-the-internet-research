## [MALVAI-NDSS-23] Parakeet: Practical Key Transparency for End-to-End Encrypted Messaging

**Citation:** Harjasleen Malvai, Lefteris Kokoris-Kogias, Alberto Sonnino, Esha Ghosh, Ercan Öztürk, Kevin Lewi, Sean Lawlor. "Parakeet: Practical Key Transparency for End-to-End Encrypted Messaging." NDSS, 2023.
**Retrieved:** full text via candidate URL `https://eprint.iacr.org/2023/081.pdf`
**Source URL:** https://eprint.iacr.org/2023/081.pdf
**Domain:** E

### What it does
Parakeet lets a message provider prove it serves each user the one true public key it committed to, so a client can detect a provider that hands different keys to different people for the same username (server equivocation), without the client trusting the provider or a blockchain. The system separates two roles. A verifiable key directory (VKD) run by the identity provider (IdP) stores every username-to-public-key mapping and commits to it with a compact cryptographic digest each round (epoch); a client who queries it receives the current key plus a proof it belongs to the committed digest. Parakeet's VKD instantiates the ordered zero-knowledge set (oZKS) primitive over a compressed Merkle Patricia Trie, storing only the current state of each tree node rather than a new node copy at every epoch, which the paper states is what makes the storage cost bounded rather than growing with the number of epochs. Separately, a small committee of witness servers cross-checks the IdP's per-epoch digest through a consistency protocol: the IdP broadcasts a signed notification of the new digest, each witness verifies an append-only audit proof against the previous digest and signs a vote, and once a quorum of votes is collected they aggregate into a certificate that any client can check without contacting every witness. The consistency protocol runs without a leader and without an external blockchain, which the paper states is why its throughput does not degrade when witnesses crash. To bound storage growth from an always-appending tree, Parakeet adds a two-phase compaction mechanism: at a tombstone epoch, entries eligible for eventual deletion are marked (not removed); only after a further compaction epoch are tombstoned entries actually deleted; auditors check that only sufficiently old entries are tombstoned and only tombstoned entries are deleted, and a client that wants deletion-soundness must query its own key history at least once between a tombstone epoch and the following compaction epoch.

### Parameters
- Byzantine fault model: 3f+1 total witnesses tolerate up to f Byzantine (arbitrary) failures; a quorum is any 2f+1 witnesses; network is assumed fully asynchronous (messages may be arbitrarily delayed and reordered but are eventually delivered).
- Benchmark baseline configuration: 10 honest witnesses, batch size 1,024 updates, update size 64 bytes (32-byte key + 32-byte value), committee size 4 for the microbenchmarks specifically.
- Tested batch-size range: 2^5 through 2^15 updates per batch.
- Tested witness-count range: 10, 20, 50 witnesses (throughput measured flat across this range).
- Tested crash-fault range: 0, 1, 3 crashed witnesses out of a 10-witness committee (3 stated as the maximum tolerable in that configuration).
- Node-state size for storage arithmetic: 64 bytes (32-byte hash output + 32 bytes of parent/child metadata).
- Signature scheme: ed25519-dalek, 32-byte public/private key pairs.
- Storage/transport implementation: Rust, tokio for async networking, RocksDB for persistence (unless otherwise specified), TCP for point-to-point channels.

### Stated limitations
The paper states that evaluating Byzantine (as opposed to crash) fault behavior for BFT-style protocols "is still an open question" and explicitly limits its crash-fault benchmark to crash faults only — no measurement of behavior under actively malicious (Byzantine) witnesses is reported. The compaction mechanism requires a client to come online and check its own key history at least once between each tombstone epoch and the following deletion epoch; a client that does not do so cannot detect a wrongful deletion, which the paper states as a minimal but real additional assumption compared to a pure append-only construction. The append-only base construction (before compaction) is stated to conflict with a right to full account-data deletion, which the paper mentions has relevance to "right to be forgotten" regulation. The 850 GB projected figure at 1 billion users is an extrapolation from a 5-million-user measurement, not a direct measurement at that scale. The throughput ceiling is attributed to the IdP being the system bottleneck (not the witness count), but the paper does not report the throughput ceiling of the IdP itself under further load, nor push witness count high enough to find where network overhead becomes the bottleneck — it states only that this crossover is "expected" to occur eventually.

### Requirements it places on the rest of the system
Every client of the directory must independently obtain a small server commitment for each epoch from an out-of-band source it trusts to be consistent across all clients — Parakeet supplies this itself via its witness quorum-certificate mechanism, but any component depending on Parakeet must be able to reach that witness quorum (a majority of 2f+1 out of 3f+1 witnesses) rather than trusting the IdP alone. At least one honest auditor must check each update for correctness every epoch for the non-equivocation soundness proof to hold; the paper's model assumes such an auditor exists (it can be any of the witnesses, executed as part of their normal protocol step) but the proof is void with zero honest auditors. Compaction's security depends on every client periodically running the KeyHistory check on its own key at least once per tombstone-to-deletion interval; a component that never re-queries an inactive user's key cannot detect that user's data being wrongly deleted. The protocol assumes bounded clock drift among witnesses is sufficient for f-fault tolerance deductions in the asynchronous model (the paper references bounded-clock-drift reasoning without giving a numeric bound). The system assumes the IdP and witnesses each hold a durable private signing key and that key compromise of the IdP is out of scope — Parakeet detects equivocation but does not itself prevent a compromised IdP from producing internally consistent but wrong data before compromise is discovered by another means. Deployment at the paper's benchmarked scale assumes access to persistent storage with fast random writes (RocksDB or MySQL in the reported configuration); the SEEMless-style comparison measurement shows that a naive append-only construction becomes storage-write-bound at a few hundred thousand users, so a system layering key transparency at billions-of-users scale needs the oZKS-style bounded-storage construction Parakeet supplies, not the plain append-only aZKS from SEEMless.
