## [KLEPPMANN-PAPOC-22] Making CRDTs Byzantine Fault Tolerant

**Citation:** Martin Kleppmann. "Making CRDTs Byzantine Fault Tolerant." 9th Workshop on Principles and Practice of Consistency for Distributed Data (PaPoC), co-located with EuroSys, 2022. 8 pages. DOI 10.1145/3517209.3524042.
**Retrieved:** full text via https://martin.kleppmann.com/papers/bft-crdt-papoc22.pdf
**Source URL:** https://martin.kleppmann.com/papers/bft-crdt-papoc22.pdf
**Domain:** D+H

### What it does
Adapts operation-based CRDTs (Conflict-free Replicated Data Types, data structures that let independent replicas apply updates in any order and reach the same state without coordination) to keep Strong Eventual Consistency when some replicas are Byzantine-faulty (deviate arbitrarily from the protocol, whether by bug or by intent). Strong Eventual Consistency has three requirements: eventual delivery (an update delivered at one correct replica is eventually delivered at all correct replicas), convergence (correct replicas that delivered the same set of updates hold equivalent state), and termination. The mechanism has two parts.

First, every update is identified by the cryptographic hash of its own byte-string encoding, and every update carries the hashes of its direct causal predecessors (updates it causally depends on), not the transitive closure. Updates and predecessor hashes form a directed acyclic graph (DAG), stored in full by each node, resembling a Git commit history without merge commits: after concurrent updates, the DAG simply has multiple heads (updates that are not yet a predecessor of any other update). Two nodes compare the hashes of their current heads; if equal, the two nodes have delivered identical update sets, because the head hashes transitively cover every update reachable from them. If the heads differ, a graph traversal locates the missing parts and each side sends the other only those. A Byzantine node can add arbitrary vertices and edges to the DAG, including updates that reference nonexistent predecessor hashes, but a correct node simply never delivers an update whose dependency cannot be resolved; this cannot prevent two correct nodes from eventually delivering the same update set, assuming hash collisions are computationally infeasible.

Second, operation identifiers are derived from the same hash rather than from a per-node sequence number. A per-node counter fails under Byzantine nodes because a faulty node can equivocate: emit two distinct updates carrying the same declared sequence number and send one to each of two correct nodes (demonstrated in the paper's Figure 1, where nodes p and q end up with identical version vectors after delivering different updates from Byzantine node r, defeating version-vector-based reconciliation). Using the update's own hash as its identifier removes this failure because a Byzantine node cannot alter the numbering without changing the hash, so duplicate identifiers become computationally infeasible to produce. When an update contains multiple operations needing multiple identifiers, each is the update hash concatenated with an integer 1, 2, ... local to that update.

For CRDTs whose operations require validity conditions beyond bare uniqueness (for example, RGA (Replicated Growable Array) requiring a deletion to reference a previously inserted, still-existing element, or WOOT/YATA requiring insertion operations to reference valid predecessor/successor elements), the paper gives a rule for making the accept/reject decision replica-independent: define `before(u)` as the set of updates transitively reachable through the predecessor hashes of update u. Two nodes with different total delivered-update sets `Up` and `Uq` still compute the identical `before(u)` for the same u, because `before(u)` depends only on u's own causal history. Basing the validity decision solely on `before(u)` guarantees every correct node reaches the same accept/reject verdict for u, which is what Section 2.4 shows is otherwise not guaranteed (a state-dependent validity check can accept an update at one correct node and reject it at another, causing divergence even under eventual delivery). An alternative for monotonic existence conditions (elements can be created but never destroyed, i.e. deletions retain tombstones) is to delay delivery of a dependent update until the referenced element's creating update has itself been delivered, which also preserves convergence.

### Measured results
None. The paper states no experiment, testbed, implementation, or performance measurement. Section 5 states explicitly that measuring the performance impact is left to future work.

### Parameters
None numeric beyond a size estimate given as an example, not a measured result: with up to three concurrent heads and 256-bit hashes, the set of all updates a node has delivered can be summarized in under 100 bytes regardless of the total update count or node count, citing the mechanism's prior source (Kleppmann and Howard, arXiv:2012.00472) rather than presenting it as newly measured here.

### Stated limitations
The paper conjectures, without proof, that hash-based unique identifiers plus the `before(u)`-restricted validity rule suffice to guarantee convergence for CRDTs in general; a detailed proof for particular CRDT algorithms is explicitly left to future work. The paper does not demonstrate the techniques are effective for any specific CRDT algorithm; that demonstration is left to future work. The paper does not address message authentication as a requirement: it states that if authentication (attributing an update to the node that generated it) is desired, updates can additionally be signed, but this is not necessary for Strong Eventual Consistency and is not analyzed further. The mechanism assumes hash collisions are computationally infeasible; it does not defend against an adversary that can produce collisions. Eventual delivery still requires that every pair of correct nodes can communicate, directly or indirectly through other correct nodes — a Byzantine node on every path between two correct nodes can block their communication, and no mechanism in the paper resolves that case. Byzantine nodes can degrade performance by generating a large number of concurrent updates (inflating the head count) or updates with many predecessor hashes, without breaking correctness; no bound or defense against this degradation is given. The hash-as-identifier scheme increases storage cost relative to short sequence-number identifiers; the paper suggests, without designing or measuring, a compression scheme that recomputes hashes on demand instead of storing them all.

### Requirements it places on the rest of the system
Every node must store the complete DAG of updates it has delivered (all vertices and edges), not a summary, since validity and delivery decisions read the full causal history of an update through `before(u)`. The system needs a way to encode each update as a byte string before computing its hash, and operation-based CRDT implementations must follow the generator/effector split (an operation is generated without side effects, then applied through a separate effector function) because the update's hash-derived identifier is only known after encoding, and the effector, not the generator, is what needs the identifier. The transport layer must support pairwise exchange of head-hash sets and DAG-traversal-based reconciliation of missing updates between any two nodes; no upper bound is placed on how many Byzantine nodes may be present, so the reconciliation protocol must not depend on quorum votes or a bound such as fewer than one-third or one-third Byzantine, unlike Byzantine reliable broadcast. Any CRDT with validity conditions beyond identifier uniqueness needs its accept/reject rule rewritten to depend only on `before(u)`, or on monotonic existence with delayed delivery; a CRDT that inspects mutable replica state outside `before(u)` when deciding validity is not covered by the proof sketch given. The mechanism assumes a cryptographic hash function collision-resistant against the deployment's adversary and, if update authorship matters, a signature scheme layered on top — neither is designed in this paper.
