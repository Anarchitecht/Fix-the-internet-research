## [ROSENBERG-RFC-03] STUN - Simple Traversal of User Datagram Protocol (UDP) Through Network Address Translators (NATs)

**Citation:** Jonathan Rosenberg, Joel Weinberger, Christian Huitema, Rohan Mahy. "STUN - Simple Traversal of User Datagram Protocol (UDP) Through Network Address Translators (NATs)." IETF RFC 3489, March 2003. DOI 10.17487/RFC3489.
**Retrieved:** full text via https://www.rfc-editor.org/rfc/rfc3489
**Source URL:** https://www.rfc-editor.org/rfc/rfc3489
**Domain:** L

### What it does
STUN (Simple Traversal of User Datagram Protocol Through Network Address Translators) lets a client behind a network address translator (NAT) discover the address and port the NAT has substituted for its own, and additionally determine which of four behavioral categories the NAT falls into, by sending UDP requests to a public STUN server and comparing what address the server reports receiving against what address the client actually sent from. The four categories, in order from least to most restrictive, are: full cone (every external host can reach the internal host at its one mapped address, regardless of which external address the internal host has contacted); restricted cone (only an external host the internal host has previously sent a packet to, identified by IP address alone, can reach it back); port restricted cone (the same restriction, but matched on the external host's IP address and port together); and symmetric (the NAT assigns a distinct external mapping to every distinct destination address-and-port pair the internal host contacts, so a mapping learned by contacting the STUN server cannot be reused to receive traffic from any other peer).

The client determines which category applies through a sequence of up to three tests built on two request variants the server supports: an ordinary Binding Request, answered from the same server address and port the request arrived on, and a Binding Request carrying a CHANGE-REQUEST attribute asking the server to answer from a different IP address, a different port, or both. Test I (an ordinary request) reveals whether the client sits behind any NAT at all, by comparing the client's own socket address against the MAPPED-ADDRESS the server reports receiving; if they match, the client is unNATed, and a further test (requesting a response from a changed address and port) distinguishes open Internet access from a symmetric UDP firewall (a firewall that requires replies to originate from the address a request was sent to, without performing any address translation). If the addresses differ, the client is behind some NAT, and requesting a response from the changed address and port distinguishes full cone (response received) from the three more restrictive types (no response). Among those, repeating Test I toward the server's alternate address, then comparing the newly returned mapped address against the first test's result, distinguishes symmetric NAT (different mapping per destination) from the two cone types; a further request asking only for a changed port then distinguishes restricted cone from port restricted cone. Because the NAT closest to the public Internet along the path is the one that determines actual reachability, when several NATs sit in series between the client and the server, this procedure reports the behavior of whichever of them is the most restrictive, not necessarily the one nearest the client.

### Parameters
- Binding Request retransmission schedule: retransmit starting at a 100 ms interval, doubling on each retransmit until reaching 1.6 s, then continuing at 1.6 s intervals until a response arrives or 9 requests total have been sent; requests are sent at 0 ms, 100 ms, 300 ms, 700 ms, 1500 ms, 3100 ms, 4700 ms, 6300 ms, and 7900 ms, and the client declares the transaction failed if no response arrives by 9500 ms (1.6 s after the final retransmit).
- Shared Secret Request / Binding Request transaction failure timeout: 9.5 seconds after the first request is sent (matches the retransmission-schedule endpoint above).
- Post-response listen window: after receiving one response, the client MUST keep listening for further (duplicate) responses to the same request for 10 seconds.
- Username validity window for a shared secret obtained via a Shared Secret Request: 9 minutes.
- Recommended interval between repeating the full discovery process from the same local address and port: at least half an hour, stated as sufficient for prior NAT bindings from an earlier discovery run to have expired and stop interfering with a repeated test; alternatively, the client can use a different local address and port for each repeated run to avoid the issue entirely.
- Transaction ID: 128 bits of randomness per request, used by the client to reject any response not matching an outstanding request.

### Stated limitations
The specification states its own applicability limits explicitly at the outset: STUN does not enable incoming TCP connections through a NAT at all; it does not enable incoming UDP packets through symmetric NATs, described as common in large enterprises; its discovery procedure rests on assumptions about how NATs treat UDP that the document itself flags as liable to become invalid as new NAT devices are deployed; it does not work when the peer a client wants to reach sits behind the same NAT as the client; and it does not work if the STUN server itself is not reachable within a shared public address realm common to both communicating clients. Section 14 (framed as the IAB's required brittleness discussion for any "UNilateral Self-Address Fixing," UNSAF, proposal) lists further concrete failure conditions: the binding-acquisition technique yields a usable address for any application only behind a full cone NAT, requires application-specific handling behind restricted or port restricted cone NATs, and yields no usable address at all behind a symmetric NAT; NAT binding refresh intervals are described as highly implementation-specific and therefore not reliably determinable, so a client waiting for an incoming message rather than actively receiving traffic wastes bandwidth on refresh traffic it cannot size correctly; using STUN adds at least one round-trip time of latency to call setup for a real-time application; and binding-lifetime discovery itself is described as "prone to error" because it assumes one lifetime applies uniformly across a NAT's bindings, an assumption a NAT using dynamic lifetimes under load, or one that reboots mid-discovery, can violate. Two topological failure conditions are stated explicitly: an address obtained from a STUN server is not usable by a peer if that STUN server does not sit in an address realm that is a common network ancestor of both communicating clients, and even when it does, some NATs refuse to accept a packet sent from inside their own network back to a public address that maps back into that same network (a case this document states requires additional, unspecified protocol mechanisms or configuration to detect). The document states its central security limitation directly: STUN "introduces potential security threats which cannot be eliminated," calling the underlying problem "provably unsolvable" given what STUN attempts, and describes only mitigating heuristics, not a resolution, deferring the full description to its Security Considerations section.

### Requirements it places on the rest of the system
The mechanism requires a STUN server reachable over UDP by the client and located in a public address realm that both communicating peers can treat as a common topological ancestor; if the client's application later shares its discovered mapped address with a peer, correct operation depends on that ancestor condition holding, which STUN itself has no way to verify or detect a violation of. The classification procedure requires the STUN server to support the CHANGE-REQUEST attribute, meaning the server must itself have more than one public IP address and more than one listening port available to answer from, since two of the three tests ask the server to reply from an address, a port, or both, that differ from where the request arrived. Any application depending on the discovered mapped address remaining valid must independently track and refresh the underlying NAT binding, at an interval the application must determine for itself since this document states NAT binding timeouts are implementation-specific and not discoverable with certainty; the document's companion "Binding Lifetime Discovery" procedure (Section 10.2) offers only an approximation, degraded further under a NAT with dynamic, load-dependent lifetimes. A client repeating the discovery procedure must either wait roughly half an hour or use a fresh local address and port each time, or risk a leftover binding from the prior run corrupting the new classification result. Any protocol built on top of STUN's discovered address for peer-to-peer rendezvous must independently defend against the injected-fake-mapped-address attacks this document describes (Section 12.1): it names Distributed Denial of Service against a third-party target, silencing a legitimate client, identity assumption, and eavesdropping, and states the transaction-ID randomness (128 bits) as the only structural defense STUN itself supplies, which is effective only against an attacker who cannot observe the client-to-server traffic.
