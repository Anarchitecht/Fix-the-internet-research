## [GOODRICH-ALLERTON-11] Invertible Bloom Lookup Tables

**Citation:** Michael T. Goodrich, Michael Mitzenmacher. "Invertible Bloom Lookup Tables." 49th Annual Allerton Conference on Communication, Control, and Computing, 2011. DOI 10.1109/ALLERTON.2011.6120248.
**Retrieved:** full text via https://arxiv.org/abs/1101.2245
**Source URL:** https://arxiv.org/abs/1101.2245
**Domain:** D

### What it does
An Invertible Bloom Lookup Table (IBLT) supports insertion, deletion, and probabilistic lookup of key-value pairs, and additionally supports listing every key-value pair it holds with high probability once the number of stored pairs falls at or below a threshold t fixed at construction; unlike a standard Bloom filter, whose bit array cannot be read back into a list of members, an IBLT's cells retain enough information to reconstruct the actual entries. The structure is a table T of m cells, each holding a count field (the number of key-value pairs hashed into that cell), a keySum field (the sum of all keys hashed into that cell), and a valueSum field (the sum of all values hashed into that cell). Each key x is hashed by k independent hash functions h_1...h_k to k distinct cells (achieved in practice by splitting T into k subtables of size m/k, one hash function per subtable). INSERT(x,y) adds 1 to count, x to keySum, and y to valueSum at each of the k cells; DELETE(x,y) subtracts the same three values; both always succeed. GET(x) checks each of x's k cells: if any has count 0, x is not present (return null); if a cell has count 1 and its keySum equals x, that cell's valueSum is the answer; GET can return a "not found" error with low but constant probability when x is present but every one of its cells holds more than one entry. LIST_ENTRIES() repeatedly finds any cell with count exactly 1, reads off its (keySum, valueSum) as a genuine key-value pair, and calls DELETE on that pair (which removes its contribution from every other cell it was hashed into, potentially exposing new count-1 cells), continuing until no count-1 cells remain; if every cell then holds count 0, every pair was recovered, otherwise recovery is partial and the paper reports a "list-incomplete" condition. The paper identifies this exact process as the peeling algorithm that computes the 2-core of a random hypergraph, where table cells are hypergraph vertices and key-value pairs are hyperedges connecting the k cells each key hashes to; recovery succeeds exactly when the hypergraph's 2-core is empty. To tolerate operational errors — a delete issued for a pair that was never inserted (an "extraneous deletion"), or a key that erroneously receives more than one distinct value — the structure is augmented with a hashkeySum field (the sum of an independent hash G1(x) of each key hashed into the cell) and, for the multiple-value case, a hashvalueSum field (sum of an independent hash G2(y) of each value). These checksum fields let count-1 cells be verified before being trusted, and let a cell with count -1 (produced when a key is deleted before or without a matching insertion) still be checked and, if verified, resolved during listing by negating and processing it as if it were a normal single entry.

### Parameters
- k (number of hash functions per key): all reported experiments use k=5; Table 1 gives 2-core threshold constants c_k for k=3 through 7, with c_k growing slowly with k and remaining close to 1.
- m (number of cells): set above (c_k + epsilon) * t for the target threshold t, per Theorem 1; example values used: 14,600 (t approx. 10,000, k=5), 144,000 (t approx. 100,000, k=5), 80,000 (t=10,000, k=5, ratio m/n=8), 800,000 (t=100,000, k=5).
- R (range of the checksum hash G1, and G2 for values): must be chosen large enough that a false checksum match does not occur across the structure's operational lifetime; the paper states O(log n) bits suffice for a lifetime polynomial in n, giving a false-check probability of at most 1/R per check.
- gamma (fraction of keys that are invalid, i.e., erroneously multi-valued or deleted-without-insertion): example configuration gamma = 1/10 with k=5, m/n=8 gives a computed per-key unrecoverability probability of approximately 8.16e-7.
- beta (theoretical analysis parameter for n^(1-beta) invalid keys, Theorem 2): using k = ceil(1/beta) + 4 hash functions guarantees, with high probability, every valid key retains at least 3 hash locations free of invalid-key contamination, at which point the same 2-core threshold analysis as the error-free case applies.

### Stated limitations
LIST_ENTRIES fails (returns a "list-incomplete" partial listing) whenever the number of stored pairs n exceeds design threshold t enough that the 2-core of the underlying random hypergraph is non-empty; the paper states m must be chosen above (c_k + epsilon) * t for the listed success guarantee to hold, and below that, in the region where m < (c_k - epsilon) * n, LIST_ENTRIES succeeds only with probability o(1). GET can return a spurious "not found" for a key that is genuinely present, with a stated approximate probability (1 - e^(-kn/m))^k that grows as the load n/m grows, so GET accuracy degrades under overload even before listing fails outright. If a constant fraction of keys are invalid (multiply-valued or extraneously deleted with no matching prior state), the paper proves this defeats complete recovery under linear space: "we first claim that if the invalid keys make up a constant fraction of the n keys that this is not possible under our construction with linear space," because a constant fraction of cells become permanently "poisoned" and some valid keys will, with constant probability, hash only to poisoned cells. The fault-tolerance mechanism assumes hash functions are close enough to fully random that the checksum collision-probability argument (a false check probability of at most 1/R) holds; the paper explicitly flags this as an open theoretical question for hash functions with only limited independence acting on worst-case data ("It is an interesting theoretical question to obtain better bounds on the randomness needed"). The paper's own simulations did not measure running time or account for word-value overflow, stating a practical implementation "could require significant optimization" and that overflow handling was set aside. Stated future work: whether multiple values per key can be supported as an intended feature rather than handled only as an error condition.

### Requirements it places on the rest of the system
Both the structure's designer and any party issuing lookups must fix the threshold t (and correspondingly m, sized above (c_k + epsilon) * t) in advance, since the probabilistic guarantees for both GET and LIST_ENTRIES are conditioned on the actual number of stored pairs n staying at or below t at the moment of the operation — the paper is explicit that INSERT and DELETE always succeed and never enforce this bound themselves, so a caller that lets n grow arbitrarily beyond t without later reducing it will not regain listing or lookup accuracy until n returns to t or below. Correctness under extraneous deletions and multiply-valued keys depends on an independent checksum hash function (G1 for keys, G2 for values) with a sufficiently large range R chosen so that the false-check probability 1/R stays negligible over the structure's operational lifetime; a system deploying the fault-tolerant variant must supply and size this hash function itself. The peeling-decode process (LIST_ENTRIES) requires the caller to detect and handle a "list-incomplete" result, since partial recovery is a normal, non-error outcome of the mechanism when n exceeds t or invalid keys are present, not a crash condition. The paper's database-reconciliation usage case (Section 1.3) requires the two reconciling parties to use the same hash functions and threshold parameters when constructing their respective IBLTs, and requires each stored value to be a checksum of the actual record (not the record itself), so record retrieval after reconciliation needs a separate mechanism to fetch full records once mismatched checksums are identified.

### Contradicts
None found. This entry is the primary source EPPSTEIN-SIGCOMM-11 and GOMES-ARXIV-25 (both in this corpus) build on; those papers' idSum/hashSum/count cell layout is a keys-only variant of the keySum/valueSum/count/hashkeySum layout this paper defines for key-value pairs, not a disagreement.
