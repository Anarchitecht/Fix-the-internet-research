## [HALKES-NETWORKING-11] UDP NAT and Firewall Puncturing in the Wild
**Citation:** Gertjan P. Halkes, Johan A. Pouwelse. "UDP NAT and Firewall Puncturing in the Wild." IFIP Networking, 2011. DOI 10.1007/978-3-642-20798-3_1.
**Retrieved:** full text via https://opendl.ifip-tc6.org/db/conf/networking/networking2011-2/HalkesP11.pdf
**Source URL:** https://link.springer.com/chapter/10.1007/978-3-642-20798-3_1
**Domain:** L

### What it does
This paper measures how often two Network Address Translator (NAT) boxes or firewalls, of unknown and possibly differing behavior, can be made to accept a direct UDP connection from each other using UDP hole punching, a technique in which each peer sends an outbound packet toward the other so that the intervening NAT or firewall opens a path for the reply. The paper classifies a NAT or firewall's outbound-mapping behavior into three categories: Endpoint-Independent Mapping (EIM, the NAT reuses the same external IP and port for a given internal IP and port no matter which remote host is contacted), Address-Dependent Mapping (ADM, a new external mapping per remote IP address), and Address-and-Port-Dependent Mapping (APDM, a new external mapping per remote IP-and-port pair); ADM and APDM are collapsed into one category, A(P)DM, because the experiment used only single endpoints per host. Filtering behavior (whether inbound packets are accepted at all) is classified as Endpoint-Independent Filtering (EIF, any external source may reach the mapped port) or Address(-and-Port)-Dependent Filtering (A(P)DF, only a host the internal side has already contacted may reach it). The measurement software, built into the Tribler BitTorrent client and deployed to real users' machines over two trials, has each peer self-determine its own NAT/firewall type by comparing the external address and port reported back to it by different communication partners (rather than using STUN, a centralized address-discovery protocol) and by checking whether a direct connection request from a remote peer arrives before or after a rendez-vous-mediated reverse connection request. A third peer already connected to both endpoints acts as a rendezvous server, relaying each side's address to the other so both can attempt simultaneous outbound packets, and this rendezvous role does not require the relaying peer itself to be directly connectable.

### Measured results
| Result | Condition |
|---|---|
| 21% of peers are directly connectable (EIM-EIF: no NAT-imposed mapping change, no filtering) | Trial 1, 907 peers, 646 peers for which a NAT/firewall type conclusion could be drawn |
| 52% of peers are EIM-APDF (endpoint-independent mapping, address-and-port-dependent filtering), the largest single category | Trial 1, same 646-peer subset |
| 11% of peers are behind an A(P)DM NAT (mapping changes per remote host), the type the paper calls the largest obstacle to connectability, because it can only connect to EIM-EIF and EIM-ADF peers | Trial 1, same 646-peer subset |
| 79% of peers are not directly connectable without a NAT-traversal mechanism | Trial 1, same 646-peer subset, restated in Section 6 as an aggregate finding |
| A further 64% of all peers can potentially set up connections between themselves through rendezvous-mediated UDP hole punching (the EIM-A(P)DF population), reducing the population that cannot connect at all to about 15% | Trial 1, restated in Section 6 and the Conclusions |
| More than 80% of hole-punching attempts between eligible peer pairs succeed | Trial 1 abstract-level summary figure, drawn from the pairwise success-rate breakdown below |
| Peers classified EIM-EIF still show only an 85% pairwise connection success rate against each other, attributed to a minority of peers with persistently poor connectability, plausibly caused by link saturation | Second-trial dataset: 15,545 connections between 841 peers for which both endpoints' NAT/firewall type were known |
| Connections between EIM-ADF and EIM-A(P)DF peer pairs succeed slightly more often than EIM-EIF-to-EIM-EIF pairs, but the paper states this is not statistically significant | Same 15,545-connection dataset; only 36 peers in the trial were classified EIM-ADF |
| Connections to and from EIM-APDF peers succeed slightly less often than EIM-EIF-to-EIM-EIF pairs | Same 15,545-connection dataset |
| First-attempt connections from an A(P)DM peer to an EIM-ADF peer succeed in approximately 41% of cases, attributed to Triangle Inequality Violation (TIV) — the direct packet arriving after, rather than before, the rendezvous-relayed reverse packet that opens the remote firewall hole | Same 15,545-connection dataset |
| Injecting UDP side traffic in a local test environment against newly acquired NAT routers produced packet-loss rates of 50% or more, or router crashes, on some routers; TCP side traffic on the same routers produced no more than 5% packet loss | Separate local reproduction test, not the field trial; routers described only as "newly acquired," no count or model list given |
| Mapping/firewall hole timeout: many NAT/firewalls use a timeout of one minute or less when only a single request-reply packet pair is exchanged; when an initial handshake precedes the delayed-reply probe, the timeout shifts to markedly longer values, with a large fraction of peers showing a 180-second timeout, matching the Linux kernel default | Timeout probe sent from a pre-programmed IP address and port at several delay values simultaneously from different source ports; small number of EIM-ADF NAT/firewalls excluded from this measurement because their behavior could distort the result |

The paper states no exact numeric labels for the per-pair connection success rates beyond those given in prose (the source figure, Table 1, is a colored bar matrix without printed percentages for every cell); only the specific percentages called out in the text above (85%, approximately 41%) are usable as numbers.

### Parameters
- Trial 1: 907 peers, no immediate retry on a failed connection attempt, ran several weeks, log data sent to a central collection server.
- Trial 2: 1,531 peers, up to three retries on a failed connection attempt, ran several weeks, used a less intrusive reporting method that the paper states biased the sample toward peers with unfiltered Internet connections — for this reason the paper uses Trial 1 for the market-share (NAT/firewall type distribution) result and the combined 15,545-connection dataset (drawn from peers with both endpoints classified) for the pairwise success-rate result.
- New-connection cooldown enforced during the experiment: 5 minutes, to prevent a closed connection's still-open mapping from producing a false first-attempt success.
- Recommended keep-alive interval, derived from the timeout measurement: send at least every 55 seconds, assuming several messages are exchanged within the first 30 seconds of a mapping's life, because some NAT/firewalls extend the timeout only after observing more than a single request-reply exchange.

### Stated limitations
The paper states its sample is likely biased toward home users rather than corporate users, because P2P file-sharing software use is typically discouraged in a corporate environment, and that home users tend to use less professional network equipment "more prone to misbehaviour," which may reduce the reported connection success rates below what a more diverse population would show. The paper states it did not implement a mechanism to distinguish Address-Dependent Filtering (ADF) from Address-and-Port-Dependent Filtering (APDF) in the live client, though it collected data (A(P)DF-to-A(P)DM connection attempts) that could later distinguish them, because the two categories account for only a small fraction of peers and the paper judged the software complexity not worth the benefit. The paper states it could not discount packet loss on saturated links, mapping-table exhaustion in some older router models, or other unidentified points of packet loss as causes of below-100% success rates among nominally compatible peer pairs, and states it did not have access to older router or modem models to test this directly. The local packet-loss reproduction test used only "newly acquired" NAT routers, which the paper states may behave differently, and possibly more resiliently, than the router population actually deployed among the trial's peers.

### Requirements it places on the rest of the system
A design relying on this paper's rendezvous mechanism needs a third peer already holding an established connection to both endpoints that want to connect, so a directly-connectable-peer population (this paper measures it at 21% of the total in Trial 1) must exist for rendezvous relaying, or another means of introducing peers to a shared connected third party. NAT/firewall type self-classification depends on receiving consistent address/port reports from multiple independent communication partners, so a peer with too few prior connections cannot yet classify itself and the classification is stated to be probabilistic, not certain, in the presence of "behavioural subtleties" the paper documents in some NAT implementations. The paper's connection-setup protocol depends on a direct connection request being sent before, or nearly simultaneously with, a rendezvous-relayed reverse connection request, and unpredictable one-way-delay ordering between the two paths (attributed to a Triangle Inequality Violation between direct and relayed paths) is stated to determine whether the very first attempt at an asymmetric peer pair succeeds, so a system depending on first-attempt success for A(P)DM-to-EIM-ADF pairs cannot assume it above roughly 41%. Any system relying on the measured mapping timeouts must send periodic keep-alive traffic at intervals no longer than about 55 seconds per this paper's data, or a NAT/firewall mapping will close and require a fresh hole-punching exchange.

### Contradicts
None found. The paper's own numbers are internally two-sided: the abstract's rounded "approximately 64%... more than 80%" summary corresponds to the more granular breakdown in Section 5.2 and Section 6 (85% for EIM-EIF pairs, approximately 41% for A(P)DM-to-EIM-ADF first attempts), which are lower than the abstract's rounded floor for specific peer-type pairs; a reader citing only the abstract figure would understate the variance the paper itself reports across NAT/firewall type combinations.
