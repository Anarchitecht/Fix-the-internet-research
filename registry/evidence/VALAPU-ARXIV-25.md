## [VALAPU-ARXIV-25] Towards a Non-Binary View of IPv6 Adoption

**Citation:** Sulyab Thottungal Valapu, John Heidemann. "Towards a Non-Binary View of IPv6 Adoption." ACM Internet Measurement Conference (IMC), 2025. DOI 10.1145/3730567.3764467.
**Retrieved:** full text via https://arxiv.org/pdf/2507.11678
**Source URL:** https://arxiv.org/abs/2507.11678
**Domain:** L

### What it does
The paper measures how much of a dual-stack participant's actual Internet Protocol version 6 (IPv6) traffic is used, at three levels — client, server, cloud/CDN (content delivery network) provider — instead of measuring only whether IPv6 is supported at all. At the client level, commodity routers running OpenWRT with a custom flow monitor record every inbound/outbound flow's protocol version, byte count, and timing at five residences, without inspecting payload content, to compute the day-by-day and site-by-site fraction of traffic that is IPv6 rather than IPv4. At the server level, the OpenWPM web-privacy-measurement framework drives a real Firefox browser to load each of the Tranco top 100,000 websites' main page plus five randomly chosen same-domain internal links, recording every HTTP request, DNS result, and connection IP address for the main page and every embedded (including third-party) resource, then classifies each site by whether its main page has an IPv6 (AAAA) DNS record (else IPv4-only), whether every embedded resource is IPv6-reachable (IPv6-full) or only some are (IPv6-partial). At the cloud level, the same server-side crawl's resource fully qualified domain names (FQDNs) are attributed to a hosting organization via CAIDA's AS-to-Organization dataset, and IPv6 readiness is compared per organization; to separate a cloud's own IPv6 support from a tenant's choice to enable it, the paper isolates "multi-cloud tenants" (one eTLD+1 domain whose subdomains are split across two or more different cloud organizations) and compares the same tenant's IPv6-full fraction of subdomains across the different clouds serving it, using a two-sided Wilcoxon signed-rank test per cloud pair.

### Parameters
- Tranco list snapshot used: top 1M list dated 2024-10-16 (list ID Z3Z3G), top 100,000 sites analyzed
- Internal-link crawl depth: main page plus 5 randomly chosen same-eTLD+1 links (fewer if a page has too few links)
- Measurement rounds for server-side crawl: October 2024, April 2025, July 2025 (nine-month span)
- Client-side flow-monitoring duration: 9 months (November 2024-August 2025) across 5 residences
- OpenWRT version on measurement routers: 22.03.3, Linux kernel 5.10
- Misclassification check for Happy-Eyeballs-driven protocol-dependent resource selection: found 106 potentially misclassified sites, 0.4% of all IPv6-partial sites (FQDNs containing substrings such as "v4", "ipv4", "px4")

### Stated limitations
The client-side residence study covers only five residences in a single metropolitan area (Los Angeles), with partial traffic visibility at two of the five residences because some individuals opted out; the authors state they make no claim that this small sample represents the Internet or even users in their region. The client-side dataset contains only flow-level information (five-tuple, byte/packet counts, timing), with no visibility into specific websites accessed or payload content, a restriction the authors state was required by their Institutional Review Board (IRB) agreement to protect study-participant privacy. The server-side analysis inherits known limitations of any top-list-based study: results can vary by choice of list, list age, and list size; the authors state they chose Tranco for its use of multiple ranking sources and its wide adoption but note no list perfectly reflects popularity. A site's set of embedded resources can differ depending on which IP protocol wins the browser's Happy Eyeballs race, which can misclassify an otherwise IPv6-full site as IPv6-partial if IPv4 wins the race and the page then dynamically selects IPv4-only resources; the authors estimate this affects at most 0.4% of IPv6-partial sites via a substring-based check and state this rare edge case is unlikely to affect overall conclusions. The paper treats all third-party resources as one category despite functional differences (a broken ad versus a missing JavaScript library), which the authors state may overlook differences in real-world impact. The cloud-adoption analysis evaluates only default-policy differences (default-on versus opt-in) and does not evaluate secondary factors such as a provider's operational history or pre-existing customer configurations that could also explain adoption-rate differences between providers sharing the same default policy; the authors state they leave a more detailed investigation of these differences to future work.

### Requirements it places on the rest of the system
A design that treats "the client has IPv6" or "the destination has IPv6" as a fixed, binary property of a participant or service is contradicted by this paper's own measured variance: external IPv6 byte-fraction at a single residence has a daily standard deviation exceeding 15% (Table 1's per-residence daily standard deviation column ranges roughly 0.09-0.42 across residences), so any component that hard-codes an assumed protocol availability for a peer must instead re-check or re-negotiate protocol capability per session or per day rather than caching a one-time determination. A design relying on full IPv6 reachability of a named web resource (not just its main page) must budget for the finding that only 12.6% of top-100,000 sites are IPv6-full end to end, and that this fraction was measured to rise only 0.6 percentage points over nine months, so a network deployed against an assumption of near-universal IPv6 destination reachability needs an IPv4 fallback path for the majority of named web-scale destinations for the foreseeable future. A design that depends on a cloud or CDN provider's default configuration to determine tenant IPv6 support cannot assume uniform behavior across providers, because the paper measures a 3%-85% range in per-provider tenant IPv6-full adoption largely attributable to whether that provider enables IPv6 by default versus requiring explicit opt-in.

### Contradicts
None found within this corpus. The paper's own within-study comparison shows a common assumption is not supported by its data: the belief that a dual-stack host, which prefers IPv6 via the Happy Eyeballs algorithm, will show IPv4 traffic only for genuinely IPv4-only services is complicated by the finding that the majority of bytes remain IPv4 at 3 of 5 residences even though the majority of flows are IPv6 at those same residences — large-volume flows (downloads, streaming) more often remain IPv4 even where flow-count-based adoption looks high.
