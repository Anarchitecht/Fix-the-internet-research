## [CASTRO-SOSP-03] SplitStream: High-Bandwidth Multicast in Cooperative Environments
**Citation:** Miguel Castro, Peter Druschel, Anne-Marie Kermarrec, Animesh Nandi, Antony Rowstron, Atul Singh. "SplitStream: High-Bandwidth Multicast in Cooperative Environments." ACM Symposium on Operating Systems Principles (SOSP), 2003.
**Retrieved:** full text
**Source URL:** target record (registry/targets-deduped.json)
**Domain:** L (also relevant to K, application-layer patterns: peer-assisted video)

### What it does
SplitStream distributes the forwarding load of live multicast (one source sending the same stream to many receivers) evenly across all participating peers, instead of concentrating it on a small set of interior tree nodes, so that every peer can be asked to forward only as much data as it receives. The source splits the content into k stripes (for example, k separately encoded portions of a video stream, produced by multiple description coding, or k erasure-coded blocks of a file). Each stripe is multicast over its own tree, built with Scribe (an application-level multicast system layered on the Pastry structured overlay: each node has a random nodeId, and a multicast tree for a group is the union of Pastry routing paths from each member to a pseudo-random groupId). SplitStream chooses each stripe's groupId (called the stripeId) so the k stripeIds differ in their most significant digit; because Pastry routes messages toward nodes sharing a longer prefix with the destination key, this forces the trees' sets of interior (forwarding) nodes to be disjoint by construction, so a node that forwards stripe i is necessarily a leaf, not an interior node, in every other stripe's tree. To bound a node's outbound bandwidth (its number of children across all trees, i.e., its forwarding capacity), a node that has reached its outdegree limit rejects one existing child (a "push-down") when a new child requests to join, favoring rejection of children in stripes that do not share a prefix with the node's own nodeId; the rejected child then either finds a new parent among its former siblings (recursively) or anycasts to a "spare capacity group" of nodes with unused forwarding capacity, located via a depth-first search over that group's own Scribe tree so the located parent is near the orphan in the underlying physical network.

### Parameters
- Number of stripes k = 2^b, tied to the Pastry base parameter b; experiments used b=4, giving k=16 stripes.
- Pastry leaf-set size l=16.
- Node-degree configurations tested: 16x16 (desired indegree 16, forwarding capacity 16, spare capacity 0 beyond stripe-origination exemption), 16x18 (12.5% spare capacity), 16x32 (100% spare capacity), 16xNB (no forwarding-capacity bound), dxd (indegree equals forwarding capacity per node, with each node receiving its "home" stripe with probability 1 and each other stripe with probability 0.5), and a Gnutella-bandwidth-derived configuration (desired indegree = max(1, min(inbound_bandwidth/20 Kbps, 16)), forwarding capacity = min(outbound_bandwidth/20 Kbps, 32), assuming a 320 Kbps stream at 20 Kbps per stripe, sampled from measured Gnutella peer bandwidth distributions, yielding approximately 90% of nodes with desired indegree 16 and a mean spare capacity of 6.9 per node).
- Simulation topologies: GATech (5,050 routers, transit-stub, 10 transit domains averaging 5 routers each, 10 stub domains per transit router averaging 10 routers each, 10 random seeds averaged), Mercator (102,639 routers, 2,662 autonomous systems, hop count as delay proxy), CorpNet (298 routers, measured Microsoft corporate network, link delay = minimum measured delay over one month).
- LAN link delay: 1 ms.
- Implementation optimizations used in simulation: cycle-detection state maintained only at nodes whose parent does not share a longer prefix than the child (reduces construction overhead up to 40%); batched anycasts across multiple stripes per join (reduces anycast count up to 8x); depth-first anycast traversal that avoids revisiting a parent.

### Stated limitations
The correctness and complexity analysis (Section 4.5) assumes all nodes in the node set N join the forest simultaneously, that communication is reliable so all spare capacity is visible in the spare capacity group, and that nodes do not leave voluntarily or through failure; the authors state SplitStream includes mechanisms to handle violations of each assumption but that these mechanisms "may block some" of the guarantees the analysis provides. The bandwidth-bottleneck model assumes the bottleneck between two communicating nodes lies at the sender or receiver access link, not in the network interior; the authors state this does not hold universally and describe extending SplitStream (monitoring per-stripe arrival rate and re-parenting on shortfall) as future work, not implemented. Free-riding (a node that consumes forwarding capacity without contributing its own, cited by the authors as prevalent in Gnutella) is identified as an issue in open cooperative environments; the authors state that discouraging it, beyond local enforcement of the node-degree constraint, would need either a trusted execution platform or an incentive mechanism, and state this explicitly as "an interesting area of future work," not solved in this paper. The Mercator topology has no measured link-delay data, so delay-penalty (RAD/RMD) results are not reported for it. Anycast to the spare capacity group can fail to find a parent even when eligible capacity exists, if every candidate would create a routing cycle with the orphan; the paper's own mechanism to resolve this (finding and displacing a non-descendant leaf in the desired stripe tree) is described but its own success rate under this specific failure mode is not separately measured.

### Requirements it places on the rest of the system
SplitStream requires a structured peer-to-peer overlay with prefix-based routing (the paper uses Pastry) whose group-communication layer builds each multicast tree as the union of overlay routing paths from members to a group's rootId (the paper uses Scribe); the interior-node-disjoint property is obtained purely by choosing k groupIds that differ in their most significant digit, so it depends on the overlay's routing actually converging by shared key prefix, not by any separate scheduling step. Applications using SplitStream must supply content encoded so each stripe requires approximately equal bandwidth and so the content can be reconstructed from a sufficient subset of stripes (the paper names multiple description coding for streaming media and erasure coding for file data as the two encodings it is designed around); a stripe-splitting scheme without this redundancy property loses playable or reconstructible content whenever any stripe's tree is disrupted. The system needs each node's own nodeId to determine which one stripe it is obligated to forward (the stripe whose stripeId shares its nodeId's leading digit), so nodeId assignment must precede stripe-tree construction. Bounding a node's outbound bandwidth to its stated forwarding capacity is enforced only locally by each node's own SplitStream instance; the mechanism does not verify a node's claimed capacity or degree against any external check, so it requires participant honesty about capacity, or a separate incentive or trusted-execution mechanism supplied elsewhere, to resist a node that falsely advertises high spare capacity or refuses forwarding after joining.
