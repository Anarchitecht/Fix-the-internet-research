### What it does
SPHINCS+ produces a digital signature scheme that needs no persistent record of which keys it has already used (stateless), built entirely from hash-function security assumptions (no lattice or pairing assumption), so a signer can reuse the same long-term key pair on multiple machines or after restoring from backup without risking a forgery from key reuse — a failure mode that stateful hash-based schemes such as XMSS or LMS suffer if their usage counter is ever rolled back or duplicated. It generates a large virtual tree of one-time signing keys (a hypertree, split into d layers of Merkle trees, each of height h/d), addresses a leaf key pseudorandomly by hashing the message together with the signer's secret seed, and never needs to track which leaf was used before because a new message picks a fresh pseudorandom leaf with overwhelming odds of avoiding collision. Instead of a single-use one-time signature scheme signing the message digest directly, SPHINCS+ replaces it with a new few-time signature scheme the authors call FORS (forest of random subsets), which the authors state gives better size/speed trade-offs than the plain hash-to-obtain-a-leaf-index approach used by SPHINCS. The framework's second contribution is an abstraction called a tweakable hash function — a hash function parameterized by a public "tweak" value distinct per tree position — which lets the paper's security reduction treat every internal hash call generically and derive a single unified security bound, rather than re-deriving security for each hash-function instantiation choice from scratch. The framework offers two families of tweakable-hash-function instantiations, "robust" and "simple": robust achieves security in the standard model plus a quantum random oracle model (QROM) argument for compact public parameters, while simple gives up that formal guarantee for smaller code and faster execution. Signing is deterministic by default — the per-message randomizer R is derived from a secret PRF key and the message, with no external entropy source needed — but the framework supports an optional additional randomness input (OptRand) to counter side-channel attacks that exploit deterministic signing.

### Parameters
- Hypertree height h and layer count d: search-selected per target instantiation (examples above range h=51 to h=66, d=9 to d=22); h is not free — the paper's parameter-search script iterates h from `s-8` to `s+20` where `s = log2(max signatures)`, and requires `h % d == 0`.
- FORS parameters b (height of each FORS tree) and k (number of FORS trees): search-selected together with the target forgery-probability bound; example values k=29 to k=49, b=7 to b=12.
- Winternitz parameter w: fixed to 16 or 256 in the exploration script; all reported benchmark instantiations use w=16, which the paper states is chosen for a "reasonable trade-off between signing time and signature size."
- Hash-function output length n: 192 or 256 bits in the reported comparisons (also 128-bit variants in the NIST table); larger n raises security level and signature size together.
- Tweakable hash function instantiation choice: robust (SHA-256, SHAKE256, or Haraka; needs a QROM argument for compact public parameters) or simple (same three hash-function choices, no such proof); Haraka-based instantiations cannot reach as high a security level as SHA-256/SHAKE256 because of a generic meet-in-the-middle collision attack on Haraka's internal state, with classical complexity 2^128.
- Maximum signatures per key pair: parameter sets are generated for a target maximum (e.g., 2^50 for the SPHINCS-256 comparison, 2^64 for all NIST-submitted instantiations) — the maximum is a design input to the parameter search, not a fixed constant of the framework.
- Message-randomization input R: derived deterministically as `R = PRF(SK.prf, OptRand, M)`; OptRand can be set to a fixed public value (fully deterministic signing) or to fresh randomness (probabilistic signing, stated as a side-channel countermeasure) — this is a configurable choice, not a fixed value.

### Stated limitations
The paper states that all its benchmarked schemes — SPHINCS+, SPHINCS-256, Gravity-SPHINCS, Picnic — "do not reach the performance of, e.g., lattice-based signature schemes like Dilithium, Falcon, or qTESLA," and states these symmetric-primitive-only schemes are "mainly interesting for applications without strong latency requirements, such as offline code signing or certificate signing," not applications with strict latency needs. The paper states a general rule of thumb for the whole hash-based-signature design space: "a linear decrease in signature size comes with an exponential decrease in signing speed" — smaller signatures cannot be obtained without an exponential signing-time cost within this framework. The robust tweakable-hash construction's proof of compact-public-parameter security depends on a quantum random oracle model (QROM) assumption; the paper characterizes this as "slightly stronger" than the assumptions needed for other constructions, and states this assumption is unneeded if one is willing to accept exponential-size public parameters instead. The "simple" instantiation drops that formal QROM guarantee for smaller code and higher speed, so choosing simple over robust is stated as an explicit security-versus-performance trade-off, not a strict improvement. Verification speed for SPHINCS+ is stated to be structurally slower than Gravity-SPHINCS because SPHINCS+ requires tweakable-hash calls at every node rather than plain hashing. LowMC v3, the symmetric primitive Picnic2's competitive performance relies on, is stated by the authors as "not [having] been intensively studied," with earlier LowMC versions shown by cited prior work not to meet their claimed security levels — the paper flags this as an open question about Picnic2's assumptions, not a property of SPHINCS+ itself.

### Requirements it places on the rest of the system
A verifier must have access to and trust the public parameters (a public seed, or a larger public-parameter structure depending on the robust/simple construction choice) associated with a given public key; the security reduction is stated relative to those parameters being generated as specified, not arbitrarily. The deterministic default signing mode requires the signer to hold a secret PRF key (SK.prf) and secret seed (SK.seed) with confidentiality equivalent to the signing key itself — compromise of either breaks the unforgeability argument the same way a stolen private key would for a conventional scheme; no additional live entropy source is required to sign, which the paper's own design of `R = PRF(SK.prf, OptRand, M)` establishes as a difference from a nonce-based scheme like ECDSA that fails catastrophically on repeated or predictable per-signature randomness. A system embedding SPHINCS+ must pick a maximum-signature bound in advance (as a parameter-search input) — the paper's own search script takes `maxsigs` as a configuration constant, and instantiations are tuned to a chosen ceiling (2^50 in one comparison, 2^64 for the NIST submissions); a deployment issuing signatures indefinitely without such a planned ceiling is outside what this paper's parameter derivations cover. A system choosing a hash function for the tweakable-hash instantiation must independently trust that hash function's security (SHA-256, SHAKE256, or Haraka) at the target security level; Haraka-based instantiations are stated to be unable to reach the highest security levels reachable with SHA-256 or SHAKE256, because of the generic meet-in-the-middle attack noted above — a system requiring the highest formally provable security level should not select Haraka. Systems requiring fast verification at scale (e.g., verifying many signatures per second) should weigh SPHINCS+'s tweakable-hash-per-node verification cost against alternatives; the paper's own Picnic2 comparison shows SPHINCS+ verification nearly 50 times faster in that specific comparison, but the Gravity-SPHINCS comparison shows the opposite ordering, so verification speed is stated to depend on which competing scheme and parameter set is being compared, not a fixed universal ranking.

### Contradicts
None found against other entries in this corpus — no other paper in this batch measures hash-based post-quantum signature performance. Note: the paper's own text corrects a claim commonly attributed to SPHINCS-256 (128-bit post-quantum security) — the paper states this figure ignored a tightness gap in the original proof and that a later attack reduced the actual figure to below 190 bits classical / 95 bits post-quantum; a reader citing "SPHINCS-256 achieves 128-bit post-quantum security" without this correction would be citing a claim this very paper says does not hold.
