## [FORD-USENIX-05] Peer-to-Peer Communication Across Network Address Translators
**Citation:** Bryan Ford, Pyda Srisuresh, Dan Kegel. "Peer-to-Peer Communication Across Network Address Translators." USENIX Annual Technical Conference, General Track, 2005.
**Retrieved:** full text via arXiv mirror
**Source URL:** https://www.brynosaurus.com/pub/net/p2pnat.pdf (arXiv:cs/0603074)
**Domain:** L

### What it does
The paper documents "hole punching," a technique that lets two clients each behind their own NAT (Network Address Translator) establish a direct peer-to-peer session, for both UDP and TCP, using a well-known rendezvous server only to introduce the two clients and never to carry their traffic afterward. Both clients first establish an active UDP or TCP session with a rendezvous server S. S records, for each client, the client's private endpoint (the (IP address, port) pair the client reports using itself, taken from a field in the registration message body) and its public endpoint (the (IP address, port) pair S observes the message arriving from, taken from the packet's own IP/UDP or IP/TCP headers). To connect, client A asks S for help reaching client B; S replies to A with B's public and private endpoints and simultaneously forwards A's public and private endpoints to B over S's existing session with B. Each client then sends packets — UDP datagrams, or for TCP, simultaneous outgoing connection attempts — to both of the other client's reported endpoints (public and private) and locks onto whichever endpoint elicits a valid response first. Sending the first outbound packet toward the peer's public endpoint is what "punches a hole" in the sender's own NAT: it creates a NAT session entry for that destination, so a return packet from the peer is no longer "unsolicited" from the NAT's point of view and is forwarded inward. For TCP, the API obstacle is that the Berkeley sockets API does not normally allow one local port to both listen for inbound connections and originate multiple outbound connection attempts; the paper's answer is to set `SO_REUSEADDR` (and, on BSD systems, `SO_REUSEPORT`) on every socket bound to that port, letting the same local TCP port back a listen socket and several concurrent outbound connect() attempts.

### Stated limitations
The authors state NAT Check's volunteer-submitted dataset is drawn from a "self-selecting" community and therefore does not constitute a random sample or necessarily represent the true distribution of NATs in common use. They state three specific testing-protocol limitations: NAT Check does not obfuscate the IP addresses it transmits in message payloads, so it cannot detect or protect against the small number of NATs known to blindly rewrite IP-address-shaped byte sequences found in application payloads; NAT Check's hairpin translation test may under-report support because it assumes a NAT that permits hairpin traffic does not separately filter that traffic as if it were arriving from the untrusted public side, an assumption the authors state they later realized may not hold for all NATs; and NAT Check cannot detect NATs that behave consistently for a single client behind them but degrade to symmetric-NAT behavior (or worse) once two or more clients on the same private network use the same local port concurrently, because reliably testing for that behavior requires running NAT Check on two client hosts simultaneously. The paper states multi-level NAT scenarios in general require hairpin translation for hole punching to fully succeed, and states hairpin translation support was rare among tested NATs (24% UDP, 13% TCP) even though the scenarios requiring it were also comparatively rare at the time of writing.

### Requirements it places on the rest of the system
Hole punching requires a rendezvous server reachable by both peers before the peers can establish a direct session, and that server's role ends once the hole is opened — it never carries session traffic, unlike the relay-server alternative the paper contrasts it with (see DUARTE-ABAKOS-20's measured throughput collapse for a relay path under bandwidth constraint). The mechanism requires the NAT to be a "cone" NAT — consistently mapping one private (IP, port) pair to the same public (IP, port) pair across sessions — and fails when the NAT is "symmetric," assigning a different public mapping per destination; the paper states 82% (UDP) and 64% (TCP) of the tested population met this requirement, so roughly one-fifth of UDP participants and over one-third of TCP participants in a design targeting that same population cannot be reached by unmodified hole punching. Because A's first message toward B's private endpoint may reach an unrelated host that happens to hold the same private IP address (NATs commonly assign private addresses from the same default DHCP pool), any application built on this mechanism must authenticate every inbound message — by an application-specific credential, a cryptographic token, or at minimum a nonce pre-arranged through the rendezvous server — to filter out such stray traffic, rather than trusting that a message arriving on the punched session is necessarily from the intended peer. Multi-level NAT topologies (a shared ISP-operated NAT layered with per-customer consumer NATs) additionally require hairpin translation support in the shared NAT layer, measured present in only 24% (UDP) / 13% (TCP) of tested devices, so a design that must support multi-level NAT cannot assume hairpin support is available and needs a fallback (such as the relay-server path) for that case.

### Contradicts
None found. DUARTE-ABAKOS-20 measures the same connection-reversal-plus-hole-punching mechanism this paper defines and reports comparably low overhead, not a disagreement.

RFC 3489, 2003. — defines the cone/symmetric NAT terminology this paper's Section 5.1 relies on, and the protocol used for NAT-behavior classification in corroborating studies.
- **Foundational** — Rosenberg. "Interactive Connectivity Establishment (ICE)." Internet-Draft, 2003 (later RFC 5245). — protocol built on hole punching for offer/answer session negotiation.
- **Competing** — Guha, Takeday, Francis. "NUTSS: A SIP-based approach to UDP and TCP network connectivity." SIGCOMM Workshops, 2004. — a more complex TCP hole-punching approach the paper states requires the rendezvous server to spoof source IP addresses and requires client raw-socket access, contrasted with this paper's own approach requiring neither.
- **Competing** — Biggadike, Ferullo, Wilson, Perrig. "NATBLASTER: Establishing TCP connections between hosts behind NATs." ACM SIGCOMM Asia Workshop, 2005. — the paper states this uses similar spoofing/raw-socket tricks to NUTSS to handle bad NAT behaviors this paper's own technique does not attempt to work around.
- **Competing** — Eppinger. "TCP connections for P2P apps: A software approach to solving the NAT problem." CMU-ISRI-05-104, 2005. — the paper states NatTrav implements an asymmetric TCP hole-punching procedure, contrasted with this paper's symmetric procedure (Section 4).
- **Foundational** — Holdrege, Srisuresh. "Protocol complications with the IP network address translator." RFC 3027, 2001. — the paper states this is where UDP hole punching was first mentioned, in section 5.1.
- **Attack or critique** — Duarte, Cardoso, de Mello, Borges. "Beware: NAT Traversal is a Simple and Efficient Approach to Open Firewall Holes." Abakós, 2020. — states the exploitable side effect of this paper's own mechanism: any internal host can use hole punching to open a firewall hole for an unauthorized service (already in this batch, DUARTE-ABAKOS-20).
- **Foundational** — Francis, Gummadi. "IPNL: A NAT-extended Internet architecture." SIGCOMM 2002. — one of several architectural alternatives the paper states would decouple host identity from location, contrasted with hole punching's no-upgrade-required property.
