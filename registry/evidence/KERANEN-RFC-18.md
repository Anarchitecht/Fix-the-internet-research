## [KERANEN-RFC-18] Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal
**Citation:** Ari Keränen, Christer Holmberg, Jonathan Rosenberg. "Interactive Connectivity Establishment (ICE): A Protocol for Network Address Translator (NAT) Traversal." IETF RFC 8445 (obsoletes RFC 5245), 2018. DOI 10.17487/RFC8445.
**Retrieved:** full text via https://www.rfc-editor.org/rfc/rfc8445
**Source URL:** https://www.rfc-editor.org/rfc/rfc8445
**Domain:** L

### What it does
This document specifies a procedure two network agents (endpoints, called L and R) use to discover which pair, among many possible pairs of network addresses, actually lets them exchange UDP (User Datagram Protocol) traffic directly or through a relay, without either agent knowing in advance what kind of Network Address Translator (NAT) or firewall sits in its path. Each agent first gathers candidates: a host candidate is a transport address (an IP address and UDP port) taken directly from a local network interface; a server-reflexive candidate is the address a Session Traversal Utilities for NAT (STUN) server observes as the public-side translation of that interface's address, learned by sending the STUN server a Binding request and reading the mapped address the server reports back; a relayed candidate is an address allocated on a Traversal Using Relays around NAT (TURN) server, obtained by sending that server an Allocate request, which returns both a relayed address and (in the same response) a server-reflexive address. A fourth type, a peer-reflexive candidate, is discovered only later, when a connectivity check itself arrives from a source address neither side had previously listed. Each agent exchanges its complete candidate list with the other agent over a signaling channel outside ICE's own scope (for example, Session Initiation Protocol (SIP) offer/answer exchange), forms every possible local-candidate/remote-candidate pair, assigns each pair a priority, sorts the pairs into a per-stream ordered list called a checklist, and works down the checklist sending a STUN request from the local candidate to the remote candidate of each pair (a connectivity check) — a pair whose check receives a valid STUN response becomes a valid pair, and one or more valid pairs are then nominated for the actual data exchange between the client acting as controlling agent and the other acting as controlled agent.

The candidate priority (Section 5.1.2.1) is computed as `priority = (2^24) * (type preference) + (2^8) * (local preference) + (2^0) * (256 - component ID)`, where type preference is an integer from 0 to 126 that must be identical for every candidate of the same type and different across types (the RFC's recommended values are 126 for host, 110 for peer-reflexive, 100 for server-reflexive, 0 for relayed), local preference is an integer from 0 to 65,535 distinguishing multiple candidates of the same type (set to 65,535 when only one interface address exists), and component ID is an integer from 1 to 256 identifying a sub-stream (for example, Real-time Transport Protocol (RTP) is component 1, Real-time Transport Control Protocol (RTCP) is component 2, when the two are not multiplexed onto one component). The candidate-pair priority (Section 6.1.2.3), used to sort the checklist, is `pair priority = 2^32 * MIN(G,D) + 2 * MAX(G,D) + (G>D ? 1 : 0)`, where G is the priority of the candidate offered by the controlling agent and D is the priority of the candidate offered by the controlled agent — this formula gives an identical pair priority to both agents regardless of which one computes it, because MIN and MAX do not depend on which side is which, up to the tie-breaking term that always favors the controlling agent's higher contribution.

### Measured results
This document is a normative protocol specification, not an experimental study; it reports no dataset, testbed, or trial with sample size, and every number in the sections below is a specified default or a formula parameter, not a measured outcome. The RFC does state two derived (not measured) bandwidth estimates as illustrative arithmetic:

| Figure | Basis | Condition |
|---|---|---|
| One STUN request/response pair for a basic voice call is a 20-byte request and a 28-byte response | Stated protocol-message sizes, not measured | Basic voice-only IPv4 VoIP deployment, one STUN transaction pair each for RTP and RTCP, for both caller and callee (4 transactions per call total) |
| A system of 1 million users, each making 4 calls in a busy hour, requires an aggregate STUN bandwidth of 1.7 Mbps | Arithmetic derivation from the per-transaction message sizes above, multiplied out per user and per call | Stated as "a very small number (relatively speaking)"; the RFC gives no measurement of an actual deployment's traffic |
| In a network with 100% BEHAVE-compliant NATs (per RFC 4787 and RFC 5382), TURN relay traffic volume for data relay is exactly zero | Stated as a logical consequence of the protocol's candidate-priority ordering, not a measurement | Idealized network condition; the RFC states real TURN traffic volume "is highly dependent on network topologies, and can and will vary over time" |
| Congestion from unpaced gathering and connectivity checks "has proven to be a problem in deployments that did not utilize pacing," with access links becoming congested as endpoints send checks as fast as possible | Stated as an observed deployment problem, cited without a specific deployment name, dataset, or numeric congestion figure | No further condition given; not attributable to a specific measured trial |

### Parameters
- Default candidate-pair checklist-set limit: 100 candidate pairs, configurable, imposed specifically to bound the STUN amplification attack described in Section 19.5.1.
- Recommended type-preference values: 126 (host), 110 (peer-reflexive), 100 (server-reflexive), 0 (relayed); each MUST be a distinct integer in 0-126 per type, identical within a type.
- Local preference range: 0-65,535; set to 65,535 when only one candidate of a type exists.
- Component ID range: 1-256 (component 1 = RTP or the only component, component 2 = RTCP when not multiplexed).
- Candidate priority: strictly a positive integer between 1 and 2^31 − 1, unique per candidate for a data stream.
- Ta (STUN/TURN transaction pacing interval): default 50 ms during gathering and connectivity checks; agents MAY negotiate a different value, and both agents MUST use the higher of the two proposed values; regardless of the per-agent Ta, all concurrent transactions from all agents on one implementation MUST NOT be sent more often than once every 5 ms in aggregate.
- RTO (STUN retransmission timeout) during gathering: `RTO = MAX(500 ms, Ta * Num-Of-Cands)`, where Num-Of-Cands is the count of server-reflexive and relay candidates being gathered.
- RTO during connectivity checks: `RTO = MAX(500 ms, Ta * N * (Num-Waiting + Num-In-Progress))`, where N is the total number of checks to perform and Num-Waiting/Num-In-Progress are checklist-set state counts that change per transaction; RTO MUST NOT be set below 500 ms regardless of formula.
- Keepalive interval Tr: SHOULD be 15 seconds; agents MAY use a larger value but MUST NOT use a value smaller than 15 seconds; keepalives are sent only on the pair(s) actually selected for data, only if no other traffic has crossed that pair within Tr seconds.
- STUN Voice Activity Detection (VAD) comfort-noise keepalive interval (illustrative, not normative): a packet every 15-20 seconds during silence, contrasted against a packet every 20-30 ms during active voice.

### Stated limitations
The RFC states ICE does not eliminate the need for STUN and TURN servers to be provisioned and reachable; it only reduces TURN's traffic volume toward zero as the fraction of BEHAVE-compliant NATs in the deployment approaches 100%, and states real-world TURN usage "is highly dependent on network topologies, and can and will vary over time." The RFC states ICE increases session-establishment time compared to a naive single-address attempt, as an explicit cost of the pacing that avoids network congestion: "The penalty of these improvements is that ICE increases session establishment times." The RFC's own security analysis (Section 19.1) states that probing for candidates and exchanging them "reveals the source addresses of the client and its peer to any on-network listening attacker" or to any attacker able to observe the negotiation channel, and that some revealed addresses (for example, a VPN user's local-interface server-reflexive address) may be sensitive; the RFC leaves mitigation of this exposure to the higher-layer ICE usage or to implementation-specific controls over which interfaces generate candidates, rather than solving it within ICE itself. The RFC states classic STUN's NAT-type discovery/classification process (as used before ICE) is "error prone," and ICE avoids that specific failure mode by testing connectivity directly rather than classifying NAT type — but this substitution is stated as ICE's own design choice, not as a claim that ICE eliminates every failure mode the RFC's own Security Considerations section documents (false-invalid, false-valid, false-peer-reflexive-candidate, and false-valid-on-false-candidate attacks are all analyzed as live threats mitigated, not eliminated, by STUN short-term credentials and secured candidate-exchange signaling). Section 19.1 also states that from the types of candidates a peer supplies and the timing characteristics of the resulting connectivity checks, the peer "might be able to determine characteristics of the local network" and "probe the local network," an information-exposure channel the RFC documents without providing a countermeasure for.

### Requirements it places on the rest of the system
ICE itself supplies no mechanism for exchanging candidates between the two agents; it depends on a separate signaling channel (the RFC names SIP offer/answer as the typical example) that both agents can already reach, and the RFC states explicitly that "ICE is not intended for NAT traversal for the signaling protocol, which is assumed to be provided via another mechanism." The RFC requires, not merely recommends, that all endpoints send periodic keepalives (STUN Binding Indications, at intervals no smaller than 15 seconds) on every candidate pair carrying data, because NAT/firewall UDP bindings are not permanent — a system embedding ICE must budget for this continuous background traffic for the lifetime of every active session, not only during setup. Server-reflexive and relayed candidate discovery depends on the availability of at least one reachable STUN server and, for relayed candidates and Allocate-request authentication, a TURN server holding a long-term credential the client already possesses; a deployment offering only STUN, with no TURN server available, cannot produce a relayed candidate and falls back to whatever host and server-reflexive candidates connectivity checks can validate. STUN Binding requests used for server-reflexive candidate discovery are unauthenticated by design (Section 19.3), so a system relying on ICE for its NAT traversal inherits an attack surface in which a compromised DNS resolution, an on-path observer on a shared network segment, or a compromised STUN server can inject a false server-reflexive candidate; the RFC's own mitigation for this is that peer-reflexive candidates (learned only from a successful connectivity check, and generally prioritized above server-reflexive candidates) still let the session succeed even if server-reflexive discovery is fully disrupted, provided at least one of the peer's own candidates was independently reachable.

### Contradicts
None found. This RFC's stated keepalive-interval default (15 seconds) and HALKES-NETWORKING-11's independently measured recommendation (send keepalives at least every 55 seconds, based on the shortest observed NAT mapping timeout in that paper's field trial) describe different quantities under different methods — this RFC's figure is a specified conservative protocol default chosen without a stated empirical derivation, while HALKES-NETWORKING-11's figure is a measured upper bound on interval safety drawn from real NAT/firewall timeout behavior in the field — and a synthesis step selecting a keepalive interval should cite HALKES-NETWORKING-11's measured figure over this RFC's unmeasured default when the two are compared, because only the former traces to an experimental measurement.
