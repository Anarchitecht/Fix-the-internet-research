## [HERRMANN-P2P-14] Censorship-Resistant and Privacy-Preserving Distributed Web Search
**Citation:** Michael Herrmann, Ren Zhang, Kai-Chun Ning, Claudia Diaz, Bart Preneel. "Censorship-Resistant and Privacy-Preserving Distributed Web Search." IEEE P2P, 2014. DOI 10.1109/P2P.2014.6934312.
**Retrieved:** full text via https://cosicdatabase.esat.kuleuven.be/backend/publications/files/conferencepaper/2422
**Source URL:** https://cosicdatabase.esat.kuleuven.be/backend/publications/files/conferencepaper/2422
**Domain:** B

### What it does
The paper analyzes the three real-world distributed web search engines (DWSE) the authors identify as actually deployed — Faroo, Seeks, and YaCy — for resistance to censorship of search results and for protection of a searcher's identity, demonstrates working attacks against one of them (YaCy) on a live network, then proposes two new defense protocols (node density and webpage verification) and evaluates them by simulation.

Faroo runs a modified Kademlia distributed hash table (DHT); each crawled webpage generates reverse-word-index (RWI) entries of the form search-term to URL, each entry stored on the 20 nodes whose Kademlia IDs are closest to the hash of the search term, and a query is answered by the nodes closest to that hash, returning only the top 100 results. Node IDs are self-chosen (derived from the querying client's MAC address and other local information), which the paper identifies as the property an eclipse attack (placing malicious nodes to surround and intercept traffic to a target ID) exploits: an attacker computes the target ID of a keyword, generates 20 node IDs closer to it than any honest node, and deploys nodes with those IDs to become the sole index holders for that keyword.

Seeks runs on a Chord DHT but maps a query to other users who issued similar queries (via a locality-sensitive hash placing similar queries at the same index nodes), not to RWI entries, and re-ranks results already returned by centralized search engines rather than maintaining its own web index; the paper states this design already forgoes searcher anonymity by construction, since finding who is interested in a query only requires issuing that query.

YaCy addresses its full 63-bit ID space as a ring resembling Chord; every peer maintains a near-complete view of every other peer via principal (super-)peers that aggregate peer information and a periodic peer-ping gossip protocol. An RWI entry's address is 4 bits from the URL's hash and 59 bits from the word's hash, stored at the 3 closest successor peers; because all words on one URL share the same top 4 bits, all entries for one page fall in one "vertical partition" of the address ring. A single-term search builds a candidate set from the 2 closest successors of each of the 16 possible vertical positions for that term, plus (with 80% probability each) the 5 self-reported highest-RWI-count peers; the paper identifies that every value entering this candidate-set computation (RWI count, "root-mode" gossip-freshness flag, last-seen timestamp) is self-reported by the peer being described, with no verification by any other peer.

The paper's two proposed defenses: (1) the node density protocol flags a lookup target as likely eclipsed when the span (distance) covered by the r closest successor nodes to that target falls below a threshold p_n times the network-wide average span s, on the reasoning that an attacker inserting malicious nodes to surround a target compresses that span; it depends on a separately cited node-ID generation scheme (Zhang et al., reference [11]) to prevent an attacker from freely choosing IDs. (2) The webpage verification protocol distributes verification "tickets" for stored entries to random other peers, who periodically re-query the network for that entry and can detect a peer that is silently dropping or filtering it, using an anonymous lookup mechanism (Octopus) so the verifying peer's own identity and target are not exposed to the peer under test.

### Parameters
- Threat model: an internal, active, static (per Raymond's taxonomy) attacker controlling a set of colluding nodes with a modified client; the network is established by honest users and the attacker does not control bootstrap machines; a global (network-wide passive observer) attacker is explicitly excluded from scope.
- Node density protocol: r = 8 (successor nodes an attacker must control to censor a target — described by the authors as deliberately low, favoring the attacker, relative to Faroo's real value of 20); p_n swept over {0.4, 0.45, 0.5, 0.55, 0.6}; Sybil-fraction f swept over {20%, 30%, 40%, 50%}.
- Webpage verification protocol: p_q (per-minute query probability) = 7%; p_v (per-minute verification-request probability) swept over {1e-6, 1e-4, 1e-3}; 20 topics, Zipf exponent 0.5, 1,000 entries per node, 2 tickets per entry, one-month simulated run.
- YaCy live test network: 149 PlanetLab nodes plus 1 lab-controlled principal/bootstrap peer; unmodified YaCy client software on all honest peers.

### Stated limitations
The two proposed protocols provide only heuristic, not formally verified, guarantees; the authors state that formally verifying whether a DWSE satisfies censorship resistance and privacy protection is left to future work. The authors state explicitly that their countermeasures do not make a censorship attack impossible — they only raise its cost, so that an attacker with modest resources cannot inflict significant harm, while a sufficiently resourced attacker remains a known-hard, unsolved problem in peer-to-peer (P2P) systems generally. The threat model excludes a global (network-wide) passive adversary by construction. The Solr-search route-capture attack against YaCy could not fully control the random-Robinson-peer subset of the candidate set: an honest peer that already knows another peer stores RWI entries cannot be deceived into believing that peer is a Robinson peer, so this vector was identified as harder for the attacker than the root-mode and RWI-count vectors, though the authors state the attack can still partly succeed by spreading false Robinson-peer claims or via denial-of-service against Robinson peers. The node density protocol's underlying node-ID generation scheme is not evaluated in this paper; the authors explicitly defer to a separately cited paper [11] for that evaluation. No live-network experiment tests the two proposed defenses; both are evaluated only by simulation.

### Requirements it places on the rest of the system
- The node density protocol requires an ID-generation scheme (cited separately, not built here) that prevents an attacker from freely choosing arbitrary node IDs; without it, an attacker can still place IDs precisely enough to defeat the density check, as demonstrated for YaCy and Faroo's current unrestricted self-chosen IDs.
- The node density protocol requires a network-wide consistent value for the reference span s that all honest nodes agree on; the paper states this needs a trusted certification authority (CA) known to all peers if a single fixed value is to be used network-wide, introducing a trust dependency the base DHT design does not otherwise have.
- The webpage verification protocol requires an underlying anonymous-lookup primitive (the paper specifies ShadowWalker or Octopus) so that a verifying peer's identity and target are not exposed to the peer being checked; without query anonymity, the peer under test could distinguish verification traffic from ordinary search traffic and pass every check while still censoring real users.
- The webpage verification protocol requires a routing-table update mechanism that removes a peer once flagged as malicious from every honest peer's local view; the paper assumes this removal is possible and effective but does not itself specify or evaluate that removal mechanism's own robustness against a peer rejoining under a new identity.
- Achieving searcher anonymity and query unlinkability (the two privacy properties the paper specifies) requires layering a separate anonymous-communication protocol (onion-routed paths via ShadowWalker or Octopus) beneath the DWSE; the DWSE mechanisms proposed here (node density, webpage verification) address only censorship resistance, not privacy, on their own.
- Recommendations are stated as built for a structured (DHT) overlay specifically, using Chord as the underlying routing substrate; the authors state this choice is made for scalability over unstructured networks and to avoid routing private information through a central server, so the proposed defenses are not stated to transfer to an unstructured overlay without further work.

### Contradicts
None found against other entries in this corpus. Within its own related-work discussion, the paper states that a separately cited evaluation methodology for obfuscation-based private web search (OB-PWS, e.g. TrackMeNot-style dummy-query techniques) overestimates the privacy protection it provides, because that evaluation does not model a strategic adversary aware of the obfuscation mechanism — this is the authors' own attributed characterization of a different paper's [10] finding, not an independent measurement made in this paper.
