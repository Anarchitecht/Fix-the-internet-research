## [DZIEMBOWSKI-CRYPTO-15] Proofs of Space
**Citation:** Stefan Dziembowski, Sebastian Faust, Vladimir Kolmogorov, Krzysztof Pietrzak. "Proofs of Space." CRYPTO, 2015. DOI 10.1007/978-3-662-48000-7_29.
**Retrieved:** full text via https://eprint.iacr.org/2013/796.pdf
**Source URL:** https://eprint.iacr.org/2013/796.pdf
**Domain:** C

### What it does
A proof of space (PoS) lets a party (the prover) convince a second party (the verifier) that the prover is persistently dedicating a specified amount of disk storage, without the verifier ever transferring or storing that amount of data itself. The protocol has two phases. In the initialization phase, the verifier sends the description of a hash function to the prover; the prover uses it to label every node of a directed acyclic graph chosen for having high "pebbling complexity" (defined below), where each node's label is the hash of its children's labels, builds a Merkle hash-tree over all labels, and sends only the tree's root hash (a single L-bit value) to the verifier. In the execution phase, run any number of times later, the verifier picks a small set of random node positions and asks the prover to open the corresponding labels; the prover answers by revealing the label and its Merkle-tree authentication path, and the verifier checks the path against the previously stored root. The prover can only answer efficiently if it stored the full labeling; a prover that discarded most of the labeling must either keep a large residual fraction of them or recompute from scratch at high time cost at every execution.

The security argument reduces cheating-prover storage to a graph-pebbling game: placing a "pebble" on a graph node models an algorithm holding that node's label in memory, and a pebble can be placed on a node only once its parent nodes are pebbled. A graph family has pebbling complexity Ω(f,g) if any successful pebbling strategy that starts with fewer than f initial pebbles held between rounds must, during a further pebbling execution, use at least g simultaneous pebbles or make at least g total pebbling moves. The paper constructs two explicit graph families achieving different pebbling-complexity guarantees (Theorems 1 and 2) and uses each to instantiate the protocol above, giving two proof-of-space constructions with different storage/time tradeoffs for a cheating prover, formalized in Section 3.2's (N0, N1, T)-security model: a cheating prover is defeated unless it either retains N0 bits of storage between the initialization and execution phases, or retains up to N1 bits and spends T oracle queries during a single execution.

γ is the statistical security parameter (number of random challenge positions the verifier checks). N is the storage size in L-bit blocks the honest prover dedicates. Prover computation during execution is stated as 0 (constant, independent of N) in both constructions, once the labeling is stored. The initialization time for the prover, I, is proved Θ(N) for the first construction and O(N log log N) for the second; the paper states I must be at least linear in N for any such protocol, so the first construction meets that lower bound exactly.

The graph construction of Theorem 1 draws on the Paul-Tarjan-Celoni (1976/77) graph family with mᵢ = 2ⁱ sources/sinks and nᵢ = Θ(i·2ⁱ) nodes; for a target size N, the largest such graph with nᵢ ≤ N gives mᵢ = Θ(N/log N), the source of the N/log N storage bound. The graph of Theorem 2 combines random bipartite expander graphs, superconcentrators, and dense-long-path graphs of Erdős, Graham and Szemerédi (1975), constructed by a randomized algorithm with polynomial expected running time that succeeds with probability at least 1 − 2^(−Θ(N/log N)).

### Parameters
- N: storage size dedicated by the honest prover, in L-bit blocks
- L: random-oracle output length, stated as needing to be set large enough that finding a collision (roughly 2^(L/2) oracle queries) is infeasible; the paper gives L = 512 with a bound of 2^(L/3) total oracle queries across the experiment as "a conservative choice" — the paper's own words, not this extraction's judgment
- γ: statistical security parameter, controls the number of random challenge positions Θ(γ) checked in each execution
- d: maximum in-degree of the pebbling graph — 2 for the Theorem 1 construction, O(log log N) for the Theorem 2 construction
- (N0, N1, T): the security model's three adversary bounds — storage retained between phases, storage retained during a single execution (N1 ≥ N0), and oracle-query budget during execution
- ε: a tunable slack parameter trading verifier efficiency against the tightness of the storage bound (set to c1/(2 log N) for the first construction, c4/2 for the second)
- τ: a threshold constant (0 < τ < 1) below which the second construction's Ω(0, [S0 < τN]·max{N, N²/S1}) pebbling-complexity bound applies

### Stated limitations
The security proof does not reduce to the plain random-oracle model; it needs an added assumption (Section 3.1) that the set of hash outputs a bounded-storage cheating prover can write down without re-querying is well-defined at every time point, because the standard "ex post facto" argument used for related pebbling-based proofs cannot be applied when the adversary is allowed unbounded queries during initialization. The authors state this additional assumption is "a bit unsatisfactory" and identify removing it, using techniques for proving random oracles incompressible, as future work. The paper explicitly notes it does not claim its storage-tracking set SH exists for every possible cheating prover strategy, only that an equivalent prover obeying the assumption exists with almost the same parameters and advantage. A simpler PoS built by storing sorted outputs of a random function is noted to achieve only weak security because of time-memory tradeoffs for inverting random functions or permutations (inversion in √N time and space for permutations, N^(2/3) for general functions), which is why the paper does not use that simpler construction. A related primitive, proof of storage / proof of retrievability, is stated as not qualifying as a PoS because the verifier there must send at least |F| bits to the prover during setup, violating the polylogarithmic-communication goal.

### Requirements it places on the rest of the system
The construction requires a cryptographic hash function modeled as a random oracle, with output length L chosen large enough that no party (including any adversary) can find collisions within the total query budget of the deployment; in practice this needs instantiation with a concrete hash function such as SHA3, which the paper notes carries only heuristic (not reduction-based) security. The verifier must be able to sample and remember one Merkle-tree root hash per prover per commitment period, and must issue random challenge queries during each execution phase — the protocol supplies no mechanism for choosing when to challenge, only that repeated challenges over time make the proof "persistent." The scheme assumes the prover has random access to its stored labeling during execution; if the prover cannot hold the full N-block labeling, it must either retain a large residual fraction (Θ(N) or Θ(N/log N), depending on construction) or recompute at Θ(N) or higher time cost per execution — the system built on top of this primitive must decide what storage threshold and time budget count as a passing prover, since the theorem gives asymptotic bounds with unspecified constants, not concrete disk-size or millisecond figures. The paper's Spacecoin application (cited, not itself part of this paper) uses this PoS to gate mining: a miner runs initialization once for N bits of space, then answers per-round execution challenges cheaply — that composition requires whatever consensus layer sits above the PoS to bind one completed initialization (one committed Merkle root) to one accepted unit of space per identity, a binding this paper does not itself provide or analyze.

### Contradicts
None found within this batch. The paper's own related-work discussion states that its "collapsed" single-phase variant (running initialization and execution together) is essentially the same construction independently proposed as a Proof of Secure Erasure by Karvelas and Kiayias (SCN 2014) and by Ateniese et al. (SCN 2014); those two papers give a security proof directly in the random oracle model without this paper's added assumption, because a Proof-of-Secure-Erasure security argument does not need the "ex post facto" strengthening this paper's persistent PoS argument requires.
