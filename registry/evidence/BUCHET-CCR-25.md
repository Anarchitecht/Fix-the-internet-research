## [BUCHET-CCR-25] An Analysis of QUIC Connection Migration in the Wild
**Citation:** Aurélien Buchet, Cristel Pelsser. "An Analysis of QUIC Connection Migration in the Wild." ACM SIGCOMM Computer Communication Review, 2025. DOI 10.1145/3727063.3727066.
**Retrieved:** full text via https://arxiv.org/abs/2410.06066
**Source URL:** https://arxiv.org/abs/2410.06066
**Domain:** L

### What it does
QUIC's connection-migration mechanism lets a client switch the IP address and/or port it uses for an already-established connection without a new handshake, so an in-progress transfer or session survives a network change (Wi-Fi to cellular, address rebinding behind a NAT, or a deliberate switch for tracking resistance). QUIC identifies a connection by Connection Identifiers (CIDs) carried in the packet header rather than by the IP/port 4-tuple TCP uses, so a packet arriving from a new address can still be matched to an existing connection as long as the CID is recognized. To migrate, an endpoint first announces spare CIDs to its peer via encrypted `NEW_CONNECTION_ID` frames sent at any point during the connection; once both sides hold at least one CID not previously used in cleartext headers, the client can send a `PATH_CHALLENGE` frame from the new address, and the server must echo it back in a `PATH_RESPONSE` to validate the new path before migration completes. Using a fresh CID on both sides (not just a new address) prevents an eavesdropper from linking the pre- and post-migration traffic by matching the CID visible in the cleartext packet header.

This paper does not modify QUIC; it measures how many real-world QUIC-speaking servers actually implement and permit this migration handshake, as opposed to how many merely speak QUIC. Method: (1) discover QUIC-capable IP targets via ZMap-based UDP scans of the full IPv4 address space on port 443, plus IPv6 targets seeded from a published responsive-address Hit-list and from DNS resolution of over 125 million domain names (Centralized Zone Data Service com/net/org zones plus the Tranco top-sites list); a reserved QUIC version-negotiation number is used to elicit a response that confirms QUIC support without completing a full handshake. (2) Map discovered IP addresses to domain names via forward DNS (A/AAAA records via MassDNS through a local Unbound resolver), to supply Server Name Indication (SNI) for TLS Client Hellos, since many hosts (especially behind CDNs) will not complete a handshake without SNI identifying the requested domain. (3) A custom stateful scanner (approximately 1,200 lines of Rust, built on Cloudflare's Quiche QUIC library, since the alternative quic-go library used by a prior study's scanner did not support migration at the time of writing) attempts a full QUIC handshake with HTTP/3 ALPN negotiation against each target, and where the server offers at least one spare CID, triggers a migration (new source port, same interface) and confirms success only on receipt of a valid `PATH_RESPONSE`; on success it also issues an HTTP request to capture the server's HTTP header. (4) Post-processing maps successful targets' IPs to Autonomous Systems (ASes, internet routing domains) via RouteViews BGP route data and to owning organizations via the CAIDA AS-to-Organization dataset.

### Measured results
Scans conducted in May 2024, run in parallel from two vantage points (VP1: cloud provider, western Europe; VP2: data center, North America); the paper reports only VP1 in the main text because the two vantage points' results did not differ meaningfully. Datasets: IPv6 Hit-list (4 May 2024), CZDS com/net/org zones (10 April 2024), Tranco list (25 April 2024), RouteViews BGP RIBs (17 May 2024), CAIDA AS-to-Organization mapping (1 May 2024).

### Parameters
- Scan month: May 2024. Two vantage points: VP1 (cloud provider, western Europe, reported in main text), VP2 (data center, North America, results in appendix, described as "very similar" to VP1).
- IPv4 target discovery: full /0 address space, ZMap, UDP port 443.
- IPv6 target discovery: seeded from a published responsive-address Hit-list (4 May 2024) plus AAAA records resolved from the domain-name corpus; not exhaustive (IPv6 address space is not fully scannable).
- Domain corpus: over 125 million domain names from CZDS (com/net/org zones, 10 April 2024) and the Tranco top-sites list (25 April 2024); DNS resolution via MassDNS through a local Unbound server yielded 3M distinct IPv6 addresses and 6.2M distinct IPv4 addresses.
- Migration scanner: custom, approximately 1.2k lines of Rust, built on Cloudflare Quiche (quic-go was rejected because it lacked migration support at the time); tested against a controlled Cloudflare Quiche server under multiple configurations and against a handful of independently-verified Google/Cloudflare production servers before the wide scan.
- Migration performed: same network interface, different source port only (the paper states investigating true multi-interface or server-preferred-address migration is left as future work).
- Rate limiting applied to all scans per Internet-measurement best-practice guidance (Menlo Report); an opt-out prefix exclusion list was maintained from requests received via a published contact page hosted at both vantage points.
- Handshake success criterion: reception of a complete, valid TLS 1.3 Server Hello. Migration success criterion: reception of a valid `PATH_RESPONSE` frame after sending `PATH_CHALLENGE` from the new source port.

### Stated limitations
The authors state the scanner does not record server-advertised transport parameters that could explain non-migration, such as `disable_active_migration` or `preferred_address`, so the paper cannot attribute specific non-support cases to a specific declared server policy versus a network-path failure (load balancer misrouting, firewall blocking of the non-handshake `PATH_CHALLENGE` packet, or simple lack of implementation support) — the authors list all of these as plausible causes but state their current scanner cannot distinguish among them. The authors state the scanner was validated against a controlled Quiche deployment and a small number of independently-verified Google/Cloudflare servers, not against the full range of known QUIC implementations, so some migration-capable implementations using behavior the scanner does not anticipate may have been missed; they note the QUIC Interop Runner could broaden this coverage but did not, at the time of writing, fully support migration testing. The authors state the study measures migration on the same network interface with only a source-port change, not true multi-interface migration or migration to a server-preferred address, and list both as future work. The authors state the IPv4-with-SNI and CZDS/Tranco-derived target sets are biased toward popular websites and cloud providers, and separately cite prior work (Steger et al.) finding the IPv6 Hit-list itself biased toward ISP networks — both dataset-selection biases the authors flag as affecting who is represented in the with-SNI results, not measurement noise. The authors state successful handshakes obtained without SNI likely represent either misconfigured servers or servers not associated with any domain name, since HTTP/3 formally requires SNI when a server is identified by domain name.

### Requirements it places on the rest of the system
A NAT-traversal or reachability design that depends on QUIC connection migration to survive an address change needs to account for measured migration support being far from universal even among servers that speak QUIC and pass a full TLS handshake: with SNI supplied (the condition closest to a normal client connecting to a named service), migration succeeded for 52% of IPv4 targets and 78% of IPv6 targets that had already completed a handshake — meaning roughly half of IPv4 QUIC servers and a fifth of IPv6 QUIC servers that a client can talk to at all will not support a mid-connection address change, so any design relying on migration for continuity needs a fallback path (new connection/new handshake) for the non-supporting majority or near-majority. A design specifically counting on migration for privacy against network-path observers (unlinking pre- and post-migration traffic) needs the presence of a spare, not-yet-used CID on both ends before migrating, which this paper's own mechanism description states is required to prevent an eavesdropper from linking the two paths by the visible CID — a precondition the scanner enforces operationally by requiring the server to have offered at least one additional CID before attempting migration. The measured concentration of IPv6 migration support in a single organization (94% of IPv6-with-SNI migration-successful targets belong to one hosting provider, Hostinger) means a decentralized reachability design cannot treat "IPv6 QUIC migration is broadly available" as a property of the IPv6 QUIC ecosystem generally; it is presently a property of a small number of large hosting operators' default configurations, not a general server behavior. A design needs a mechanism to detect migration support per-server at connection time (offer a CID and observe whether the server accepts a subsequent PATH_CHALLENGE) rather than assuming it, since this paper found no reliable way, short of an actual attempt, to predict from other server-visible information (organization, HTTP header) whether a given target supports migration, beyond the coarse observation that some providers (Cloudflare, Hostinger) are internally consistent (all-or-none) while others (AWS, OVH) are not.

- foundational: Kosek, M., Doan, T. V., Granderath, M., Bajpai, V., "One To Rule Them All? A First Look at DNS over QUIC," PAM 2022 (cited as reference [10]) — methodological precedent for QUIC scanning technique this paper's target-discovery approach is based on.
