## [XU-ARXIV-25] Distributed Retrieval-Augmented Generation
**Citation:** Chenhao Xu, Longxiang Gao, Yuan Miao, Xi Zheng. "Distributed Retrieval-Augmented Generation." arXiv:2505.00443, 2025.
**Retrieved:** full text via https://arxiv.org/abs/2505.00443
**Source URL:** https://arxiv.org/abs/2505.00443
**Domain:** B

### What it does
Distributed Retrieval-Augmented Generation (DRAG) answers a user query by combining a large language model (LLM, a machine-learned text-generation model) running locally on a device with knowledge fetched from other devices over a peer-to-peer network, instead of drawing on one centralized knowledge base. Each device (peer) holds a local knowledge base, a local LLM, and a communication module. On a query, the querying peer's local LLM first checks whether its own knowledge base answers the query, by comparing semantic similarity between the query and local content against a threshold (or by using explicit or implicit user dissatisfaction signals). If local knowledge is insufficient, the peer starts a network search using the paper's routing algorithm, Topic-Aware Random Walk (TARW). Once a peer along the search path returns a relevant knowledge snippet, that peer applies a privacy filter (rule-based or LLM-driven) before releasing the snippet, so raw local data does not leave the source peer. The querying peer's local LLM combines the returned snippet(s) with its own local context to generate the final answer, and caches the result locally, along with which peers held which topics, to speed and reduce the cost of future queries on similar topics.

TARW is a random walk over the peer graph, modified to prefer neighbors that past experience suggests hold relevant knowledge. Given a query, the querying peer's LLM first extracts a set of topics from the query text. The walk keeps a visited-peer set and a queue of (peer, hop-count) pairs, starting from the querying peer at hop 0, and a cache of peer expertise built up as the walk (and past walks) proceed. At each step the algorithm dequeues one (peer, hop-count) pair; if the hop count has reached the maximum `H_max` it drops that branch. Otherwise it queries the dequeued peer's local knowledge base and computes a relevance score between the returned knowledge and the original query. If that score meets or exceeds a threshold `θ`, the walk stops, the peer's identity and the query's topics are added to the expertise cache, and the returned knowledge is passed through the privacy filter and returned as the result. Otherwise the algorithm looks at the dequeued peer's not-yet-visited neighbors, scores each neighbor using the cached expertise history against the query's topics, and enqueues only the top `k` scoring neighbors (rather than all neighbors, as an unweighted random walk or query broadcast would) at hop-count+1. If the queue empties before any peer meets the relevance threshold within `H_max` hops, the walk returns no result.

### Measured results

Network simulated with the NetworkX Python library using the Barabási-Albert preferential-attachment topology model to approximate Internet- or social-media-like connectivity. Three question-answering datasets: MMLU (a multiple-choice general-knowledge benchmark), Medical Extended (a synthetic dataset of generated patient questions and doctor answers), and News (approximately 210,000 HuffPost news headlines, 2012-2022, task is identifying the article's author from its headline). Default LLM Llama 3.2-3B (3-billion-parameter model), with Gemma 2 2B and Qwen2.5 3B also tested. Default network: 20 peers, connectivity 4 (Barabási-Albert attachment edges per new node), `H_max`=6, neighbor-selection count `k`=4, relevance threshold `θ`=0.8. All figures below are averages; the paper does not state the number of independent simulation runs per data point.

### Parameters
- `H_max` (maximum walk hops): fixed at 6 for all reported experiments; not swept.
- `k` (neighbor selection count, top-k neighbors forwarded to per hop): default 4; swept over 2, 4, 6, 8.
- `θ` (relevance threshold to accept a peer's local answer): fixed at 0.8 for all reported experiments; not swept.
- Network size (number of peers): default 20; swept over 20, 40, 60, 80, 100.
- Network connectivity (Barabási-Albert attachment edges per new peer): default 4; swept over 2, 4, 6, 8.
- LLM: default Llama 3.2-3B; Gemma 2 2B and Qwen2.5 3B also evaluated.

### Stated limitations
The paper states DRAG-TARW trades a small amount of accuracy for lower message count relative to query broadcast (DRAG-FL): "there is a slight trade-off in accuracy, with DRAG-FL generally exhibiting marginally higher EM, F1, Precision, and Recall scores." The paper states TARW itself is vulnerable to deanonymization if an adversary observes network traffic and infers query topics and peer expertise from the routing pattern, and lists candidate but unevaluated defenses: adding noise to topic extraction, mix networks to obscure routing paths, and access-control restrictions on peer visibility. The paper states knowledge-quality control is unresolved: because peer knowledge bases vary in expertise and data quality, the system can propagate misinformation or stale knowledge, and the paper only proposes unimplemented mitigations (peer rating of snippet quality, consensus mechanisms for conflicting snippets, reputation tracking of peer history) rather than evaluating any of them. The paper states peer connectivity does not reliably improve either accuracy or message cost in its simulations, attributing this to "the inherent randomness in knowledge distribution across the peer-to-peer network" interacting unpredictably with topology. The paper states, as future work, that the knowledge-search algorithm needs further optimization for very large and dynamic networks, without giving results at scales beyond 100 peers. The paper never evaluates incentive mechanisms for peer participation; it only lists token-based, reputation-based, and knowledge-marketplace approaches as unimplemented candidates.

### Requirements it places on the rest of the system
Requires each peer to run a local LLM capable of two functions used inside the routing algorithm itself: extracting topics from the query text, and scoring semantic relevance between a returned knowledge snippet and the query, against threshold θ. The routing decision at every hop therefore depends on local LLM inference quality — the LLM-substitution results above show F1 varying by more than 6 percentage points (77.13% to 83.92% on MMLU) purely from swapping the local LLM, with no change to TARW itself. Requires every peer to maintain a persistent local expertise cache, keyed by topic, of past-successful peer contacts, because TARW's per-hop neighbor scoring reads this cache (`RelevanceScore(N_i, E, T)` in the paper's Algorithm 1); the message-cost convergence result (34.73 to 27.67 messages over 10,000 queries) is a direct consequence of this cache accumulating entries, so a deployment that resets or does not build this cache will not obtain that convergence. Requires a privacy filter (rule-based or LLM-driven) that can be applied to a knowledge snippet before it leaves the holding peer; the paper does not specify or evaluate this filter's false-negative rate — how often it fails to remove sensitive content. Requires an underlying peer graph with fixed, discoverable neighbor sets per peer (the paper's simulations use a static Barabási-Albert graph generated once per experiment); the paper does not evaluate TARW under peer churn (peers joining or leaving during a walk). Assumes queried peers answer truthfully about their own local knowledge-base content and relevance scores; the paper's threat model addresses only traffic-observation deanonymization, not a peer that misreports relevance to attract or divert queries.
