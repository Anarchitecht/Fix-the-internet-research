## [FREIRE-PKC-13] Non-Interactive Key Exchange
**Citation:** Eduarda S.V. Freire, Dennis Hofheinz, Eike Kiltz, Kenneth G. Paterson. "Non-Interactive Key Exchange." Public Key Cryptography (PKC), 2013. DOI: 10.1007/978-3-642-36362-7_17.
**Retrieved:** full text via https://eprint.iacr.org/2012/732.pdf (full version of the PKC 2013 paper)
**Source URL:** https://eprint.iacr.org/2012/732.pdf
**Domain:** H

### What it does
Non-Interactive Key Exchange (NIKE) lets two parties, each holding only the other's public key, compute a shared symmetric key with no protocol messages exchanged between them at the time of computation. The canonical instance, from Diffie and Hellman's original paper: Alice holds public key g^x and private key x, Bob holds public key g^y and private key y, in a group G of prime order p with generator g; each computes g^(xy) independently and hashes it together with both parties' identities to derive the shared key. This paper's contribution is not a new NIKE scheme in isolation but a systematic security-definition and construction-relationship study built on the earlier Cash-Kiltz-Shoup (CKS) formal model for NIKE.

The paper defines a NIKE scheme as three algorithms plus an identity space and a shared-key space: CommonSetup (produces system parameters), NIKE.KeyGen (produces one identity's public/secret key pair from those parameters), and SharedKey (takes one party's own identity and secret key plus a second party's identity and public key, and outputs the shared key or a failure symbol). It defines four security models differing only in which oracle queries an adversary may make against a challenger: CKS-light (the simplest — exactly two honest users, no corruption, a single test query), CKS (the original Cash-Kiltz-Shoup model — arbitrary honest and corrupt user registration and reveal queries, but no extract queries against honest users' secret keys and no honest-reveal queries), CKS-heavy (adds extract and honest-reveal queries, but only a single test query), and m-CKS-heavy (the paper's preferred model — the same expanded query set as CKS-heavy but with unlimited test queries). All four models operate in what the paper calls the dishonest key registration (plain/bare PKI) setting: an adversary may register any public key of its own choosing under any identity, and the model does not assume the Certificate Authority checks that a submitted public key is new or that the registrant knows the corresponding private key. The paper proves (Theorem 1) that all four models are polynomially equivalent to one another, with explicit reduction-loss factors given for each direction of implication, meaning a scheme's security proved in the simplest model (CKS-light) automatically implies security in the strongest model (m-CKS-heavy), at a stated multiplicative security loss.

The paper gives two concrete NIKE constructions meeting the CKS-light definition (and hence, by the equivalence theorem, the m-CKS-heavy definition): a Random-Oracle-Model scheme (NIKE_fac) proved secure under the factoring assumption, built in the group of signed quadratic residues; and a standard-model scheme (NIKE_dbdh-2) proved secure under a variant of the Decisional Bilinear Diffie-Hellman assumption for asymmetric pairings, combining a weak Programmable Hash Function with a chameleon hash function so the security proof's simulator can handle shared-key queries between one honestly generated and one adversarially chosen public key. The paper also gives a generic transformation converting any CKS-light-secure NIKE scheme, combined with a strongly one-time-secure signature scheme, into a Key Encapsulation Mechanism (KEM) proved secure against Indistinguishable-under-Chosen-Ciphertext-Attack (IND-CCA): the KEM's public/secret key pair is a NIKE key pair, a ciphertext is a freshly generated NIKE public key from the sender together with a one-time signature binding it to the intended recipient's identity, and the encapsulated key is the NIKE shared key the two public keys jointly determine.

### Measured results
None — this is a formal cryptography paper. Its quantitative content is derived security-reduction bounds and construction-efficiency figures stated directly by the authors from their own constructions, not measured by experiment, benchmark, or implementation. Two derived (not measured) figures the paper states explicitly:
- Model-equivalence reduction loss (Theorem 1, derived): going from the m-CKS-heavy model down to the simplest CKS-light model loses a multiplicative factor of q_T · q_H² in the security reduction, where q_T is the number of test queries and q_H the number of register-honest-user queries an adversary makes; the paper attributes this loss to the hybrid-argument proof technique used to establish the bound and states it as an open problem whether a tighter relation between the models can be proved, or proved impossible.
- Concrete key size (stated by the authors as a computed example, not a benchmark): at the 128-bit security level, using Barreto-Naehrig (BN) pairing-friendly curves with point compression, the standard-model pairing-based NIKE scheme's public keys consist of 768 bits plus one element from the chameleon-hash range space; the derived KEM built from this NIKE scheme has public keys consisting of an identity string, two group elements (one in each of the pairing's two source groups G1 and G2), and one chameleon-hash key, with ciphertexts additionally carrying a one-time-signature verification key and signature. The paper states this KEM's decapsulation cost is two bilinear-pairing evaluations (one to check public-key validity, one to compute the shared value) and describes the resulting KEM as comparable in performance to the Boyen-Mei-Waters (2005) direct-chosen-ciphertext-security scheme, without giving a numeric benchmark for either.

### Parameters
Not applicable as a tested range — the paper reports proved security bounds and one illustrative parameter choice, not a swept experimental study. The one concrete parameter given: 128-bit security level, BN curves, point compression, yielding the 768-bit-plus-one-chameleon-element public key size stated above; the paper does not state this is the only or a required choice, only an example computed for illustration.

### Stated limitations
The paper's standard-model factoring-based NIKE construction (a variant of NIKE_fac transported out of the Random Oracle Model) requires an additional assumption the authors state explicitly does not hold in their own default security model: that the adversary registers only valid public keys. The authors state this scheme therefore does not strictly meet their own stated security definitions in the plain (dishonest key registration) setting, and would require validity to be enforced through some external interactive registration protocol — for instance, a proof of correctness of the public key submitted at registration — that the paper does not itself construct. The paper flags an error in prior work it builds on: it states that Cash, Kiltz, and Shoup's claim that the basic (unhashed) Diffie-Hellman NIKE scheme is secure under the Strong Diffie-Hellman assumption is problematic, because the security reduction needs two Decisional Diffie-Hellman (DDH) oracles (one per party sharing the challenged key) while the Strong DH assumption supplies only one; this paper's own factoring-based construction is offered as a way to avoid needing a gap assumption to patch that gap, in a different group (signed quadratic residues) than the CKS-analyzed scheme. The paper's own concluding section states three explicit open problems it does not solve: constructing a pairing-free NIKE scheme secure in the standard model (called particularly challenging in the RSA/factoring setting, for the same public-key-validity-checking reason the paper's own standard-model factoring scheme falls short of the full plain-setting definition); constructing an identity-based NIKE scheme provably secure in the standard model, beyond the Random-Oracle-Model schemes cited from prior work, noting that starting from an Identity-Based Encryption (IBE) scheme is not straightforwardly reversible because IBE private-key generation is typically randomized; and defining a security model and constructing a three-party NIKE scheme based on the Joux protocol, for which the paper states no security model or adversarially-robust construction currently exists. The paper states directly that the unhashed basic Diffie-Hellman NIKE scheme (shared key g^(xy) with no hash of identities) is completely insecure in the paper's own default (dishonest key registration) setting even though it is provably secure under the Decisional Diffie-Hellman assumption in the weaker honest-key-registration (HKR) setting, giving the explicit attack: an adversary registers an honest party Alice's own public key g^x as if it were the adversary's key, then queries for the shared key between itself and another honest party Bob, immediately obtaining Alice and Bob's actual shared key g^(xy) — a homomorphic-key attack the paper states also applies to Bernstein's earlier NIKE scheme.

### Requirements it places on the rest of the system
Achieving the paper's default (plain, dishonest-key-registration) security model requires no assumption whatsoever about the Certificate Authority's registration checks — no proof of possession or knowledge of the private key is assumed — which the paper states is deliberately a stronger, more realistic assumption than models that assume such checks; a system layering identity binding or other guarantees on top of a NIKE scheme proved secure only in the weaker honest-key-registration (HKR) setting must independently add its own registration-time validity checking, or inherits the full-break homomorphic-key attack the paper demonstrates against the unhashed Diffie-Hellman scheme in the plain setting. The NIKE-to-KEM (and onward to public-key encryption) conversion requires a strongly one-time-secure signature scheme as a separate component and requires that scheme's verification key be bound into every ciphertext; the resulting KEM's IND-CCA security proof works specifically by having the reduction respond to a decapsulation query with a NIKE corrupt-reveal query, so the security of the composed system is bounded by, and cannot exceed, the security of the underlying CKS-light NIKE scheme against corrupt-reveal queries. The paper's pairing-based standard-model NIKE construction requires every public key submitted by any party (honest or adversarial) to satisfy a publicly checkable well-formedness condition, verified by two bilinear-pairing evaluations at each SharedKey computation — any system deploying this construction must perform that check at share-computation time, not merely at registration time, since the model allows an adversary to submit malformed keys directly rather than only through a registration step. NIKE provides no forward-secrecy property by its nature: the paper states explicitly that because the primitive is non-interactive (no fresh per-session randomness is exchanged), one cannot hope to obtain any forward-security guarantee from NIKE alone, so any system requiring forward secrecy must obtain it from a different, session-fresh mechanism composed around the NIKE-derived shared key, not from NIKE itself.

### Contradicts
This paper contradicts a specific security claim made in prior work within the same technical line: it states that Cash, Kiltz, and Shoup's claim that the basic (unhashed) Diffie-Hellman NIKE scheme is secure under the Strong Diffie-Hellman assumption is "problematic," because the stated reduction needs two DDH oracles while the Strong DH assumption supplies only one — the paper identifies this as a specific proof gap in a named prior result, not a report of a different measured outcome. No contradiction found against any other paper in this corpus.
