## [KEIZER-CSUR-24] A Survey on Content Retrieval on the Decentralised Web

### What it does
The survey classifies published and deployed mechanisms for locating and retrieving content on a decentralized web — one whose control, governance, and management are not concentrated in a single organization — into three functional layers: search engines (finding content by keyword), name registries (mapping human-readable names to content identifiers), and decentralized file systems (storing and serving the content itself, addressed by a hash-derived content identifier rather than a location). It builds a systematization framework around these three layers, each analyzed along a common set of properties: how content enters the system (curation, registration), how it is organized for lookup (indexing, resolution), how results are prioritized (ranking), how the mechanism defends itself (security, privacy), and how participants are paid for the work of maintaining it (incentives). The survey states its scope covers both peer-reviewed research proposals and running industry projects, and explicitly separates the two because industry projects generally implement complete but narrow-focus systems while research proposals generally implement one mechanism in isolation without a full deployment.

The survey's own definitional content, usable directly as fact: a peer-to-peer (P2P) network is unstructured when nodes form connections without an imposed topology (easy to build, resilient to churn, but requiring query broadcast or random walk to find content because no node can be told in advance where a given item is stored) or structured when the overlay topology is fixed by a protocol rule, most commonly a distributed hash table (DHT), in which a variant of consistent hashing assigns responsibility for each key to a specific peer and any peer can retrieve a value in a bounded number of steps (stated as usually O(log n) hops, where n is the network's peer count) — at the cost of requiring topology maintenance that is both less robust under high churn and exposed to attacks that are harder to mount against an unstructured overlay. Content identifiers (CIDs) on the decentralized web achieve verifiability without a trusted third party through one of two self-certifying constructions: hashing the content itself (so any recipient can hash the retrieved bytes and check the result against the claimed identifier), or hashing a public key whose corresponding private key signs the content (so the signature, not the content hash, proves authenticity, which allows the underlying bytes to change while the identifier stays fixed to that key). The survey states Zooko's triangle as a stated tradeoff among three naming properties — human-readability, security (a verifiable binding between name and content), and decentralization (no trusted party performs the binding) — of which any naming scheme can have at most two simultaneously; hash-based CIDs satisfy security and decentralization but not human-readability, motivating decentralized name-registries (Section 5) that attempt to add human-readable names on top via a blockchain-recorded mapping.

### Parameters
The survey states no tunable numeric parameter of its own (it defines no mechanism, only classifies existing ones). It does report specific configuration facts about deployed systems as descriptive, not experimental, content: in IPFS's Kademlia DHT, provider records for a content identifier c are stored at the 20 peers whose peer IDs are closest to c by XOR distance, and a get() operation returns provider records from those 20 closest peers — this is stated as IPFS's fixed replication-factor design choice, not a result of a parameter sweep.

### Stated limitations
The survey states that, to the best of its authors' knowledge, no existing project achieves full decentralization across all of search engine, name registry, and file-system layers simultaneously ("decentralised search on decentralised data") — every industry project or research proposal it reviews retains at least one centralized component (a centralized crawler, a centralized index store, a centralized gateway, or a permissioned or hybrid resolution path). It states that most decentralized search-engine research proposals address only one search component (typically indexing or index storage) in isolation and have not addressed ranking, curation-based governance, or a full end-to-end system; it states this explicitly as an open issue ("Complete Systems," Section 4.7.2) rather than a solved problem understated elsewhere. It states that claims of superior privacy or security for decentralized search "have not been shown in practice, as new attacks may arise in a new infrastructure," and calls for dedicated security analyses rather than treating decentralization itself as a security guarantee. It states that decentralized name-registries built on blockchains have not addressed key-loss, key-compromise, or key-revocation handling, and that threshold-signature-based ownership verification (multiple keys required to control a name) has not been implemented in the blockchain-based systems it surveys, in contrast to prior peer-to-peer social/personal naming literature that has considered the problem. It states that decentralized file systems exhibit "a trend toward centralisation" driven by three separate pressures — performance (DHT lookup latency, addressed by adding centralized cloud-hosted indexers), content-moderation requirements (addressed by a single company, Protocol Labs, centrally curating a public "bad bits" blocklist that other IPFS operators may or may not consult), and reliability — and states that little is known about the moderation process used to build that blocklist or about how widely other node operators actually apply it. It states that privacy for both content readers and content providers in decentralized file systems has been "mostly overlooked" by currently deployed systems, and that the strongest published defense it reviews (Backes, Goldberg, Kate, Toft's threshold-cryptography DHT query-privacy scheme) "requires significant overhead to content retrieval," presenting an unresolved performance/privacy tradeoff. It states that mutable (updatable) content is fundamentally in tension with hash-of-content addressing, because any content change necessarily changes a content-hash-derived identifier; the survey's stated partial mitigation (hash-of-public-key naming, as in IPNS) solves identifier persistence but not the separate problem of guaranteeing that a lookup on a persistent name returns the current version rather than a stale cached one, which the survey states remains an open problem even with version-number suffixes, because a reader has no way to know what the current version number actually is without an out-of-band source.

### Requirements it places on the rest of the system
As a survey, this paper does not itself impose requirements on a system built to its recommendations, but its classification of the mechanisms it reviews makes explicit several composition requirements a designer must satisfy to use them. Content-addressed storage (self-certifying CIDs) requires that any component providing a "current version" or "latest state" abstraction over that storage supply its own separate identifier-to-version mapping, because the survey states the content-hash-derived identifier itself cannot serve this role: a content hash changes on every update, so name persistence for mutable content requires layering a public-key-based naming scheme (or an external name-registry) on top of raw content addressing. Kademlia-DHT-based provider-record storage (as used by IPFS) requires that the DHT's key space have peer identifiers distributed independently and unpredictably of any single actor's control, because the Sybil-based censorship attack the survey cites (Sridhar et al.) succeeds specifically by placing enough attacker-controlled peer IDs near a target content identifier's XOR-distance neighborhood; a system adopting unmodified closest-20-peer provider-record storage inherits this precondition and its associated attack surface. Privacy-preserving retrieval via double-hashing (using hash(CID) rather than CID as the DHT lookup key, per Michel) requires that only parties who already know the plaintext CID be able to compute the lookup key, which in turn requires the CID itself to have reached the requester through some channel outside the DHT lookup being protected — the survey does not describe such a channel, so a system adopting this mechanism must supply one. NAT (Network Address Translation) traversal via a relay peer with a public IP (as IPFS implements) requires that some fraction of the network's participants hold public, reachable IP addresses to serve as relays, since the survey states this is how IPFS bootstraps communication between two NAT'ed peers, using standard hole-punching once a relay is found.

- Trautwein, Raman, Tyson, Castro, Scott, Schubotz, Gipp, Psaras, "Design and Evaluation of IPFS: A Storage Layer for the Decentralized Web," SIGCOMM 2022 — foundational/independent measurement of IPFS performance, source of the DHT-resolution-latency-bottleneck finding.
- Wei, Trautwein, Psaras, Castro, Scott, Raman, Tyson, "The Eternal Tussle: Exploring the Role of Centralization in IPFS," NSDI 2024 — independent measurement/critique of IPFS centralization trend, directly relevant to the centralization-tradeoff discussion in Section 6.7.1.

- Benet, "IPFS — Content Addressed, Versioned, P2P File System," 2014 (arXiv 1407.3561) — foundational, the base design this survey's file-system section repeatedly analyzes.
- Benet, Greco, "Filecoin: A Decentralized Storage Network," Protocol Labs, 2018 — foundational, the blockchain-incentive layer built atop IPFS discussed in Section 6.6.
- Cox, Noble, "Samsara: Honor Among Thieves in Peer-to-peer Storage," SOSP 2003 — foundational, the tit-for-tat symmetric-storage-claim incentive mechanism described in Section 6.6, including its stated weakness that the claim mechanism cannot force a peer to actually replace a claim with real data on request.
- Li, Zhu, Zhang, Tan, Xia, Angel, Chen, "Bringing Decentralized Search to Decentralized Services" (DeSearch), OSDI 2021 — competing decentralized search architecture using a Trusted Execution Environment (TEE)-based verifiable-worker design with a centralized cloud index store; holds the detailed reward-chain (consumers→rankers→indexer→crawlers→publishers) mechanism.

- Wang, Wu, "Keyword Search Technology in Content Addressable Storage System," 2020 — competing decentralized search engine ranking by network metrics (freshness, proximity, resource quantity, bandwidth) rather than content relevance alone.
- Raza, Han, Hwang, "A Framework for Privacy Preserving, Distributed Search Using Smart Contracts," 2020 — competing decentralized search architecture using Tor relay groups and Practical Byzantine Fault Tolerance (PBFT) consensus for ranking.
- Steiner, En-Najjary, Biersack, "A Global View of KAD," IMC 2007 — foundational deployed-DHT measurement, already in this batch (STEINER-IMC-07); cited by this survey (reference [176]) in its structured-P2P-network discussion.
- Maymounkov, Mazières, "Kademlia: A Peer-to-peer Information System Based on the XOR Metric," IPTPS 2002 — foundational, already in corpus per BRIEF.md; the DHT construction underlying IPFS's provider-record resolution described throughout Section 6.
