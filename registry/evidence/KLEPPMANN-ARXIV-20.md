## [KLEPPMANN-ARXIV-20] Byzantine Eventual Consistency and the Fundamental Limits of Peer-to-Peer Databases
**Citation:** Martin Kleppmann, Heidi Howard. "Byzantine Eventual Consistency and the Fundamental Limits of Peer-to-Peer Databases." arXiv preprint arXiv:2012.00472, 2020.
**Retrieved:** full text via https://arxiv.org/abs/2012.00472
**Source URL:** https://arxiv.org/abs/2012.00472
**Domain:** D+H

### What it does
Byzantine Eventual Consistency (BEC) is a correctness condition for a replicated database that a system can guarantee while tolerating an unbounded number of Byzantine-faulty replicas (replicas that may deviate from the protocol in arbitrary, possibly colluding ways), which makes any system meeting it immune to Sybil attacks (an adversary joining many fake peers) without proof-of-work or centrally controlled peer admission — because tolerance does not depend on any bound on the faulty fraction. BEC requires three properties of every correct replica: it applies its own generated updates immediately (self-update); any update one correct replica applies is eventually applied by every correct replica (eventual update); and two correct replicas that have applied the same set of updates reach the same state regardless of application order (convergence). The paper proves a necessary-and-sufficient theorem: a fault-tolerant BEC algorithm exists for a given set of transactions and invariants (predicates a database state must satisfy, such as a non-negative balance or a foreign-key constraint) if and only if those transactions are invariant-confluent (I-confluent) with respect to every invariant — meaning that whenever two transactions are executed concurrently by different replicas, each individually preserving an invariant, applying both together (in either order, since I-confluent transactions' updates commute) still preserves the invariant. The construction proceeds in two layers. First, Byzantine causal broadcast delivers messages to every correct replica in an order consistent with causal dependency, implemented by having each replica sign its messages, reference the hashes of its own causal predecessors in each message (forming a directed acyclic graph over delivered messages, since a cycle would require a hash collision), and periodically reconcile with peer connections by exchanging the hashes of "heads" (delivered messages with no known successor) and walking backward through the predecessor graph to discover and request every message the peer lacks — vector clocks are explicitly ruled out for this role because a faulty replica can hand two correct replicas different messages carrying the identical vector timestamp, making them believe falsely that their message sets already agree. Second, a replication algorithm layered on top of this broadcast applies each delivered update only if it passes a per-invariant safety check (for example: a foreign-key deletion is unsafe unless the referencing tuple's insertion causally preceded it) and only if any deletion in the message targets a tuple whose insertion the same message causally follows — a correct replica drops any update failing these checks rather than corrupting its own state, even though a faulty replica may have broadcast it.

### Parameters
- Fault-tolerance definition used for the main theorem: an algorithm is called fault-tolerant if it can commit a transaction after receiving responses from up to r-2 of r replicas (tolerating one crashed or unreachable replica); the paper states the theorem also holds for algorithms tolerant of more faults, and uses the weaker one-fault definition because it makes the impossibility result stronger.
- Bloom filter configuration in the evaluation: 10 bits per entry, 7 hash functions (not stated as swept — this is the single configuration the round-trip and byte figures above were measured under).
- Assumed per-update size for the bandwidth cost model: 200 bytes, excluding predecessor hashes.
- Assumed hash size: 32 bytes (SHA-256).
- Assumed fixed per-message overhead: 100 bytes.
- Number of replicas in the evaluation: 4 (not swept).
- Averaging: 600 reconciliations per data point, 100 between each distinct pair of the 4 replicas.
- Byzantine agreement replica counts cited from prior work, for contrast (not this paper's own result): typical Byzantine agreement requires at least 3f+1 replicas to tolerate f faults; some require 5f+1; this can be lowered to 2f+1 assuming synchrony and digital signatures; Upright separates crash faults u and Byzantine faults r and uses 2u+r+1 replicas; Zeno makes progress with f+1 replicas but safety requires fewer than one-third of replicas Byzantine-faulty.

### Stated limitations
The main theorem requires that correct replicas form a single connected component in the graph of replicas and network links (Figure 1); if two correct replicas can communicate only through faulty replicas, no algorithm can guarantee data exchange between them, since the adversary can always block that path (an eclipse attack) — the paper states connecting each replica to every other is the simplest way to satisfy this, but calls "how can we best ensure correct replicas form a connected component" an open question in its conclusion, since full connectivity is expensive at scale. The evaluation ran only with all replicas correctly following the protocol; the paper states it believes adding faulty replicas would not fundamentally alter the results (this is an unmeasured belief, not a reported measurement, and must not be recorded as a figure) because faulty replicas could alter the shape of the predecessor graph, e.g. producing more concurrent updates than there are replicas. CPU and memory use of the prototype were not measured; the paper states this is left for future work. The paper could not compare its algorithms against Depot, a prior system tolerating arbitrary Byzantine faults, because the available Depot publications did not describe its algorithm in enough detail to reproduce it. The theorem's proof assumes an asynchronous system (no bound on message delay) but the paper states it also holds for partially synchronous systems in which delay is only temporarily unbounded. The paper explicitly does not resolve Bitcoin's proof-of-work electricity cost, because it shows a cryptocurrency's payment transactions are not I-confluent with respect to a non-negative-balance invariant (two concurrent debits from the same account can jointly violate the invariant even though each alone would not), so a cryptocurrency requires a Sybil countermeasure beyond what this result can remove. Two further open questions are stated without answer: how to formalize the process (given only informally in Table 1) of checking whether an update is safe with respect to an invariant, and whether the equivalence "solvable without coordination in a non-Byzantine system if and only if immune to Sybil attacks in a Byzantine one" holds in general.

### Requirements it places on the rest of the system
Every replica must hold a distinct private key for digital signatures, with every other replica's corresponding public key known to it; every message must be signed by its sender, and a recipient discards any message with an invalid signature — a deployment without this signing infrastructure cannot use the algorithm, since it relies on signatures to prevent a faulty replica from impersonating a correct one. Pairwise network links between replicas must eventually deliver a sent message provided neither endpoint crashes (retransmission of lost messages is assumed available, e.g. via TCP), and replicas need a timer capable of triggering periodic actions (retransmission, reconciliation) without requiring synchronized or exact clocks. The construction requires a collision-resistant cryptographic hash function (the paper names SHA-256 as meeting this) because the predecessor graph's acyclicity, and the whole causal-delivery mechanism, depends on no two distinct messages sharing a hash. Applying BEC to a specific application requires that application's designer to determine which of its transactions and invariants are I-confluent, using rules like those in Table 1 (e.g. a foreign-key deletion is unsafe unless the deleted tuple's insertion causally precedes it in the message graph) — a transaction set found not to be I-confluent with respect to some invariant needs a separate Byzantine-consensus mechanism for just that portion, since the paper's theorem proves no fault-tolerant BEC algorithm can preserve a non-I-confluent invariant under arbitrary Byzantine faults. The reconciliation algorithm depends on each replica durably storing, per remote peer identity, the "heads" recorded at the end of the last successful reconciliation with that peer (via StoreHeads), so the optimized Algorithm 2's constant-round-trip performance requires persistent per-connection state across reconciliation rounds, not just per-message state.

None found — no other entry in this batch measures Byzantine causal broadcast reconciliation cost. Cross-reference: this paper's I-confluence necessary-and-sufficient theorem for Byzantine systems extends I-confluence as originally defined for non-Byzantine systems by Bailis et al.; a claim that I-confluence alone was already known to be necessary and sufficient in a Byzantine-fault setting before this paper would be a claim this paper does not support — the paper states its own theorem is the extension.
