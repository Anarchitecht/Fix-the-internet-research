## [BALDUF-IMC-24] Looking AT the Blue Skies of Bluesky
**Citation:** Leonhard Balduf, Saidu Sokoto, Onur Ascigil, Gareth Tyson, Björn Scheuermann, Maciej Korczynski, Ignacio Castro, Michał Król. "Looking AT the Blue Skies of Bluesky." ACM Internet Measurement Conference (IMC), 2024. DOI 10.1145/3646547.3688407.
**Retrieved:** full text via https://arxiv.org/abs/2408.12449
**Source URL:** https://arxiv.org/abs/2408.12449
**Domain:** J+K

### What it does
The paper measures whether Bluesky's decomposition of a social network into independently swappable components (identity, data hosting, feed aggregation, content moderation) actually produces provider diversity in practice, or re-concentrates around one operator per component instead.

Bluesky's architecture, as described by the paper, separates five roles. A Decentralized Identifier (DID) names each user, resolved to a DID Document that lists the user's current handle and the network endpoint of the Personal Data Server (PDS) holding that user's data. A PDS stores a user's repository, a signed, git-like append log of every action (post, like, follow, block) the user performs; a user can migrate their repository to a different PDS, including a self-hosted one, while keeping the same DID and social graph, by updating the endpoint field in their DID Document. Because polling every PDS individually for updates does not scale, a Relay aggregates repository updates from all known PDSes into one stream (the Firehose) and caches repository copies locally; Bluesky PBC (the company) operates the default Relay and Firehose at bsky.network, though the protocol does not require a single Relay. Feed Generators are services, operable by anyone, that consume the Firehose (or a subset of it) and produce a ranked list of post references implementing a particular feed-ranking algorithm; they can be self-hosted or run through a hosting platform. Labelers are accounts that attach machine-readable labels (for example "nudity" or a spoiler warning) to specific posts, accounts, or media; any account can register as a Labeler by publishing a service-information record in its own repository, and each user chooses, individually, which Labelers to subscribe to and how their client should react to a given label from that Labeler. The AppView is the component that collates data from across the network (consuming the Firehose) into the views a client displays (a user's timeline, a thread, search results); Bluesky PBC operates the only AppView the paper found in production use.

The paper's measurement methodology, for each component, is to enumerate the full population of operators of that component from Bluesky's own public data streams, then compute how concentrated that population is. Data sources: the Relay's sync.listRepos call for the full list of active user DIDs and their latest repo-commit version (queried weekly, March-April 2024); each user's DID Document (downloaded via Bluesky's centralized plc.directory service for the did:plc method, and via HTTPS .well-known lookups for the did:web method); a full snapshot of every user's repository content via the Relay's sync.getRepo endpoint; a continuous subscription to the Firehose from March 6 to April 30, 2024; the AppView's getFeedGenerator and getFeed endpoints for Feed Generator metadata and posts; and each Labeler's own public label-stream endpoint, listed in its DID Document.

### Parameters
The paper is a measurement study of a live deployed system, not a system with tunable design parameters. Its own methodological parameters (data-collection windows, not protocol settings) are:

| Parameter | Value used |
|---|---|
| User Identifier Dataset collection window | Weekly queries, March-April 2024 |
| DID Document snapshot window | One week, March 2024 |
| Repository snapshot collection window | 10 days, April 2024 |
| Firehose continuous subscription window | 2024-03-06 through 2024-04-30 |
| Feed Post collection window | 2024-04-16 through 2024-05-10, bi-weekly polling |
| Labeler reconnection check frequency | Daily |
| Random-sample verification of self-assigned language tags | Approximately 0.1% of tagged posts manually checked against actual post language |

### Stated limitations
The paper states it "deliberately omit[s] a deeper analysis of the social graph, as Bluesky does not introduce novel solutions in this regard," so no independent social-graph structural analysis comparable to Mastodon-instance studies is reported here. It states that it cannot distinguish, from the Feed Generator metadata alone, between a Feed Generator that is permanently deleted versus temporarily unavailable, and consequently excludes 4.3% of discovered Feed Generators lacking retrievable metadata from further analysis. It states Feed Generators differ in how much post history they retain (some impose duration or count limits), so the Feed Post Dataset cannot be assumed complete for any Feed Generator's full history predating the collection window. It states that user label-subscription preferences (which Labelers a given user follows, and how their client reacts) are not publicly visible, and that the authors deliberately made no attempt to infer them, for ethical reasons; so no measurement of Labeler adoption from the subscriber side is reported. It states that the Brazil user-migration event (following a 2024 court-ordered ban on Twitter/X in Brazil) fell outside the data-collection period, so its effect on Bluesky's growth curve is not captured in this paper's figures. It states explicitly that it is not clear how a user migration away from Bluesky PBC's centralized Relay and AppView would work in practice, and that network effects might prevent it regardless of the protocol's technical openness. It states that whether the current open Feed Generator and Labeler ecosystems remain economically viable and scalable as non-Bluesky-PBC-operated infrastructure (rather than as a thin layer atop Bluesky PBC's centralized Firehose and AppView) "remains to be seen," explicitly flagging this as unresolved rather than answered by the paper's data.

### Requirements it places on the rest of the system
A component-diversity claim about Bluesky (or an architecture like it) requires specifying which component is meant, since this paper's own results diverge sharply by component: identity-handle hosting is stated as 98.9% concentrated in the platform operator's own free domain, Feed-Generator hosting-as-a-service is stated as 85.86% concentrated in one third-party platform (Skyfeed), while domain registrar choice among the small fraction of self-managed-domain users is comparatively less concentrated (top four registrars hold 50%) — a synthesis step that treats "Bluesky's decomposition produces diversity" as one true-or-false claim would need to average or otherwise combine these disparate per-component figures, which this paper does not do. Interpreting any Bluesky content-moderation measurement requires knowing that the official Bluesky Labeler's specific label values (for example !takedown) carry hardcoded client behavior that ordinary community Labelers' labels do not, so a labeling scheme built on this architecture must reserve some label namespace for platform-operator-only enforcement actions if it wants a takedown mechanism, since the paper states this exclamation-mark-prefixed namespace is "valid only when issued by the official Bluesky Labeler." Any system relying on this paper's Firehose-based full-network-visibility approach requires a client to sustain roughly 30 gigabytes per day of bandwidth per subscribed consumer, which sets a lower bound on the bandwidth cost of running an independent Relay, AppView, or comparable full-network-observing service without relying on Bluesky PBC's own infrastructure. The handle-ownership-verification mechanism for self-managed domains requires the domain owner to control DNS TXT records under an _atproto subdomain (used by 98.7% of measured self-managed handles) or, less commonly, a /.well-known/atproto-did HTTPS-served file (1.3%); a system reusing this verification approach inherits dependence on DNS or web-server control as the ownership-proof channel, with the associated registrar-level concentration this paper measures (50% of self-managed domains through four registrars).

### Contradicts
None found within this batch as a direct numeric disagreement. The paper's finding that identity-handle concentration (98.9% under one operator-controlled domain) coexists with comparatively higher registrar-level diversity among the remaining self-managed handles illustrates, within this single paper, that "decentralized identity" is not a single measurable quantity; a synthesis step should not cite this paper for one undifferentiated Bluesky "decentralization score." This paper cites La Cava, Greco, Tagarelli (the LACAVA-ANS-21 entry in this batch) directly, as reference [11], solely as an example of prior Fediverse-centralization measurement work in its related-work discussion of Mastodon; it does not reproduce or dispute LACAVA-ANS-21's specific structural figures.
