## [HUGENROTH-USENIXSEC-21] Rollercoaster: An Efficient Group-Multicast Scheme for Mix Networks
**Citation:** Daniel Hugenroth, Martin Kleppmann, Alastair R. Beresford. "Rollercoaster: An Efficient Group-Multicast Scheme for Mix Networks." USENIX Security Symposium, 2021.
**Retrieved:** full text via https://www.usenix.org/system/files/sec21-hugenroth.pdf
**Source URL:** https://www.usenix.org/system/files/sec21-hugenroth.pdf
**Domain:** H

### What it does
Rollercoaster delivers a message to every member of a group at latency that grows logarithmically in group size, over a mix network, while preserving the mix network's metadata-privacy guarantees. A mix network delays and reorders messages at each relay (mix node) so an observer of network traffic cannot correlate a message's arrival with its departure; this paper builds on Loopix, a mix-network design in which every user's client generates payload messages, decoy drop messages, and decoy loop messages at independent Poisson-process rates, and every relay adds an exponentially-distributed random delay to each message it forwards, so that traffic volume and timing carry no signal.

Sending a message to a group of m members by having the sender unicast to each member individually (naive sequential unicast) takes the sender's fixed payload-sending rate lambda_p, so total delivery time to the last recipient grows linearly, O(m), because the sender's own rate is the bottleneck and every one of the m copies passes through it before the last one leaves. Rollercoaster instead forms a distribution tree: after the source sends the message to its first recipient, every node that already holds the message becomes a further sender, so the set of nodes holding the message multiplies by a branching factor k+1 at every tree level, and the number of levels needed to cover m recipients is L = ceil(log_{k+1}(m)). Each node computes its position in this tree deterministically from a single shared nonce via a GenSchedule algorithm, so no additional coordination messages are needed beyond the nonce itself. Rollercoaster requires no modification to the underlying Loopix protocol and adds only a 16-byte header (recording message source, sender, and role) inside the existing Sphinx packet format Loopix already uses.

A fault-tolerant variant (RC-FT) detects when a node assigned to forward the message in the tree is offline (the source detects a missing acknowledgment after a timeout) and reassigns that node's children to another already-informed node, so a single offline forwarder degrades delivery to its subtree rather than blocking it. This variant assumes the original source node stays connected and acts honestly for the duration of message distribution; the paper proves this assumption formally in its extended appendix.

An optional protocol extension, MultiSphinx, modifies a small, bounded number of mix nodes so a single input message can be split into a small fixed number p of output messages inside the mix layer (p-restricted multicast) rather than only at the endpoint nodes of the distribution tree, further lowering the payload-sending rate each client needs to sustain — relevant because a mobile device's radio incurs a fixed energy cost each time it wakes from idle to send, so fewer, larger message batches save battery relative to many small ones at the same total data volume.

### Measured results
All measurements come from a deterministic, single-machine, reproducible Python simulator (not a real network), because the authors state Loopix's real-network performance was already established in the original Loopix paper and simulation lets them eliminate external interference (unrelated network congestion, CPU contention) and gather far more results per unit of computation; no cryptographic operations are actually performed in the simulator (justified by Loopix's own finding that queuing and per-hop delay dominate total message latency, with crypto and network transmission time being negligible by comparison). The simulator was validated by reproducing a latency-distribution figure from the original Loopix paper. The final evaluation ran 276 independent simulations totaling more than 992,160 hours of simulated node time in under 209 hours of CPU core time (a 4,500x simulated-to-real speedup). Fixed simulation parameters throughout: 16 users per provider, client rates lambda_p = lambda_d = lambda_l = 2/s, per-hop mix delay rate lambda_mu = 3/s (overall client sending rate lambda = 6/s, satisfying Loopix's suggested lambda/lambda_mu >= 2 ratio), a 3-layer mix network with 3 mix nodes per layer, 10 ms simulation tick granularity, 24-hour simulated time span per configuration. Application traffic is modeled as a Poisson process, one message sent on average every 30 seconds by an online group member, with an 80/20 participation-inequality split (20% of users generate 80% of messages).

All-online scenario, average message latency reduced from unicast to Rollercoaster (k = p = 2), group size 128: 34.9 s to 7.0 s; group size 256: to 8.3 s. At group size 128, 99th-percentile latency dropped from 75.6 s (unicast) to 12.3 s (Rollercoaster), 90th percentile from 60.8 s to 9.9 s. Overall, for group size 128, the paper's summary states a 5x speedup in mean latency (34.9 s to 7.0 s) and a reduction in 99th-percentile latency from 75.6 s to 12.3 s.

Fault-tolerance scenario, offline behavior modeled from the Device Analyzer smartphone-usage dataset (traces filtered to n=27,790 total, n=25,618 with connectivity information, n=20,117 covering at least 48 hours, n=2,772 with no gap over 12 hours; the paper notes this dataset is more than five years old and is used only to derive archetype online/offline behavior models, not as a live measurement). Three connectivity models were built at 65% (matching the dataset), 80%, and 88% mean online time. At 65% online, group size 128, without fault tolerance the 99th-percentile latency exceeded 10,000 s; with the fault-tolerant variant (RC-FT), 99th percentile fell to under 21.9 s (90th percentile 18.0 s), compared to 103.3 s (99th percentile) / 61.9 s (90th percentile) for unicast under the same offline model.

Multiple-groups scenario: 128 users distributed across 1 to 16 groups (every user a member of every group), at both 100% and 80% online — the number of group memberships had little measured impact on Rollercoaster's latency.

Message-burst scenario: group size 128, burst sizes b of 1 to 32 messages sent at once, at 100% and 80% online — Rollercoaster (fault-tolerant variant) tolerated much larger bursts than unicast before send-queue growth degraded latency; both schemes showed queue-growth-driven latency increases at b=32, with the effect appearing at a higher burst size for p-restricted multicast than for plain Rollercoaster.

p-restricted multicast (MultiSphinx) scenario: group size 128, 80% online, increasing the branching factor k alone (holding p=1) had negligible or negative effect on mean latency; increasing k and the multiplication factor p together allowed a reduced client sending rate lambda (with lambda_mu decreased proportionally to preserve the lambda/lambda_mu >= 2 ratio, which increases per-hop delay) while maintaining comparable latency — reported as a heatmap over lambda/1 through lambda/16 and k=p from 1 to 16, without a single summary percentage.

Asymptotic comparison (analytical, not simulated): naive sequential unicast has latency O(m) and zero packet-size overhead; naive mix-node multiplication has latency O(1) but packet-size overhead O(m) (because a single input packet must carry m-1 payloads and headers); Rollercoaster achieves latency O(log m) with O(1) packet-size overhead (Table 2).

### Stated limitations
Group membership is assumed fixed and known to all members for the duration of a message distribution; the problems of group formation and of adding or removing members are explicitly left for future work. The fault-tolerant variant assumes the message's original source node remains connected and behaves honestly throughout distribution; the paper states this assumption is used in its formal proof (given in an appendix of the extended paper) rather than relaxed or tested against a dishonest or disconnecting source. The threat model assumes trust among group members: the scheme provides no unlinkability or unobservability guarantee against an attacker who compromises or colludes with a group member, only against outsiders. A naive mix-node-multiplication alternative (rejected in favor of Rollercoaster) is shown to leak the exact group size to a corrupt or even merely observing multiplication node, and the paper explains why cover traffic mitigation for that alternative would require bandwidth scaling with the largest supported group size — this is presented as the reason the naive design was not used, not as a residual property of Rollercoaster itself. MultiSphinx, the optional mix-node-splitting extension, is stated to weaken the assumption Sphinx normally relies on (that every input message to a mix node is independent); if an adversary corrupts a p-restricted multiplication node, that adversary gains a chance to correlate which two output messages came from the same input, a partial reduction in anonymity relative to unmodified Loopix, described but not quantified with an attack success rate in the retrieved text. Receiver anonymity and unlinkable group membership (hiding membership even from other members, or hiding which specific member received a message) are explicitly left for future work; the paper's own guarantee is membership unobservability against outsiders only. The evaluation is entirely simulation-based; the authors state they rely on the pre-established real-network performance of Loopix rather than re-measuring on a real network or with a black-box network simulator such as Shadow, and no live-deployment or adversarial-network experiment is reported. The Device Analyzer connectivity dataset used for the fault-tolerance evaluation was, at time of writing, more than five years old, and the paper uses it only to derive behavioral archetypes for a synthetic connectivity model rather than as a direct current measurement. Related-work comparisons name Vuvuzela's cover-traffic-based design as reaching call-setup delays up to 10 minutes and message latency over 30 seconds, which the authors state they consider too large for the collaborative-application target this paper sets (this is the paper's own comparative judgment about a different system, included here as an attributed statement, not as this paper's own measured result).

### Requirements it places on the rest of the system
Requires an underlying Loopix-model mix network already deployed and correctly parameterized (fixed per-client Poisson rates for payload, drop, and loop messages; per-hop exponential delay; a layered mix topology with providers as user entry points); Rollercoaster is a layer on top of this network and supplies no mix-network mechanism of its own. Requires every group member to be able to compute the same deterministic distribution-tree schedule from one shared nonce (the GenSchedule algorithm), so key distribution or group setup must supply that nonce to every member before a multicast begins. Requires a fixed, mutually known group membership at message-send time; a system that needs dynamic add/remove of members mid-session is not covered. The fault-tolerant variant requires an acknowledgment-and-timeout mechanism between a forwarding node and its parent, and its correctness proof depends on the message's original source remaining online and honest; a design that cannot guarantee source availability for the duration of one multicast round does not meet this precondition. The optional MultiSphinx extension requires modifying a subset of mix nodes to support message multiplication with a fixed small factor p, which is a change to the underlying Sphinx/Loopix relay software, not merely client-side logic — a deployment unable to modify relay behavior can use only the base Rollercoaster scheme (k branching among endpoints), not MultiSphinx's added mix-layer splitting. The scheme's metadata-privacy guarantee (sender-recipient unlinkability, online unobservability, membership unobservability) inherits directly from Loopix's own guarantees against a global active adversary; a deployment that weakens or omits the underlying Loopix decoy-traffic and delay parameters correspondingly weakens Rollercoaster's guarantees, since Rollercoaster adds no independent anonymity mechanism beyond the distribution-tree structure and the MultiSphinx header.
