## [BONEH-CRYPTO-18] Verifiable Delay Functions
**Citation:** Dan Boneh, Joseph Bonneau, Benedikt Bünz, Ben Fisch. "Verifiable Delay Functions." CRYPTO, 2018.
**Retrieved:** full text via https://eprint.iacr.org/2018/601.pdf
**Source URL:** https://eprint.iacr.org/2018/601.pdf
**Domain:** I

### What it does
A verifiable delay function (VDF) forces anyone computing it to spend a specified minimum number of sequential computation steps, even given an unbounded number of parallel processors, while letting any third party check the output in far less time than the computation itself took. A VDF is a triple of algorithms. Setup(security parameter, delay parameter t) produces public parameters that fix the input and output domains. Eval takes an input x and, after t sequential steps, outputs a value y and a proof pi. Verify takes x, y, and pi and accepts or rejects in time much shorter than t. The paper defines the security property a VDF must have as sigma-sequentiality: no adversary limited to parallel time sigma(t) on any polynomial number of processors can distinguish a correct output from a random string with more than negligible advantage, even after an unbounded pre-computation phase before the challenge x is known. Four candidate constructions are given. First, a theoretical construction from incrementally verifiable computation (IVC), in which a prover updates a succinct proof of correctness at each step of an underlying sequential function so the full proof is ready immediately after the computation finishes; this achieves sigma(t) = (1-epsilon)t - O(1) sequentiality given a tight IVC scheme, itself built from succinct non-interactive arguments of knowledge (SNARKs). Second, a candidate built from injective permutation polynomials over finite fields whose inverse requires computing a polynomial greatest common divisor (GCD), a computation the paper states is sequential in the polynomial's degree on any machine with fewer than a stated number of processors; this is called a "weak VDF" because the honest evaluator itself needs greater-than-polylogarithmic parallelism to run in the stated delay. Third, a practical efficiency technique that plugs a "time-asymmetric encoding" (a function cheap to invert but expensive to compute forward) into the IVC construction as the repeated sequential step, so the SNARK proof only needs to verify inversion rather than the forward computation, cutting the arithmetic complexity the SNARK must verify per step. Fourth, an exponentiation-based construction in a group of unknown order (an RSA group whose factorization nobody knows, or a class group of an imaginary quadratic order) that is secure only against an adversary bounded to a fixed amount of pre-computation done before the challenge is issued, trading the strength of the general sigma-sequentiality guarantee for a much shorter proof than the IVC-based constructions produce.

This is a construction and proof paper; it reports no deployed-system benchmark. Its quantitative figures are analytical or micro-benchmark extrapolations tied to a stated construction and hardware model, not an end-to-end system measurement.

### Parameters
- Delay parameter t: the number of sequential steps Setup fixes (or, in the incremental variant, that Eval specifies within a single set of public parameters).
- sigma(t), the achieved sequentiality: (1-epsilon)t - O(1) for the tight-IVC-based construction; t - o(t) for the polynomial-GCD-based weak VDF under Assumption 2 (no algorithm computes the GCD of two degree-d univariate polynomials in fewer than O(d^2) parallel steps).
- Preprocessing security parameter B for the bounded-pre-computation exponentiation construction: worked example B = 2^30; determines both public-parameter size (encoding key holds B group elements) and how many challenges may be safely answered before regenerating parameters.
- RSA modulus size for the bounded-pre-computation construction: worked example 4096 bits, with prime factors chosen as strong primes.
- SNARK field size for the IVC-based practical constructions: p is approximately 2^128 in the base pairing-based SNARK; the Sloth-family improvement instead matches the iterated function's field to the SNARK field Fq with q approximately 2^256.
- Sloth++ field-extension degree r = 2 over Fp, chosen so verifying one iteration costs exactly 4 multiplication gates over Fp.

### Stated limitations
The security of using a VDF-based delay to protect a proof-of-work blockchain randomness beacon "remains an informal conjecture due to the lack of a complete game-theoretic model capturing miner incentives in Nakamoto-style consensus protocols," so no formal bound on the required delay parameter against a profit-motivated miner is given. The polynomial-GCD-based construction is stated to be only a "weak VDF": the honest evaluator itself must use super-polynomial parallelism (not merely poly-logarithmic) to complete in the stated delay, because the polynomial's degree must be super-polynomial in the security parameter to block an adversary from running the polynomial-time GCD algorithm on polynomially many processors. The bounded-pre-computation exponentiation construction is explicitly stated to not satisfy the paper's own VDF security definition: the authors describe a concrete pre-computation attack requiring tB group operations and O(sB) space that grants a parallel adversary a factor-s speedup, and state the construction "is secure for only B challenges, after which new public parameters need to be generated." The paper states that using a group of unknown order without a trusted setup (by sampling a sufficiently large random RSA-form modulus N) forces N to be large enough to make factoring hard, and that this larger N both gives an adversary more opportunity to parallelize the group arithmetic and increases the verifier's running time, compared to a trusted-setup modulus. Sloth, a prior construction the paper builds on, is stated not to meet the paper's VDF definition because its output, a t-bit number, requires time proportional to t simply to read, so verification cannot run in the paper's required polylogarithmic time. The paper states that the class of proof-of-replication constructions it enables is "quite delicate to formally define" and had at the time of writing been developed further only in unpublished follow-up work.

### Requirements it places on the rest of the system
A VDF-based randomness beacon requires the network to post public parameters (from Setup) before any challenge is issued, and requires whoever evaluates the VDF to have no way to learn the challenge input earlier than every other party, since the entire security argument rests on the evaluator needing t sequential steps starting from when the input becomes known. The trusted-setup variants (the IVC-based construction using a pairing-based SNARK, and the RSA-modulus exponentiation construction using a modulus with unknown factorization) require a one-time setup ceremony run by a party trusted to discard the corresponding secret (the SNARK toxic waste, or the RSA factorization); an alternative that avoids this trusted party is to use the class group of an imaginary quadratic order, which the paper states has an efficient public setup, at the cost of the larger-modulus tradeoffs described above. The bounded-pre-computation construction's security assumption is violated if an adversary can run a pre-computation of size proportional to B group operations between the time the public parameters are published and the time the challenge is issued, so any deployment must bound or monitor that interval. Using a VDF as the time-asymmetric encoding inside a proof-of-replication protocol requires modeling the VDF as an ideal cipher (an oracle that is a bijection from a random subset of inputs to outputs and takes T sequential steps per query) rather than merely as sigma-sequential, which is a strictly stronger requirement the paper states is needed for that specific application and not automatically satisfied by every construction in the paper.
