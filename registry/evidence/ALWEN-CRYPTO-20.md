## [ALWEN-CRYPTO-20] Security Analysis and Improvements for the IETF MLS Standard for Group Messaging
**Citation:** Joël Alwen, Sandro Coretti, Yevgeniy Dodis, Yiannis Tselekounis. "Security Analysis and Improvements for the IETF MLS Standard for Group Messaging." CRYPTO, 2020. DOI 10.1007/978-3-030-56784-2_9.
**Retrieved:** full text via https://eprint.iacr.org/2019/1189.pdf
**Source URL:** https://eprint.iacr.org/2019/1189.pdf
**Domain:** H

### What it does
This paper gives a formal cryptographic security proof for TreeKEM, the group-key-agreement protocol at the core of the IETF's Messaging Layer Security (MLS, message-layer security) draft standard for secure group messaging (SGM). It defines continuous group key agreement (CGKA) as a standalone cryptographic primitive — a protocol that lets a dynamic set of users add members, remove members, and perform updates, where each update run by any one member produces a new shared secret ("update secret") that every other member can compute, while looking random to an outside attacker. The paper proves TreeKEM satisfies a formally defined but non-adaptive CGKA security notion, identifies a specific forward-secrecy weakness in the version of TreeKEM under standardization, and proposes and proves secure a modified TreeKEM that fixes it.

Mechanism (TreeKEM/ratchet trees). Group members occupy the leaves of a left-balanced binary tree (a binary tree built so that its left subtree is always a maximal full binary tree — every internal node in it has two children — and the remainder recurses on the right); every non-root node in the tree, internal or leaf, holds a public/private key pair for a public-key encryption (PKE) scheme, and every member knows the private keys on the direct path from its own leaf to the root. To perform an update, a member generates fresh key pairs for every node on its own direct path to the root, deriving each level's key pair and the next level's seed from the previous level's seed via a pseudorandom generator (PRG), then for every node on its co-path (the sequence of siblings of direct-path nodes) encrypts the information needed to derive the new keys under that co-path node's public key — or, if that node is "blank" (holds no key because of a prior add/remove that left a gap), under the public keys of every node in that node's "resolution," the smallest set of non-blank nodes covering all leaves beneath it. The seed value at the root, produced this way, is the new update secret; it is fed to a higher-level protocol (via a PRF-based pseudo-random-number generator, PRF-PRNG, plus a per-user forward-secure authenticated encryption with associated data, FS-AEAD, construction) that derives symmetric encryption keys for the actual chat messages. Adding a member fills the first blank leaf, or grows the tree by one leaf if none is blank; removing a member blanks that leaf's direct path and truncates trailing blank structure. The paper's central claim about efficiency, inherited from the MLS design rather than proved fresh here, is that an update's packet size can be made logarithmic in group size n by encrypting only along the co-path (order log n ciphertexts) rather than separately to every other member (order n ciphertexts), which is the entire motivation for using a tree rather than running a pairwise double-ratchet protocol (the two-party predecessor to TreeKEM, underlying Signal and applications built on it) between every pair of group members.

Forward-secrecy defect found and proved. After a member processes an update, it must retain the private keys it used to decrypt that update's ciphertexts, because those same keys are needed to process future updates encrypted along overlapping co-paths. The paper proves that corrupting (compromising the full local state of) any group member other than the one that ran a given update can therefore reveal that update's secret in full, because the corrupted member's retained keys are exactly the keys the update secret was encrypted under. The paper shows this failure is structural, not incidental: it requires, in the best case, a logarithmic number of additional updates by other specific members before a compromise for the older update secret to become unrecoverable, and a linear number in the worst case depending on update order; if the sibling (in the tree) of the update's initiator never performs its own update, that update secret is never forward secret at all.

Fix (Modified TreeKEM). The authors replace the standard PKE used at each tree node with a new primitive, updatable public-key encryption (UPKE), whose public and secret keys change with every encryption and decryption respectively, so that after a node's secret key is used to decrypt one update, the post-decryption (evolved) key no longer reveals the plaintext of that decryption. This closes the forward-secrecy gap because the retained key a corrupted member holds after processing an update no longer suffices to recover that update's secret. The paper instantiates UPKE from the Computational Diffie-Hellman (CDH) assumption in the random-oracle model, building on a construction by Jost, Maurer, and Mularczyk (cited as [15]) and a suggestion from Konrad Kohbrok on the MLS mailing list (cited as [16]), and proves the resulting Modified TreeKEM achieves the strongest ("optimal," per the paper's own CGKA definition and matching what the MLS specification aims for) forward secrecy and post-compromise security (PCS, the property that a compromised member's security is eventually restored once the compromise ends and normal protocol use, i.e., updates, continues) simultaneously, at close to no added computational or communication cost over unmodified TreeKEM.

Ordering assumption. Every security definition and proof in the paper assumes the delivery server that queues protocol messages for offline members delivers CGKA (group-key) messages in the same order to every member of a session — the server may still drop or delay messages, and may deliver in different orders to different sessions/pairs of users, but within one session's view all members eventually see the same total order of protocol messages. This assumption is taken directly from the MLS draft specification, where it is stated explicitly, and the authors note it can in principle be realized without a centralized delivery service, by using a public bulletin board such as a blockchain protocol.

### Measured results
This is a theory paper: its results are cryptographic security proofs (reductions to standard hardness assumptions) rather than empirical performance measurements, and no benchmarked latency, bandwidth, or throughput figures with experimental conditions (hardware, node counts, trial counts) appear in the paper.
- Theorem 1 (non-adaptive security of TreeKEM): given a PRG that is (t_prg, epsilon_prg)-secure (an adversary running in time at most t_prg distinguishes the PRG's output from random with advantage at most epsilon_prg) and a PKE scheme that is (t_cpa, epsilon_cpa)-CPA-secure (secure against chosen-plaintext attack under the same time/advantage parameterization), TreeKEM is a (t, c, n, P, epsilon)-secure CGKA protocol for each of the three safety predicates P studied (tkm — TreeKEM's own exact predicate; pcs — post-compromise security only; fsu — forward secrecy with updates), with epsilon = 2·c·n·(epsilon_prg + epsilon_cpa), where n is group size and c bounds the number of adversary queries; this is a reduction bound, not a measured number, and requires the reader to instantiate the underlying PRG and PKE security parameters to obtain a concrete numeric value.
- Theorem 2 (non-adaptive security of Modified TreeKEM): an analogous bound for the UPKE-based fixed protocol, likewise stated as a reduction (the paper defers the full statement's exact constants to the theorem text/appendix; the underlying UPKE construction (Theorem 3) is proved CPA*-secure under the CDH assumption over a group G in the random-oracle model, again as a reduction, not a benchmark).
- Communication complexity claims are structural, not measured: the paper states MLS/TreeKEM packet sizes can in certain circumstances degrade to Omega(n) (linear in group size) rather than the intended O(log n) (logarithmic), and that this degradation "can, in principle, continue indefinitely and/or reoccur in any session once the right conditions are created" — this is a claim of a worst-case complexity regime the protocol can enter under adversarial or unlucky update ordering, not a number from a run of the protocol, and the paper does not give a numeric threshold, node count, or reproduction condition beyond this qualitative description.
- The adaptive-security bound the paper sketches (applying a reduction technique of Jafargholi et al.) is explicitly characterized by the authors as requiring block-cipher keys of size on the order of n·log(n) bits to apply meaningfully, which they state is "practically speaking, unrealistic" — recorded here as the authors' own characterization of their bound's looseness, not as a claim this corpus should treat as a usable parameter.

### Parameters
- Tree shape: left-balanced binary tree (LBBT) on n members — defined recursively so the root's left subtree is a maximal full binary tree on the largest power of 2 not exceeding n, and the right subtree is an LBBT on the remainder.
- Security-definition parameters in Theorem 1/2: t (adversary running time), c (number of oracle/protocol queries the adversary makes), n (group size) — all left as free variables in the reduction rather than fixed to specific tested values.
- Adaptive-security bound (sketched, not the paper's main proved result): requires block-cipher key size of order n·log(n) bits to be meaningful, per the authors' own statement, which they characterize as impractical.
- UPKE instantiation: built from the CDH assumption over a group G, in the random-oracle model (Theorem 3).

### Stated limitations
The paper's proofs (Theorems 1 and 2, for both TreeKEM and Modified TreeKEM) hold only against a non-adaptive adversary — one that must announce every corruption at the start of the security game rather than choosing corruptions adaptively based on protocol messages observed so far. The authors state the restriction stems from commitment issues with PKE ciphertexts common in the cryptographic literature, and that removing it without an exponential loss in the security bound is an open problem; they sketch, but do not complete, a proof technique (adapted from Jafargholi et al.) toward adaptive security, and explicitly characterize the resulting bounds as "still quite far from usable in practice."

The global-ordering-of-delivery assumption (same order of CGKA messages seen by every group member) is not removed or weakened in this work; the authors state that removing it would require either significantly weakening the adversary in the security definition, or making larger changes to TreeKEM's construction that they suspect would be impractical for real-world use, drawing an analogy to how stronger two-party ratcheting protocols end up requiring hierarchical identity-based encryption (HIBE) with arbitrary depth.

The paper explicitly sketches an attack (Section 8.3) showing that even TreeKEM variants with local-state leakage only (no active/malicious-insider corruption) fail to achieve what the authors call "ideal security" in a fully arbitrary, unordered network model: when two siblings in the ratchet tree (Bob and Charlie, with Alice a third party) each process a concurrent update from a different party, a leaked state from one sibling can let an adversary recover a group key the honest protocol design did not expect that party to be able to compute; the paper states this generalizes to all TreeKEM variants it is aware of, including the Kohbrok fix used elsewhere in this paper (which fixes the case only when the two concurrent updaters' direct paths intersect the third party's path at the same node) and Causal-TreeKEM.

The paper explicitly states it does not construct or prove security for a complete secure-group-messaging (SGM) protocol — only for the CGKA primitive that TreeKEM implements — and lists provable full-SGM security, more accurate PKI (public-key infrastructure) modeling, protection against active/malicious-insider attackers, metadata protection against a corrupt delivery server, deniability, post-quantum instantiations, and fully decentralized SGM as open research directions the paper does not resolve.

### Requirements it places on the rest of the system
- Every group member must retain, for each node on its own direct path, the most recently generated private key, because processing future updates whose co-paths overlap that path requires it; a system layer that tries to erase keys more aggressively than TreeKEM's own update logic requires would break the protocol's own correctness, not just its forward secrecy.
- The delivery mechanism (an untrusted server or equivalent) must deliver CGKA protocol messages in the same order to every member of a session, though it may drop, delay, or reorder relative to other sessions; a system that cannot guarantee this consistent per-session total order is outside the model this paper's security proofs (Theorems 1 and 2) apply to. The paper states this ordering could in principle be supplied by a public bulletin board such as a blockchain protocol, rather than a single centralized server, but the paper does not construct or evaluate such a substitution.
- The paper's own Section 8.5 (Decentralization) states MLS "is defined to operate using untrusted but centralized server infrastructure" — specifically a key server (for retrieving other members' initial public keys) and a delivery server (for queuing and ordering protocol messages) — and that this centralization reflects the standardization working group's corporate/organizational orientation rather than a cryptographic necessity; the authors state that naive ways to implement both servers atop a blockchain exist, but that it is unclear how to do so while also minimizing metadata leakage, latency, and the cost of writing to the blockchain, and what security guarantee such a substitution would actually provide — they identify fully decentralized SGM as an open, unresolved research direction, not a solved problem.
- The public-key infrastructure (PKI) that supplies members' initial keys is treated in this paper as an idealized functionality (any user can request a fresh public key for any user ID, and the corresponding private key is available only to that ID); the authors state real MLS deployments require an out-of-band mechanism to authenticate a peer's long-term signing key before trusting any key server response, and that this out-of-band step is the actual root of trust for the whole system — the paper's formal proofs do not model or verify that step.
- Attack availability caveat relevant to composing this mechanism with a partition-tolerant or asynchronous delivery layer: the Section 8.3 sketch shows that removing the global-ordering assumption (i.e., substituting a fully arbitrary/unordered network) breaks the paper's own non-adaptive security proof for TreeKEM and, per the authors, for every TreeKEM variant they are aware of at the time of writing — a decentralized design that cannot guarantee consistent per-session delivery order needs a different CGKA construction than TreeKEM as analyzed here.

### Contradicts
None found against other entries in this batch. Within its own scope the paper's central finding directly contradicts an informal claim commonly made about TreeKEM/MLS at the time — that the draft protocol already achieved standard forward secrecy — by proving TreeKEM (pre-fix) achieves only a strictly weaker property the authors formalize as "forward secrecy with updates" (fsu), not full forward secrecy.
