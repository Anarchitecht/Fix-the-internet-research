## [HUANG-ATC-12] Erasure Coding in Windows Azure Storage
**Citation:** Cheng Huang, Huseyin Simitci, Yikang Xu, Aaron Ogus, Brad Calder, Parikshit Gopalan, Jin Li, Sergey Yekhanin. "Erasure Coding in Windows Azure Storage." USENIX Annual Technical Conference (ATC), 2012.
**Retrieved:** full text via https://www.usenix.org/system/files/conference/atc12/atc12-final181_0.pdf
**Source URL:** https://www.usenix.org/system/files/conference/atc12/atc12-final181_0.pdf
**Domain:** C

### What it does
A Local Reconstruction Code (LRC) reduces the number of fragments a storage system must read to reconstruct one unavailable data fragment, while keeping storage overhead close to a standard Reed-Solomon erasure code. A (k, l, r) LRC divides k data fragments into l equal-size groups, computes one local parity per group from only that group's fragments, and computes r global parities from all k data fragments; total fragment count is n = k + l + r, giving storage overhead n/k = 1 + (l+r)/k. Reconstructing a lost data fragment reads only the other fragments in its own group plus that group's local parity — for the paper's (6,2,2) example, 3 fragments instead of the 6 a (6,3) Reed-Solomon code needs for the same task, because Reed-Solomon parities are each computed from all data fragments and cannot narrow the read to a subgroup.

Because LRC parities are not Maximum-Distance-Separable (MDS — the property that any k of n fragments suffice to reconstruct the original k), not every combination of up to l+r simultaneous failures is recoverable; the paper's coding-equation construction (Section 2.2.1) is chosen specifically to achieve the Maximally Recoverable (MR) property — decoding every failure pattern that is information-theoretically decodable, given the fixed choice of which fragments feed which parities, even though some patterns (e.g., losing all data fragments of one group plus that group's local parity, leaving only the two global parities to cover multiple lost data fragments) remain undecodable by construction, not merely unimplemented.

Windows Azure Storage (WAS) deploys the coding scheme inside its append-only stream layer: an extent is written as three full replicas, sealed once it reaches 1–3 GB and stops being written, then erasure-coded asynchronously and lazily in the background by the Stream Manager, after which the three full replicas are deleted. Every fragment of one coding group is placed in a distinct fault domain, so a single-fault-domain outage cannot take out more fragments than the code's stated fault tolerance assumes are independent.

### Parameters
- (k, l, r): LRC construction parameters — k data fragments split into l equal groups each producing one local parity, plus r global parities computed from all k data fragments; deployed production parameter set for storage cost 1.33x is (12, 2, 2), yielding n=16 total fragments
- Fault-domain cap: 20, the maximum fragment count considered in the paper's parameter sweep, set by the number of fault domains available per WAS storage cluster ("storage stamp")
- Reliability-model inputs: M (storage node count) = 400, S (storage per node) = 16 TB, B (network bandwidth per node) = 1 Gbps, ε (fraction of bandwidth allowed for repair traffic) = 0.1, T (failure detection + repair-trigger time) = 30 minutes
- Extent size at which an append-only extent is sealed and becomes eligible for erasure coding: 1 GB to 3 GB
- Replica count before erasure coding: 3 full copies, deleted once erasure coding of the sealed extent completes successfully

### Stated limitations
LRC is not Maximum-Distance-Separable, so it needs strictly more total parity fragments than an MDS code offering the same fault tolerance would need in principle; the paper states this explicitly as the reason LRC "requires higher storage overhead for the same fault tolerance" relative to Reed-Solomon. LRC is optimized specifically for reconstructing lost data fragments, not lost parity fragments: reconstructing a global parity in the (12,2,2) deployed configuration needs as many as 12 fragments, the same cost a plain Reed-Solomon reconstruction would need, and the paper states this tradeoff is deliberate because parity loss (triggered only by disk, node, or rack failure) happens off the critical path of serving client reads, unlike data-fragment reads. The Markov reliability model in Section 3.1 assumes independent failures; the paper states correlated failures do occur in practice and that the model "can be readily extended" to add non-adjacent-state transitions to capture them, but does not itself report a correlated-failure analysis or its resulting MTTF figures. The comparison to alternative modern storage codes (Weaver, HoVer, Stepped Combination) is stated to hold specifically for WAS's design goal of fast data-fragment reconstruction; the paper concedes those codes reconstruct lost parities more efficiently than LRC does. Aggressive over-reading (fetching more fragments than the minimum and taking the first arrivals) is stated to help hide slow-fragment latency for small I/O but to actively worsen latency for large I/O, because large-I/O reconstruction is bandwidth-bound rather than straggler-bound — a mechanism-dependent limitation, not a universal one. Techniques that read from more fragments but transfer less data per fragment (the paper cites two specific systems for this alternative) are stated, per those systems' own reported numbers, to achieve only around 20–30% I/O and bandwidth savings, "much" less than LRC's reduction, which the paper offers as its comparison rather than an independent re-measurement in this paper.

### Requirements it places on the rest of the system
Every fragment belonging to one coding group must be placed in a distinct fault domain; the reliability figures in Table 1 and the correlated-failure caveat both depend on this placement holding, since a shared fault domain across group members would violate the model's independence assumption and invalidate the stated MTTF. The stream layer must support an asynchronous, off-the-critical-path background process (the Stream Manager) that scans sealed extents and schedules erasure coding without blocking client writes, and must keep the three full replicas available and undeleted until the coded fragments are validated (the paper states failed erasure-coding operations are aborted, leaving the full replicas intact, and are retried later). On-demand reconstruction for a client read requires a coordinator node capable of reading the minimum needed fragment set (3 of 16 for the deployed (12,2,2) configuration reconstructing a data fragment) with low enough latency to meet customer service-level agreements; the paper's own production measurements show this becomes bandwidth-bound rather than straggler-bound for large I/O, so the network capacity per storage node (1 Gbps in this deployment) directly bounds achievable reconstruction latency. Detecting failures and triggering repair within a bounded time T is required for the reliability model's repair-rate terms (ρ₆ through ρ₉) to hold at the stated values; the paper sets T=30 minutes as the dominant term in single-failure repair rate, meaning any system adopting this scheme needs a failure-detection subsystem operating on that timescale to reproduce the stated MTTF.

### Contradicts
None found within this batch. The paper's own comparison in Section 6 states that prior deployed erasure-coded storage systems at Facebook and Google "do not explore alternative erasure coding designs other than Reed-Solomon codes," positioning this as a gap this paper closes rather than a disagreement with a specific prior measurement.
