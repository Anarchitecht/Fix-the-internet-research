## [BACK-HASHCASH-02] Hashcash - A Denial of Service Counter-Measure
**Citation:** Adam Back. "Hashcash - A Denial of Service Counter-Measure." Self-published technical report, 1st August 2002.
**Retrieved:** full text via http://www.hashcash.org/papers/hashcash.pdf
**Source URL:** http://www.hashcash.org/papers/hashcash.pdf
**Domain:** I

### What it does
Hashcash lets a server force a client to spend a chosen amount of computation before the server accepts a request, so that a resource with no per-use charge (email delivery, an anonymous remailer, a TCP connection slot) cannot be consumed at unlimited rate by one sender. The paper defines a cost-function abstractly as a pair of routines: MINT, run by the client, which finds a token expensive to produce, and VALUE, run by the server, which checks the token cheaply. The hashcash construction of MINT is: given a service name string s that identifies the target service (a host name or an email address, so a token minted for one service cannot be replayed against another), pick a random string x, and search for an x such that a public hash function applied to (s, x) produces an output whose leading b bits match a fixed target (originally the hash of the service name, later simplified by Hal Finney and Thomas Boschloo to the fixed all-zero string, which the paper states halves verification cost). VALUE recomputes the hash of (s, x) once and checks the same b leading bits. Because the only known algorithm for finding such an x is brute-force search, and each trial hash independently has a 2^-b chance of matching a b-bit target, minting is expensive in the leading-bit count b while verification always costs exactly one hash evaluation, and this asymmetry is the whole rate-limiting effect. Hashcash is non-interactive (the client chooses its own random start value with no challenge from the server, so it works over one-way channels such as email) and trapdoor-free (the server holds no secret that lets it mint tokens more cheaply than a client can, unlike a known-solution client-puzzle scheme). The server keeps a database of spent tokens to reject reuse, bounded by embedding a timestamp in the service-name string so expired entries can be discarded. An interactive variant lets the server issue a challenge string and, combined with a keyed message authentication code sent to the client instead of stored server-side state, defends TCP connection-slot exhaustion (a hashcash-cookie, generalizing the syn-cookie) by requiring a computed token before the server commits any per-connection state.

### Measured results
None usable. The paper is a construction and classification paper; it states it "describes initial experience from experiments using hashcash" but reports no run count, hardware, wall-clock time, or deployment-scale figure for that experience anywhere in the retrieved text, so no number from it meets the experimental-conditions requirement.

### Parameters
- b: the number of leading bits of the hash output that must match the target (the work factor). The paper does not state a recommended numeric value of b for the non-interactive hashcash construction itself; it treats b as adjustable per deployment and, for the interactive variant, as dynamically adjustable by the server in response to measured CPU load (Section 4.1).
- Start-value length |x|: the paper states |x| must be long enough that the probability of two clients independently reusing the same start value is negligible, and states a specific bit length "should be enough even for a busy server," but the digit string for that recommended length is corrupted in the extracted text (a font-encoding artifact) and is not recorded here because it cannot be verified against the source PDF.
- Spent-token database retention: bounded by embedding a timestamp in the service-name string and discarding database entries once an expiry period elapses; the paper states the expiry period should account for clock inaccuracy, computation time, and transmission delay, without giving a numeric value.
- Time-lock-puzzle variant (an alternative fixed-cost, non-parallelizable cost-function the paper also presents, built on Rivest-Shamir-Wagner time-lock puzzles): the author recommends not deploying it with a modulus below 768 bits and states RSA moduli of 512 bits had by publication been factored by two independent groups; the author further suggests changing the public modulus "every hour or so," which the paper itself flags with "say," marking it as a suggestion rather than a derived or measured figure.

### Stated limitations
Hashcash's non-interactive form supplies no defense against a precomputation attack: an adversary with a year of spare compute can mint tokens in advance, all valid for one future date, and spend them in a burst on that date, an attack the interactive form is immune to because the server's challenge cannot be predicted in advance. The paper's proposed mitigation (mixing in a slowly changing, unpredictable public beacon value, such as a lottery result) is presented as a possible fix, not one the paper implements or measures. The double-spend database requires the server to hold state per accepted token until its embedded timestamp expires; the paper does not bound how large that database grows under high request rates. The paper states as an open problem that no known non-interactive, publicly auditable, fixed-cost (rather than probabilistic) cost-function exists with verification as cheap as hashcash's, and likewise states as open whether any non-parallelizable cost-function exists with verification cost in the same order of magnitude as a symmetric-key construct like hashcash. The interactive hashcash-cookie mechanism allocates connection slots in proportion to each client's available CPU resources, which the paper states biases outcomes toward clients with faster processors. The author's own assessment (attributed to Back, not a derived or measured claim) is that non-parallelizable cost-functions give only marginal added resistance to distributed denial-of-service compared with hashcash, because an attacker who already controls many network-connected nodes can have each node run the ordinary protocol independently rather than sub-dividing one puzzle, and that this equally defeats per-connection fairness throttling regardless of parallelizability.

### Requirements it places on the rest of the system
A deployment needs a server-side store, keyed by spent token, that persists at least as long as the timestamp-derived expiry window it uses to reject double-spent tokens; without an accurate, loosely-synchronized clock across server and client, the timestamp-based expiry either rejects valid recent tokens or fails to bound database growth. The service-name string bound into each token must be chosen so that it is unique per protected resource (a specific host name, mailbox address, or connection identifier), or tokens minted against one resource can be replayed against another. Any component that wants graceful throttling under load (the paper's interactive hashcash and hashcash-cookie designs) needs a live measurement of current server CPU or connection-slot load, since the mechanism only produces fair, load-proportional degradation if the required bit count b is adjusted from that measurement. A hashcash-cookie deployment additionally requires a server-held symmetric MAC key shared across the server's own instances of the check, since the server sends a MAC of the connection state to the client instead of storing that state itself, and any component verifying the returned token must hold that same key.

- Rivest, Shamir, Wagner, "Time-lock puzzles and timed-release crypto," MIT/LCS/TR-684, 1996 -- foundational (source of the time-lock-puzzle-based fixed-cost, non-parallelizable cost-function this paper presents and evaluates as an alternative to hashcash).
- Dean, Stubblefield, "Using client puzzles to protect TLS," USENIX Security 2001 -- competing (the paper this one cites as the one deployed implementation of a client-puzzle system integrated into a real protocol, TLS).

- Dai, "b-money," 1998 -- foundational (this paper states hashcash was adopted as the minting mechanism in Dai's b-money electronic-cash proposal, a design later cited as a direct precursor to Bitcoin's proof-of-work).
