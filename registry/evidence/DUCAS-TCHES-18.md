## [DUCAS-TCHES-18] CRYSTALS-Dilithium: A Lattice-Based Digital Signature Scheme

**Citation:** Léo Ducas, Eike Kiltz, Tancrède Lepoint, Vadim Lyubashevsky, Peter Schwabe, Gregor Seiler, Damien Stehlé. "CRYSTALS-Dilithium: A Lattice-Based Digital Signature Scheme." IACR Transactions on Cryptographic Hardware and Embedded Systems (TCHES) 2018(1), 238-268. DOI: 10.13154/TCHES.V2018.I1.238-268.
**Retrieved:** full text via https://eprint.iacr.org/2017/633.pdf
**Source URL:** https://eprint.iacr.org/2017/633.pdf
**Domain:** E

### What it does
Dilithium is a digital signature scheme (a mechanism letting a holder of a private key produce, for any message, a value that anyone holding the matching public key can check was produced by that key) whose unforgeability rests on the hardness of two lattice problems, Module Learning With Errors (MLWE, a generalization of the Learning With Errors problem to structured polynomial-ring modules) and Module Short Integer Solution (MSIS). It differs from earlier compact lattice signature schemes (NTRU-GPV, BLISS) by avoiding discrete Gaussian sampling entirely: those schemes draw secret randomness from a discrete Gaussian distribution during signing, and the paper cites three separate side-channel results ([BHLY16], [EFGT17], [PBY17]) showing that securely implementing that sampling step in constant time is error-prone in practice. Dilithium replaces Gaussian sampling with rejection sampling over uniform distributions, which the paper states is "easily implementable in constant-time" — an implementation where the sequence of operations executed does not depend on secret data, closing the timing side channel.

The scheme follows the "Fiat-Shamir with Aborts" paradigm (originating in Lyubashevsky's 2009 scheme). Key generation produces a public matrix A and a public value t = As1 + s2, where s1 and s2 are small-coefficient secret vectors; the public key stores only the high-order bits of t (dropping the low d=14 bits per coefficient), shrinking the public key. To sign a message M, the signer samples a masking vector y, computes w1 as the high-order bits of Ay, derives a challenge c = H(M || w1) via a hash function modeled as a random oracle, computes a candidate response z = y + c·s1, and restarts the entire signing attempt (rejection sampling) whenever z or a related bound exceeds fixed thresholds (γ1, γ2, β) — a step that leaks no information about the secret because an accepted z's distribution is independent of s1, at the cost of a variable number of signing attempts per message signed. Because the public key withholds the low bits of t, the verifier cannot recompute w1 exactly from a candidate signature (z, c) alone; the signer therefore transmits a small "hint" — the positions where dropped low-order bits of c·t0 would have caused a carry into the high-order bits — as extra signature bytes, letting the verifier reconstruct the needed high bits without full knowledge of t.

### Parameters
Four named parameter sets (weak, medium, recommended, very high), all sharing modulus q=8,380,417 and coefficient-drop parameter d=14 and challenge weight (number of nonzero coefficients in c) 60, and each varying: γ1=(q-1)/16=523,776 and γ2=γ1/2=261,888 fixed across all four sets; module dimensions (k,l) = (3,2) weak, (4,3) medium, (5,4) recommended, (6,5) very high; secret-coefficient bound η = 7, 6, 5, 3 respectively; rejection-sampling bound β = 375, 325, 275, 175; hint-count bound ω = 64, 80, 96, 120; expected number of signing-loop repetitions (derived from the scheme's own Eq. 5) = 4.3, 5.9, 6.6, 4.3. The paper states signing was benchmarked with a 32-byte message. The paper states an alternative parameterization sampling from a Gaussian distribution instead of uniform could save roughly 10-15% in signature size, but states this "does not justify the added complexity of securely implementing the scheme" — a value judgment attributed to the authors, not a measured constraint.

### Stated limitations
The security reduction (Dilithium's unforgeability reduces to the hardness of MLWE and MSIS) holds in the classical random oracle model via the forking lemma, and the paper states explicitly that "the reduction does not transfer over to the quantum setting" because the forking lemma's rewinding step has no known quantum analogue; the paper argues around this by introducing an intermediate problem (SelfTargetMSIS) that has a tight reduction to unforgeability under quantum reductions, but this reduction to SelfTargetMSIS from the base MSIS/MLWE problems is itself non-tight in the classical random oracle model. The paper states its own classical reduction is non-tight and offers only an empirical, not a proof-theoretic, argument that this does not matter in practice (citing that Schnorr and GQ signatures, which have similarly non-tight reductions, set parameters ignoring the non-tightness with no known resulting attack). The paper states it does not know whether the sketched attack against l-infinity-norm SIS (its Appendix C.3) is optimal, describing an unstudied combinatorial variant that might improve the attack, and explicitly states "we leave [this] to future work" rather than resolving it. It states there exist no constant-time implementations of the Gaussian-sampling-based competing schemes (NTRU-GPV, BLISS) "to the best of our knowledge," citing one contemporaneous partial fix ([MW17]) that it states still uses side-channel-vulnerable lookup tables. Benchmarked signing time is variable per invocation (median differs materially from average, e.g. 1,804,738 vs. 2,326,829 cycles at the recommended parameter set) because rejection sampling forces a variable, secret-dependent-in-distribution-only number of loop iterations; this variability is by design (it is what removes the discrete-Gaussian side channel) but means worst-case signing latency is not a fixed constant.

### Requirements it places on the rest of the system
Verifying a Dilithium signature requires the verifier to reconstruct the high-order bits of Az-ct using the signer-supplied hint bytes, so any transport or storage layer carrying a Dilithium signature must preserve those extra hint bytes alongside (z, c) — dropping them makes verification impossible, not merely less efficient. The scheme's hash function H, modeled as a random oracle mapping (message, w1) to a challenge c, must be instantiated with a function with no exploitable algebraic relationship to the underlying MLWE/MSIS structure; the paper's own security argument (the SelfTargetMSIS problem) depends on assuming no such relationship exists, which is an assumption about the hash function choice, not a proof. The scheme requires an implementation that runs signing and verification in constant time to realize its side-channel-resistance goal; the paper achieves this design property but explicitly does not claim to have audited hardware-level side channels (power, electromagnetic) beyond timing. Any protocol composing Dilithium as a component needs to budget for a variable per-signing-attempt cost (rejection sampling: an expected 4.3 to 6.6 repetitions depending on parameter set) rather than a single fixed-cost signing operation, and needs to carry the larger of the two combined sizes (public key + signature, 1,472 + 2,701 = 4,173 bytes at recommended parameters) versus the alternative post-quantum schemes the paper benchmarks, when key and signature are both transmitted (the paper names TLS certificate chains as the motivating case for minimizing this sum).
