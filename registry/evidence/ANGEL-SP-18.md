## [ANGEL-SP-18] PIR with compressed queries and amortized query processing
**Citation:** Sebastian Angel, Hao Chen, Kim Laine, Srinath T. V. Setty. "PIR with compressed queries and amortized query processing." IEEE Symposium on Security and Privacy, 2018. Pages 962-979. DOI 10.1109/SP.2018.00062.
**Retrieved:** full text via https://eprint.iacr.org/2017/1142.pdf
**Source URL:** https://eprint.iacr.org/2017/1142.pdf
**Domain:** G

### What it does
This paper (the system is called SealPIR in the text, though the paper's own title does not use that name) makes single-server computational Private Information Retrieval (PIR) cheaper on two axes: the size of the query a client sends, and the per-query computation a server performs when many queries from the same client arrive together. Ordinary computational PIR built on Fully Homomorphic Encryption (FHE), of which the paper's baseline XPIR is an instance, requires the server to hold the database as a d-dimensional hyperrectangle of ciphertext-encrypted elements; the client's query, under the prior approach (Stern's protocol, which XPIR implements), must contain one ciphertext per candidate position along one dimension, so a database of n elements arranged with dimension d needs roughly the d-th root of n ciphertexts in the query. SealPIR replaces this multi-ciphertext query with a single compressed ciphertext plus a server-side procedure called EXPAND: using a technique built on ciphertext substitution (a property of the underlying FHE scheme, here the SEAL library's implementation of the Fan-Vercauteren, FV, encryption scheme), the server homomorphically expands the client's one compressed ciphertext back into the same d ciphertexts XPIR would have required, without the client ever having to send them explicitly. This shrinks client-to-server query bandwidth without changing what the server ultimately computes over. The second technique, probabilistic batch codes (PBC), lets a server answer several PIR queries from the same client (for a batch of k desired elements) using less total computation than running k independent single-element PIR queries. A PBC encodes the n-element database by replicating each element into w candidate positions ("buckets") chosen by w independent hash functions (a construction called Cuckoo hashing when the specific reverse-hashing allocation strategy of Cuckoo hashing is used to place elements into buckets), producing m = w times n total encoded elements across b buckets; to retrieve k desired elements, the client maps its k indices to b buckets using the matching consumer-side hashing procedure (this mapping can fail, returning an explicit failure marker, with a computable failure probability) and issues one PIR query per bucket rather than one per original element, and the server runs standard single-query PIR independently on each bucket.

### Measured results
All measurements on Microsoft Azure H16 server instances (16-core 3.6 GHz Intel Xeon E5-2667, 112 GB RAM) and F16s client instances (16-core, 2.4 GHz Intel Xeon E5-2673, 32 GB RAM), Ubuntu 16.04, compiled with Rust nightly 1.25, across three Azure data centers (West US, South India, West Europe). Each experiment run 10 times with averaged results; standard deviations reported as under 10% of the mean in every case. The paper reports hardware as multi-core (16-core) instances but does not state explicitly, for the microbenchmarks in Figure 9, whether the implementation used a single thread or multiple threads of that 16-core machine; this detail could not be verified from the text.

Microbenchmarks (Figure 9), 288-byte database elements, FHE ciphertext polynomial degree 2048 with 60-bit coefficient modulus, comparing XPIR (dimension d=2 and d=3) against SealPIR (d=2):

Query size reduction over XPIR is 274 times at d=2 and 63 times at d=2-vs-d=3 comparison basis, for larger databases. SealPIR's EXPAND procedure adds 11% to 38% server CPU overhead relative to answering a query vector directly (no query compression), but keeps total server answer time comparable to XPIR at the same database size.

Response-time measurements deploying the PIR server in Azure US West and clients under four network conditions, retrieving one 288-byte element, compared against scp (secure copy, downloading the whole database) as a naive-PIR baseline: intra-datacenter (about 3.4 Gbps, measured with iperf), inter-datacenter (client in South India, about 800 Mbps), home network (client in South India, rate-limited to 20 Mbps via the Linux tc traffic-control utility, chosen to match the reported 18.7 Mbps mean US download speed from a cited Akamai report), and mobile network (client in South India, rate-limited to 10 Mbps via tc, chosen to approximate reported average US mobile carrier data speeds). At intra-datacenter bandwidth, scp gives the lowest response time; SealPIR is competitive with both XPIR variants except at the largest tested database size (2^22 elements), where SealPIR falls behind because its EXPAND optimization forces a small plaintext modulus at that size, increasing the number of plaintexts needed. At lower bandwidth (home and mobile conditions), SealPIR's lower network consumption yields up to a 42% reduction in response time relative to the compared schemes.

Throughput (Figure 11), server in Azure US West, 4 to 256 concurrent clients across South India and EU West, database of 2^20 elements of 288 bytes each, experiment designed so the server's CPU or WAN link (not the client or a specific inter-datacenter link) is the bottleneck: XPIR with d=2 saturates at 9 requests/second; SealPIR saturates at 7 requests/second (23% lower throughput than XPIR d=2 in this comparison); against XPIR with d=3, SealPIR achieves about 50% higher throughput. Both SealPIR and XPIR achieve more than 20 times the throughput of naive PIR via scp, because scp's bottleneck is network bandwidth rather than CPU.

Probabilistic Batch Code (PBC) benchmark (Figure 12), database of 2^20 elements, 288 bytes each, SealPIR (t=2^20) as the underlying single-query PIR library, comparing mPIR (SealPIR plus PBC with Cuckoo hashing, w=3 hash functions, b=1.5k buckets) against Pung's own multi-retrieval scheme, at batch sizes k = 16, 64, 256: at k=256, mPIR gives a 2.6 times reduction in server CPU cost for answering queries compared to Pung's scheme, and a 40.5 times reduction compared to running k independent single-query PIR instances. mPIR is 6 times more network-efficient (combined upload and download) than Pung's scheme at the measured batch sizes. mPIR's estimated Cuckoo-hashing failure probability is about 2^-40 for k > 200 (closer to 2^-20 for smaller k), lower than Pung's stated 2^-20 failure probability.

End-to-end case study porting SealPIR and mPIR into the Pung private-messaging system (256K simulated users, 32 real clients, remainder simulated by pre-populating the server database with random messages, closed-loop round-based operation), each client sending one message and retrieving k messages per round, k up to 256: at k=64, the modified system ("Pung+MS," using both mPIR and SealPIR) achieves 3.1 times the throughput, in messages per minute, of the original Pung implementation. Per-client network cost for one round at k=16 falls from 279 MB (original Pung) to 7.7 MB (Pung+MS), a reduction the paper states as over 36 times.

### Parameters
- FHE ciphertext polynomial degree N: 2048, with 60-bit ciphertext coefficient modulus q (SEAL uses q = 2^60 - 2^18 + 1; XPIR uses q = 2^61 - i times 2^14 + 1 for various i), chosen following XPIR's published security estimates based on the Albrecht-Player-Scott hardness analysis.
- Database element size: 288 bytes throughout the main evaluation, chosen to match the message size used by the Pung system in the case study.
- Plaintext modulus t: 2^23 as the default SealPIR setting (a larger t lowers network and computation cost but risks decryption failure from excess noise growth, so t is lowered in some experiments, e.g. to 2^20 for the PBC benchmarks, to guarantee correct decryption).
- XPIR packing parameter alpha: 14 elements packed per XPIR plaintext, chosen to have roughly the same effect as SealPIR's t=2^23 setting for 288-byte elements under the paper's security parameters.
- PIR dimension d: tested at d=2 and d=3 for XPIR; SealPIR evaluated at d=2 in the main comparisons.
- PBC parameters (Cuckoo-hashing variant): w=3 independent hash functions, b=1.5k buckets for a batch size of k, following prior empirical analysis of Cuckoo hashing failure rates cited from other work.
- Batch size k for multi-query PIR: tested at 1 (no amortization baseline), 16, 64, and 256.

### Stated limitations
The paper states that determining the exact failure probability and constant factors of Cuckoo hashing analytically remains an open problem in the literature it cites, so its own failure-probability figures (2^-40 for k > 200, 2^-20 for smaller k) are described as empirical estimates from prior work rather than proven bounds. The paper states that under a malicious (not merely semi-honest) server, the server controls where database elements are placed and so can deliberately place specific elements at index combinations that make GenSchedule always fail for a client requesting that combination, opening what the paper calls a "selective failure" attack analogous to one already known in single-query PIR; the paper states this requires additional mechanisms (making the client's externally visible reaction independent of query success or failure) to convert an information-leaking failure into a mere availability failure, but the paper does not implement or measure such a mechanism. The paper states SealPIR falls behind XPIR in response time specifically at the largest tested database size (2^22 elements) under high-bandwidth (intra-datacenter) conditions, because its EXPAND optimization there forces a smaller plaintext modulus and more plaintexts. The paper states, as future work rather than a solved problem, that CPU costs could be further reduced using a matrix-multiplication aggregation technique from prior work (Beimel et al.) not implemented in this paper, and that PBC bucket-allocation strategies studied here are drawn from online load-balancing literature (elements arriving one at a time) rather than from strategies specific to the offline setting (all elements available at once) that PBC actually operates in, leaving offline-optimized allocation as an open direction.

### Requirements it places on the rest of the system
The client must already know, before issuing a query, which numeric index or indices in the database it wants; the paper states three alternative external mechanisms an application must supply to produce that index (a Bloom filter shared out of band, as in the Pung system; a PIR-by-keyword scheme; or the client independently simulating the server's Cuckoo-hashing placement given a shared pseudorandom seed), none of which SealPIR or the PBC construction itself provides. Multi-query batching (mPIR) requires the client and server to agree in advance on the batch size k and the hashing parameters (w, b) used to construct and consume the PBC; a client that does not know these parameters cannot correctly map its desired indices to buckets. The scheme's privacy guarantee (the server cannot tell which index was retrieved) holds under a semi-honest (honest-but-curious) server for the analysis given; the paper states that a fully malicious server breaks a distinct property (whether a client's chosen batch of indices can be retrieved at all) unless a system built on this scheme separately adds the selective-failure countermeasure described above. mPIR's failure mode (GenSchedule returning an explicit failure marker for a chosen index set) is visible to the client before any PIR query is issued, so a system relying on mPIR must have a defined recovery behavior (retry with different indices, retrieve fewer elements, or otherwise) built into its application logic, since the paper does not mandate a single response to a schedule failure.

### Contradicts
The prior-pass claim (recorded in the target-retrieval registry's rationale) that this paper reports a throughput of "102 MB/s" with no attached experimental condition is not supported anywhere in this paper's text: no figure or table in the paper states a MB/s throughput number at all. The paper's own throughput results are stated in requests per second (7 for SealPIR, 9 for XPIR d=2, both saturating at a 2^20-element, 288-byte-element database under a specific multi-client, multi-datacenter deployment) or in messages per minute (Pung case study), never in MB/s; the "102 MB/s" figure attributed to this paper should be treated as unverified against the primary source and possibly misattributed from a different PIR paper. No other cross-corpus contradiction found.
