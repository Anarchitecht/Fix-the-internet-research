## [LEVIEN-USS-98] Attack-Resistant Trust Metrics for Public Key Certification
**Citation:** Raph Levien, Alexander Aiken. "Attack-Resistant Trust Metrics for Public Key Certification." 7th USENIX Security Symposium, 1998.
**Retrieved:** full text via https://www.usenix.org/legacy/publications/library/proceedings/sec98/full_papers/levien/levien.pdf
**Source URL:** https://www.usenix.org/legacy/publications/library/proceedings/sec98/full_papers/levien/levien.pdf
**Domain:** F

### What it does
The paper defines a trust metric as a function that decides, for a given client key (the source) and a target name/key binding, whether to accept that binding, computed from a graph of digitally signed certificates (a certificate is a signed statement binding a name to a key, made by one key about another). It gives an analytical framework for comparing trust metrics by how many keys or certificates an attacker must control to force acceptance of a false binding, proves a best-case theoretical limit no trust metric can beat, and presents a maximum-network-flow-based metric that meets that limit.

Mechanism, threat model: two attack types are distinguished. A node attack assumes the attacker fully compromises a key (equivalent to stealing its secret key), letting the attacker issue arbitrary certificates from it. An edge attack is weaker: the attacker cannot compromise a key but can trick its legitimate owner into signing one specific bad certificate (one edge in the certification graph), for instance by social-engineering a legitimate keyholder into vouching for an untrustworthy party. A trust metric can be tuned to resist one attack type more than the other; the paper's specific network-flow construction resists edge attacks far more than node attacks.

Mechanism, the theoretical limit (Section 5): define d as the minimum number of direct certifiers (predecessors) held by any key the trust metric is willing to widely accept. Because a node attack lets the attacker fabricate an entire subtree of certificates behind a single compromised key, no trust metric can be immune to an attack on d keys or more (the attacker simply compromises all d certifiers of some already-accepted key, then certifies an arbitrary target through them). For edge attacks, the paper shows the analogous best-case bound is beta*d/2, where beta (<=1, defined as the ratio between the actual number of second-degree predecessors of some widely-accepted key and d^2, the maximum possible) captures how much the certification graph's inbound paths overlap near any given widely-accepted node; beta is stated to be near 1 for random graphs and "hoped to be fairly high (greater than 0.5, say)" for realistic certification graphs, though the paper does not measure beta on any real certificate graph.

Mechanism, the network-flow trust metric that meets this bound (Section 6): treat the certificate graph as a flow network from source s (the client key) to target t (the key being verified), and accept the binding if the maximum flow between s and t is at least 1. Rather than giving every node a uniform capacity (which, for a target flow of 1, would require every node's capacity set to 0.5, meaning an attacker controlling any two well-placed nodes can already force acceptance), the metric assigns each node n a capacity C_(s,t)(n) = max(f_s(dist(s,n)), g_t(dist(n,t))), where dist(s,t) is the shortest-path hop count between source and target and f_s, g_t are functions of hop-distance from source and target respectively, tunable to weight nodes near the source (or target) with higher capacity than nodes farther away. One instantiation given in the paper (tuned to resist node attacks rather than edge attacks) sets f_s(1) = max(1/d, 1/|succ(s)|), f_s(l>=2) = 1/d, and g_t(l) = 1/d for all l, where succ(s) is the set of s's direct successors; these values are derived to make the network's maximum flow equal 1 for most (source, target) pairs while guaranteeing no more than d nodes anywhere in the graph carry capacity greater than 1/d. Raising capacities specifically near the source and target (rather than uniformly) is stated by the authors to have only a small effect on node-attack resistance (because the uniform-capacity metric is already close to the theoretical bound for node attacks) but to substantially improve edge-attack resistance, from requiring d edges to requiring beta*d/2.

### Measured results
This is a theoretical/analytical paper: its results are proved bounds and a comparison table of attacker resource requirements under different metrics, not measurements from an implemented system or a dataset. No experiment, simulation, testbed, node count, or runtime is reported anywhere in the retrieved text.

| Trust metric | Nodes needed for a successful node attack | Nodes needed for a successful edge attack | Edges needed for a successful edge attack |
|---|---|---|---|
| Shortest path (accept the target reachable by the shortest certificate chain) | 1 | 1 | 1 |
| Maurer (probabilistic reachability metric, simplified to a single edge type) | 1 | 1 | d |
| Reiter & Stubblebine (bounded vertex-disjoint paths) | d | d | d |
| Maxflow (uniform node capacities) | d | d | d |
| Maxflow-edge (the paper's own capacity construction, weighted toward source/target) | d | beta*d/2 | beta*d/2 |
| Best case (proved bound; no metric can exceed this) | d | beta*d/2 | beta*d/2 |

The paper offers one concrete illustrative example, not a general experiment: for d=3 in a small hand-drawn graph (Figure 5), f_s(1)=0.5, f_s(l>=2)=0.333, g_t(l>=1)=0.333; the paper states that with uniform capacities set at 0.5 (the level needed for a maxflow of 1), "most attacks on two nodes succeed," whereas with source/target-weighted capacities in the same graph "the only successful two node attack is on {keyB, keyE}." For a numeric illustration of the theoretical bound's practical stakes, the paper states that for d=10 (each key certified by at least 10 others) and beta=0.5, an attacker needs 10 keys for a node attack but 50 keys for an edge attack under the maxflow-edge metric — this beta=0.5 figure is explicitly a plugged-in illustrative value, not a measured one (the paper elsewhere states "for realistic certification graphs" beta is merely "hoped to be" above 0.5).

The paper additionally reports a structural fact about one real certificate graph, cited from an external source rather than measured by the authors themselves: about 35% of the keys in the strongly-connected subgraph of the PGP web-of-trust key database (cited from N. McBurnett's "PGP web of trust statistics," 1996) have exactly one predecessor, meaning d=1 is the effective bound for that graph and no trust metric can offer any attack resistance advantage over a single-signature requirement there.

### Stated limitations
The framework's central assumption is that a good trust metric should accept most good name/key bindings; the authors state explicitly this assumption "is not always valid" — for high-security applications wanting a "very restricted guest list," a metric that rejects many good bindings may be preferable, and the paper's optimality results do not apply to that regime. The framework's second assumption is that the name space is opaque (no information can be extracted from the name string itself); the paper notes real names often have exploitable structure but states this is not modeled. The authors state a trust metric of any kind is "not particularly helpful" on certificate graphs like the PGP web of trust, where about 35% of keys have only one predecessor (d=1), because a source key must then choose between rejecting a large fraction of the graph or being highly vulnerable to a single-key forgery — the metric's protection scales with d, and low-d graphs give it almost nothing to work with. The paper explicitly leaves open a comparison between its maxflow-based metric and Reiter & Stubblebine's bounded-vertex-disjoint-paths metric on the question of whether a path-length bound improves resistance; it argues analytically (not empirically) that it does not, and states the argument's validity depends on the assumption that both compared metrics accept most good keys, which may not hold for metrics that intentionally accept only a fraction of good keys. The paper explicitly ends without validating the metric on any deployed or prototype certificate infrastructure, stating "only practical experience with a prototype system can determine whether this tradeoff is worthwhile," referring to the tradeoff between attack resistance and the increased certification burden the mechanism imposes on every key's owner.

### Requirements it places on the rest of the system
Requires every key that will be widely accepted to be certified by at least d other keys, where d directly sets the minimum number of keys or certificates an attacker must control; the paper states this outright as a precondition ("for an attack-resistant key infrastructure based on trust metrics to be viable, the owner of every key must be willing and able to have a number of people to certify it") and states resisting attacks "increases the cost of certification" for every participant, not merely the operator. Requires a directed graph of signed certificates reachable from the verifying client's own key as the sole input to the flow computation; the mechanism itself supplies no way to discover, revoke, or freshness-check certificates, so an external certificate-distribution and revocation system must supply and maintain that graph. Requires the client (source) to already hold its own key as a fixed, trusted starting point (s in the flow formulation) — the metric evaluates trust in a target relative to one already-trusted source, and does not itself bootstrap that source's own trustworthiness. Requires whoever tunes f_s and g_t to know or estimate the graph's realistic d and beta, since the paper's own worked numeric comparisons (d=10, beta=0.5) are stated as illustrative choices rather than values derived from a specific measured deployment; deploying the metric without measuring these two figures on the target certificate population means the attacker-resource-requirement claims in the comparison table are unverified for that population.

### Contradicts
None found within this corpus. On attribution: the paper's own comparison table shows the Reiter & Stubblebine bounded-vertex-disjoint-paths metric requiring d nodes/edges for either attack type — identical to the paper's own uniform-capacity maxflow metric and strictly worse than the paper's own source/target-weighted maxflow-edge construction (beta*d/2) — which is a direct numeric disagreement with any claim that bounding path length improves attack resistance over unbounded maximum flow; the paper states this itself as its own analytical finding, not as a disagreement with an external source, since Reiter & Stubblebine's original paper is a comparison target here rather than a source of a rival measured figure.
