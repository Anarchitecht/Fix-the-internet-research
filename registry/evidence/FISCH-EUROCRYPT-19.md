## [FISCH-EUROCRYPT-19] Tight Proofs of Space and Replication
**Citation:** Ben Fisch. "Tight Proofs of Space and Replication." EUROCRYPT, 2019. DOI 10.1007/978-3-030-17656-3_12.
**Retrieved:** full text via https://eprint.iacr.org/2018/702.pdf
**Source URL:** https://eprint.iacr.org/2018/702.pdf
**Domain:** C

### What it does
A proof of space (PoS) lets a prover convince a verifier it is persistently storing at least a specified amount of data, through a compact commitment plus cheap spot-check challenges (defined identically to DZIEMBOWSKI-CRYPTO-15). This paper's contribution is closing the gap, called the space gap ε, between the storage N an honest prover actually uses and the storage (1−ε)N a cheating prover can get away with while still passing verification; a PoS is "arbitrarily tight" if ε can be driven toward zero by a construction parameter without inflating the degree of the underlying graph (only the number of stacked layers grows, as O(log(1/ε))).

The construction, Stacked Depth-Robust Graphs (Stacked DRGs), builds on the stacked bipartite-expander PoS of Ren and Devadas (TCC 2016): a graph of O(log(1/ε)) layers, each n nodes, where each layer individually is a depth-robust graph (DRG) — a graph in which any subgraph on a stated fraction of the nodes (the paper analyzes 80%) retains a long directed path (length Ω(n)) — and bipartite-expander edges connect consecutive layers. The prover labels every node with a hash of its parents' labels (as in the generic graph-labeling PoS), commits to the labels of each layer with a vector commitment (e.g. a Merkle tree), and stores only the final layer's labels, deleting earlier layers as computed. Deleting an ε fraction of the final layer's stored labels forces the prover to recompute nearly all labels in the earlier layers to answer future challenges, because the expander edges between layers make each later layer's labels depend on a spreading fraction of nodes in every earlier layer; since each layer is itself depth-robust, that recomputation costs Ω(N) sequential steps. This is what makes the space gap tight and, unlike the Ren-Devadas base construction, resistant to parallel-execution cheating (a prover running many computations at once cannot substitute time for storage).

A second construction, ZigZag DRGs, adapts Stacked DRGs into a proof of replication (PoRep): a publicly verifiable proof that the prover holds several independently generated, individually retrievable copies (replicas) of a specific input file, not merely one copy referenced multiple times. Each layer is the union of a DRG and a constant-degree non-bipartite expander graph, and the direction of the inter-layer expander edges alternates layer to layer (the "zig-zag"), so dependencies that were computed forward in one layer become recoverable backward in the next. Each layer's labels encode the data of the previous layer using a key derived from that layer's own DRG edges. This makes decoding the original data from any replica fast and parallelizable, at the cost of roughly double the number of layers versus the plain PoS variant, whereas the direct PoRep application of the base Stacked-DRG construction makes data extraction as expensive as generating the replica in the first place.

### Parameters
- N: total space (in blocks) the honest prover commits to store
- ε: target space gap; the fraction of storage a cheating prover might save and still pass verification, tunable toward zero
- 𝓁 (number of layers): O(log(1/ε)) for the Stacked-DRG PoS; roughly double that for the ZigZag PoRep variant, to maintain the same space-gap guarantee while enabling fast extraction
- d: degree of the depth-robust graph within each layer, fixed independent of ε (the paper's concrete construction uses a degree-8 Chung random bipartite graph for the inter-layer edges)
- Depth-robustness threshold: analyzed concretely at (n, 0.80n, Ω(n)) — any subgraph on 80% of a layer's nodes retains an Ω(n)-length path
- λ: cryptographic/statistical security parameter, drives the number of challenge queries per layer
- δ: a challenge-query tuning parameter; the paper shows total proof queries across all layers can be held to O(1/δ), giving overall proof complexity O(d/ε)
- k (Merkle-tree pruning depth): free parameter trading storage for extra hash computation during path reconstruction; the paper's own example sets k=7

### Stated limitations
The Ren-Devadas base construction this paper builds on is stated to not be proven secure against a graph-labeling adversary in the random oracle model generally, only against a pebbling-modeled adversary; this paper's own construction is stated to close that gap by additionally proving security against parallel pebbling attacks, from which security in the random oracle model follows. The paper states that constructions of depth-robust graphs achieving arbitrarily small α (i.e., very strong depth robustness) exist in theory but are "purely theoretical and not viable in practice," which is why this paper deliberately targets a construction needing only a weak, fixed 80%-subgraph depth-robustness property instead. The direct PoRep application of the plain Stacked-DRG PoS (without the ZigZag modification) is stated to make data extraction "as inefficient as replica generation," meaning recovering the original file from a replica costs as much sequential computation as producing that replica did — the paper's stated reason for introducing the separate ZigZag construction. The paper's own analysis of a compression-robust encoder graph (the Cecchetti-Miers-Juels PIE construction, discussed in comparison) demonstrates a counterexample where compression-robustness alone does not imply proof-of-space security, because data labels can sometimes be recomputed out of topological order using an inverse pseudorandom-permutation decoding path rather than needing genuinely sequential recomputation — the paper states this is a specific caveat about a competing definition, not a limitation of its own Stacked-DRG or ZigZag constructions. The paper notes an incompletely optimized proof-size tradeoff at one point in the ZigZag analysis ("here does not yet optimize this tradeoff"), without further elaboration on what the achievable optimum would be.

### Requirements it places on the rest of the system
The Stacked-DRG PoS requires a cryptographic hash function (used as the graph-labeling function) and a vector-commitment scheme such as a Merkle tree, with the verifier retaining only the O(polylog(N))-size commitment root, not the data itself. For a PoRep built on this PoS to guarantee ε-rational replication (the property that storing k independently-generated replicas is the storage-minimizing strategy up to an ε loss), the paper states it needs the composed scheme to be simultaneously a tight proof of space and a proof-of-retrievable-commitment (PoRC) — a component this paper defines separately (Section 2.1) and does not itself argue can be substituted by an arbitrary proof-of-storage scheme without re-verifying that composition. A prover instantiating this PoS must be able to compute the full graph labeling once (initialization time is not stated as reduced from linear in N; the earlier Dziembowski-family result already showed initialization is at least linear in N), and must have persistent storage for the final layer's labels between the initialization and every later execution round; the protocol assumes the verifier issues challenge queries and enforces a wall-clock timing bound on responses, since soundness against a prover that discarded labels and recomputes them on demand depends on that computation being provably too slow to complete within the challenge window. For the ZigZag PoRep specifically, a system consuming the extracted data must be able to run the decoding procedure layer by layer, in parallel, recovering each earlier layer from the one after it using per-node keys derived from within-layer DRG edges — this requires the replica-holding party to retain every layer's labels in the ZigZag topology, not just the last layer, which is a storage-shape assumption distinct from the plain Stacked-DRG PoS.

### Contradicts
None found within this batch that directly disagree in a measured figure. The paper's own comparison table implicitly disputes the practicality claims made for the Dziembowski-Faust-Kolmogorov-Pietrzak (2015) and Pietrzak (2018) depth-robust-graph constructions: this paper states those constructions, while asymptotically sound, require degree and proof-size parameters that are not "concretely practical" (specific figures: 26 MB to 1 GB proof sizes at stated security levels), a stronger and more specific claim than either of those papers' own framing of their results as asymptotically efficient.
