## [VAJHA-FAST-18] Clay Codes: Moulding MDS Codes to Yield an MSR Code

**Citation:** Myna Vajha, Vinayak Ramkumar, Bhagyashree Puranik, Ganesh Kini, Elita Lobo, Birenjith Sasidharan, P. Vijay Kumar, Alexander Barg, Min Ye, Srinivasan Narayanamurthy, Syed Hussain, Siddhartha Nandi. "Clay Codes: Moulding MDS Codes to Yield an MSR Code." USENIX Conference on File and Storage Technologies (FAST), 2018. Pages 139-153. DOI not stated in retrieved text.
**Retrieved:** full text via https://www.usenix.org/system/files/conference/fast18/fast18-vajha.pdf
**Source URL:** https://www.usenix.org/conference/fast18/presentation/vajha
**Domain:** C

### What it does
A Clay code (Coupled-Layer code) reduces the network traffic and disk reads needed to repair one failed storage node in an erasure-coded system, compared to a Reed-Solomon (RS) code of the same size, by letting the repair process download only a fraction of each surviving node's data rather than that node's full content. An erasure code divides an object into k data chunks and computes m = n − k parity chunks, storing all n chunks on separate nodes so that any failure of up to m nodes is recoverable; a Maximum-Distance-Separable (MDS) code achieves this at the lowest possible storage overhead n/k for a given fault tolerance. Under conventional RS repair, restoring one failed node requires downloading k times as much data as the failed node held, because each of the k surviving nodes must send its entire chunk. A Minimum-Storage-Regenerating (MSR) code is a sub-class of MDS codes designed to avoid this: to repair a node, the system selects d helper nodes (k ≤ d ≤ n − 1) and downloads only β = α/(d − k + 1) bytes from each, where α is the sub-packetization level — the number of bytes grouped into one indivisible unit ("superbyte") per node, so the total repair download dβ is smaller than the kα bytes a conventional approach would move. The paper's own normalized-repair-bandwidth formula is dβ/(kα) = d / (k(d − k + 1)), which for d = n − 1 reduces to (n − 1) / (k(n − k)), showing repair traffic falls as the number of parity chunks (n − k) grows.

Clay codes construct an MSR code from any existing MDS code (scalar or vector) by stacking α independent copies of that MDS code in "layers," then applying a pairwise linear transformation between two bytes drawn from paired layers — a transform the paper calls Pair-wise Forward Transform (PFT) and its inverse Pair-wise Reverse Transform (PRT). This coupling lets each repair operation recover a failed byte by decoding the underlying scalar MDS code plus one elementary two-byte linear operation, rather than requiring a new theoretical code family. The construction builds directly on Ye and Barg's 2017 theoretical MSR code, re-expressing it from a coupled-layer perspective that the paper states makes an implementation more direct, generalizes it to work with any scalar MDS code (not only Vandermonde-RS codes), and extends it to a generic multi-node-repair algorithm covering more than one simultaneous failure — properties the original Ye-Barg construction did not include. The paper also modified Ceph, a distributed object-storage system, to support vector codes (multi-byte superbytes per node) rather than only the scalar codes it previously supported, and implemented Clay codes as a Ceph plugin; this Ceph modification became part of Ceph's upstream master codebase.

Experimental setup for all measurements above: a Ceph cluster of 26 Amazon EC2 m4.xlarge instances (16 GB RAM, 4 CPU cores each), one dedicated to the Ceph MON daemon and 25 running one OSD (Object Storage Daemon) apiece, each attached to a 500 GB SSD volume, giving roughly 12.2 TB total cluster capacity. Node failures were injected by removing OSDs; the failure domain was one node (one OSD per node). Measurements were taken with the nmon and NMONVisualizer tools, in both a single-PG configuration and a 512-PG configuration (the multi-PG figures for network traffic and disk read during single-node repair are shown separately in the paper, averaged across 3 runs, and are described as showing inferior performance in some cases because Ceph can dynamically reassign an already-participating OSD as the replacement, which the paper treats as effectively two failures). Two object-distribution workloads were used: W1, all objects fixed at 64 MB (8,192 total objects, 512 GB); W2, a mix of 64 MB (82.5%), 32 MB (10%), and 1 MB (7.5%) objects (820-6,758 objects depending on size, 448 GB total), chosen to match a distribution reported for the Facebook data-analytics cluster in a separate cited paper. Repair comparisons for the multiple-node-failure case (codes C4, C5, C6, all (14,10,d) parameters for d = 11, 12, 13, matching a Facebook-cluster (14,10) RS deployment) were run under workload W1 in the 512-PG setting, injecting between 1 and 4 simultaneous node failures; the paper states the average multi-failure network-traffic figures assume every failure pattern of a given size is equally likely, and it separately reports a purely theoretical (non-measured) average-network-traffic curve for f = 1 to 4 failures in Figure 17.

### Parameters
- Six evaluated code instances and their (n, k, d), sub-packetization level α, storage overhead, and normalized repair bandwidth β/α: C1 (6,4,5), α=8, overhead 1.5, β/α=0.5, chosen to match the RDP (Row-Diagonal Parity) code; C2 (12,9,11), α=81, overhead 1.33, β/α=0.33, chosen to match the locally repairable code used in Windows Azure; C3 (20,16,19), α=1024, overhead 1.25, β/α=0.25, chosen to match the (20,17)-RS code used at Backblaze; C4 (14,10,11), α=128, overhead 1.4, β/α=0.5; C5 (14,10,12), α=243, overhead 1.4, β/α=0.33; C6 (14,10,13), α=256, overhead 1.4, β/α=0.25 — C4-C6 all chosen to match the (14,10)-RS code used in Facebook's data-analytics clusters.
- Finite-field size: the paper's simplified presentation assumes a field of size 2^8 (one byte per field element) but states the construction works over a field only approximately as large as n, "significantly smaller" than 2^8 if desired.
- Ceph version used: Jewel 10.2.2.
- Cluster size: 26 EC2 m4.xlarge nodes (1 MON + 25 OSD), 500 GB SSD per node, ~12.2 TB total capacity.
- Workload W1: fixed 64 MB objects, stripe size S = 64 MB (chosen to avoid zero-padding).
- Workload W2: mixed 64 MB / 32 MB / 1 MB objects in 82.5% / 10% / 7.5% proportion, stripe size S = 1 MB.
- The construction requires q = (d − k + 1) to divide n for the base parameter set; the paper describes a "shortening" extension (padding n up to the next multiple of q with zeroed systematic nodes) for parameter sets where this does not hold, and states this extension is included in their implementation.

### Stated limitations
When the design parameter d is less than n − 1, single-node repair requires that, whenever a failed node's "y-section" (its layer-group in the coupled-layer grid) contains other failed nodes, all surviving nodes in that y-section must also be used as helper nodes; if no valid choice of d helper nodes satisfying this exists, the failure pattern is not repairable with bandwidth savings and the paper's algorithm falls back to a plain decode operation instead (Remark 1: this occurs, for example, when q failures land in the same y-section). Repair-bandwidth savings for multiple simultaneous failures hold only for what the paper calls "repairable failure patterns"; patterns outside that set are recovered through decoding, at a higher bandwidth. The encode computation time for a Clay code is higher than for the matching RS code, attributed to the extra pairwise linear-transform multiplications; the paper treats this as an acceptable trade against the larger measured savings during repair, without quantifying the encode-time increase as a number in the sections read. The paper explicitly frames its Clay-Ye-Barg comparison as showing Clay's advantages (any scalar MDS code as a building block, multi-failure repair, coupled-layer implementability) but does not claim Clay improves the Ye-Barg construction's theoretical repair-bandwidth bound itself — Clay is presented as a practical realization of that existing bound, not a new bound.

### Requirements it places on the rest of the system
The storage system must support vector codes — multi-byte "superbytes" grouped per node — because Clay codes require sub-packetization level α > 1; the paper states plain Ceph did not support this and had to be modified (upstreamed into Ceph's master codebase) to add sub-chunking through interleaving. A repair operation needs the coordinator (in the paper's Ceph implementation, the primary OSD, "p-OSD") to be able to select and contact d distinct helper nodes out of the surviving n − 1, and, when d < n − 1, to identify and include every surviving node sharing the failed node's y-section as a helper — this requires the coordinator to know the code's layer/grid structure, not just node liveness. Disk-read savings depend on the storage medium's read granularity matching the sub-chunk fragment size (S/kα): the paper's own measurement shows that when this alignment fails (workload W2, code C3), 4x more data is read from disk than is needed, so a deployment must choose stripe size and α relative to the underlying disk or SSD block size to realize the disk-I/O benefit, not just the network-traffic benefit. The construction assumes an MDS code already exists to serve as the per-layer building block; Clay codes do not replace that MDS code, they wrap it.

### Contradicts
None found against another entry in this corpus. The paper's own Table 1 comparison states that the prior product-matrix MSR implementation (Rashmi, Nakkiran, Wang, Shah, Ramchandran, FAST 2015, citation [24] in this paper's bibliography) is disk-I/O-optimal but has higher storage overhead, of the form (2 − 1/k) — this is presented as a design trade-off between two published systems, not a numeric disagreement to be resolved.
