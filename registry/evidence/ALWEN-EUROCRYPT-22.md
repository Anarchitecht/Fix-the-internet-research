## [ALWEN-EUROCRYPT-22] CoCoA: Concurrent Continuous Group Key Agreement
**Citation:** Joël Alwen, Benedikt Auerbach, Miguel Cueto Noval, Karen Klein, Guillermo Pascual-Perez, Krzysztof Pietrzak, Michael Walter. "CoCoA: Concurrent Continuous Group Key Agreement." EUROCRYPT, 2022. DOI 10.1007/978-3-031-07085-3_28.
**Retrieved:** full text via https://eprint.iacr.org/2022/251.pdf
**Source URL:** https://eprint.iacr.org/2022/251.pdf
**Domain:** H

### What it does
CoCoA (COncurrent COntinuous group key Agreement) is a continuous group key agreement (CGKA) protocol — a protocol letting an evolving group of clients continuously derive a shared symmetric group key across a sequence of epochs, each epoch beginning when a member joins, leaves, or updates (refreshes) its own cryptographic key material — designed so that many members can update concurrently without the per-user communication cost this normally forces. CoCoA still relies on a centralized, untrusted delivery server that batches operations into synchronized rounds and forwards them, so it operates under the same total-ordering-of-delivery assumption as TreeKEM (the protocol underlying the IETF's Messaging Layer Security, MLS, draft standard) and other prior CGKA protocols; its contribution is handling many members updating within the same round efficiently, not removing the ordering requirement itself.

Mechanism. Members sit at the leaves of a ratchet tree — the same binary-tree structure TreeKEM uses, where each node holds a public/private key pair and a member knows the private keys on the path from its leaf to the root. In prior TreeKEM-family protocols, when several members submit concurrent update requests within one round, the delivery server accepts exactly one and rejects the rest, forcing the losers to retry. CoCoA's server instead attempts to apply every submitted update: if two or more updates target the same tree node in a round, the server arbitrarily picks one winner for that node, but every update still contributes progress elsewhere in the tree. The paper's proved result is that this merging strategy guarantees all previously compromised members recover full security (achieve post-compromise security, PCS — the property that a group's security is restored once a compromised member updates and communication continues normally) within at most ⌈log(n)⌉+1 rounds of such merged concurrent updates, regardless of how the server breaks ties, where n is the number of group members. To keep per-update packet size low despite concurrent merging, CoCoA is server-aided: rather than broadcasting one packet to be relayed unchanged to everyone (as plain TreeKEM does), the untrusted server actively computes an individualized packet tailored to each recipient, containing only the ciphertexts and public keys relevant to that member's own path in the tree; this requires new mechanisms (explicit signatures on protocol messages, and a parent-hash-based consistency check across members' partial views) to keep every member's partial view of the shared tree state consistent despite no member seeing the full tree, since the paper's security proof shows that undetected disagreement between members — for example, about tree membership — can lead to serious security failures.

Trade-off circumvented and its cost. A prior lower bound (Bienstock, Dodis, Rösler, cited as [BDR20]) shows that any concurrent-update mechanism completing in at most 2 rounds must incur communication cost at least linear in the number of concurrently updating members T, and Omega(n^2) total if all n members update concurrently within 2 rounds. CoCoA circumvents this specific bound by using up to ⌈log(n)⌉+1 rounds instead of 2, at which point every member's cumulative communication (sending and receiving) across the whole healing process is only order log(n)^2 (i.e., (log n) squared) ciphertexts, rather than growing linearly or worse in n or T. Unlike the "propose-and-commit" concurrency mechanism MLS adopted (in which committing to T concurrently proposed updates leaves the T members' tree paths blanked, degrading future commit-packet size toward linear in n until those blanks are later repaired), CoCoA's merge-based approach never blanks tree nodes during concurrent operation, so it does not degrade the cost of subsequent, later updates.

Security-model assumption. The paper's security proof holds against a "partially active" adversary: the adversary can adaptively leak any member's full local state (including random coins) at will and can send arbitrary, even malformed, messages as the untrusted server, but cannot forge protocol messages as an honest member because it never obtains members' signing keys through corruption. The authors state this is a common but strong assumption for this line of work, and explicitly identify proving CoCoA secure against a fully active adversary (one that can forge as a corrupted member) as an open question for future work.

### Measured results
This is a theory paper: its quantitative results are asymptotic communication-complexity bounds derived from the protocol's construction and proved via formal security reduction, not measurements from a running implementation on real hardware, node counts, or network conditions — no implementation, deployment, or benchmarked wall-clock/bandwidth figures are reported anywhere in the paper.

Table 5 (the paper's own comparison of CGKA protocols' communication complexity) gives Big-O bounds under a fixed comparison setting: a group of n members, t of which have been compromised, with the ratchet tree assumed fully unblanked at the start, comparing scenario (a) — the group knows it has been compromised but not which t members — against scenario (b) — the compromised set is publicly known, so only those t members must act:

|---|---|---|---|---|---|
| Original TreeKEM & variants [ACDT20, BBR+23, KPPW+21, Mat19] | n (a) / t (b) | n log(n) | t log(n) | n log(n) / t log(n) | log(n) |
| Propose-commit TreeKEM [BBR+23] | 2 | n^2 (uncoordinated) / n (coordinated) | t^2(1+log(n/t)) / t(1+log(n/t)) | n / t(1+log(n/t)) | up to n (a) / up to t(1+log(n/t)) (b), degraded by blanking |
| Bienstock et al. [BDR20] | 2 | n^2 / n | t^2(1+log(n/t)) / t(1+log(n/t)) | n (uncoordinated: n^2) / t(1+log(n/t)) | log(n) worst case, but only in a weak security model — matches propose-commit TreeKEM once strengthened to comparable PCS via tainting |
| Bidirectional channels [WKHB21] | 2 | n^2 | tn | n / t | n |
| CoCoA (this work) | ⌈log(n)⌉+1 | n·log(n)^2 | t·log(n)^2 | log(n)^2 (a) / log(n)·min(t,log(n)) (b) | log(n) |

Conditions for this table: ratchet-tree-based protocols assumed to start fully unblanked; "coordination" distinguishes whether concurrently updating members know of each other's in-flight updates (avoiding server-rejected packets) versus not; all non-O() entries in the last five columns are to be read as O(x) per the table's own note; the Bienstock et al. entry's uncoordinated-case recipient communication is separately stated as n^2 (case a) / t^2(1+log(n/t)) (case b).

Transition-from-fully-blanked-to-fully-unblanked-tree comparison (a stated worked example, not a separate experiment): TreeKEM needs n/2 rounds, with per-user recipient complexity (ciphertexts downloaded) of order n·log(n); the Bienstock et al. protocol unblanks the whole tree in 2 rounds at linear sender and recipient communication per user; CoCoA unblanks the tree in 1 round at linear sender cost but only logarithmic (order log(n)) recipient cost per user.

Per-round state a CoCoA user needs (a structural, derived figure rather than an experimental one): to process an update, a CoCoA user needs only order log(n) secret keys and about 2·log(n) public keys — far less than the full 2n−1 public keys in the shared ratchet-tree state — because the server delivers only individualized, per-recipient packets rather than the shared broadcast every prior TreeKEM-family protocol relies on.

Theorem 1 (correctness/robustness under encryption/signature security): if the encryption scheme CoCoA uses is IND-CPA-secure (indistinguishable under chosen-plaintext attack) and the signature scheme is UF-CMA-secure (existentially unforgeable under chosen-message attack), the stated robustness property holds; this is a reduction-based proof, not a numeric measurement, and the paper states the proof follows from corresponding results in prior work ([KPPW+21]) applied to the general public-key group-state-distribution (GSD) result in the random-oracle model.

### Parameters
- Group size n and number of compromised members t, treated as free asymptotic variables throughout; no concrete numeric group size is tested or benchmarked.
- Rounds to heal from compromise: exactly ⌈log(n)⌉+1 in the paper's proved worst case, though the paper states "typically fewer rounds" suffice in practice (not separately quantified).
- Per-user cumulative communication after full concurrent healing: order n·log(n)^2 total across all users (case a) or t·log(n)^2 (case b, only compromised users act), i.e. each acting user's own share is order log(n)^2.
- Per-user local knowledge requirement: order log(n) secret keys and order 2·log(n) public keys, versus the full 2n−1 public keys a member would need to track the entire shared ratchet tree in prior non-server-aided protocols.
- Security-parameter lambda: referenced only abstractly (`CGKA.Gen(1^lambda)` in the formal syntax) with no concrete bit-length instantiated or tested.

### Stated limitations
The paper's security proof (Theorem 1 and the surrounding security-model discussion) applies only to a "partially active" adversary that can adaptively leak any member's local state and send arbitrary server-side messages but cannot forge protocol messages, because it never obtains signing keys through corruption; the authors state extending the analysis to a "fully active" adversary — one that also compromises the ability to forge on behalf of corrupted members — is an important open question left for future work.

The lower bound the protocol circumvents ([BDR20]) applies only to protocols that complete concurrent healing within 2 rounds; the authors state their circumvention is achieved specifically by trading additional interaction (up to ⌈log(n)⌉+1 rounds instead of 2) for lower bandwidth, and explicitly frame this as a trade-off, not a free improvement: "we are paying a log(n) factor in sender communication in exchange for faster PCS that is independent from the number of compromised users" relative to non-concurrent pre-propose-and-commit TreeKEM, and "this comes at the cost of slower healing and a factor of log^2(n)... in sender communication cost" relative to propose-commit TreeKEM specifically when many members need to heal quickly.

Signature-key distribution is stated as an unavoidable Omega(n) communication cost independent of round count or concurrency: distributing n fresh signature verification keys (one per updating member) to every other group member inherently costs order n communication for each recipient, because every member must know every other member's current verification key to authenticate packets. The paper's mitigation — "lite updates," which refresh all of a member's secret key material except its signature key — is explicitly described by the authors as "not ideal from a security perspective," offered only as a practical way to avoid the cost of re-certifying signature keys (which the paper notes may require an external, slow process such as manual certificate authority issuance) on every key refresh.

The paper's own concluding comparison states CoCoA's bandwidth is not universally superior: it states CoCoA "seems to have a slightly worse efficiency than TreeKEM based protocols predating the propose-and-commit paradigm" when only a single member needs to heal (a case where CoCoA reduces to ordinary sequential TreeKEM-like behavior and grants immediate PCS to a lone updater, matching that baseline), and the stated bandwidth advantage of CoCoA's approach is conditional on "fast PCS... required for many users" concurrently.

The paper explicitly separates "corrupted parties known" (scenario b) from "corrupted parties unknown" (scenario a) as materially different costs throughout Table 5 and its surrounding discussion, and does not claim a mechanism for a group to determine which case applies in a real deployment — this determination is treated as an external input to the protocol, not something CoCoA itself resolves.

### Requirements it places on the rest of the system
- CoCoA still requires a stateful, synchronized-round delivery mechanism: the untrusted server "works in rounds, collects operations into batches and sends them out at the end of each round" (the paper's own formal definition, Section 2.1) — this is the same total-ordering-of-delivered-messages structure TreeKEM/MLS depends on, only batched rather than one-message-at-a-time; a fully asynchronous, unordered, or partition-tolerant delivery layer that cannot guarantee this per-round batching and consistent per-session delivery is outside what CoCoA's security proof covers.
- The delivery server must actively compute individualized, per-recipient packets rather than relaying one broadcast packet verbatim, because CoCoA members deliberately do not track the full shared ratchet-tree state; a deployment that wants to keep the delivery server as a "dumb" relay (as plain TreeKEM allows) cannot adopt CoCoA's bandwidth savings, since those savings specifically depend on server-side computation tailored to each recipient's partial view.
- Every group member must be able to verify every other member's signature-verification key; the paper states distributing n fresh signature keys costs at least order n communication per recipient regardless of round count, so any system layer that wants to avoid this floor needs a separate mechanism (the paper's own suggestion is "lite updates" that refresh all secret material except the signature key, explicitly presented as a security-availability trade-off, not a solution that removes the cost).
- The protocol's security proof assumes the adversary cannot forge protocol messages on behalf of corrupted members — that is, it assumes signing keys of corrupted members are not accessible to the adversary through the corruption model used in the proof; a deployment where an attacker can otherwise obtain or forge valid signatures (for example, via a compromised certificate authority or signing-key-extraction attack) is outside the threat model this specific security result covers, and the paper flags a fully active adversary as unresolved future work.
- CoCoA's consistency mechanism (parent-hash checks and explicit signatures across individualized packets) exists specifically because, unlike prior CGKA protocols where the majority of what one member uploads is downloaded by everyone, CoCoA's uploaded and downloaded communication for a given member diverge substantially — any composition with a different transport or storage layer needs to preserve the property that every member can independently verify its partial-tree view is consistent with the rest of the group, or the paper's stated attack surface (severe security failures from undetected member disagreement, e.g. about group membership) reopens.

### Contradicts
None found against other entries in this batch. Within the paper's own comparison, it explicitly contradicts an implicit assumption that concurrent CGKA updates must cost either the Bienstock-et-al.-style Omega(T) per-round communication or the propose-and-commit-style future-blanking penalty: CoCoA achieves neither, at the stated cost of needing up to log(n)+1 rounds rather than 2.

### References worth retrieving
- foundational: Bhargavan, Barnes, Rescorla, "TreeKEM: Asynchronous Decryption-Key Update for Secure Group Messaging," cited as [BBR18] — the original TreeKEM proposal, including its early (later-dropped) concurrent-conflict handling that this paper's CoCoA formalizes and analyzes.
- foundational: Alwen, Coretti, Dodis, Tselekounis, "Security Analysis and Improvements for the IETF MLS Standard for Group Messaging," CRYPTO 2020, cited as [ACDT20] — this is ALWEN-CRYPTO-20, already a target in this corpus; the non-concurrent TreeKEM security baseline this paper's Table 5 compares against directly.
- competing: Bienstock, Dodis, Rösler, "On the Price of Concurrency in Group Ratcheting Protocols," cited as [BDR20] — source of the Omega(T) / Omega(n^2) lower bound this paper explicitly circumvents by using more rounds; contains the closest direct comparison numbers (Table 5's "Bienstock et al." row).
- competing: Weidner, Kleppmann, Hugenroth, Beresford, "Key Agreement for Decentralized Secure Group Messaging with Strong Security Guarantees," cited as [WKHB21] — a decentralized, bidirectional-channel-based CGKA the paper compares directly in Table 5 (linear communication complexity, explicitly called "impractical" by this paper's authors "in the contexts we are interested in"); this is the DCGKA line that the brief identifies as BeeKEM's direct predecessor.
- competing: Weidner, "Group Messaging for Secure Asynchronous Collaboration," Master's thesis, cited as [Mat19] — Causal TreeKEM, which re-randomizes rather than overwrites node secrets to support a form of concurrency, but which the paper states "lacks forward secrecy and a complete security proof."
- competing: Klein, Pascual-Perez, Walter, Kamath, Capretto, et al., cited as [KPPW+21] — Tainted TreeKEM (TTKEM), the source of the security model and GSD (group-state-distribution) proof technique this paper's own Theorem 1 builds on, and a direct comparison point in Table 5.
- foundational: Alwen, Coretti, Jost, Mularczyk, "Continuous Group Key Agreement with Active Security," cited as [ACJM20] — source of the "ideal/real" CGKA security notion against fully active adversaries that this paper's own security model falls short of, explicitly marked as future work here.
- competing: Alwen, Hartmann, Kiltz, Mularczyk, "Server-Aided Continuous Group Key Agreement," cited as [AHKM22] — the server-aided CGKA line CoCoA's individualized-packet mechanism is built in the same spirit as; this is the SAIK protocol that ALWEN-CRYPTO-23 (Fork-Resilient CGKA) builds FREEK on top of, already a target in this corpus.
- foundational/critique: Cohn-Gordon, Cremers, Garratt, Millican, Milner, "On Ends-to-Ends Encryption: Asynchronous Group Messaging with Strong Security Guarantees," cited as [CCG+18] — the ART protocol, credited by this paper as initiating the study of logarithmic-complexity E2E group protocols and the CGKA research line generally.
