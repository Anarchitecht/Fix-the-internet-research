## [NEGENTROPY-NIP77-23] NIP-77: Negentropy Syncing

**Citation:** Doug Hoyte (Negentropy protocol); wrapped for Nostr as NIP-77 by the nostr-protocol contributors. "NIP-77: Negentropy Syncing." Protocol specification, github.com/nostr-protocol/nips and github.com/hoytech/negentropy, 2023. No DOI (not a peer-reviewed paper).
**Retrieved:** full text via https://github.com/nostr-protocol/nips/blob/master/77.md
**Source URL:** https://github.com/nostr-protocol/nips/blob/master/77.md
**Domain:** D

### What it does
Lets a Nostr client and a Nostr relay (or two relays) discover which events each side holds that the other lacks, transmitting less data than sending the full event set or even the full ID list when the two sides already hold events in common. Nostr is the decentralized social protocol this specification extends; a relay is a server that stores and serves events on behalf of clients. The protocol is a Nostr-specific message-framing wrapper (`NEG-OPEN`, `NEG-MSG`, `NEG-ERR`, `NEG-CLOSE`) around the Negentropy binary protocol, described in the specification's own words as using "Range-Based Set Reconciliation" (the algorithm family covered by MEYER-TR-24 and its parent SRDS 2023 paper elsewhere in this corpus). The wire messages hex-encode the Negentropy binary payload for transport inside the Nostr JSON message format.

The high-level exchange: the client picks a NIP-01-format filter, retrieves or reads from cache the set of events it locally holds matching that filter, builds an initial Negentropy message, and sends it inside a `NEG-OPEN` message alongside a subscription ID and the filter. The relay selects its own locally matching event set, constructs a response, and returns it in a `NEG-MSG`. The client parses the response to learn which event IDs it holds that the relay needs, and which IDs it needs that the relay holds; if further rounds are needed it sends another `NEG-MSG`, otherwise it sends `NEG-CLOSE` or disconnects. The protocol by itself only produces two ID sets (what the client has/relay needs, what the client needs/relay has); actual event transfer happens separately, over `EVENT` (upload) and `REQ` (download) messages on the same connection, which the specification states can run in parallel with continuing `NEG-MSG` rounds. A client interested only in a count of unique events (the specification gives reaction counts as an example) can skip transfer entirely.

Each record reconciled is a pair of a 64-bit timestamp and a 256-bit event ID; both sides sort their local records by timestamp ascending, breaking ties by lexical ID order ascending on first differing byte. The maximum uint64 value is reserved as a special timestamp meaning infinity and may not be used by a real record. A protocol message is a version byte (`0x61` for version 1) followed by an ordered, gap-free list of Range structures that together always cover the entire timestamp/ID space — the first Range starts at timestamp 0, ID 0, and an implicit trailing Skip-to-infinity Range is appended if the explicit list does not reach the infinity bound. Each Range carries an upper bound and one of three payload modes: mode 0 (`Skip`, empty payload, sender does not want to process this range further), mode 1 (`Fingerprint`, a 16-byte digest of every ID the sender holds in the range), or mode 2 (`IdList`, the sender's full list of IDs in the range, used once a range is small enough that direct transfer is cheaper than further recursive fingerprint splitting). A Range's lower bound is implicit — the previous Range's upper bound, or the zero bound for the first Range — so only the upper Bound is transmitted per Range. A Bound encodes a timestamp (as `0` for infinity, or `1 + offset` from the previously encoded timestamp within the same message, with offsets always non-negative because ranges are ascending and non-overlapping) plus a variable-length (0 to 32 bytes) disambiguating ID prefix, the shortest prefix sufficient to separate the first record of this Range from the last record of the previous Range — length 0 if the two records' timestamps already differ, otherwise the byte length of their common ID prefix plus one.

The fingerprint for a Range is computed as: interpret every element ID in the range as a 32-byte little-endian unsigned integer and sum them with addition modulo 2^256; concatenate that sum with the element count of the range, itself encoded as a Varint (a base-128, most-significant-digit-first variable-length integer with the high bit set on every byte but the last); hash the concatenation with SHA-256; take the first 16 bytes of the digest as the fingerprint. This construction gives a homomorphic-style fingerprint (addable across disjoint subranges before hashing) built from a conventional hash function (SHA-256) rather than requiring a hash function with a built-in algebraic homomorphism, by moving the homomorphic combining step (modular addition of raw IDs) before hashing rather than expecting the hash itself to be homomorphic.

The specification defines two error conditions a relay may return in a `NEG-ERR` message: `blocked`, when a relay declines to service a query that would require processing too many records or records that are too old (a relay may optionally return the maximum record count it will process as a fourth response element), and `closed`, when a relay times out an inactive, stateful query to reclaim memory. After a `NEG-ERR`, the subscription is closed.

### Measured results
None. This is a protocol specification, not an experimental paper; it contains no benchmark, no message-count figure, no bandwidth measurement, no node count, and no deployment-scale data. Any bandwidth or round-count claim for this protocol would need to be measured separately against a real implementation and is not present in this document.

### Parameters
Fingerprint length: 16 bytes (128 bits), taken as the first 16 bytes of a SHA-256 digest. ID length: 32 bytes (256 bits). Timestamp width: 64 bits, with the maximum value reserved as an infinity sentinel. Varint encoding: base-128, most-significant digit first. Bound ID-prefix length: variable, 0 to 32 bytes, chosen per-message as the shortest prefix that disambiguates consecutive records. Protocol version: 1 (byte `0x61`); the specification defines a downgrade path where a relay unable to handle a client's version replies with a single byte naming its own highest supported version. No default or recommended value is given for a relay's `blocked` record-count ceiling or `closed` timeout duration; both are left to relay implementations to choose.

### Stated limitations
The specification states relays "may" reject queries that would require processing too many records or records too old, and "may" time out inactive stateful queries — both are optional relay-side policies, not protocol-mandated limits, so no participant can rely on any specific record-count or time bound being enforced by every relay. The protocol reconciles ID sets only; it does not itself transfer event content, and does not define how upload (`EVENT`) or download (`REQ`) of the reconciled IDs is scheduled, retried, or prioritized beyond stating they can run in parallel with continuing `NEG-MSG` exchange. The specification gives no censorship-resistance or malicious-input analysis: it does not state what happens, or what guarantee holds, when one participant's Range list is inconsistent (contains gaps, overlaps, or a malformed Bound) or when a participant deliberately misreports a fingerprint. It does not specify authentication of the participants or of individual events beyond what the rest of the Nostr protocol (NIP-01, referenced but not part of this document) already provides.

### Requirements it places on the rest of the system
Both participants must maintain their event sets as records addressable by a `(timestamp, 256-bit ID)` pair, sortable into one consistent total order (timestamp ascending, ID lexical ascending on ties), because the Range-based recursive splitting depends on both sides partitioning the identical ordered space identically. The reserved infinity timestamp value (max uint64) must never be assigned to a real record, or the implicit trailing Skip-to-infinity Range breaks. Any component computing a fingerprint for a Range needs the full, correct set of 256-bit IDs in that range, since the fingerprint is a direct modular sum over all of them plus a SHA-256 hash — an implementation that omits or duplicates an ID silently produces a matching fingerprint for a mismatched set only in the (cryptographically unlikely but not analyzed here) case of a hash or sum collision. The transport layer needs to support the underlying Nostr message framing (`NEG-OPEN`/`NEG-MSG`/`NEG-ERR`/`NEG-CLOSE` over the existing Nostr WebSocket connection) and a NIP-01-format filter to scope which events are being reconciled. A relay that wants to bound resource use for an open-ended or too-large query must implement its own policy (`blocked` or `closed` responses) since the specification does not mandate one.
