Making Post Quantum Key Exchange Efficient:
An Implementation with the MLS Protocol
Noah Greene Britta Hale
noah.greene@nps.edu britta.hale@nps.edu
Abstract
The development of quantum computing technology poses
a serious and credible threat to modern public-key cryp-
tography, which is a pillar of secure communications. Post
quantum cryptographic (PQC) algorithms can protect against
this threat, but key establishment protocols supporting PQC
algorithms pose non-trivial overhead costs. Prior proposals
have pointed to the use of strategic traditional/PQC protocol
combinations as a means of balancing performance and
security, namely as an amortization of PQC overhead. This
work provides the first benchmarking of this method within
the context of the Messaging Layer Security (MLS) protocol.
Comparative metrics include group size, CPU cycles, bytes,
and runtime. The results show substantial overhead savings
across the board when compared to a simple post-quantum
cipher suite use, and marginal increase over traditional cipher
suite performance when amortized. At small group sizes
such as 1-to-1 channels, the method performs comparably
to MLS using a traditional cipher suite. This work shows
viability of deploying PQC solutions for constrained settings
and achieving PQC security with efficiency.
I. Introduction
The growing threat of Cryptographically-Relevant Quan-
tum Computers (CRQC) against traditional asymmetric
cryptography creates an urgent need for the widespread
adoption of post-quantum cryptographic (PQC) solutions.
Such CRQCs are capable of breaking modern public-key
algorithms, leading to wide-spread effects on cryptographic
security, including putting at risk the security of data that is
currently protected by classical encryption. To address this
threat, new asymmetric algorithms have been finalized by
NIST including ML-KEM (FIPS 203 [1]) as a post-quantum
KEM, and ML-DSA (FIPS 204 [2]) as a post-quantum digital
signature algorithm. These standards are being incorporation
into key exchange protocols, such as TLS, to provide network
security. However, algorithm overhead, especially in the form
of impacts on bandwidth, raise a question on how to achieve
efficient PQC key exchange. Prior work has proposed an
approach to this problem, offering amortization of the PQC
overhead [3]. We will term this approach to the protocol
security Amortized PQ (APQ). This work provides the first
public testing results for the APQ method in the context of
the Messaging Layer Security (MLS) protocol. These results
are not optimized, but presented as an early comparison
point to other PQC methods.
The MLS protocol is a group messaging protocol that
seeks to provide strong security properties with Forward
Secrecy, Post-Compromise Security, as well as efficient
scalability for group communications. It was standardized by
the Internet Engineering Task Force (IETF) in 2023. MLS
functions using an asynchronous key update ratchet, i.e., a
continuous key agreement (CKA), and is based on a Key
Encapsulation Mechanism (KEM) which provides smooth
integration of the FIPS PQC KEM.
Within an MLS group, participants contribute to a shared
secret and are able to verify identities of other group
members. When secrets need to be refreshed, such as
when group membership changes, the key updates drive
all legitimate members to a new shared secret, which is
considered a new group state, referred to as an epoch. Users
only have access to the internal secrets of epochs which they
are members of, which keeps new members from accessing
previous epochs, as well as keeping former members from
accessing new epochs.
As with other protocols, MLS implementations are now
transitioning to use of PQC algorithms and dealing with
the FIPS PQC algorithms’ well widely recognized size
and overhead increase in comparison to traditional modern
standards, the need for PQC migration has motivated the
development of a type of hybrid amortization approach
(i.e., APQ) that aims to provide a middle ground between
post-quantum security and the efficiency of traditional
cryptography. It was first proposed in the context of the
MLS protocol (APQ-MLS) [3].
The asynchronous design of MLS enables further potential

2
for efficiencies within the context of PQC. APQ-MLS aims
to offer low-overhead PQC security by linking two parallel
MLS sessions, one classic and the other PQC, with different
key evolution frequencies, thus spreading out the associated
overhead.
With a PQC-capable MLS, APQC-MLS can provide CKA
capabilities to meet the quantum threat. This is done by
cryptographically linking the secret shared by a traditional
session of the MLS protocol with the secret shared by a
PQC session of MLS. This linking can be achieved by using
the MLS export function to generate a PQC-secure secret
which the traditional session can import as a pre-shared key
(PSK). Using a PQ-secure value as a PSK incorporates the
PQC security into the traditional session, allowing it to carry
the bulk of the group’s message traffic with the efficiency
of traditional encryption. This efficiency-security trade off
can be modulated with the frequency with which the PQC
secret is updated, allowing applications with more stringent
PQC requirements to incur a higher computational cost to
achieve stronger PQC security which in theory still beats
out the computational cost of using a PQC MLS session
exclusively. This work successfully showed the practical
viability of efficient PQC secure communications through
the APQC-MLS protocol.
While there the theoretical advantages of amortizing
overhead are clear, APQ-MLS protocol lacks any formal
implementation and performance data to confirm the security-
performance trade-off it seeks to achieve, both of which are
barriers to its real-world use as a standard.
This work aims to provide a concrete analysis of the per-
formance of the APQC-MLS Combiner protocol measured
against MLS running traditional and PQC cipher suites. After
intensive development to integrate a PQ Key Encapsulation
Mechanism into OpenMLS, the Rust implementation of MLS,
it was possible to implement an approximation of APQC-
MLS in Rust. The code was used to simulate simplified
long-term runs of the protocol with different PQC Update
frequencies, as well as to simulate the same length runs of
MLS with traditional and PQC cipher suites.
II. Background and Related Work
In the realm of secure communications, session-based
protocols are a common approach. Transportation Layer
Security (TLS) [4] is a widely used communications protocol
which performs AKE during its handshake subprotocol
using Ephemeral Diffie-Hellman (DH) key exchange. There
is currently a draft RFC integrating Hybrid Public Key
Encryption (HPKE) into TLS [5]. IPsec [6] similarly uses
DH variants for key exchange. Such protocols are being
adapted to include PQC capability. Efforts are ongoing
to integrate Key Encapsulation Mechanisms (KEMs) into
TLS [7] which could allow for use of ML-KEM [8] or a
hybrid KEM [9], [10]. Similar efforts are ongoing for IKEv2
[11], [12], SSH [13]. When considering the PQC variant
of handshakes for current standards such as TLS and SSH,
overhead can increase up to 50% for SSH and up to 300%
for TLS, depending on the PQC algorithms used [14].
All of the above protocols are session-based, which means
that after the initial AKE, often referred to as a handshake, the
key material is not refreshed without re-doing the handshake,
which starts a new session. 1 The security impact of the
session-based approach is that a session cannot recover from
short-term key compromise, though a new session can be
re-established if long term keys remain secure [15]. The
capability to recover from a short-term key compromise
without the need to re-establish a new session is called
post-compromise security (PCS) [16], and it is a desirable
quality and is often present in long-term, continuously
evolving session protocols where a session might last years.
Such protocols are termed continuous key agreement (CKA)
protocols.
CKA protocols operate through periodic refresh of keying
material within the context of the session, breaking the entire
session into segments called epochs that represent individual
cryptographic states. CKA protocols are also known as
ratcheted key exchange protocols [15]. Well designed CKA
protocols offer PCS as well as an additional property called
forward secrecy (FS), which is the quality of past messages
being secure in the event of a compromise [17]. CKA is
the cornerstone of modern group messaging protocols, with
ongoing improvements and research since its inception [15],
[18]–[25]. Some CKAs are also making advances in PQC
capabilities [26], [27]. One existing CKA protocol relevant
to this work is the Messaging Layer Security (MLS) protocol
[28], which will be discussed in depth in Section III.
III. Preliminaries, MLS, and Post-Quantum
MLS
MLS [28] is a communications protocol designed to facilitate
group CKA to achieve secure scalable group messaging. It
performs CKA for group members during a session by
generating a shared secret with input from all members
and uses that to seed its key schedule. MLS is organized
according to groups and epochs, with the group being a
“logical collection of clients that share a common secret
value at any given time” [28], and epochs being the time
segments during which the group’s CKA remains on a
particular shared secret. The epoch is advanced periodically
according to application security requirements, or when
group membership changes.
MLS builds on the CKA concepts established in the Signal
protocol for ratcheting to support more two parties. This is
achieved through a tree-based Key Encapsulation Mechanism

(KEM) structure [29]. Group members are assigned to leaf
nodes within the tree structure, each of which holds a public
key and a view of the keys that lead to the root. Updates to
the tree thus require only log(N) update messages, rather
than N messages [28], and the synchronicity is unnecessary
because members can independently arrive at the shared
secret at the root of the tree without requiring input from
any other members.
The addition of the commit secret prevents former mem-
bers or attackers who hold the previous epoch secret from
learning the current secret, and newly added members lack
the previous epoch secret, which ensures post-compromise
security and forward secrecy respectively. The epoch secret
is then used to generate a tree of secret values corresponding
to the ratchet tree, such that each member has a secret for
use with the current group and epoch.
The ratchet tree structure used by MLS makes scalability
far more efficient, as group size scales the computational
efforts of deriving and updating shared keys scale logarith-
mically instead of the linear scaling that other prominent
strategies such as Signal face [28].
A. PQC in MLS
MLS uses several cryptographic mechanisms to achieve
its security goals, with the most relevant to this work being
Hybrid Public Key Encryption (HPKE). HPKE is a scheme
that combines asymmetric and symmetric key cryptography
to securely generate and exchange symmetric keys, utilizing
an asymmetric Key Encapsulation Mechanism (KEM), an
Authenticated Encryption with Additional Data (AEAD)
algorithm, and a Key Derivation Function (KDF).
1) KEM in HPKE: The KEM is the core algorithm for
HPKE. The following provides the KEM Definition 1 and
the associated correctness Definition 2.
Definition 1 (Key Encapsulation Mechanism (KEM) [30]) .
A KEM is a triple
(KGen, Encap, Decap):
• KGen(1κ)→ (pk, sk): On input security parameter κ
return key pair pk, sk (probabilistic algorithm),
• Encap (pk)→ (C, K): On input pk return ciphertext C
∈ C and key K ∈ κ (probabilistic algorithm).
• Decap(sk,C)→ K/⊥: On input sk and ciphertext C
return key K∈ κ or rejection⊥ /∈ κ (deterministic
algorithm).
Definition 2 (KEM Correctness [30]) . We say a KEM is
(1− δ) correct, if for every key pair (pk, sk)← $KGen(1κ)
and every encapsulation (C, K)← $Encap (pk) we have:
Pr[K′̸= K|K′← Decap(sk,C)]≤ δ.
A KEM is perfectly correct if δ = 0.
The KEM is particularly relevant to this work, as adap-
tation of the HPKE to use a PQC KEM is an intrinsic
component. KEMs consist of three component functions: a
key generation function, an encapsulation function, and a
decapsulation function. These functions are used to send
a symmetric key between communication partners using
asymmetric cryptography. The generation function creates a
public/private key pair for the recipient, and the encapsulation
provides a shared secret key to the sender and a copy of
the shared secret within an encrypted ciphertext that can be
safely transmitted to the receiver. The receiver then uses
their private key to decapsulate the ciphertext and obtain
the same shared secret as the sender.
KEMs make use of public-key cryptography and HPKE
in particular currently makes use of Diffie-Hellman-based
KEMs (DHKEM) [31], all of which are elliptic-curve
variants. The result of this dependency is that HPKE and
any protocols utilizing it are not quantum-safe currently, but
could in theory be made quantum safe through use of a
PQC KEM.
PQC KEMs are a growing subject of research, with the
ML-KEM standard at the forefront amid other PQC and
hybrid algorithms [32], [33], [34]. A PQC cipher suite for
MLS must consist of an HPKE component that uses a
PQC KEM, and optionally can include a digital signature
component that uses a PQC digital signature. Neither MLS
nor OpenMLS currently support any form of PQC cipher
suite, which necessitated the implementation of at least one
new cipher suite.
B. PQC MLS
Much like the efforts for other CKA protocols, research is
moving to add PQC security to MLS. In order to achieve this,
a PQC KEM must be used by the HPKE implementation to
gain confidentiality during key exchange.
1) Simple PQC MLS: HPKE is specified to accept new
KEM constructions given that they satisfy its security
requirements [31], which means utilizing a PQC KEM within
HPKE is dependent on implementation and requires no
changes to the HPKE protocol itself to lend it PQC security.
However, an addition is required specifically to allow Kyber,
the predecessor to ML-KEM that was used for this work,
to interface fully with HPKE. Kyber lacks a DeriveKeyPair
functionality unlike the DH-based KEMs specified by HPKE
[31], which prevents it from accepting an Input Keying
Material (IKM) value to generate its keys as in DHKEM,
making the drop-in replacement of Kyber for DHKEM not
entirely straightforward. Thus an additional step is used to
take the IKM value as an random number generator (RNG)
seed and passing that to Kyber’s KeyGen function, which
successfully incorporates the IKM into Kyber and allows
it to meet the specifications of the HPKE DeriveKeyPair
function. While this does not represent a modification to
HPKE as a protocol nor to Kyber as an algorithm, it was a
necessary addition to allow the two to be integrated together.
The simplest configuration is thus to incorporate a PQC

4
KEM into HPKE and use it with a new MLS cipher suite.
This PQC KEM could be either hybrid, such as X-Wing
[33], [35], or pure, such as ML-KEM [1] depending on the
security and performance needs of the application.
The issue with simple PQC solutions is that the PQC KEM
is in use for all key establishment and update operations.
This means that while PQC security is present, the high
overhead cost of PQC algorithms is incurred with every
operation [3] – this applies to both use of ML-KEM and
hybrid cipher suites like X-Wing. Thus the APQC-MLS
Combiner seeks to strike a balance between performance
and PQC security by combining a PQC MLS session with a
traditional session in a way that can spread out the overhead
of PQC key updates.
C. APQC-MLS Combiner
The APQC-MLS Combiner [3] is a draft RFC that
defines a protocol for achieving post-quantum security while
lessening the performance costs incurred by PQC KEMs. It
proposes to achieve this through a protocol-level combination
of traditional and post-quantum cryptography.
The APQC-MLS design dictates that for a given group of
users who seek to form a group, two MLS sessions must be
run in parallel. The group construction of the two sessions
must have identical membership, while one session utilizes
a traditional cipher suite and the other uses a post-quantum
cipher suite. The APQC-MLS Combiner draft notes that
there are two degrees of PQC security that can be achieved
with the protocol, depending on the mode of operation. The
mode relevant to this work is the Post-Quantum/Traditional
(PQ/T) Confidentiality Only mode which only requires a
PQC KEM for the PQC MLS session [3] and aims to provide
protections against harvest-now-decrypt-later attacks, but not
quantum impersonation. The PQ/T Confidentiality Only
mode uses the PQC KEM to provide confidentiality against
a Cryptographically-Relevant Quantum Computer (CRQC)
by securing the all asymmetric key exchange between clients
in a group. It also provides, as the APQC-MLS draft RFC
states, PQC authenticity against group outsiders due to the
inclusion of PQC keying material in the key schedule and
use of AEAD ciphers [3].
The other mode, PQ/T Confidentiality + Authenticity
mode, adds PQC authenticity to the Confidentiality Only
mode via use of PQC signatures on key updates in the PQC
session. This adds overhead to the operation of the PQC
session but blocks the potential for a quantum impersonation
attack on the key updates [3].
The APQC-MLS Combiner creates a cryptographic tie
between the PQC group and the traditional group in order to
take advantage of the traditional cipher suite’s performance
for the majority of the group’s messages and Updates
and using the PQC group to export a PQ-generated secret,
which is integrated into the traditional group as a pre-
shared key (PSK) Proposal. This injection of PQC security
gives the traditional session PQC protection that persists
across Updates within the traditional session, and can be
applied as often as desired by the application utilizing
it. The only requirements for frequency in applying a
PQC Update through use of such an exporter key into
the traditional session are for changes in membership. This
is because membership changes require the formation of a
new cryptographic state for the group to keep past epochs
confidential to members of those epochs only. By only
performing the PQC computations for changes of group
membership and an application-set frequency relative to
the desired security level, the group’s operations are PQC-
secured without the performance cost of regular PQC key
updates. Note that increasing PQC Update frequency does
not necessarily imply a proportional increase in PQC security.
PQC keying material lifetimes are a deciding factor in the
PQC security level achieved in both sessions and more
frequent PQC key refresh does not always introduce practical
security changes.
The APQC-MLS Combiner uses specific terminology to
describe the two different forms of “ Updates” used in its
operation. A Full Update is an Update to the PQC group,
the export of a new PQC secret, and the secret entering the
traditional group’s key schedule as a PSK. The Commit
itself, which is a protocol message sent to all members of the
group, informs the member of the change and prompts them
to proceed into the next epoch, so a Full Update results in
both groups advancing to a new epoch. A Partial Commit
occurs when the traditional group advances to a new epoch
without the PQC group doing so, which is only allowed
when there are no changes in membership.
The APQC-MLS Combiner is a flexible protocol. The
degree of PQC security and performance cost are variably
determined by the frequency of Full Updates performed
during the session, which gives a great degree of control to
the application in terms of the exact trade-off that is achieved.
Three frequencies are measured in this work to establish a
baseline understanding, but applications are by no means
bound to those parameters in their own implementations.

A. Experiment 1
Experiment 1 seeks to present three key metrics which
serve as the basis of comparison for the long-term perfor-
mance of APQC-MLS against MLS using a PQC cipher
suite. Those metrics are:
• Execution time
• CPU cycles consumed
• Control Message sizes
Time-based performance data (execution time and CPU
cycles) was gathered using the Rust benchmarking library
criterion.rs [38]. This library is a powerful tool that provides
rigorous and statistically significant performance data. It
accomplishes this by running each benchmarked function
100 times after a 3-second warm-up interval during which
the function is executed several times to warm up the
machine’s caches so as to provide a consistent level of
performance across the 100 samples. It also explicitly blocks
compiler optimizations to ensure that the entirety of the
function is executed during each sample, using a black box
function on all parameters to the function being measured.
A complication from using the Rust implementation and
criterion to measure the simulations was that every session
was freshly initiated for the simulation. Since CKAs only
perform initiation once, including for potentially multi-year
sessions, session initiation is not a realistic measure for the
steady-state operation of the protocol. Thus, in practice
the computation needed by an individual client during
normal operation is far smaller than the simulations represent.
Execution time is used as a measurable representation of
the total computational work required to simulate an entire
group’s operations.
Epochs: The first controlled variable was the number of
epochs iterated for each group simulation, set at 500 epochs
as the constant total epoch iterations for each simulation. This
was chosen as being a large enough number to expect the
results distinguish minor differences between the different
configurations. Consequently, 100 samples of 500 epochs
each were calculated for the time-based measurements.
For the message size measurements, a single run of the
simulation code was executed. Statistical analysis was
unnecessary for message size capture, as the messages are
consistently the same size for a given set of simulation
parameters.
Message Types: The second controlled variable was the
types of messages in use. The setup of the group includes a
one-time Add operation which creates a Welcome message,
and sustained operations only utilized the self Update, which
replaces a single user’s keys within the key management
tree [28], and the pre-shared key Proposal message, which
was necessary for each Full Update within the context of

Group Size: Capturing the performance trends across
group sizes requires sufficient data points. Group size, as
measured by total number of members, directly affects the
number of times a particular message must be processed
in the simulation. Any crossover point between group size
and protocol configuration at which one is only better than
the other for a certain range of group sizes is a notable
consideration for performance optimization in practice.
Patterning from [37], the tests started with group sizes of 2,
3, 4, and 5. To more quickly scale the data up to a higher
magnitude, the following intervals were used for group size:
10, 15, 20, 25, 30, 35, 40, 45, 50, 60, 70, 80, 90, 100. These
intervals serve to establish the trend of computational effort
and message sizes required to operate a group within each
protocol configuration. All tests were performed using these
group size intervals.

B. Experiment 2 – In-Session Cycles
The goal of Experiment 2 is to assess the CPU cycles
per epoch on average for each configuration once running.
Experiment 1 included calculations for session initiation;
however, under a CKA the session is initiated once and
run long-term (even spanning network disconnections), as
opposed to session-based protocols like TLS where session
re-initiation occurs on a regular basis. Thus, Experiment 2
seeks to capture the CPU cycle differences under normal
use. It closely follows Experiment 1 in most respects, with
the following changes.
A new benchmark was written to gather the data. To
measure the average runtime and therefore the CPU cycles
consumed on average per-epoch in session for of each
protocol configuration, the new benchmark was designed

7
to allow for the session instantiation to occur outside of
the measurement window. As with the previous runtime
measurements, this benchmark used Criterion to measure
the execution 100 times following a 3-second cache warm-up
period. The benchmark was set to measure three functions:
• Execution of a single epoch of traditional MLS with
the traditional cipher suite. The single epoch comprised
of the group owner initiating an Update, serializing the
message, committing to the Update, and each client
processing the message.
• Execution of a single epoch of traditional MLS with
the PQC cipher suite. The single epoch operations were
identical to those described for the traditional cipher
suite.
• Execution of a single Full Update in the context of
an APQC-MLS session. This consisted of the PQC
group performing an Update exactly as described
in the two functions above, exporting a PSK to the
traditional group, and the traditional group proposing
and then committing to the Update containing the PSK
Proposal.
The measurement of these three functions allows us to
represent the average cycles required for a given epoch in-
session, on average for 500-epoch simulations. The average
value across the 100 Criterion iterations provides the
expected time and thus CPU cycles required to execute
Traditional and PQC Updates directly. For the APQC
configurations this cannot be done directly because an epoch
for APQC-MLS requires different operations depending on
whether it is advanced by a Full Update or a Partial Update
and therefore an average is required. An average APQC-
MLS epoch’s execution can be calculated as the average of
the cycles for the Full Updates (PQC plus Traditional) and
Partial Updates (Traditional only) that take place across
the 500-epoch simulation. Note that the code to simulate
a Partial Update is identical to the code that updates
the Traditional configuration, so the data collected for that
configuration can be used for the calculations of the APQC
configurations. To calculate the estimate for APQC-100, an
average over 5 Full Updates and 495 Partial Updates were
calculated. For APQC-50, an average over 10 Full Updates
and 490 Partial Updates were calculated, and for APQC-10
an average over 50 Full Updates and 450 Partial Updates
were calculated.
C. Abstractions and Limitations
Several abstractions were taken in the design and im-
plementation of the MLS group simulation with which the
performance data was measured. The first was the group
construction itself, which was all performed on a single
machine using a single Rust source file. The computational
work of instantiating each client and storing its group data, as
well as the processing of each message, was also performed
within the same source file. The development was absent of
any threading or parallel processing, much like the design
of Lenz’s tests [37]. This abstraction was taken to reduce
code complexity to fit within the scope of feasibility for this
work, so the understanding that the simulations handle all
events sequentially for each client must be acknowledged
when interpreting the results.
Network simulation was deemed out of scope for the work
as well, so there was no simulation of the transportation
of network traffic, thus the code only goes as far as the
serialization of messages in preparation to be transmitted,
treating them as though transmission time was instantaneous.
Finally, the APQC-MLS draft RFC [3] denotes a require-
ment for an extension to MLS that must be supported
for correct operation, adding a specialized data structure
to ensure the groups are synchronized. Implementing this
extension into the simulation was not feasible for the scoping
and timeline for this work, so while it is a necessary element
for practical implementations of APQC-MLS it was not
present in the simulations. The data structure incorporated
into MLS by APQC-MLS is unlikely to noticeably impact
computation time.
Possible confounding variables include the computational
noise introduced by the background operations of a standard
windows 10 machine. The machine was chosen to provide a
realistic environment under which MLS might be employed,
and as such there were consistently background applications
in operation during the simulation runs, and it is impossible
to consider the impact of those background applications to
be consistent nor negligible.
An additional confounding factor to consider is the
construction of the group simulation functions in Rust. The
implementation structure for the fully traditional and fully
post-quantum simulations is inherently different from that
of APQC-MLS, as that protocol introduces the need for two
concurrent groups with a cross-group interaction, none of
which occurs in the MLS-only simulations. A more accurate
comparison might be found by considering the computational
time required only to iterate the group(s) through 500 epochs
after setup is complete, but it was not possible to implement
such a measurement using Criterion.

VI. Conclusions and Recommendations
This work showed that the APQC-MLS Combiner can
achieve a scalable trade off between the performance of
traditional MLS and the PQC security offered by using a
PQC cipher suite on MLS. The data supports that for groups
between 2 and 100 members (the tested parameters), the
computational work required to start and maintain an MLS
group under the APQC-MLS Combiner protocol is less than
that of starting and maintaining an MLS group using a post-
quantum cipher suite with equivalent FS epochs, largely by
a margin of 30-50 percent. It also supports the advantages of
APQC-MLS in the contexts of CPU cycle consumption per
epoch by margins of primarily 30-45 percent, and control
message size requirements by margins of 68-80 percent.
Implementers can expect advantages across all group sizes,
with the flexibility of adjusting the Full Update frequency to
meet PQC security needs without sacrificing computational
and data transmission efficiency. These conclusions support
the viability of achieving efficient post-quantum secure
communications.
